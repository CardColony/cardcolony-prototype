# 鼠标卡顿诊断报告 — 2026-10-30（最终结论）

**结论一句话**：**这是远程会话（远控）本身的问题，不是本机硬件、不是本机资源、也不是 USB/驱动。**

用户 2026-10-30 10:56 明确说明「**我在远程**」——用户是通过远控客户端操作这台机器的。
决定性证据与之吻合：低层鼠标钩子（`WH_MOUSE_LL`）抓到的输入事件 **全部带 `LLMHF_INJECTED`（flags=1）**，
即**光标是远控客户端用 `mouse_event()` 注入的，不是本机鼠标硬件产生的**。
同一台机、同一只鼠标，09:5x 的捕获里 flags 还是 0（真实硬件），11:1x 变成 1（注入）——
**变的是"谁在动光标"，不是本机的状态**。

三个现象由此统一解释：
- **光标跳着走 / 乱飘 / 不受控制** = 远控注入的位置更新有延迟/被合并（远端丢包或客户端节流）
- **点不上** = 点击按注入时的坐标落点，与用户看到的画面脱节
- **任务管理器置于最前台就正常** = 本机被逼着持续 present，远程画面流才有新帧；
  没有动态窗口时流会停更，看起来就是光标卡住
- **Edge 同时卡死** = 本机 Edge 48 进程 / 19 标签页 + 3840×2560，核显抓屏+编码扛不住，整条流一起顿

**因此本机的资源、显存、驱动、鼠标硬件全部无辜**：物理内存剩 30GB、GPU 引擎利用率 6.7%、
显存预算 32.5GB 用 1.87GB、无 TDR、`WH_MOUSE_LL` 实测报告间隔中位 15.9ms/p90 17.6ms。

> 下方 §一~§三 保留了排查过程中的实测数据与已被推翻的中间假设，作为过程记录；
> **§四 的修复仍然有效且对远程场景有利**，§五 的方法论教训同样适用。


> 本报告经过 3 次自我修正：
> ① 早期把「接收器从 USB 总线消失」当故障 → 实际是用户自己拔插
> ② 早期把「WorkBuddy AI 国际版」当元凶 → 实际是症状载体，被待机搞挂的那个
> ③ 早期把「S0 现代待机」当根因 → 实际只是**触发器**（46 次待机只坏 1 次）
> ④ 早期称 GameViewer 虚拟显示器驱动「永久损坏」 → 实际 GameViewer 启动后能正常加载

## 一、三个因素是乘法关系，不是二选一

### ① 共享内存 / 显存（主因，已实测）

```
GPU Process Memory(pid_2148 = dwm.exe):
    Total Committed = 3,241 MB     ← 合成器独占 3.24 GB 显存承诺
    Shared Usage    = 1,878 MB     ← 其中 1.88GB 是"借走"的系统内存
GPU Adapter Memory: dedicated usage = 1,869 MB   ← 核显从系统内存划走了 1.87GB
下一个最大的: pid_8428 (MiniMax Code GPU 进程) 388MB
GPU Engine 利用率 = 6.7%（GPU 本身没在忙）

dwm.exe 进程态: Commit=2.31GB  WS=1927MB  Private=2370MB  Threads=61  Handles=3100
```

**Radeon 780M 是核显，没有独立显存——它的"显存"就是系统内存。**
dwm 独自把 1.87GB 系统内存划成了显存。**dwm 是光标的绘制者**：
分配失败 → 无法 present → 光标不更新（卡住/跳格）→ 点击落不到你看到的位置。
所有 Chromium 应用共用同一份 GPU 显存预算 → **Edge 与 WorkBuddy AI 一起卡死**。

### ② 系统内存压力（放大器，已实测）

```
09:03:39 / 09:11:53 / 09:23:39 / 09:27:22 / 09:30:03
   Resource-Exhaustion-Detector 2004: low virtual memory condition
   python.exe 预留 28.9 / 28.9 / 28.9 / 28.9 / 29.8 GB
09:12:01  WerSvc: The paging file is too small for this operation to complete
09:30:20  Connected User Experiences and Telemetry 服务意外终止
09:30:25  Microsoft Defender 防病毒网络检查服务意外终止
```

分页文件原本固定 **8 GB** ⇒ commit 上限只有 **47.83 GB**。
服务在故障那一分钟成片终止 ⇒ dwm 拿不到显存的"最后稻草"。

### ③ 现代待机（触发器，不是根因）

```
Kernel-Power 506: 09:28:18  entering Modern Standby (Idle Timeout)
Kernel-Power 507: 09:31:42  exiting  Modern Standby (Input Keyboard)
Display 4107: SetDisplayConfig() 调用方指定了 SDC_FORCE_MODE_ENUMERATION
             （强制重枚举显示模式）10/27、10/28 各两次
```

这台机**只支持 S0 现代待机** ⇒ **"关屏" = 进待机**。
唤醒时的显示拓扑强制重枚举，会让 dwm 为新的显示目标**再叠一层 surface** —— 这是 3.24GB 的累积来源。
**但 7 天 46 次待机只坏了 1 次 ⇒ 它是触发器，不是根因。**

### ④ 累积状态的来源：dwm 的显示目标过多

```
✔ WSM2820 / BBC0105 / RTK2271     三块物理屏，全部 Active
✔ GameViewer Virtual Display Adapter: 3840x2160@60Hz  ← 虚拟屏也是 4K
✘ DISPLAY\DELD0E6 (S2719DGF)      Present=False  ← 幽灵
✘ DISPLAY\DEFAULT_MONITOR         Present=False  ← 幽灵
注册表 Control\Video 下 2 条 GameViewer 虚拟适配器条目:
   {74D64A6C-D3FD-11F1-BC9F-010101010000}
   {B4A33E91-2763-11F1-BC67-90DE805197AE}
dwm 线程: 60 个在等，其中 43 个 WaitReason=Unknown（正常 10-20 线程）
Kernel-PnP 219: \Driver\WUDFRd failed to load, ROOT\DISPLAY\0000, 0xC0000365
             （10/24、10/26、09:00:01、09:01:38 —— 每次开机）
```

### 现象逐条对应

| 现象 | 机理 |
|---|---|
| 光标跳着走 | dwm 欠帧，积压的位置一次性应用 |
| 不受控制 | 光标位置与真实输入脱钩（输入本身是干净的，见下） |
| 点不上 | 看到的是旧帧，点击落在旧光标处 |
| Edge 一起卡死 | 共用同一份显存预算的 GPU 进程一起要不到显存 |
| **任务管理器置顶就正常** | **强制一次 present**，dwm 把欠的那一帧补上 |
| WorkBuddy AI 一起卡 | 同上；它的 renderer 日志 09:30:03–09:30:52 停写，是**被待机切换搞挂的**，不是它搞挂别人 |

### 排除项（都有实测数据）

| 嫌疑 | 实测 | 判定 |
|---|---|---|
| 射频/接收器/USB 丢包 | **`WH_MOUSE_LL` 低层钩子：报告间隔中位 15.9ms、p90 17.6ms** | 排除（输入链路无辜） |
| 系统资源不足 | CPU 5%、内存剩 30.6G、DPC 0.2%、队列 0 | 排除（故障时刻除外） |
| 指针速度设置 | MouseSpeed=1、阈值 6/10、曲线标准 | 排除 |
| 第三方鼠标驱动劫持 | Mouse/HID/USB 类 Upper+LowerFilters **全空**，接收器用微软原版 `mouhid` | 排除 |
| 按键/修饰键卡死 | 601 次采样 LMB/RMB/Shift/Ctrl/Alt **按下次数全 0** | 排除 |
| 远控注入抢鼠标 | GameViewerService 空转、sunshine 无客户端、无远控会话 | 排除 |
| WiFi 抢占 2.4G | WiFi 在 5GHz/48 信道 | 排除 |

| # | 修复 | 验证 | 备注 |

## 三、待执行（按性价比排序）

1. **重启一次** —— dwm 那 3.24GB 显存承诺 / 61 线程 / 3100 句柄是**累积状态，只有重启能清**；
   同时让分页文件的新配置生效。
2. **清掉两个幽灵监视器**：设备管理器 → 显示监视器 → 卸载 `Generic Monitor (S2719DGF)` 与 `Generic Monitor`（Present=False）。
3. **关掉用不到的屏**（3 物理 + 1 虚拟 = 4 个显示目标）→ dwm 的 surface 与显存直接下降。

   （Run 项 `GameViewer -> "D:\uu\GameViewer\GameViewer.exe" --auto-run`）与 `GameViewerService` 的 Automatic。
5. **给网易报 bug**：4.44 升级包仍带 `2026-02-28, 15.6.5.199` 的 IddDriver；开机时 `WUDFRd failed to load 0xC0000365`，
   但 GameViewer 启动后又能正常加载 —— **IddCx 驱动在 app 接管前存在时序竞态**。
6. **查 dwm 为什么 61 线程**（正常 10-20，43 个 WaitReason=Unknown）。

## 四、顺带发现（与本故障无关，但该处理）

- **`C:\ProgramData\PveScreen\pve_health_check.py` 明文存放 PVE 主机 root 密码**
  （`HOST=192.168.9.188 / USER=root / PASS=...`）→ 改用 SSH 密钥或凭据管理。
- **`pve_screen.exe` 每 10 秒往串口屏刷一帧，且持有设备句柄、会拦截设备移除**
  （Kernel-PnP 225）⇒ `pnputil /restart-device` 对鼠标所在集线器 `USB\VID_05E3&PID_0610\6&3878ef1f&0&2` 会被拒。
- **`sunshine` 以 Automatic 常驻并监听 `0.0.0.0:47989`（对外可达）**。
- `USB\VID_0000&PID_0002`（Fosi Audio SK02）长期 Code 43 枚举失败。
- Realtek 蓝牙适配器每次开机报 `BTHUSB 18`（无法存储 link key）。
- `Pool Nonpaged Bytes = 1028 MB`（40GB 机器上偏高，典型 100-400MB）→ 内核池泄漏的嫌疑，值得跟踪。
- 国内版 `WorkBuddy.exe` 的 GPU 进程 **133 线程 / 4879 句柄**，异常（正常 30-40 / 1200）。

## 五、方法论备忘

- **「谁和谁一起卡」比「谁卡了」信息量大**：Edge 与 WorkBuddy AI 一起卡 ⇒ 共享 GPU/显存预算 ⇒ 不是单个 app 的锅。
- **物理层结论必须用独立于窗口消息泵的仪器测**（`WH_MOUSE_LL` / Raw Input）；
  用 `GetCursorPos` 轮询会把「用户没在动鼠标」误读成「断流」（本次犯过）。
- **事件日志要按 provider 逐类扫**：Kernel-Power 506/507（待机）和 Kernel-PnP 219（驱动加载失败）
  都不在我最初筛的 provider 里，漏了两轮才找到。
- **改动硬件/服务状态后要恢复**；改系统级设置（如分页文件）要**读注册表确认真正落盘**——
  本次 `New-CimInstance Win32_PageFileSetting` 没能写进 `PagingFiles`，差点让下次重启变成"无分页文件"。
- **设备在诊断期间"自己消失"时，先确认是不是用户刚做过物理操作**，再谈故障归因。
