================================================================================
日期：2026-10-21　分支：5713　worktree：D:\AI_station\推演agent\.worktrees\5713

一、缺陷（旧态，可核对）
--------------------------------------------------------------------------------
1. 旧基线 verify/5713/baseline_known_red.json 的 command_scope.cmd[0] 是
       D:\AI_station\写作agent\.venv\Scripts\python.exe        ← 隔壁项目的 venv
2. 旧 baseline_diff.py 的 DEFAULT_CMD = [sys.executable, "-m", "pytest", ...]
   而工具环境下 sys.executable 实测就是上面那个「写作agent」的 python。
3. 旧基线原样留档（不覆盖、不删）：
       verify/5713/baseline_known_red.json.bak-badvenv-20261021T000331
   它就是「这份基线是在错误 venv 下采的」这一事实的证据。
4. 后果：基线绑的不是「本项目的命令作用域」，而是「谁的 python 启动了这个工具」。
   换机器 / 换启动方式，同一 HEAD 同一命令也会漂 —— 裁决 A7 的「命令作用域」当时是假的。

二、修法（verify/5713/baseline_diff.py，行号以本提交为准）
--------------------------------------------------------------------------------
  L65   _venv_python_under(base)     base 下有 .venv 就返回其解释器（先 Scripts/python.exe，后 bin/python）
  L74   _main_repo_root(cwd)         主仓根 = git rev-parse --git-common-dir 的父目录（worktree 下也指回主仓）
  L95   _bounded_ancestors(start)    从本文件位置向上找，**截到主仓根为止**：宁可回退也不越界去捡别的项目的 venv
  L109  resolve_project_python()     返回 (解释器, 来源说明, 项目根)；找不到 ⇒ 回退 sys.executable
  L123  PROJECT_PYTHON / PROJECT_PYTHON_SOURCE / PROJECT_VENV_ROOT
  L124  DEFAULT_CMD = [str(PROJECT_PYTHON), "-m", "pytest", "tests", "-q", "--junitxml={xml}"]
  L244  interpreter_source(exe)      打印与基线共用同一个判据（不会「打印说 A、基线记 B」）
  L260  announce_interpreter()       每次开跑先打**完整绝对路径**＋来源；回退时打醒目警告
  L521  main() 调用它 —— --collect 与跑闸两条路径都会打出这一行

  钉法的三条约束都落在代码里：
  · **不硬编码项目名**：路径只由 __file__ 位置与「.venv 这一目录约定」推导，全程没有项目名字面量
    （B-03「路径无单一注入点」正在修，不能反手新增一处硬编码债）；
  · **回退必须留痕**：找不到 .venv ⇒ 回退 sys.executable，打
    「警告：未找到项目 venv，改用 sys.executable，结果可能不可复现」，
    并把同一句话写进基线 command_scope.note（新基线另有 interpreter_source / project_venv_root 两个字段）；
  · **打印不许再缩写**：旧打印把解释器缩成 ``python``（两个项目各有一个 python，等于没说），
    现在打完整路径。
