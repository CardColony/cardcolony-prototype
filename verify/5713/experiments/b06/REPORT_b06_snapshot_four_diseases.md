## 2 四病逐条实测

### 病1 全量拷贝无锁（`data_snapshot.py:267` `_SNAPSHOT_LOCK`；`:324` 全量拷贝循环）

- **锁只管快照之间，不管写入方**。`_SNAPSHOT_LOCK` 只串行化"快照 vs 快照"；
  `card_store`/`shadow_store`/`work_store` 走的是 `data_snapshot.schedule(...)`，**不参与任何锁**。
- **T6 跨文件不是同一时点**（沙箱里一个写入线程持续"先写库、再原子替换 canvas.json"，同时连拍 4 张）：
  - 3 张一致（db=k, canvas=k-1，与"先库后 canvas"的写序相容）；
  - **1 张不一致：db=25 / canvas=20**（`coherent_pair:false`）⇒ 这一批**不是任何一个时刻的真实状态**；
  - 同轮还抓到一条副产品：快照把写入方的临时文件 `works/work_conc/canvas.json.tmp` 也列进受保护集合，
    走到拷贝时它已被 `os.replace` 挪走 ⇒ `FileNotFoundError` 记进 `failed` 清单（不致命，但说明
    枚举集合和"完整文件"不是一回事）。
- **T7 撕裂（产品同款写盘模式）**：`canvas.json` 在产品里由 `canvas_store.py:598` **原地 `write_text`**（非原子，
  先截断再写）。用同款写法持续重写 1.5MB 内容 + 连拍 6 张 ⇒ **4/6 张批次里的 `canvas.json` 是撕裂的**
  （3 张 1,048,576 字节处截断、1 张 0 字节），另有 2 张抓到 `missing-file`。
- **T10 撕裂批次的后果（真删真恢复）**：取一张撕裂批次 —— 活文件此时 1,500,030 字节，
  删掉后从该批恢复 ⇒ 恢复**成功**（`ok:true`），**数据根里被种下一个 0 字节、JSON 不可解析的 canvas.json**。
  恢复层不校验内容、不校验大小，撕裂批次照单收货。
- **T8 全量代价**：400 文件 / 48,600,000 字节的一批 —— 每批 `batch_bytes == source_bytes`
  （整份复制，无增量、无硬链接），单批 **0.69 / 0.72 秒**（冷启首批 4.84 秒）。
  与 `KEEP_BATCHES=200`（`data_snapshot.py:40`）相乘 ⇒ **单 work 最高约 200 倍数据量**。
  生产快照根现况（只读盘点）：**49,491 文件 / 5,018.7 MB / 24 个 work 目录**。
- **为什么病1 的杀伤面比字面小**：`*.db` 走 `VACUUM INTO` 一致副本（T1：批内库 `integrity=ok`、行数相等；
  T3：恢复后库各表行数与恢复前**逐字相同**）；`memory`（`memory_store.py:226-227`）、
  `session`（`session_facade.py:216/230`）都是 `tmp+os.replace` 原子写。
  ⇒ 撕裂真正落在**非原子写的派生文件**（canvas.json，可由 cards.db 重建）与**只追加流的尾部**，
  不是用户的会话正文与卡片库。

### 病2 返回路径不一致（`data_snapshot.py:368` `"dir": str(SNAPSHOT_ROOT / stamp)`；`:70` `_batch_dir`）

- **T2**：`snapshot_sync` 返回的 `dir = SNAPSHOT_ROOT/<stamp>` —— **`returned_exists=false`（恒不存在）**；
  真实批次在 `SNAPSHOT_ROOT/<work_id>/<stamp>`（`actual_exists=true`），`same=false`。
  只拍一个 work 时**缺了 work 层**；拍全部时返回**单个** dir 而实际产出多个 work 的批次
  （`work_id: "work_b06,work_b06_other"`）⇒ 从语义上就不可能是真路径。
- 今天谁在替它兜：`tests/test_snapshot_roundtrip.py:22-25` 自己注释了这处不一致，只取 `Path(dir).name` 当 stamp。
  对外（UI/脚本/迁移）**没有任何调用点能靠 `dir` 找到批次**。

### 病3 指纹去重跳过显式快照（`data_snapshot.py:231` 指纹 = 路径+大小+**整秒 mtime**；`:317` 相同即跳过）

- **T5（真删真恢复）**：`doc.md` 写 A（4096 字节）→ 拍一张；改成同长度 B 并 `utime` 设回**同一整秒 mtime**
  → 调 `snapshot_sync("显式快照：改前保险")` ⇒ **`skipped=true`、`files=0`、批次数 2→2（没产新批次）**；
  然后**真删**该文件 → 从最新批次恢复 ⇒ **拿到的是 A**（`restored_content_is_new_B=false`），
  且 B 在**所有批次里命中 0 次**（`new_content_in_any_batch=false`）⇒ **B 永久丢失，任何回退都救不回来**。
- **T6 旁证**：并发写场景下同一秒内的状态变化被判为"内容未变"，**整次快照直接跳过**
  （上一轮跑出现过 `skipped=true, files=0, batch missing`）。指纹的整秒粒度会让高频写窗口整体蒸发。
- 危害形态：用户明确要"改前保险"这张快照，系统回 `ok:true` 但什么都没拍 —— **成功回执掩盖了空动作**。

### 病4 restore 落点易写平行树（`restore_from_snapshot.py:25` `BASE_DIR=脚本目录`；`:27` **硬编码** `"推演agent_data_snapshots"`；`:69` `dst = BASE_DIR / rel`）

- **T9（真跑仓库自带 CLI，cwd=`...\.worktrees\5713`）**：
  - `--list` 打印 `...\.worktrees\推演agent_data_snapshots`（**该目录原本不存在**）；
    而库按实例名派生的应是 `...\.worktrees\5713_data_snapshots` ⇒ **`same_root=false`**，两个推导源。
  - `--file` 恢复返回 **`ok:true`**，文件落在 `...\.worktrees\5713\works\work_b06probe\session_001.md`（**平行树**）；
    活实例 `D:\AI_station\推演agent\works\...` **完全没动**（探针目录不存在）。
    ⇒ 用户以为"救回来了"，实际活数据一个字没变 —— **比失败更坏**。
  - 探针痕迹已清理并核对：硬编码根已删、平行树已删、活实例无残留（`T9_cleanup` 三项全 true）。
- **T9b 跨实例口径**：库里按 `BASE_DIR.name` 派生（`data_snapshot.py:34`），CLI 恒指 `推演agent_data_snapshots`。
  盘上现存的快照根有 4 个（`推演agent_data_snapshots`、`推演agent_test_data_snapshots`、
  `推演agent-5705_data_snapshots`、`_tooltest_20261012_data_snapshots`）
  ⇒ **任何非正式实例跑 CLI，读的是正式实例的快照库，写的是自己的根**（跨实例污染入口）。

## 3 能证明的 / 证明不了的

**能证明（本轮实测）**
- **能存**（T1）：12 个受保护文件（含 `cards.db`）一批落盘，非库文件 **sha256 逐个一致**，
  批内库 `integrity=ok`、三张表行数与源相同；一批总字节 43,722 = 源总字节（当批完整）。
- **能恢复**（T3/T4）：整目录 `rmtree` 后 `restore_batch` → **12/12 文件全回**、非库 sha 全一致、
  库 facts（integrity + 表清单 + 行数）与删除前**逐字相同**；单文件恢复（会话 md 4613 字节）sha 一致。
- **前提必须写进裁决**：恢复要"能"，必须 (a) 走库函数、(b) `SNAPSHOT_ROOT`/`BASE_DIR` 显式给定。
  默认派生 + 自带 CLI 走的是病4 的平行树路径（T9）。

**证明不了（不得当结论）**
1. **生产活进程内的真实并发撕裂/跨文件不一致**：T6/T7 是沙箱内"产品同款写盘模式"的复现，
   证明**机制存在且可复现**，不等于生产上已经发生过；生产上 cards.db 有一致副本保护、memory/session 原子写，
   撕裂面只剩 canvas.json（派生）与事件尾部。
2. **`KEEP_BATCHES=200` 真实触发时的修剪行为**：未触发（生产 `_ops` 199 批未越界）；
   "高频 work 回退窗口≈1 小时"沿用 card_009 的 P12，我**本轮未复现**。
3. **恢复与并发写的竞态**（恢复进行中又有写入）：未测。
4. **热恢复后内存态**（画布缓存 / goal driver / 事件读取位点）是否必须重启：未测。
5. **快照侧撞锁重试预算**：本轮只见到写方自己撞锁（`writer_errors=2`），没把快照侧重试打满。

## 4 修序与理由（建议进《5713 下一批修复方案裁决》）

### P0 · 病3（指纹去重跳过显式快照）—— 先修
- **理由**：四病里唯一"静默 + 永久 + 无法回退"的数据丢失路径（T5：新内容在所有批次里 0 命中）；
  且修面最小、可独立验收，不牵动写路径。
- **落点**：`data_snapshot.py:231/317`。
- **修法（二选一，建议都做）**：① **显式快照必须绕过去重**（手工/CLI/迁移脚本/改前保险一类调用，
  语义上就是"我要一个还原点"，跳过即违约）；② 指纹从"路径+大小+整秒 mtime"换成**内容哈希**下限兜底。
- **验收判据（可直接复用 T5 当回归）**：同尺寸改写 + 同整秒 mtime → 显式快照**必须产新批次**，
  且从该批恢复**拿得到新内容**；反向断言"新内容在所有批次里命中 ≥1"。

### P1 · 病2 ＋ 病4 同批修 —— 同一条缝
- **理由**：两病共用一个根因——**快照根/批次路径有两个各自独立的推导源**
  （库按 `BASE_DIR.name` 派生；CLI 硬编码名 + 脚本目录），而 `snapshot_sync` 返回的 `dir` 又恰是不存在的那一个。
  分开修只会得到"报错对但落点仍错"或反之。它们是"恢复到一处**不是**活数据根的地方却回 ok"的直接成因，
  失败形态比报错更危险（T9）。
- **落点**：`data_snapshot.py:368`＋`restore_from_snapshot.py:25/27/69`。
- **修法**：① 返回**真实批次**（或 `{root, work_id, stamp}` 列表，拍全部时逐批给）；
  ② CLI 不再自算根，直接 import 库的 `SNAPSHOT_ROOT`/`restore_*`；
  ③ 恢复落点必须**显式给 target**（缺省=实例 `BASE_DIR`），写前校验 target 落在实例数据根内，
  否则**拒绝**并要求 `--force`；④ 恢复层加内容完整性校验（尺寸/可解析性），撕裂或 0 字节直接报失败。
- **验收判据**：用 `snapshot_sync` 返回值**能直接**恢复同一批；在 worktree 里跑 CLI 恢复必须**落到实例根或被拒**
  （复现 T9 即为用例）；恢复 0 字节/不可解析文件必须报失败（复现 T10）。

### P2 · 病1（全量拷贝无锁）—— 最后，但拆两步、顺序写死
- **理由**：这是**最贵的架构改动**，而数据安全伤害已被现有两道保护挤到最小
  （db 走 `VACUUM INTO`、memory/session 原子写），真正的痛点是**成本**（T8：48.6MB 全量复制 0.69s／批；
  生产快照根已 5.0GB／49,491 文件，×200 上限）。
- **第一步（便宜、先做，可与 P1 同批）——原子写＋一致性标记**：
  ① `canvas_store.py:598` 改 `tmp+os.replace`（与 memory/session 同款）；快照枚举时排除 `*.tmp`；
  ② 批次里记一致性标记（每批记 `cards.db` 的 rev 与快照起止时刻），非一致批次在 manifest 里**显式标注**，
  恢复前告警。**验收**：并发写下批内各文件版本号一致或显式标注（复用 T6）；
  任意批次恢复后不出现 0 字节/不可解析文件（复用 T7/T10）。
- **第二步（贵、后做）——增量＋写方协调**：manifest + 只拷变更文件/未变文件硬链接；
  与写方约定"只拷完整文件"（写侧原子写是前提）。**验收**：单批耗时不随数据总量线性增长
  （基线：48.6MB/400 文件 0.69–0.72 秒），且 `batch_bytes < source_bytes`。
- **禁止**：把"增量＋加锁"当一条一次做完（B-06 台账原口径）。先做增量＝先动最贵的部分、且不解决撕裂。

## 5 与另两域的接缝（须在唯一裁决里对齐，避免两处各写一份）

1. **架构域 B-03「路径单一注入点」**：病2/病4 的"根有两个推导源"本质是 B-03 在快照子系统的实例。
   建议裁决明确：**路径单源归 B-03**，B-06 这边只做**语义修复**（返回真实路径、落点校验、CLI 不再自算根），
   不新增第三份路径逻辑。若 B-03 先落地，病4 自然减半。
2. **测试域（B-01 类）**：病1 的回归红线需要"并发写 + 快照"的沙箱夹具（写入线程 + 原子写，
   如本目录 `b06_probe.py` 的 T6/T7 做法）。测试域不提供夹具，这条红线就只能靠人工复跑。
3. **恢复入口不是 UI 功能**：目前实例 openapi 66 条路径里没有读快照的恢复入口（card_009 P-serial 已列）。
   病4 修完之前**不应**把快照恢复挂到 UI ——否则"ok 但恢复进平行树"会直接暴露给用户。

## 6 残留与如实标注（本轮发现、建议入清单，不在本卡修）

  与"只拷完整文件"的第一步同批做。

- 整批恢复**只补不删**（非时间点回滚）：本轮未复测（T3 是整目录删除后恢复，不涉及该情形）。
