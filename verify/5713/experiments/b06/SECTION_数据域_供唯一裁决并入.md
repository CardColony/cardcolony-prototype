# 数据域（card_015 · B-06 快照四病）

## 一句话
四病**先修病3**（指纹去重跳过显式快照）；**病2＋病4 同批**修（同一根因：快照根/批次路径两个推导源）；**病1 最后且拆两步**。
另并入一条由质量域移交、经本域复核为**真坏**的条目：**病4b 恢复回执不诚实**（`ok=True` 但 stale WAL 重放，未真正回滚）。

## 能证明的（每条都有证据编号，证据在 `verify/5713/experiments/b06/`）

| 判定 | 证据 | 内容 |
|---|---|---|
| 能存 | T1 | 12 个受保护文件一批落盘，非库文件 sha256 逐个一致；批内 `cards.db` integrity=ok、表行数与源相同；批总字节 43,722 = 源总字节 |
| 能恢复（**限非 WAL/无旁挂**） | T3/T4 | 整目录 rmtree 后 `restore_batch` → 12/12 全回、非库 sha 全一致、库 facts 逐字相同；单文件恢复 sha 一致 |

**前提必须写进裁决**：恢复走库函数且 `SNAPSHOT_ROOT`/`BASE_DIR` 显式给定；默认派生＋自带 CLI 会落进平行树（T9）。

## 证明不了的（不得当结论）
生产活进程内的真实并发撕裂/跨文件不一致（T6/T7 是沙箱内产品同款写盘模式的机制复现，非生产已发生）；
`KEEP_BATCHES=200` 真实触发时的修剪；恢复与并发写竞态；热恢复后内存态是否需重启；快照侧撞锁重试预算打满。

## 四病修序与落点

### P0 · 病3 指纹去重跳过显式快照（`data_snapshot.py:231/317`）
- **为什么第一**：四病里唯一「静默＋永久＋无法回退」的数据丢失路径。T5：同尺寸改写＋同整秒 mtime →
  显式快照 `skipped=true, files=0`、批次 2→2；真删后恢复拿到改前内容，**新内容在所有批次命中 0**。
- **修法**：① 显式快照（人工/CLI/迁移/改前保险）**绕过去重**；② 指纹由「路径+大小+整秒 mtime」换**内容哈希**兜底。
- **验收**：同尺寸改写＋同整秒 mtime → 显式快照必须产新批次，且从该批恢复拿到新内容（现成 T5 即回归用例）。

### P1 · 病2＋病4＋病4b 同批（同一条缝）
- **病2**（`data_snapshot.py:368`）：返回的 `dir` 恒不存在（缺 work 层；拍全部时只给单个 dir）。
- **病4**（`restore_from_snapshot.py:25/27/69`）：CLI 硬编码 `推演agent_data_snapshots`＋脚本目录自算根；
  T9 真跑恢复回 `ok=True` 却写进 `.worktrees\5713\works\` 平行树、活实例零改动；盘上 4 个 `*_data_snapshots` 根 ⇒ 跨实例读错库。
- **病4b（新）**：见上表 R10 行；`data_snapshot.py:467-476` 把「删不掉 `-wal`/`-shm`」降级成 warning 后照发 `ok=True`（锚点含 `:467 copy2` 与 `:476 return {"ok": True}` —— 「真写了／清不掉只 warning／照样回 ok」三段同属一个缺陷）。
- **修法**：① 返回**真实批次**（或逐批给 `{root, work_id, stamp}`）；② CLI 不再自算根，直接用库常量与库函数；
  ③ 恢复落点显式给 target，写前校验落在实例数据根内，否则拒绝；④**恢复 db 改用 SQLite backup API 反向导入**
  （`src.backup(dst)` + `wal_checkpoint(TRUNCATE)`，实测绿；不依赖任何句柄状态），文件级替换只能当兜底且删不走即 `ok=False`；
  ⑤ 恢复后做内容校验（rev/行数与快照不符即 `ok=False`）。
- **验收**：用 `snapshot_sync` 返回值能直接恢复同一批；worktree 里跑 CLI 恢复必须落实例根或被拒（复现 T9 即用例）；
  **WAL 下 `card_store.read_card` 必须读回快照态**（复现 R10 即用例，即 `test_snapshot_restore_roundtrip` 转绿）。

### P2 · 病1 全量拷贝无锁 —— 拆两步，顺序写死
- **为什么最后**：最贵的架构改动，而数据安全伤害已被两道保护挤小（db 走 `VACUUM INTO`；memory/session 走 `tmp+os.replace`）。
  撕裂只落在非原子写的派生文件：T7 六拍四张撕裂（1,048,576B 截断或 0 字节）；T10 从撕裂批恢复把 0 字节文件种回数据根
  （活文件原 1,500,030B）；T6 并发下 1 批 db=25/canvas=20 非任何时刻真实态。
- **真痛点是成本**：T8 400 文件/48.6MB 每批全量复制 0.69–0.72s（冷启 4.84s）；生产快照根已 **49,491 文件 / 5,018.7 MB / 24 个 work**。
- **第一步（便宜，可与 P1 同批）**：`canvas_store.py:598` 改 `tmp+os.replace`；枚举排除 `*.tmp`；批次记一致性标记（rev＋起止时刻），
  非一致批次在 manifest 显式标注、恢复前告警。
- **第二步（贵，后做）**：manifest + 只拷变更/未变文件硬链接 + 与写方约定「只拷完整文件」。验收：单批耗时不随总量线性增长、`batch_bytes < source_bytes`。
- **禁止**：按台账原口径把「增量＋加锁」当一条一次做完。

1. **架构域 B-03**：病2/病4 的「根有两个推导源」是 B-03 在快照子系统的实例。建议裁决写明**路径单源归 B-03**，
   数据域只做语义修复（返回真实批次、落点校验、CLI 不自算根），不新增第三份路径逻辑。
2. **质量域（card_016）**：R10 那条已由本域定性为**真坏**（不是断言滞后、不是噪声），请在基线重生时把它从
   known-red 噪声类改标为「真坏·待修·归 P1」；`test_snapshot_restore_roundtrip` 的断言**正确，不改**。
3. **恢复入口不是 UI 功能**：病4/病4b 修完之前不应把快照恢复挂到 UI —— 否则「ok 但没生效/恢复进平行树」会直接暴露给用户。
