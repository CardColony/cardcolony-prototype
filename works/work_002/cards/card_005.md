# 影子卡机制（需求定义）

**状态：只在定义需求，未实现。** 代码、存储结构、接口均未落地。本轮定的是「记什么 + 怎么更新」。定义人：用户。

## 一、要解决什么
正卡（工作卡）推进过程中会产生大量过程性信息：进度、产物位置、迭代与改动。这些不该塞进正卡正文（正卡要干净、给人看），但也不该丢。影子卡 = 挂在正卡旁边、只服务于「追踪」的一张附卡。

## 二、记录什么（本轮确认三条）
1. **进度更新** —— 正卡走到哪一步了，时间线形态：什么时候、发生了什么变化。
2. **产物清单** —— 正卡项目的文档、代码库文件的「信息 + 路径」：是什么、在哪、干什么用。是指路牌，不是文件内容本身。
3. **迭代历史 / 更改记录** —— 改了什么、为什么改、改前改后（与本项目已有的 git 自动提交通道存在重叠，见 Q6）。

## 三、更新与推送
- 影子卡由正卡的活动驱动更新（触发方式待定，见 Q3）。
- 影子卡的更新要向**上级卡推送**：上级卡能直接感知下级动态，不必逐卡去翻。推送的粒度、频次、载体（写入上级卡正文／上级卡附属字段／仅提示）待定。

## 四、必须解决的冲突（重要）
本项目现有设计哲学明写「拉取不推送」「组装中性上下文时不推正文」。影子卡的「推送」语义与此直接相撞。两条路，先选一条：
- **A 保留「推」**：把上级卡设为唯一例外，接受「拉取不推送」被打破。
- **B 改写语义**：所谓「推送」实为「上级卡拉取时能一次性拿到下级影子卡摘要」，推变聚合成可拉取视图，原则不破。

## 五、待决问题（未定）

- Q2 一正卡对一影子卡，还是按主题分 N 张？多张正卡能否共用一个？
- Q3 谁写？自动（正卡写入或 git 提交时钩住）／模型／人？
- Q4 影子卡自己进不进对话上下文？进的话如何与「中性上下文不推正文」共存？
- Q5 能否删除、能否有子卡？（牵涉 delete_card 的「有子卡不可删」规则）
- Q6 与已有 git 通道的关系：git log 已是更改记录，影子卡是二次加工还是索引层？
- Q7 「上级卡」是直接父卡，还是沿树一路上溯／由根卡汇总？
