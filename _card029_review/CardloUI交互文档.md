## 一、页面结构与信息层级

### 1.1 主界面三区布局（建议）

Cardlo 主界面在既有旧形态（批C §一 P1 画布页 / P2 对话页）基础上重构为**三区 + 两个顶层视图**，对齐旧系统已具备的面（画布、对话、规则面板、通知、项目动态）：

| 区 | 承载内容 | 对齐旧系统 |
|---|---|---|
| **左导航栏** | 树 / 搜索 / 新建 / 最近访问 / 通知入口 / 模型设置（详见 §二） | 批C P1 `nav.app-nav.rail` 与 P2 同构左栏 |
| **中央主区（双视图）** | 「画布视图」与「对话视图」二选一切换 | 画布＝批C P1 `#viewport`；对话＝批C P2 `#chatArea` |
| **右侧面板** | 卡详情（Inspector）＋ 规则面板双态 | 批C P1 右列 `.rule-panel`＋`#cardDetail`；P2 `.inspector`＋`.rule-panel` |
| **全局通知层** | toast / 通知面板 / 项目动态抽屉 / 异常清单（见专章 §四） | 批C P1 `#notifyPanel`/`#activityDrawer`/`#toastContainer` |

**共享导航**：两个视图共用同一左导航栏与顶栏，视图间切换**不重建导航、不丢失导航展开态/搜索框焦点/已读角标**。此设计对齐旧系统现状（P1/P2 左栏同构 `#navRailBtn`/`#navNotify`/`#navTree`），但在新系统必须解决旧系统「两页各持一套导航状态」的断层（见 fn_007 请求①：状态断层未入复盘范围）。

**视图切换语义**：「画布」看整体拓扑＋并发状态；「对话」进入单卡/单会话深读与干预。二者是同一棵卡的两种观察尺度，不是两个产品——因此**导航、右侧面板、全局通知三者跨视图共享**，只有中央渲染区域随视图切换。

### 1.2 「画布」与「对话」视图

- **画布视图**（默认）：
  - 展示卡树空间（父子关系线 `#edgesSvg`、通信线独立层 `#commSvg`）；
  - 卡片面显示状态徽标（queued/working/blocked/stalled/需决策/done/error，见专章 R9/R10）；
  - 头部聚合视图（服务端算好的状态分桶计数＋异常清单，见 R10）；
  - 可选中卡就地展开对话（批C P1「卡片就地展开对话」）、并行对话层（批C P1 `#watchLayer`）、钉住窗（`#cvDock`）。
- **对话视图**：
  - 单卡对话流（输入卡＋排队条＋模型徽标，批C P2 全套）；
  - 右栏 Inspector（使命/现状/需求文档/关系/历史/自动模式/角色台账）；
  - 过程细节折叠、主题切换（批C P2 `#procToggleBtn`/`#themeToggleBtn`）。

### 1.3 首屏与画布主视图硬指标（建议）

对标旧系统实测基线与耦合病灶，给出**口径明确的首屏与 bundle 硬指标**（理由均【本仓·实测/可核实】；口径按 D06⑤ 补齐四项）：

**四项口径（每一项都是可直接在 P1 写成断言的判定基准）：**
1. **首屏**＝首帧 HTML ＋ 首帧渲染完毕后同步加载的区块（全局 graph 交错加载首包，不含按需/懒加载部分）。
2. **计量单位**＝**wire bytes（传输层，含 gzip/br 压缩后实际下发字节）**，非源码体积。
3. **冷缓存条件**＝无 localStorage、无 Service Worker 预载、清空 HTTP cache 后的首次加载。
4. **层预算表**（按层一步步加起来的 budget，总包不超下列合计；每层可直接在 P1 写成断言，含改前旧系统对照值）：

| 层 | 预算（wire bytes） | 改前对照（旧系统，全部无压缩） | 含哪些文件（示例清单） | 对齐/理由 |
|---|---|---|---|---|
| 壳（导航/框架） | ≤40KB | — | `nav` 骨架、顶栏、共享导航、全局主题 | 左栏＋顶栏＋共享骨架 |
| 画布 | ≤150KB | `canvas.js` 392,967 B | 画布渲染/交互/状态徽标/聚合视图 | 画布视图渲染/交互 |
| 对话 | ≤80KB | — | 对话流、输入卡、Inspector、逐字流渲染 | 对话流/输入/Inspector |
| HTML 首帧 | ≤20KB | 旧首帧 HTML `work.html` 197 行/`card.html` 273 行 | 首帧 HTML 骨架 | 首帧 HTML wire 字节 |
| 规则面板 / 设置 | 按需加载 ≤60KB | — | 规则面板、设置页（不进首屏） | 不进首屏，进入再拉 |
| **首屏 wire 总预算** | **≤150KB 压缩 / ≤450KB 未压缩** | 旧系统首屏 **801,122 B 无压缩** | 壳+画布+对话+首帧合计 | 未压缩按常规 gzip/br 约 3:1 反推 |

> **改前→改后对照断言（每项可直接在 P1 写成断言）**：旧系统首屏 **801,122 B 无压缩**（【本仓·实测】card_002 基线：首屏 801,122 B、canvas.js 392,967 B，均无 gzip/br）→ 新首屏 wire **≤150KB 压缩 / ≤450KB 未压缩**；画布主视图 `canvas.js` **392,967 B 无压缩**（耦合导航/渲染/交互/存储四责）→ 拆分后单块 **≤120KB wire / 分块 ≥4**。

- **bundle 分块 ≥4 块，单块 ≤120KB wire**（对应上表壳/画布/对话/HTML 分层，探索再附规则/设置按需块）。反对旧系统把导航/渲染/交互/存储四责耦合进单一巨型 bundle：旧系统 `canvas.js` 392,967 B 单文件兼四责（【本仓·实测】card_002 基线；批C `static/canvas.js` 7250 行、`workspace.js` 2709 行承担多重职责）——耦合证据，新系统必须拆。

> 口径说明：旧系统首屏 801,112 B 且无 gzip/br（【本仓·实测】card_002 基线；批C P4 静态资源无压缩）。首屏 total 预算 ≤150KB wire（压缩）是为抵消旧系统无压缩 801KB 而定的设计目标与验收口径，理由＝旧基线折半再考虑压缩收益；属设计目标【推断·假设】、【**此 150KB 数值待 P2 实测校准，不得作为验收依据**】，须在 P1 实测兑现。

## 三、四条主流程界面走法（D04 产品核心闭环）

四条主流程＝D04 定义的产品核心闭环，每条给「进入状态 / 可逆操作 / 失败态 / 恢复动作」。这四条是 UI 文档主轴，其中「观察」必须正面承载并发可视化专章（§四）的核心地位。

### ① 发起（建项目 → 建卡 → 派活/对话 → 自动模式开关）

| 环节 | 进入状态 | 可逆操作 | 失败态 | 恢复动作 |
|---|---|---|---|---|
| 建项目 | 从首页「创建」/左栏「＋新项目」进入草稿页（对齐旧系统 `home.js:29-36` 跳 `/work/draft`） | 草稿态零网络可改可弃（批C O8：`enterDraftProjectPage` 零网络出画面） | 落库失败 | 失败 notify「建卡失败（可重试）」（批C O7：`workspace.js:475`），保留草稿不丢 |
| 建卡 | 画布右键/顶栏「新建」→ 确认制弹窗（见 §五） | 建卡走创建确认制；建成后可拖拽重挂（批C P1 `canvas.js:2419`）、改名 | 空标题拦截（批C `canvas.js:5191`） | 重新输入合法标题 |
| 派活/对话 | 选中卡进对话视图，输入区发送指令；可走自动模式目标驱动 | 输入可编辑/撤销重做/排队（批C P2 `queue-dock.js`/`input-bar.js`） | 忙时 Enter 策略（批C `submission-policy.js` queue/steer） | 插话/停止（见 §三③） |
| 自动模式开关 | 卡右侧 Inspector「自动模式」开关（批C P2）；开启后目标驱动自动续轮（批B 主题1 F-059~F-063） | 可随时关（手动停止须同时停当前轮＋关自动继续＋级联停自动子卡，批B 自动模式-方案:69-76） | 自动续轮失败/死锁 | 手动停止（释放执行锁），改目标重开 |

**并发可视化衔接**：发起成立后进入「观察」即看到该卡及其子树状态进入事件流（见专章）。

### ② 观察（画布 / 导航 / 状态可视化 —— 并发可视化的核心承载）

| 环节 | 进入状态 | 可逆操作 | 失败态 | 恢复动作 |
|---|---|---|---|---|
| 画布总览 | 画布视图，卡面状态徽标＋顶部聚合统计（服务端算好，见 R10） | 缩放/平移/框选/整理布局（批C canvas 全套） | 聚合视图加载失败 | 降级：仅显示本地缓存状态＋「重试」；事件流恢复即自动更新 |
| 导航监控 | 左栏树行尾状态点＋通知未读 | 展开/折叠 | 版本探测失败 | 断流兜底（见 §六） |
| 并发状态可视化 | 分层视图：概览计数 → 分组(异常清单) → 单卡下钻 → 会话（见专章 §四） | 状态永远可回溯到真实事件（R11） | 事件流拥塞 | 自动切稀疏视图（R12，只显示异常+需决策者） |

**观察环节的核心地位（D04 显式要求）**：并发可视化的分层视图是「观察」的第一屏，观察者第一眼看到的应是**状态分桶计数＋异常清单**（谁在跑、谁卡住、谁需决策），而不是 N 行同名卡列表。这正是 fn_007 请求②「多 agent 实时状态可视化缺席」的正面回应。

### ③ 干预（插话 / 停止 / 恢复 / 消息编辑重发 / 自动续轮拉起）

**排程字段与心跳戳（承接 D06 与根卡心跳定义）**：每张卡保留 `blocked_on` 排程字段（二值 `in_llm_wait` / `in_tool_call`）＋ 最后心跳时间戳；`turn_in_flight` 用**三值** `none` / `held_live` / `held_stale`（非布尔）。

**「一次心跳」的唯一定义（按 card_001 根卡权威定义；修与 R11 的自相矛盾）**：
> **心跳＝LLM 流式响应的每一个帧**（`content_chunk` / `reasoning_chunk` 逐字/逐 token 流），**不是「轮」、不是卡自己写的状态字段**。具体落在事件流哪类事件 / 哪张表，P1 写死。
> 依据＝旧系统 `progress.py` `heartbeat()` 注释原文「逐字流每帧调用：仍在吐字的超长请求因此持续被判定为『仍在推进』」【本仓·可核实，progress.py heartbeat()】。

- **由 runner（观测者侧执行体）记录，卡自身无法写入**——天然满足 R11「不能被观测方自证存活」（否决被观测方自报存活）。
- **解除 stalled 只认 runner 记录的流式帧**；卡的 self-reported「我在跑」不作为解除依据。判定源＝runner 帧记录，否定「被观测方自我证明存活」。
- 与旧 D06① 表述的关系：D06 曾以「服务端账本进展型事件 run_start/round_start/deliver/tool_result/turn_end」为心跳，根卡权威定义将其细化为**流式响应的逐帧**——以次 token 级帧为心跳粒度（比「轮」级进展事件更密、更真实反映「正在吐字」）；二者都属「服务端落账非自报」的同一方向，根卡定义把判定粒度收敛到帧。

**stalled 判定（按根卡权威定义 一句话规则）**：
> **working 的 stalled ＝「runner 记录 >30s 无该卡流式帧，且该卡当前不处于 `in_llm_wait` / `in_tool_call` 任一在途阻塞态」。**

**`blocked_on` 在途阻塞豁免（防误报）**：runner 维护每卡 `blocked_on` 排程态，二值之一＝`in_llm_wait`（LLM 调用 in-flight，含首 token 前等待）或 `in_tool_call`（工具 call_id 已发起未回）。**当卡处于 `in_llm_wait` 或 `in_tool_call` 时，不启动 stalled 计时**——在该阶段无流式帧是预期内、属正常 working。仅当卡无在途阻塞（排程判定「应自主推进但 runner 无新帧 >30s」）才计时→stalled。

- 阈值具体值（【推断·假设】**此值待 P2 实测校准，不得作为验收依据**）：**runner 记录 >30s 无流式帧 且 不在在途阻塞** ⇒ 标 stalled。

> **★ 阈值校准豁免（单独成段，D16 要求）**：心跳 30s 的**阈值数值**待校准（如上标死），但「**阈值对齐帧间隔而非轮时长**」这个**方向不是假设**——它有实测支撑（004 帧间隔分布 p10/p50/p90＝0.089/0.456/1.682s ⇒ 单轮 674/132/36s【本仓·可核实】）。若把整句标成「待校准」，P2 极可能把方向一并改回「对齐轮」，即回到「既误报又漏报」。故：数值待校准、方向有实测背书，二者分开标注。
- **阈值对齐帧间隔，不对齐轮时长**：正常流式输出帧间隔秒级 ⇒ **>30s 无帧即判 stalled**，判定与轮时长（旧系统 3–11 分钟）完全解耦。理由（【本仓·可核实】）＝004 实测帧间隔分布 p10/p50/p90＝0.089/0.456/1.682s ⇒ 单轮 674s/132s/36s【本仓·可核实】；**若阈值对齐轮时长，必然既误报又漏报**——长回复拉长轮时长而误判正常，短回复压短轮时长而漏判挂死。故阈值锚定帧间隔而非轮时长。
- **心跳状态必须持久化**：旧系统 `progress.py` 单进程内存态、重启即清空 ⇒ 重启后「谁在跑」全部归零，只解了一半【本仓·可核实】。新系统心跳落**持久化存储**，重启后可重建。
- 效果：长静默＝LLM 首 token 前 / 工具调用中（`blocked_on` 在途）**不**被误标（属正常 working）；真挂死（批B B-14 工具循环挂起，阻塞非预期或无流式帧）**被**标；且因判定源是 runner 帧记录，**否定「被观测方自证存活」**（按根卡权威定义）。

| S4 `yielded` 让位等子卡 | **是**（让位≠卡死） | 「等子卡」（独立可视） | **无归属**（v1 断态） | **归 working 桶**（理由见下） | 否（但「等子卡」独立可辨识） |
| S5 `stopping` 中止链在途 | 否 | 「正在停止」（有终点、可观测） | **无归属**（v1 断态） | **单独不入六桶，独立计 stopping 数**（理由见下） | 否（异常清单会标「正在停止」过渡态） |
| S6 `stopped` | 否 | 按 `stop_requested.reason` 分立（§六 reason 处置） | `blocked/done/error` 三合一 | **done 桶**（终态归 done；`error` 非态，是「上一回合异常结束」展示属性，可从 done 明细下钻看 error） | 否（reason 可下钻） |
| working 派生（S3 held_stale 帧超时）＝**stalled** | — | 「疑似卡住·待回收」/「卡住·已回收」 | `stalled` 派生态 | **stalled 桶**（派生自 working，不再计 working） | **是**（卡住三档） |
| blocked 具名子类＝**需决策** | — | 「需决策」（等人工决策） | `blocked` | **blocked 桶**（含需决策） | **是**（需决策） |

> 桶归属判定（**我自己判，给 P2 待裁核对**）：
> - **`yielded` 归 working 桶**：`yielded` 是活跃卡且是「自主推进中让位等子卡」——本质仍在「跑」（父卡 wait 在 P1-2 回合内仍在途），若单列一桶会导致「活跃工作卡」计数与 P1-2 活跃率口径（S2/S3/S4 都活跃）对不上；且 `yielded` 一错聚合计数全错（D16 断层①）。故计 **working 桶**，但「等子卡」状态须**独立可辨识**，不得与 S3 `running` 混同视觉。
> - **`stopping` 单独不入六桶**：`stopping` 是**非活跃**的过渡态（中止链在途、有终点、可观测），不属于任何终态桶的「结果」——其消费的是「停了一半」的中间态，若计 done 假完成、计 working 假进行。故**单列 `stopping` 计数**（不算入 done/working 任一桶），与 done 桶并列显示一个独立数。
> - 两处判定**无重复计数、每桶口径可判**；因涉及「P1-2 六态 × 六桶」的映射是需求侧口径决定，非实现细节，我将其列为 **P2 待裁核对项**（见 §六）。

> 映射要点：**stalled＝working 的派生态**（底层态仍是 S3 running、流式帧超时在展示层派生 stalled，故 stalled **计入 stalled 桶、不计 working 桶**）；**需决策＝blocked 具名子类**（不单独占底层态）；**`yielded` 计 working 桶**、**`stopping` 独立计数不入六桶**（判定见上）；**`error` 不是态**，是「上一回合异常结束」的展示属性，终态统一归 done 桶、可从 done 明细下钻看 error。P1-2 六态一一映射、无交叉重复计数。

- 异常清单：只列「需决策 / 卡住（stalled 三档）/ 错误（error 展示属性）」三类，每项可下钻单卡（D03 R10）。需决策来自 blocked 子类（在 blocked 桶内单列）。
- 分桶计数（R10 六桶＋1 独立数）：`working(含 yielded) / queued / blocked(含需决策) / stalled(派生自 working) / error(展示属性) / done` 各多少，另**单列 `stopping` 独立计数**（非活跃中间过渡态，不入任一终态桶）；桶口径严格对上面 P1-2 六态映射表。

**可检验判据**：聚合视图数据包含 `{buckets:{working:n,queued:n,blocked:n,stalled:n,done:n,stopping:n}, anomalies:[{kind:needs_decision|stalled|error, card_id}]}`；任意状态事件发生后聚合计数在一条事件推送内更新（可测：发出 N 张卡状态事件，断言前端收到一次聚合更新而非 N 次拉取）；stalled 计数与 working 计数互斥、blocked 计数含需决策且异常清单单列需决策项、yielded 计入 working 且独立标「等子卡」、stopping 独立计数（断言无重复计数、口径可判）。

### 4.3 R12 刷新模型（单流订阅驱动全局 + 降级触发可测化）

**一条事件流驱动全局**：所有状态（画布卡面、左栏行尾、聚合计数、异常清单）都由同一条**事件流主体**驱动，杜绝旧系统「8 处轮询各行其是、签名口径一变即失效」的病灶（批C A1–A8 共 8 处发请求轮询，D §A）。

- **工作级事件流** `/events`（对齐旧系统批C B1，但旧系统该流**从未承载未读角标增量**——批C H3：单卡 SSE 订阅时把 card_id 传成 work_id，未读角标增量通道从未活过、只剩 60s 轮询扛；新系统必须在工作级事件流上真正承载未读/状态增量，把 60s 轮询废除）。
- **单卡过程流** `/stream`＋`/tokens`（对齐批C B3/B4）仅在**展开到单卡**时才订阅（下钻模式）。

**分层订阅**：
- 聚合视图层：只订阅工作级聚合事件（服务端算好，R10）。
- 单卡层：**仅展开该卡才下钻**订阅其过程流（D03 R12「仅展开单卡才下钻订阅详情」）。避免旧系统「每张盯的卡各拉一次 / 一张卡占 2 条 SSE，切 3 张占满 6 连局限」（批C H1 连接上限：同域 HTTP/1.1 6 条连接、每卡占 2 条 SSE ⇒ 切 3 张卡占满）。

**稀疏视图降级（D06④：废弃 SSE 丢帧率，改双测量点可测）**：当**活跃卡数超阈值**或**事件流拥塞**时，界面自动切稀疏视图——只显示异常清单（需决策＋卡住＋错误）＋需决策者，隐藏全部正常 working/done 卡，不卡死（D03 R12）。

- **废弃**旧「SSE 丢帧率 20%」：SSE over TCP 无丢弃语义，丢帧率不可作为测量点（D06④）。
- **主选＝服务端降采样标志 `sampled:true`**（测量点＝**服务端**）：
  - 服务端监控**事件产生率**，超阈值（【推断·假设】**此值待 P2 实测校准，不得作为验收依据**：>200 事件/s/工作区）时，聚合端点**停发逐卡详情、只发分桶＋异常清单**，并置 `sampled:true`；前端收到 `sampled:true` 即切稀疏视图。
  - 可检验判据：注入事件产生率 >200/s 场景，断言聚合响应带 `sampled:true`、前端切稀疏；事件率回落 <200/s 且持续 30s 回完整视图（**回落时长 30s 亦待 P2 校准**）。
- **备选＝客户端渲染队列滞留时长**（测量点＝**客户端**）：前端渲染队列**首事件滞留 >2s**（【推断·假设】**此值待 P2 实测校准，不得作为验收依据**）时切稀疏视图（可测：注入滞留时延断言切换）。
- **活跃卡数阈值**（【推断·假设】**此值待 P2 实测校准，不得作为验收依据**）：**活跃卡数（口径＝P1-2 六态：S2 `runnable` / S3 `running` / S4 `yielded` 为活跃，S1/S5/S6 非活跃——见 §4.1 活跃卡定义）** **≥ 50** 时主动退到稀疏视图做首屏；再按需展开。理由：50 卡是旧系统从未在真实量级触碰过的门槛（D02 治理边界：不还原旧实现的量级上限）；并参考量级档（50–200／名义 100，见 card_003 结论【本仓·可核实】）。**注意**：若把 S4 `yielded`（活跃）误判为不活跃或用错活跃口径，稀疏降级触发数与 P1-2 活跃率各自按自己理解算，两个都自称遵守同一句——故此处必须引用 §4.1 的 P1-2 活跃卡定义。

**明文禁止逐卡轮询**：禁止任何「每张卡一个 setInterval 拉状态」形态。在 1Hz 刷新下 100 卡需 100 req/s，而旧系统单进程串行 ≈3.8 请求/秒（【本仓·实测推导】card_002），逐卡轮询即 **26 倍**超载——逐卡轮询形态在新系统直接判不可行。

### 4.4 R11 诚实回执（可证伪 → 可回溯到真实事件）

任何显示为「成功 / 进行中」的状态必须**可证伪**——能回溯到一条真实事件，**禁乐观假信号**（D03 R11）。

旧系统乐观假信号证据（全部【本仓·可核实】）：
- **WAL 指纹失灵**（批B 主题5）：SQLite WAL 模式写入落 cards.db-wal、主文件 mtime 不变 → 指纹不变 → 前端以为「没变」不刷新。【修法：meta 表维护单调递增 rev 做指纹】
- **快照恢复假 ok**（批B 主题5 病4b）：WAL 下直接复制 cards.db 拿不到最新提交（须 VACUUM INTO/backup/checkpoint）——若前端据此判「快照已恢复」即假成功。
- **P10 disk-live 同源**（批B 主题13）：disk 与 live 同源，装配器思考建自己的节点、键与 live 相同；刷新后思考流整段挂错位置、长链中间丢失——用户以为 live 显示的思考是真实进程，实则刷新后位置全错。
- **P15 承诺≠结果**（批B 主题13）：链完成判据只认主模型 step_complete 回执，末步由板执行器交掉时主模型只拿幂等回执 → 标志永不置位 → 板全 done 但承诺的三席不触发——「承诺提交了」≠「真的发生了」。
- **批C 乐观渲染 11 处**（O1–O11）：乐观用户气泡、画布乐观运行态（POST 前显示 running）、批量下指令先显示「排队中」、停止过渡态、先出画面数据后到、整理布局本地不回滚、delete 后 notify 撤销、排队中假显示等。核心病灶＝「先显示、后回执」，且部分无真实对账（O9 整理布局失败本地状态不回滚）。

**诚实回执判据（按根卡心跳定义）**：
1. 任何 working/进行中状态必须能点开看到「最后流式帧时间戳＋最近 1 条流式帧内容（content/reasoning 片段）与 seq＋当前 blocked_on（若有）」（可测：显示内容与事件流 seq 对齐）。
2. 任何「成功」回执必须可回溯到服务端真实落库/完成事件（如 run_start/done 帧），禁仅由前端乐观插入驱动。
3. 乐观更新**必须带对账与失败回退**（见 §五）：乐观显示的中间态在真相事件到达时必须被覆盖/回滚，不留假终态。
4. 状态推进不依赖任何本地「看起来在前端运行」的假信号；stalled 判定源＝runner 流式帧记录（持久化，卡无法写入），**否定卡自证存活**（对齐 C5 状态可对账、旧系统 C5 双账）

| 建线 | 从卡 A 拖到卡 B，或卡格菜单「建立通信线 / 建立依赖关联线」；选线类型 | 建线走确认制弹窗（先展示目标卡与线类型，用户确认才建立；对齐批B 主题8 确认制「弹窗本身就是最硬闸」） | 失败给四要素回执（谁 / 向谁 / 哪类线 / 为何拒〔缺哪个开关〕/ 如何放开），对齐 C2 边界机械、批B 主题6 权限底座 |

### 4A.2 R13.2 协作往来可读

**卡间消息按类型聚合**：任一条通信线上流动的卡间消息，按消息注册表类型 **msg_ask / msg_answer / msg_notify**（批B F-035/F-036 卡间通信、消息类型注册表）可按「一对卡」或「一条线」聚合查看——不只散落在各卡对话流。

**聚合视角**：
- **按「一对卡」**：选定 A↔B，看到它们之间全部往来消息（双向、按时间线）。
- **按「一条线」**：选中某通信线，看到该线全部卡间消息流。

**未应答询问（pending）与应答超时显式标记，不得只显示未读角标（对齐 P1-5 口径）**：
- **应答超时按每消息类型**：应答时限**不是全局一个值**，而是引用该消息类型自己的 `reply_timeout_sec`（P1-1 消息事件扩展字段，每消息类型一个）。示例值 60s 仅作【推断·假设】**此值待 P2 实测校准，不得作为验收依据**，不作为通用阈值。
- **未闭环询问数只认 `reply_expected=true`**：通知类消息（`reply_expected=false`）**不产生应答义务**，不计入未闭环询问数（否则重演旧系统「952 封」污染）。一条 msg_ask 且 `reply_expected=true` 发出后尚无 msg_answer 落账（批B 主题2 收件箱演进 unread_by_card）⇒ pending。
- **消息状态机含 `superseded` 态**：P1-5 状态机 `pending→delivered→consumed／superseded`，`superseded`（已取代）态必须补上——一条旧 ask 被新消息取代（consumed_by=supersede）视为「已处置」，不再计入未闭环询问数。**`delivered` 态不可归因**：D113 裁定后投递维度不能作归因（`msg_delivered` 未登记、事件类型唯一真源＝P1-1 冻结 6 类），UI 不得以「已投递」作为应答义务或未读归因依据，只以 `reply_expected` 与 `superseded/consumed` 判定待办与处置。
- 应答超时＝pending 的 ask 超过**其消息类型的 `reply_timeout_sec`** 仍无 answer/superseded ⇒ 显式标记「应答超时」并进协作异常清单，不只角落标。
- 依据（【本仓·可核实】）：旧系统卡间通信「只发不收 952 条」（D113 接受代价：不含投递维度归因）；批C H3 未读角标增量通道从未活过（只剩 60s 轮询扛）——新系统必须以事件流真正承载 pending/超时标记，而非只显示未读角标；批B 主题2 说明收件箱演进已把 status 做成显式。

**可检验判据**：任一线/一对卡可聚合查看卡间消息并按类型过滤；一条 `reply_expected=true` 的 msg_ask 无 msg_answer ⇒ 显式 pending 标记；超过其消息类型 `reply_timeout_sec` ⇒ 显式「应答超时」标记并进异常清单；`reply_expected=false` 的 notify 不计入未闭环询问数；被 `superseded` 取代的 ask 从待办移除（可测：构造无应答 ask 断言 pending→超时；构造替换消息断言 superseded 后进「已处置」）。

### 4A.3 R13.3 协作聚合视图（观察第二屏，与状态桶并列）

**三项计数＋协作异常清单（口径对齐 P1-5）**：
- **协作中关系数**（当前活跃的通信线＋依赖关联线数）
- **未闭环询问数**（pending msg_ask、**仅 `reply_expected=true`** 计数）
- **超时关系数**（应答超时关系数，按每消息类型 `reply_timeout_sec`）
- 协作异常清单：列「未应答询问 / 应答超时 / 待清理悬空线」各卡，每项可下钻。

**口径与 R10 一致**：服务端算好、禁前端拉 N 份再聚合、禁逐卡轮询（对齐 R12 单流订阅驱动）：协作聚合由服务端在事件流落库/推进时算好，前端只订阅聚合结果——**依赖 `reconcile_run`**（服务端周期性/事件驱动的聚合结果落账，前端订阅它，不在前端算；`reconcile_run` 为 card_002 ⑪项 6 类新事件正式名之一）。

> **事件类型封闭（V2 任务六约束）**：本文档任何 UI 状态不得依赖自造事件。协作聚合/协作干预/协作解析均落在 P1-1 冻结 6 类事件（`action_rejected`／`msg_consumed`／`reconcile_run`／`stop_*` 三态／`perm_resolved`／`action_rejected(reason=registry_check)` 子形态）；`registry_check` **不是独立事件类型**，是 `action_rejected` 的 reason 子形态。凡需新增，动作是「改冻结清单」不是「往注册表加一条」。

**观察第二屏与状态桶并列共存**：状态桶（R10/§4.2）首屏、协作聚合（R13.3）作为观察的**并列第二屏**；两者并存而非二选一（D08：不得以状态桶替代）；与 §五「统一消息中心」呼应——消息往来按线/按对卡聚合。

**可检验判据**：协作聚合数据含 `{relation_count, pending_ask_count(仅reply_expected=true), timeout_count, anomalies:[{kind:pending|timeout|orphan_line, card_id/line_id}]}`；由服务端一条事件推送更新（可测：断言一次推送含全部计数）；禁逐卡轮询（引 26 倍实测推导同 R12）；consumed/superseded 的消息不计入 pending/unclosed。

### 4A.4 R13.4 协作级干预

从协作视图可直接发起三类操作，每动作**可回溯到真实事件（R11 诚实回执，禁乐观假信号）**：

| 动作 | 界面走法 | 可回溯到真实事件 |
|---|---|---|
| **解除一条通信线/依赖关联线** | 协作视图选中线 → 「解除此线」，走确认制 | 解除成功以服务端落账确认（对齐批B F-006 unlink_rel 落账）；失败给四要素回执 |
| **停止该协作子树（级联停，继承 C6 中止缝）** | 协作视图选中某协作关系/子树 → 「停止此子树」，级联停止该子树内卡 | 停止级联逐卡落账，显示每卡中止缝（在哪一步停止、进度是否落盘）；对齐 §三③ 单卡停止（停止三件套：停当前轮＋关自动继续＋级联停子卡，批B 自动模式-方案:69-76）与 C6 中止有缝 |
| **向协作对方补发/重发消息** | 协作视图选中未闭环询问 → 「重发/补发」，复用 pair_id（对齐批C P2 `message-actions.js` 重发、workspace.js:1946-1999） | 补发/重发以服务端 msg 落账回执确认；禁前端乐观插入假成功（对齐 R11、批B P14 谎报成功病灶） |

**`stop_*` 三态事件 / 扩 `msg_*` 动作事件（D13 补齐可回溯落点）：每次解线/补发重发落 `msg_*` 动作事件、级联停落 `stop_*` 三态事件，各含 **actor + target + action + 结果**，R11 可回查（对照上文 `reconcile_run`：一个承载聚合结果的只读可订阅，一个承载每次干预动作的可回查记录，二者分层不混；`stop_*` 三态 / 扩 `msg_*` 动作事件为 card_002 ⑪项 6 类新事件正式名族——具体归哪一类由 P1 事件模型最终确认，必须是这几类之一、不得悬空）。

**可检验判据**：从协作视图能发起解除线/停止子树/补发消息三类动作；每动作成功/失败都以服务端真实事件回溯（可测：断言动作后出现对应 `msg_*` 动作事件或 `stop_*` 三态事件，含 actor/target/action/结果 四要素）；级联停逐卡显示中止缝、不产生假信号。

4. **批量操作**：批量删除/批量下指令（批C `batchCommand`）须先展示「将作用于哪些卡」并逐项可退（避免旧系统批量下指令「排队中」假显示与排队超时 10 分钟假消失——批C O4/H16）。
5. **快捷键**：全局 ⌘K 命令面板、Esc 分层关闭、Tab 焦点循环、Shift+Enter 换行（批C P2 theme.js/input-bar.js 全套沿用，统一交互）。

## 六、错误与异常状态呈现

四种错误/异常给出「界面怎么显示」＋「用户可做什么」（对齐 C2 边界机械 / C4 通信可闭环 / C5 状态可对账 / C6 中止有缝 四条涌现目标落到位；成本触线已按 D12 排除预算维度、降为纯 stats 展示入 B-13，不再列为异常，见下表「成本展示」行）：

| 异常 | 界面怎么显示 | 用户可做什么 | 关联涌现目标/证据 |
|---|---|---|---|
| **权限拒绝（四要素回执）** | 拒绝提示必须含四要素：**谁操作、操作什么、为什么拒绝（缺哪个开关）、如何放开**；不静默、不笼统「无权限」 | 按四要素定位权限缺口→联系卡主/改配置；不重复尝试相同操作 | C2 边界机械；批B 主题6 权限底座（默认关门、操作某卡查某卡开关） |
| **消息超时（C4 超时上报）** | 消息发送/工具调用超时须明确显示「超时」而非「成功」，含超时方向（哪一步未回） | 可重发（复用 pair_id）；可插话；可手动停止兜底 | C4 通信可闭环；批B H17（/messages 与 /draft 不设超时，靠单次 recoverIfDone 探测——新系统须给消息建立显式超时上报） |
| **任务刹停（C6 中止缝）** | 停止必须显示「中止缝」（在哪一轮/哪一步停止、进度是否落盘），不假装「已干净停止」 | 确认中止缝后恢复或多轮重试；中断点可续 | C6 中止有缝；批B P15（承诺≠结果）、自动模式手动停止三件套 |
| **对账不一致（C5 状态可对账）** | 乐观态与真相事件不一致时显示「待对账/已回滚」视觉标记，不静默掩盖（引批C H15 事件流断线窗口变化、H2 两套 seq 计数空间） | 可手动强制重拉/重算该卡；可上报对账失败 | C5 状态可对账；批C O1 对账机制、H2 seq 断区 |
| **成本展示（原「成本/配额触线」改判，D12；金额维度彻底排除，D13）** | **成本仅作可观测展示（stats 记录消耗，适用量单位——token 数/轮次数/调用次数，守「不可只看不露」B-13）**；**金额维度彻底排除**（平台费用/￥/$ 永久不进任何界面，用户已三次排除预算）；**无触线告警——用户已排除预算维度（2026-10-22）**；删除原「触线询问续跑」语义与 D06⑥ 的四选一（续跑额度/降档模型/降活跃数/停止）。留痕说明：原「成本/配额触线」异常态因用户排除预算维度而不再为「异常」，仅保留为统计展示；若今后预算维度回归，需重新立项评估是否恢复触线告警（勿自动加回）；金额永久不出现 | 查看各卡 stats 成本展示（哪张卡/哪个额度/token 数/轮次数/调用次数，只展示不告警、不出现金额） | C5 状态可对账、B-13「stats 不可只看不露」 |

**配额档位面板（只读，D13 新增·与成本无关）**：显示当前 **TPM / RPM / 并发数 / 轮次配额** 的「档位 + 占用率（已用/上限）」，数据源＝服务端真实计数。**不告警、不阻断、不询问续跑**，仅作可观测。理由：配额不是钱，是**可用性约束**——超配额会导致调用失败（旧系统 B-16「跑在 429 死 key 上静默运行」即此病【本仓·可核实】）；用户须能看见「我这档够不够、用了几成」。
- **配额超限时的行为**：**调用失败并如实回显错误（含当前档位与占用率）**；**不是**「询问续跑」——续跑与否是钱的问题，钱已排除。用户看到的是「配额满了，等一会儿或提档（提档属平台操作，不在产品内）」。
- 与「成本展示」区分：成本展示=用量单位统计（token/轮次/调用次数，不出现金额）；配额面板=体量可用性档位（TPM/RPM/并发/轮次占用率），二者都只读可观测、都不告警不阻断不询问续跑。

**`stop_requested.reason`（8 值）界面处置（D16 §六 v2 落改）**：终止原因按 8 值区分/合并呈现，用户可行动：

| reason | 用户看到 | 界面处置 |
|---|---|---|
| `user_request` | 「你停的」 | **独立显示**（用户可行动的停止） |
| `card_stuck` | 「卡死了，需介入」 | **独立显示**（需介入）；与 `turn_lease_expired` 在列表层**合并为「卡住」**，账本层分开 |
| `gateway_timeout` | 「端点超时，查端点」 | **独立显示**（查端点） |
| `turn_orphan_reaped`（L2 运维清场） | 「服务重启，已自动清场」 | **与协作失败分视觉**（绝不与「卡住」同色同形） |
| `idle_zero_tool` | 「连续 N 轮无工具调用，自动暂停（保险丝）」 | **分视觉**（非故障） |
| `hard_cap` | 「已达设定上限」 | **分视觉**；同时走 `msg_ask`（问人）需**「等我回答」入口**（可作答），非 stop |
| `cascade` | 「上级停连带停」 | **分视觉** |
| `turn_lease_expired`（L1/L3 回收）→`stop_consumed` | 「卡住·已回收」 | 列表层与 `card_stuck` 合并「卡住」；**账本层必须分开**（两者都进中断率分子，混统计就废） |

- **`repeat_same_action` / `hard_cap` 不走 `stop_*`**：它们是 `msg_ask`（问人、状态不变）⇒ **UI 必须有「等我回答」入口（可作答）**，不能只在异常清单里显示一行字样。这条要落成可检验判据：断言出现 `repeat_same_action`/`hard_cap` 时 UI 提供可作答的「等我回答」入口（而非只显示异常行）。

每种异常都要「可回溯到真实事件」的原则（R11）：显示「出错/超时/中止/不一致」时，用户都能点开看到触发它的那条事件记录，而非只看到一句错误文案。（成本/配额：仅为 stats 展示，不属异常告警，见上「成本展示」行。）
