## 1. 这个产品是什么

### 1.1 你的定义（第一手，2026-10-19 口述）

- **核心不是画布，画布只是入口。**
- 形态：**树形卡片结构，每张卡是一个智能节点，节点之间靠三种线互相连接，形成一张智能节点的网络**。
- 它解决传统 agent 的问题：上下文、过程留痕可追溯、长程任务天然需要的工程与思维拆解。
- 你认为不止于此，所以做**自动模式**：让模型彻底理解这套系统，然后**自行发挥**，期待涌现。

### 1.2 落到代码的形态

| 概念 | 落地 | 语义 |
|---|---|---|
| 卡 | `cards` 表一行 | 一个能自主跑的节点；卡面三块是**卡与卡之间唯一接口** |
| 三块 | `mission` / `status_block` / `rulings` | 使命（只有用户能写）／现状（只写已发生事实）／需求文档（总裁执笔） |
| 影子卡 | `shadows` 五节 | 记**过程**（进度/待协作/产物/迭代历史/**笔记**）；正卡记**结论** |
| parent | `card_parent` 边表 | **权限线**：我能管谁（读侧全开，写侧叠子树） |
| links | `card_links` 边表 | **通信线**：唯一的通信边界 |
| relations | `card_relations` 边表 | **依赖线**：迭代时不能孤立，要通知受影响方；不通信 |
| 九种卡 | `config/card_type_registry.json` | project / sub_project / topic / tool / coder / rule / role / function / **review** |
| 自动模式 | `src/goal/` ＋ `auto_driver` ＋ `scheduler` | goal 状态机＋续轮驱动＋点火队列，**不设任何上限** |

### 1.3 治理：总裁制

- **总裁**＝项目根卡，对用户唯一汇报口、需求文档执笔人。
- **四职能**（pm / cto / qa / 涌现守门）：只在阶段任务**头尾介入**，中间零介入。
- **唯一向上通道 `report_up`**：收件人由系统按关系算，模型不能选也不必选。
- **伴生评审卡**（10-26 需求 → 10-27 落地）：子卡建卡时自动派生一张离树评审卡，
  在职职能各自用自己的模型、在评审卡这个"场地"里读证据、表态 `approve`；全员通过才收口成正稿。

## 7. 一条主线（此前的诊断，复述不新增）

10-26 的三份笔记把三个问题归到同一个降级：

| 你要的 | 现在给的 | 降级 |
|---|---|---|
| 参谋（专业判断） | 核对员（逐处对照） | 判断 → 核对 |
| 节点网络（沿边通信） | 群聊（点名广播） | 网络 → 群聊 |
| 基础设施（谁都能基于它做提醒） | 一条规则（写死的 if） | 基础设施 → 功能 |

根因写的是：**系统把"文本"当成了"事实"**——结构化的只有身份类字段（card_type/parent/links/perms/state/goal），
而需求、现状、裁定、判据、观点、汇报全是自由文本，系统只知道"有多长、变没变"。

**10-27 这一天的八条线，基本都是在给这条根因补零件**：
边表＝把"线"变成可路由的事实；落点统一＋seq 水位＝把"消息"变成可统计的事实；
精准编辑＋版本＝把"卡面"变成有主人的块；三套事实源机制＝把"说明"绑到代码；
sqlite 结算＝把"上下文/凝练"变成单一事实源。
