## 1. 这个产品是什么

### 1.1 用户的原话定义（第一手，2026-10-19 口述）

> **核心不是画布，画布只是入口。**
> 形态：**树形卡片结构，每张卡是一个智能节点，节点之间靠三种线互相连接，形成一张智能节点的网络。**
> 解决传统 agent 的上下文、过程留痕可追溯、长程任务天然需要的工程与思维拆解问题。
> 因为认为不止于此，所以做**自动模式**：让模型彻底理解这套系统，然后**自行发挥**，期待涌现。

### 1.2 落到代码的形态

| 概念 | 落地 | 语义 |
|---|---|---|
| 卡 | `cards` 表一行 | 一个能自主跑的节点 |
| 卡面三块 | `mission` / `status_block` / `requirements` | 使命（只有用户写）／现状（只写已发生事实）／需求文档（总裁执笔）——**卡与卡之间唯一接口** |
| 影子五节 | `progress` / `coordination` / `artifacts` / `note` / `iterations` | 记**过程**；正卡记**结论**。`note` 是**私有节**，别的卡读影子时被剥掉 |
| parent 线 | `card_parent` 边表 | **权限线**：我能管谁 |
| links 线 | `card_links` 边表 | **通信线**：唯一的通信边界 |
| relations 线 | `card_relations` 边表 | **依赖线**：迭代时不能孤立，要通知受影响方；**不用于通信** |
| 九种卡 | `config/card_type_registry.json` | project / sub_project / topic / tool / coder / rule / role / function / **review** |
| 自动模式 | `src/goal/` + `goal/driver.py` | goal 状态机 + 续轮驱动 + 点火队列，**不设轮次封顶**（上限在 goal 自身的 `maxGoalRounds`，缺省 256） |

### 1.3 四条防错机制（README 明示，至今成立）

1. **结论是卡片间唯一接口** —— 卡内推理留在各自对话，只有沉淀后的结论跨卡流动。
2. **权限由卡片树机械决定** —— 读侧全盘可读，写侧限自己子树，建卡只能建自己的子卡。
3. **全量留痕可对账** —— `logs/`（每次模型调用全文）+ git（卡片改动）+ `tool_events`。
4. **机械兜底接住模型缺陷** —— 工具调用被模型以文本形态泄漏时机械解析并真实执行。

## 2. 内核诊断：这套系统一切失效的共同根因（2026-10-26 用户与作者共同得出）

> **系统把「文本」当成了「事实」。**

系统里结构化的只有**身份类字段**：`card_type` / `parent` / `links` / `perms` / `state` / `goal`。
所有真正重要的内容——需求、现状、裁定、判据、观点、汇报——**全是自由文本**，
系统对它们只知道两件事：**有多长**、**变没变**。

于是系统能验证「有没有写」，不能验证「写得对不对」。

| 现象 | 由这个内核直接产生 |
|---|---|
| 写入不可验证 | 文本没有 schema，在系统眼里只是「变了」，不是「错了」 |
| 状态不显式 | 状态藏在句子里（「R1 已收口」），不是字段 ⇒ 查不到、判不了 |
| 可观测性缺失 | 「我改了」和「真改了」都是文本，无法区分 |
| 职能退化成逐格巡检 | 验证文本只能靠「读」，读的活只能交给人（模型） |
| 通信不沿连线 | 文本不需要走边。边是给「可路由的事实」用的 |
| 系统消息只有一条 if | 只能对「工具被调用」这种结构化事件下判断；「事情做成没有」是文本，判不了 |

**⇒ 「加机制」总是失败的原因**：每加一道机制，约束只能加在**动作**上（有没有调这个工具、有没有变），
加不到**内容**上（对不对、全不全、和别处一致不一致）。

> 这条诊断是理解本项目后续所有设计取舍的钥匙。10-28 的三套事实源机制
> （`tool_doc.py` / `prompt_facts.py` / `system_claims.py`）本质是「让写了的都对」，
> 而 10-28 笔记自己承认：**机制只保证「写了的都对」，不保证「该写的都写了」**——
> 全新概念没被想到不会红，语义漂移能绕过字面检查。

### 4.1 卡型：两轴模型（2026-10-08 底座收口）

**L0 `project_class`**（仅根卡可写，决定本树 L1 词表作用域）：

| code | 标签 |
|---|---|
| `rd_project` | 研发项目（子卡分「子项目卡」＋「工具卡」） |
| `research_project` | 研究项目（子卡统一为「课题卡」） |

**L1 词表**：`rd_project` 7 型（sub_project/tool/coder/rule/role/function/review）、
`research_project` 5 型（topic/rule/role/function/review）、`root` 2 型（project/function）——
去重后 **9 个 card_type code**。

**写路径四闸**（`card_store._write_gate`）：闸1 非法值 → 闸2 词表归属 → 闸3 工具卡 owner → 闸4 状态迁移。
**读路径宽容**：legacy 值原样可读不报错。6 个 legacy 类型（剧本/线索/世界观/行为体/节点/假设）全部 `write_blocked=true`。

> 注意：**卡型注册表不参与工具面过滤**。它只管写门。
> 工具面是另一条链：`config/permissions.json` → `policy.SWITCHES`(21 个) → 建卡时固化进卡 `perms`
> → `card_tools.TOOL_SWITCH` 映射 → `policy.has_perm`。
> **运行时只读卡上固化的 perms，不查配置**（配置改动只对新卡生效）。

```
入口 ① POST /cards/{cid}/messages              （固定 work_001）
入口 ② POST /works/{wid}/cards/{cid}/messages  （归档 coder 解档复活 / 完工 coder 重新派活 / auto 首条消息设为 goal）

  ② 沉默闸         非 human 拒；human 可达但**不解除**沉默

  ⑥ 建卡（工具通道 ＋ 文本通道兜底，跨通道按标题去重）
  ↓

  ↓
```

### `step()` 状态机（`message_runner.py:714-1190`）

```
check_control（中止缝，三处挂点）→ wb_exec.maybe_delegate（命中则外部执行体代跑）
→ rounds += 1 → _apply_steer（插话入槽）→ 模型调用 _call_model_resumable（按次数 3 次、零退避）
→ 文本工具抢救（text_tool_rescue）
→ 无工具 ⇒ 插话优先 → 抢救反馈 → 三席判定（**当前不触发**）→ deliver
→ 有工具 ⇒ execute_tool（perm_gate=True）→ 工具块**原子落盘**（finally 内必落，异常也落）→ continue
```

**模型断连续跑**按**次数**不按墙钟（`_RESUME_MAX_ATTEMPTS=3`），零等待——
注释写明：「限流该等多久，端点会告诉你，不该由我拍一个数」。

> ⚠️ **一条容易误读的语义**：工具结果「落会话」≠「进上下文」。
> 落盘在 `message_runner` 的 finally（块 A assistant+tool_calls ＋ 块 B×N 工具结果全文）；
> 进上下文时 `predicates.enters_context` **排除工具块**（连带 tool_calls 的 A 块一起丢）。
> 理由（实测）：某卡工具结果占 92% token。

## 10. 自动模式（`src/goal/`）

**四个相位** `active/paused/blocked/complete` ＋ **activation** `armed/disarmed`。
**`activation` 永不落盘** ⇒ 重启后全部 disarmed ⇒ 启动时 `rearm_active_goals()` 按三条判据重新授权
（① `goal_state=="active"` ② `auto_mode==1` ③ 卡面 goal 非空）。

**12 条转移规则**写在 `src/goal/fold.py` 头部（`pause` 只 active→paused；`complete` 不能从 complete 再来；
`create` 必须 `revision=1/phase=active/roundsStarted=0` 且当前 goal 已 complete；`resume` 需 `roundsStarted < maxGoalRounds`）。

**续轮驱动** `goal/driver.py` 的 `drive()` 六步：停止中/竞争排队 → 跳过 → **`_auto_enabled` 闸**（读 `cards.auto_mode`，
**位置在 goal 判定之前**）→ goal 须 active+armed → `rounds_started >= max_goal_rounds` ⇒ block →
`_yield_to_children`（有未终止子卡则让位）→ 预留 round 后 spawn（`append_user=False`）。

**`goal/fold.py` 与 `memory_store` 的凝练毫无关系**——只是同名：
`goal/fold.py` 是**事件溯源投影**（把 `goal/change` 事件累加成状态，非法变更 fail-loud）；
`memory_store._maybe_fold` 是**调模型把记忆条目归拢合并**（内容压缩）。

**接线**：`routes.py` 的 finally 里 `goal_driver.notify_idle` ＋ `notify_parent_idle`。

`after_turn` 现存但**生产已无调用方**。`api/auto_driver` 仍承担 `will_continue` / `kick` / `reactivate_card` /
`ensure_goal_from_message` / `has_active_child`。

## 17. 一处「查实后不是 bug」的陷阱（记录以免误判）

`main.py` 里有**两个同名 `_start_goal_driver()`**：`main.py:156`（10-28 修复版，含 `rearm_active_goals()`）
与 `main.py:219`（10-20 旧版，只有 `install()`）。

**看似**后者遮蔽前者 ⇒ 10-28 的 goal 重启恢复修复是死代码。
**查实后不成立**：
- Starlette 0.41.3 的 `on_event` 装饰器在**装饰时**就 `add_event_handler` 并返回原函数
  ⇒ **两个 handler 都会被注册**，名字遮蔽不影响注册。
- `goal.driver.install()` 有 `global _INSTALLED` 幂等保护 ⇒ 第二次调用是 no-op。
- ⇒ 实际行为：`install()` 执行一次、`rearm_active_goals()` **执行一次**。**10-28 的修复是生效的。**

**但仍是一处隐患**：旧函数的 docstring 写着「activation 永不落盘 ⇒ 进程重启后全部 disarmed，
必须人显式 /goal resume」——**这句已经过时**，且与新函数的说明直接矛盾。
将来若有人「清理重复定义」而删掉**第一个**，会静默弄坏 goal 重启恢复。
