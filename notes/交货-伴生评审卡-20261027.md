## 四、已知边界

1. **`approve` 只能由职能调**：它不在基础池（`FUNCTION_ONLY_TOOLS`），子卡/根卡看不见。子卡自己不是成员，调了也会被拒。
2. **评审卡会话是场地，职能卡会话零写入**——这是"评审内容不进职能卡上下文"的落点。
3. **`_model_of` 取职能卡配置的模型**：走 `model_config.resolve_card_model`，失败回落 `pick_model`。**真实取值未在实跑中验证**。
4. **批次状态存 `review_state` 列**（JSON），卡面现状块是它的系统渲染投影。这是"事实在列、卡面是投影"，与 P1 的严格读法有差距，但没有第二个可写源。

## 六、补：重评触发器（2026-10-27 09:20）

### 先报一个致命发现：草稿版本从来没推进过

`review_store._card_hash` 读的是 `cards.content_hash` 列——**该列在 SQLite 库里根本不存在**
（那是卡面 markdown 镜像的字段，`PRAGMA table_info(cards)` 里没有）。异常被 `except` 吞成空串
⇒ `base` 和 `cur` 都是空 ⇒ `sync_draft` 永不推进 ⇒ **「改草稿 ⇒ 全员重评」是空的**。

昨晚交付文档里那条断言"子卡改卡面 ⇒ 草稿变 ⇒ 全员重评"是假绿：它只测了 `status()` 里的
hash 比对，没测版本真的会变。改判据那条（`criteria` 版本）是真的，改草稿那条是死的。

修法：`_card_hash` 直接对**三块正文**取 sha1（`mission` / `status_block` / `rulings`），
不算 meta——改标题、改父、改开关不算草稿变了。

### 再补触发器：一轮没过之后没人再叫它

`run_round` 只在 `_h_open_review` 里 spawn 一次，之后**没有任何再触发点** ⇒
成员一轮没过就永久挂着，第二轮永远不会发生。

| 补的东西 | 位置 | 干什么 |
|---|---|---|
| `sync_draft()` | `review_store` | 卡面指纹变了 ⇒ `draft+1`（旧 `approve` 因版本不等自动失效，不逐个 revoke） |
| `maybe_rerun(child)` | `review_runner` | 子卡有伴生卡＋有批次＋版本推进 ⇒ 起一轮 |
| `rerun_if_pending(review)` | `review_runner` | 版本已被别处推进（改判据／撤销）⇒ 起一轮 |
| `spawn_round()` | `review_runner` | 后台起一轮，返回 Task（测试可 await） |
| `_round_loop()` | `review_runner` | 收尾**只比对**版本、不推进；版本推进就再来一轮。退出条件是状态（无批次／全过／版本没变），不设次数上限 |
| `_INFLIGHT` | `review_runner` | 同一张评审卡同时只跑一轮（防同一版本评两遍；丢掉的触发由 `_round_loop` 的版本自检兜住） |

**三个钩子**（都挂在唯一入口上，不新增路径）：

1. `card_store.update_card` —— 正文三块**真变**之后（工具路径与 HTTP 路径都覆盖）
2. `_h_set_criteria` —— 判据版本 +1 之后
3. `_h_revoke_approve` —— 撤销之后（只跑未通过的，所以只会叫被撤的那个）
