# 需求 · 评审临时卡（2026-10-26）

> **【已作废】** 本文把结构写成"一次性临时卡"，术语与结构均错（实际是子卡的**伴生卡**：一对一、建子卡时自动建、随子卡归档）。
> 现行版本见 `需求-伴生评审卡-20261026.md`。本文保留仅为留痕。

> 状态：需求整理，未施工。
> 一句话：**评审不再是"发消息让各方各评一遍、收齐再汇总"，而是"开一张临时卡，所有人对着同一份草稿过闸，全员 approve 才结束"。**

---

## 一、要解决的问题

**实测**：`card_061` 一次阶段收尾，11:03 → 14:07 **3 小时、26 条往返**，fn_004 与 fn_005 交替，标题里"补件轮四／轮五／轮九／轮十／第十一轮／终核"逐轮递增。

**对账周期 = 轮次 ×（排队等待 ＋ 上下文重读 ＋ 往返投递）**

四个乘数现在全踩：评审走对话流（排队）、每次重读全量卡面（重读）、结论发回去再排队（投递）、评审是"自由发现"所以轮次无上限。

**根因**：评审这个动作**没有形状**——没有固定输入、没有固定输出、没有终止条件。它只有"人"（职能模型）和一篇文章。

---

## 二、新流程（七步）

1. **发起**：A 要评审 → 开一张**临时卡**（评审卡），A 是发起方。
2. **写死现场**：临时卡里写清三样——**评审焦点**、**判据清单**、**待评审的卡面草稿**（冻结版本）。
3. **召集**：所有在职职能加入，各以本职能角色参与（各带自己的职责书）。
4. **一轮表态**：每个角色对**同一份草稿**独立表态。调 `approve` ＝ 通过；不调 ＝ 未通过。
5. **收敛**：只要有一个角色没通过 → 发起方改草稿 → 下一轮（只叫没通过的人 ＋ 被改动波及的人），直到全员 `approve`。
6. **落地**：全员通过 → 执行卡面变更 → 落文档。
7. **归档**：临时卡归档，**不删除**。

---

## 三、已定的机制约束

| # | 约束 | 理由 |
|---|---|---|
| 1 | **`approve` 是唯一工具**，没有 `reject` | 不通过＝不调工具。两个工具就多一个岔路（调了 reject 没给判据怎么办） |
| 2 | **默认未通过** | 不调工具＝没过。若默认通过，沉默就等于放行 |
| 3 | **通过后不再讨论** | 工具调用是不可分割的，结构上排除"通过但两处要改"这个第三态 |
| 4 | **`approve` 绑定草稿版本** | A 通过 v3，草稿改 v4 ⇒ A 的通过作废，否则"没看新版也算通过" |
| 5 | **草稿一变，全员重评** | 不要求发起方"声明改了哪几条"——那是靠模型自觉，属于低级机制。简单、无歧义 |
| 6 | **什么都没调 ＝ 未完成评审** | 既非通过也非不通过，是"该做没做"，交给系统提醒（harness），不由评审机制自己兜 |
| 7 | **共用事实，不共用观点** | 角色判断依据是卡面草稿；查阅工具结果在临时卡上下文里保留共享，避免"四方各读一遍" |
| 8 | **临时卡是过程记录，不是事实源** | 事实源永远是原卡卡面。临时卡只读、不作为输入、不参与"以哪份为准" |
| 9 | **临时卡不进卡清单／画布／统计** | 否则几十张临时卡会淹掉上下文与画布 |

## 四、必须拆掉的原有件

> **这不是"可以顺便清理"，是互斥**：新旧两套并存，模型会两套都用（今天 `review_request` 与 `direct`/`sync` 并存已经演过一次），结果比现在更乱。
> 旧工具必须**从工具面物理移除**，不能只写"不推荐"——模型看不见才不会调。

| 原有件 | 现在做什么 | 为什么必须拆 |
|---|---|---|
| `review_request` 工具 | 建批次 ＋ 广播唤醒全部职能 | 被"开临时卡"取代。留着就有两条发起路径 |
| `review_batches` 批次（open/collected） | 存 subject/focus/expected/status | 临时卡本身就是批次。留着就有一套并行的"批次状态" |
| `submit_review` 工具 | 职能提交 `verdict` 自由文本 ＋ concerns ＋ divergence | `verdict` 是文本 ⇒ "通过但两处"合法 ⇒ 收齐≠通过。这是 26 轮的直接来源 |
| `completeness` 收齐判据 | 判"每个人都提交了" | 收齐 ≠ 通过。新判据是"每个人都 approve" |
| `close_batch` ＋ 唤醒总裁 | 收齐后汇总呈总裁 | 全员通过后结论已明，不需要"汇总再裁" |
| `_invite_function_room` | 给全部在职非总裁职能发消息 ＋ 唤醒 | 被"召集进临时卡"取代。留着就是广播唤醒的第二条路 |
| `function_sync` 队列 ＋ `notify_event` ＋ `spawn_opinion` | 订阅 signals → 冷却 → 起观点回合 | 职能不再靠"被消息叫醒"，改为"被拉进现场"。这套订阅机制（且词表早已错配）整体退役 |
| `stage_open` / `report_up` 里的职能邀请 | 阶段头尾各调一次 `_invite_function_room` | 语义保留（阶段头尾要评审），实现改为"开临时卡" |
| `peers_opinions`（总裁统筹看同僚观点） | 从 verdicts 表取各家最新观点 | 现场里观点已经互相可见，不需要二次汇总 |

### 顺带必须一起处理的

- **`review_batches` 前端零展示**（`routes.py` 与 `static/esm/` 均无引用）——旧批次本来就是"只写不读"的黑洞，拆掉不会有界面损失。
- **`function_verdicts` 台账**：`record_verdict` 是否保留，取决于它在新流程里还有没有位置（见待定项 3）。

## 六、待定项（我没想清，需要裁）

1. **临时卡的成员是引用还是快照？** 职能卡改名／停职／删除后，历史临时卡里的成员怎么显示。
2. **全员通过后谁执行卡面变更？** 发起方自己，还是走总裁（`curate_face`）？这决定总裁在新流程里还有没有位置。
3. **`record_verdict` 留不留？** 如果职能的判断只活在临时卡发言里，台账就空了；但台账是"职能有记忆"的唯一载体。
4. **一张卡同时有多张临时卡怎么办？** 两个并发评审基于不同草稿版本，通过后执行哪一个？
5. **临时卡归档后，结论怎么被后续引用？** 我倾向：结论写进原卡的 rulings（一条决策），临时卡只留过程；但这又回到"决策落面"的老问题。

## 七、这套需求解不了什么

- 解不了"判据本身对不对"——判据是发起方写的，错了照样全票通过
- 解不了"某个角色永远不通过"——那是流程问题（升级），不在这层解决
- 解不了"谁说了算"——全员通过是充分条件，但不回答"谁有权定义判据"

## 八、UI 端怎么显示

### 前提：临时卡不设 parent

**数据上独立，用 `review_of` 指向被评审卡**，不设 `parent`。

理由：`function` 卡的教训——「`off_tree=true` 但 `can_have_children=true`」自相矛盾，导致子卡计数、删卡护栏、上下文"直接子卡现状"、画布过滤全都要各加一处判断，漏一处就出问题。

临时卡若挂 `parent`，会立刻踩三件事：被评审卡变成"有子卡"（删不掉）、子卡计数虚高、上下文里多出一堆"子卡现状"。

### 1. 左栏列表：加一个「评审」入口，不塞进树

- 位置：搜索框下方、树上方，一行聚合入口 `〔评审 2〕`
- 展开：每条一行 `被评审卡标题 · 第 N 轮 3/4`，行尾状态角标（评审中／待执行／已归档）
- 点击 → 打开临时卡对话页

**不塞进任务树**的理由：评审是**过程**，不是**结构**。树只画任务。要"看这张卡被评过几次"，在卡详情页里给，不在树里堆。

（现有先例：`tool` 卡就是"连同子树在投影层剥掉、不进侧栏"；职能卡是 `row.kind === "function"` 单独渲染。评审卡走 `row.kind === "review"` 同一条路，不改树结构。）

### 2. 画布：不画节点，只给被评审卡加角标

- 被评审卡右上角一个角标：`评审中 3/4` / `评审通过·待执行`
- 画布**不画临时卡节点，不连线**

**理由：保住"三种线"的产品定义。** 临时卡与源卡的关系既不是 parent、也不是 links（通信线）、也不是 relations（依赖关联）——硬画一条线就等于发明第四种线，把定义搞乱。

开关：画布右上角 `显示评审` 只在角标太吵时提供关闭，不提供"画节点"。

### 3. 临时卡自己的页面（群聊现场）

这是主界面，要让人**一眼看出进展**：

```
┌ 评审 · card_061《卡侧体系 · 总负责人》       第 3 轮 · 3/4 通过 ┐
│ 焦点：R1 阶段收尾是否成立                                      │
│ 判据：C-1 状态行一致 / C-2 现文无假引述 / C-3 不自称通过        │
│ 草稿：draft@v4（本轮改动：C-2 段）                             │
├────────────────────────────────────────────────────────────────┤
│ fn_004 产品经理   ● 通过（v3）                                  │
│ fn_005 技术总监   ● 通过（v4）                                  │
│ fn_006 测试验收   ○ 未表态                                      │
│ fn_007 涌现守门   ● 通过（v4）                                  │
├────────────────────────────────────────────────────────────────┤
│ 第 2 轮 · fn_006：C-3 只写了结论没写证据来源，不通过            │
│ 第 1 轮 · fn_004：C-2 引述的是旧版现文，不通过                  │
└────────────────────────────────────────────────────────────────┘
```

三个必须有的东西：
- **每个角色的状态点**：● 通过（带通过的草稿版本）／○ 未表态／— 本轮未参与
- **每轮结果摘要**：谁没过、针对哪条判据、理由首句
- **草稿 diff**：本轮改了哪几段（否则角色和人都要重读全文，回到老问题）

### 4. 归档后

- 左栏「评审」入口不再列它（或折进"历史评审"）
- 被评审卡详情页：`评审记录 · 3 次`，展开可看每次的焦点、轮次、结论
- 画布角标消失

### 5. 用户在现场的角色：不是旁听，是甲方

**这是硬要求：评审不能是黑盒。用户能看、能说、能纠正、能在卡住时裁决。**

| 动作 | 机制后果 |
|---|---|
| **发言** | 进同一上下文，下一轮角色读得到。不改变任何状态 |
| **纠正判据** | 判据一变，**所有已 `approve` 作废**（通过的基准变了），全员按新判据重评 |
| **纠正草稿** | 同上，作废并重评；发起方的"改了哪几条判据"声明由用户覆盖 |
| **推翻某个角色的通过** | 该角色退回未通过，需重评 |
| **裁决（兜底）** | 直接 `approve` 一票通过，或解散评审。用于"某角色永远不通过"的死循环 |

**由此推出一条机制修正：`approve` 绑定的是（草稿版本 ＋ 判据版本），任一变化即作废。**

只绑草稿版本不够——用户纠正了判据而通过仍有效，等于没纠正。

### 6. 「不能是黑盒」的三条落地要求

1. **复用普通对话页，不新造界面。** 临时卡就是一张卡，用现有对话页渲染，只是多两样：顶部判据／轮次条，发言左侧状态点。用户不需要学新界面。
2. **证据区可见。** 角色调阅工具（`read_card`／`read_file`）的结果要留在现场且**用户也能看到**——否则用户不知道角色的判断基于什么，也就无从纠正。
3. **每步留痕，且必须区分「发言」与「动作」。**
   - **发言**＝一句话，进上下文，要靠模型理解才生效；
   - **动作**＝改判据／推翻通过／裁决，**当场改变状态**，单独记一条（动作类型／目标／时间）。

   区别不是"谁说的"（`actor` 字段本来就分得清），是**有没有改变状态**。

   今天的实例：card_001 里用户 12:36 说「技术实现，不应该是我来裁，你或者相关负责人裁定才对」——这是一个授权决定，机制上却只是一段文本。**用户的意志进了对话，没进状态**，于是每个人对"用户到底定了什么"各有理解，然后互相纠正；事后要查也只能靠读哪句像裁定。

### 7. 动作怎么发生：工具调用，不是按钮

**判据、通过、推翻、裁决都是工具。** 模型读懂用户的话，自己决定调哪个工具；系统记录"改了什么、从什么改成什么、什么时候"，记录可查、可撤销。

- 用户说「C-3 这条不对，应该改成'状态行不得由被审方自称通过'」→ 模型调 `set_criteria` → 判据版本 +1、通过作废
- 用户说「fn_006 这条通过不算」→ 模型调 `revoke_approve` → 该角色退回未通过
- 用户说「别评了，按现在的过」→ 模型调 `decide`

**不设"选择条"、不让用户点按钮决定"这句话是发言还是动作"。** 那是防模型读不懂话——属于低级机制，且把用户变成操作员。

**真正要防的是"说做了没做"**：模型说"我改了判据"是文本（不可信），调 `set_criteria` 是动作（留痕）。所以关键变更一律走工具，理由一律走文本。
