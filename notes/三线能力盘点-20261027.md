# 三线能力 · 现状盘点（2026-10-27）

> 用户：「三线能力需要做一次重新梳理，可能涉及到三线底层架构上的调整，也涉及到工具层面的变更」

**只摆事实，不写方案。** 三条线的定义按用户 2026-10-27 裁定：
parent＝权限管理线／links＝通信线／relations＝依赖关系线。

---

## 一、数据形态：三条线都不是"边"，是卡上的字段

| 线 | 存哪 | 形态 |
|---|---|---|
| `parent` | `cards.parent` | **单值**（一张卡只有一个父） |
| `links` | `cards.links` | **JSON 数组** `[{target, type, note}]`，只写在发起方卡上 |
| `relations` | `cards.relations` | **JSON 数组** `[{target, kind, detail}]`，只写在发起方卡上 |

**库里没有边表。** 实测 `work_027/cards.db` 33 张表，没有 `edges`／`links`／`relations` 表。
`src/storage/card_db.py` 的建表清单里也没有。

这带来三个结构性后果（都是事实，不是评价）：

1. **反向查询要全表扫。** `context_assembler._load_cards_index` 把全部卡的
   `links` / `relations` 读进内存，再逐卡扫 `target == 我`。卡多了就是 O(N) 每轮。
2. **删卡不清理边。** `unlink_cards` 的说明写着「目标卡已删时也可用（清理悬空线）」
   ——**靠人调**，不是删卡时自动清。
3. **没有图能力。** 涌现守门要的「自主连线率／横向互核数／环闭合率」，
   需要按边查询（谁连了谁、有没有环），现在只能把全表读进内存自己算。

## 二、每条线的全部使用点

### parent（权限线）

| 函数 | 用它做什么 |
|---|---|
| `policy.can` → `_is_in_subtree` | **写权限**（能改谁的卡）、**读权限**（读侧全开，写侧叠树） |
| `_h_create_card` / `_h_create_coder_card` | 只能建自己子树内的子卡 |
| `_h_reparent_card` | 换父时校验目标父在子树内 |
| `_h_archive_card` / `_h_stop_card` / `_h_silence_card` | 只能归档/停/沉默自己子树内的卡 |
| `_h_stage_open` | 只能给自己子树内的卡开阶段 |
| `_h_continue_task` | 只能给子树内的 coder 续派 |
| `goal.tools.h_resume_child` | 只能恢复子树内的卡 |
| `_h_report_up` | **读 parent 算收件人** ← 通信用途 |
| `_h_scene_sync` | **读 parent 兜底收件人** ← 通信用途 |
| `_h_send_card_message` | **`_is_in_subtree` 退路** ← 通信用途 |
| `_h_scene_direct` | **`_is_in_subtree` 校验** ← 通信用途 |

**11 处用 parent，其中 4 处是通信用途。**

### links（通信线）

| 函数 | 用它做什么 |
|---|---|
| `policy.check_linked` / `_linked_between` / `_has_edge` | 判两卡之间有没有线 |
| `_h_link_cards` / `_h_unlink_cards` | 建线／解线（写 `cards.links`） |
| `_h_read_linked` → `read_via` | 沿线路读对方卡（三块／影子／对话摘要） |
| `_h_send_card_message` | **唯一一处**「没线就拒」的通信校验 |
| `_h_scene_sync` | **读 links 算收件人，但不校验** |

**6 处用 links，只有 1 处把它当"通信边界"用。**

### relations（依赖线）

| 函数 | 用它做什么 |
|---|---|
| `_h_link_rel` / `_h_unlink_rel` | 写 `cards.relations` |
| `context_assembler._dep_relations_for` | 渲染 250 区（正反双向） |

**2 处，全部是"写"和"渲染"。零机制消费**——没有任何动作由依赖关系触发。

## 三、五处混用（用 A 线的判据做 B 线的事）

| # | 在哪 | 混成什么样 |
|---|---|---|
| 1 | `_h_send_card_message`（`card_tools.py:4458`） | `check_linked` **或** `_is_in_subtree` 任一成立即放行 ⇒ **parent 实际在承载通信**。已登记 `UNMET` |
| 2 | `_h_scene_direct`（`:5339`） | 只校验 `_is_in_subtree`，**完全不看 links** ⇒ 子树内不建线也能发指令 |
| 3 | `_h_link_rel` / `_h_unlink_rel`（`:2384` / `:2455`） | 调 `_require_wire_switch(SWITCH_LINK)` ⇒ **依赖线用的是通信线的权限开关**，两条线共用一个 perms 位 |
| 4 | `_h_scene_sync`（`:5296`） | 收件人＝显式 `card_ids` → `links` → `parent`，**三种来源并列且都不校验** ⇒ 线只是"缺省值"，不是边界 |
| 5 | `_h_report_up`（`:4862`） | 收件人＝`parent` ＋ 总裁，**不看 links** ⇒ 汇报走父子关系，不走通信线 |

第 1、2、4、5 条合起来的意思是：**通信的边界现在有四种替代判据（子树／父卡／显式卡号／全在职职能），links 只是其中之一。**

## 四、三处缺失

| # | 缺什么 | 后果 |
|---|---|---|
| 1 | **links 没有被当作唯一通信边界** | 画布上画的网络与实际信息流无关（详见 `notes/卡间通信-现状梳理-20261027.md`） |
| 2 | **relations 没有触发能力** | 依赖方不知道被依赖方改了；迭代时孤立（用户 2026-10-27：「形同虚设」） |
| 3 | **没有"谁指向我"的索引** | 每轮装配上下文都要全表扫；图查询能力为零 |

## 五、工具层面的现状

| 线 | 建 | 解 | 读 | 判 |
|---|---|---|---|---|
| parent | `create_card(parent=)`、`reparent_card` | — （删卡即断） | `read_card` 的 meta | 隐式（权限闸里） |
| links | `link_cards` | `unlink_cards` | `read_linked` | 隐式（只有发信一处） |
| relations | `link_rel` | `unlink_rel` | 250 区（自动注入） | **无** |

**三件不对称**：

1. `parent` 没有"解"的工具（不能把自己变成无父卡），只能 `reparent_card` 换到别处
2. `relations` 没有"读"的工具（只能靠 250 区自动注入，不能按需查"谁依赖我"）
3. 三条线**共用一个 `link` 权限开关**（`link_cards` / `link_rel` / `unlink_*` 全挂 `SWITCH_LINK`），
   没有"能建通信线但不能建依赖线"这种区分

## 六、我判断需要先定的三件事（不是方案，是岔路）

1. **要不要独立边表。**
   现在三条线都是卡上字段。改成边表能拿到：反向索引（O(1) 查谁指向我）、图查询（环、连通度）、
   删卡自动清边。代价是所有读写点都要改，且现有 `cards.links` 数据要迁移。

2. **`parent` 到底还承不承载通信。**
   按你的定义不承载（父子默认连一条 link）。但改成"完全不承载"意味着：
   `report_up` 的收件人要改成沿 line 算、`direct` 要改成校验线、`sync` 的 parent 兜底要删。
   这四条改完，`work_027` 现存所有纵向协作都要求先有线——存量树要补线（补线脚本）。

3. **`relations` 的"触发"做到什么程度。**
   你已定：信息常驻上下文（已有）、迭代时要考虑受影响方并通知（靠模型看到后自己发）。
   那么机制侧只负责"把关系写清楚、呈现清楚"，不负责自动叫醒。
   要不要额外做"被依赖方改动时，给依赖方一条同步消息"，是另一个决定。

**这三件我不替你定**，因为它们都改产品行为语义。
