## 零、母问题

### P0-1 「一条消息」没有唯一定义

**现象**：全仓没有"消息"这个对象。每个需要发消息的场景，各自在调用点实现「存哪、要不要叫醒、谁能发」三件事。结果是同一条卡间消息有 7 条投递路径，落点 4 种、唤醒 3 种、连线校验只有 1 条做。

**证据**：见 P2-1 矩阵（7 条路径逐一实读）。

**与既有口径的冲突**：`session_facade.emit_message_event:673` 自称"单一落点"，但那只统一了**事件**的形状，没有统一**投递**本身；`function_room.notify_event` 与 `_invite_function_room` 各自实现唤醒；`harness.deliver:297` 又实现了一遍。三处都写了"与卡间通信同一条路"，实际是三条路。

**影响面**：P1、P2、P3 全部。这是它们共同的母体——所以三块不是三个独立问题。

## 一、职能卡（P1）

### P1-1 职能权限：目录声明与实际权限是两套，且实际那套是根卡级

**现象**：
- `config/function_catalog.json` 给每个职能声明了 `perms`：pm/cto/qa/涌现守门＝`["read","read_linked"]`，ceo＝`["read","edit","create_child","link","unlink","read_linked"]`。
- 这个字段**全仓零消费**：`function_room.py` / `card_tools.py` / `message_runner.py` 三处 grep 无任何读取点。
- 实际权限来自 `config/permissions.json` 的 `function` 行（`rd_project.function` / `research_project.function`）＝13 个开关，与 `project` 行同集合：含 `edit` / `create_child` / `invoke_tool` / `plan` / `send_card_message` / `manuscript`。
- 线上实测：work_027 全部 7 张职能卡 `perms` 字段逐字相同，都是这 13 个开关。

**锚点**：`card_store._perm_fields:163` → `policy.compute_perms(project_class, card_type)`；`permissions.json` 的 `function` 行。

**与既有口径的冲突**：目录 `_meta.doc` 写「每个职能的职责书/管辖/盯线/唤醒事件/工具面/权限/**卡面区块全部由本目录定义**」；卡类型注册表写职能卡是「离树的观察者/顾问」「不进任务树」。而实际给的 `create_child` + `edit` 是**任务卡的写权**，不是观察者的权。

**影响面**：职能回合的工具面（P1-2 在它之上叠加）、所有按 perms 派生的执行层关口、`scripts/refresh_perms.py` 的刷新口径。

**与既有口径的冲突**：`_h_send_card_message:3807` 的 docstring 写「模型侧一律 require_link=True——通信走专门的通信线」；`policy.py` 的 `SCOPE_LINKED` 注释写「卡间通信的边界**是通信线，不是 parent 树**」。这两条口径只落在路径 1 上，其余 6 条都不遵守。

### P2-2 消息账本已经失真

**现象**：work_027 `messages` 表 1352 行，按类型分布：


**结论**：账本里**一条 sync、一条 directive 都没有**——而这两类是 2026-10-26 改造后真实在用的通信形态。`read_inbox` 的数据源就是 `messages`（`card_db.select_pending:1578`），所以模型用 `read_inbox` **永远看不到同步与指令**。

**与既有口径的冲突**：`read_inbox` 的说明写「读**你自己**的消息账本……incoming 是增量的」；账本现在只覆盖 7 条路径里的 3 条。

### P2-3 `report_up` 零留痕

**现象**：`_h_report_up` 的 `_deliver` 只调 `deliver_now(text=...)`——不写 `messages`、不落会话块、不发消息事件。父卡被叫醒并拿到正文，但**事件流里没有任何"子卡汇报了"这件事**。

**后果**：`harness` 的 `turn_end_without_report` 规则靠子卡侧 `tool_result{report_up, ok:true}` 判定，这条还能用；但"谁向谁汇报了什么"在网络层面无法追溯，也无法统计。

**与既有口径的冲突**：`prompts.py:357` `_SEC_ORG_TEXT` 写「系统会把汇报同时送到父卡、相关职能卡与总裁——**收件人由连线算**」；实际是硬编码 `parent + ceo`，与连线无关。

### P2-4 路径 7 只写库不唤醒，注释说"投递即唤醒"

**现象**：`_notify_activation_blocked:460` 只调 `card_db.append_inbox`，注释写「激活被拒 ⇒ 给上级卡投信提示（**投递即唤醒**，上级知道为什么没动静）」。函数体内**没有** `deliver_now`。

**后果**：这封信落在 `messages` 里，要等上级卡自己下一次回合 `take_pending` 才被看到；上级卡若已空闲收口，就永远不知道。

### P2-5 三套唤醒语义，同一件事三种行为

| 语义 | 实现 | 用在 |
|---|---|---|
| 取件唤醒 | `deliver_now()` 内部 `take_pending` → 拼 prompt → 起轮 | 路径 1、5 |
| 文本唤醒 | `deliver_now(text=...)` 不取件，正文已在历史里 | 路径 3、4、6 |
| 不唤醒 | 只落库/只落块 | 路径 2、7 |

**与既有口径的冲突**：`deliver_now:1764` 的 docstring 只描述了"取件模式"一种语义，`text` 参数是 2026-10-26 追加的，docstring 未同步——**函数契约与实现已经不同步**。

### P2-6 `inbox` 这个词已经名不副实

**现象**：`inbox` 表仍在 DDL 里，线上 0 行；`insert_inbox:1557` 实际写 `messages` 表；`append_inbox` / `list_inbox` / `select_inbox` / `take_pending` 全部围绕 `messages` 工作。

**后果**：读代码的人会以为有两套收件箱。`_h_read_inbox` 的函数名、`read_inbox` 工具名都还叫 inbox，但底下是 messages + 水位。

## 三、系统消息（P3）

### P3-1 规则表声明 6 种判据，引擎只认 2 种，其余静默不触发

**现象**：
- `config/harness_rules.json` 的 `_meta.guard_kinds` 列了 6 种：`card_state` / `field_empty` / `field_not_empty` / `no_event` / `has_event` / `child_count`。
- `harness.evaluate_guard:118` 只处理 `no_event` / `has_event`；其他 kind 走 `else` 分支：**只打一条 warning，然后 return False**。
- `_child_count:201` / `_cmp:206` 成了死代码，注释写「已废弃」。

**后果**：任何人照 `guard_kinds` 文档写规则，该规则**永不触发**，且只在日志里留一条 warning。

### P3-2 只有 1 条规则启用，且 target 不能指职能

**现象**：`rules` 两条，`turn_end_without_report` enabled、`child_created_needs_mission` disabled（注释：用户只批了第一个）。`resolve_targets:212` 支持 `self`/`parent`/`ancestors`/`links`/`card:<id>`——**没有 `functions` 一类**，系统提醒送不到职能卡（除非写死 `card:fn_00x`）。

### P3-3 投递双事件

**现象**：`harness.deliver:310` 调 `append_card_message(..., event_type=EV_TYPE)` → `append` → `_emit_block_event` → `emit_message_event` 落**第一条** `harness_message`；紧接着 `:318` 又调 `event_stream.emit(..., EV_TYPE, ...)` 落**第二条**。

**后果**：每条系统提醒在事件流里出现两次；`harness_fired` 的防重只防投递，不防这双事件。

### P3-4 `append_sync` 路径不 flush 汇总表

**现象**：`event_log.append:250` 落盘后调 `event_hub.maybe_flush`；`append_sync:277` **只调 `_notify_harness`，不调 `maybe_flush`**。而 `event_hub.record` 是同步入缓冲、靠 `maybe_flush` 批量落表。

**后果**：走 `append_sync` 的事件（`goal/change` 等）进了缓冲，但落表要等下一次异步 `append` 触发——若之后没有异步事件，这批汇总就停在内存里。

### P3-5 与职能唤醒是两套"事件→唤醒"，互不知情

**现象**：`harness.fire` 从 `event_log` 的落盘钩子触发（`_notify_harness`）；`function_room.notify_event` 是另一条（订阅 + 队列 + 观点回合）。两者看同一批事件，各自决定"要不要叫醒谁"，没有共享的规则表，也没有互相去重。

**后果**：同一次 `done` 事件，可能既触发 harness 提醒，又触发职能邀请（实际由 P1-5 的广播实现），收件卡被叫醒两次。

### P3-6 消息没有成为节点

**现象**：`harness` 的投递产物是一条 `msg_notify` 会话块 + 一条 `messages` 行（实际路径 6 连 `messages` 都不写）。它在卡树/图里**没有位置**：不能被 `read_card` 读、不能挂线、不进任何统计。

**与既有口径的冲突**：`harness.py:15` 模块头写「消息也是通过节点网络连线通信，是智能网里的其中一个节点，而不是完全自造一套体系」——这句话目前只做到"走同一条投递路"，没做到"是节点"。
