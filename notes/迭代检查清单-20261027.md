# 迭代必查清单（2026-10-27 立）

> 用户：「那就把这个作为迭代必须检查项」

**用法**：改完代码，跑

```
.venv/Scripts/python.exe -m pytest tests/test_tool_doc_facts.py \
    tests/test_prompt_facts.py tests/test_system_claims.py -q
.venv/Scripts/python.exe scripts/prompt_audit.py
```

红了就是漏了。下面是「改什么 → 必须同时做什么 → 漏了哪条红」。

---

## 一、改动对照表

| 你要做的事 | 必须同时做 | 漏了会红在哪 |
|---|---|---|
| **加一件工具** | ① `ToolDef(..., doc=ToolDoc(group, scene, usage, effect))` ② 配 `TOOL_SWITCH` ③ 归到卡型（类型闸／末段追加） ④ 从 `PENDING` 删掉该名字 | `test_tool_doc_facts`（构造期就报错／`test_no_new_undocumented_tool`） |
| **改工具的落点或唤醒** | 改 `effect` 声明（`sink` / `wake` / `wire`） | `test_effects_match_implementation`（AST 扫 handler） |
| **删一件工具** | 从 `TOOL_REGISTRY` 与 `PENDING` 删；提示词里提到它的地方也要删 | `test_no_new_ghost_tool`（幽灵检测） |
| **加一种错误码** | 在 `prompt_facts.ERROR_CODES` 登记 ＋ 写「收到该怎么办」＋ 从 `PENDING_CODES` 删 | `test_every_error_code_is_declared` |
| **加一种消息类型** | 在 `message_type_registry.json` 登记 ＋ 提示词写它的应对 ＋ 从 `PENDING_MSG_TYPES` 删 | `test_prompt_covers_all_msg_types` |
| **加一种卡类型** | 配 `card_type_registry.json`（能否建子卡／是否离树）＋ `permissions.json` ＋ `FILE_SCOPE` | `test_system_claims::nine_card_types`（矩阵自动渲染，覆盖不全就红） |
| **加一个上下文区** | 在 `system_claims.REGION_KIND` 归类（属于卡面／结构／过程／规则／目标／meta） | `test_system_claims::what_you_see` |
| **加一个职能** | 在 `prompt_facts.FUNCTION_BRIEF` 写一句话职责 | `test_prompt_facts::test_functions_all_have_brief` |
| **改三条线的职责** | 改 `prompt_facts.LINES`（duty 与 cannot 都要写） | `test_three_lines_declared` |
| **改卡面块名／块数** | 改 `hash_utils.NEW_SECTION_MAPPING` | `test_blocks_come_from_source` |
| **改影子四节名** | 改 `shadow_store` 的节名 | `test_system_claims::shadow_is_process` |
| **改「一轮怎么结束」** | 改 `message_runner` 主循环退出条件 | `test_round_ends_without_tools` |
| **让 `sync` 会唤醒** | 改 `effect` 声明（`wake=True`） | `test_sync_never_wakes` |
| **加一条「系统是什么样」的新陈述** | 在 `system_claims.CLAIMS` 加 `Claim(text, evidence, verify)`；`verify=None` 要登记 `MANUAL` | `test_manual_list_is_honest` |

## 二、三张登记表，都只能减不能增

| 表 | 在哪 | 含义 |
|---|---|---|
| `PENDING` | `tests/test_tool_doc_facts.py` | 还没填 `doc` 的工具 |
| `PENDING_CODES` / `PENDING_MSG_TYPES` / `PENDING_GHOSTS` | `tests/test_prompt_facts.py` | 提示词还没写／还没删的事实 |
| `MANUAL` / `UNMET` | `src/api/system_claims.py` | 无法机械验证的陈述／目标态未达成的陈述 |

**每一张都是双向的**：漏登记 ⇒ 红（防止蒙混）；修好了不删 ⇒ 也红（防止表烂掉）。

## 三、机制管不到的地方（诚实清单）

| 盲区 | 说明 |
|---|---|
| **全新概念没被想到** | 明天加一套「卡的生命周期状态机」，代码写了、说明书没写——**不会红**，因为没有 claim 提到生命周期。机制只能校验已有陈述，发现不了缺一条陈述 |
| **语义漂移绕过字面检查** | `_v_sync_no_wake` 查的是「有没有调 `deliver_now`」。改成「先判断忙不忙再调 `_maybe_wake()`」就绕过去了——**检查通过，而同步其实会唤醒** |
| **判断性内容的质量** | 「过程不进卡面」在 `MANUAL` 里，靠人。新写一段判断性内容时，作者没想到要加 claim，就没有约束 |
| **清单本身的全** | 反查能保证「清单里的每一项都有归属」，但清单之外的整个世界它看不见 |

**结论**：这套机制保证「写了的都对」，不保证「该写的都写了」。
第三、四行那两类，只能靠每次迭代时**人先想到「这算不算一条新的系统事实」**。
