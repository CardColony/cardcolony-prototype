# 三个问题的产品层理解（2026-10-26）

> 本文取代 `问题台账-三块-20261026.md` 的地位——那份记的是"实现有没有自相矛盾"（代码层），
> 本文记的是"产品有没有做到它承诺的事"（产品层）。
> 不写方案。每条只回答三件事：**你要它干什么 / 它现在实际是什么 / 差在哪**。

## 一、职能卡

### 你要它干什么

10-23 22:52 你的原话：「我们还需要角色卡，来监督整个工作，第一阶段，需要什么角色？最好是人类团队职务，这样模型最了解。」

你要的是一个**有专业立场的参谋**：
- 产品经理管"需求的前提有没有来源"
- 技术总监管"技术方向有没有违背既定裁定、被否掉的方向有没有复活"
- 测试验收管"验收判据在不在、成不成立"
- 涌现守门管"协作有没有退化"

它该在关键节点说一句"我不同意，理由是 X"，其余时间闭嘴。

### 它现在实际是什么

一个**逐格核对员**。

- `fn_007` 跑到第 120 轮、第 123 轮，报的是"第 N 处相左""五件请裁"
- `fn_004` 每次都是"通过，但两处要改""通过，附两点补充"
- `fn_005` 是"三条判据无红项，技术面三债"

这些**不是专业判断，是核对结论**。核对是机器该干的活，判断才是参谋的活。

### 差在哪（产品层）

**1. 职能说的话，没有一个"必须被听"的地方。**
它把观点写进评审批次，而批次**没有任何读取入口**——被评的卡不知道自己正被按什么焦点评，上级也读不到批次正文。它唯一能让人听见的方式是发消息，而消息到了对方那里，又变成一条"待核对项"。
⇒ **职能是个哑巴，只能靠喊。**

**2. 沉默不值钱。**
设计上"沉默即判断"，但沉默不产生任何记录，所以沉默等于没干活。于是它必须每轮报点什么来证明自己在——你看到的"每轮报同样的第 N 处"，固定开销就是这么长出来的。
⇒ **沉默没有成本，也没有收益，所以没人选择沉默。**

**3. 它被当成质检用，不是参谋用。**
质检问"改没改"，参谋问"该不该"。现在所有职能的输出格式都是"通过/不通过 + 几处要改"——这是质检格式。你的四种开口情形（阶段放行／判据成立性／越界／用户令）里，没有一条是"逐处核对"。

## 二、卡间通信

### 你要它干什么

你的产品定义是「树形卡片结构，每张卡是一个智能节点，节点之间靠三种线互相连接，形成一张智能节点的网络」。

**线不是权限装饰，线就是拓扑**：谁和谁有关系、信息沿哪条路走、谁该知道什么。你后来那句更明确：「卡间通信有专门的通信线」「收件人由连线算，你不能选也不必选」。

### 它现在实际是什么

一个**群聊加点名**。

- 同步：可以指定任意卡（不建线也能发）
- 指令：只看子树（不看线）
- 汇报：硬编码"父卡 + 总裁"（不看书也不看线）
- 只有"发消息"这一条路径检查线

### 差在哪（产品层）

**1. 你在画布上画的网络，跟实际信息流无关。**
建了线不会让通信更容易，不建线也不妨碍——**线变成了装饰**。于是"节点网络"这个产品本体，在通信这一层没有落地。

**2. "谁该知道什么"不是拓扑算出来的，是写死的。**
你要的是"收件人由连线算"，现在是"父卡+总裁"硬编码，模型想发给谁就指定谁。⇒ 汇报关系混乱不是执行问题，是**收件人从来没按拓扑算过**。

**3. 消息不可统计，所以涌现指标没有数据源。**
涌现守门要看"自主连线率、横向互核数、环闭合率"——这三项的前提是**消息沿边走、能计数**。现在同步与指令都不落消息账本（实测账本里 `msg_sync` 和 `msg_directive` 各 0 条），它**没有数据可看**，只能去读对话文本。
⇒ 它退化成逐格核对员，是被这一条逼的。

**第 3 条把问题一和问题二连起来了**：职能退化成核对员，和通信脱离连线，是同一件事的两面——**因为没有可统计的通信，所以只能用人去读；因为用人去读，所以职能变成核对员。**

## 三、系统消息

### 你要它干什么

10-26 10:44 你的原话：「这不是一个附属功能，就是 harness 本身。事件管理、日志、消息层是一个模块，属于项目基础设施」「基于事件的提醒，只是节点里的一个服务，我们可以做，第三方也可以做」。

三句话定死了它的定位：
- **基础设施**，不是功能
- **系统有主动性**：看事、发现缺口、主动补
- **提醒本身是网里的一个节点**，可追溯

### 它现在实际是什么

**一条 if 判断**。

一条规则，判"这一轮有没有调 `report_up` 这个工具"，命中就塞一段固定文本进对方会话。

### 差在哪（产品层）

**1. "基础设施"退化成了"功能"。**
你要的是第三方也能基于它做提醒的平台；现在是一张写死的规则表，第三方接不进来，加一条规则要改配置文件。

**2. 判据盯的是"动作"，不是"结果"。**
规则判"有没有调 report_up"，不判"事情有没有做成"。模型调一次 `report_up`、内容写空，提醒就绕过去了。
你要的是"该发生而没发生的事"——那需要知道"什么叫发生"，而系统里没有这个定义，只有"哪个工具被调用过"。

**3. 提醒本身不是节点。**
系统说过什么、提醒过几次、提醒有没有被响应，都不可追溯、不可统计。它不参与"涌现"观测，也不挂在任何一条线上。

## 四、三条是同一个降级

| 你要的 | 现在给的 | 降级 |
|---|---|---|
| 参谋（专业判断） | 核对员（逐处对照） | **判断 → 核对** |
| 节点网络（沿边通信） | 群聊（点名广播） | **网络 → 群聊** |
| 基础设施（谁都能基于它做提醒） | 一条规则（写死的 if） | **基础设施 → 功能** |

**我的判断**：三次降级是同一个原因——**系统里没有"一张所有人都能读的图"**。

- 没有它，判断只能靠人复述（职能只能写长文、别人只能重读）
- 没有它，通信只能靠点名（收件人写死）
- 没有它，提醒只能靠 if（因为不知道"网里发生了什么"）

你的产品定义里，「网络」是本体；现在实现出来的是「一堆卡片 ＋ 一个群聊」，**网络这一层没有落地**。三个问题都是这一层缺失的下游表现。

## 五、再往下一层：真正的内核

上面说"没有一张所有人都能读的图"。再往下挖一层，图之所以建不起来，是因为：

> **系统把"文本"当成了"事实"。**

系统里**结构化的**只有身份类字段：`card_type` / `parent` / `links` / `perms` / `state` / `goal`——它们回答"我是谁、我爸是谁、我能不能改"。

而**所有真正重要的内容，全是自由文本**：需求、现状、裁定、判据、观点、汇报。系统对它们只知道两件事：**有多长**、**变没变**。

于是系统能验证"有没有写"，不能验证"写得对不对"。

### 这一条能统一解释全部现象

| 现象 | 由这个内核直接产生 |
|---|---|
| 写入不可验证（45,935→351） | 文本没有 schema。在系统眼里这只是"变了"，不是"错了" |
| 状态不显式 | 状态藏在句子里（"R1 已收口"），不是字段 ⇒ 查不到、判不了 |
| 可观测性缺失 | 文本没有凭证。"我改了"和"真改了"都是文本，无法区分 |
| 职能逐格巡检 | 验证文本只能靠"读"，读的活只能交给人（模型） |
| 通信不沿连线 | 文本不需要走边。边是给"可路由的事实"用的 |
| 系统消息只有一条 if | 只能对"工具被调用"这种结构化事件下判断；"事情做成没有"是文本，判不了 |
| 裁定权不清 | "谁裁的"是文本里的一句话，不是一条记录 ⇒ 两种说法可以同时成立 |
| 选型 16 分钟 6 轮 | 论证是文本，无法机械检验"有没有论证" |
| 同一事实 5 份副本 | 每份文本都不能被信任为最终态，只能各留一份 |
| 上下文膨胀 | 对齐靠"重读文本"，文本越写越长 |

### 为什么内容只能是文本

因为生成内容的是模型，模型输出的是文本。系统**只把文本原样存下来**，中间没有"把自由文本转成可校验事实"的环节。

所以缺的不只是"一张图"，是**一个把模型的话变成事实的环节**。图是它的容器，不是它的替代。

### 这也解释了为什么"加机制"总是失败

每加一道机制（权限、写闸、规则），约束都只能加在**动作**上——有没有调这个工具、有没有变、变了多少。加不到**内容**上——对不对、全不全、和别处一致不一致。

因为内容没有结构，没有可以下刀的地方。

⇒ 「纪律解决不了，因为问题不在谁不守纪律」这句话的机制解释：**系统能约束动作，不能约束内容。纪律管的是动作，所以它只能管到"做了没有"，管不到"做对没有"。**

## 六、卡面唯一怎么解

### 先说清它现在只落实了三分之一

| 维度 | 现状 |
|---|---|
| 存放处唯一 | ✅ 三块在 `cards` 表里各占一列 |
| **写入唯一** | ❌ 五个入口写不同块（`edit_card`/`update_status`/`append_ruling`/`curate_face`/`update_shadow`），消息通道还能绕过卡面传事实 |
| **时刻唯一** | ❌ 每人读的是自己那一刻的快照（fn_004 拿建卡前快照说"仍是旧句"） |
| **版本唯一** | ❌ 同一事实在需求块／现状块／总账／表体各存一份 |

**被频繁改动、常常出错，不是执行问题，是"唯一"只落实了存放处这一维。**

### 解法：把"卡面"从"一坨文本"变成"有主人的块 ＋ 有版本的事实"

每块补三个属性——**主人、版本、差异**。四个"不唯一"会同时收口。

**① 有主人 → 写入唯一**

一个写入口 `write(card, block, patch)`，权限从"能不能改这张卡"细化到"能不能改这个块"：
- 使命块：只有用户
- 现状块：只有这张卡自己
- 需求块：总裁（或按树指定执笔人）
- 台账：只有该职能

别人要改，只能**提请**（生成一条待确认），不能直接写。

同时解掉 45,935→351：`patch` 是差异集不是整块文本，**结构上不可能丢内容**。也解掉"只改一块被 `mission_locked` 拒"——单块写入本来就是常态。

**② 有版本 → 引用唯一、时刻唯一**

每块带版本号（`card_067/status@v21`）。要引用这份事实，写指针，不抄文本。

- 副本消失：总账、表体、消息里不再各存一份，只存指针
- 取值由系统按指针取，不是让人重读全文
- 指针带版本 ⇒ 块已更新时读者立刻知道"我引的是 v19，现在 v21"

收口时冻结一个**版本集合**（本次收口基于 `status@v19 + rulings@v24`），五方表态都针对它；快照之外的改动不进这次收口。
⇒ 「你读的是过期读数」这个指控在结构上消失。

**③ 有差异 → 同步变便宜**

改动产出"变了哪三处"，通知也带这个差异集，而不是让人重读全文。

这是让**正路比旁路便宜**的关键：现在写卡面比发消息贵（要权限、要整块、怕写坏），所以大家发消息。写卡面变成"改三行 ＋ 自动通知"之后，旁路就没有存在理由。

**④ 一条减法：砍掉派生副本**

"总账""表体"本质是同一批事实的另一种排版。有了指针之后它们不该再存在——应该是"指针列表的视图"，随取随渲染，不落第二份。
**副本的源头砍掉，一致性才有地方收敛。**

### 这不是新架构，是把现有零件接上线

- 三块**已经是独立列**（`cards.mission/status_block/rulings`）
- 版本**已经有**（`card_revisions`，每块一行、带 version）
- 差异**已经会算**（`_check_block_rules` 本来就在做分区 diff）

缺的只是把"列 + 版本 + diff"接成一个入口，并让引用走指针。

### 这套解法解不了什么（必须说清）

- **解不了内容对不对**——语义没有 ground truth，做不到
- **解不了该不该做这件事**——那是判断，不是事实
- **解不了"谁来裁"**——块级写权只解决"谁能写"，不解决"谁说了算"

它只解决一件事：**所有人看到的，是同一份、同一版、由同一个主人写的事实。**
