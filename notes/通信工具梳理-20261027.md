## 三、三个问题（按严重程度）

### ① `read_inbox` 是**死工具**，而它在被频繁调用

**121 次调用，一次也读不到东西。**

原因是我们上一轮把落点统一了：消息现在落**会话块**（进上下文），
`messages` 表不再写入新消息。而 `read_inbox` 读的正是 `messages` 表。

所以模型每次调它，拿到的都是空（或很早以前的旧数据）。它还会因此以为"没人给我发消息"。

**这是"落点统一"的连带后果——机制改了，工具没跟着删。**

### ② `scene_report` 与 `report_up` 完全重复

`scene_report` 的实现只有一行：`arguments.setdefault("kind", "done")` 然后转 `report_up`。

它多占一个工具位、多一个让模型犹豫的选择，而**语义上没有任何区别**（真实调用 3 次）。

### ③ `record_verdict` 376 次，但配套的 `verify_directive` **0 次**

职能台账是**单向的**：判词写了 376 条，指令核验一次没做过。

要么是这套台账没人用（写判词只是"表个态"），要么是核验环节根本没接上。
**这是职能机制的问题，不是通信工具的问题**，但它占了通信面的一个大位置。

## 四、按场景重排（我的建议）

通信不是"一坨工具"，是四个场景：

| 场景 | 该给谁 | 件 |
|---|---|---|
| **发话** | 作业卡 | `sync`（不叫醒）／`direct`（叫醒） |
| **向上** | 作业卡 | `report_up`（唯一的向上通道） |
| **建/解关系** | 所有卡 | `link_cards`／`unlink_cards`／`link_rel`／`unlink_rel` |
| **沿线读** | 所有卡 | `read_linked` |
| **治理**（改别人的状态） | 父卡/根卡 | `wake_card`／`stop_card`／`silence_card`／`stage_open`／`continue_task` |
| **评审** | 按角色 | `open_review`／`set_criteria`／`approve`／`revoke_approve`／`decide` |
| **职能台账** | 职能 | `record_verdict`／`issue_directive`／`verify_directive` |

**要删的两件**：

- `read_inbox` —— 消息已在上下文，没有"取件"这回事
- `scene_report` —— `report_up` 的壳，语义完全重复

**要查的一件**：

- `record_verdict` 376 次 / `verify_directive` 0 次 —— 台账单向，要么补上核验，要么这整套该退

## 五、删 `read_inbox` 的连带影响

它不是孤立的：

| 连带 | 说明 |
|---|---|
| `card_msg.TRIGGERS` | 发信时记的触发队列，现在只有 `read_inbox` 的"水位"在消费 |
| `msg_seen` 水位 | 只有 `read_inbox` 推进它 |
| `card_db.list_pending` / `take_pending` | `deliver_now` 还在用取件模式（虽然主要走 text 模式了） |
| `messages` 表 | 旧数据 1352 行，不再写入 |

删工具本身简单，**但要把这套水位/队列一起退役**，否则留着没人用的机制。
