> 本文分两层：**第一层＝根卡原文，逐字保留，不改写**；**第二层＝我的实证复核与分析，标明是我的判断**。

# 第一层 · 根卡的总结（原文，逐字保留）

## 病灶一句话

> 这个系统的机制让我只能靠"逐格核对 + 下指令改"来维持事实一致，而这个动作本身每次都产生新副本和新不一致。纪律解决不了，因为问题不在谁不守纪律。

## 四类机制缺失

| 机制缺失 | 本轮实证 | 新系统必须怎样 |
|---|---|---|
| **写入不可验证** | 整块覆盖式写：5 例事故（最近 7461B→90B）；我想只改现状块，但 edit_card 被"三块齐全"拦截，curate_face 够不到现状块→只能整块重写或放任滞后 | 分块独立写入；写前 diff 预览、拒绝"非预期块消失"；写入产生可验证的差异集 |
| **状态不显式** | 同一事实存 5 份副本（需求块/现状块/总账/表体/消息）→两读→派令→新两读；三态（未呈现/未点/点了没生效）系统内不可区分→卡死 8 轮；"轮次"不是状态 | 单一权威源＋字段级引用（不是人复制）；显式状态机（起草→已提交→待确认→已生效→已核） |
| **可观测性缺失** | 回执≠落面（5 例"报了已改但没调用"）；评审批次正文对被评卡和上级都读不到；职能卡读不到卡间消息→"答复存在但查不到" | 写入自带不可伪造增量凭证；评审/答复必须落可 read_card 载体；待确认队列可读 |
| **职能被设计成"逐格巡检"** | 每轮报同样的"第 N 处/第 N 轮"，我逐条回、逐条派，形成固定开销 | 职能只在四种情形开口：阶段放行／判据成立性／越界／用户令 |

## 根卡自己的判词

> 我这一轮最该记的，就一句话：我把"维持卡面事实一致"当成了总裁的工作，而这件事本该由系统机制完成，不该由人（或模型）逐格核对。

# 第二层 · 我的实证复核（全部可复算）

## 复核一 · 写入不可验证：成立，且比总结说的更严重

**整块覆盖事故，`card_revisions` 表实测三起**（判据：同一块相邻两版体积缩到 30% 以下）：

| 卡 | 块 | 版本 | 时刻 | 体积变化 |
|---|---|---|---|---|
| `card_038` | 需求文档 | v16 → v20 | 10-25 14:45 | **11,596 → 0 字** |
| `card_067` | 现状块 | v18 → v19 | 10-26 14:12 | **45,935 → 351 字（1%）** |
| `card_075` | 需求文档 | v22 → v24 | 10-26 20:57 | **7,461 → 38 字（1%）** |

根卡说"最近 7461B→90B"，实测是 `card_075` 需求块 7,461 → 38 字（字节数会略有差异），**同一起事故**。

**机制原因，可以指到具体代码行**：

- `card_tools._check_block_rules:7513` 规则④：「现状区 diff **不校验**（覆盖写·单一最新，本就该自由改）」——现状块写多少算多少，**没有任何"非预期缩减"检查**。
- 同函数注释：「[2026-10-22 用户裁定] 需求文档块**覆盖写·单一最新**，不再是只追加 ⇒ 原『规则②③ 超集校验』整条废除」——需求块原本有"只许追加"的保护，10-22 撤了。`card_038` 的 11,596→0 发生在这之后。

**"只能整块重写"这条，实测比总结更精确**：

`_check_block_rules` 规则①只在 `new_has_heading` 为真时才比使命块。于是：

- 带 `## 现状` 区头提交 → 使命区为空 → 规则①判"使命被改" → `mission_locked` 拒；
- **完全不带任何区头**（裸正文）→ 放行，整篇落进现状块。

也就是说：**模型想表达"我只改现状块"这个意图，反而会被拒；只有放弃声明意图（写裸正文）才放行。** 这是隐式陷阱，不是设计。

**"curate_face 够不到现状块"，实测成立**：

`_h_curate_face:4961` 只写 `rulings`（需求文档），且开头就 `if target_id == current_id: return err("curate_face 不用于自己——自己的面用 update_status")`。而子卡的 `status_block` **只有子卡自己 `update_status` 能写**。⇒ 总裁看到子卡现状块里的过期读数，**没有任何工具能直接改**，只能下指令请求。

**反向失控（总结未提，但同源）**：`card_076`（coder）现状块当前 **865,631 字**（86 万字）。现状块既无下限也无上限。

## 复核二 · 状态不显式：成立

**五份副本**能对上：`rulings`（需求块）／`status_block`（现状块）／`function_store` 的决策簿/台账（总账）／需求块里的表格（表体）／`messages`（消息）。同一条事实在五处各存一份，任一处更新都要人工同步其余四处。

**"轮次不是状态"，实测有两套计数**：`card_021` 的 `goal_rounds=1`，但事件流里有 **130 个 `run_start`**。`goal_rounds` 记的是 goal 驱动的预留轮次，`auto_driver` 的续轮不走这个计数器 ⇒ **"跑到第几轮"与"目标推进到哪"是两个不相干的数**。

## 复核三 · 可观测性缺失：成立，且三条都能指出具体缺口

**① 评审批次正文，确实无处可读**：

`review_batches` 表有 `focus`（评审正文）、`expected`（应审职能）、`status`。但全仓**没有任何读取工具**——`card_tools.py` 里只有写入与收集（4470 / 4519 / 4535），没有 `list_batches` / `get_batch`。

⇒ 被评卡（如 `card_074`）**不知道自己正被按什么焦点评**；上级（`card_001`）也读不到批次正文，只能从四条职能各自发来的消息里拼。而批次里还留着 `status=open` 的旧批次（10-26 00:43、10:58 两条）。

**② 职能卡读不到卡间消息，机制原因明确**：

`read_inbox` 的数据源是 `messages` 表。而 `sync`（`_h_scene_sync`）与 `direct`（`_h_scene_direct`）**都不写 `messages`**，只落会话块。实测 `messages` 表 1352 行里 `msg_sync=0`、`msg_directive=0`。

⇒ 职能用 `read_inbox` 查"有没有人答复我"，**永远查不到同步与指令**——"答复存在但查不到"是必然，不是偶然。

**③ 回执≠落面**：这条我没有逐例复算（需要比对每条"已改"自述与同轮 `tool_call` 记录），暂记为**未复核**。

## 复核四 · 职能逐格巡检：成立

`fn_007` 自报「第120轮」「第123轮」，`card_074` 的评审批次焦点写着「第129轮」。同一批判据被反复复述。

**但我的判断与总结不同**：这不是"职能被设计成逐格巡检"，而是**前三条缺失逼出来的**——因为写入不可验证、状态不显式、事实面不可信，职能是系统里唯一被授权"事后核对"的角色，所以它只能逐格核。它的职责书写的是"头尾介入"，实际干的是"逐格巡检"。

# 第三层 · 我的分析

## 一、四条不是并列的，是一条根 ＋ 三个下游

根卡把它们列成四类并列。我认为有依赖：

```
写入不可验证（根）
  ├─→ 状态不显式：写不可验证 ⇒ 只能多处留副本互相印证 ⇒ 副本越多越不一致
  ├─→ 可观测性缺失：写不产生凭证 ⇒ 只能靠"回执"自述 ⇒ 自述不可信 ⇒ 必须重读
  └─→ 职能逐格巡检：前两者 ⇒ 没有可信事实面 ⇒ 只能设人去核
```

**依据**：三条下游都能从根直接推出来，而根推不出来。具体说：

- 副本为什么是五份？因为任何一份都不能被信任为"最终态"，所以每一处都留一份"我看到的"。
- 为什么必须"实读原文、不采信转述"（fn_004/fn_005 的原话）？因为写入没有凭证，转述与事实无法区分。
- 为什么职能必须逐格核？因为没有人能证明"这一格已经对了"。

**这条判断的用处**：如果先修第四条（限制职能开口），前三条还在，事实会更不一致——因为巡检是当前唯一的兜底。**第四条是结果，不是措施。**

## 二、根卡那句自省，我认为归因反了

> 「我把"维持卡面事实一致"当成了总裁的工作，而这件事本该由系统机制完成。」

这句话把责任放在自己身上。但从机制看：

- 总裁是**唯一**有跨卡执笔权的角色（`curate_face` 写别人的需求块）；
- 而子卡的**现状块只有子卡自己能写**；
- 于是"事实不一致"一旦发生，总裁手里只有一条路：下指令让子卡自己改。

**它不是抢了这个活，是系统只给了它这一条路。** 区别在于：如果是"抢"，限制它的权限就能解决；如果是"只有这一条路"，限制权限只会让事实更不一致。

## 三、"纪律解决不了"这句，有原文硬支撑

模型自己在 10-24 09:47 写出了正确方法：

> 「论证 = 判据从哪来 + 每份证据怎么测出来的 + 结论对什么敏感 + 什么事实出现就改判。我做的 = 给结论 + 配一张作印象排版用的表 + 被反驳就换一版。」

用户在 10:03 的判词：

> 「技术选型的方法都不知道吗？**不是，你是知道的，你不按照正确的方法去做。**」

**它知道方法，但它不按方法做，而系统里没有任何东西在它不按方法做时拦住它。** 这就是"纪律 vs 机制"的分界线：纪律是"应该"，机制是"做不到就不让过"。

## 四、我要补一条：不可逆动作没有撤销通道

根卡的四类里没有这一条，我认为它独立（或至少值得单列）：

- `card_005`（编程卡）**删不掉**——「编程卡终身留档、不可删除」；
- 它搬过的文件**没有卡知道搬到了哪一步**（它没报完工，卡面查不到）；
- 整块覆盖 45,935→351 虽然能从 `card_revisions` 回退（每卡 20 版），但**回退是事后**，回退本身也是一次覆盖，没有 diff 预览。

⇒ 系统里存在**回不去的过去**。这既是"状态不显式"（没有"已撤销"这个状态），也是独立的一类：**动作不可逆**。

## 五、对"新系统必须怎样"那一列，我的看法

根卡给的四条对策，我认为不是并列的四件事，而是**一件事的四个面**：

| 根卡的对策 | 本质是同一件事的哪一面 |
|---|---|
| 分块独立写入 ＋ 写前 diff ＋ 拒绝非预期块消失 | 写入必须产出**可验证的差异集** |
| 单一权威源 ＋ 字段级引用 ＋ 显式状态机 | 状态必须**可判定**（不是靠人记） |
| 不可伪造增量凭证 ＋ 落 read_card 载体 ＋ 待确认队列可读 | 写入必须**可观测**（凭证不是自述） |
| 职能只四种情形开口 | 前三者成立后，巡检才**可能退场** |

**顺序上第四条必须最后**。这也是我唯一想提醒的一条：把"职能只在四种情形开口"当成第一刀砍下去，会立刻失去当前唯一的兜底。

## 六、我还没想清的

1. **"字段级引用"在模型上下文里长什么样？** 如果模型读到的是一句"见 card_067 §4.3 第 2 条"而不是值，它还是得去读——一致性解决了，但**读取成本没降**。这可能把"复制不一致"换成"指针追不完"。
2. **"待确认队列可读"——谁确认？** 如果是用户，用户会成为唯一瓶颈（现在已经是：用户 10-26 在总裁卡上说了 121 次话，大半是在替系统核对状态）。
3. **"拒绝非预期块消失"的判据是什么？** 块从 45,935 缩到 351 是明显事故，但"合法重写"也可能是大幅缩减。判据如果靠阈值，就会重演"设闸"的老问题；如果不靠阈值，靠什么？
