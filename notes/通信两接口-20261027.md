# 通信两接口：唤醒 / 同步（2026-10-27）

> 用户五条裁定：
> 1. 卡片通信只取决于卡片自己的两个接口：**唤醒、同步**
> 2. **唤醒以用户消息去包装**，同步则只是出现在上下文历史中
> 3. 样式上同步已有专属样式，**唤醒也需要专属样式**；对模型两者都是 user 消息，都要**转述特质**
> 4. **inbox 直接取消**，没意义——消息留在上下文里直到被凝练掉（**要确保它进凝练**）
> 5. 工具面变成**按场景搭配能力**

---

## 一、先修的前提：消息块原来**不进凝练**

第 4 条说「消息留在上下文里直到被凝练掉」，我去查了凝练的判据：

```python
# src/storage/predicates.py
MESSAGE_TYPES = {"user_message", "assistant_text", "tool_call", "tool_result"}
def is_original_event(block, etype):
    if etype not in MESSAGE_TYPES:
        return False        # ← msg_sync / msg_directive 全在这里被判 false
```

**卡间消息块的事件型是 `msg_sync` / `msg_directive` / …，不在这个集合里 ⇒ 永远不进凝练。**

后果：消息落在上下文里，凝练时被跳过，**只增不减**，永久占上下文。
`inbox` 一旦取消，这条通道就会成为上下文膨胀的新来源。

**已修**：`MESSAGE_TYPES` 纳入全部 `msg_*` 与 `coder_done`。实测：

```
msg_sync       算原文=True  进凝练=True
msg_directive  算原文=True  进凝练=True
msg_notify     算原文=True  进凝练=True
msg_report     算原文=True  进凝练=True
coder_done     算原文=True  进凝练=True
msg_ask        算原文=True  进凝练=True
msg_answer     算原文=True  进凝练=True
```

## 三、为什么"唤醒 = text 模式"

用户第 2 条：**唤醒以用户消息去包装**。

实现上就是 `deliver_now(text=激励文)`：
- 消息正文已在会话块里（上下文历史）
- 唤醒只负责**起一轮**，prompt 是一句「你收到一条来自 X 的消息，正文已在上文」
- 模型看到的是 role=user 的输入 ⇒ 会当轮处理
- 不落 user 块（`append_user=False`）⇒ 不冒充用户说的话

`sync` 则连这一步都不做：只落会话块，等它下次回合自然看到。

## 四、样式（第 3 条）：现状

| | 人类侧 | 模型侧 |
|---|---|---|
| 同步 | **已有专属样式**（前端认 `card:` 前缀） | role=user ＋ 转述头「卡 X（《标题》）给你发来一条同步」 |
| 唤醒 | **还没有** | 同上（转述头）＋ 那句激励文 |

**唤醒的专属样式还没做**——前端目前只按 `card:` 前缀渲染成消息块，分不出这条是"只通知"还是"叫起来干活"。
