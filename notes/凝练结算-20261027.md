# 凝练以 sqlite 结算（2026-10-27）

> 用户令：「凝练水位的计算，凝练窗口的投递，应该都只以 sqlite 的信息来结算。
> 这样，我们哪些信息要进凝练窗口，就把这个信息存进 sqlite 就行了。」

第一版我做错了：发现库不可靠就**退回读文件**。用户的原则是「库就是结算依据」——
**该把库修可靠，不是退回文件**。已改。

---

## 一、改了什么

### ① 读数入口统一到库

`memory_store._read_origin(work_id, card_id, mark)` —— **凝练唯一读数入口**：

```python
def _read_origin(work_id, card_id, mark=0):
    return origin_store.read_blocks(work_id, card_id, from_seq=int(mark or 0))
```

4 处读点全换（`condense_turn_end` / `condense_sweep_once` / `condense_before_send` 两处）。
`memory_store` 里已无 `session_facade.read`。

### ② 水位按 seq，不再当列表下标

改前：`pending = prior[mark:]` —— `mark` 是 **seq 水位**（`target_mark = 窗口末块 seq + 1`），
却当**列表下标**用。seq 连续时碰巧对，**有空洞就错位**。

改后：`from_seq=mark` 直接交给 SQL 的 `seq >= ?`。

### ③ 库写失败不再静默

```python
except Exception as exc:
    _DB_WRITE_FAILS += 1                     # 累计计数
    _LAST_WRITE_FAIL[0] = {work, card, n, err}
    logger.error("[origin] 原文写库失败（凝练将漏掉这批块，需 backfill）…")
    return 0
```

新增 `origin_store.db_health()` → `{write_fails, last_fail, last_ok_at}`。
**这是「库还信不信得过」的唯一可观测面**——凝练以库结算后，没有它就只能靠猜。

仍然不抛：md 已落盘，库可由 `scripts/backfill_session_blocks.py` 补回；抛了会让一轮对话因副本失败而失败。

## 三、顺手修掉的真 bug：消息块从来没进过凝练


**以后谁绕过门面直接写会话，凝练就读不到那批块**——这是「以库结算」的代价，

## 为什么还是回退了

改 `routes.py:2808` 一行，跑宽面测试破 6 个。但**每个都单跑通过、一起跑才破**——
说明是**测试间耦合**（有测试走 `session_store.append_message`，那条路只写 md 不写库，
读库自然读不到；而它是否污染后续用例取决于执行顺序）。

把 `session_store.append_message` 改成委托门面，破得更多（11 个）——
因为它会把 md 格式从 V1 变成 V2，连带破「V1→V2 升格」那组测试。

**结论：这不是改一行的事。** 要切需要两件配套：

1. **统一写入路径**：`session_store.append_message` 要么委托门面、要么删掉。
   但它一改就动 md 格式，要连带处理升格测试。
2. **排查测试耦合**：`session_store.append_message` 的 14 处测试调用要么改走门面，
   要么给 fixture 加隔离。

两件都是独立一轮的量。**当前状态：凝练只读库（已生效于代码）、上下文读 md（未改）。**
两边来源不同这一点，在 `routes.py:2808` 的注释里写明了。
