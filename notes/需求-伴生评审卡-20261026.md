# 需求 · 伴生评审卡（2026-10-26）

> 状态：需求已捋，**未施工**。本文取代 `需求-评审临时卡-20261026.md`（那份把结构写成"一次性临时卡"，已作废）。
> 一句话：**每个 sub_project 卡自带一张评审卡；评审是这张卡上的批次，批次内全员 `approve` 才收口。**

---

## 一、要解决的问题（实测）

`card_061` 一次阶段收尾：11:03 → 14:07 **3 小时、26 条往返**，fn_004 与 fn_005 交替，标题里"补件轮四／轮五／轮九／轮十／第十一轮／终核"逐轮递增。

**对账周期 = 轮次 ×（排队等待 ＋ 上下文重读 ＋ 往返投递）**，四个乘数全踩。

**根因**：评审这个动作**没有形状**——没有固定输入、固定输出、终止条件。

---

## 二、结构：四层

```
sub_project 卡（发起方／干活方）
  └ 评审卡（伴生，一对一，随子卡归档）
      └ 批次（每个阶段一次：R1 收尾、R2 收尾…）
          └ 轮（批次内 approve 的迭代）
```

**伴生卡的定义** `[P7]`：建子卡时系统自动建，一对一，`off_tree`、不设 `parent`、`review_of` 指向子卡，子卡归档时一起归档。

**它和影子卡同族**：都是"每张卡自动派生、不进任务树、随正卡生死"。影子记过程，评审卡记验收。

---

## 三、批次内的流程

1. **开批次**：子卡要评审 → 在评审卡上开一个批次，写清 **焦点**、**判据**（卡面第三块）、**待评审的卡面草稿**（冻结版本）。
2. **召集**：所有在职职能以本职能角色参与 `[P1]`（成员＝用 `relations` 连到评审卡的那些卡）。
3. **表态**：每个角色对同一份草稿独立判断。调 `approve` ＝ 通过；不调 ＝ 未通过。
4. **收敛**：有人没过 → 发起方改草稿 → 下一轮，直到全员 `approve`。
5. **收口**：全员通过 → 出**正稿** → 批次关闭。
6. **下一批次只带上一批次的正稿**，本批次的过程（发言、工具结果）留在会话里归档，不进上下文 `[P6]`。

**正稿落评审卡卡面** `[P1]`：它是完整长文本，不摘要、不截断、不结构化 `[P2][P6]`。

## 四、机制约束

| # | 约束 | 理由 |
|---|---|---|
| 1 | `approve` 是唯一工具，没有 `reject` | 不通过＝不调工具。两个工具多一个岔路 |
| 2 | 默认未通过 | 若默认通过，沉默就等于放行 |
| 3 | 通过后不再讨论 | 工具不可分割，结构上排除"通过但两处要改"这个第三态 |
| 4 | `approve` 绑定**（草稿版本 ＋ 判据版本）** | 任一变化即作废，否则"没看新版也算通过" |
| 5 | 草稿一变，全员重评 | 不要求发起方声明"改了哪几条"——那是靠自觉 |
| 6 | 什么都没调 ＝ 未完成 | 既非通过也非不通过，是"该做没做"，交给系统提醒 |
| 7 | 共用事实，不共用观点 | 判据依据是卡面草稿；工具结果在批次内保留共享，避免四方各读一遍 |
| 8 | 评审不写别人的卡面 | 卡面归主人 `[P1]`；评审只出结论，子卡自己改 |

## 六、必须拆掉的旧件（互斥，不是清理）

新旧并存，模型会两套都用（`review_request` 与 `direct`/`sync` 并存已演过一次）。旧工具必须**从工具面物理移除** `[P4][P5]`。

| 旧件 | 为什么必须拆 |
|---|---|
| `review_request` | 被"开批次"取代，留着有两条发起路径 |
| `review_batches` 表 | 批次改由事件＋卡面承载 |
| `submit_review` | **`verdict` 是自由文本 ⇒ "通过但两处"合法 ⇒ 收齐≠通过。这是 26 轮的直接来源** |
| `completeness` | 判"都提交了"，不判"都通过了" |
| `close_batch` ＋唤醒总裁 | 全员通过后结论已明，不需汇总再裁 |
| `_invite_function_room` | 广播唤醒，被"召集进评审卡"取代 |
| `function_sync`／`notify_event`／`spawn_opinion` | 职能不再被消息叫醒，改为进现场（且词表早已错配） |
| `stage_open`／`report_up` 里的邀请 | 语义保留，实现改为"开批次" |
| `peers_opinions` | 现场里观点已互相可见 |

`review_batches` 在 `routes.py` 与 `static/esm/` **零引用**，拆掉无界面损失。

## 七、UI

### 1. 左栏：**激活才出现入口**

平时评审卡不在树上。只有存在进行中批次时，**子卡节点旁**出现入口（`〔评审 3/4〕`），点击进评审卡。

不常驻"评审"分组——那会让左栏永远挂着几十个空壳。

### 2. 画布：它是节点，用 `relations` 连

`[P1]` 节点就是节点。连法：发起方／被评审卡／参与职能 → 评审卡，用 `relations`，`detail` 写清"发起／被评／参与"。**不新增线类型。**

### 3. 评审卡页面

复用普通对话页 `[P2]`，多两样：顶部判据／轮次条，发言左侧状态点。

必须有：**角色状态点**（●通过＋通过的版本／○未表态／—未参与）、**每轮结果**（谁没过、哪条判据、理由）、**草稿 diff**。

### 4. 用户是甲方，不是旁听

能看、能说、能纠正、能裁决。**发言与动作的区别不是谁按的按钮，是留痕形态** `[P3]`：

- **发言**＝文本，进上下文，靠模型理解才生效
- **动作**＝工具调用（`set_criteria`／`revoke_approve`／`decide`），当场改状态、留痕、可撤

用户说「C-3 不对，应该改成X」→ 模型调 `set_criteria` → 判据版本 +1、通过作废。

### 5. 证据可见

角色调阅工具的结果留在现场，**用户也看得到**——否则无从纠正。

## 十、评审上下文怎么构造（2026-10-27 用户补充，硬要求）

### 输入由谁给、给什么

**发起方（子卡）调评审时必须填清三样**：
1. **任务背景**——这件事为什么存在
2. **当前状况**——做到哪了
3. **要评审的内容**——这次评什么

**填的内容原样进上下文，不可截断**（P6：换上下文，不压缩）。

**子卡的三块（使命／现状／需求文档）原样进上下文**——它们是已知信息的唯一事实源（P1）。

### 谁参与

评审卡**自动邀请相关职能卡，包括 CEO**（不是"在职非总裁"，是含总裁）。

### 上下文边界（关键）

**评审的内容，不进各自职能卡的上下文。**

评审卡是**场地**，职能是**视角**。视角进场用场地，不把自己屋子弄脏。

### 执行模型（由此推出）

职能卡参与评审时：

| 用什么 | 从哪来 |
|---|---|
| **上下文／会话** | **评审卡**（不是职能卡自己的会话） |
| **模型** | **职能卡上配置的模型** |
| **身份与职能提示词** | **切换成该职能卡的信息**（职责书、管辖、发言契约） |
| **工具面** | 该职能的 perms（含 `approve`） |

⇒ 一次评审发言 = 「用职能的模型 ＋ 职能的身份提示词，在评审卡的上下文里跑一轮」。
职能卡自己的会话**零写入**——所以评审历史不会污染它的日常上下文。

**对实现的含义**：`approve` 不是"职能在自己回合里调"，而是"评审卡跑一轮时以职能身份调"。
这需要一个"以某职能身份、在某评审卡上下文中发言"的执行器，**复用现有回合内核**（不自造第二套）。
