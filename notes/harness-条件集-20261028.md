# harness 条件集（第二个东西）· 建成记录（2026-10-28）

> 用户规格（第一手）：
> 「一个是条件集，数据集根据条件集的【激活状态的策略】来进行状态记录，
> 一旦出现符合策略的条件，就触发 harness 任务。」
> 「触发了 harness 任务，这条状态就应该清掉重新记录。」

代码：`src/infra/policy_set.py`（值班员与小本子）、`src/infra/policy_runner.py`（接线与投递）、
`src/infra/policy_config.py`、`config/harness_policies.json`
测试：`tests/test_policy_set.py`（24）、`tests/test_policy_runner.py`（7）

---

## 一、一条策略＝一个值班员

```json
{
  "id": "parent_dispatched_no_report",
  "active": true,
  "desc": "父卡派过活的子卡，干完了却没汇报",
  "scope":  {"kind": "relation"},
  "watch":  ["msg_directive", "msg_notify", "tool_result", "done"],
  "window": "24h",
  "when":   { ...条件树... },
  "then":   {"target": "self", "message": "...", "wake": true}
}
```

他不翻台账：事情一发生就送到他手上，他往自己的小本子上记一笔；账凑够条件就喊人，
喊完把本子撕了重记。

## 二、三个关键设计

**一、本子是「每个作用域一份」，不是「每条策略一份」。**

| scope.kind | 一本代表 | 例子 |
|---|---|---|
| `card` | 一张卡 | 这张卡连续失败三次 |
| `relation` | **一对父子** | 这个父卡对这个子卡派了活没回音 |
| `work` | 整个 work | 这个 work 一天没完工 |

「父卡对子卡做了什么」的状态不挂在某一张卡上，而是挂在每一对 `(父, 子)` 上。
新子卡建出来自动多一本空本子——不需要谁去登记（实测 work_027 建了 26 本）。

**二、只记自己关心的那几类事。** `watch` 声明关心哪几类事件，事件进来先按类型找
关心它的值班员（倒排），其余连看都不看。这是「N 条策略不会全跑」的来源。

**三、喊完只撕那一本。** 父子 A 触发了，父子 B 的本子原样不动；清零后要重新攒够
才会再喊。清零本身防了重复触发，原来的 `harness_fired` 防重表因此退役。

## 三、条件树补了 `after`（这一步的硬缺口）

原来只有 `event` / `count` / `field` / `all` / `any` / `not`，表达的是「窗口内有没有」。
但「干完了没汇报」是**先后关系**：

> 用「24 小时内没有 report_up」来表达，上一轮的汇报会把这一轮盖住——
> 24 小时内汇报过一次，之后永远不提醒。

所以加了：

```json
{"after": {"anchor": {"types": ["done"]},
           "expect": {"types": ["tool_result"], "where": {"tool": "report_up", "ok": {"eq": true}}}}}
```

语义：窗口内有 anchor，且**最近一次** anchor 之后没有 expect。anchor 之前的 expect 不算。

顺带让比较器认符号写法（`">="` → `"ge"`），写配置更自然。

## 四、接线

```
event_log.append 落盘成功
  └ policy_runner.feed(work, rec)
      ├ fact_store.ingest        写库（冷，0.29 ms）
      ├ policy_set.dispatch      喂关心它的值班员（热，内存，10 µs）
      └ 有人凑够 ⇒ 后台投递（复用 harness.deliver，不另造通道）
```

- **写库同步**：0.29 ms/条，相对事件落盘的 fsync 不算什么；而且数据集必须立刻有这条事实，
  否则新建策略回溯时会漏掉刚发生的事。
- **投递异步**：要落会话块、发事件、必要时起一轮，绝不能在落盘的调用栈里做。
- **旧路径保留**：`ECO_HARNESS_LEGACY=1` 可一键回到「规则表 + harness.fire」，
  便于出问题时回退。`test_harness_turn_end.py` 就是守着这条旧路径的（12 个用例）。

## 五、真实数据验证（work_027，243,186 条事实）

**喂食成本**：逐条 dispatch 24.3 万条 ⇒ **2497 ms（每条 10 微秒）**。
这就是「触发式」的代价——不查历史，只改内存里几个计数器。

**三条策略实测**：

| 策略 | 结果 |
|---|---|
| 某张卡 24h 内工具调用 ≥10 | 触发 12 次，7 本（card_104 反复凑够） |
| 某对父子 24h 内工具调用 ≥5 | 触发 17 次，2 本（card_001 → card_104） |
| 根卡 done 之后没有成功汇报 | 触发 48 次（48 个 done，每个一次） |
| 配置里的示例（父卡派活没汇报） | **0 次**——最后 24h 内根本没有消息事件 |

最后一条不是机制坏了：work_027 最后 24 小时的 1,079 条事实里，消息事件是 **0 条**，
`from` 字段全空（历史数据产生于补字段之前）。条件不该成立。

## 六、一个必须知道的现象

**「done 后没汇报」在历史回放里触发了 48 次**——每个 done 一次。

这在语义上是对的（每次干完没汇报就该催一次），但实时运行时要注意：
提醒 → 唤醒 → 模型可能没 report_up → 又 done → 又提醒。

如果模型始终不汇报，这条策略会一直催。**这是策略配置的问题，不是机制的问题**——
机制保证「每次条件成立就触发」，催不催、催几次由策略决定。

## 七、撤掉的一处（第 1 步的错）

第 1 步给 `msg_report` 加了 `kind` 零件（done/phase/blocked/ask）。
但 2026-10-28 的裁定是「**汇报就是汇报，没有 kind**——工作有问题，上级自然会 direct 下发修改」，
`_h_report_up` 的入参已经去掉了 kind。

所以：`config/event_catalog.json` 里 `msg_report.fields.part` 去掉 `kind`，
对应的过期测试删除。**这是撤销我自己逆着裁定的改动。**

## 九、语义修正：`done` 不是任务完成（2026-10-28 用户指出）

用户原话：

> 语义是错的，done 是每轮的收口，不是任务完成。每说一句话都要汇报，那就大错特错了。

**我错在哪**：把 `done` 当"干完了"的锚点。但 `done` 是**回合收口**——说一句话也算一轮，
拿它当锚点等于要求模型每轮都汇报。

**「阶段完成」以什么为准：尚未定论。**

用户 2026-10-28 明确：「不要着急给这条策略定调，先让它失效。」
所以示例策略 `active=false`，只作**格式示范**。下面这两个只是**候选信号**，不是结论：

| 候选信号 | 含义 | 线上出现 |
|---|---|---|
| `goal/change` 且 `operation=complete` | 目标被标记完成 | 30 次 |
| `coder_done` | 编程卡完工回报（发给父卡） | 有 |

策略定义保留成这个样子（**未启用**）：

```json
{
  "id": "goal_completed_no_report",
  "scope": {"kind": "card"},
  "watch": ["goal/change", "tool_result", "coder_done"],
  "window": "24h",
  "when": {"after": {
    "anchor": {"types": ["goal/change"], "where": {"operation": "complete"}},
    "expect": {"types": ["tool_result"], "where": {"tool": "report_up", "ok": {"eq": true}}}
  }},
  "then": {"target": "parent", "message": "..."}
}
```

配置文件的 `_meta` 里也写死了这条警告：**绝不要把 `done` 当任务完成**。

**实测只用来验证机制，不代表认可这个语义（work_027）**：

| 窗口 | 回放条数 | 耗时 | 窗口内 goal complete | 触发 |
|---|---|---|---|---|
| 24h | 1,079 | 169 ms | **0 条** | 0 次（那 24h 没人标完成） |
| 48h | 54,490 | 11.0 s | 19 条 | 19 次（每个 complete 一次） |

⇒ 说明「锚点 + 之后没有 X」这套写法在真实数据上是通的；**用不用、锚在哪，等你定**。

## 十、修掉一个 O(n²)

`State.prune` 原来每次都遍历整个本子重建列表。7 天窗 + 24 万条事件时直接跑不完。

改成**只从头部剔**（本子按时间追加，超窗的必然在最前面）⇒ O(被剔除数)。

修完：48h / 5.4 万条回放 11 秒（每条 0.2 ms，主要成本是 entries 大的卡上求值扫全表）。
实时场景（一天约一千条）是 169 ms 量级。

**已知成本**：条件求值是 O(窗口内条目数)。窗口越大、条目越多，每条事件求值越贵。
真实负载（一天几千条、窗口 24h）在毫秒级；回放整周数据会明显变慢，那是压力测试不是日常。
