> 用户三条裁定：
> 1. 「建表，所有的通信必须基于底层，而不是基于卡本身，而且要三张表吧？」
> 2. 「父子之间，是建卡的同时，同时建两条线，一个是父子关系线，一个是 link 通信线，靠通信线通信」
> 3. 「你先把【能实现自动通知】的底层能力具备了，要不要自动通知，后续都可以开关」

## 一、三张表

```sql
card_parent    (card_id PK, parent_id, created_at)      -- 一张卡一个父
               idx: parent_id                            -- 查直接子卡
card_links     (from_card, to_card, type, note, created_at)
               PK(from_card,to_card,type)                -- 可多条，按 type 区分
               idx: to_card                              -- 查谁连了我
card_relations (from_card, to_card, kind, detail, created_at)
               PK(from_card,to_card,kind)
               idx: to_card                              -- 查谁依赖我
```

**三张不是一张**：约束不同。parent 一张卡只能一个父（主键即卡号），通用边表表达不了"唯一"；
links/relations 可多条、字段不同，合并会让字段退化成 JSON。

**links 存一行、双向可用**：判据是 `(from=A,to=B) OR (from=B,to=A)`。
存两行会有"删一半"的中间态。这与改前 `check_linked`「任一侧有就算有线」语义一致。

## 二、建卡同时落两条线

`create_card` 的写事务里，`insert_card` 之后：

```python
if _pid:
    card_db.upsert_parent(conn, card_id, _pid, now)                    # 父子关系线
    card_db.upsert_link(conn, card_id, _pid, "关联", "父子默认通信线", now)  # 默认通信线
```

于是「父子能通信」不再是 parent 边自带的能力，而是**那条默认 link** 的作用。

**换父时**：旧的默认线删掉、给新父补一条（父子关系断了，默认线也该断）。
**`links` 整块覆盖时**：保留默认线（它不在 cards.links 字段里，不保留会被一次
`link_cards` 顺手清掉，父子通信无声断掉）。

## 三、唯一写门拦截

不在四个 handler 里各改一遍——在 `update_card` 这个**唯一写门**里同步：

```python
card_db.update_card_row(conn, card_id, meta_patch, body_patch)
_sync_edges(conn, card_id, updates, now)     # ← 新增
```

`updates` 带 `parent`/`links`/`relations` 就同步进表。任何走 `update_card` 的
调用方（handler、脚本、测试）都自动覆盖，**结构上漏不掉**。

`cards` 上的同名字段照旧写，作为**回退**：边表读不到时（迁移失败/空库）
`iter_card_metas` 回退到字段，系统仍可用。验证稳定后再停写字段（那一步单独做）。

## 四、删卡清边

`delete_card` 的写事务里，`delete_card_row` 之后调 `clear_edges_of`：
作父、作子、作两端，三个方向一起清。

改前靠人调 `unlink_cards` 清悬空线，漏一次就留一条指向空气的线。

## 五、迁移：自动、幂等、只读字段

挂在 `_ensure_tables`（每次建连接都跑）：

```python
for ddl in _EDGES_DDL:
    conn.execute(ddl)
_migrate_edges_from_cards(conn)     # INSERT OR IGNORE，幂等
```

- **只读 cards、只写新表**——`cards.parent/links/relations` 一个字节不改，迁移错了删表重来
- 存量 work 首次连接即完成搬迁；新 work 建卡时同步写入（不走这条）
- 坏 JSON 当空处理，不炸迁移
- **给存量父子补默认通信线**：新建卡在 `create_card` 里已经补，存量卡没有 ⇒ 迁移时补。
  不补的话「父子默认有线」只对新卡成立——将来拆掉 `_is_in_subtree` 退路，存量父子会立刻断。
  父子之间已有「关联」线的就不补（`INSERT OR IGNORE` 按 (from,to,type) 去重）

### 踩到的坑（值得记）

第一版验证脚本用 `shutil.copyfile` 备份，**6 个 work 报 `no such table: cards`**。
原因是这些库是 **WAL 模式**——主库文件是空的，数据在 `-wal` 里。

改用 `sqlite3.connect(源).backup(目标)` 后 60 个全过，而且 **relations 从 7 涨到 27**
——之前漏读的 20 条全在 WAL 里。

**教训**：验 SQLite 存量数据不能 `copyfile`，必须用 backup API。

## 七、依赖通知：能力具备，开关后置

`src/api/edge_notify.py` + `config/edge_notify.json`（`dependency_change_notify: false`）。

三件底层能力：

| 能力 | 在哪 |
|---|---|
| 查「谁依赖我」 | `card_db.dependents_of` / `dependents_detail`（`idx_card_relations_to` 索引） |
| 卡面变更时能触发 | `update_card` 的后置钩子（与评审重评同一个位置） |
| 能发同步 | `session_facade.append_card_message`（落上下文、不唤醒） |

**为什么不会自激**：通知只写会话块、不碰卡面 ⇒ 不触发 `update_card` ⇒ 没有环。

打开后发的内容：

```
【依赖变更】card_A 的**现状**变了。
你在依赖线里声明过：依赖 A 现状块里的接口清单
迭代前请确认：你依赖的那部分是否受影响；受影响就同步改，并通知你的下游。
```

## 十、删后门（第 4 条）

### 删之前先验覆盖率

```
扫描 60 个 work，父子对 229 对
没有通信线的父子对：0
```

**229 对父子 100% 有线**（建卡时补 ＋ 迁移时补），所以拆掉「祖先-后代」退回不会让现存纵向协作断。

### 三处后门，全拆

| 在哪 | 改前 | 改后 |
|---|---|---|
| `_h_send_card_message` | `check_linked` **或** `_is_in_subtree` 任一即放行 | **只认 `check_linked`** |
| `_h_scene_sync` | 收件人＝显式 `card_ids` → `links` → **`parent` 兜底**，都不校验 | 只沿 `links`；每个收件人都要 `check_linked`，不过的进 `refused` 如实返回 |
| `_h_scene_direct` | 只校验 `_is_in_subtree` | 子树（权限）**＋** 通信线（通信）两道 |

### 由此产生的行为变化（三条，要记住）

1. **`sync` 显式点名不再能绕过线**：以前给任意卡号就能发，现在必须有线，否则被拒并列进 `refused`。
2. **根卡不能直接给孙子卡下指令了**：根卡与孙子卡之间没有默认线（默认线只在直接父子之间），要先 `link_cards`。
3. **`report_up` 保持系统算收件人，不走线校验**。判断依据：它不是「模型选收件人发信」，是**组织通道**（向上汇报，收件人由系统按关系算）。如果也要求线，总裁就得和每张卡都连线，线会退化成"全连"。

### 机制自己抓到了我漏的一步

删完后门，`test_system_claims::test_unmet_is_honest` 立刻红：


—— `UNMET` 的双向约束起了作用：**修好了不删登记表也红**。已从 `UNMET` 移除该条。

## 十一、拆开关（第 2 条）

### 三个开关位

```python
SWITCH_LINK       = "link"        # 建通信线
SWITCH_UNLINK     = "unlink"      # 解通信线
SWITCH_LINK_REL   = "link_rel"    # 建依赖线   ← 新增
```

### 存量数据两处补齐

| 补什么 | 在哪 | 数量 |
|---|---|---|
| `config/permissions.json` 各卡型的开关列表 | 脚本追加 | 16 个位置 |
| 存量卡的 `perms` | `card_db._ensure_link_rel_perm`（挂在 `_ensure_tables`，只加不减） | 有 `link` 的卡自动补 |

**为什么必须补**：改前有连线权的卡本来就能建依赖线。拆开后不补 ⇒ **功能倒退**（能建通信线却不能建依赖线）。

## 十五、两条没做，理由

### ① 四个 handler 改「直接表操作」——不做

原计划：`link_cards`/`unlink_cards`/`link_rel`/`unlink_rel` 绕过 `update_card`，直接写表。

查了 `update_card` 之后才发现它不只写字段，还做四件事：
**记修改历史（`card_history`）、存块版本（`card_revisions`）、刷画布缓存、广播工作级事件**。

绕过去省下的只是一次全量替换，丢掉的却是这四件。**收益不抵风险，不做。**

现在的双写方式（`update_card` → `_sync_edges`）功能正确，只是多一次整块替换——
等哪天 `update_card` 本身被拆细了再顺手优化。

### ② 删 `cards` 上三个旧字段——暂不删

对齐已验证（60 个 work、0 处不一致），但删之前要先改 **11 处读 `row["parent"/"links"/"relations"]` 的地方**：

```
context_assembler.py  2 处（含依赖区渲染）
canvas_store.py       2 处（画布投影）
card_archive.py       1 处
coder_archive.py      2 处
review_store.py       3 处
card_store.py         1 处（_subtree_ids，同步上下文）
```

其中 `_subtree_ids` 是**同步**函数，改成查表要动调用链；`review_store` 那三处还在伴生评审卡的
热路径上。而且 `ALTER TABLE DROP COLUMN` **不可逆**。

现在双写、两份数据一致、**没有功能问题**。建议：
**重启跑一轮确认边表在生产稳定 → 再删字段**（那时一次性改完 11 处，风险可控）。
