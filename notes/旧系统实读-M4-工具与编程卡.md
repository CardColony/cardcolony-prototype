## 3. 动作确认 pending_action（状态机）

### 3.1 登记结论（重要）

**任务所要求的 `pending_action` 机制在当前代码树中未实现。** 具体证据：

- 设计文档 `docs/卡片工具区域化与确认制-任务书-20261014.md` 描述的新模块 `src/api/pending_action.py`（进程内 `PendingAction{id, work_id, card_id, kind, payload, event: asyncio.Event, result}` + 600s 超时 + `pending_action`/`pending_resolved` 事件）**文件不存在**：
```
$ ls src/api/pending_action.py  →  No such file or directory
```
- `event_stream.EVENT_TYPES`（`event_stream.py:93-124`）**不含** `pending_action` 与 `pending_resolved`，仅含 `run_start/context/round_start/.../turn_end` 等 29 类事件。
- `create_card` handler（`card_tools.py:627` 直接 `card_store.create_card(...)`，`:641` 仅判 `"error" in result`）与 `delete_card` handler **直接执行、不落 pending、不挂起、无 asyncio.Event、无超时**。

→ 因此「模型调什么工具会触发挂起 / 挂起存在哪里 / Event/轮询等待 / 超时多长 / 三终态事件名与处理函数 / 挂起后恢复」这套状态机**在代码中无对应实现**。按硬要求登记为 **【未解 / 未实现——代码树中无 pending_action 模块及其事件类型】**，不猜测。

### 3.2 代码树中实际存在的「动作确认类」近似机制（供参考，非 pending_action）

以下两件是被实读到的、名称/语义接近「确认/挂起」的真实代码，但与任务描述的 asyncio.Event+超时三态机制**不是同一套**：

**(a) `confirm_with_user`（总裁专用）** — `card_tools.py:5033` / 注册 `:5158`
- 仅向用户发起确认：写 `function_store.add_verdict` + `event_stream.emit(work_id, current_id, "ceo_confirm_requested", {...})`（`:5058`），然后**立即返回** `{"asked": True, "premises": len(items), "text": ...}`（`:5061`）。**不挂起本回合、不 await、无超时、无 confirm/reject/timeout 终态事件**——它只是发一个事件并继续。

**(b) 角色指令验收流 `issue_directive` / `verify_directive`** — 状态值 `issued / rejected / overdue`
- `card_tools.py:751-767`：编程卡/`update_goal(complete)` 收口前查 `role_room.open_directives_for(...)`，若有 `issued/rejected/overdue` 未验收指令则**拒收口**（非悬挂，是即时拒绝）：
```python
# （issued/rejected/overdue）时不许收口；出路由角色 verify_directive
_blockers = role_room.open_directives_for(work_id, current_id)
...
return err("validation",
           f"收口被拒：本卡还有 {len(_blockers)} 条未验收的角色指令...")
```
- `verify_directive`（`card_tools.py:6364`）由角色卡验收指令为 `complied/rejected/cancelled`（`card_tools.py:6299-6302` 校验枚举；`rejected` 必须带 `evidence`）。这是**指令验收状态机**，非工具调用挂起确认。

**(c) 收件箱驱动的回合唤起（非用户确认挂起）** — `message_runner.py:1843-2028`：A 回合收口时对本轮记下的 pending 目标 `asyncio.create_task` 起 B 回合；靠**持久化收件箱**（`card_db.list_pending`/`take_pending`）保证「丢任务不丢信」，下次收口重新判 pending 调起（`:1859-1861`）。这是**消息队列驱动**，不是 asyncio.Event 工具调用挂起。

> 小结：任务第 3 项所描「模型调某工具→挂起→Event/轮询→600s 超时→确认/拒绝/超时三终态」在整个 `src/` 中**找不到实现**。最接近的三处如上，均不符。建议后续确认 `pending_action.py` 是否被裁剪/改名/从未合入。

## 4. 编程卡（生命周期 / 完工后能否续派 / 回执 / 是否可删）

### 4.1 生命周期状态值全集
- **`active`**（派生即首跑、被派活时）→ **`completed`**（模型调 `report_done` 收口）。
- 源码锚点：`_h_report_done` 判态 `state=="active"` 否则 `denied`（`card_tools.py:988-989`）；完工落 `{"state": "completed"}`（`:1031`）。

## 5. 工具卡（建卡/调用/完工/存储）与编程卡的区别（代码层面）

实现包：`src/toolcard/`（driver.py / finalize.py / artifact_store.py / state_store.py / script_loader.py / step_prompt.py）。

### 5.1 建卡
- **工具卡**：`_h_run_tool_card`（`card_tools.py:2402`）每次调用**新建一张** `card_type="tool"`、带 `owner_card_id=当前卡`、`parent=当前卡` 的卡（`:2457-2463`）。**N 次 N 张，不复用**（`:2431-2432`）。剧本从 `works/toolcard_scripts/{name}.json` 装载（`script_loader.py:49,110`）。
- **编程卡**：`_h_create_coder_card`（`card_tools.py:1087`）建 `card_type="coder"`、`parent=当前卡`、`charter="## 使命\n{task}"` 且 `skip_kick=True`（`:1131-1139`），随后**建卡即首跑**（`asyncio.create_task` 调 `_run_message` `:1147`）。

### 5.2 调用 / 推进
- **工具卡**：运行时在进程内 `_runtimes: dict[card_id, CardRuntime]`（`driver.py:60`）。`driver.start`（`driver.py:86`，幂等，恢复优先于新建 `:101-133`）、`driver.advance(step_id)`（`:136`，**照单收下**，唯一拒绝＝「目标步不存在」 `:156-160`）、`driver.commit`（`:189`，落产物）、`driver.done(verdict)`（`:210`，**收下终态声明，链结束**）。

- **编程卡**：推进由模型回合 + `auto_driver` / 目标域驱动，状态 `active→completed` 由 `report_done` 显式收口（见 4.1）。

### 5.3 完工 / 收口
- **工具卡**：`driver.done` → `finalize.finalize`（`finalize.py:57`）：① 终态重试一次 ② manifest 落盘 ③ 终态声明落卡面 `toolcard_final:{verdict, at}`（`state_store.write_final` `:85`）④ **产物路径回传 owner 影子卡「## 产物清单」节一次**（`relay_to_owner` `:102-124`）。**永不抛**（`finalize.py:20`）。
- **编程卡**：`report_done` 落 `state=completed` + `coder_final` + 系统发 `coder_done` 回执（见 4.2-4.3）。

### 5.4 存储
- **工具卡**：产物落 `works/{work_id}/toolcards/{card_id}/`，命名 `{两位序号}-{stepId}-{名称}-{版本号}.{ext}`，**版本化不覆盖**（重做落 `-02`，`-01` 保留，`artifact_store.py:5-6,70-91`）；manifest 进程内 + `manifest.json` 落盘（`:170-186`）；失败账 `_failures.json`（`:101-112`）。卡面三字段 `toolcard_script / toolcard_step / toolcard_round`（`state_store.py:40-42`），`toolcard_final` 落终态声明。**绝不命名 `step_status: done`**（那是判定，`state_store.py:14-17`）。
- **编程卡**：产物/成品即卡正文与影子（`## 产物清单` 由系统回执填充）；终态落 `state=completed` + `coder_final` 列（`card_tools.py:1011-1031`）；归档后转 `coder_archive` 记录（`coder_fold.py`）。

### 5.5 代码层核心区别（一句话）
- 工具卡＝**进程内运行时 + 剧本步骤机 + 只记录不判定**（driver 七不、无 done 字段、终态声明照单收）；编程卡＝**目标域相位机 + 模型显式 report_done 收口 + 系统自动回执 + 可归档/可复活**。

## 6. 文本工具抢救（text_tool_rescue.py）

实现文件：`src/api/text_tool_rescue.py`（7.3KB）。**纯机械模式匹配，不判内容、不拦产出、不引导方向**（`:10-17`）。

### 6.1 触发条件
- 统合官 deepseek 批量发工具调用时，把调用以**文本形态**写进 content（全角/半角双竖线 `｜｜` 是特殊 token 的可打印近似），而非标准 `tool_calls` 字段 → 原 `routes.py` 只认标准字段 → 正文里的调用**零执行零反馈 → 模型永远等一个不会来的结果（等待黑洞）**（`:4-8`）。
- `extract_text_tool_calls(content)`（`:74`）从正文解析文本形态调用。

### 6.2 抢救成什么
- 形态 A（DeepSeek 原生标记）：`<｜tool_calls｜> / <｜invoke name="X"｜>` 等，竖线统一按 0-2 条匹配（`:32-44`，`:89-108`）。
- 形态 B（标准围栏 JSON）：` ```json [{"name":..., "arguments":{...}}] `（`:49-51`，`:111-137`）。
- 解析出 `calls: [{name, arguments, _origin: "textA"|"textB"}]`，并把已识别的调用块从正文**剥离**得 `stripped_content`（`:139-147`）。

### 6.3 是否产生独立事件类型
- **不产生新事件类型**。`extract_text_tool_calls` 返回三元组 `(calls, unresolved, stripped_content)`（`:74-152`）。`unresolved=True` 仅当正文有疑似标记但零解析（`:149-150`），由调用方把「未识别为调用、未执行」这个**机械事实回注模型上下文**（关闭等待黑洞），回注句由 `feedback_note()` 生成（`:155-164`，内容为「你上一轮正文中出现了工具调用样式的标记，但未被系统识别为可执行调用，未执行…」）。无 SSE 新事件、无事件流新类型。
