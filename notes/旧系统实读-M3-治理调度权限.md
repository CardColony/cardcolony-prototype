## 1. 调度：队列结构、优先级规则、是否串行、同时跑几轮

### 1.1 点火调度器（`scheduler.py`）
- **队列结构**：`asyncio.Queue`（懒建）+ `_pending` 去重集合，key=`(work_id,card_id)`。
  `scheduler.py:39-41`
  ```python
  _queue: Optional[asyncio.Queue] = None
  _pending: set[tuple[str, str]] = set()   # 在队/在跑去重集合
  _workers: list[asyncio.Task] = []
  ```
- **入队**：`enqueue(work_id, card_id)`——同卡只排一次（去重）；调度器未启动时退回直点 `auto_driver.kick`。`scheduler.py:55-78`
- **出队 / 并发上限**：N 个 worker，每个 worker 取一张卡 → `auto_driver.kick` → **`await task` 等整个回合跑完**才取下一个。N＝`max_turns`，缺省 3。
  `scheduler.py:81-103`、`scheduler.py:45`、`scheduler.py:105-114`
  ```python
  max_turns: int = 3
  ...
  if task is not None:
      await task          # 关键：等回合结束才释放槽位＝并发上限的实现
  ```
- **优先级规则**：**明确不做优先级**——先到先得，谁先建谁先跑。
  `scheduler.py:24`（docstring）：「不做优先级：先到先得，谁先建谁先跑（父卡建完自己的活，子卡按建卡顺序排队）」
- **是否持久化队列**：不持久化，进程重启丢队列；卡的 `goal_state=active` 还在，下次唤醒/建卡重入队。`scheduler.py:26-27`
- **不持久化、无超时**：超时兜底在 gateway（流静默 600s）。`scheduler.py:25`

> 结论：点火调度器层面＝**FIFO 队列 + 全局最多 max_turns(缺省3) 个并发回合**，无优先级。

### 1.2 串行闸（`serial_gate.py`）——每 work 一把执行锁
- **锁模型**：每 `work_id` 一把 `asyncio.Lock` + 当前持有者 `card_id`。`serial_gate.py:38-39`
- **串行**：`acquire` 拿不到锁就 `await`（排队等待，不是 409）；锁持有期＝整张卡的目标生命周期。`serial_gate.py:74-90`
- **并行模式**：`exec_mode()` 默认 `serial`，文件缺失/损坏 fail-open 到 `parallel`（直接放行）。`serial_gate.py:42-58`
- **释放**：回合末按 `will_continue` 判定 / 目标终止 / 手动停止显式释放。`serial_gate.py:93-110`

> 结论：调度层（全局≤3 并发）与串行层（每 work 同时仅 1 张卡跑）**叠加**。
> 「同时能跑几轮」＝全局 ≤max_turns(3) 个回合，且同一 work 内串行（同时刻 1 个）。

### 1.3 优先级相关（人类回合 / 职能同步 / 叶子优先）
- 在所读 6 个文件中**未找到**「人类回合优先 / 职能同步优先 / 叶子优先」这类显式优先级排序代码。调度器明确声明不做优先级（`scheduler.py:24`）。
  ⇒ 登记为「未解／未在本批文件中发现该优先级规则代码」。

## 2. 停止与暂停（重点·穷举）

### 2.1 停止入口（全部枚举）
1. **`control.request_stop(work_id, card_id)`**——人停唯一入口（stop 端点）。`control.py:118-159`
2. **`control.halt(work_id, card_id, reason, by)`**——强制停止标记 + 杀当轮，并置 `_HALTED` 拒绝一切内部唤醒（goal 续轮/收件箱/观点回合），仅用户直接发话或 `resume_child` 解除。`control.py:46-65`
3. **`control.stop_auto(work_id, card_id)`**——自动模式停止的②③件 + 释放执行锁（幂等，非 auto 卡 no-op）。`control.py:263-349`
4. **`scheduler.stop()`**——关停时取消 worker；队列中未跑完的卡靠 `goal_state` 下次重入队。`scheduler.py:117-122`
5. **`serial_gate.release_work(work_id)`**——停止路径释放该 work 执行锁（防串行队列饿死）。`serial_gate.py:105-110`
6. **`routes.post_work_stop`**（引用见 `control.py:233`）——一次调齐 `request_stop` + `stop_auto`（组合入口，代码在 routes.py，不在本批 6 文件内）。

### 2.2 能否打断「正在跑的那一轮」——**能**
- 在途回合协程登记于 `_turn_tasks`，`cancel_turn` 直接 `task.cancel()`；
  同协程内调用（自杀）则退回置位等步边界。`control.py:84-115`
  ```python
  def cancel_turn(work_id, card_id) -> bool:
      task = _turn_tasks.get((work_id, card_id))
      if task is None or task.done():
          return False
      if task is asyncio.current_task():   # 不能 cancel 自己
          return False
      task.cancel()
      return True
  ```
- `request_stop` 按状态分两路，都不靠墙钟：
  - 在模型流里（`model_service.in_stream` 为真）→ 置 `asyncio.Event` 信号，流把它和「下一个 chunk」一起 await，谁先到算谁 ⇒ **立刻收口且保住已产出的字**（`control.py:74`、`control.py:140`、`control.py:195-208`）；
  - 不在流里（卡工具执行/上下文装配）→ 信号没人等 ⇒ 直接 `cancel_turn` 取消协程。`control.py:144-150`
  ```python
  stop_event_for(work_id, card_id).set()      # 流里：与下个 chunk 赛跑
  if not _waiting_on_stream:
      cancel_turn(work_id, card_id)           # 不在流里：直接 cancel 协程
  ```

### 2.3 停止粒度：既有「细于轮边界」也有「轮边界」
- **细粒度（掐断在途回合）**：`cancel_turn` / 流信号 ⇒ 可以在一轮模型调用中途立即中断（非轮边界）。`control.py:99-115`、`control.py:140`
- **轮边界（自动续轮暂停）**：`stop_auto` 把目标 `goal_state → paused`（经 `goal.service.pause` 写事件+重投影），运行中的自动续轮不再起下一轮。`control.py:263-313`
- **组合**：`post_work_stop` 同时调 `request_stop`（掐在途轮）+ `stop_auto`（关续轮）+ `release_work`（放锁），三件缺一即失效。`control.py:224-233`

> 结论（暂停粒度）：系统**同时支持两种粒度**。
> - 「暂停只做轮边界」**技术上可行**——走 `goal_state→paused`（`control.py:263-313`）即可只阻止后续轮、不动在途轮；
> - 但停止入口本身还能**更细**地立即打断正在跑的那一轮（`cancel_turn`/`request_stop` 流信号，`control.py:99-150`）。
> 即：轮边界暂停是可选的语义层，物理上停止可直达协程级。

### 2.4 停止后状态怎么记
- **进程内（非持久）**：
  - `_stop_requests` 集合（consume-once，消费即清，STOP 只终止当前回合不影响下一回合）。`control.py:36`、`control.py:162-171`、`control.py:174-187`
  - `_HALTED` 字典（状态机持久于进程内存：拒绝内部唤醒）。`control.py:43`、`control.py:46-65`
  - `_turn_tasks` / `_stop_events`。`control.py:74`、`control.py:84`
- **持久（权威在事件日志）**：
  - `stop_auto` → `goal.service.pause()` 写 `goal/change` 事件 + 重投影（跨重启有效，不会被下次投影覆盖）。`control.py:294-312`
  - 纯 legacy 卡无 goal 事件 ⇒ 退回写投影列 `goal_state:"paused"`。`control.py:304-308`
  - `goal_await_children` 置 0（用户按停优先，取消「等子卡」意图）。`control.py:313-335`
- **留痕**：`session_ops.ops_log("human_stop"/"auto_stop"/...)`。`control.py:151-153`、`control.py:340-344`；观点回合异常 `ops_log("function_opinion_error"...)`.`function_room.py:692-693`

## 6. 写范围校验（重点·穷举）

### 6.1 `WriteScope` / `effective_write_scope` —— **不存在**
- 全仓检索（grep `WriteScope|effective_write_scope|write_scope`）**无任何定义/引用**。
- 在所读 6 个文件内也无此实现。
- 结论：**`WriteScope` / `effective_write_scope` 在本系统不存在**（登记为「不存在」，不猜）。

### 6.2 实际的「写范围校验」机制 = 文件写权限 + 路径前缀锁
> 本系统对「写」的范围约束落在 **文件/路径** 这一维（即 `tools_file` 能力 + `FILE_SCOPE` 前缀），由 `file_tools.py` 实现（该文件不在本卡点名清单内，但因第 6 项专门问「写范围校验」，且 grep 确认 WriteScope 不存在，故补登记其最接近实现）。

- **实现位置**：`file_tools.py`
  - `FILE_SCOPE` 表：`file_tools.py:108-124`
  - 前缀判定 `_prefix_hit`：`file_tools.py:144-152`
  - 总校验 `check_file_access(path, card_meta, write=...)`：`file_tools.py:155-206`

- **三层机械判定**（`check_file_access` docstring，`file_tools.py:155-174`）：
  ① 权限分档：`write=True` 须 `tools_file`；`write=False` 须 `tools_file` 或 `tools_read_file`。`file_tools.py:175-178`
  ② 全盘边界：resolve 后须落 `ALLOWED_ROOTS` 之下（`_resolve`，`file_tools.py:209-216` 起）。
  ③ 内部凭证排除 + `FILE_SCOPE` 前缀。

- **前缀匹配逻辑**（`_prefix_hit`，`file_tools.py:144-152`）：
  ```python
  def _prefix_hit(target: Path, prefix: str) -> bool:
      if prefix == "":
          return True                       # "" 哨兵匹配一切（全放行现状）
      try:
          rel = target.relative_to(BASE_DIR)
      except ValueError:
          return False
      return str(rel).replace("\\", "/").startswith(prefix)
  ```
  调用：`hit = any(_prefix_hit(target, p) for p in FILE_SCOPE.get(card_type, []))`（`file_tools.py:204`）。
  当前 `FILE_SCOPE` 各 card_type 值均为 `[""]` ⇒ `""` 哨兵 ⇒ **全放行**（用户裁定「全盘可读可写」保持现状；真实前缀待用户提供，属 Open Item）。`file_tools.py:90-124`

- **越权时返回什么**：返回 `False`（grant=False）。`file_tools.py:191-205`
  （权限不足 `file_tools.py:191-193`、解析越界 `:198-200`、凭证排除 `:201-203`、前缀不中 `:204-205` 均返回 `False`）。

- **拒绝是否留痕（写到哪里）**：**是**，统一经 `prompt_log.append_perm_log`（perm 口径，fn="check_file_access"）两态同记（granted true/false）。`file_tools.py:181-189`、`file_tools.py:191-205`
  ```python
  def _log(granted, prefix_hit):
      prompt_log.append_perm_log({
          "fn": "check_file_access", "path": path, "card_type": card_type,
          "write": bool(write), "prefix_hit": prefix_hit, "granted": granted,
      })
  ```
- 另有 `ALLOWED_ROOTS` 全盘边界（在 `_resolve`），越界同样返回 `(None, error)` ⇒ `check_file_access` 记 False 返回 False。`file_tools.py:197-200`、`file_tools.py:209+`

> 结论：写范围校验 = `policy.has_perm(..., tools_file)`（能力层）＋ `check_file_access` 的 `FILE_SCOPE` 前缀锁（路径层）。`WriteScope`/`effective_write_scope` 符号不存在；拒绝记 `prompt_log`（perm 口径），非异常抛出（调用方据 False 自行拒绝）。

## 7. 多用户 / 多实例（重点·穷举）

### 7.1 本批所读 6 文件内的结论
- 在 `scheduler.py` / `serial_gate.py` / `control.py` / `function_room.py` / `role_room.py` / `permissions/*` 中：
  - **不存在** `user_id`、`登录态`、`会话隔离（按人）`、`账户`、`注册`、`token（应用层）` 等任何多用户身份代码。
  - 隔离单元是 **`work_id`（项目/工作域）**，不是用户。所有调度/串行/权限/职能/角色的键均为 `(work_id, card_id)` 或 `work_id`。例：`scheduler.py:41`、`serial_gate.py:38-39`、`control.py:36,43,74,84`、`policy.py:can/check` 的 `cards` 参数是单 work 内的卡集合。
  - 人类操作以「用户」名义出现在 `actor="用户"`/`by=""` 等字面量（`role_room.py:280`、`role_room.py:353`），但**不承载身份标识**，仅作留痕文本。

### 7.2 全仓中出现的 auth/login 是什么
- grep `login|password|account|authenticat|token` 命中的文件几乎都在 `src/api/wb_exec/*`（`winenv.py`/`registry.py`/`bridge.py`/`acp_client.py`/`config.py`/`cli_pool.py`）与 `src/model_gateway/*`。
- 这些是 **codebuddy 外部 CLI 网关的登录/认证**（桌面端进程 `CODEBUDDY_GATEWAY_PASSWORD`、CLI `/login`、authSession）——即**模型执行环境的外部认证**，用于驱动 LLM/命令执行体，**不是推演agent 应用层的用户账户/会话隔离体系**。
- 例：`wb_exec/winenv.py:5,15,87-88`（网关口令在桌面端进程环境）；`wb_exec/registry.py:194-196,231,390-421`（CLI 执行体 unauthenticated 标记，针对外部网关）；`wb_exec/bridge.py:229,328,477,574-575`（网关返回 Authentication required 的处理）。

> 结论：**推演agent 应用层（卡片/回合/权限/调度/职能/角色）不存在多用户代码、用户ID、登录态或按人会话隔离**。系统以 `work_id` 为隔离域，单进程服务多个 work 但不区分「是哪个人的 work」。出现的 authentication 仅属于外部 codebuddy 网关（模型执行客户端），与本应用用户模型无关。
