### 2.4 是否携带基线哈希

**携带。** `base_hash` 是 draft 的返回值之一（card_draft.py:205），commit 的必填入参
（`CommitRequest.base_hash: str = Field(min_length=1)`，routes.py:174），服务端在写前重算并比对：

```python
    card = _apply_block_set(raw_card, work_id)
    current_block = _get_current_block(card, kind)
    current_hash = _block_hash(current_block)

    # hash 比对：不一致 → 拒绝、卡面零改动
    if base_hash != current_hash:
        return {
            "error": "内容已被改，请重新起草",
            "code": "hash_mismatch",
            "current_hash": current_hash,
        }
```
（card_draft.py:228-238）

同类第二条通道（"更新现状"按钮）：`propose_status` 工具返回 `{proposed, old, base_hash}`，
`base_hash = sha256(old)`，与 `card_draft._block_hash` 同算法，同样走 `/commit`
（card_tools.py:1231-1261，尤其 1258-1260）。

### 2.5 切卡后草稿归属怎么记（card_id 与草稿的绑定关系）

**代码里没有"草稿对象"，也没有"草稿—card_id"的绑定记录。** 绑定只存在于两处：
① commit URL 路径里的 `card_id`；② `base_hash` 与该卡当前块 hash 的相等关系。

前端起草弹窗的提交代码——**提交时取的是"当前卡"，不是"起草时那张卡"**：

（static/workspace.js:2519-2532）

`dm` 的字段只有 `{kind, baseHash, draft, feedbackRounds, busy}`（workspace.js:2456、2476），
**不含 cardId**；起草请求也用当时的 `currentCard.meta.card_id`（2502）。`API.postCommit`
把 card_id 放进路径：`/api/works/${wid}/cards/${cid}/commit`（static/esm/api.js:393）。

      ...

由此可机械推出的事实（全部有锚点，不含推断）：

1. 起草弹窗（requirements / status 的"起草"路径）在**切卡后提交**时，`card_id` 取自
   `currentCard.meta.card_id`（workspace.js:2527），即**切到哪张就提交到哪张**。
2. 唯一拦截＝`base_hash != current_hash`（card_draft.py:233）。`_block_hash("")` 是定值
   `sha256("")`（37-39），占位符/空块同口径当空（67-89），故**两块都空（或都命中占位符）时
   hash 相等**，比对不会拒绝。
3. 后端 `commit` 不校验"这张卡是不是起草时那张"——它没有任何"起草记录"可比
   （card_draft.py:208-238 全函数只有 work 存在、卡存在、kind、hash 四项判定）。
4. 前端未见"切卡即关弹窗"的钩子：`closeDraft` 只绑在关闭按钮、右上 ×、遮罩、提交成功四处
   （workspace.js:2534、2585-2587），未在切卡路径调用（未解，见 §8）。
5. `work_id` 同样是"提交时取"：提交调 `API.postCommit(WORK_ID, currentCard.meta.card_id, …)`
   （workspace.js:2527），而 `WORK_ID` 是模块级 `let`，跨项目切卡时就地改
   （workspace.js:279-280）。⇒ 草稿弹窗对 `(work_id, card_id)` **两者都不持有快照**，
   提交时一律用"此刻的当前项目 + 当前卡"。

## 3. 立项提案 `card_proposal`

**先登记一处名实不符（事实，不是判断）**：`card_proposal.py` 的文件语义是**建卡提案**
（"建卡协议解析（白板版）"，card_proposal.py:2-35），不是项目级"立项提案"。
模块头自述："[建卡工具化 2026-10-08] 本模块降级为**兜底通道**：建卡主通道已改为标准工具
create_card"（card_proposal.py:4-7）。项目（work）的创建在别处（3.5）。

### 3.1 提案数据结构

只认三个字段，多余忽略（card_proposal.py:19、156-160）：

```python
        proposals.append({
            "title": title,
            "parent": (item.get("parent") or "").strip(),
            "content": (item.get("content") or "").strip(),
        })
```

- 承载形态两种（card_proposal.py:9-12、50-62）：` ```card-proposal\n[...]\n``` ` 与
  `<|｜card-proposal｜｜>…<|｜/card-proposal｜｜>`（竖线全/半角、0-2 条、标记词两侧可空白）。
- 解析：`parse_proposals(reply_text) -> (clean_text, proposals)`（163-182）；

### 3.2 谁能发起

## 4. 项目 / 工作区：按 work 隔离怎么实现

### 4.1 `__WORK_ID__` 的形态：不是路径占位符，是前端可变全局

- 后端 `src/` 搜 `__WORK_ID__`：**无匹配**（Grep 0 条）。后端隔离不靠占位符替换，
  靠**一 work 一目录、一 work 一库**，且每个函数都显式吃 `work_id` 形参。
- 前端**有** `window.__WORK_ID__`：模板注入的 JS 全局，被各模块读成模块级常量/惰性读：

```javascript

 * （不整页跳转，首条消息"只感知正常发送"），本模块所有闭包引用同一绑定，随取随新。
 * 同步写 window.__WORK_ID__：nav_system / rule_panel 惰性读，落库后不失准。 */

let IS_DRAFT_PROJECT = (WORK_ID === "draft");
```
（static/workspace.js:36-43；块内含 39、43 两行声明，中间为注释）

- 该全局**运行时会改**（不是只读）：跨项目切卡时 `WORK_ID = switchWid; window.__WORK_ID__ = switchWid;`
  （workspace.js:277-282），草稿项目落库后同样就地换真 id（workspace.js:397-400）。
  其余模块：`const WORK_ID = window.__WORK_ID__`（static/canvas.js:44、static/esm/main.js:19）、
  `const WID = () => window.__WORK_ID__`（static/esm/rule_panel.js:11、static/esm/nav_system.js:31）。

    async def _access_log(request, call_next):  # noqa: ANN001
        path = request.url.path
        if any(path.startswith(p) for p in _SKIP_PREFIX):
            return await call_next(request)
        t0 = time.perf_counter()
        status = 0
        err = ""
        try:
            resp = await call_next(request)
            status = int(getattr(resp, "status_code", 0) or 0)
            return resp
        except Exception as exc:  # noqa: BLE001 记下来再抛（不吞异常）
            err = f"{type(exc).__name__}: {exc}"
