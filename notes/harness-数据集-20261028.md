# harness 数据集（第一个东西）· 建成记录（2026-10-28）

> 用户规格（第一手）：
> 「一个是全新的数据集，它是部件化的，可快速查询的，因为很可能会随时新建条件。」
> 「不是对当前这一个事件进行评估，而是要组合 N 条历史事件组成条件……比如【24小时内】
> 【父卡】对【子卡】进行了【什么操作】。」
> 「不能是实时查询（太耗性能），而应该是触发式的才对。」
> 技术选型：**sqlite**（2026-10-28 用户定，第一版是纯内存，已重做）

代码：`src/infra/fact_store.py`　测试：`tests/test_fact_store.py`（17 个用例）

---

## 一、它是什么

事件账本（`works/<work>/events/*.jsonl`）是**日志形态**：按卡分文件，写快、顺序读快、
按卡读快。而条件要的是**集合形态**：任意维度筛、跨卡关联、时间窗。两种访问模式相反，
所以旧做法（每次评估读这张卡最近 200 条）一步都问不出来：

| 用户的条件 | 旧做法 |
|---|---|
| 【24小时内】 | 只有"最近 200 条"——实测 200 条覆盖 **9.3 分钟 ~ 25.9 小时**，差 170 倍 |
| 【父卡】对【子卡】 | 只读一张卡；work_018/card_006 有 24 个子卡 ⇒ 要读 25 个文件 |
| 【什么操作】 | 只有"类型 + 顶层字段等于" |

数据集是**旁路**：账本一个字节不动，这里只存一份零件副本。

## 二、为什么从内存改成 sqlite

第一版把事实全放内存（dict + 三本索引）。实测 work_027（875 MB / 153 个文件）：

    25 万条事实 ⇒ 内存 256 MB、每条约 1.1 KB、重启要重建 12 秒、重建峰值 493 MB。

而需求是**触发式**——日常不查询，只在「新建或修改策略」时回溯一次。也就是说
「查询 0.8 ms」这个优势根本用不上，却要每天付 256 MB 和 12 秒。

**两版实测对比（work_027，251,021 条）：**

| 指标 | 内存版 | **sqlite 版** |
|---|---|---|
| 常驻内存 | 256 MB | **~0**（页缓存几 MB） |
| 磁盘 | 0 | 93 MB |
| 首次重建 | 12.1 s | 18.9 s |
| **再次启动** | **12.1 s（每次都重建）** | **0.007 s（水位命中）** |
| 24h 窗查询 | 0.8 ms | **0.3 ~ 0.9 ms** |
| 4 天窗 + 字段筛 | 99 ms | 66 ms |
| 单条写入（逐条提交） | 微秒 | 0.29 ms |
| 单条写入（批量提交） | — | 0.04 ms |

sqlite 版除了首次重建慢 6 秒（一次性），其余全面胜出，且**不占内存**。

## 三、边界（用户约束，必须守）

| 对象 | 处置 |
|---|---|
| `cards.db` | **不动**（卡面与会话的唯一真相） |
| `events/*.jsonl` | **不动**（上下文与回放的原文，只读） |
| `works/<work>/facts.db` | **本模块的库**，派生数据，删掉即可重建 |

正因为它可随时丢弃重建，它才是「harness 自己收集的事件信息」——
7 天保留期的合法对象就是它。

## 四、表

```sql
facts(seq, card, ts, ts_iso, type, run_id, round, parts)
    PRIMARY KEY (card, seq)        -- seq 只在卡内唯一，跨卡会撞号
    parts 是 JSON：该事件类型声明的零件（catalog 的 part + optional）

file_watermark(path, size)         -- 增量重建：每个事件文件已读到哪
```

索引：`(ts)` / `(type, ts)` / `(card, ts)` —— 覆盖「时间窗」「什么操作」「哪张卡」三轴。

**主键必须是 (card, seq)**：`seq` 只在卡内唯一（每张卡的文件各自从 0 起号）。
实测 work_056 里 card_001 / shadow_card_001 / card_002 全都是 seq=1，
只用 seq 当键会让事实互相覆盖、静默少数据。

## 五、一条事实

```json
{"seq": 9057, "ts": "2026-10-26T14:41:15.123+08:00",
 "work": "work_027", "card": "card_021", "type": "msg_directive",
 "run": "...", "round": 3,
 "from": "card_001", "to": "card_021", "msg_type": "directive"}
```

- **只取零件**：字段来自 catalog 的 `fields.part` + `fields.optional`。
  原文（`content`/`text`/`result`/`old`/`new`）一概不取。
- **不收逐字流帧**：`reasoning_chunk` / `content_chunk` 是渲染增量，不是事实。
- **有界**：保留期 7 天，`evict` 按 ts 删。

## 六、查询怎么走

SQL 只做**能走索引的三轴**（时间窗 / 类型 / 卡），`where` 的字段条件在结果集上
用 `harness_cond.match_where` 过滤——语义与条件集同源，不另写一套；
三轴收窄后结果集通常只有几十到几百条，字段过滤是微秒级。

```python
st.query(work_id,
         types=["msg_directive"],                  # 什么操作
         cards=["card_092", "card_093"],           # 一组卡（跨卡）
         from_="card_074", to="card_092",          # 主体方向
         since=now-86400, until=now,               # 时间窗（epoch 秒）
         where={"by": "card_074", "ok": {"eq": False}},   # 任意字段 + 比较器
         limit=200)
```

实测（work_027，24 万条）：

| 查询 | 结果 | 耗时 |
|---|---|---|
| 24h 窗 某父卡对 11 个子卡的操作 | 0 条（那 24h 没动） | 0.3 ms |
| 4 天窗 同一条件 | 11 条 | 66.5 ms |
| 24h 窗 全部 tool_result | 149 条 | 0.9 ms |
| 24h 窗 失败的 tool_result | 3 条 | 0.7 ms |
| 7 天窗 全部事实（**不该这么查**） | 243,186 条 | 1208 ms |

## 七、重建

- **倒读**：账本按时间追加，最近的都在尾部。要重建"最近 7 天"只读尾部，不必解析全部。
- **增量**：`file_watermark` 记每个文件读到哪；文件没长过 ⇒ 直接返回 0（实测 7 ms）。
- **批量提交**：每 2000 条一次，比逐条快一个数量级。
- **跳过逐字流**：按行首 300 字节判 type，不做 `json.loads`（122 万条不必解析那 274 MB）。

## 八、三个必须记住的发现

**1. 逐字流帧占了 83% 的条数。**
`reasoning_chunk` 122 万条 / 274 MB。它是 `wb_exec/bridge.py` 用错通道逐帧落盘的历史
（已修）。跳过它之后重建从 59.5 秒降到 18.9 秒，事实从 147 万降到 25 万。

**2. 历史数据缺字段，新数据才有。**
work_027 里 1,030 条消息事件，`from` / `to` **全是空的**——它们产生于第 1 步补字段之前。
代码现在会带（`session_facade.emit_message_event` 717-720 行），但**历史补不回来**。
⇒ 依赖 `from`/`to` 的条件对旧数据永远不成立，这是必须接受的代价。

**3. 「父卡对子卡做了什么」在数据里有两种形态。**
- 消息：`from=父卡`、`to=子卡`（落在子卡的事件流里）
- 建卡/改卡：事件归属在**子卡**，主体是 `by=父卡`（`card_created` 没有 `parent` 零件）

所以条件里要能表达「主体是父卡」，不能只认 `from`。

## 九、下一步（条件集）

数据集只管"存什么、怎么查"。条件集负责：

- 每条策略的 `active` 开关、`scope`（一张卡 / 一对父子 / 整个 work）、`window`、`watch`（只关心哪几类事件）
- 只为**激活**的策略挂状态；事件进来按倒排只喂关心它的那几个
- 状态达成 → 触发 harness 任务 → **该状态清零重记**
- 新建策略时从数据集回溯一次，把初始状态建起来

热状态放内存（微秒级更新），冷事实放 sqlite（不占内存、重启不重建）——
这就是前面说的**冷热分离**。
