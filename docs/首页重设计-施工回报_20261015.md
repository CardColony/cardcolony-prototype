## 二、两个关键实现决策（与任务书字面不同，按实读代码订正）

### 1. hash 用复合键 `#wid/cid`，不是 `#cid`

任务书写「跳 `/work/{wid}#{cid}`」。实读 `state_layers.js:150` —— hash 的规范形态是
**复合键** `#wid/cid`；裸 `#cid` 只是 R-09 的旧链接兼容形态，会被 `parseHash`
回落到「当前页 WORK_ID」。同页时两者都能开卡，但跨 work 时裸 cid 会开错卡。
故一律写复合键，与 `serializeHash` 同口径。方案表格里的 `#{cid}` 按此订正。

### 2. 第 2 态要落「对话页」，必须补根卡 hash

`/api/works` 只返回 work 列表，**不含卡 id**；而工作页无 hash 时停在**画布态**
（`work.html:57` `data-view="canvas"`，`restoreFromHash` 无选中即 return）。
要满足验收第 4 条「落在最近活跃 work **对话页**」，须补根卡 hash 让
`restoreFromHash` 打开根卡并切 chat 视图。根卡 id 取列表项的 `work_card_id`
（已实读确认 `list_works` 返回的是 `work.json` 原样 dict，含该键），
该键缺失时退回纯 `/work/{wid}`（至少进得去）。

> 若你认为第 2 态「进得去 work 即可、对话页非必须」，改 `home.js:97-102` 一段即可，
> 去掉 rootCid 拼接。这条我按方案字面（对话页）实现了，如与你的本意不符请指出。

## 六、⚠️ 施工过程中的一次生产数据事故（如实记录）

**我的验收脚本一度把两个空项目写进了正式 `works/`。**

- 事故：`work_014`、`work_015` 落到真实数据目录
- 成因：脚本只 patch 了 `work_store.WORKS_DIR`，而 `create_work` 的建卡/建画布/铺会话
  三步走的是 `card_store` / `canvas_store` / `session_store` **各自独立的
  `WORKS_DIR` 模块常量**——这三处仍指向真实目录。`card_db` 不设路径常量
  （`card_db.py:9` 明写「库路径调用时从 `card_store.WORKS_DIR` 派生」），
  故 patch `work_store` 对它们无效。
- 处置：核对两目录内全部文件的时间戳与内容（均为本次运行的自动产物：空会话、
  空画布、自动根卡 `card_001`，**无任何用户数据**），确认后**可恢复删除**，
  `works/` 已复原为 `work_001`…`work_013`（13 个，与事故前一致）。
- 修复：两个脚本改用与 `tests/conftest.py` autouse sandbox **同口径**的五件套 patch，
  并各加一道自证闸——① 启动前断言五个模块的 `WORKS_DIR` 均已离开真实 `works/`；
  ② 跑完做起止快照比对「真实 `works/` 本次运行期间零改动」。重跑全绿。

**遗留发现（非本次引入，供你决策）**：全量 pytest 自己会写进正式 `works/`
（`work_001/canvas.json`、`session_029.md`、`work_008|009/events|sessions` 等），
即 `conftest.py` 的 autouse sandbox 未覆盖到全部写入路径。属既有数据卫生问题，
不在本次任务书范围，**未擅自改动**。
