# 卡片工具区域化与确认制 · 方案（2026-10-14）

## 一、目标

五个卡片工具随「内容分区域」（正卡正文四块 SQLite 化、影子四节）完成形态迭代：

1. `read_card`：清单 + 按需读区
2. `read_shadow`：清单 + 按需读节 + 只读本卡
3. `create_card`：弹窗确认 + 描述写死「用户要求才建」
4. `delete_card`：只删子卡 + 弹窗确认
5. `update_shadow` → `edit_shadow`：改名 + 按节编辑

## 三、技术裁定（总工定，全部落死）

### 裁定 1 · 区域清单形态＝「单工具两态」：缺省给清单，给了参数读单块

**不新增 `list_regions` 工具**。`read_card` / `read_shadow` 各加一个可选参数，缺省调用返回「meta + 区域清单（各区域名/一句话说明/字数）」，带参数调用只读指定块。

理由：① 工具面不加件；② 与 `read_memory(card_id?, from_seq?, to_seq?)` 的「单工具按需取」同款先例；③ 模型自然用法就是「先看清单、再取所需」。

### 裁定 2 · 确认制＝同步等待（工具调用挂起等用户点弹窗），带 10 分钟过期

**不复用 draft/commit**（那是「文本起草→确认写入」，形态不同；这是「动作发起→确认执行」）。新机制 `pending_action`：

- 模型调 `create_card` / `delete_card` → 后端**不执行**，落一个待确认项（进程内表 + 事件流 `pending_action` 事件）→ SSE 推给前端 → 前端弹窗（复用 draftModal 三态模式：确认 / 拒绝 / 关闭）→ **工具调用挂起**（`asyncio.Event`）。
- 用户**确认** → 真正执行（建卡/删卡）→ 工具返回真实结果（卡号等）；**拒绝/关闭** → 不执行，工具返回「用户已拒绝」；**10 分钟无操作** → 过期，工具返回「超时未确认，未执行」。
- 过期时间性质＝UI 交互健壮性（同执行器超时），不是模型调用闸，不违零闸。
- 服务重启丢 pending 可接受（pending 只在回合内有效，重启＝回合中断）。
- 确认/拒绝/过期均落事件流（留痕铁律）。

选同步等待而非异步通知的理由：模型上下文里动作结果不悬空（调了就有终态），语义最自然；跨回合追状态会让「建卡回执卡号」这条核心收益失效。

### 裁定 3 · 「用户要求才建卡」＝描述写死（软） + 弹窗（硬），不做读心闸

代码无法判定「用户是否要求过」，做硬判定闸只能是假的。**弹窗本身就是最硬的可实现闸**——用户不点头，卡不存在。工具 description 写死约束（见 §四.3），双保险到此为止。

### 裁定 4 · read_shadow 收窄＝schema 删掉 card_id 参数，只读本卡

上级卡直查子卡影子的通道**关闭**（现描述已这么写，本次让 schema/handler 与之相符）。后果：原「推送到达机制」（上级经 read_shadow 查子卡）失效，跨卡协作走「待协作事项节 + 卡间消息」。这是产品语义变化，按你今天的话执行，风险在此声明。

### 裁定 5 · edit_shadow＝整节覆盖写（不是追加）

`edit_shadow(section, content)` 一次写一节，整节覆盖。粒度已从「整卡」缩到「节」；模型需保留旧内容时先 `read_shadow(section)` 再写回（与 edit_file 同款契约）。若实际使用发现「产物清单」追加高频，再加 append 模式参数（Open Item）。

## 四、五件工具的新形态（schema 级定义）

### 1. `read_card(card_id, region?)`

- `region` 可选，枚举＝**三块**：`mission`（使命）/ `status`（现状）/ `third`（第三块——对外名随树类：rd_project→需求文档、其余→定论）。
- **缺省**：返回 `card_id/title/parent/relations` + `regions` 清单：`[{region:"mission", desc:"要做什么、做成什么", chars:312}, …]` 三项。
- **带 region**：只返回该块内容 + 简短 meta。
- 权限不变（`SWITCH_READ` 关口）。不返回 shadow（本就不返回，保持）；history 不给（裁定 3 沿革：机械留痕是污染，界面自有通道）。

### 2. `read_shadow(section?)`

- schema **删掉 `card_id` 参数**；`section` 可选，枚举：`progress`（进度）/ `coordination`（待协作事项）/ `artifacts`（产物清单）/ `iterations`（迭代历史）。
- 缺省返回节清单（各节名/一句话说明/字数）；带 section 只读该节。
- **只读本卡**（handler 删 card_id 分支，目标恒为 `current_id`；`shadow_write` 关口语义不受影响——读侧本来无关口参数，收窄在签名层焊死，同 update_shadow 先例）。

### 3. `create_card(title, parent?, content?)` —— 加确认制

- schema 不变，description 重写（含两条硬话）：
  - 「**只有用户明确要求建子卡时才可调用**；自主拆解任务不得建卡，改用 create_plan」
  - 「调用后需用户在界面确认，确认前不建卡」
- handler：过 CREATE_CHILD 关口 → **不建卡**，落 pending_action → 挂起等确认 → 确认后走 `card_store.create_card` 原路径（回执卡号不变）。

### 4. `delete_card(card_id)` —— 加确认制 + 范围收紧

- 现状树作用域已是「操作者须在目标上游」＝只能删自己子树。**语义保持**，description 写死「只能删除你自己的子卡」。
- handler：存在性 + 根卡护栏 + DELETE 关口照旧 → **不删**，落 pending_action → 挂起等确认 → 确认后走 `card_store.delete_card` 原路径。
- 弹窗文案带卡标题，防误删。

### 5. `update_shadow` → `edit_shadow(section, content)`

- **改名**（注册表键、schema name、说明书全换；旧名退役留档 `RETIRED_TOOLS` 风格注释一行——生产无 tool_catalog，落 card_tools 内注释即可）。
- `section` 必填（四节枚举）、`content` 必填（整节覆盖写）。
- handler：`shadow_write` 关口照旧 → 按 section 落对应库列（复用 `update_shadow_sections`）。
- 节内容三禁（不写结论、不写无关、不当备份）进 description。

## 五、说明书（BASE_PROMPT 手写段）同步

生产说明书仍是手写形态，本次同步改五处：`read_card`/`read_shadow` 两行（清单+按需）、`create_card`（用户要求+确认制）、`delete_card`（子卡+确认制）、`update_shadow` 行改 `edit_shadow`。「工具错误码」节新增一条：`pending_timeout`（确认超时）——错误码枚举加 `pending_timeout`（超时不是 error 信封而是正常返回文案，故只加说明不加码；见 Open Item 2）。

7. 事件流有 `pending_action` / 确认/拒绝/过期事件（留痕）。
