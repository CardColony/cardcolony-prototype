## 一、第一批 进程间转发与运行状态

**病灶（实测）**：`_forward` / `_fanin_get_merge` / `_fanin_sse_stream` / `forward_ctl`
四个入口**逐请求现建** `httpx.AsyncClient`。本机默认构造 **~1.0s/次**（Windows CA 装载，
进程内不缓存：连建三次 1453/953/1000ms）；回环目标全是 http:// 明文。
2026-11-19 18:00–20:26 生产访问日志四条慢路径全部由此解释（nav/running 中位 1.21s、
会话标签 1.01s、进度 0.92s——前两者/三者分别走扇入与转发）。

**改动**（`src/infra/procs.py` + `main.py` 接线）：
1. 每**事件循环**一套回环客户端族（web 服务循环 B / runner 主环与分槽环各自一份，
   首用即建、随循环优雅关停——`close_all_loop_clients()` 挂在 `_serve` finally 与
   主进程 finally），按用途三池：
   - `short`＝状态扇入（30s 超时语义照旧，池容量 2×runner 数，SSE/长跑占满 stream 池挤不着它）；
   - `stream`＝请求转发中继 + SSE 扇入泵（timeout=None 长流语义照旧）；
   - `ctl`＝runner 控制转发（承载完整模型回合，timeout=None）。
2. 回环 http:// 构造传 `verify=False` 跳过 CA 装载（实测 1453ms→2.6ms；verify 只作用于
   https 握手，纯 http 回环零安全影响；`_URLS` 若配 https 自动回退默认校验）。
3. `keepalive_expiry=25s < uvicorn timeout_keep_alive=30s`：空闲连接由我们先关，
   不在服务端 30s 关闭竞态窗口里捡死连接；fanin 幂等 GET 另有传输层错误单次重试兜底。
4. fanin 观测：每扇入一行日志，逐片毫秒数 + ok/n + 错误名（慢 runner/部分失败时
   WARN 可见是哪一片、各等了多久；总耗时>1s 也留 WARN）。
5. 白名单补 `/api/works/{}/cards/{}/sessions`（席位会话复数端点，与既有单数 `/session`
   同族本地无锁读——它此前不在白名单被逐请求转发）。

**读数**（隔离实例探针 `perf_batch1_probe.py`，同一后端 A/B）：

| 项 | 旧样式（每次现建客户端） | 新样式（复用） | 倍率 |
| --- | ---: | ---: | ---: |
| nav/running 扇入 P50 | 525.7ms | **11.6ms** | ~45× |
| nav/running 扇入 P95 | 3330.4ms | **36.9ms** | ~90× |
| 转发 GET（stream 池）P50 | —（旧约 0.5-1s+） | 14.8ms | — |
| 本地 sessions（新白名单）P50 | —（旧被转发 ~1s） | 6.6ms | — |
| SSE 常驻+慢订阅期间短查询 P50 | — | 12.3ms | 分池不挤占 |

- forward_ctl：8 次调用 + 1 次探测 = **9 请求 / 1 条 TCP 连接**（服务端连接计数实证复用），
  8 连发全程 10.6ms；非 2xx→`runner_http`、不可达→`runner_unreachable`，错误语义照旧。
- 客户端创建次数：隔离 web 进程 server.log 仅 **1 条**「回环客户端族已建
  loop=0x… role=web kinds=short/stream/ctl verify_bypass=True」——创建只随进程+循环+用途。
- 故障演练：杀 runner2 后扇入 200 合并、日志 `per_runner_ms=[10.1, 4050.3, 9.1, 9.0]
  ok=3/4 err=['runner1:ConnectError']`（逐片归因）；全杀 → 502「全部 runner 不可达」

  全绿。过程中出现两次秒级尖峰（6.0s/2.7s，四片耗时完全一致）复测未复现——该形状

## 二、第二批 大卡时序与轻量读取

**病灶（实测，109MB 合成卡 = 3000 行 + 5×20MB 巨型行 + 8 revoke，`perf_batch2_gen.py` 可复现）**：
1. 撤销区间缓存按 (mtime,size) 整体键控 ⇒ **每追加一行即失效**，下次 timeline 全文件重扫
   （追加后首击 221ms/109MB；card_007 747MB 按比例 ~1.5s，与基线 tail=50 首击 1.02s 吻合）。
2. `before` 翻页恒走全量 `read()`：每次 360-388ms + 内存翻 2-4 倍（747MB 即 MemoryError 高危）。
3. 会话标签/时序端点走 `read_card` 全行读（正文大列全捞）。

**改动**（`src/storage/event_log.py` + `card_db.py` + `card_store.py` + `routes.py`）：
1. **增量撤销/索引扫描器**（`_scan_state`，沿用 `_REVOKE_CACHE_MAX=512` 条目上限口径）：
   - 状态按路径记「已扫到的**完整记录边界** size_scanned + spans + 可选行位置索引」；
   - 文件只增（追加）⇒ 只扫 `[size_scanned, 最后一个 \n 边界)` 的**新增完整行**——
     并发追加只发布完整边界结果，半行由下次补读；前缀一致性用头 64 字节指纹确认；
   - 截断/替换/同长改写（mtime 变长未增）/前缀不确认 ⇒ 从现有原文**安全重建**；
   - 巨型行零整行拷贝：行定位与 "revoke" 探测走 `mmap.find`，seq/ts 抽取只切行首/行尾
     小片（ts 是骨架末键，行尾 rfind 可靠），抽取失败才整行解析兜底；
   - 行位置索引（ts/seq/offset，供翻页免全量）与 spans 同扫描器增量维护；单路径超
     `_INDEX_MAX_ENTRIES=20万` 行弃用索引、翻页回退全量路径（spans 不受影响继续扫）；
   - 观测：`scan_stats()` + 每次重建/增量 INFO 行（触及字节量/跳过字节量/耗时）。
2. `timeline(before=…)` 改走索引：可见集合按 (ts,seq) 全局排序（`_norm_ts` 与
   `_chrono_key` 同函数，语义逐字一致）→ 序位截窗口 → **只解析窗口内那些行**；
   索引不可用时回退全量路径（原语义兜底）。tail/from_seq 路径不变。
3. 窄投影三件：`card_db.get_card_row_cols`（白名单列 SELECT）、
   `card_store.read_card_sessions_light`（sessions/created_at 两列，供 /sessions 与
   /timeline 存在性+附加会话校验）、`card_store.iter_card_titles`（align-status 浮窗
   名单不再全表捞 meta）。

**读数**（改前 → 改后，同卡同口径）：

| 项 | 改前 | 改后 |
| --- | ---: | ---: |
| 追加后 tail=50 首击（缓存失效重扫） | 221.3ms（全扫 109MB） | **30.1ms**（增量 2.6ms 扫 278KB、跳过 109.8MB，日志实证） |
| tail=50 温读 | 8~267ms（窗口含巨型行时 267） | 8.5~10.7ms |
| from=水位 增量 | 8~268ms | 8~10ms |
| before 翻页 | 360~388ms（**每次全量**） | 首建 191ms 一次性 → 温 9~11ms；**追加后 9.7ms（纯增量，无重建）** |
| sessions 端点 | 5~6ms（小卡） | 6~7ms（窄列；大正文卡省 IO 与解析） |

- 语义等价：`tests/test_event_log_incremental.py`（7 用例）钉住——追加只增量
  （full_rebuilds 不涨/delta_scans 涨）、半行不发布补读后发布、截断/替换重建且
  **撤销项不复活**、翻页与参考实现逐条等价（乱序 ts+嵌套 revoke+坏行+100KB 巨型行）、
  追加后翻页锚点稳定、并发追加不崩且最终一致、追加成本不随历史增长（<4KB 断言）。
  既有网 `test_event_log_tail.py`（含「tail 不许全量解析」性能契约）与
  `test_revoke_scan_perf.py`（P24 缓存契约）全绿。
- 一次性成本（诚实项）：进程重启后该卡首次 tail/翻页各付一次全量重建
  （109MB 实测 118/161ms；747MB 约 ×7）——tail 契约禁止 eager 全量解析，索引只能
  惰性补建；此后追加/翻页全程纯增量。
- facts.db-wal（9.4GiB 占盘 vs 1.6MiB 有效帧）：按方案口径**占盘与写入积压分别记账**，
  本批未动存储侧；未观察到持续积压增长，如增长再按锁等待/检查点证据立项。

## 三、第三批 模型请求装配

**病灶（实测）**：
1. `compose_model_request` 在**每个工具续跳整单重渲染全部分区**（生产分区装配体积
   中位 1.23MB/次，`logs/observe-20261119.jsonl` regions 行）——而 system 区在回合内
   不变（request_* 字段仅被 prior/user/once/tail 区消费，逐区核实）。
2. 回合开场 `build_context_bundle` 渲染 viewpoints 剖面，但席位进场时 run_seats 会带
   seat_identity **重新 compose**——开场那份从未作为模型输入，直答回合（绝大多数）纯白付；
   且日志留痕的 vp_system_prompt 是无身份注入的陈旧版，不是席位实际收到的。
3. 装配链无分段耗时；网关出站等待里「等首字」不可见。

**改动**（`context_regions.py` + `context_assembler.py` + `message_runner.py` +
`observe.py` + `gateway.py`，全部增量）：
1. **同回合 system 区缓存**：`compose_model_context` 拆 system（按 ctx 实例×profile
   缓存，生命周期＝单回合，**零跨回合复用、零失效机制**——任务书口径：事实源无可靠
   版本不跨回合复用）+ 动态通道（prior/user/once/tail 逐跳渲染，均直通零加工）。
   `system_override/system_prefix`（draft 链路每次可变）在场时缓存自动旁路。
   观测：`system_cache_stats()` 命中账 + assembly 打点行（system_render/dynamic_render ms）。
2. **viewpoints 懒渲染**：`build_context_bundle(with_viewpoints=False)` 生产主链路跳过
   开场渲染；席位进场 compose 后 `state.vp_system_prompt` 改存**真实席位请求**
   （带身份注入那份——留痕更准）。缺省 True，测试/其他调用方契约逐字不变。
3. **分段打点**（observe JSONL）：
   - `kind:"assembly"`：build_context（memory_load / build_ctx_render ms）；
     compose_model_context（system_render / dynamic_render ms + system_cached）；
     model_hop:first / model_hop:tools（serialize＝轮槽折叠+compose，outbound＝网关全程），
     带 round/seat/pair_id/model_used——首跳、续跳天然可分，凝练请求由 model_call 行
     caller（`condense:*`）区分；
   - `model_call` 行新增 `first_chunk_ms`（发起调用→首个提供方事件，流式通道采集；
     None＝未采集如实留空）——出站等待里「等首字」分段可拆。
4. 模型端连接配置未动（网关自理，任务书口径）。

**读数与语义核对**：
- 受控替身（`tests/test_perf_batch3_assembly.py`，4 用例全绿）：
  ① 续跳 system 区**逐字节一致** + 缓存命中账 +1；② main/viewpoint 各自缓存互不串；
  ③ bundle viewpoints 懒渲染契约（False⇒None、缺省不变）；④ 两跳最终请求核对——
  system 逐字节一致、工具调用对完整（assistant(tool_calls) 与 tool 结果配平）、
  当前轮短提示只随首跳、续跳 user 位按「工具轮去假 user」既有语义留空且本轮原文
  固化在 prior[0]（上下文完整）。
