# 权限管理 · 需求（开源生态版，2026-10-14）

> 性质：需求定义（未施工）。承 `docs/卡片生态-架构定义-20261014.md`。
> 权限是底座**唯一横切约束**——其余一切皆接口、皆可组合，唯独权限不许绕过。本文定义权限管理在开源生态下的完整需求，与实现方案、第一步任务书分离。

---

## 一. 定位：唯一的横切约束

底座管机制、不管形态；一切皆接口、一切皆可组合。**唯独权限**：卡片不能获取「权限管理」之外的权限。

含义：权限系统是系统里唯一的能力发放口。无论第三方卡怎么写、写什么，它能拿到的一切能力，只能从这个口流出、被记录。代码再自由，它的世界就是关口发给它的那组能力——没发的，它连看都看不见。

## 二. 分层：底座给能力，资格归权限管

| 层 | 干什么 | 边界 |
|---|---|---|
| 底座 | 给**能力**（纯机制，不判资格） | 能力与资格的判定分离 |
| 权限 | 管**资格**（谁持有、对谁生效、何时可撤） | 唯一有能力发放权 |

底座新增任何能力（沿连线读、发消息、读文件…），都只是"能力"；它的资格，一律归权限管理。

## 三. 现状盘点（读码实证）

| 项 | 现状 | 问题 |
|---|---|---|
| 两级定位 | project_class（工牌）× card_type → 开关列表 | 按类型发权，类型解绑后失效 |
| 词汇表 | SWITCHES 常量（12 项，封闭集合） | 正确，保留 |
| 固化 | 建卡算一次写卡上 perms＋version，运行时读固化值 | 正确，但只有"建卡固化"一条路 |
| 默认关门 | 未配置＝全拒 | 正确 |
| 树作用域 | 仅对写开关（edit/delete/link/unlink/create_child） | READ 无树作用域 |
| 缺口 | 对话（timeline）**无鉴权裸奔** | 三样数据安全性不一致 |

## 四. 开源生态打破的两个假设

**假设一：能力按"卡片类型"发。** 现状 `project_class × card_type → 开关`，类型是封闭集合。生态开放后卡种无限，按类型发权这条路断了。

**假设二：授权只在建卡时固化。** 现状建卡算一次存死。生态要求：用户下载卡时**知情、逐项批准、事后可撤销**——授权从"类型固有"变成"用户对该卡的具体决定"。

**最狠的一条**：代码执行。第三方卡一旦能跑自己的代码，它在进程内无所不能，可绕过一切开关。守不住这一条，"卡片不能获取权限外的权限"就是空话。

## 五. 目标权限模型（三层）

### 5.1 能力是唯一的权限单位

系统能提供的每样东西（读卡、写产物、调模型、联网、读写文件、发消息、调其他卡、挂上下文…）都叫一个"能力"。权限＝某主体持有哪些能力。现有 12 个开关是能力的雏形，保留作底子、随需求扩充。

### 5.2 授权三层叠出

```
系统默认规则（根卡不可删等，不可覆盖）
  ＋ 类型默认（出厂卡种自带的习惯）
  ＋ 用户对该卡的具体批准（下载时逐项勾、事后可撤销）  ← 生态新增的关键一层
```

### 5.3 能力只从关口发放，别处无门

- 第三方代码运行在受限环境，**无裸进程权限**（不能直接碰文件/开网络/调系统），要任何东西都通过关口发的**能力句柄**——句柄是能力的化身，没发的句柄看不见。
- 每次能力使用过关口、全量留痕（现有 append_perm_log 机制天然支持，扩到全部能力）。

## 六. 申请制 ＋ 代码层事实（外部卡片的核心需求）

1. **申请制**：外部卡片安装时，用户必须知道它要用哪些权限，**同意才生效**；不同意，卡片不安装/不激活。
2. **代码层事实，而非声明**：权限清单**不是卡片自己报的**（声明可撒谎、可少报），而是系统从卡片的**代码实际调用**里静态提取出来的——调用「读文件」接口就查出要文件权限，没调用就查不出。信任根放在代码上，不放声明上。
3. **最小权限**：实际用了什么申请什么，没用的一个不申请——看它"用"多少，不是听它"要"多少。
4. **权限提升须重新确认**：卡升级新增权限项时，已装用户须重新确认新增项；未确认前按旧授权集运行，**不静默扩权**。

## 七. 词汇表封闭（唯一不许开放的地方）

能力词汇表（SWITCHES）是**封闭集合**：manifest/代码里出现词汇表外的权限码 → 拒。安全必须集中，词汇表由底座代码定义、随版本走，第三方只能**引用**现有能力，不能自造能力。加能力＝升版本＋代码加常量＋配置用起来（裁定 6）。

## 八. 与第一步的关系

第一步（沿关系读/通信）只做两件事：

- 新增两个能力码 `read_linked`、`send_card_message` 入词汇表；
- 保证它们**能被权限管理接住**（词汇表可扩展、代码常量可加）。

**申请制＋代码层事实＋沙箱**属权限迭代主体，独立推进，不在第一步。第一步落能力，权限迭代落资格。

## 九. 待裁项（不阻塞，登记备查）

1. **沙箱强度**：代码执行器的隔离级别——A 重沙箱（受限解释器/容器，机制上碰不到系统）／B 轻沙箱（只准 import 底座 SDK，防君子不防小人）／C 分期（v1 不开放代码执行，纯声明式能力先行）。当前倾向 C。
2. **能力码命名**：read_linked / send_card_message 为暂定名，权限迭代统一收口。
3. **粒度细分**：读正文/影子/对话是否拆三个能力码，还是一个码覆盖（当前倾向一个码先行）。
4. **对话鉴权缺口**：timeline 现状无鉴权，是否纳入权限关口、何时收口，待裁。
