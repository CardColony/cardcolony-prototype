## 二、先取证再动请求路径

前序样本在 `card_007` 观察到 timeline 请求至 TTFB 约 0.54–0.60 s，响应头已测的服务端执行约 32–35 ms。差额的归属待证。`/api/nav` 的首份快照构建、热读和过期后台重建分别记录，固定预热、TTL 与数据快照。[既有分段](../logs/chat-seg-u0VyNa/segments.json) · [导航快照](../src/api/routes.py#L555)

1. **补齐同一次开卡的时序。** 浏览器侧记录导航、模块就绪、timeline 发起与真实可读点。用 CDP waterfall、Resource Timing 和必要的 Chrome 轨迹区分发起前依赖、浏览器排队及连接阶段、请求发出至首字节、正文传输、解码和渲染。服务端以同一个请求标识串起 web 入口、转发、各 runner 排队和处理、合并与编码。先复用已有的 `Server-Timing` 和逐片耗时。时钟或采样覆盖范围不足时保留未归因耗时。记录当时的协议、实际并发、SSE 连接数、API 请求发起栈及 nav 构建状态。[分段探针](../tests/chat_perf_segments.mjs) · [runner 扇入](../src/infra/procs.py#L459)
2. **只改变可延后状态请求的启动时机，跑一次成对干预。** 固定代码、数据、浏览器缓存与服务端预热。对照臂照常启动。干预臂优先用测试旗标，在调用发出前把重复状态读取和首屏无需消费的后台读取推到可读点之后。使用 CDP 拦截时，用瀑布图确认受控请求在可读点前的发送与连接占用情况。两侧均保持必要快照、timeline 和应用数据语义。记录受控请求清单，报告 timeline 的排队、TTFB 和双帧可读点分别变了多少。状态请求若已明显变少而首屏时序相近，按实测归因，保留请求减量的独立结果。
3. **冻结前后版本和改动边界。** 保存提交、局部补丁及静态指纹、数据快照标识、进程和端口、runner 数、缓存与预热设置。优先从现有入口接线。证据表逐条给出请求 URL、发起者、初连/定时/事件/重连触发、权威来源、可合并项和必要读项。重点检查聊天恢复时的裸 `/api/nav/running` 与导航初探是否重复。[聊天恢复入口](../static/stream.js#L2048) · [导航启动与轮询](../static/esm/nav_system.js#L600)

### 3.2 施工顺序

1. **统一查询入口。** 移除同一页面同义查询的重复发起者。对同作用域、同查询语义的在途读共享结果，合并短时间内的事件触发。保留现有共享请求的取消和写后读规则。补丁只写对应 work 和卡，应用前核对请求、订阅归属和世代。首屏可用状态先到先交给界面，活动查询按使用时机发起。状态刷新失败与成功返回空集分别处理。
2. **初连和重连读权威快照。** 当前工作级 SSE 依赖连接后的推送。首次进入取快照，断线降级成同作用域单通道查询并退避。重连查缺并停止降级循环，初连/重连的取快照窗口内到达的事件也要正确合并。沿用已有水位时按水位排先后。缺少可对账水位时，用刷新世代和必要的补读保证迟到快照盖不回新事件。连接显示健康时仍保留低频校准，覆盖丢帧及其他 work 的变化。记录校准与退避周期及其依据。
3. **处理多 runner 的覆盖范围。** 复用现有 web 扇入。现状允许部分成功返回 200 聚合，因此需要向新消费方提供完整性及已覆盖/缺失的范围，字段或响应头可增量扩展。基于已分类的响应局部更新可确认分片，缺失分片保留上次状态并标为待校准。成功且完整的空结果可清除已结束或重启前的运行态。逐项测试超时、非 200、全失联和恢复。兼容旧后端时走现有读口与校准路径，并验证旧前端仍可消费既有响应。新增只读端点时明确 web 本地、属主 runner 或全 runner 扇入的落点。

## 四、独立回归和性能总验收

### 4.1 任务三独立验收

用同一隔离快照和固定事件序列，分别测健康连接、断线有变化后重连、一个 runner 无响应及恢复。扇入必须在至少两个 runner 的真实拓扑上验到，记录各 runner 地址和测试卡属主。覆盖开始、排队、完成、失败、用户停止、续跳、切 work 和同号卡。至少验证一次重复事件、一次旧 work 迟到响应、一次活跃不翻转的阶段变化，以及抽屉打开时的历史与已读交互。每个用例对账事件或权威读口与最终界面。保留已有热切位置、失败回滚、发送归属与对话页 SSE 回归。

按等长观测窗口分别给出首屏、稳态和恢复期的请求数、状态请求数/分钟、响应字节、事件到界面可见的 P50/P95、超时数和缺失范围。采样间隔与计时起点写入证据。独立通过条件是健康连接的同义请求确实减少，断线期间同一作用域无并发探测风暴，重连后正确收敛，部分缺失时状态无误清。报告任务三改前和合源版的 `card_007` 冷开、`card_009` 普通卡冷开、同文档热切，以及画布状态延迟。首屏段归因与实测耗时单独汇报。

### 4.2 合并后的累计门槛

用固定的原始基线 `8f1ce45` 加第一批已登记保留块，对任务一、二、三合并版做第二组对照。原轮记录的 1,886 ms 属于旧探针口径，正式门槛按本次同口径基线重算。任务三单项用任务二最终版作基线，累计收益用原始基线作基线，两组结果分别出表。[第一批对照记录](../logs/chat-perf-5rjIaC/result.json) · [基线工具](../scripts/make_baseline_tree.py)

- 总门槛为 `合并版 P95 ≤ 原始基线 P95 × 0.70`。主样本为 `work_073/card_007` 的冷开。两边用同一探针，成功标准为目标卡的真实用户或助手正文有字，与实际滚动视口相交，并在连续两帧后仍可读。补齐现有探针的视口检查，验证它能覆盖基线与新渲染路径。工具、步骤、骨架和视口外余量行不能触发完成。
- 固定浏览器版本、视口、数据、进程拓扑和预热规则。每个核心场景至少 20 个有效配对，交替先后次序。冷开用隔离浏览器上下文，热切用同一文档内已加载卡。服务端冷启动与已预热样本分开出数。保留所有长尾、超时和失败，作废规则在跑前写明并对两侧一致应用。提交逐轮原始值、P50/P95/最大值、失败与作废理由、请求与字节、关键轨迹。按有效样本实报通过、未达或未验证。
