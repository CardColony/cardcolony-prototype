> 定位：**第三种连线**——卡片之间的依赖／关联关系。模型侧建、双向可见、注入上下文；
> **不参与通信**。同时把「通信线」与「关系」在**命名**上分开：`relations` 这个名字
> 从通信线手上收回，交给这条新线。

## 三、设计

### 3.1 命名腾挪：通信线让出 `relations`

- 通信线卡上字段 `relations` → **`links`**（建议名，可推翻；备选 `channels`）。
- 改名波及：存储列名、投影字段、工具内部、前端 `vm.relations`、测试、BASE_PROMPT 文案
  （清单见 §四）。
- **数据迁移**：`ALTER TABLE cards RENAME COLUMN relations TO links`，走 `card_db`
  既有的**幂等升级**通道（与 `_ensure_tables` 同款做法）；迁移前备份 `works/*/cards.db`。
- **语义一字不动**：`read_linked` / `send_card_message` 的判据、`link` / `unlink` 关口，
  全部原样保留——**本次只改名字，不改行为**。

### 3.2 新线（依赖关联线）数据形态

- 卡上字段 **`relations`**（JSON 数组，与 `links` 并列）。
- 条目形态：

```json
{ "target": "card_007", "kind": "依赖", "detail": "依赖它的接口设计" }
```

- `kind`：`依赖` / `关联`（区分两类语义）。
- `detail`：自由文本，写清"依赖什么 / 关联什么"。
- **"关联哪些" = 多条条目**（一条一个 target）——同一张卡可以有多条。
- **只在发起方卡上存一条**（保留方向：source 发起、target 被指）。

### 3.3 双向可见（B 也要知道）

- **存储不冗余**：只在发起方 A 上存。
- **注入时双向渲染**：
  - 正向（读自己的 `relations`）→「我依赖/关联：B（detail）」
  - 反向（全库扫 `relations` 找 `target = 我`）→「依赖/关联我的：C（detail）」
- 反向扫**零额外 IO**：上下文装配本就加载全库卡清单（`_load_cards_index`），
  在它上面多带 `relations` 一列即可。

### 3.4 建线工具（模型侧）

- 新增一对：`link_rel(target_id, kind, detail)` / `unlink_rel(target_id, kind?)`。
- 与 `link_cards` / `unlink_cards` **对称但不混用**——它们写的是两个不同字段
  （`links` vs `relations`），工具名与字段名一一对应。
- 权限：复用现有 `link` / `unlink` 开关（**不新开**）；树类收紧「只能连自己子树内的卡」同款。
- 工具面按现有四级过滤（角色／分类／卡类型／根卡）自动生效。

### 3.5 上下文注入

- `context_regions.py` 的 `REGION_TABLE` 新增一区：key = `relations`、name = `依赖关联`。
- **order 建议 250**（200 记忆之后、300 对话历史之前）——满足"不能太靠上"。
  - 备选：180（紧随 170 直接子卡现状，语义上同属"卡间关系"，但更靠上）；
    350（更靠下）。
- 渲染内容＝当前卡的**双向**依赖关联线；无线 → 区不出现（沿用"没有来源就不出现"）。
- seats：main only（三席零指令铁律不动）。
- `config/context_regions.json` 同步加控制面条目。

### 3.6 画布

- **本次不做**（用户明说）。
- 但注意：`static/canvas.js` 里的 `vm.relations`（**通信线**）**必须跟着 §3.1 改名**，
  否则前端读不到数据——这属于"改名"，不是"新线渲染"，两者别混。
