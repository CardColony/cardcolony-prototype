# 推演agent 项目统筹职能联调与验收任务书

实施仓库为 `D:\AI_station\推演agent`。本批交付一个完整的隔离 work。用户能从计划卡的原事项查到统筹发令、域责任卡接令和派工、执行回报及独立 QA 结论。A5–A8 交正式路径的验收记录，A9 并行交成本和判断质量对照。本批沿用原任务书与上一批已经通过的实现。 [原施工任务书](推演agent项目统筹职能施工任务书-20261121.md) · [上一批任务书](推演agent项目统筹职能下一批施工任务书-20261122.md)

## 开工与分工

项目内统筹先在计划中登记事项、域责任卡和证据归档位置，再沿正式消息入口发令。统筹给出目标、依据和验收判据。域责任卡决定如何拆分、哪些工作沿用已有卡、哪些工作确需建卡，派工留在本域。外部统筹负责核对证据和纠偏。试验进程、配置、works、日志、PID 文件与快照目录一并隔离。5700 生产组维持运行，生产旁观与实发由用户按原任务书另行裁定。

| 工作 | 开始条件 | 交付顺序 |
| --- | --- | --- |
| 一、双 runner 联调 | 当即准备隔离拓扑、固定模型和故障夹具 | 先验证 A5 的投递恢复和 A6–A7。工作二完成后补 A5 的执行证据。 |
| 二、执行证据回挂 | 当即开工 | 先完成宿主绑定和只读回读，供 A5 和浏览器共同使用。 |
| 三、域责任卡接令与派工 | 当即对照现有通信权限和域内派工入口开工 | 与工作二共用事项和证据关联。执行回报回到原事项后做浏览器验收。 |
| 四、A9 模型回放 | 固定可还原的历史材料后开工 | 独立出对照结果。缺原始材料时登记缺哪一段、哪些结论因此无法得出。 |

开工记录写明代码版本、工作区差异和现有用例结果。以本轮闭环为范围，遇到正式路径失败时先记录断点和实际证据，再修出相应回归。此前通过的 QA 断点恢复、普通 `direct`、独立回看只读、同轮先存计划再发令保留为回归项。现有工作因权限或拓扑被拒绝时先查既有契约，沿正式入口解决。

## 工作一　双 runner 实际投递与恢复

使用两个不同 PID 的 runner，采用现有 `ECO_RUNNER_COUNT=2` 和独立 `ECO_RUNNER_BASE_PORT` 启动。两 runner 共用同一套隔离 work 数据，计划卡与目标开发卡分属不同属主。启动回执记录实际读写路径、端口、PID、卡号与属主映射。通过正式入口、实际 HTTP 转发及目标属主验证。测试替身只负责固定模型输出和指定中断点，收件、事件、唤醒与恢复走现有服务实现。 [进程拓扑](../src/infra/procs.py) · [正式恢复调度](../src/infra/coordination_watcher.py)

| 用例 | 操作 | 通过条件 |
| --- | --- | --- |
| A5.1 并发与回执丢失 | 两片并发提交同一行动。目标落信后切断转发回执，再按原行动键重放。 | 得到同一消息号。目标会话块、原文账和事件按该消息号各一条，实际回合接纳一次。 |
| A5.2 目标离线与自动恢复 | 在目标测试 runner 不可达时实发，确认待投，再启动目标 runner。另用一个行动在收件后、唤醒接纳前中断。两个场景都等正式调度恢复。 | **主动重发之前**，读到调度沿原行动键完成补投或补唤醒的证据。首次已收件的场景沿用原消息号。已经接纳的回合重放后次数不增。 |
| A5.3 执行证据 | 让实际接纳的目标回合走正式回执，提交一项可读产物或明确失败事实。 | 原事项显示对应行动的执行证据。能打开原回执及证据，且 QA 结论独立呈现。 |
| A6.1 收件前变更 | 分别由用户改计划版本、缩小范围、暂停和撤回。每次在目标提交收件前完成变更，再核查旧回合的发令结果。 | 每种都有拒因。实际目标会话、事件、回合的新增均为零。 |
| A6.2 收件后变更 | 收件已提交，唤醒尚未被目标回合接纳时撤权。再用新任命重放旧行动。 | 原消息号仍可查，新增收件和唤醒接纳均为零。 |
| A7 旁观、实发和越权 | 对同一张无父子关系的开发卡分别尝试旁观和已授权实发。另试范围外目标和缺正式通信线的目标。 | 旁观只留拟发。授权与通信线均成立时有实际收件，署名可追溯到任命职能。两个反例均有拒因，收件和唤醒增量为零。 |

## 工作二　让执行证据回到原行动

沿已有统筹行动记录、目标回合来源与正式执行回执做关联。目标回合已有 `coordination_msg_id` 等宿主来源，正式汇报已有 `reply_to` 等回执坐标。先查清正常入口上的绑定点，再将本 work、计划事项、原行动键、收件消息号、目标卡与已落盘回执关联起来。产物使用现有能回读的会话、事件或产物坐标。目标、来源和回执归属由宿主核验。模型正文里的卡号、任务号和路径可以作为内容展示，其本身无法确认这条关联。 [目标回合来源与行动回读](../src/api/coordination_runner.py) · [正式汇报](../src/api/card_tools.py)

- 已落信和已唤醒沿现有证据更新。目标回合提交可打开的正式回执，经绑定校验后，才显示「已取得执行证据」。证据可以说明完成、部分完成或执行失败，QA 照自己的结论显示。
- 重复回执按原坐标去重，刷新和重启后仍能打开。普通汇报继续按原路径展示和投递。重复、无关联、错行动、错目标、他 work 同号和坐标不可读分别验收。除正确回执外，行动状态不推进。范围外材料遵照现有读权限。
- 前端继续走「项目统筹 → 计划卡 → 原事项」。同一行动可看到目标、验收判据、发令版本、消息号和可打开的回执。刷新、查看历史和打开回执期间，统筹模型调用增量为零。 [现有统筹面板](../static/esm/coordination.js)

## 工作三　域责任卡接令、派工与 A8 浏览器验收

在隔离 work 准备两个有明确域责任卡的事项。统筹正式回合向两张责任卡发指令，带上原事项、依据与验收判据。第一项由责任卡交已有子卡承接，验证零新增卡。第二项确需新增执行卡，由责任卡在自己的正式回合里按现有权限调用 `create_worker_card`，在其有权管理的父卡下创建并启动。检查责任卡会话中的原指令、派工决定和执行卡回报，再由责任卡向统筹回报并关联原事项。 [正式执行卡派生](../src/api/card_tools.py#L1999)

1. 对同一条统筹指令并发重放，并在责任卡建卡成功、执行回合接纳前中断后续办。核对原指令消息号、责任卡派工记录、执行卡号和目标回合接纳次数。建卡路径只创建一张执行卡，首轮只接纳一次。失败时能从原事项读到受阻环节及原因。
2. 分别验证旁观、旧版本及任命撤回导致统筹发令被拒，检查该指令产生的责任卡收件、派工、建卡及接纳增量均为零。统筹回合直接请求建开发卡、责任卡越权派工时，分别核对零新增卡、零接纳。正向用例走在任统筹发令、责任卡接令和执行卡回报的正式回合，夹具只准备初始数据、固定模型输出和指定故障。
3. **A8 用真实浏览器验收。** 让 PM 统筹在该事项自行处理一个产品问题，再向 CTO 单独提问。核对 PM 没有另开自问回合、CTO 实际身份和只读工具面。让正式 QA 差事提交明确失败及证据，再发一条关联该失败的修正行动。QA 失败保留，修正和复验可分别回读。
4. 从画布「项目统筹」打开计划卡和原事项，确认谁发令、谁派工、谁执行。进入责任卡会话核对原指令及域内派工记录，逐个打开 CTO 答复、原 QA 失败回执、修正行动和执行证据。同卡有两份回执时，分别点击并核对各自正文，刷新后复验定位。保存操作路径、关键截图、对应 API 返回、差事号及刷新前后模型调用增量。若已有证据覆盖同一条款，可引用可复跑的原记录。

## 工作四　A9 历史回放对照

固定同一个历史窗口、当时有效的需求版本、证据快照和样本标签。按当时可见的顺序分别运行「每批叫强模型」「仅到期回看」「弱模型观察＋独立回看」。保留正常样本和未参与唤醒标准编写的样本。后来写出的纠偏、报告和源码排除在当时材料之外。缺原文或版本无法复原的样本记「资料不足」。SQLite 使用一致快照，涉及 `build_ctx` 的回放使用隔离副本。 [A9 原验收口径](推演agent项目统筹职能施工任务书-20261121.md)

每组给出实际强弱模型调用次数、可取得的 token 用量、从首条相关证据到首次有效判断的时延，以及误报、漏报及其原始样本。模拟调用单独列，缺用量记未知。给用户保留比较和判断试点价值所需的原证据。

## 回执与完成条件

每项回执落在项目内对应事项，包含代码版本及改动文件、正式入口、实际运行命令与输出、初始状态、操作和中断顺序、证据坐标及结论。双 runner 另附 PID、端口、属主映射，以及每个行动的会话、原文账、事件和回合接纳对账。浏览器另附刷新前后证据。回执统一标「通过」「失败」或「未验证」，失败附首个断点和待解决条件。保留原任务书 A1–A4 的证据索引，缺实证的条款补相应缺口。
