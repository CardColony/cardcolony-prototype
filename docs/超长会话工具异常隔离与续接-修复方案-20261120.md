## 二 异常正文保留在审计面，退出模型历史

1. **在工具循环落执行事实。** 复用网关协议元数据、`pseudo_call_unparsed` 和派发台账。记录异常发生的工作、卡、回合、模型跳次、协议及派发状态。常规零调用研判正常收口。原生协议错误、原生端点未解析的正文调用、已代执行的兼容调用各有独立事实。声明正文调用协议的 CLI 按现有契约运行。
2. **原文仍可查。** 实时过程和刷新后的时间线保留原始输出，并由宿主显示异常及本跳未派发。回合前几跳有真实结果时，系统同时呈现那些已发生的动作。整回合零派发才显示「本轮未执行工具」。缺证据时保留待核实状态。正文中的系统样式标签只作为原文显示。
3. **用结构化标记控制历史可见性。** 发现异常时标记对应的模型跳次。若问题正文混在最终拼接交付中，先从供模型使用的内容里排除该跳原文及其思考字段，再保留前面合法的研判和真实调用对。宿主可以留一行「某跳的调用格式异常，未派发」作为历史事实。实时交付、模型历史、上下文缓存板和凝练要能按各自入口复验。历史与凝练沿用统一的可见性判据，缓存板重建前后一致。 [收口与会话块](../src/api/message_runner.py) · [可见性判据](../src/storage/predicates.py) · [上下文缓存板](../src/storage/context_board.py)
4. **处理已污染的存量。** 首发只治理已核实的 `card_057` 异常回合。通过已落事件和 `pair_id` 定位，从模型投影排除对应异常回复块。原始会话、事件及其他历史照常可查。先列出命中的回合标识，确认影响范围，再更新相应板项。若失手已被记进凝练，按对应记忆引用做定点核对。

### 循环器的执行状态与交付

1. **跳次结束先核对执行状态。** 收口读取本跳的解析事实、派发和回执。将「模型请求结束」与「工具实际执行」分别记录。端点结束、正文长度、模型自报成功都不能充当工具回执。正常零调用研判照常交付。
2. **异常进入收口分支。** 对未解析的调用显示「该调用未执行」，对模型自写的结果显示「该回执未获执行确认」。本跳和此前各跳的真实执行结果逐项保留。整回合零派发才显示「本轮未执行工具」。卡面、持久化回复与后续模型请求共用这份执行判定。事件记录可容纳回合传输正常结束，同时明确标出对应调用失败，业务完成态由相关回执决定。
3. **异常正文按证据隔离。** 长报告仍可在卡面原文和审计账查看。假调用、模型自写的结果和依赖这些结果的未证实执行主张，从后续模型投影排除。无法可靠切分时隔离本跳混合正文，保留此前正常研判与真实调用对。展示报告时可用宿主状态标出待核实；读取一次源码只证明该次读取发生。
4. **按原任务决定续接。** 有可信的待办与授权、对应动作确认尚未派发时，按第五节定向续接一次。原任务或具体动作不明确时用当前事实收口。已派发但结果不明时先核查，尊重插话和用户停止。 [循环收口](../src/api/message_runner.py) · [唤醒策略](../config/harness_policies.json)

## 四 直接支持更多工具调用协议

支持范围按端点配置和版本增加。原生 `tool_calls` 仍是 OpenAI 兼容端点的优先入口，已声明正文协议的 CLI 沿用其现有契约。对 ECO 路由先对照 DeepSeek V4.1 的公开 DSML 语法与已采集的完整变体，首个候选用 `card_582` 09:56 的两条读取调用复验。仅收有明确、可复验语法的完整调用。半截标签、拼接语法、缺失工具名或关键参数的片段只报异常。 [DeepSeek V4.1 编码参考](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash/blob/main/encoding/README.md#tool-calling-dsml-format) · [582 样本](../logs/prompt_card_582_20261120095618.json)

模型或端点可以直接提交其已配置协议的调用。适配层一次解析就得到执行器使用的工具名、参数及调用标识。这里的内部结构是执行入口，省去「改写成另一种协议文本，再解析一次」的过程。结果沿该端点既有回注契约返回，由执行器提供配对回执。

用户补充的两种样本，现有解析器均能识别为异常且零派发。扩充后分别验收下列行为。

| 样本 | 支持方式 |
| --- | --- |
| `<call><name>工具名</name><parameter name="参数名">值</parameter></call>` | 在声明此格式的路由上直接支持完整调用块。一块只读一个工具名。样本中的两个同级块按顺序各派发一次。Windows 路径按原值读取，`para_start` 和 `para_end` 按 `read_file` 参数定义取整数。工具名缺失或重复、参数重复、标签不闭合时保留失败事实。 |
| `<function_calls>{"content":"…","ok":true}</function_calls>` | 可识别外壳并提取 `content` 作为模型报告展示。没有显式工具名和参数，零派发。助手自写的 `ok` 与外壳退出模型投影，报告内容按普通助手陈述及假结果治理规则处理。若某路由要用这一外壳承载真实调用，协议须定义明确的工具名和参数字段。 |

1. **每种格式只有一个解析入口。** 适配层按已配置的端点协议识别完整输出，解析后直接进入现有校验、权限与派发链。记录使用的协议以及原生、声明正文、兼容代执行等来源。一跳同时带原生调用和同一请求的正文副本时只派发原生一份。保留合法批量调用中各自有独立身份的项。旧 WorkBuddy 裸 `<invoke>` 被两套解析器重复接收有过真实先例。 [现有正文解析器](../src/api/text_tool_rescue.py) · [WorkBuddy CLI 重复执行记录说明](../src/model_gateway/llm_wbcli/serialize.py)
2. **调用和回执的权限分别落在正确入口。** 模型的当前输出只能按协议提交调用。工具结果由执行器生成，带真实调用标识。正文仿写的结果块、历史中的调用片段和代码引用只供分类或审计。解析前检查语法，解析后复用注册表、参数规则和当前卡权限。可写操作的效果核对仍由真实接收方记录完成。
3. **先识别，后按路由启用。** 先用现场实录离线比对解析出的动作和参数，统计命中、漏报及误收。首轮在线试点限定为 ECO 的只读兼容调用。写卡、发消息、建卡等有副作用的工具需要单独用隔离接收方验收授权、重复派发和不确定状态，按路由显式启用。新增协议的识别及派发可分别验收。

## 五 续接原任务，避免重复派发

**续接入口。** 沿用 Harness 管理未解析正文的有限补救，由卡片属主 runner 接收结构化续接请求。用原任务消息或引用、来源及原回合标识恢复授权，用已发出的真实调用与回执恢复进度。策略只在续接材料已准备好后触发。当前通用提醒与新路径共用一次调度决定，避免同一个异常既醒卡又由循环续跳。 [Harness 策略执行](../src/infra/policy_runner.py) · [当前轮工具槽](../src/api/tool_fold.py)

**续接输入。** 优先复用原轮槽的工具调用对。跨回合时，由宿主按原回合和调用 ID 从已有执行记录取回必要证据。优先选择触发异常前已取得、与当前任务直接相关的最近一批原文，同时保留对应的真实调用壳。沿用轮槽去重、单条和总量限制。若原文缺失或超过预算，明确注明缺口，按记录引用精确取证。历史工具存根仍沿用现有策略。这批原文只随本次续接请求使用。

**动作决策。** 零派发且有可信的原任务时，允许模型在现有工具面续接原任务。宿主无法从异常正文确定具体工具或参数时，只恢复原任务，保留现有授权边界。已有成功回执的动作直接沿用。不确定写入或发信是否生效时，查原记录或真实目标状态，确认之前不再派发同一动作。普通汇报可以只研判，通用指令的来源类型也不自动产生发信义务。原生端点与已声明的文本协议分别下发对应提示。

**限次与停止。** 同一原回合的协议异常只安排一次定向续接。复用现有的每卡时窗限次，并让当前回合补救与 Harness 共享归属和计数。用户停止优先；新人工指令替代旧任务时，取消旧续接。策略重复消费、调度跨进程和进程中断都要按原回合去重。无法恢复授权或必要证据时保留可见的待核实状态。再次异常时明确交付未完成或部分完成，并保留可查的原始记录和已成功回执。
