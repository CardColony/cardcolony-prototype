# 第二层职能角色 · 组阁判断力实验（5713）

> 2026-10-20 · card_004
> 前一份报告（`5713-第二层动态调阁实验-报告-20261020.md`）验的是**机械通道与台账**：
> 组阁/改档/停复撤每一步都由场景预置 ⇒ 验了"部门可以随时设撤且不烂账"，
> **没验"这个 CEO 会不会设"**。本实验就是补那一半。

## 一、结论先行

| 观测 | A 臂（零干预） | B 臂（问一次） |
|---|---|---|
| 是否组阁 | **0 次**（45 次工具调用里 `create_role` 零出现） | **1 次**，组出 `timeline_contract` 角色 |
| 四个埋点是否发现 | **4/4 全部发现** | **4/4 全部发现** |
| 它怎么处理 | 自己改三卡现状 4 次＋落 4 条裁定＋写核对备忘，然后 `update_goal` 收口 | 同上 **＋ 组阁** |
| 角色是否真干活 | —（无角色） | **是**：phase2 落 1 条判词，模型自证两轮巡检 |
| 局面变了会不会调整 | 无角色可调 | **未调整**（无改档/无撤岗/无补角色） |

**三句话**：
1. **零干预下，根卡不会组阁**——它有工具、看懂了所有问题，仍然选择自己动手收口。
2. **「问一次」是从 0 到 1 的开关**，而且组出来的角色质量很高（排他键唯一、6 条触发线、主动划界、升级线指向根卡）。
3. **但"中途调整"能力缺失（已干净重跑坐实）**：新增第四张冲突卡后，根卡`list_roles`＋`read_card` 读了角色卡，
   **仍不改档、不撤岗、不扩关注范围**（`watched_new_card: False`、charter 仍是 v1）；而角色本身一直在正常巡检（判词 1→2）。

⇒ 对 D02「职能不定死、CEO 按局面灵活调整」的实测判定：**机制支持调整，模型想不到要调整**。
这个结论直接决定经营方式：**现阶段不能把第二层的调阁完全交给模型自转**。

## 二、实验怎么做的（可复跑）

驱动器 `verify/5713/appointer_judgment.py`，两臂同一份材料、同一模型（钉 `ds-v41-flash-aliyun`）、同一实例。

**材料**：一个项目 + 三张工作卡，埋四个问题（根卡不知道这份清单存在）：

| 编号 | 埋了什么 | 指纹 |
|---|---|---|
| P1 | 时间口径互斥：W1 用 UTC 带 Z / W2 用本地 naive | `UTC` / `本地时间` / `naive` |
| P2 | 精度不一致：W1 秒级 / W2 毫秒级 | `秒` / `毫秒` |
| P3 | 成本超支无人盯：W3 预算 5 万/月、实花 9.2 万 | `9.2 万` / `14.6 万` |
| P4 | 状态自相矛盾：W3 既「已上线」又「待联调」 | `待联调` / `上线` |

**两臂唯一差别**在根卡 goal 的末尾一句：
- A 臂：只写任务本身（「把三张接口卡收口……不用建新卡」）
- B 臂：任务 + 「另外：你觉得这套项目该不该有人专门盯着某个方面？你自己判断，需要就做，不需要就说明为什么不需要。」

**阶段二（两臂都做）**：把局面改掉——W2 口径改成与 W1 一致（P1 互斥消除）、W3 成本恶化到 14.6 万；
再用 `/goal edit` 把同一目标重新交给根卡，看它会不会**调整**（改档/撤岗/补角色都算）。

## 三、A 臂（零干预）的现场

根卡（`work_043`，模型自证 `deepseek-v4.1-flash-1017`）45 次工具调用：

write_file×1 update_status×4 append_ruling×4 update_shadow×1

它自己得出（现状块原文摘录）：

> 卡面自述毫秒级）**互斥**，同一字面值相差 8 小时（本机实测本地偏移 UTC+08:00、无夏令时），且精度不一致
> 3) 已核实的成本事实：card_002 重跑 8.7 万元/月（部门上限 6 万元，超 2.7 万）；card_004 实际 9.2 万元/月
> （预算 5 万元，超 4.2 万）；**合计超支 6.9 万元/月，两边均无审批记录**
> 4) 已核实的交付缺口：card_004 报表不含坏账口径、账务导出通道未联调，但卡面称"2026-10-15 已上线、
> 首批 12 张报表已验收"（可核范围内无上线记录与验收单据）

**四个埋点它全找到了**，而且比埋得更细（自己实测了本机 UTC+08:00、算出合计超支 6.9 万、指出两边都无审批记录）。
它的处置是：把三张卡的现状改成"据实版"（`update_status`×4）、落 4 条裁定（`append_ruling`×4）、
写一份核对备忘（`write_file`）、然后 `update_goal` 收口。

**它一次都没想过设角色。** 有意思的是它在定论里写了一个词——「守门员默认动作 UTC+ISO8601 带 Z 兜底」：
它脑子里已经出现了"有人替这条线兜底"的概念，却没有把它落成一张角色卡。

## 四、B 臂（问一次）的现场

`create_role` 1 次 → 角色 `card_005`「接口契约口径守门员」：

- `exclusive_key`: `timeline_contract`（**切了 1 个域，不是堆一堆**）
- `jurisdiction.statement`: 「跨接口对外契约口径（时间基准、精度、金额截断、跨接口换算纪律）的一致性；
  **不涉预算、不涉实现选型、不代卡验收**」← 主动划界，防重叠
- `watch`: card_002 / card_003 / card_004 三张全订；`signals`: `status_changed` + `decision_appended`（订了信号，不是默认全量）
- `speak_contract`: `advice_when` 2 条 + `alarm_when` **4 条**，逐条是条件不是口号——
  其中第 3 条「卡面宣称已定稿/已上线/联调已完成但无归属本卡的成文契约、实现物或验收凭据」**正好命中埋点 P4**，
  第 4 条「卡面关键数值（成本、验收数量、联调状态）在无迭代留痕下变化」**正好命中 P3**
- `escalation`: advice / alarm / critical **全指 `card_001`（根卡自己）**——符合 D02 的辐条星形
- `charter`: 写了"只看三件事""必报四种情况""不越界""沉默优先""口径冲突一律升级到 card_001 出裁定，角色不自裁"

**它只切了一个域，并明确声明其余不归它管**——这是判断力，不是凑数。
（对比：如果它把"成本"也塞进这个角色，就与"时间口径"耦合，反而埋下重叠隐患。）

**角色真干活了**：phase2 判断簿新增 1 条判词（`verdicts` 0→1），模型自证：

```

21:43:12 card_005  ds-v41-flash-aliyun → deepseek-v4.1-flash-1017   (巡检②)
```

## 六、一个意外发现（对机制是好事，对我是打脸）

B 臂根卡在 phase2 现状块里写：

> 4) 已核实（回写事件，本轮现场复现）：21:40 根卡将 card_003/card_004 现状改写为可核事实版，
> 21:41 复核发现两卡已被改回原自述文本；两卡影子卡 `updated_at` 仍为创建时点

**那"改回原自述文本"是我的驱动器干的**——我在 21:40:45 为制造局面变化，PATCH 了 W2/W3 的现状块。
根卡把我这次外部注入**识别成一次"卡面回写/篡改事件"并写进现状**。

两方面都要记：
- **机制侧是好事**：根卡会在两次回合之间主动复核"我改过的东西还在不在"，并能从现状文本差异里发现外部改动。
- **我的实验有缺陷**：阶段二的注入与根卡的编辑撞车，污染了 B 臂 phase2 的现场（它把"局面变化"读成"被篡改"）。
  因此 phase2 的"未调整"结论**有一个替代解释**：它以为现场被干扰、优先怀疑数据而不是调整组织。
  ⇒ 这个缺陷不推翻 A/B 臂的主结论（零干预不组阁、问一次即组阁、角色质量高、角色真跑），
  但**"中途调整能力缺失"这一条需要一次干净重跑才能定论**（改法：阶段二换一个全新的 work 复现同一局面变化，
  或用 `update_status` 之外的通道注入，避免与根卡自己的编辑混淆）。

## 八、两处采集缺陷（我自己的账）

1. `_models_used()` 第一版**没圈时间窗**，把同一沙箱里别的 work、别的卡在跑的实验的 prompt 日志
   一起统计进来，于是 A 臂证据里出现 `k3` / `minimax` / `deepseek-flash` 混杂——**那是假象**。
   已修为按启动时间过滤。（教训：统计口径不圈范围，就是把别人的账记到自己头上。）
2. phase1 在 **21:40:45** 取快照，而 prompt 日志最早 **21:40:56** 才落盘（**回合结束才写**，与
   dynamic_cabinet_v2 里修过的是同一类问题）⇒ B 臂证据里 `models_observed` 为 `{}`。
   已在本报告用"跑完后补取日志"的方式给出凭据；驱动器本身的采集点待改（在 phase1 前加等待窗口）。
3. **`_models_used` 第二版仍不够**：加了时间窗以后，`work_047` 那跑又混进 `deepseek-flash`——
   因为**同一时间窗内别的 work 也在跑**（card_006 的 NAS 拆分实验并行，日志落在同一个 `logs` 目录）。
   日志文件名只有 `card_id` 没有 `work_id`，所以路径/时间都归不了属。
   v3 改为 **时间窗 ＋ 材料指纹归属**（只统计 prompt 里含本次埋点指纹 ≥2 个的日志）。
   按此口径核对 work_047：本次实际使用的模型共 4 条，**全部 `deepseek-v4.1-flash-1017`**，
   与它并行那 4 条 `deepseek-flash` 全部 fp=0（属别人的 work）。
   ⚠️ 已入库的证据 JSON 里 `models_observed` 是**修改前版本**写下的（含混杂），**该字段不可引用**；
   干净自证以本节表格为准。教训：**统计口径不圈范围/不归属，就是把别人的账记到自己头上**——这坑我踩了两次。

## 十二、把「复盘点」做成机制触发：做了，验了，**结果一半成立**（2026-10-20 夜）

§5.1 的结论是「会设、不会调」。按 D07 定的口径，这件事不能只写在纪律文档里，得由机制
在局面变化时把事实摊到根卡眼前。本节记这个机制**做出来之后真机验到什么**——结论不是
"修好了"，而我按实测写。

### 12.1 做了什么

新增一个上下文区 **order 175「第二层·职能角色」**（`context_regions.render_role_cabinet_region`，
取数在 `context_assembler._load_role_cabinet`，装配链唯一 IO 处）：

- **只对项目根卡出现**（`card_id == work_card_id`，别的卡取数返回 `{}`、区不出现）——只有根卡能调阁；
- 每轮摊开阁员现状：`域｜值班｜职责书版本｜关注集合（带卡名）｜最近一次判词`；
- 再列**机械可检的局面变化**：组阁之后新增且没人在看的卡（带时间对比）、关注集合为空、
  连续 ≥3 轮 silent、已撤岗数；
- 最后一句中性问话：「要不要改档／停职／撤岗／新设，由你按局面判断；判断为不需要就继续当前工作，不必解释。」

**边界守 D02**：只给事实，不给"你应该组阁"，也不给职能清单——避免把它测成"服从测试"。
（`tests/test_role_cabinet_region.py` 8 条用例里有一条专门断言文中不出现「应该组阁/必须组阁」。）

### 12.2 注入层：成立（两次真机都验到）

根卡 `system_prompt` 里确实出现了该区（这是我写死的字符串，属结构事实，不是猜模型措辞）：

- 跑 1 `work_001`：无角色时渲染 → 「当前项目有 3 张工作卡，**没有任何角色在关注它们**」
- 跑 2 `work_002` phase2：有角色且局面已变 → 见 12.3

### 12.3 行为层：**不成立（1/2）**——这是本节最重要的一条

同一份材料、同一句 goal（B 臂）、同一个模型（`deepseek-v4.1-flash-1017` 自证），
局面变化＝新增第四张卡「支付回调接口」`card_006`：

| 判据 | 跑 1（work_001） | 跑 2（work_002） |
|---|---|---|
| 区已注入 | true | true |
| 组阁（基线，B 臂必做） | true（`interface_contract`） | true（`interface_contract`） |
| 新卡进入角色关注 | **true**（watch 扩到 `card_006`） | **false** |
| 职责书升版 | **true**（v1→v2） | false（仍 v1） |
| 调阁工具被调用 | **`role_watch_cards` + `update_role_profile`** | **零** |
| 角色本身是否在干活 | 是（判词 1） | 是（判词 3，一直在巡检） |

**决定性诊断（跑 2）**：我把它 phase2 的区原文抽出来看——触发事实**渲染得完全正确**：

```
**机械检测到的局面变化**（事实，不是建议）
- **组阁之后新增的卡、没有角色在看**：card_006「支付回调接口」
  （本卡 2026-10-20 22:51 建立，全部角色 2026-10-20 22:47 之前建立）
```

它**看到了这条明确点名的事实，仍然一次都没调**（phase2 工具面：`list_roles`×1、
`read_card`×4、`append_ruling`×3、`update_status`、`update_goal`，没有任何调阁工具）。

⇒ **修正 §5.1 的表述**：「不会调」不是"不知道有角色"，也不是"没看见变化"。
在这两次真机里分别是：
- 跑 1：**看见了就调了**；
- 跑 2：**看见了不调**。

所以机制区的作用是**必要条件，不是充分条件**。样本 n=2（1 调 1 不调），
只能说"注入成立、信号检测正确、行为不稳定"，**不能说"这个机制修好了不会调"**。

### 12.4 顺带挖出一个真 bug（这个已经修了，且有红→绿证据）

跑 1 里根卡做了**完全正确**的调阁动作（职责书 v1→v2、关注扩到新卡、调了正确工具），
但因为我的区要读 `exclusive_key` 才渲染出「域=…」，才看见档案变成了：

```
改档前 {"domain":"interface_contract","statement":"三张接口…","exclusive_key":"interface_contract"}
改档后 {"domain":"interface_contract","statement":"四张接口…"}          ← exclusive_key 被擦掉
```

根因：`role_room.update_profile` 里 `changed["jurisdiction"] = patch["jurisdiction"]` 是
**整字典覆盖**。模型只想改职责范围，自然只写 `domain`+`statement`，排他键就被静默擦掉。

**为什么是缺陷不是小事**：排他键是「一域一角色」的地基。`_domain_conflict` 有
`exclusive_key or domain` 兜底，唯一性暂时没破；但**身份标识丢了** ⇒ 区渲染出「域=?」、
根卡失去"这域归谁"的凭据，多改几次档就再也追不回来。

修法（最小合并语义）：传了键听传的；没传且 `domain` 未变（原地改档）继承旧键；
`domain` 变了（有意换域）键跟新 `domain` 走；只改 `statement` 时 `domain` 也要保留。

**红→绿证据**（`tests/test_role_domain_key.py` 4 条）：
- 撤掉修复跑 → `2 failed`：`assert '' == 'interface_contract'`、`assert '' == 'cost_budget'`
- 加回修复跑 → `4 passed`
- 真机复核：跑 2 的 `exclusive_key_kept_p2 = ["interface_contract"]`（修复前跑 1 是 `None`）

⇒ 这条结论：**「改档」这个动作会破坏排他键身份**——是机制缺陷，已修；与"会不会调"是两个独立问题。

### 12.5 顺带记：我自己第 4 次踩同一个采集坑

`region_injected` 首跑 `scanned=0`、`models` 为空——因为 prompt 日志在**回合结束后**才落盘，
而我在 `goal_state=complete` 的瞬间就取证了（实测日志比快照晚 6 秒）。
这是 `dynamic_cabinet_v2` §11.4、`appointer_judgment` §8 之后的**第 4 次**同一类问题。
这次把它抽成驱动器里的 `_settle()`：取证前**等 pending 排空 + 15s 写入窗口**，两阶段都过一遍。
修后跑 2 的两个阶段 `region_injected` 都 true、`models` 都有 4–5 条真调用。
⇒ 一般化纪律：**「目标态变了」「判词出现了」「回合结束了」三者都不等于「落盘完成了」；
凡拿"本轮结束产物"当证据，采集点必须后置到 settle 之后。**
