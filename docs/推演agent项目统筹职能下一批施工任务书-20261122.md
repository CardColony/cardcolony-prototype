## 责任卡派工与项目内留痕

外部 agent 在项目正式入口查证、纠偏和核验结果。项目内统筹按计划向事项的域责任卡发正式消息，由责任卡根据域内现状决定自行处理、交已有子卡或创建执行卡。确需建卡时，责任卡以自己的身份沿现有派工入口，在其有权管理的父卡下创建和启动。统筹发令沿用任命、版本、模式和通信权限校验，域内建卡与起轮分别按正式入口的结果和目标回合接纳认定。 [现有执行卡派生](../src/api/card_tools.py#L1999)

从同一事项能打开统筹发令、责任卡的派工决定、执行卡回报及验收结果。责任卡会话里保留收令和域内处置过程。使用现有消息、卡片来源和回执坐标，让用户能确认谁交办、谁派工、谁执行。失败也回到原事项，显示实际卡点及已发出的动作。重放时按原行动和消息核账，已创建的执行卡沿原卡续办。

**试点验收。** 在临时 work 验证责任卡接到正式消息后沿真实回合派工，并把执行回报带回原事项。重放同一条指令时，已发生的派工沿原卡继续。旁观、越权或任命过期时，该条统筹指令的收件和起轮均为零。统筹回合直接请求建开发卡应被拒绝，开发卡数量和执行回合数均不增加。历史上的 1150 保留原来源。 [联调与验收任务书](推演agent项目统筹职能联调与验收任务书-20261122.md)

## ① 发令契约与同轮改计划

**补齐一条真实指令的内容。** `coord_submit_instruction` 必须提交现有计划中的 `item_id`、开发卡、指令正文、非空验收判据 `acceptance`、可回读的证据引用。宿主校验事项属于本次任命读取的计划版本，证据属于本 work 且仍在授权范围内。把验收判据和发令身份随行动持久化。收件人可在正式 `msg_directive` 看到正文和验收判据，记录可追溯到计划卡及其任命职能。没有验收判据的历史记录如实显示缺项。普通 `direct` 调用保持现行行为。 [统筹受理](../src/api/coordination_runner.py) · [正式 direct](../src/api/card_tools.py)

**沿现有协议提交一次施工决定。** 保留原有只提交计划和只发令两种输出。新增组合形态，在现有顶层 `plan` 旁增加可选 `instruction` 对象，字段沿用 `coord_submit_instruction` 的参数。组合提交走以下顺序。

1. 宿主对新计划和指令形状做校验，指令的 `item_id` 在待保存计划内。
2. 用读入的任命和 `expected_rev` 调用现有 `save_plan`。强模型写入在同一事务内要求任命仍在任且活跃，用户暂停期间编辑的能力保持。版本冲突、暂停、撤回或任何保存失败均终止组合提交，发令受理、收件和唤醒均为零。
3. 保存成功后，宿主取 **保存回执的 `appointment.rev`** 和已保存事项，沿 `coordination_intake → coordination_deliver` 提交。目标属主仍在收件事务内复核原任命、新版本、模式、双范围和正式通信权限。模型填报的身份、版本和行动键没有授权效力。
4. 新版保存后如果用户又改版、暂停或收权，保留已经保存的版本，发令按旧令牌被拒。分别记录「计划已保存、指令尚未受理」和「指令已受理、目标尚未确认」。已受理但目标属主暂不可达时，沿现有恢复调度按原行动键核账及补投，并重查授权。并发重放、断连补投和补唤醒使用同一行动键，有收件时返回原消息号。

**沿同一权限规则发指令。** 将普通 `direct` 与统筹的权限校验、消息头及会话落信、属主唤醒落在共用原语上。普通调用保持原有参数与行为。统筹仍以目标属主同一事务提交的行动记录为权威，三项投影完成后才记落信。旁观模式的发令动作只保留拟发记录。独立回看保持只读，拒绝组合发令、问专家等动作。现有线路不足时，只有在原任务书所述授权和既有建线权限均具备时才可走正式建线入口，其他情况显示拒因。 [收件及唤醒](../src/api/coordination_runner.py) · [会话门面](../src/storage/session_facade.py)

**本段验收。** 正向从计划卡正式回合入口提交，旧版 `r` 成功保存为 `r+1`，收到的指令绑定 `r+1`，正文含原验收判据。再分别注入保存冲突、保存成功后暂停或改版、空验收判据、无通信线、旁观和独立回看，逐项查开发卡实际会话、事件、唤醒次数，确认没有新增指令效果。恢复已有收件时继续复跑上批的投影中断、取消、撤权和重复唤醒用例。

## ② 专业答复回原事项，QA 独立验收

**用一项真实的专业问题启动指定职能的一次只读回合。** 修改现有 `coord_ask_function`。请求由宿主绑定本 work、计划卡、任命、读入版本、事项、指定职能、问题、需求版本及证据引用。宿主用 `function_room.identity_for` 核实职能与职责书，保存同一问题的稳定标识。启动前校验任命仍有效、引用仍可见。重试和并发领取沿用同一问题标识，已经完成时回读原答复。只落通知的旧记录显示为未取得答复。 [职能身份](../src/api/function_room.py) · [既有差事回合](../src/api/deploy_runner.py)

- **PM** 收到待回答的问题、需求版本和来源、受影响的用户场景。答复给出原有承诺、可观察的验收例和待用户取舍的分歧。统筹本人担任 PM 时在当前回合做产品判断，向自己提问的动作由宿主拒绝。
- **CTO** 收到技术问题、它对应的承诺、代码或契约坐标。答复给出当前生产路径、建议、涉及的责任域，以及能证伪建议的验证办法。产品问题与技术问题各有自己的回执，一方失败不清除另一方结果。
- **只读** 由宿主保证。优先使用已有职能身份和会话入口，给专家一份按当前授权组装的证据材料和最小工具面。若证据已由宿主读取，可以完全不授工具。用实际出站和实际派发验证空工具集合跨 runner 仍为空，正文中的调用指令也无法触发写入。该回合的历史、事实材料及工具读取都要受范围约束。启动前和模型实际出站前复核授权，答复入账时再核对任命与版本。
- **答复落回原事项。** 保存问题号、答复职能、版本、结论及可打开的证据引用。排队、错误、无答复、过期和已答复以实际记录呈现。晚到的旧版本答案可在原记录查阅，当前事项不会被其自动覆盖或续权。答复可供统筹后续决策使用。专家无权改计划、下令或替用户改承诺。

**沿正式 QA 差事取验收结果。** 由已有权限的责任卡对明确对象派驻 QA，给出原验收条款及实际产物。统筹在原事项保存差事编号，回读 QA 的通过、失败或未验证及其原始证据。QA 失败后保留原结论，统筹可另发修正指令并请求独立复验。权限不足或派驻失败显示真实原因。普通 PM 执笔、CTO 评审和已有 QA 流程继续走原入口。 [正式派驻入口](../src/api/card_tools.py)

**本段验收（A8）。** 在同一个临时事项里证明 PM 统筹自行判定产品问题，再向实际 CTO 职能问一个实现问题。核对实际调用数、出站身份、工具清单、会话位置以及原事项读回的答复。再让真实 QA 差事返回失败，面板仍显示失败，后续另发修正可关联原 QA 记录。反例须覆盖职责书缺失、重复领取、缩权后晚答、只读回合尝试调用写入工具，以及没有派驻权限时的拒绝。

## ③ 面板与两进程验收

**用户入口仍是「项目统筹 → 计划卡 → 原事项」。** 使用现有统筹面板 API 读取专业问答、行动和 QA 回执。行动显示目标卡、验收判据、发令版本、可回读的消息号和状态。状态以事实区分 **拟发、待投、已落信、已唤醒、已取得执行证据、被拒**。开回合只证明唤醒，普通汇报只显示原文。只有可打开且经宿主关联到原行动、目标卡的执行证据，才推进到「已取得执行证据」。QA 结论单列，未验和失败清楚可见。刷新、读历史及查询回执都保持只读。 [现有面板](../static/esm/coordination.js) · [面板 API](../src/api/routes.py)

**在不同 PID 的两个 runner 上跑一遍 A5–A7。** 用临时 work 和回环测试端口，让计划卡、目标卡分别归不同属主。走实际 HTTP 转发和接收端，模型用固定输出。保存 PID、属主映射、实际用的命令及回执坐标。ASGI 同进程测试保留为自动回归。

| 用例 | 施工验收 |
| --- | --- |
| A5 并发、断连及恢复 | 两片并发提交同一行动。目标落信后切断原请求回执，用同键重放。停止并重启**测试 runner**，验证未确认的投影或唤醒能按原收件恢复，已经接纳的回合不会再次起轮。按消息号核对会话、原文账、事件各一条，再从面板打开目标执行证据。 |
| A6 暂停、撤权及换人 | 两个时点分别注入变更。收件提交前变更，目标零收件。收件已提交、唤醒尚未接纳时变更，原收件仍可读，唤醒增量为零。用新任命重放旧行动也只读回旧收件。 |
| A7 旁观、实发和越权 | 使用无父子关系的开发卡，验证旁观零收件，明确授权且有正式通信线时有实际收件及原署名。对授权范围外的目标及没有通信线的目标分别验证拒绝和零副作用。 |
| A8 界面回读 | 从计划卡浏览器入口打开原事项，找到 CTO 的只读答复、QA 失败和后续修正行动。刷新后仍能回读。只读操作的模型调用增量为零。 |
