## 一、目标

把**由 `context_assembler` 负责的 system 上下文区**从手工逐段接线，改成：

1. 每个区在一处注册，声明自己的标识、顺序、归属、渲染方式等；
2. 装配器不再为每个具体区写专门逻辑，而是遍历注册项，取出有内容的区并按顺序组合；
3. 通过配置文件全局启停区或覆盖其顺序；配置不可读时回退默认，不能阻断装配；
4. 把数据读取与文本渲染分开：集中准备 `RegionCtx`，渲染函数保持纯函数。

**本步只改变上下文装配机制，不改变各区的具体文案、内容和出现条件。**

---

## 二、改前结构（基线）

原上下文区有三类定义/实现分散：

| 位置                                        | 改前作用                                        |
| ----------------------------------------- | ------------------------------------------- |
| `context_regions.REGION_TABLE`            | 记录 order/name/channel/seats/source，但装配器不遍历它 |
| `context_assembler.build_context_regions` | 手工写每个具体区的取数、渲染及结果字典                         |
| `context_regions.render_*`                | 各区文本渲染器，已是纯函数                               |

其中 `REGION_TABLE` 声明了 9 项（0/90/100/150/155/200/300/900/999），但 `build_context_regions` 只实际装配其中由它负责的 system 区；0 由 `prompts.build_system_prompt` 引用，300/900/999 由 `message_runner` 处理。声明与实际装配分离，容易造成理解偏差。

## 三、落地结构

### 3.1 注册表

注册表放在 `src/api/context_regions.py` 的 `REGION_TABLE`。**本次没有新建方案草稿里示意的 `context_registry.py`**：实现选择沿用现有区表所在模块，避免多出第二个声明入口；渲染函数仍留在同一纯函数模块。

每个注册项包含：

| 字段        | 用途                                   |
| --------- | ------------------------------------ |
| `key`     | 稳定机器标识，供控制配置定位区                      |
| `order`   | 默认装配顺序                               |
| `name`    | 展示名/日志名                              |
| `channel` | system、messages 或 user 通道说明          |
| `seats`   | 席位声明；当前装配器不据此过滤                      |
| `owner`   | 组件归属：`assembler`、`prompt` 或 `runner` |
| `source`  | 人可读的数据来源说明                           |
| `render`  | `RegionCtx → str` 的渲染函数；空串表示无内容      |
| `count`   | prompt 日志用的条目计数                      |

现有注册项 key：

```text
instruction / card_duty / card_list / current_card / region_guide /
memory / history / tool_turn / user_message
```

### 3.2 归属边界

- `owner="assembler"`：由 `build_context_regions` 遍历渲染；当前是 `card_duty`、`card_list`、`current_card`、`region_guide`、`memory`。
- `owner="prompt"`：`instruction`（BASE_PROMPT）仍由 `prompts.build_system_prompt` 处理。
- `owner="runner"`：`history`、`tool_turn`、`user_message` 仍由 `message_runner` 处理。

**因此，本步不是把所有消息通道都统一到一个遍历器。**&#x6CE8;册表提供统一描述；实际执行仍由 owner 模块负责。messages/user 通道的控制化不在本步范围。

### 3.3 `RegionCtx`

`context_regions.RegionCtx` 集中承载装配所需数据：

```text
work_id / card_id
cards / work_card_id / cur / cur_meta
project_class / type_registry
memory_state / memory_entries
```

`context_assembler.build_ctx(...)` 负责读取、拼成 context；渲染器只使用传入数据，不自行读取数据库、文件或配置。

### 3.4 装配流程

`build_context_regions(work_id, current_id, memory_state=None)`：

1. 调 `build_ctx` 准备数据；
2. 读取控制面配置；
3. 遍历注册表，只处理 `owner="assembler"` 的区；
4. 若配置将区设为 `enabled=false`，跳过；若有整数 `order` 覆盖，则使用覆盖顺序；
5. 调该区 `render(ctx)`；空串就跳过；
6. 生成原有输出契约（`order/name/channel/seats/text/entries`）；
7. 最后按实际 order 排序。

装配器本身不再出现对 `render_card_list_region`、`render_memory_region` 等具体 renderer 的逐项调用。

### 3.5 控制面

配置文件：`config/context_regions.json`。

目前它对五个 assembler 区提供全局开关/顺序：

```text
card_duty / card_list / current_card / region_guide / memory
```

配置未列某区、文件不存在、JSON 损坏或 `regions` 结构异常时，回退到注册表默认。当前仅支持**全局**；按卡/按类型的覆盖尚未实现。

控制面路径由 `context_assembler._control_path()` 在调用时派生，不另设模块级路径常量。

### 3.6 日志也走注册表（2026-10-15 补做）

首轮实现后复核发现：`build_log_regions` 在 `context_regions` 内部**另行硬编码**了  
`0/300/900/999` 四个区的 order／名称／通道／席位——注册表并非字面意义上的唯一声明处。  
后果是静默的：改 `REGION_TABLE` 里 `history` 的 order 或名称，只改上下文、不改日志，  
审计凭据与实际装配分叉且无人察觉。

已改为按 key 反查注册表（`_spec_by_key` → `instruction`/`history`/`tool_turn`/  
`user_message`），system 区沿用装配器从注册表带出的元数据（其 order 是控制面覆盖后的  
**生效值**，非默认值）。条目形状七键不变，`test_t11_regions`／`test_t11_tool_fold`  
钉着的顺序口径 `[0,90,100,150,155,300,900,999]` 不变；因 order 来源改为注册表，  
收尾按 order 升序排一次（sort 稳定，同 order 保持原位置序）。注册项缺失时**降级保  
审计**（`name` 标 `[未注册:key]`、order=-1），不抛异常、不丢条目。

### 8.1 接管口径

| 概念             | 含义                                                                                                                          |
| -------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `owner`        | **运行 owner 恒为 `context`（唯一底座）**。注册表里不再有第二个运行 owner。                                                                         |
| `source_owner` | 原先产出该区的代码路径（`assembler`／`prompt`／`runner`／`current_turn/message_runner`／`simple_service/message_runner`）——**仅审计用，不再拥有装配权**。 |
| `delivery`     | 底座把该区放进模型请求的哪个槽：`system` / `prior` / `user` / `once` / `tail`。                                                              |
| `profiles`     | 哪些模型调用消费它：`main` / `viewpoint` / `draft`。                                                                                   |

### 8.3 新增底座函数

- `project_history_messages(blocks, mark, allowed_roles)`：对话历史的**统一投影**（凝练水位切片 → 滤 `behavior` 留痕块 → 卡间块换头 → 保留 `reasoning_content`）。会话文件本身不改。
- `render_registered_regions(ctx, profile, deliveries, source_owner=None)`：**唯一执行入口**，按注册表与控制面渲染任意槽位的区。
- `compose_model_context(ctx, profile, ...)`：一次性组合出 `{system_prompt, neutral_context, system_regions, prior_messages, user_prompt, turn_once, turn_tail}`，**顺序仍按 gateway 契约**：system → prior → user → once → tail。

### 8.5 自查发现并修掉的实质缺陷

**round≥2 历史会发两遍**：`ToolTurnSlot.wire_messages()` 返回的是**整条 prior**（历史＋本轮工具轮）。若 `history` 区同时渲染，请求里历史出现两次。

实测：round1 prior＝`[H1,H2]`；round2 prior＝`[H1,H2,T1,TR]`（条数与 wire 一致）✓。
