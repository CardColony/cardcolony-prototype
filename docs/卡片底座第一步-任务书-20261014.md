## 〇、目标（一句话）

底座补上"沿关系"两个方向：**读**（A 沿通信线读 B 的正文/影子/对话）＋**写**（A 发消息，消息进 B 模型视野，B 读到并回复）。共用同一套关系机制、同一权限关口、同一留痕账本。**存量数据零迁移。**

## 一、任务清单（按序执行，每步完成即验收，不跳步）

### T1 新增两个能力码（权限基础）

- `src/permissions/policy.py`：`SWITCHES` 加两个常量——`SWITCH_READ_LINKED = "read_linked"`（沿连线读）、`SWITCH_SEND_MESSAGE = "send_card_message"`（沿关系发消息）；两个都进 `SWITCHES` 集合。
- `config/permissions.json`：`version` 3，给相应类型配 `read_linked`、`send_card_message`（与 `read` 分开——沿连线读比直接读更敏感，独立授权）。
- 按裁定 6 纪律：加开关＝代码加常量＋配置用起来；配置里未配的组合默认关门（空列表＝全拒，现状语义不变）。

### T2 read_via 沿连线读

- 新函数（落 `src/api/card_tools.py` 或新模块）：`read_via(source_id, target_id, part)`。
  - 沿边寻址：校验 `source` 的 `relations` 里存在指向 `target` 的边；不存在 → 返回「无通信线」。
  - `part ∈ {正文, 影子, 对话}`：正文→复用 `card_store.read_card`（三块）；影子→复用 `shadow_store.read_shadow_raw`；对话→复用 `event_log.timeline`。**不重做读工具，只加"沿边寻址"这一步。**
- 权限：调前走 `policy.check(..., SWITCH_READ_LINKED, ...)`（在 handler 层判，与现状 read_card 分层一致）。
- 模型工具面：注册新工具 `read_linked`（ToolDef，readonly=True），描述写清"沿通信线读对方卡"；`TOOL_TABLE_VERSION` 递增。

### T3 待处理收件箱存储

- `src/storage/card_db.py` 新增表 `inbox`：
  - `msg_id TEXT PRIMARY KEY`、`work_id`、`target_card_id`（收件卡）、`from_card`（发件卡）、`type`（msg_*）、`content`、`reply_to`、`status`（`pending`/`consumed`）、`seq`、`created_at`、`consumed_at`。
- 新增读写原语：`append_inbox`（投递，status=pending）、`list_pending(target)`（列待处理）、`mark_consumed(msg_id)`（置 consumed）。
- 纯新增，不接线时零影响。

### T4 通信闭环改造（发信→收件箱，调起读收件箱）

- **发信落点改**：`_h_send_card_message` 里，落信从 `session_facade.append`（塞对话块）改为 `inbox.append`（进收件箱，status=pending）。六道门槛、权限、`event_stream.emit` 通知帧**全部保留**。事件流留痕照旧（`_emit_block_event` 或等价处仍写 msg_* 事件）。
- **调起数据源改**：`schedule_card_message_triggers` 里，pending 判定从 `find_pending`（从对话块扫）改为 `inbox.list_pending`（读收件箱）。激励文照旧（带发件卡名＋类型中文名＋应对说明）。
- **回复后移出**：B 回合收口时，本轮已处理的 msg_id 调 `inbox.mark_consumed`（status → consumed）。移出 = 状态置位，不删行（留痕可回溯）。
- **对话块干净**：新消息不再写进对话块；B 自己的回复仍走 `session_facade.append`（assistant 块）——对话块只放 B 自己的话。

### T5 存量数据处置（零迁移）

- **953 条历史消息不动**（2 个 session 文件，均为 card_002 的 msg_ask）——保留在历史对话块里作既成事实；新机制只管未来消息。
- 历史 pending 尾巴：若 `find_pending` 仍报 pending（旧逻辑最后一次兜底），登记即可，不强制迁移。

## 三、约束（违反即返工）

1. **底座给能力，不判资格**：read_via/发信的函数体只做机制（寻址/投递/读），权限判断只在 handler 层，资格归权限管。
2. **只定机制不定形态**：不规定"卡该有哪几块/影子该有哪几节/消息该有哪几型"；part 是开放取值，映射到现成读工具。
3. **零迁移**：存量 953 条消息、现有读路径、现有权限表语义，一律不动。
4. **复用不重做**：读卡工具、发信六道门槛、收信调起机理、事件流留痕——只改数据源/落点，不重写。
5. **两种线并存**：parent（上下级线）与 relations（通信线）不统一；read_via/发信只沿 relations（通信线），不碰 parent。
6. **版本化纪律**：TOOL_TABLE_VERSION、permissions version 逐条递增；prompt 日志照常全量。
7. **上下文自由**：底座只提供"待处理消息"这个可组合素材（激励文数据源），不进 context_regions 内部规定区序。
