## 〇 这份方案要解决的问题

【用户】要的不是一个功能，是**一次实验**：

> 「这套系统如果完全交给模型处理，很可能会有意想不到的效果。先完全放权给模型（但在沙箱里），
> 然后测试复杂任务，看效果，看它是否会犯错，是否会越权，再根据现实情况，收窄权限。」

【用户】实验的第一步是让**一张卡（及其子树）能完全自主把任务做完**——这就是「自动模式」。

【用户】当前唯一的机制缺口：

> 「唯一的问题，是机制如何确保模型不停下来。」参考 dsh 的 goal 模式。

---

## 一、目标与非目标

### 目标

1.【用户】一张卡开「自动模式」后**完全自主运作**，用全部工具把布置的任务做完，**不需要人一条条喂**。
2.【用户】它建的子卡**自动继承**自动模式（递归往下），同样自主干活。
3.【用户】权限**字面全开**——模型可操作所有功能。
4.【用户】能**手动停止**。
5.【用户】不设闸；兜底＝**沙箱/纯净分支** + 人工停止。
6.【用户】预期用途之一：**让纯净分支用它自己测试自己、自己找问题**（自举）。

### 非目标（本来可做、明确不做）

1.【用户】**不设任何闸**——不设轮次上限、不设墙钟、不设 token 上限（拆闸铁律）。
2.【起草】本次**不做权限收窄**——收窄是实验出结果之后的事；本次只做「全开」。
3.【起草】本次**不实现 dsh 的完整授权体系**（人类授权证明、blocked 阈值、暂停/恢复权限分级等）——
   那是产品化阶段的事，沙箱实验阶段不需要。
4.【起草】本次**不做画布呈现**（只做最小可见性 + 停止按钮）。

## 二、设计

### 2.1 自动模式＝三件东西

【起草】一个**开关** + 一个**目标** + 一个**驱动器**。

| 件 | 是什么 |
|---|---|
| 开关 | 卡上一个 `auto_mode` 标记；开了 → 权限全开；它建的子卡继承 |
| 目标 | 这张卡「当前要做什么」——就是你布置给它的任务 |
| 驱动器 | 卡一轮跑完 → 目标没完成 → **自动再起一轮** |

### 2.2 轮次驱动器（核心件，借鉴 dsh goal 模式）

【业界】dsh 的做法（实读 `deepseek-harness`）：

- 层次是 **Goal → Goal Round → Turn → Step**；Goal Round 是「外层继续策略的一次迭代」，
  本身是一个完整的会话轮次，里面可以跑任意多步。
- **驱动器**：agent 空闲 + 没有排队的活 + 目标还是 `active` ⇒ **自动起下一轮**（把目标再喂给它）。
- **「停」的权威在模型**：模型必须**显式**把目标标成完成/暂停/卡住；否则驱动器一直起下一轮。
- 任何异常结果都**不自动重试**。

【起草】映射到本系统：

| dsh | 本系统 |
|---|---|
| Agent（一个会话 + 一个模型） | **一张卡**（本来就是一条独立对话 + 一个模型） |
| Goal | 卡的「目标」 |
| Goal Round（外层迭代） | **一次 `_run_message`** |
| Step（轮内步） | 轮内的工具循环（**本就不封顶**） |
| goal-round-driver | **本次要新增的件** |

【起草】驱动器规则（本次范围）：

- **触发**：卡空闲（没有在跑的回合）+ 目标仍为「进行中」。
- **动作**：自动起下一轮，把目标喂给它。
- **停止**：模型**显式声明完成**（或暂停/卡住）才停；否则一直起下一轮。

### 2.3 目标从哪来、谁改它

【起草】

- 目标存在卡上（一个独立字段）。
- **你布置任务 = 给卡一个目标**（在 auto 卡上发一条消息即点火）。
- **模型可改目标状态**：完成 / 暂停 / 卡住（三态）——这是「停」的唯一权威。
- **子卡的目标 = 父卡派给它的任务**。

### 2.4 父子怎么协作

【起草】复用现有的**卡间消息链**（A 的回合收口时自动起 B 的一轮、B 干完自动回发 A）——
【系统】该链今天已在运行（`schedule_card_message_triggers` + `_auto_reply_pending_letters`）。

- 父卡建子卡 + 给它目标 → 子卡（auto）的驱动器起跑 → 干完回报父卡 → 父卡被自动调起继续。

【系统】现状注意：**建卡本身不触发运行**（`_h_create_card` 只建卡、不发起回合）——
现有链靠「发消息」触发。

【起草】取舍：**auto 卡由「有目标 + 空闲」直接起跑，不依赖发消息**。
理由：发消息是「通信」语义，用它来「启动运行」是借道；自动模式本就要「目标驱动」。
⇒ 父卡建子卡时，把任务写成子卡的目标即可。
（备选：仍要求父卡给子卡发一条消息才起跑——改动更小，但把两套语义混在一起。）

### 2.5 手动停止

【系统】现有停止（`src/api/control.py`）是 **consume-once** 置位，只在**步边界**消费，
**只停当前这一轮**，下一轮不受影响；无在途回合时按＝no-op。

【起草】自动模式的手动停止必须同时做三件（缺一即失效）：

1. **停当前这一轮**（现有的）。
2. **关掉这张卡的「自动继续」**——否则驱动器立刻又起一轮，等于没停。
3. **级联停它的自动子卡**——否则你按了停，子卡还在后台转。

### 2.6 权限「全开」怎么落

【系统】现有权限按 `project_class → card_type` 分权，**建卡时固化在卡上**，默认关门。

【起草】自动模式**绕过**这套分权：

- 开关打开时，把该卡 `perms` 重算为**全部开关**。
- 子卡建卡时若父卡为 auto ⇒ 子卡 auto + 全开。
- **不改 `permissions.json`**——自动模式不是「按类型分权」的一种，是绕过它。
  （「全开集」作为一个常量，放在权限模块里。）

### 2.7 可见性

【起草】最小可见：卡上有自动模式标记（视觉）；「谁在跑」复用现有左栏；对话流本就实时；
停止按钮（见 2.5）。

## 七、预期效果（可判的判据）

1. 一张 auto 卡领到任务后，**无人干预下连续跑多轮**，直到自己声明完成。
2. 它建的**子卡也自动跑**，并把结果回报给它。
3. 按下停止：**循环真的停**（不再起新轮，子卡也停）。
4. 全过程**可从日志/timeline 复原**：每一步调了什么工具、有没有越权、有没有犯错
   ——这是后续「收窄」的依据。

## 附：与 dsh 的一处已知冲突（事实登记）

【业界】dsh 的目标**带轮次上限 `maxGoalRounds`**（到顶即 blocked），而本项目有**拆闸铁律**。
【用户】已明确：**先不设闸**。本方案遵此，不设任何上限。
（登记此事仅说明：dsh 这条上限的存在，意味着「无上限的自主循环」在成熟实现里是刻意不做的——
风险由用户自行权衡，本方案不代为设闸。）
