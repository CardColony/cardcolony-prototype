## 〇、一句话

**一切机制围绕三原语——卡片+连线、卡面权威信息、通信——不造第四种机制;
职能从「根卡自由组建」改为「目录预设」,总裁(根卡兼职能卡)统筹决策,
子卡只汇报;引导块的笔在总裁手里。**

## 一、用户裁定记录(对话原文口径,施工时不得偏离)

1. **不能把任务情况写进 base prompt**(会变成非通用 agent);对接口出问题——
   它是纯思考窗口、自动模式下的最终决策点,却「总是急于执行」「被项目进度绑架」;
   合格的对接口应「拆解问题→向我确认关键信息→同步到卡面成为唯一核心权威」。
2. **职能是被动的判断机,被系统实际状况牵着走;职能应是引导者,是控制系统走向的存在。**
3. **通信必须分级控制,要做机制层的控制。**
4. (方案否决记录)逐卡审批闸被否——「你这么搞会搞死系统的」「产品经理的工作
   不是什么能开工什么能扩建,人类的产品经理不是这么工作的」。
5. **整个系统所有机制围绕:卡片+连线、卡面权威信息、通信,三个手段足够掌控局面;
   若职能卡能掌控局面,子卡的发信权甚至可以摘走,它只有汇报权。**
6. 汇报不是父卡路由——「父卡一定会回答,因为模型眼中没有答不了的问题」;
   **汇报同时出现在父卡与关联职能卡眼中,信息多方汇聚**。
7. **卡面是全局权威事实源;卡面编辑权现在在卡自己手里可能不对,应在职能卡手里;
   卡面的权威事实就是引导卡片往正确方向执行的引导;卡面信息应常驻卡片自己的上下文,
   不应该需要 read。卡片和连线给了职能卡操作和管理的管道;通信是它管理的手段。**
8. **需要总裁:总裁是根卡也是职能卡,和我对接,也参与观点汇聚。汇报到达时
   所有职能发表观点,由父卡统合整理,再发回总裁;总裁根据总结做统筹式管理
   (包括卡面编辑、下达指令),然后向用户汇报(中间汇报留痕)。**
9. (施工补充令)工具面和权限面的重新梳理、上下文和提示词的重新梳理,
   必须是方案的一等公民——否则「做了也无效」「效果打折」。
10. (执行令)**执行完不要重启**;实例启停归用户。

## 二、定稿架构

### 2.1 组织与控制回路

```
用户 ⇄ 总裁(根卡·职能卡):对话/确认/裁定落面(唯一入口)
        ↑ 统合文+分歧           ↓ 指令/跨卡引导块编辑(决策簿·指令簿留痕)
     父卡(统合者):读全部观点+自身上下文→统合文(分歧如实保留)
        ↑ 观点                    ↓ 汇报广播(拓扑分发,发件人不选收件人)
     职能卡(PM/技术总监/QA/涌现守门):观点簿+专业台账,盯线观察,面变唤醒
        ↑ 汇报                    ↓ 策展引导=总裁执笔
     子卡:常驻自己的面(引导块+现状)→执行→汇报(完工/阻塞/请示)
```

### 2.2 写权阶梯(谁能在什么面上写什么)

| 角色 | 能写 | 不能写 |
|---|---|---|
| 子卡 | 自己的现状块(汇报面) | 一切引导块;无自由发信 |
| 父卡 | 自己的现状+统合记录;子树派工 | 引导块——统合上报,不落笔 |
| 职能卡 | 自己的整张面(观点簿/台账) | 别人的卡——影响力经汇聚流到总裁的笔 |
| 总裁 | 全树引导块(需求文档/裁定)、指令、对用户汇报 | 使命块(仍经用户确认) |

### 2.3 汇聚协议(汇报到达时,五步)

①广播分发(父卡+盯线职能+总裁同刻收到,收件人由连线计算);
②各职能发表观点(轻回合,落观点簿;沉默也落账);总裁亦参与;
③父卡统合(观点+自身上下文→统合文,分歧如实保留→落面+送总裁);
④总裁统筹(跨卡面编辑/指令,决策簿指令簿留痕);
⑤总裁向用户汇报(汇报簿留痕);分歧未消→总裁带上分歧问用户,裁定经总裁落面。

### 2.4 职能卡面结构(替代通用三块,台账动态拼装)

职责书/管辖/观点簿(function_verdicts)/警报簿(function_alarms)/指令簿
(function_directives)+专业台账(PM=前提台账/CTO=技术裁定簿/QA=判据验收/
涌现守门=判据登记+体检);总裁另加决策簿/汇报簿/分歧待裁(P3/P5 落地存储)。
