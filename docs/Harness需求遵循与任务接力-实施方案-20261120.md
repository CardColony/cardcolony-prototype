# Harness 需求遵循与任务接力实施方案

2026-11-20 · 试点范围为 `work_073` 的 ACC-1 · `work_027` 用于历史回放

试点次序已调整。先优化 Python 原型自动卡的目标续轮与事件等待，再启用本方案中会主动接力的策略。手动卡在已发起的任务内使用相同的依据与核证，额外续轮遵循其授权入口。[原型自动模式方案](原型自动模式-目标推进与事件续跑方案-20261120.md)

## 一、要交付什么

在现有 Harness 模块上交付三条策略。模型开始工作前收到当前有效的需求和任务边界。明确依赖得到核实后，下一步才接手。完工和验收以原始证据为准。Harness 读事实、按已批准策略决定是否干预，原责任人仍负责需求裁定、研判、实施和业务验收。普通指令、自由调研和并行准备继续按原来的入口运行。

试点选 `card_007` 给 `card_057` 的 ACC-1 正式启动取证。以 `card_049` 的 S1→S5 单段取证作为可引用的前段产物，以 `card_007` 的阶段判定作为显式交接。正式验证要用用户授权的实际需求版本和卡关系，方案中的历史编号只用于回放。两条线的由来和原始样本见复盘。[两个重构工作复盘](两个重构工作复盘与Harness策略-20261120.md)

| 使用场景 | 施工职责 | 生效条件 |
| --- | --- | --- |
| Python 原型当前 work | 用现有 Harness、派工、模型请求装配、干预台账和验收入口验证三条策略。先回放和影子评估。 | 策略按 work、显式任务启用，经用户批准后再启用正式干预。涉及 5700 的后端发布单独请示。 |
| CardColony Go 底座 | S5 消费真实 S1 事实并按批准的策略发动作。S2、Context 或验收入口各自兑现动作和记录。用同一组样本验证语义。 | 正式组合根接上真实投递及实际消费，才能判定产品侧策略生效。原型施工用的需求评审和定稿流程按各自产品口径处理。 |

## 二、先做两项基线核对

1. **防止评审等待反复续跑。** 原型现行 `review_step_not_finished` 可仅凭 `has_next=true` 续跑。`card_050` 样本同时是 `awaiting_halted`。在隔离实例复验现有代码是否仍对该组合点火，并检查 `_run_step`、`_report` 与其它续接规则。如果还能点火，保持「还有未处理项」的原有事实，另由生产者明确报告「现在有可运行的动作」。规则只对后者及确切的恢复事实点火。达到一次评审步骤后，确实有下一席可运行、票齐后需要派定稿等正常路径都要继续。忙、暂停、已否决、换批、已定稿各自验证。相关对象解除暂停或结束在途步骤时，重读原批次动态，确认仍有可运行的步骤，再续一次。用真实对应事件衔接，避免定时扫卡。旧事件在离线回放中没有足够可运行事实时只诊断。[评审生产者](../src/api/review_runner.py#L1124) · [原型规则](../config/harness_policies.json#L27) · [真实等待样本](../works/work_073/events/card_050.jsonl#L100146)
2. **核对 Go 正式投递与测试适配器的差异。** 读取时，Go 已有 `s2port.Adapter` 和公开消费取证。组合根使用的 `s2Bindings.deliver` 在解析唯一会话后仍返回 `s2_delivery_unwired`。由 S9 与 S2 负责人在目标版本复核并登记。正式跑通时，用 `start` 实际装配路径验证配置、真实目标会话和可读回的受理记录。测试适配器的通过记为组件证据。此项可以与原型策略试验并行，正式 Go 交付受该项约束。[正式组合入口](../../../CardColony/cmd/cardcolony/ops.go#L52) · [正式投递绑定](../../../CardColony/cmd/cardcolony/bindings.go#L273) · [已有投递适配器](../../../CardColony/components/s2port/adapter.go#L149)

一次 **干预事项** 对应一个需要解决的业务状态。复用原型 `intervention_store` 的事项和动作两级记录。事件重放复用既有触发身份。等待状态反复产生新事件时，沿用仍打开的事项，避免仅靠事件身份去重。评审续接以工作域、评审批次、稿次、待处理对象与当前可运行步骤识别。任务策略用原派工 ID、需求版本和步骤识别。实际动作再绑定目标和动作类型。恢复、重放、同卡并发均要在起动作前复查当前对象与事项状态。[原型动作台账](../src/infra/intervention_store.py#L278)

## 三、三条策略的施工契约

### 1. 开工时送入有效依据

- **触发。** 有权入口提交了带明确范围的试点任务。由派工记录提供工作域、任务 ID 或原消息 ID、责任卡、适用需求引用和验收点。需求引用用卡 ID、正本版本或存档记录 ID、条目号。任务中如有「先办什么、哪些动作暂缓」，由入口显式登记。历史普通指令只有文本时保留原有语义。
- **求值。** 查需求当前正式版本、条目和授权边界。评审中正文、工作状态、代码注释和模型转述可以作为查证线索。正式依据和冲突的裁决由原负责入口给出。需求改版后按实际受影响的条目失效旧任务依据。条目对应关系无法确认时送给负责人裁定，已明确不受影响的任务可继续。
- **干预。** 将任务目标、有效条文引用、本次允许动作、验收点和必须查看的证据注入首个相关模型请求。能直接读取的关键短条文随引用给到模型。引用长材料时保留可定位的原文入口。缺依据时展示具体缺项和决策人，并允许读取和提问。补齐依据后解除。
- **接线。** 原型的 `pending_inject` 当前按卡存字符串，装配会取走并清空。任务注入需按任务及有效版本选择，兼容现有普通注入，不能让其他回合取走。复用任务上下文的装配入口，避免额外唤醒。Go 优先沿用已有注入类型，分别验证 S2 受理、Context 装配和实际模型请求三个点。[原型注入](../src/infra/harness.py#L210) · [原型装配入口](../src/api/context_assembler.py#L520) · [Go 注入适配器](../../../CardColony/components/s2port/adapter.go#L242)

`057` 的正式启动任务可以这样呈现给模型。「按 S9-R03 在指定的正式装配中取证。记录装配摘要、启动尝试 ID、拒绝原因或业务监听。查阅所附 S5 第三段记录可定位事件链。」具体版本和启动尝试由派工记录与权威运行记录绑定。

### 2. 按明确依赖接力

- **触发。** 试点只挑一个已有动作做约束，例如「提交 ACC-1 正式验收」依赖「正式启动证据已到位」。前置写成来源、判据和权威回执引用。运行诊断、准备试验与复跑失败可以先做并如实登记。
- **求值。** 从现有业务入口读前置状态。待确认、目标不符、已驳回、依据过期、记录尚未生成，分别具名。用户暂停、换任务或取消后，旧干预停止。恢复时重读当前任务、前置及已有动作回执。
- **干预。** 提交入口核对任务、当前步骤与判据，前置缺失时显示「当前等待哪条证据、谁能补齐」，同一状态沿用一个事项。收到真实前置结果后，按原任务和版本将输入引用交给下一责任方。优先用已有 `message` 或 `continue`。只有接收入口需要表达可机械解除的等待、现有动作无法表达时，才为该入口补一种窄的等待动作。等待只关联这次提交，原权限检查和用户停止优先。
- **判定。** 请求受理到实际提交之间若发生换版、用户暂停或任务取消，动作提交处需核对绑定版本与任务状态。派发已开始、投递待确认或结果缺锚时先对账，避免同一个副作用重复发生。能证明此前未受理、且原授权仍有效时，方可由原步骤再提交。

### 3. 凭真实证据收口

- **触发。** `worker_done`、指定的阶段交付记录或授权验收入口发出核证请求。事件提供任务和交付的关联。报告正文可以说明结果及引用，验收事实由实际生产者或有权验收者发出。
- **求值。** 核对同一任务和版本下的判据、来源、对象、运行入口及原记录。正式启动以本次 `startup_attempt_id` 和装配摘要明确执行对象。S1 原事件、S5 策略批准与触发、S2 目标会话与受理记录要能沿引用对上。关联可以来自各自的权威记录，验收方按引用对照。局部通过、失败、待核实、未覆盖分别展示。
- **干预。** 给验收负责人展示一份简短对账。缺证据时只发给具备补证职责的卡。定向补查复用 `message` 或 `continue`，附原任务和缺项。收录真实投递回执时按实际目标和记录编号校验，模型自写的系统结果或工具结果壳交给已有隔离机制。正文异常可请求补读证据，写操作已派发或状态未明时只做查证。经有权入口接受后才解除事项和交接给下一步。[原型工具回执读取](../src/api/tool_receipt.py#L220) · [S1 已有原始证据](../../../CardColony/evidence/card_049/20261119/acc1-s1-consume/raw/03_acc1_tests.txt#L12)

## 四、最少新增的契约

先由施工方逐项标明现有权威记录能否提供下表字段。优先用既有派工、执行、版本和回执记录引用，缺字段才扩展生产者。第一批只覆盖一个工作域、一个任务链和一个待验收动作，可沿原任务、版本和动作台账检索。

| 需要核对的对象 | 最少需要关联的字段 | 从哪里读取 |
| --- | --- | --- |
| 谁被交付了什么 | 工作域、原派工 ID、责任卡或目标会话、步骤、授权入口 | `direct` 等派工记录、既有任务状态。模型输出的 ID 作为待查引用处理。 |
| 按哪条需求做 | 需求正本记录 ID 或版本、条目 ID、对应判据、有效状态 | 原型需求正稿与版本状态，Go 当前需求和版本史。需要裁定时读经授权入口确认的记录。 |
| 前置和结果来自哪 | 前置步骤或判据 ID、同任务和版本的证据 ID、目标与结论。正式启动另有尝试 ID、装配摘要。 | 权威任务状态、测试与启动原始输出、S1 和实际执行回执。 |
| 干预推进到哪 | 触发事实、目标、动作 ID、已受理记录、实际消费记录、解除所依赖的事实 | 现有干预事项和投递回执。消费由 Context、执行或提交入口留证，解除依据回读原事实。 |

同一份注入可能先进入队列，再被装配，最后进入实际模型请求。装配失败时保留未消费状态，以同一动作身份恢复。请求受理情况未知时保留「待核实」，同一逻辑请求重试沿用原引用。引用不再有效时停止使用，并保留过期原因。**实际消费**指作用于目标任务的请求确实采用了该输入。模型是否理解与遵循要看后续行为和交付。

业务策略以外部批准的配置交付，按 work 限定。原型同一事项只出一次面向责任方的提示。重复触发用来更新证据，达到明确阶段或确需上级裁定时才汇报。Go 首轮验证读现有 S1 记录，沿公开取流求值，调用正式 S2 或对应业务入口。动作口缺失或目标不唯一要如实返回拒绝，取证时保留第一个断点。首次投递的真实批准、受理、消费、解除四处都要有可核验的来源。

## 五、施工顺序和验收

| 批次 | 施工与交付 | 可验收的完成条件 |
| --- | --- | --- |
| **A · 回放与防重复续跑** | 以 `027/230` 和 `073/050` 为等待反例，提取原始前后事件到离线夹具。用隔离实例复验现行评审，必要时修生产者的可运行事实及续跑判据。 | 重放相同事件、持续得到新事件但状态不变、重启后同一状态，均无新增唤醒。席位确实恢复或后续机械动作就绪时，可恰好接续一次。旧事件缺字段时能看见不足。 |
| **B · 开工注入与验收核证** | 接一条明确的 ACC-1 派工和它的验收。先在影子模式记录「会附哪些依据、会报哪项缺证」，保留裁判真值。通过后启用任务定向注入和核证提示。 | 首次相关模型请求能回读准确版本和步骤。无关回合拿不到注入，失败重试沿相同逻辑任务恢复。真实工具回执与手写正文结果同时出现时，只有可回读记录能作为满足判据的证据。 |
| **C · 单节点等待与真实接力** | 在一个正式提交入口兑现等待，安排真实前置由其权威来源解除。在原型试点获批准后启用。Go 正式链用正式装配、获准策略、真实目标和存储回读独立验收。 | 前置未满足时无法完成这一个提交，诊断和其它并行任务可运行。前置补齐只续一次，暂停和换版可撤销待执行动作。交付只发生一次，结果未确认时自动重发为零。 |

下表给出必测场景和预期。历史样本用于独立回放，第一轮主动等待仍只接一个已批准的提交入口。

| 输入 | 预期输出或状态 |
| --- | --- |
| `007` 的历史首条派工允许起草和 `report_up`，暂缓写需求与开评审 | 首个模型请求含真实根稿引用及暂缓动作。回放中获准的汇报和查证照常，两个暂缓动作分别受约束。 |
| `017` 的 R7/R19 在新稿评审中，或任务运行时只有其中一条正式改版 | 在评稿留作参考。正式改版后，仅依赖该条的任务重新对齐。需求的正式状态由权威版本记录给出。 |
| 同一评审批次、同一稿次、同一组待投票席位持续 `awaiting_halted` | 一个开放等待，零自动续跑。确切席位恢复后仍属当前批次时才继续。 |
| `328` 的测试装配通过、`049` 的单段事件链通过、`884` 的正式启动失败 | 每项按对应入口、快照和判据留证。模块证据保留，正式验收仍显示本次运行的明确断点。 |
| 假回执、收件人错、真实编号缺失、同动作已写入待受理 | 可分别定位缺失或目标不符。待受理使用原记录对账。零重复自动写入。 |
| 卡内并行派来另一件任务、两个执行者同时处理一个前置完成、暂停后重新开工 | 注入只向匹配任务送达。相同业务步最多一次真实交接。恢复时发现已作用的记录可继续核证。 |
| 普通研判、公用只读指令、未参加试点的 work | 无新增强制提示、等待或唤醒。 |

试点要回答「模型做事有没有改善」。同一任务形态、需求版本、模型路由下，用历史回放和试点样本分别记录有效依据绑定数、顺序漏步数、验收结论可回读数，以及重复唤醒、误拦截和人工纠正次数。回放衡量规则是否命中。使用中的实际样本衡量模型有没有按步骤做、能否补齐证据。样本不足时报告分母与反例，继续观测。

## 六、交付和启用

施工方交付入口与事件字段对照、策略配置及其批准记录、隔离回放和真实链路证据、影子对照及误拦截清单。每个结论写清代码或装配快照、实际运行入口、原始证据位置及仍缺的能力。正式 Go 证据需要从同一次 `start` 关联到实际批准的策略、S1 真实提交、S5 触发和目标会话的受理。验证注入时再回读实际模型请求。绑定未接通时登记独立阻塞和负责人。

第一轮交付到影子评估。上线批准后，先启用任务定向注入和验收提示，再启用单节点等待。撤回时关闭试点策略，取消尚未受理的待办，保留既有事实和回执供对账，对已经派发的动作沿原入口核查。原型涉及 5700 的后端发布按项目规则另请示。[项目规则](../AGENTS.md)
