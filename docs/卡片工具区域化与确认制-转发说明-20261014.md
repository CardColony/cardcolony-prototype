## 一、这次改了什么（一句话）

五个卡片工具随「内容分区域」（正卡正文三块、影子四节，SQLite 各占一列）完成形态迭代：**读按需取、写按节改、建删卡要用户确认**。版本 `TOOL_TABLE_VERSION → tools-tc-6`、`BASE_PROMPT_VERSION → t20-1`。

## 二、区域背景（不懂这个就不懂改造）

- **正卡＝三块**（cards 表三列）：`mission`（使命，要做什么做成什么，仅用户可改）／`status_block`（现状，当前确定的状态与结论）／`rulings`（第三块——对外名随树类：rd_project→「需求文档」、其余→「定论」）。另有 `card_history` 修改历史表（系统自动流水账，工具不给）。
- **「职责与边界」duty 已取消**（用户 2026-10-14 17:56 裁定：边界靠权限，不靠文字描述；列已 DROP）。**任何地方不要再出现 duty。**
- **影子＝四节**（shadows 表四列，节序固定）：`progress`（进度）／`coordination`（待协作事项）／`artifacts`（产物清单——含系统自动回传的产物指针）／`iterations`（迭代历史）。
- 影子是**本卡私有**的过程记录；正卡三块才是跨卡可读的对外内容。

## 三、五件工具改造后的确切行为

### 1. `read_card(card_id, region?)` —— 两态读

- **缺省**（不带 region）：返回 `card_id / title / parent / relations` ＋ `regions` 清单（**三项**，每项 `{region, name, desc, chars}`）。
- **带 region**（enum：`mission | status | third`）：只返回 `{card_id, region, name, content}`。
- `third` 的 name 按目标树类型外露（研发树＝需求文档，其余＝定论）。
- 非法值（含 `duty`）→ `validation`。修改历史**不给**。返回体旧的 `body`/`使命`/`现状`/第三块名多键并存形态**已退役**。
- 权限不变：`SWITCH_READ` 关口，跨卡可读。

### 2. `read_shadow(section?)` —— 两态读 + 只读本卡

- **schema 已删 `card_id` 参数**——只能读**当前卡自己的**影子（旧「上级查子卡影子」通道已关闭，跨卡协作走 coordination 节 + 卡间消息）。
- 缺省：返回 `sections` 清单（**四项**，每项 `{section, name, desc, chars}`）。
- 带 section（enum：`progress | coordination | artifacts | iterations`）：只返回该节内容。

### 3. `edit_shadow(section, content)` —— 新工具（原 update_shadow 退役改名）

- **一次只编辑一节，整节覆盖写**。section 四节枚举必填；content＝该节完整新内容。
- **先读后写契约**：需保留旧内容时先 `read_shadow(section)` 取回、拼上新内容、整节写回。
- 只能写**当前卡自己的**影子（无 card_id 参数）。
- 动机：旧 update_shadow 是整篇覆盖——模型只交一节会**清空其余三节**，产物清单里系统自动回传的指针会被误清。这是本次改造最实的一条。
- 旧名 `update_shadow` 已从注册表退役（card_tools 内留档注释一行）。

### 4. `create_card(title, parent?, content?)` —— 确认制

- description 写死两条：**「只有用户明确要求建子卡时才可调用；自主拆解任务不得建卡，改用 create_plan」**＋「调用后需用户在界面确认，确认前不建卡」。
- 流程：关口（存在性＋CREATE_CHILD＋树作用域）全过 → **不建卡**，落 pending_action → 前端弹窗 → 用户**确认**才走 card_store 原路径建卡（回执卡号形态不变）；**拒绝/关闭** → 不建；**10 分钟无操作** → 超时未执行。
- 越权调用**不产生弹窗**（关口层就拒）。

### 5. `delete_card(card_id)` —— 确认制 + 范围收紧

- 只能删**自己子树**内的卡（树作用域本来就有，description 现在写死）。根卡不可删（护栏不变）。
- 流程同 create：关口全过 → pending_action 弹窗（**弹窗显示卡标题**防误删）→ 确认才真删。带子卡的卡在确认执行时由存储层护栏拒。

## 四、pending_action 确认机制（新增基础设施）

- 新模块 `src/api/pending_action.py`：进程内表（uuid 前 8 位 id）＋ `asyncio.Event` 挂起＋ **600s 超时**＋ 同目标去重（同卡同动作同 payload 复用同一 pending，不重复弹窗）＋ 单次执行闸。
- 前端端点：`POST /works/{w}/cards/{c}/pending/{action_id}/confirm | reject`（action 不存在 404、已终态 409）。
- 事件流新增两类型（本体论 27→29）：`pending_action`（发起，前端据此弹窗）／`pending_resolved`（终态，data.outcome ∈ confirmed/rejected/timeout，前端关窗）。timeline/SSE 均可见——**确认全过程有留痕**。
- 前端：`#pendingModal`（复用 draftModal 样式）＋ workspace.js 单窗队列控制器；缓存戳 `?v=27→28`。
- 服务重启丢 pending＝设计内（pending 只在回合内有效）。
