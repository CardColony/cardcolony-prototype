# 任务书：当前轮注入消息事件改造

> 日期：2026-10-14  
> 性质：实现任务书；本文只定义目标、事件形态、来源、时序、验收，不在本文写代码。  
> 目标读者：负责卡片消息事件与当前轮消息组装的实现 Agent。  
> 需求依据：用户 2026-10-13/14 本轮对话直接提出的「当前轮」与 160/165 区拆分要求。本文不把旧文档里关于“不引入当前轮”的历史表述当作当前需求；本任务以本轮用户要求为准。

---

## 一、目标

把工具卡步骤信息（现 160 区）和思维链步骤信息（现 165 区）从常驻 system 文本改造成**消息事件形式的注入信息**，并将一轮模型交互组织为明确的【当前轮】消息序列。

本任务要表达两种注入消息：

1. **固定总领消息**：说明当前流程及后续步骤信息的通用含义；位于当前用户发言之后。
2. **动态步骤注入消息**：携带当前工具卡步骤或思维链步骤信息；在对应步骤开始处注入。后续调用、工具返回等事件按实际时序追加在它后面；步骤变化时在新步骤位置注入新消息。

这两类信息都作为一次性的消息事件进入当前轮序列；**不得在每次模型调用时将其重新贴到 prompt 最下方**。后续对话中它们可以作为既有历史事件存在，但不能因每次续调而复制成新的尾缀。

## 二、当前实现基线（代码实读）

### 2.1 消息事件底座（当前工作区正在形成的实现）

当前工作区可见一条未提交的消息底座改造线，包含 `src/storage/event_log.py`、`src/api/event_stream.py`、`src/storage/session_facade.py`、`src/api/routes.py` 等改动。本文按**当前工作区盘面**描述，不将其误称为已提交或已验收的基线，不覆盖、不回滚该线。

当前盘面中 `event_log` 外层记录为七键：

```json
{
  "seq": 42,
  "card_id": "card_001",
  "run_id": "<pair_id>",
  "round": 3,
  "type": "tool_call",
  "data": {},
  "model": ""
}
```

消息块已有映射：`user_message`、`assistant_text`；过程事件与思考事件也写入卡级事件流。`data` 是结构化对象。**本任务沿用既有七键外壳，不另造第二种日志格式；两种注入消息使用不同 `type`，具体字段放在 `data`。**

当前代码中 `round` 表示外层的对话轮/turn 锚，不应拿它冒充 `message_runner.state.rounds` 的模型工具续调次数。动态步骤定位应由数据中的步骤标识表达。

### 2.2 160 区来源：工具卡

现行组装点：`src/toolcard/step_prompt.py::build_instruction` / `build_region`。

- 运行态来源：`src/toolcard/driver.py::_runtimes[card_id]`，含 `script_name`、`step_id`、`round`、已登记产物。
- 本步提示词来源：`src/toolcard/script_loader.py` 按剧本名读取 `works/toolcard_scripts/{script}.json`，用当前 `step_id` 找步骤，再按 `prompt_ref` 读取 `works/toolcard_scripts/prompts/*.txt` 原文。
- 上一步产物来源：`src/toolcard/artifact_store.py::manifest_entries(card_id)`；当前构造器只列出已登记、且登记步骤不同于当前步骤的文件名，不检查文件内容或质量。
- **重要现状**：`build_instruction` 当前把剧本名、当前步、本步提示词、可选产物文件名拼成一段；代码里没有单独定义的“160 固定总领正文”。实现时不得虚构其现存来源。固定消息可携带运行内稳定的剧本来源信息；若需要新增通用指导正文，先从用户/已有正式说明取得定稿，不得由实现 Agent 自行编写并当作既定需求。

### 2.3 165 区来源：思维链

现行组装点：`src/thinkchain/step_region.py::build_region`。

- 数据来源：`src/thinkchain/board.py::snapshot_sync(work_id, card_id)` 的计划板快照，盘上位置为 `works/{work_id}/plans/plan_{card_id}.json`。
- 快照中计划级信息：计划名、步骤数组、当前步骤指针。
- 当前步骤动态信息：步骤 `id`、`prompt`、`criteria`、`deliverable`、类型等字段。
- 前序成果动态信息：状态为 `done` 的步骤及其 `prompt`、`result`；现行 165 渲染的 `result` 最多显示 800 字符。
- 固定执行纪律来源：`board.STEP_BRIEF_TEMPLATE`；`board.step_brief(step)` 将 `prompt/criteria/deliverable` 填入模板。固定模板文字与当前步字段必须可分辨，不得把完整模板每次重复伪装成新的动态事实。
- 无活板、快照不可读或没有当前步骤时，现行行为是 165 区不出现；消息化后须维持同等的“无来源不发注入事件”语义。

### 2.4 当前组装路径

`context_assembler.build_context_regions` 目前在 150 区之后生成 160；仅当 160 有内容时不生成 165，否则尝试生成 165。随后可生成 200 记忆区。`message_runner.build_context` 将 system 区合成 `system_prompt` / `vp_system_prompt`；gateway 再把 system、历史、当前 user prompt 组成模型请求。此路径说明：要实现“用户消息后插入注入消息、后续调用按时序继续”的消息序列，不能只改区域排序；任务必须核对当前调用边界如何承载有序消息事件。

## 三、两种注入消息形态

建议沿用 event log 七键记录外壳，增加以下两种事件类型。名称是本任务书给实现的建议名；若事件底座 owner 已有命名约定，可在施工前对照统一，但语义与顺序不得改变。

### 3.1 固定总领消息：`context_preamble`

**语义**：当前流程/步骤信息的稳定说明；在本轮用户消息之后出现一次。固定是指在该流程运行的有效范围内不随工具续调或步骤数据刷新而改写。

**来源与内容**：
- 思维链执行纪律：取自 `board.STEP_BRIEF_TEMPLATE` 中不含占位变量的通用部分。
- 工具卡：运行级元数据可来自 `driver` 当前 runtime（如 `script_name`）；当前实现没有单独的固定总领正文。不得把动态 `prompt_ref` 内容误标成固定内容，也不得临时编造新指令。确需新增统一工具卡总领时，先提交文案供需求方确认，再实现。

**建议记录形态（data 是结构化对象；字段名为任务书建议，施工前需与 event_log 实际接口对齐）：**

```json
{
  "type": "context_preamble",
  "data": {
    "source_kind": "thinkchain",
    "source_ref": "board.STEP_BRIEF_TEMPLATE",
    "run_context": {"plan_name": "导出功能"},
    "content": "……固定总领正文……"
  }
}
```

`source_kind` 至少可区分 `toolcard` / `thinkchain`；如没有可用固定正文，不能发空壳事件，也不能复制动态内容冒充固定总领。

### 3.2 动态步骤注入消息：`context_injection`

**语义**：在执行流程进入某一步时，注入该步当前有效的信息。每个步骤/状态版本在对应位置出现一次；工具调用、工具结果等之后发生的消息继续追加在它之后。步骤前进后，新步骤信息在新步骤位置产生，不回头覆盖或重贴旧事件。

**工具卡 `source_kind="toolcard"` 的结构化数据来源：**

```json
{
  "type": "context_injection",
  "data": {
    "source_kind": "toolcard",
    "source_ref": {"script_name": "方案链", "step_id": "p2"},
    "step_id": "p2",
    "content": {
      "prompt": "……该步骤提示词原文……",
      "artifacts": ["01-p1-任务书读取-01.md"]
    }
  }
}
```

字段来源分别为 driver runtime、剧本 JSON 的当前 step 与其 prompt 文件、artifact manifest 登记。原文照取；产物仍只报代码登记的文件名，不读取内容、不评价。

**思维链 `source_kind="thinkchain"` 的结构化数据来源：**

```json
{
  "type": "context_injection",
  "data": {
    "source_kind": "thinkchain",
    "source_ref": {"plan_name": "导出功能", "step_id": "S2"},
    "plan_name": "导出功能",
    "step_id": "S2",
    "index": 2,
    "total": 4,
    "completed_steps": [
      {"step_id": "S1", "prompt": "……", "result": "……"}
    ],
    "current_step": {
      "prompt": "……",
      "criteria": "……",
      "deliverable": "……",
      "type": "execute"
    }
  }
}
```

字段均由 `board.snapshot_sync` 快照读取；完成步结果的长度/原文口径沿用现状，除非另获明确需求，不在本任务自行改写。

## 四、【当前轮】的消息顺序

【当前轮】是按消息事件时间顺序组成的当前 run 视图，不是常驻在 prompt 末尾的文本区，也不是每次调用重建后把注入信息搬到最后。

```text
user_message（本轮用户原话）
context_preamble（固定总领；有适用来源时）
context_injection（当前步骤；有有效步骤时）
judgment / plan_created / round_start 等实际发生的事件
tool_call
tool_result
……
step_advanced（步骤确实推进时）
context_injection（下一步骤信息；只在进入下一步时）
tool_call
tool_result
……
assistant_text（最终回复）
```

顺序要求：

1. 本轮 `user_message` 是当前轮第一条消息事件。
2. 固定总领消息若存在，紧随用户消息之后；缺来源则跳过，不造空事件。
3. 当前步骤消息在其步骤开始时插入；第一步紧跟固定总领/用户消息，后续步骤在上一步推进事件之后、该步第一次执行动作之前。
4. 后续调用不得复制这些消息到 prompt 尾部。网关输入投影必须能保留当前轮事件的原始先后顺序，工具调用与工具返回的配对结构不变。
5. 当前轮视图按当前 `run_id`（现 pair_id）取本轮消息事件；对话 `round` 锚与工具续调次数不是同一概念，不得混用。
6. 160/165 沿用现行运行态来源选择；无活跃工具卡且无有效计划时，不产生相应注入事件。两者是否可同一轮并存不在本轮需求中，默认不改变现行互斥选择。

## 五、接口与范围边界

### 要做

- 为固定总领与动态步骤注入定义两个可辨别的消息事件类型，载荷结构化并保留来源引用。
- 将 160/165 的稳定说明与动态步骤数据分离；动态数据由现有权威数据源生成，不复制一份独立状态。
- 在当前轮消息序列正确的时间点插入事件，并让当前轮后续模型调用按原顺序消费这些事件。
- 更新事件日志类型登记/校验（若实现中存在）、timeline 展示/前端渲染和恢复读取，使两种注入消息能被区分、定位来源、按时间顺序显示。
- 为当前工作区已有的 `event_log` 七键记录外壳和未提交消息底座改动提供兼容扩展；先审阅该工作树，不覆盖、重置或整文件回滚其他未提交改动。

### 不做

- 不改 200 区凝练记忆语义、`mark` 水位、300 区历史范围、归拢算法或工具轮折叠规则。
- 不修改用户原话，不把注入事件伪装成用户发言或助手最终回复。
- 不把固定总领/动态注入再次永久拼在 `system_prompt` 末尾。
- 不凭空补写 160 区通用指令文案；若现有源中没有对应固定内容，列为阻塞项交需求方确认。
- 不改 `works/{work}/sessions/*.md` 的既有对话块契约，除非事件底座当前实现明确要求；该项需先报范围和影响，不在本任务书内默许迁移。
- 不改 gateway 配置或供应商适配；若现有调用接口无法表达“用户消息之后插入注入消息、后续正常追加”的次序，先提交消息投影方案及兼容性证据，不能擅自绕过既有禁改边界。

## 六、任务分解

### 任务 1：冻结现状与事件接口

- 对齐当前未提交消息底座的真实记录结构、事件类型定义、timeline 渲染投影、gateway 消息组装方式。
- 给出一次实际链路的序列图，标明用户消息、固定总领、步骤注入、工具调用/返回、步骤推进和最终回复的生产点。
- 列出可复用数据源与160固定总领文案是否有现存来源；无来源必须报告，不得补写。

**交付**：接口对齐清单 + 事件来源表；不改动其他未提交文件。

### 任务 2：定义两类注入事件载荷

- 定义 `context_preamble` 与 `context_injection` 的最终 type/name 和 data schema。
- schema 必须保留来源类型、来源标识、步骤标识和结构化内容；避免只存无法回溯的长文本 blob。
- 对事件向模型消息的投影定义合法 role/表示方式。不得让自定义事件 type 作为不受支持的模型 role 泄漏到供应商接口；须用配置模型兼容测试验证。

**交付**：schema 表、投影规则、一个工具卡样例和一个思维链样例。

### 任务 3：接入固定总领消息

- 用户消息事件成功落定后，在当前轮序列紧邻位置追加固定总领事件（如有）。
- 固定内容每轮/每 run 的生命周期依需求定义；在同一轮模型续调时不重新追加。
- 思维链固定纪律应从 `STEP_BRIEF_TEMPLATE` 的固定部分拆出，不复制维护第二份文本。
- 工具卡固定总领若无现成内容源，阻塞等待文案确认；不得以临时文案代替。

### 任务 4：接入动态步骤注入

- 工具卡：从 `driver`、`script_loader`、`artifact_store` 当前源读取动态字段；步骤 prompt 原文照取。
- 思维链：从 `board.snapshot_sync` 读取当前步及既有完成步数据；固定纪律不随动态事件重复传。
- 进入当前步骤时只追加一次；若步骤推进，按步骤身份/板版本区分下一条；同一步同版本的模型工具续调不重复追加。
- 没有活跃步骤/来源缺失时不发对应事件。事件是否失败的处理沿用消息底座的 fail-open 约定，不得影响用户发言及模型主链路。

### 任务 5：当前轮视图与模型输入投影

- 当前轮按 run_id 建立有序消息视图；用户消息是首条，随后固定总领、当前步骤消息、正常过程事件按发生顺序排列。
- 明确 `event_log` timeline 事件到模型 `messages` 的投影边界：哪些事件是模型可见消息，哪些只是 UI/审计事件。不能把 tool_call/tool_result 的事件记录直接误当成可发送消息；工具协议配对仍走现有轮槽。
- 每次模型续调沿用当前轮已经发生的注入事件，不重新移至消息尾。新的动态步骤只在对应步骤转换点追加。
- 在无需注入、直答、工具卡执行、思维链执行四种场景分别验证序列。

### 任务 6：回归与交付

- 离线测试覆盖时序、去重、来源字段、逐字原文、消息角色投影、步骤转换、多轮工具续调。
- 真实端到端或模型兼容性测试仅在实现环境具备授权与可运行条件时执行；不得将 mock 测试描述为实弹验收。
- 全程保护工作区中既有并行修改；不得整文件 checkout/reset，不得改动与本任务无关的未提交内容。
- 完成后报告变更文件、测试结果、未覆盖项、是否需要重启；不自行提交、不部署。

## 八、实施前阻塞项 / 必须在方案确认时显式处理

1. **160 固定总领正文来源缺失**：现有 `step_prompt.build_instruction` 是剧本名/步号/提示词/产物名拼装，没有独立固定总领正文。不得直接创作。可先只定义 `toolcard` 的固定来源元数据；若确需固定正文，需求方确认内容后再施工。
2. **模型消息角色与有序注入接口**：`model_gateway` 当前以 system + prior_messages + user_prompt 的接口构造消息；而新需求要求用户消息后还可插入注入消息，不能假定将事件塞入 `user_prompt` 或用非法 role 就能满足。实现前需给出有序消息投影办法及 endpoint/model 兼容证据。现有代码/文档对 `gateway.py` 有禁改边界，若方案认为必须改，先单独呈报变更范围与理由，不在本任务书中默许。
3. **动态注入的幂等键**：至少区分当前 run、来源类型、步骤标识，以及同一内容是否因板修订而变化；具体 key 算法由实现方案写明并测试，不能只靠“当前轮最后一条”判断是否重复。
4. **两种运行源同一轮并存**：当前装配选择逻辑是 160 有内容时不调用 165。本任务书默认保留该选择；如消息事件底座允许同一 run 同时存在工具卡与思维链来源，须先提供真实场景与冲突处置方案再扩范围。

## 九、红线

- 这是当前轮消息/上下文注入的任务；不把“记忆区正常进入上下文”重新定义成问题。
- “区移到尾部”不是本任务的等价实现。验收对象是**当前轮有序消息事件序列**。
- 注入消息必须有来源和结构，不把区渲染成不可追溯的长文本后丢掉字段。
- 不猜测、不评价模型生成的步骤成果；代码只搬运来源数据与插入时序。
- 不把一条高频事件拆成无必要的重复注入；续调期间保持既有事件位置。
- 先解决数据源、时序、投影，再动实现；需求没裁定的固定总领文案和角色映射不得由施工方代拍。
