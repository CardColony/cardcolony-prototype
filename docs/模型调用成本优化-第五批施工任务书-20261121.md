# 模型调用成本优化 · 第五批施工任务书

**目标**　减少两种自动提醒造成的重复起轮，给同一逻辑模型跳次的所有重试和层内换座共用一次尝试预算。用户指令、真实回执、有效任务续跳和已执行动作仍按各自契约处理。按整条任务的实际模型请求和业务回执验收。 [总方案第六节](模型调用成本优化-方案与施工任务书-20261120.md#六-第五批-合并可避免的起轮与重发)

**施工顺序**　固定改前出站与业务基线 → 第一部分两种唤醒分别验收 → 第二部分重试预算 → 四组开关交叉验证。两个试点开关分别为 `COST_WAKE_COALESCE=1` 和 `COST_HOP_RETRY_BUDGET=1`，缺省沿原路径。

## 一、自动唤醒只合并同一件事

### 1. 现状连续超限期间只受理一次提醒

- 沿 `card_block_edited → policy_runner.feed → intervention_store → harness` 接入。判断字段为 `block=status_block` 与 `new_len`。登记和恢复共用现行阈值，**达到 10,000 字即超限，低于 10,000 字即恢复**。每次连续超限以该次进入超限的可信事实为锚，按工作和目标卡登记一次独立事项及动作。复用台账的业务键、唯一约束和领取租约。 [现行提醒](../config/harness_policies.json#L347) · [策略入口](../src/infra/policy_runner.py#L91) · [动作登记](../src/infra/intervention_store.py#L381)
- 首次超限登记一条提醒。后续仍超限的编辑更新同一事项的最新字数、事实锚和待投递材料，保持同一动作编号。投递领取时读取该事项的最新有效材料。动作已经进入会话或被在途回合受理后，后续编辑只更新台账事实，历史提醒原样可查。同一连续超限期的有效提醒最多一条，自动起轮也最多一次。
- 恢复阈值内时关闭该事项并使尚未受理的提醒过期。再次超限起新事项。领取后、实际注入前复核事项锚和当前现状，旧提醒从等待中回来时以此核销。按可信事件身份去重并识别晚到事实，旧事实回放不能反转现有状态。无法证明顺序时读当前卡面和台账再决定。首次启用遇到已超限卡时，以一次新编辑触发或恢复流程的可靠证据立案，启动本身不广播存量提醒。 [现状更新入口](../src/storage/card_store.py#L1492) · [事项关闭和动作领取](../src/infra/intervention_store.py#L336)
- 卡忙时沿用现有受理或插话入口，保护用户插话优先级。新合并事务或领取失败时给本事项记待核实，依现有恢复入口处理。发送已受理、结果未确认时先依动作编号和实际落信核账。同一卡间的普通指令、验收汇报和新任务保持现有即时路径。

### 2. `pseudo_call_reinvoke` 与 runner 共用一次补救决定

- 沿用 `handled=runner`、`recent` 和现有补救台账。事件补齐可回读的原回合身份和异常身份，至少关联工作、卡、会话、原 `pair_id`、原跳次和异常类别。绑定任务时记录任务号、版本或已有动作目标。新增参与判断的字段纳入事件目录并在 `feed → ingest → dispatch` 实际读回。使用宿主字段构造身份，正文片段只作排障。 [现有策略](../config/harness_policies.json#L405) · [事件契约](../config/event_catalog.json#L248) · [runner 决定](../src/api/routes.py#L4439)
- runner 和策略在调起前以同一原异常身份核对决策。已有 runner 占位、已裁定、已发送或待核实时沿已有动作销账。能证明原回合仍有有效轮槽或可恢复位置的，交给属主按原任务续接，继续使用已取得的真实工具对与宿主回执。用现有 `record_action` 与恢复对账，重复事实换事件编号、并发触发和重启重放均关联原决定。 [补救占位](../src/api/message_runner.py#L1913) · [补救恢复](../src/infra/intervention_runner.py#L728)
- 未接管的真实异常沿现有受控兜底。已收口且只剩历史存根时，先查原任务与执行记录。确认空手、任务仍有效、用户控制允许时，可按原规则受理一次提醒唤醒，并单独计为新起轮。已有写入、发信待确认或原任务换版时走核账或等待。缺原回合身份的旧事件沿事实级身份及既有节流处理，记录缺证。供方残片与模型自写结果沿现有异常分类。

## 二、模型重试按同一逻辑跳次扣账

### 1. 统一身份、额度与发送边界

- 从 `_call_model_resumable → call_main → gateway.stream_call` 接入普通主回合的首跳和工具续跳。一份预算对象贯穿网关内层重试、同层换座和循环器同位置重发。宿主身份至少包含工作、卡、会话、原 `pair_id` 与逻辑跳次。实际座、网关 trace、外层重试号和内部尝试号用于对账。工具结果带来的正常下一跳产生自己的预算。同一位置恢复应携带原身份和已用额度，缺证时给待核实回执。沿用分片属主和已有恢复入口。 [外层重发](../src/api/message_runner.py#L1095) · [同层换座](../src/model_gateway/gateway.py#L1019)
- **试点额度含首次，取首选座当前 `retry.max_attempts`，沿用配置缺省值 3。** 端点各自的尝试上限、已启用的错误分级、退避与时间限制继续生效，合并后的总额始终取更紧约束。额度至少为 2、有合规同层备选且失败允许换座时，保留最后一次尝试给下一合规座。用持续可恢复失败且无更紧约束的样本验顺序，额度 2 对应 A→B，额度 3 对应 A→A→B。现有 `retry_grading` 配置保持原值。 [重试配置读取](../src/model_gateway/gateway.py#L615)
- **一次尝试在适配器即将提交实际模型请求时扣账。** HTTP 入口以 `send_stream` 调到 `client.send` 之前为准，CLI 候选以实际进程调用边界为准。适配器完成鉴权准备、请求构造及停止／材料复核后再原子领用额度。排并发槽、构造失败、模拟帧和代理连接握手本身不算独立模型请求。进入发送调用后即记一次尝试，连不上或没有确认发送也保留该次本地尝试记录。另用现有 `on_dispatch` 确认已发送，真实终帧单独记录。一次响应模型元数据更新不重复扣账。 [传输发送证据](../src/model_gateway/llm/transport.py#L19) · [真实终帧结算](../src/api/message_runner.py#L372)
- 复用 `before_send` 保留材料守卫，并在每个真实发送边界查当前人停、授权和恢复依据。预算拒绝走可上抛的控制结果，网关内外都识别，释放并发槽并直接收口。失败后的等待既有退避照常执行，取消可打断。`record_dispatch` 是观察回调，预算闸应能在网络调用前明确拒绝。直接 `gateway.call`、三席、草稿、评审、后台凝练及独立执行体沿各自原调用入口。若同层候选有多种适配器，先验证每条候选发送路径共用预算，再将该路由纳入试点。 [发送前守卫](../src/model_gateway/gateway.py#L1321)

### 2. 根据失败事实决定下一步

从适配器到网关外层保留结构化错误类别与 `Retry-After` 等可用字段。外层以这些字段决定是否重发，出站后的拒绝、断流和调度控制均带回原跳次身份。

| 失败或控制事实 | 本跳处理 |
| --- | --- |
| 可恢复断连、超时、503 | 符合现有路由限制且有余额时，重发当前逻辑跳次或使用有资格的同层备选。沿用冻结的本跳材料，并复核是否过期。 |
| 429 等显式限流 | 能取得 `Retry-After` 时纳入既有退避决策和剩余时间。等待后复核停止和额度。缺值时沿已有退避规则。 |
| 鉴权、确定性参数错误或明确协议拒绝 | 保留来源与结构化错误码，到原回合交回需要修正的问题。同一份请求停止自动重发。模型产出的伪调用走异常续接判据。 |
| 已发可见正文或思考、半截工具片段、用户停止或插话 | 区分已发增量、真实终帧、尚未派发的候选和真实派发回执。已有有效控制入口优先。断流且无法从已证实位置续接时如实标未完，保住已产生的回执。禁止把半截输出当新模型回合重新执行已派发动作。 |
| 材料换版、预算用尽、恢复缺证 | 输出对应控制状态和已用次数。待确认的副作用保留原动作号或消息号，由原台账核对。 |

## 三、隔离回放与验收矩阵

从同一源码和数据基线建独立测试副本。使用 `tests/conftest.py` 的运行根隔离，并在测试入口断言 `works`、`works_data`、日志和台账均指向隔离根。关闭外部执行体自动启动，验证不会落进生产。测试唤醒走真实策略、事实目录、投递和会话写入，模型端用 `OutboundRecorder` 在 HTTP 发送处替换响应。真实用户控制走 `steer`／停止入口。在同一回合同时核对动作行、会话增量、模型实际请求和目标侧执行结果。 [测试沙箱](../tests/conftest.py#L47) · [实际出站探针](../tests/outbound_probe.py#L22)

| 必测 | 定量通过条件 |
| --- | --- |
| 连续超限和恢复 | 同一卡 `9,999→10,000→12,000→13,000→9,999→10,000`。首段仅一条有效提醒，等待期间交付使用最新的 13,000 字事实。回阈值后旧 pending／领用动作不能补发，下一段有新动作。加一组真实编辑并发、晚到和重启恢复，并核对另一张卡不受合并影响。 |
| 伪调用续接与重复投递 | 用同一原回合事件分别覆盖 runner 已接管、记录未决、未接管裸事实、有有效轮槽及发信待确认。真事件目录保身份字段。同一原异常仅一次可生效决定，忙卡保留原任务与工具回执，恢复不触发重复写入或落信。已处理异常产生的额外新首跳为零。 |
| 内外层乘法重试 | 配两条同层座，注入连续 503／断连，用真实适配器出站证明首选额度 2 和 3 时，同跳实际尝试分别不越上限。至少一组失败后切换成功、一组额度耗尽，逐次列实际座。再安排一次正常工具续跳，证明新跳独立记账。 |
| 失败分类、控制优先 | 分别注入 401／403、确定性 400、429 及发送前失败和发送后断流。错误码、已用额度、发出确认和终帧分账。确定性拒绝后无自动重发。在排队、退避、在途发送时触发真实停止或插话，核对停止后的新增模型请求和落信均为零，插话由原入口处理。 |
| 副作用与发布回退 | 在续跳前真实 `direct` 已落一封但受理待确认，再注入可恢复故障。真实接收方仍只有一封，原 `msg_id` 可读。评审材料守卫和正常新用户指令各做一例。两个开关关／开四组固定其他配置，关态出站与执行结果对照基线。 |

**放行条件**　连续超限和可证重复异常减少多余唤醒，重试耗尽样本减少真实模型发送尝试。预期成功的对照仍能完成同一任务和同一接收方结果。报告所有已用额度、实际发出、终帧、成功与失败，明确标出材料过期、待确认和额度耗尽。计数以传输边界事件和抓取的请求正文对账。
