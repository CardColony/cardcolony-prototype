## 二、目标形态

### 2.1 接缝判定（本方案自定，依据 §1.7）

**拆主缝 C1＋C2＋C3**（渲染直读状态、事件直改状态后全量重绘、视图态与数据态混装），**不拆** C5/C6/C7（理由见各条）。为什么是这三条：

1. **正好对应"渲染层"定义**（session_044 L227「渲染与事件：innerHTML 拼模板、bindNodeEvents、拖拽、LOD。这一层才是框架替换的对象」）——C1/C2/C3 全落这一层；拆掉，第 3 层换与不换才成为可逆决策（L230）。
2. **是纯/不纯的自然分界**——第一步已证明"布局纯函数可 node 测试"（E1 先例）；第三步把"可见集计算＋布局"编成一条**纯投影链**，渲染只消费投影结果。纯的部分可 node 测，不纯的部分留渲染层。
3. **不动存储与接口**——L5「对外接口不变」是项目铁律（§2.4），C1/C2/C3 全是前端内部结构。

### 2.2 核心设计：投影（projection）接口

**数据形状**：

```js
projection = {
  visibleIds,        // Set<card_id>  可见集（T08-1-4 规则）
  depthOf,           // Map<card_id, depth>  相对视图根深度
  layout,            // { cid: {x, y} }   computeLayout + separateOverlaps 结果
  sizes,             // { cid: {w, h} }   实测尺寸（measureSizes）
  edges,             // 连线需要的数据（父子段、关系线、跨视图目标）
  breadcrumb,        // 面包屑链
}
```

**谁生产**：`computeProjection(state, sizes)` ——**纯函数**。把现埋 renderCanvas L618–644 的可见集规则（T08-1-4：viewRoot 恒在＋直属子卡恒在＋expanded 递归展开，三条规则一字不改）搬出为独立纯函数，与 `computeLayout`＋`separateOverlaps` 编成一条链：`computeProjection = computeVisibleSet → computeLayout → separateOverlaps → edges/breadcrumb 派生`。

**谁消费**：`renderCanvas` / `renderEdges` / `renderBreadcrumb`——**只读 projection，不碰 state**。

**流向**：**单向**。`事件 → 动作 → 改 state → computeProjection → render(projection)`。渲染内无写回。（拖拽中的临时 DOM 位移是局部状态，不进 state、不进持久化——V8。）

### 2.3 候选形态对比（本方案自定，三选一）

| 候选 | 形态 | 代价 | 判定 |
|---|---|---|---|
| **M1 投影快照** | 纯函数算投影，渲染只消费 projection | ①可见集规则要从 renderCanvas 内部抽成独立纯函数（纯搬移，规则一字不改）；②createNode 内 `state.*` 引用要改为从投影/卡片数据取；③renderCanvas 大改签名——**主要工作量和风险点** | **选** |
| M2 状态订阅 | 渲染订阅 store 变化，变化即重渲染 | store.js 现 setState 无 diff 全量替换；全部事件流程改订阅式；引入防抖/批量新时序——改动面是 M1 数倍 | 不选 |
| M3 最小签名 | 只参数化 renderCanvas/renderEdges 签名，内部保留其他 state 引用 | 没拆干净——渲染仍摸 state，达不到定义"渲染通过接口消费数据" | 不选 |

**选 M1 的理由**：最贴合定义原文；复用第一步已验证的"纯函数化"打法、可测试性最好；补齐空缺——可见集规则目前只有浏览器能测，抽成纯函数后 node 可测；改动面居中、收益最大。**此判定系本方案自定**（上游只说"把接口定死"，未指定形态）。

### 3.0 次序判断（本方案自定，写死理由）

- **D1 先纯、D2 再改消费**——先立"node 可测的纯链"，再改渲染消费它；若 D2 出事，D1 等价断言可当场定位是投影链还是消费端。

- **D4 最后**：动作层收敛依赖 D2/D3 已定型（投影入口、视图态容器都定死才谈统一动作路径）。

### 3.1 与第二步部署窗口的协调（P6 的落地）

第二步生产部署（迁移＋重启）未做。本方案动的是 canvas.js（前端），**不依赖后端部署**；但存在一个归因风险：

- **若 D2–D4 在本方案施工期间，第二步部署窗口打开**（用户执行"先迁移→再重启"），重启将同时载入 E6+D2+D3（第二步）与当前第三者动过的 canvas.js——**行为变化无法归因于单一改动**。
- **处置（写死）**：部署窗口与第三步施工**互斥**——第三步 D2 起（动 canvas.js 的第一个作业段）到全部验收通过前，不执行第二步的"重启"步骤；或反过来，第二步部署完成并验证后再动渲染。**哪个先后由派发端定，但禁止并行改canvas.js与重启生产。**
