# harness 智能干预迭代方案 v1

日期：2026-10-31。状态：**迭代提案，未施工**。

依据：本次讨论，以及 `dev` 分支 HEAD `60121ba` 加当前工作区的代码实读。工作区已有 harness 并轨、评审等未提交修改；本文以读到的实际实现为基线，不把 HEAD 或旧方案单独当作完整现状。本次仅新增本文档。

## 1. 目标与交付顺序

用户对机制的定位是：“可以很智能地干预模型的工作，来防止模型犯错，走向正确的方向。”

本方案把这一定位落实为一条完整的工作链：

> 发现具体偏离 → 查明依据是否充分 → 采取适当干预 → 观察实际变化 → 解除、修正或升级处理。

“足够好”的版本应当让同一个模型在真实项目中更少漏做、更早纠偏。正常工作受到的打扰应当减少；用户能够看懂为什么介入、是否有效、现在需要谁处理。机制不承诺所有判断必然正确，也不把模型表示同意当作问题已经解决。

建议按以下顺序交付，每个阶段都有独立可检查的结果：

| 阶段 | 用户得到的能力 | 主要交付 | 进入下一阶段的条件 |
|---|---|---|---|
| S0：把判断依据做准 | 系统分得清“确实没做”“暂时看不到”“还没到检查时机” | 事件与条件契约、策略语义校正、首条试点规格 | 正常情况不被误催；信息不全不会被判成模型犯错 |
| S1：完成一次可靠纠偏 | 干预能送达、能查结果、中断后能接续 | 干预记录、接收凭证、恢复机制；评审定稿试点 | 完成、失败、占用、停止、重启、过时等分支全部有明确结果 |
| S2：处理内容与依据问题 | 系统能发现交付缺证据、使用过期依据、结论缺乏支持 | 版本引用、验证与评审判断接入、问题回应机制 | 每项判断可追溯、可反驳；实际问题改善有证据 |
| S3：分析卡解读，用户裁决策略 | 白话看懂问题；每条策略经用户批准才生效 | 分析卡（只读解读）、提案→批准→安装流、策略体检、版本隔离 | 结论可抽查原文；未批准不生效；试算与实际一致；噪音策略可退休 |
| S4：形成可持续使用的产品 | 用户能看懂、介入和调整干预 | 分析报告、干预视图、策略批准入口、真实项目验收、迁移契约 | 非技术用户能理解并裁决；常见问题的处理稳定可复现 |

**第一轮施工范围建议定为 S0 + S1。** 先交付一条完整纠偏链，再扩大它能处理的问题。S1 就应提供基本查询与停止入口，完整界面在 S4 完善。

**分析卡的只读核心可提前交付**：它只读事实库、事件与会话，不依赖干预运行库。若用户想尽早获得白话解读能力，可在 S0 后与 S1 并行先做它的查询面与报告模板；提案→批准→安装的闭环仍归 S3。

## 2. 已确认的约束与本方案的建议

沿用本次讨论和仓库中已有的用户裁定：

- 系统以事件驱动。时间可作为事实查询维度；本方案不引入定时唤醒、轮询补漏、超时强制收口。
- 不以“第 N 轮”“失败 N 次”“字数达到阈值”代替工作判断。回合数、字数、耗时可以展示和分析。
- `done` 表示一次回合结束。任务完成、业务交付、评审定稿各有自己的事实依据。
- 卡面保存当前有效的业务内容；通信负责请求、讨论、通知和推进。harness 不另外维护一份可独立改写的业务结论。
- 原始会话、卡片与事件原文不因 harness 的保留策略而删除。七天清理的对象限于 harness 的派生事实数据。
- 保留 `message`、`inject`、`continue` 的区别；`inject` 不主动唤醒，整轮有效；`continue` 现阶段只对评审卡开放。
- 复用已有消息、上下文装配与回合执行入口。评审的业务推进由 harness 组织，业务工具负责实际操作和事实记录。
- 保留评审已有裁定：已通过席位不因草稿变化被自动叫回；正卡可以提出有理由的反对；定稿必须由模型调用工具完成。
- **权限边界（2026-10-31 用户裁定）**：harness 是纯代码底座，只机械执行已被批准的策略；策略的产生与变更**不全自动**。由分析卡解读收集的信息并给出白话建议，用户裁决后才生效。任何模型都无权自行开通规则——`design_policy` 自动生效路径降级为提案通道。

下文提出的独立运行库、干预状态、策略版本、试点选择等，属于**本方案建议的实现方案**，不作为用户此前已经指定的技术细节。

## 4. 目标机制

### 4.1 各部分分别负责什么

| 对象 | 负责的事情 | 保存在哪里 |
|---|---|---|
| 业务事实 | 卡面、会话、评审批次、真实工具结果 | 继续使用各自现有的权威存储 |
| 事实索引 | 提取可判断的事件字段，支持查询和回溯 | 现有 `facts.db`，仍是可重建的派生数据 |
| 小本子 | 记录某策略、某作用域当前累计的条件 | 内存热状态；用持久化处理记录和检查点恢复 |
| 干预事项 | 哪个具体问题正在处理、依据是什么、是否仍适用 | 建议新增项目级 `works/<work>/harness.db` |
| 投递动作与回执 | 具体提醒送到谁、绑定哪轮、有没有被接收 | 运行库保存动作；接收侧保存可核查的接收凭证 |
| 问题解决依据 | 哪项真实业务变化满足了解除条件 | 引用权威存储中的结果，运行库只保存引用及判断记录 |
| 分析结论与策略提案 | 解读收集的信息，白话说明问题与建议用法 | 分析卡的卡面与报告（供用户裁决；未批准前不生效） |

`harness.db` 保存运行责任，不应按事实缓存的七天规则删除。尤其是未解决事项、投递凭证和处理水位，必须跨重启保留。原始事件、会话正文不复制成第二份业务权威。

“撕本子”保留为一次触发后的累计重置。任务是否仍然存在、批次是否已关闭等持续前提，从业务权威状态或有来源的投影读取。提醒自身不能被当成“任务仍有效”的唯一证据。

### 4.2 一条策略要表达的完整含义

在现有 `when → then` 上补充检查节点、对象绑定、解除和失效语义。先确定契约，再确定配置字段名；以下是语义规格，不是当前可直接加载的配置：

| 问题 | 定稿试点中的答案 |
|---|---|
| 管谁、管哪件事？ | 某项目、某评审卡、某批次的定稿责任 |
| 什么时候检查？ | 出现全员通过事实；相关回合完成、目标可运行；恢复时复核未结责任 |
| 什么依据说明需要干预？ | 当前批次确已全员通过，对应正稿尚未写入 |
| 怎样干预？ | 按现有能力续接评审卡，明确要求调用定稿工具，并给出当前依据 |
| 什么变化算解决？ | 正稿实际写入，并能与当前批次及产物对应；批次按既有规则收口 |
| 什么情况失效？ | 批次取消、被替换，或者动作引用的版本已经过时 |
| 信息不足怎么办？ | 补取权威状态；仍无法核实时保留“待核实”，说明缺少的依据 |
| 遇到执行阻塞怎么办？ | 记录具体原因，交给可处理该依赖的卡；等待相关事实变化或明确恢复指令 |

实现上需要区分“收集哪些事实”和“哪些事件允许发起检查”。解除、失效所需事件也必须订阅；收到它们时可以关闭事项，不必再次发提醒。

条件结果应能表示“成立、不成立、未知”，并携带所依据的事实与缺失字段。尤其是 `not`：查不到数据不自动等于相应动作没有发生。

否定条件只有在业务检查节点已到达、所需事件源已消费到对应边界、字段契约满足时，才能判定“没有发生”。跨卡事实尚未追齐时返回未知。字段确知不存在与字段尚未被观察也要区分，避免把所有缺省值都当成业务事实。

### 4.3 干预事项与投递动作分别记录

一个未解决问题可以经历多次有原因的干预。建议：

- 干预事项绑定业务对象及有效范围，记录开放、等待依赖、待核实、已解决、已取消、被新依据替代等状态。
- 每次具体投递拥有独立 `action_id`，记录待送达、已接收、已绑定回合、执行结束、失败或结果不明。
- 动作携带策略版本、触发事件引用、目标、模式、说明、预期变化、当前依据版本及前一动作引用。
- 事项解除必须有结果依据。消息送达、模型起轮、模型结束回答分别是执行事实，不直接关闭事项。

相同动作被重复传递时，接收侧识别同一个 `action_id`。新的真实回合结束后仍未完成，可以按策略形成下一次动作；不能把传输去重误做成“同一问题永远只准提醒一次”。

### 4.4 上下文与卡面保持一致

干预说明应包含：为什么现在叫你、哪件事需要处理、依据在哪里、希望出现什么结果。必要原文通过既有上下文读取能力进入模型，避免层层转述。

永久消息保存当时的说明和出处。当前是否仍需执行，由事项的有效状态与当前权威依据决定。已解除的旧提醒不能继续作为当前任务要求反复注入；原消息仍留在历史中。

暂时性提示用 `inject` 或评审 `continue` 的 hint。需要长期有效的业务决定，由有权限的角色通过正常工具写回卡面，不能只藏在一次性提示里。

### 4.5 策略的生命周期：提案 → 裁决 → 安装 → 体检

策略权属分四层：**采集与执行归 harness（机械）；解读与建议归分析卡（模型，只读）；批准归用户；安装归校验器＋试算（机械）。**

- 分析卡只产出**提案**：白话问题说明、证据引用、候选规则草案、试算会命中哪些实例。提案不是策略，不喂小本子。
- 用户批准、修改或驳回；批准后的草案经校验器检查，写入项目级运行存储（带修订号、提案来源、批准记录）才生效。
- 同一条被驳回的建议再次出现时，必须引用新证据——防止换皮重提。
- 分析卡用同一套白话报告**复盘既有策略**：命中率、解决率、被反驳成立次数、从未解决过的事。停用与调整同样经用户批准。
- 任何「想让系统在异常时自动提醒分析卡看一眼」的需求，本身也是一条需批准的 harness 策略——自举自管不另开特权通道。

## 5. 必须补齐的运行契约

### 5.1 事件处理与恢复

1. 为来源事件使用稳定身份。当前日志至少使用 `(work, card, seq)`，不能把卡内序号当全局序号；日志重建或序号可复用时，补来源代次。
2. 运行库记录收到过的事件身份及处理顺序。跨卡依赖通过明确关联表达，时间戳只作事实维度，不能单独证明因果先后。
3. 一次处理把“待执行动作、清账后的检查点、已消费事件位置”提交在同一运行库事务中；提交后才推进对应内存状态并安排投递。
4. 提交失败时，来源事件仍可从主账本恢复，处理位置不前移。事实索引写入失败必须显式记录观察异常，不能静默证明“没有发生”。
5. 启动或恢复时读取检查点，按已记录顺序重演未处理事件；逐事件使用同一求值和清账规则。恢复使用原有求值时间依据，不让机器当前时间悄悄改变历史窗口。
6. 复核未结事项的当前有效性后，再恢复待投递动作。历史中已经解决的问题不能因为重建而重新催办。

实时事件和恢复事件必须经过同一提交入口；一个工作进程内按项目顺序提交。并发回调依靠事件身份和事务条件避免重复消费。跨进程运行必须复用实际部署底座提供的互斥与执行身份，不能仅靠进程内集合声明可靠。

### 5.2 接收侧与三种干预方式

| 手段 | 接收端需要满足的契约 |
|---|---|
| `message` | 复用 `session_facade.append_card_message`。将 `action_id` 放入真正持久化的会话元数据，在既有会话写锁下查重并追加；消息与凭证必须属于同一个完整写入结果。现有 `extra` 仅用于事件字段，不能假设它已经保存了接收凭证 |
| `inject` | 为注入项增加身份、领取回合和消费状态，兼容现有字符串项。绑定到实际回合后，该轮每次调用都可见；装配失败或调用前中断不能直接视为已使用。通过原上下文装配入口处理，保持不主动唤醒 |
| `continue` | 复用评审执行入口。区分接收、目标忙、用户停止、无有效批次、调用失败等结果；用动作身份关联实际回合。返回结构化结果，停止用非空字符串表示成功与否 |

会话当前是文件存储，运行库与会话写入不是一个数据库事务。发送侧保留可重复投递的动作，接收侧通过完整会话块中的身份核对；损坏或不完整的块按既有恢复机制处理，不能作为成功凭证。

`message(wake=true)` 还需要分别记录消息写入与唤醒接收。消息已落盘、唤醒尚未接收时，恢复只补缺少的唤醒，不能因为消息去重而把唤醒一并丢掉。

跨存储的注入绑定也要通过持久化身份和回执核对恢复，不能用“先清空队列、稍后再记成功”假装原子性。

对外部模型请求，若请求可能已执行而本地未收到结果，应记录“执行结果不明”，结合回合与工具记录核查。单有去重键不能保证任意外部副作用恰好执行一次。

### 5.3 忙、停止、过时与策略冲突

- **目标忙：** 动作留在待处理状态，订阅既有回合释放或执行体就绪信号。需要补充真实释放事件时，在释放完成后发出，避免收到事件时锁仍占用。不开定时重试。
- **用户停止：** 停止意图跨重启保留，优先于自动唤醒。只有明确的恢复行为才重新允许推进；启动扫描不能绕过它。
- **依据过时：** 发出动作前及业务工具执行前检查对象、批次和版本。旧动作作废并保留原因；已经进入某轮的提示不能声称被追溯删除。
- **同一问题命中多条策略：** 先处理解除、失效和停止，再合并相同目的的动作。相互矛盾的工作要求形成待裁决分歧，不能靠策略遍历顺序决定谁生效。
- **干预产生新事件：** 接收回执可用于判断送达，不能当成业务进展。记录因果来源，防止“发了提醒”自动成为“还要再发相同提醒”的充分条件。

没有新事件时，harness 不凭空推断执行失败。利用执行体已有的错误、退出、连接变化和用户恢复行为产生事实；上游如果完全没有提供信号，只能保留当前可确认的状态，不能承诺自动识别所有静默挂起。

## 6. 分阶段施工

### S0：把判断依据做准

**施工内容**

- 明确普通回合、评审席位回合、业务交付、批次定稿的检查节点；统一回合、批次与对象身份。
- 让当前触发事实是否参与求值成为明确语义，消除靠省略 `trigger_type` 调整窗口的隐式行为。
- 条件校验覆盖事件字段、作用域、目标、模式，以及观察数据是否完整。未知值按未知传播。
- 校正当前 `turn_end_without_report`：撤下按普通 `done` 自动催报的行为，业务交付检查按明确的交付协议接入。不要自行给 `report_up` 加回 `kind`。
- 把首条定稿试点的触发、解除、失效和接收能力写成可执行契约。

**交付物**

事件与条件契约；校正后的策略配置；接收凭证与中断恢复设计；与首条试点对应的正例和反例。接收侧凭证必须说明实际持久化落点，不能只写“加一个 id”。

**验收**

普通闲聊收口不催交付；上一轮事实不冒充本轮完成；字段缺失或历史不完整时可解释地待核实；已知正常路径不因新增条件被叫醒。

### S1：让定稿纠偏完整运行

**施工内容**

- 增加干预事项、动作、处理位置和检查点的持久化。
- 把条件命中后的清账与待投递动作可靠交接。
- 补三种模式的接收结果、动作身份与恢复语义；优先跑通 `continue` 定稿试点，再验证其余模式。
- 接入解除与失效观察；提供按项目和卡查看原因、动作、结果的最小查询入口。
- 统一启动恢复与现有 `_resume_reviews` 的责任。每个被纳入的业务推进点只有一个自动驱动者。

**首条完整试点**

1. 现有 `review_all_passed{need_promote:true}` 出现，记录当前批次的定稿事项。
2. 读取 `review_store` 与对应正卡，确认当前批次、通过状态及正稿状态。正稿已写且对应批次已收口，才直接带证据关闭事项。
3. 目标仍忙时保留动作；真实回合释放后再次检查停止位及依据。
4. 通过现有评审 `continue` 入口交给模型，说明尚缺定稿。harness 不直接代写正稿。
5. 模型调用 `promote_draft`。通过实际写入、对象身份和批次状态确认结果，不能仅凭“工具名出现过”认定成功。
6. 正稿已写且批次按规则收口，事项结束。若正稿已写而收口未完成，由业务工具按当前状态接续未完成部分，避免重复改写正稿；工具明确失败则记录原因并交给能够处理该问题的角色。
7. 批次被替换、用户停止或依据改变时，旧动作分别失效、暂停或重新绑定。过程中已通过的席位不因此重新评审。

如果草稿改变，仅使引用旧产物的未执行动作需要复核；是否仍满足通过条件，继续遵守当前评审批次的业务规则。

**验收**

完整成功路径，以及命中后崩溃、送达后未回执、目标忙、用户停止、重复事件、已自行定稿、批次替换等分支，都能解释最终状态。已解决的问题不再催；未送达的动作不因清账消失。

### S2：扩展到证据、依据与语义判断

按以下顺序增加能力，每一类都走 S1 的同一干预生命周期：

| 场景 | 新增的实际能力 | 干预与解除依据 |
|---|---|---|
| 准备交付但缺验证证据 | 明确交付对象、要求版本、产物身份、验证结果之间的关联 | 要求补验或报告具体阻塞；当前产物对应的有效证据齐备后解除 |
| 依赖的权威内容已变化 | 记录业务引用及版本，识别受影响的依赖方 | 请依赖方核对影响；确认仍适用或完成必要更新后解除 |
| 结论缺乏支持、方案可能违背要求 | 复用评审卡、职能卡和验证工具产生带依据的判断 | 将具体质疑送回当事卡；依据补足、质疑被有效反驳或有权角色作出取舍后结束 |

交付检查需要明确的业务提交事实；若现有事件没有足够信息，在业务提交入口补契约，不能用普通 `done` 替代。验证过程确实执行成功与验证足以支持结论，分别记录。

引用变化先表达为“需要检查适用性”，不能直接宣布所有下游结论错误。旧数据缺版本时记录覆盖不足，不伪造历史版本，也不推翻“已通过席位不再自动叫回”的裁定。

语义判断记录提出者、涉及的问题、证据引用、产物与要求版本、建议处理方式和不确定之处。它是一项可被回应的判断。模型可以补证据、修改，也可以有依据地反驳。

语义评估在相关产物、证据、要求变化或明确复核请求时调用。同一依据下已有的有效判断可以复用，重复投递不再次调用模型评审；新论据出现后允许重新评估。

**进展与分歧处理**

继续推进的依据是与该问题有关的新证据、有效修改、分歧处理结果或可执行的新办法。草稿变化需要解释它解决了什么；有文本、换措辞、字数增长均不单独证明进展。

出现明确的依赖缺失、权限不足或双方无法自行裁决的业务取舍时，把问题及各方依据交给父卡；需要用户取舍时再交给用户。没有统一的轮数上限，也不把一次空回复推断为永远无法继续。

**验收**

同一案例至少覆盖真实问题、正常工作、有效反驳、旧证据失效四种情况。用实际产物与依据检查是否改善，不能用干预次数或评审一致率代替结果。

### S3：分析卡解读事实，用户裁决策略

**定位**

- harness 是纯代码底座，只机械执行已批准的策略；策略的产生**不全自动**。
- 增设一张**分析卡**：专读 harness 收集的信息（事实库、事件、会话、台账），把复杂事实翻译成白话——出了什么问题、为什么有问题、建议怎么用 harness 优化。
- 它的边界：只读、不设计卡片、不改写任何卡面、不开通策略。它是顾问，不是管家。

**工作方式**

- **什么时候跑**：用户点名 ＋ 自然里程碑（批次收口、阶段完成、交付之后）。不常驻巡检；若想让它在异常信号出现时自动看一眼，「自动提醒分析卡」本身就是一条需批准的 harness 策略。
- **看什么**：事实库的三轴聚合查询（类型/卡/时间窗）＋系统给的少量机械聚合视图（各策略命中数、干预送达与解决数、各工具失败数）。卡负责解读，不负责搬原始事件。
- **怎么写结论**：每条结论挂证据（哪张卡、哪些事件、多少次、何时），用户可抽查原文；「有证据」与「推测」分开标。
- **怎么写建议**：白话问题说明＋候选策略草案（可安装的规则形态＋试算命中实例）＋非 harness 的修复建议（提示词、工具、卡面问题）分类列出。

**策略安装流程（用户是唯一开通者）**

1. 分析卡产出候选策略（白话＋结构化草案）；
2. 系统校验合法性并按历史事实试算，把「它会命中哪些实例」摆给用户；
3. 用户批准、修改或驳回；批准后写入项目级运行存储（带修订号、提案来源、批准记录）方才生效；
4. 动态策略与系统默认策略分库，杜绝跨项目同名覆盖与根卡互踩；
5. 被驳回的建议再次出现时必须带新证据，防止换皮重提。

**既有策略的体检（同一白话报告，反向用）**

分析卡复盘既有策略：命中多少次、解决了多少事、被模型反驳成立几次、从未解决过什么、是否重复吵同一件事。停用与调整建议同样交用户批准——规则只增不减的漏洞由「退休建议」堵住。

**`design_policy` 的去留**

保留其校验与试算机制，取消自动生效：产出进入「待批准提案」而非直接写表。根卡侧不再下发自动设计权限，提案通道统一到分析卡。

**验收**

报告每条结论可抽查到事件原文；提案草案通过同一校验器；未经批准任何新策略不生效；试算展示与实际命中一致；噪音策略能被点名并可被停用。

### S4：交付给非技术用户持续使用

**施工内容**

在已有项目、卡片和事件展示中增加干预视图，回答五个问题：发现什么、依据是什么、采取了什么行动、有没有改善、需要谁决定。

分析报告与策略批准入口在同一白话层：用户看结论、抽查证据、点批准或驳回，不接触规则 JSON。

提供单事项暂停、恢复、查看依据和提出纠正的入口。用户的暂停、取舍和要求变化进入同一事实与状态链，实际影响待执行动作。保留历史说明，不依赖删除旧消息来改变当前状态。

用户可见示例：

> 实现已经提交，但缺少与当前产物对应的验证结果。系统已要求补验。执行卡报告验证环境不可用，父卡正在处理依赖。当前尚未确认交付完成。

随后选取真实复杂项目验证：用户是否能看懂阻塞并作出有效决定，是否减少反复提醒、人工核对和返工，正常工作是否受到无谓干扰。每个发现落实为机制或策略修改，再验相应场景。

**与 CardColony 的衔接**

先稳定事实订阅、策略求值、干预动作、执行回执和恢复五类接口，再映射到 CardColony 的运行与持久化能力。业务判断仍属于卡片、工具和评审层。本文未重新审计 `D:\AI_station\Cardlo` 的现行接口，因此接口适配需在迁移施工时取证，不能当作已经完成。

## 9. 存量迁移、启用与撤回

1. 施工开始时记录实际代码和数据格式版本。当前未提交改动保留，逐处核对；不能直接拿旧方案覆盖正在演进的实现。
2. 新增运行存储不改写卡面、会话和原事件历史。老注入字符串以兼容方式识别；旧消息没有动作身份时，不伪造“已确认送达”的凭证。
3. 现存批次通过当前权威状态建立未结事项。首轮接管不重放历史消息，也不凭日志猜测改动评审票。
4. 先在隔离目录验收，再对指定项目启用新处理链。观察模式只生成诊断结果；启用时重新核对当前状态，观察阶段的旧动作不能直接补发。
5. 每个纳入的业务推进点同时只由一套驱动负责。现有恢复入口移交时同步取消重复调度，不恢复已经退役的第一代规则引擎。
6. 需要撤回时暂停新动作、保留事项和回执，明确未完成责任由谁接续。存储升级采用兼容的增量方式；禁止通过删除运行库“恢复干净状态”。
7. 现存由根卡写入的 `work` 级策略迁移为「待批准」状态：用户过目后选择启用或删除，不静默保留自动生效。
8. 涉及服务重启时遵守仓库 `restart_safe.py` 的起停约定，先处理在途调用。本次文档交付不涉及重启。

## 10. 第一轮施工任务与完成定义

第一轮按 A → B/C → D 的依赖顺序推进，基本查询随 B/C 一起交付。先把试点的事实、接收凭证、解除条件与停止语义写清，再接自动执行。

这一轮的交付应包含：可运行的改动、首条定稿策略、接收与恢复契约、V01—V14 及相关冲突场景的证据、迁移说明、未覆盖项。

第一轮完成时，应能展示一个可复查的完整案例：

> 一次评审已经全员通过，但对应正稿还未写入。harness 识别到这件具体未完成的事，在目标可运行时带着依据续接；模型通过工具完成定稿；系统依据实际产物关闭事项。过程中即使忙、停止、重启或重复收到事件，也能说明当前状态并按正确责任接续。

S4 的“足够好”版本还应在真实项目中证明：交付证据和引用问题确实得到纠正，正常工作受到的干扰可控，用户能理解并裁决分歧，项目策略的调整有可核查的效果。每项验证结果都要能回到具体案例及产物。
