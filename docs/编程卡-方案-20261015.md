# 编程卡方案（2026-10-15 · v1）

## 一、目标

把「执行」从主卡里剥离出来：**主卡是脑（拆解/判断/沉淀，无 edit），编程卡是手（承接开发任务，有 edit）**。一张编程卡＝一个开发任务，做完即终态留档、静默，主卡随时回看全过程。

## 二、已定原则（用户裁定，不可改）

1. 编程卡＝传统 agent 的子 agent：主卡无 edit、编程卡有 edit。
2. 承接主卡递来的开发任务；**永远留档**（不可删）；**一次只执行一个任务**；执行完静默不再被激活；主卡随时能查看编程卡过程。
3. **主卡写文件权限暂时保留**（tools_file 不收，edit 收回属「权限管理第一次」另案）。
4. **编程卡回报要激活主卡进行验收**（不是单向通知）。

## 三、设计

### 1. 新卡类型 `coder`（配置驱动，零代码加类型）

`config/card_type_registry.json` 的 `rd_project` 词表加一项：

```json
{
  "code": "coder",
  "label": "编程卡",
  "description": "承接上级卡开发任务的执行体。一次一个任务；自报完工即终态；终态后静默、不可删、永久留档。",
  "can_have_children": false,
  "requires_owner": false,
  "default_template": "coder",
  "allowed_transitions": ["active", "completed"]
}
```

`config/permissions.json` v3→v4 加一行：

| 卡 | perms |
|---|---|
| `rd_project/coder` | read, edit, tools_file, tools_web, search, plan, shadow_write, read_linked, list_memory |

**刻意不给**：create_child（不长树）、delete（留档）、send_card_message（不发信——完工回执由系统发，不归模型）、invoke_tool（不调用工具卡）。tools_web 给（查文档是开发刚需）。

### 2. 建卡即递任务（派生即调起，最小开源版清单第 1 件）

```
主卡对话中模型调 create_card(card_type="coder", content=任务书)
  → 建卡成功（任务落使命块，source=模型生成）
  → 【新接线】建卡路径识别 card_type==coder → 系统把「任务书」组装为激励文
    → asyncio.create_task(_run_message(work_id, 新卡id, 激励文, append_user=False))
  → 编程卡自动跑第一轮（读到使命块任务 + 自己的工具面开始干活）
```

- create_card 工具 schema 不向模型开放 card_type 枚举（现状即如此）——coder 类型由**专门入口**建：主卡模型调 `create_coder_card(title, task)` 新工具（或 create_card 加可选参数，施工时定，倾向前者——语义清晰、权限好判）。
- 激励文复用卡间信的素材形态（任务全文 + 上级卡名），append_user=False 不落档，任务本体已在使命块。

### 3. 执行轮（复用，零改动）

编程卡就是一张普通卡跑 `_run_message`：六区上下文（卡片清单/当前卡/记忆/对话历史）+ 按 perms 下发工具面（read_file/search_files/write_file/list_files/web_search/fetch_web + read_card/read_shadow）。无轮次上限、无墙钟（零闸原则）。改码产物自动留痕（write_file 备份 + tool_events + 影子）。

### 4. 完工：自报 + 收口 + 回执（移植工具卡语义）

- **新工具 `report_done(summary)`**（仅 coder 工具面下发）：模型认为做完时调用。代码照单执行——**不判真假、不验产物**（判断归模型）。
- 执行三步（全 IO，零判断）：
  1. `state=completed`（闸4 合法迁移）+ summary 落卡 front matter（`coder_final` 字段，形态照 `toolcard_final`）；
  2. 影子收口：完工行落影子「## 迭代历史」（时间 + summary + 改动文件数，从本会话 tool_events 机械统计）；
  3. **系统发完工回执**：卡间信 `coder_done` 类型 → owner 主卡，K2 记 TRIGGERS → 编程卡回合收口时 K3 **自动调起主卡跑验收轮**（现有链路，零新机制）。
- `config/message_type_registry.json` v1→v2 加类型：

```json
"coder_done": {
  "display": "完工回报",
  "note": "编程卡报告任务完成。收到后应验收：读它的完工报告与产物（read_card / read_shadow / read_file），对照任务与需求判断是否达标，结论写进本卡；不达标则新建编程卡返工。",
  "reply_expected": true,
  "reply_type": "msg_answer"
}
```

### 5. 主卡验收轮（现有机制自动跑）

主卡被 K3 调起，激励文含 coder_done 的应对说明 → 主卡读产物/对照需求 → 结论走 draft/按钮确认写主卡（需求文档块或定论）→ S4 自动回发 msg_answer 给编程卡（落其收件箱留档，**不再调起**——见 6）。

### 6. 静默（终态焊死，双保险）

- **入口层**：`POST /messages` 对 `card_type==coder 且 state==completed` 的卡 → 400「编程卡已完工，不再激活；新任务请新建编程卡」。
- **调起层**：K3 补齐路径对 completed 的 coder 跳过（防未来全量补齐时误调起）。
- 判定均为查字段的机械判定（同「根卡不可删」性质），无内容判断。

## 五、落地步骤

1. 三份配置（类型/权限/消息类型）＋ 刷新存量（refresh_perms）。
2. `report_done` 工具（收口 + 回执，先通完工链）。
3. `create_coder_card` 工具（建卡 + 派生即调起，再通启动链）。
4. 静默双保险 + prompts 说明。
5. 测试 + 全量回归 + 生产 restart 验证。

## 六、存量迁移

零迁移。coder 是新类型，存量卡无涉及；权限 v4 刷新只改 perms_version。

## 七、验收判据

1. 主卡调 create_coder_card → 新卡 state=active、perms=v4 值、**自动跑起第一轮**（事件流有 run_start）。
2. 编程卡工具面：含文件四件+联网两件+read_card/read_shadow/report_done；**无** create_child/delete/send_card_message。
3. 编程卡 report_done → state=completed、影子迭代历史有完工行、主卡收件箱出现 coder_done 信、**主卡被调起跑验收轮**（事件流有 run_start）。
4. completed 后：POST /messages → 400；卡间信调起被跳过；卡不可删（delete 权限无）。
5. 主卡验收轮回 msg_answer → 落编程卡收件箱留档、不调起。
6. `pytest -q MOCK_LLM=1` 全绿，失败集与基线零差异。

## 七、红线

- 只动 §四 白名单；卡间信底座（K2/K3/收件箱/S4 回发）、工具卡底座、消息底座零改动（只消费）。
- report_done 照单执行不判真假；静默判定只查 state 字段。
- 不动 sub_project 权限（主卡 edit 收回属「权限管理第一次」另案，不混批）。
- 改前 E 盘备份；不删数据；重启只走 restart_safe.py。
