# 规则卡方案（2026-10-15 · v1）

> 定位：规则卡＝这个 agent 的 AGENTS.md——全局行为准则，按卡类型分区，自动注入对应卡的上下文。

## 一、目标

把「散落在各处卡里的行为约束」收拢成一张全局规则卡：一 work 一张、按卡类型分区、右侧常驻可编辑、按当前卡类型自动注入上下文。模型只能**提议**修改（根卡通道＋用户弹窗审批），不能直接写。

## 二、已定原则（用户裁定，不可改）

1. 每 work 一张规则卡，parent=根卡；规则全局唯一。
2. 规则卡按卡类型分区（区名＝card_type code），**各区可分别编辑**。
3. **画布右侧常驻显示**规则面板（独立右栏，不跟当前卡走）。
4. 用户可在面板**直接编辑、保存即生效**（无确认框——用户自己的操作不需要审批）。
5. **根卡可提议规则修改**：根卡对话里的模型起草规则修改 → **弹窗提示用户 → 用户同意才落盘**；其它卡无此通道。
6. 注入位置：order **85**（instruction 之后、卡片职责之前——行为准则先于职责）。
7. 规则卡本体：模型侧只读（rule 类型 perms 只给 read），一切模型侧写入必须过用户审批弹窗。

## 三、设计

### 1. 新类型 `rule`（三配置，零代码加类型）

- `card_type_registry.json`：rd_project 词表加 `rule`（can_have_children=false、requires_owner=false、allowed_transitions 无——规则卡不进 active/completed 状态机，恒在）。research_project 词表同步加（规则全局机制，两类树都要有）。
- `permissions.json` v4→v5：`rd_project.rule = ["read"]`、`research_project.rule = ["read"]`——**只读**，模型写不了（含 shadow_write 也不给：影子由系统收口时记）。
- 规则卡默认模板另立（`default_template: "rule"`）：正文＝分区说明 + 六区占位（`## sub_project` / `## coder` / `## tool` / `## project` / `## topic` / `## rule`），不走使命/现状/定论三块骨架。

### 2. 规则卡存储（正文即分区 md）

- 一 work 一张：card_type=rule、parent=根卡、source=用户直接创建。
- 正文结构：

```markdown
## sub_project
（主卡行为准则…）

## coder
（编程卡行为准则…）

## tool / ## project / ## topic / ## rule
（各自规则；空区＝占位行）
```

- 区切分：按 `## ` 行机械切（**不走** hash_utils 三块语义映射——规则正文不是三块结构）；区名集合＝注册表 l1 词表 code ＋ `rule` 自身。
- 分区保存：读全文 → 只替换目标区段（区头＋区内容）→ 重算 content_hash → 写回。**写路径经 card_store 统一闸，禁绕门**（具体键形态施工定：规则正文整体为一块存储，前端按区编辑、后端按区替换）。
- 保存即生效天然成立：装配链每请求 fresh 扫库（`build_ctx` 每回合重取），无缓存层要破。

### 3. 注入区（第 14 区，order 85）

- `context_regions.py` `REGION_TABLE` 加 `rule` 区：render＝`render_rule_region(rule_sections, 当前卡 card_type)`——**当前卡是什么类型，注入规则卡对应区**；当前卡无对应区 / 无规则卡 / 规则卡对应区为空 → 区不出现（「没有来源就不出现」铁律）。
- `RegionCtx` 加 `rule_sections: dict` 字段（`build_ctx` 装配前一次取数：扫本 work card_type=rule 的卡 → 切区）。
- 规则卡自己跑对话时按 `## rule` 区注入（防递归：规则卡注入的是「关于规则卡的规则」，没有就不出现）。
- `config/context_regions.json` v3→v4：加 `"rule": { "enabled": true, "order": 85 }`（控制面口径与其它区一致）。
- seats：main only（viewpoint 三席零指令铁律不动）。

### 4. 三个编辑入口（权限分级）

| 入口 | 谁能用 | 机制 |
|---|---|---|
| 右侧规则面板 | 用户 | 分区编辑框、保存即写盘（PATCH 路由，per-section hash 比对防并发覆盖） |
| 根卡审批通道 | 根卡对话的模型 | `draft_rule_edit(section, content)` 工具（**仅根卡工具面可见**，ROOT_ONLY_TOOLS 闸，照 CODER_ONLY_TOOLS 先例）→ 返回草稿+base_hash → **前端弹窗**（区名＋原内容＋新内容）→ 用户点同意 → `POST /works/{w}/rule/commit`（用户路由，非模型工具）→ hash 比对 → 按区替换落盘 |
| 其它卡 | 无 | 工具面无 draft_rule_edit；规则卡自身 perms 只 read |

弹窗复用现有 draftModal 组件（kind 扩展 `rule_edit` 分支：标题「规则修改审批」、三键「同意/拒绝/关闭」——拒绝与关闭都不落盘）。

### 5. 画布右侧常驻面板

- 新 `#rulePanel` 右栏（独立于 inspector——inspector 跟当前卡走，规则是全局的）：常驻开合按钮（照 inspector/nav-rail 模式）、分区列表（每区：标题＋编辑框＋保存按钮＋「本区正被 N 类卡注入」提示）。
- 导航树里 rule 卡显示但**不开放对话**（点它＝展开规则面板，不是开聊天）。
- 规则卡在画布主区不渲染节点（它是全局面板，不是树上的一环）——canvas 渲染按 card_type 跳过 rule。

## 五、落地步骤

1. 三配置（类型×2词表/权限/区控制）+ 刷新存量。
2. 注入区（RegionCtx 取数 + render_rule_region + order 85）。
3. 规则面板（右栏 + 分区读写路由 + 保存即生效）。
4. 根卡审批通道（draft_rule_edit + 弹窗 + rule/commit）。
5. 测试 + 全量回归 + 生产冒烟（冻结窗口）。

## 六、存量迁移

零迁移。rule 是新类型；v5 刷新只改 perms_version；存量卡无规则卡时注入区不出现（fail-open，「没有来源就不出现」）。

## 七、验收判据

1. 建规则卡（parent=根卡）成功；类型/权限表值正确；模型工具面对规则卡只读（无任何写工具）。
2. 注入：跑 sub_project 卡 → 上下文含规则卡 `## sub_project` 区内容（order 85，位于 instruction 与 card_duty 之间）；跑 coder 卡 → 注入 `## coder` 区；无规则卡/无对应区 → 区不出现、装配零报错。
3. 面板：分区编辑 → 保存 → 盘上对应区替换、content_hash 重算；下一回合对话注入即变（fresh 验证）。
4. 审批链：根卡调 draft_rule_edit → 弹窗出现（区+原+新）→ 同意 → 落盘 + 影子/历史记一行；拒绝/关闭 → 卡零改动；非根卡工具面无 draft_rule_edit（执行层直调 denied）。
5. hash 防冲突：起草期间规则卡被用户改过 → commit 被拒、提示重新起草。
6. `pytest -q MOCK_LLM=1` 失败集差异仅限列明翻新断言，新增全绿。

## 八、红线

- 只动 §四 白名单；上下文装配底座（RegionCtx/REGION_TABLE 机制）、draftModal 组件、卡间信零语义改动（只消费/扩展）。
- **模型永远不能直接写规则**：唯一模型侧通道＝根卡 draft_rule_edit（只起草不落盘）＋用户审批落盘；rule 卡 perms 只 read。
- 分区保存/审批落盘都走 card_store 统一写闸 + hash 比对，禁绕门、禁无比对直写。
- 不改现有函数签名；不改 view 席 join 规则（三席零指令）。
- 改前 E 盘备份；不删数据；重启只走 restart_safe.py（与编程卡冒烟同一冻结窗口）。
- 不新增依赖。

## 九、Open Items（撞上停手回报）

1. 规则正文的存储键形态（整体一块 vs 分区多键）——施工时按 card_store 写闸最小侵入定，回报取舍；禁为规则卡新造第二套写路径。
2. 多张 rule 卡的异常态（用户手建两张）——取第一张＋ops 留痕，或面板提示「存在多张规则卡，请删至一张」；施工时定，回报。
3. 规则卡是否也进 git auto-commit/快照——沿用卡的既有机制，零特殊处理；若撞异常回报。
4. 注入区对 draft 通道（卡片编辑的 draft 调用）是否开放——建议开放（draft 也是 main 席位语义）；施工时确认无回归，回报。
