## 〇、一句话

把「更新现状」从**独立的 `/draft` 起草通道**，改成**本卡的一次普通回合**——走主流程、主流程模型、带卡内全部工具；用**当轮注入**把「本轮任务 + 当前现状」交给模型；模型调研完调一个**只提议不落盘**的工具交出「新现状」；前端据此弹**对比确认窗**，用户确认后走 commit 落盘。

这与项目里**既有的「规则卡审批」范式同构**（`draft_rule_edit` 只提议 → 前端扫 timeline → 弹窗 → 用户同意 → `/rule/commit` 落盘）——**不是新造机制，是把现状更新收回同一个范式**。

## 一、需求 → 落点（逐条对齐）

| 用户需求 | 落点 |
|---|---|
| 1 提示词注入到**当轮位置**、且写清楚 | 新增一类**当轮注入事件**（沿现有 `context_*` 注入族），轮首注入；文本重写 |
| 2 是**本卡的一次特殊操作**，从流程到模型都用**主流程** | 走 `message_runner`；模型＝主流程模型（**不** `resolve("draft")`） |
| 3 注入的提示词里**附上当前现状** | 注入事件正文带上「当前现状全文」 |
| 4 对话流在**卡内**、能调**卡内所有工具** | 就是一次普通回合 ⇒ 事件落本卡 timeline、工具面按本卡 perms 下发 |
| 5 **只在最终提交**才弹窗 | 模型调 `propose_status` 成功 → 前端扫 timeline → 弹窗 |
| 6 弹窗**完整、格式正确**，**原现状 vs 更新点对比**，**一块板子** | 弹窗＝单面板行级 diff（旧 vs 新） |

## 二、方案（分六步）

**1. 触发**（前端）
输入条「更新现状」不再调 `/draft`，改走 `POST /api/works/{w}/cards/{c}/messages`，请求体带一个操作标记（如 `op: "update_status"`）。本轮的用户消息＝一句固定触发语（可见、可留痕）。

**2. 注入**（后端 · 轮首）
新增一类当轮注入事件（暂名 `status_update_task`），在**本回合首次模型调用前**注入一条消息（沿现有 `current_turn` 注入机制，role=assistant、带抬头〔现状更新〕）。正文＝**写清楚的现状更新指令 ＋ 当前现状全文**（需求 1、3）。

注入提示词**文本（方案稿，待你审）**：

```
〔现状更新〕

我这一轮的任务：把本卡的「现状」更新一遍。

现状是什么：本卡「当前确定的状态与结论」。
别的卡（尤其上级卡）读本卡，先读的就是它——所以这里写的是**别的卡继续工作要知道的**东西，
不是只给本卡后续对话看的。它不是使命（本卡要干什么），也不是第三块（需求/定论）。

现状具体写三类：
· 当前确定状态：现在已经确定了什么、哪些能作为其他卡工作的依据；
· 接口与约定：本卡对外提供什么——输入输出、调用方式、约束；
· 依赖与影响范围：本卡依赖哪些模块；本卡变更时哪些卡或功能会受影响。

怎么写：整块覆盖、只保留最新一份；只写已经确定的结论；不写过程、不写「做到哪」的流水账。

我这一轮怎么做：
1. 先查证再动笔：需要什么事实就调工具去查（读卡 / 读影子 / 读文件 / 搜索都行），
   不凭记忆、不猜。
2. 查完按上面三类写一份新现状（只写已经确定的结论）。
3. 写完调 propose_status(content)，把「新现状正文」交给它——它只提议、不落盘。
4. 不直接改卡（我没有直写现状的通道），也不要动使命块和第三块。

当前现状（原样给出，供我对照修订）：
{当前 status_block 全文；为空则写「（暂无现状，从零起草）」}
```

**3. 流程与模型**（后端）
本轮走 `message_runner` 主流程；模型＝主流程模型；**工具面按本卡 perms 下发**（需求 2、4）。

**4. 产出**（后端 · 新工具）
新增工具 `propose_status(content)`——**只提议、不落盘**，返回 `{proposed, old, base_hash}`（对齐 `draft_rule_edit` 的形态）。模型调研完调它交出「新现状」。

**5. 弹窗**（前端）
回合收口后扫本卡 timeline，找 `propose_status` 的成功 `tool_result` → 打开**对比确认窗**（带本卡 card_id，防串卡）。

**6. 落盘**（后端 · 复用）
用户点「同意」→ `POST …/commit`（**复用现有 commit**：`base_hash` 乐观锁 → `update_card` 整块替换 `status_block` → 影子记一行）。

## 三、改在哪一层 · 为什么

| 层 | 改什么 | 为什么是这层 |
|---|---|---|
| 前端 | 按钮改走 `send(op)`；扫 timeline 开对比窗；弹窗 DOM/CSS | 交互与展示归前端 |
| 路由/编排 | `/messages` 认 `op`；`message_runner` 轮首注入；新增注入事件类 | 「当轮注入」是编排层既有能力（`current_turn`） |
| 工具层 | 新增 `propose_status`（只提议） | 对齐 `draft_rule_edit` 的既有范式 |
| 起草/落盘 | `card_draft.commit` 复用；`draft` 通道退役或收窄 | 写入唯一入口本就是 commit |
| **不动** | 存储层（`status_block` 仍整块替换） | 需求未要求改存储语义 |

**后端为主、前端配套**；不引入新存储、不引入新机制。

## 四、我自裁的细节（理由写明，可推翻）

- **注入事件命名** `status_update_task`，沿 `context_*` 注入族（与 `context_preamble` / `judgment_protocol` 同构）。
- **工具命名** `propose_status(content)`（动词对齐 `draft_rule_edit` 的"只提议"语义）。
- **操作标记** 用 `POST /messages` 的请求体字段 `op`（不新开端点，复用同一编排链）。
- **弹窗复用** 现有 `draftModal` 的 DOM（规则卡审批已复用过一次），新增「对比」版式，不另造弹窗。
- **diff 呈现**：**单面板、行级**（旧行/新行对照，新增/删除着色）；不用并排双栏（需求要"一块板子里"）。
- **本轮用户消息**＝固定触发语（留痕需要）；完整指令走注入（需求 1 要的就是"注入到当轮"）。

## 五、排除的替代（及理由）

| 替代 | 为什么不用 |
|---|---|
| 保留独立 `/draft` 通道，只改提示词 | 不满足需求 2、4（要主流程模型 + 卡内工具） |
| 用 system 前缀注入提示词 | 不满足需求 1（要"当轮位置"） |
| 让模型把新现状写在**回复正文**里（不设工具） | 正文会夹带解释/杂文，**无法可靠抽取**；既有规则卡已用"工具提议"解决 |
| 点按钮就弹窗（现状行为） | 不满足需求 5（只在最终提交弹） |
| 弹窗并排双栏对比 | 不满足需求 6（要"一块板子里"） |

## 七、这个方案**没解决**什么（诚实分级）

- **不改存储语义**：commit 仍是**整块替换** `status_block`（需求未要求改）。
- **不处置**问题清单里的其它技术问题（B/D/E/F/G/H/I/J）。
- **不处置**「切卡串卡」根因（已另派）；本方案只保证**新弹窗绑卡**、不再产生新的串卡路径。
- **前提未定**：需求 #7 的争议（起草喂全量历史）——改走主流程后，历史按主流程规则（含水位切片），这条**大概率自然消失**；但**要先把 #7 确认掉**。

## 八、是不是补丁？（自我评估）

**结构性，不是补丁。** 判断依据：它把「更新现状」从**旁路通道**收回**主流程**，复用的是项目**已有的**「工具提议 → 前端确认 → commit」范式（规则卡），不是在旧旁路上打补丁。
—— 诚实标一句：**若只把提示词挪个位置、其余照旧（仍走 `/draft`、仍无工具），那就是补丁**。所以「收回主流程 + 带工具」是这套方案的承重墙，不能省。

## 九、怎么验（改完只在沙箱）

1. 点「更新现状」→ 卡内出现一轮对话，注入行可见（含当前现状）；
2. 模型**调用了卡内工具**（在过程行可见）；
3. 模型调 `propose_status` → 弹**对比窗**，旧/新对照正确；
4. 点「同意」→ 落盘、影子记一行、右栏现状刷新；
5. **起草期间切卡** → 弹窗不串到别的卡；
6. 关窗 → 不落盘（草稿留在对话里，可再点）。

## 十、风险

- 改的是**主链路**（`/messages` + `message_runner` 轮首注入）——比纯前端改动面大，须**分步、每步可回退**。
- `propose_status` 进工具面 ⇒ 要动 `TOOL_REGISTRY` + `TOOL_SWITCH` + `TOOLS_TABLE_VERSION`（项目有版本纪律）。
- 与并行改动（「对话流抄 dsh」等）可能撞同一批文件——施工前先对齐。
