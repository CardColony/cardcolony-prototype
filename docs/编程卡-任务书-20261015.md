# 编程卡 · 工程任务书（2026-10-15 · v1）

> 派工性质：**施工任务书**。自给自足规格，外部 agent 照此执行，不得自由发挥。
> 依据方案：`docs/编程卡-方案-20261015.md`（同目录，先读它，以它为准）。

## 一、背景（为什么做）

把「执行」从主卡剥离：主卡是脑（拆解/判断/沉淀，无 edit），编程卡是手（承接开发任务，有 edit）。一张编程卡＝一个开发任务；完工即终态留档、静默；完工回执自动调起主卡验收。这同时落地「派生即调起」（最小开源版清单第 1 件）。

## 二、用户裁定条目（不可改，违反即作废）

1. 编程卡＝子 agent：主卡无 edit、编程卡有 edit（主卡 edit 收回属「权限管理第一次」另案，本任务**不动** sub_project 权限）。
2. **主卡写文件权限暂时保留**（tools_file 不收）。
3. 一次只执行一个任务；执行完静默不再被激活；永远留档（不可删）；主卡随时能查看过程。
4. **编程卡回报要激活主卡进行验收**（调起跑轮，非单向通知）。
5. 完工声明照单执行：模型自报 done 即收口，代码不判真假、不验产物。
6. **三冲突项裁定（用户已拍，全部按 A）**：
   - C1 指纹豁免：加类型/递增版本会打碎 7 文件的 11 个指纹断言 → **放开测试白名单，断言随版本翻新**（意图不变，仓内历次惯例）。
   - C2 search 开关：**SWITCHES 加回 `search` + 新增 `list_memory` 两常量，作为预留机关**（search 无独立工具、搜索能力仍由 web_search/fetch_web 承担；list_memory 预留）。**read_memory 仍挂 SWITCH_READ 不改挂**（改挂＝未授权的 read 侧收窄，超出本裁定）；policy.py:80-83 的「已删除」注释同步翻新为「预留机关」口径（文字追现实）；readopen:293-294 两断言翻新。**readopen:252/:287 行为断言零翻新**（语义保持「全权限不该有工具被藏」）。
   - C3 report_done 下发面：**build_tool_schemas 加第三段 card_type 闸**（coder 专属工具只对 coder 下发）；v4_positive_control 一断言翻新（readopen:252/:287 **零翻新**——report_done 挂 tools_file 后两处数学上同时成立，见 §六）。

### 块 2 · 两工具（report_done 先、create_coder_card 后）

**任务**：
- **`report_done(summary)`** 注册进 TOOL_REGISTRY（第 17 件）：
  - handler：① 读当前卡确认 `card_type=="coder"` 且 `state=="active"`（否则 err denied）② `card_store.update_card` 写 `state=completed` + front matter 加 `coder_final`（照 toolcard_final 手法，summary 原样收下）③ 影子 `## 迭代历史` 追加完工行（时间 + summary + 本会话 tool_events 里 write_file 调用数，机械统计）④ 系统发信：`card_msg.send_card_message(from=本卡, to=owner, type="coder_done", content=卡间信协议头+summary)`——owner=parent 卡（coder 的 parent 恒为主卡）。发信即被 K2 记 TRIGGERS，编程卡回合收口时 K3 调起主卡（现有链，零改）。
  - 权限：新开关 `report_done` 不设——工具只对 coder 类型下发（下发层判 card_type），执行层校验同上。schema description 写明「任务做完时调用，调完即完工、本卡静默」。
- **`create_coder_card(title, task)`** 注册（第 18 件）：
  - handler：① `policy.check(current_id, current_id, SWITCH_CREATE_CHILD...)` 复用建卡关口（照 _h_create_card 同口径）② `card_store.create_card(card_type="coder", parent=当前卡, charter=task 带 ## 使命 区头使任务落使命块)` ③ 建卡成功后 `asyncio.create_task(_routes._run_message(work_id, 新卡id, 激励文, append_user=False))`——用 `message_runner._spawn_tracked` 包（强引用防 GC，照 K3 手法）；激励文格式照 `_build_card_msg_prompt` 形态：`卡 {主卡id}（《{主卡标题}》）给你发来开发任务…任务内容：\n{task}`。**注意 create_task 在工具 handler 内、回合未收口——K3 补齐不会覆盖它（新卡无 pending 信，TRIGGERS 无它）**，此直调是首跑唯一路径，需在 handler 返回值里带 `started: true/false`。
  - 返回信封：`ok` + card_id + title + started。
- **build_tool_schemas 第三段 card_type 闸（C3）**：现两段（_filter_by_role 恒等 / _filter_by_category 按 file·web 开关）后加第三段——`coder` 专属工具（表内加常量集合 CODER_ONLY_TOOLS=("report_done",)）只对 `card_type=="coder"` 的当前卡下发，其余类型一律不出现。只做 card_type 查表，不判内容；与现两段互不触碰（同两线 R-D 纪律）。
