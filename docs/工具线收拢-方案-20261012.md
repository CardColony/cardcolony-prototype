# 工具线收拢方案（2026-10-12）

## 一、目标与已定原则

**目标**：把「工具」这条线的七件事——清单、定义、文档、权限接线、下发、执行、生老病死——从「散在多处、各写各的」收拢成「一处定义、其余全部派生」。

**已定原则（用户 2026-10-12 多轮裁定）**：

1. **工具 = 19 件**（卡片 9 · 本地文件 4 · 资料 3 · 联网 2 · 工具卡 1）。思维链六件（create_plan / plan_reorder / plan_insert / plan_remove / plan_modify / step_complete）**不算工具**，是「思维链」这条线。
2. 一个工具的全部信息**只在一处写一次**，模型看到的清单、说明书、权限判断、能不能退役，全部从这一处现算，不再手抄第二份。
3. 说明书里的工具段**从工具定义自动生成**，不再手写。
4. 工作区那批未提交改动（`src/api/tool_catalog.py` 等）是**未经允许的擅动、不作数**。本方案重新设计，不沿用其任何代码（方向虽一致，代码不接）。

## 二、设计

### 1. 唯一定义源：`TOOL_REGISTRY` + `ToolDef` 扩字段

现状 `ToolDef` 只有 `schema / handler / readonly` 三字段（B-09 版）。扩成六字段：

| 字段 | 含义 | 收拢的是哪件事 |
|---|---|---|
| `schema` | 名字 / 描述 / 参数 | **定义** + **文档**（描述就是说明书工具段的唯一来源） |
| `handler` | 执行体 | **执行** |
| `readonly` | 读 / 写 | 只读白名单从它派生 |
| `switch` | 归哪个权限开关 | **权限接线**（删掉独立的 `TOOL_SWITCH` 表） |
| `domain` | 归属域 | 说明书分组（纯分类，不参与权限判定） |
| `status` | active / retired | **生老病死**（退役 = 标 retired，留档不删行） |

七件事 → 六个字段的对应关系：清单 = `TOOL_REGISTRY` 的键，定义 = `schema`，文档 = `schema.description`，权限 = `switch`，执行 = `handler`，生老病死 = `status`。

### 2. 说明书工具段 = 从注册表生成，不再手写

删掉 `BASE_PROMPT` 里手写的「## 工具」段（`prompts.py` 的 `_BASE_PROMPT_TEXT` 里六个 `###` 域），改由一个生成函数从 `TOOL_REGISTRY` 现渲染：

- 签名从 `schema.parameters` 取；
- 描述从 `schema.description` 原文取；
- 分组从 `domain` 取。

**分界判据一句话**：这句话是「关于工具的」还是「关于系统的」。
- 关于工具（每件工具叫什么、干什么、要什么参数）→ 进生成段；
- 关于系统（错误码怎么读、卡间消息怎么办、卡片内容写入的两条路径）→ 留在 `BASE_PROMPT` 手写，因为它们是系统规矩，不是某件工具的属性。

这样「工具面」和「说明书」就**永远一致**——说明书是工具面的投影，不是第二份事实。t17 契约谎言、零文档、幽灵工具名这类漂移，从结构上不再可能发生。

### 3. 文件四件收进注册表

现状文件四件走 `file_tools.build_file_tool_schemas()` 单独注册（schema 是 lambda 延迟求值）。收拢后**直接在 `TOOL_REGISTRY` 里登记**，lambda 延迟求值保留（因为 conftest 会 monkeypatch `ALLOWED_ROOTS`，必须调用时现取，否则把真实路径冻结进 schema）。

### 4. 思维链六件分家

- `plan_tools` 维护**自己的注册表**，不再 `register_into(card_tools.TOOL_REGISTRY)`；
- `TOOL_REGISTRY` 只含 19 件工具；
- `build_tool_schemas` 只出工具；思维链的 schema 由 `plan_tools` 出；`message_runner` 下发时**合并两份**；
- `execute_tool` 只查工具；思维链调用单独路由到 `plan_tools`；
- `message_runner` 对 `step_complete` / `create_plan` 的编排特判（建板、收口、提交轮）**保留**——那是思维链机制，不是工具线，随思维链一起走。

### 5. 生老病死归口

`status=retired` 的工具不进注册表（schema、分派、只读名单同步消失），但留档进 `RETIRED_TOOLS`（记录归属域、退役版本、退役原因），不随代码删除而灭失。

## 三、改动清单（文件级）

| 文件 | 改什么 |
|---|---|
| `src/api/card_tools.py` | `ToolDef` 加 `switch/domain/status` 三字段；删 `TOOL_SWITCH` 表（改读 `ToolDef.switch`）；文件四件登记进 `TOOL_REGISTRY`；思维链六件移出；`build_tool_schemas` 过滤改读 `def_.switch`；`execute_tool` 只查工具 |
| `src/api/file_tools.py` | 注册入口统一（四件改由 `card_tools` 登记，`build_file_tool_schemas` 退役或收编） |
| `src/thinkchain/plan_tools.py` | 自己维护注册表；思维链下发 / 执行独立出口；不再 `register_into(TOOL_REGISTRY)` |
| `src/api/prompts.py` | 删手写「## 工具」段，改调生成函数；`BASE_PROMPT_VERSION` 递增 |
| `src/api/message_runner.py` | 下发合并「工具 + 思维链」两份 schema；思维链调用单独路由 |
| 新增：说明书生成函数 | 从 `TOOL_REGISTRY` 渲染工具段（签名 / 描述 / 分组） |

## 四、落地步骤

**阶段一：结构收拢（模型最终收到的工具清单逐字不变，25 件）**

1. `ToolDef` 扩字段（switch / domain / status）。
2. 文件四件收进 `TOOL_REGISTRY`。
3. 生老病死归口（`status` + `RETIRED_TOOLS`）。
4. 思维链六件分家（注册表 / 下发 / 执行独立路由）。
5. 说明书生成函数 + `BASE_PROMPT` 改调用。
6. 验证：模型视角工具清单逐字不变，全量测试绿数不降。

**阶段二：description 补写（改工具面，需版本递增）**

7. 把现状手写段里的丰富规则写进对应工具的 `schema.description`（如 `edit_card` 的三块语法、条目语法、`step_complete` 的交作业语义等）。
8. `TOOL_TABLE_VERSION` 递增（工具面变了）。
9. 验证说明书与工具面逐字一致、无残留手写工具行。

## 五、存量迁移

工具本身是代码，无存量数据要迁。要「补」的是各件工具 `schema.description` 写清楚（阶段二）——现状描述偏机械简短，收拢后它是说明书唯一来源，必须把该讲的规则讲到位。

## 六、验收判据

1. 工具清单 19 件**一处可查**（`TOOL_REGISTRY`），全仓无第二处工具清单。
2. 说明书工具段由生成函数产出，与 `schema.description` 逐字一致（grep 可验：`BASE_PROMPT` 里无手写工具行）。
3. 思维链六件不在 `TOOL_REGISTRY`，但下发仍包含（模型仍能 `create_plan`）。
4. 退役工具标 `retired` 后有留档。
5. 加 / 删一个工具**只改一处**（`TOOL_REGISTRY`）。
6. `pytest -q MOCK_LLM=1` 全绿，绿数写回。

## 七、红线

- 只动 §三 白名单文件，不碰会话底座、卡间信、凝练、toolcard、权限底座。
- 阶段一工具面**逐字不变**（name / description / parameters 零改动），`TOOL_TABLE_VERSION` 不动。
- 五铁律不动：零改平台、共存不替换、只压缩不编造、判断归模型执行归代码、schema 锁 1。
- 改前 E 盘备份；不删数据；不新增依赖。
- 5700 在跑时编辑走 worktree，重启只走 restart_safe.py。

## 八、Open Items / 待拍

1. **思维链分家是一起做还是后置**：分家涉及 `message_runner` 下发合并与执行路由，风险相对高。可以阶段一先把「工具本身的收拢」做掉（思维链暂留注册表、但标记非工具域、说明书不渲染），阶段二再真分家。本方案默认**一起做**（不彻底分家，说明书生成就得跳过思维链域，仍是半吊子）。
2. **思维链的说明书段**：分家后思维链说明是留在 `BASE_PROMPT` 手写，还是由 `plan_tools` 对称生成——本方案默认暂留手写，对称生成属后续迭代。
3. **`switch` 是否收进 `ToolDef`**：本方案默认收进（一处定义），代价是工具与权限开关耦合。若倾向保留 `TOOL_SWITCH` 独立表，则改为「独立表 + 从注册表校验完整性」，两者择一。
