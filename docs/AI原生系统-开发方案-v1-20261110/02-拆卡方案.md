## §1 拆卡规矩

### 1.1 四层

| 层 | 数量 | 在运行载体里的卡型 | 干什么 | 不干什么 |
|---|---|---|---|---|
| **根卡** | 1 | 项目根卡 | 定口径、判关口、收口待裁事项 | 不执行；不介入域内拆解、实现选择、日常催办 |
| **域卡** | 10 | 子项目卡，父为根卡 | 域内拆解与建卡、域内验收、阶段汇报 | 不亲自执行 |
| **单元卡** | 83 | 子项目卡，父为域卡 | 一个能单独验收的能力：写需求、派执行卡、收回执、单元验收 | 不亲自执行（它是管理者） |
| **执行卡** | 按需 | worker 卡、UI 卡；差事卡（验收、执笔） | 一张卡一件事 | — |

### 1.2 单元卡的边界是怎么定的

1. **一张单元卡＝一个能单独说「做到了没有」的能力**：有自己的目录归口，有绿样本也有红样本。
2. **按职责拆，不按文件拆，也不按阶段拆。** 一个职责跨几个阶段，就留在同一张卡上分段交付——卡上写明每个阶段交到哪。这样判据的归属不会随阶段换手。
3. **可以拆细，不可以合并，不可以凭空长。** 域卡在清单之外新建单元卡，必须写明它承接清单里哪张卡的哪条需求。清单里没有出处的新职责，说明方案有洞——走勘误（R§五），不自己补。
4. **探针单独成卡。** 探针的结论可能推翻选型，不能和实现卡混在一起（否则「做都做了」会变成不换的理由）。

### 1.3 单元卡的一生

1. 域卡建卡，`goal` 填本方案里这张卡的「使命」原文。
2. 第一轮只写需求草稿：把 K§6 里它那一条转写成「目标／需求／交付物／边界」四段，承接的契约条款只写指针（文件路径＋节号），不复述。**不夹带方案之外的需求。**
3. 开需求评审 → 全员通过 → 正稿。评审里职能提出的意见，凡方案已经定了的，以方案为准，意见转成勘误提请；方案没定的，按 R§四 处置。
4. 按正稿派执行卡（任务书规矩见 R§八）。
5. 收回执、验产物；不达标就下指令返工，同一件事留在同一张执行卡上。
6. 单元验收：召验收差事卡，对着正稿逐条量。证据层级按 A§11.2——强制类判据必须有整机层的证据。
7. 把通过验收的提交号交给集成归口（D2-U5）合入。
8. 写现状（做成了什么、对外接口、卡在哪），本阶段这一段完工；下一阶段的那一段到时再开。

### 1.4 执行卡怎么派

- 一张执行卡一件事；一个工作目录同一时刻只有一个任务（R§九）。
- **要在浏览器里看效果的界面活派 UI 卡，其余一切派 worker 卡。** 系统壳是要构建的前端工程：工程、构建、起预览、接数据层归 worker 卡；把页面看对、点对归 UI 卡。两张卡不同时改同一批文件。
- 执行卡不读上级卡面。它需要知道的口径、判据、边界、放行条款，必须写进任务书原文，或者指到仓库里它读得到的文件（`docs/aios/plan/`、`contracts/`）。
- 任务书只写口径与判据，不写预期的数值结果。

### 1.5 两条从 work_027 买来的规矩

**成对。** 一个能力有「发出的一方」和「受理的一方」。两方要么在同一张卡的验收里一起验，要么两张卡互列为前置、一起过集成。只交一边不算交付。
（work_027 的原样教训：读任务状态的一方早已交付并被界面用上了，写任务状态的一方在整个仓库里零调用——用户看到的状态永远是空的，而每张卡都以为自己做完了。）

**接线。** 单元验收必须在唯一的整机组合根（`cmd/colony-core`）上取证：这个能力从组合根可达，生产路径上有调用它的人。只在测试装置里成立的，不算。
（work_027 的原样教训：零件各自通过了验收，但没有一条正式路径把它们串起来——配好了也跑不起来。）

### 1.6 线怎么连

- **父子线**：建卡即有。
- **通信线**：单元卡与它所依赖的契约的归口（D1-U3）、与集成归口（D2-U5）各连一条；两张跨域的单元卡确有直接对接需要时，由双方域卡牵线。
- **依赖线**：按 K§6 每张卡的「前置」逐条画，`detail` 写清依赖的是对方的什么——哪份契约的哪个面，或哪个交付物。依赖线只表达依赖，不带通信权。
- **跨域分歧**：先在两张卡之间对齐（运行载体有对齐场就用对齐场，并拉上 D1-U3）；对不齐，再经域卡上报根卡。

### 1.7 开卡节奏与挂起

- **按阶段开卡。** 域卡只建当前阶段要动手的单元卡；标了「常设」的卡从它的起始阶段起一直在。不提前铺开。
- **前置满足即可开工**，不必等整个关口；但前置（含曳光弹的相应一段）没绿的卡不开。
- **挂起只有三种**，每一种都要写明解除条件，解除条件必须是一个看得见的事件：
  - 等基线——哪一条 B，在基线读数表里变成「到位」时解除；
  - 等裁——待裁清单的哪一条，用户裁定落面时解除；
  - 等前置——哪张卡的哪个交付物，合入集成分支时解除。
- 挂起的是那一张卡（或它的某一段），不是整个域。域卡不得以「有卡挂起」为由停下其余的卡。

## §2 装载与开跑

### 2.1 在哪跑

现在能全自动跑的是原型（5700 上的那套），所以装载步骤按它写：新开一个研发项目，自动模式。卡型对应如下；将来换到重构版上跑，对应关系在右栏。

| 本方案的叫法 | 原型里的卡型 | 重构版里的对应 |
|---|---|---|
| 根卡 | 项目根卡 | master |
| 域卡 | 子项目卡（父为根卡） | manager |
| 单元卡 | 子项目卡（父为域卡） | unit |
| 执行卡 | worker 卡、UI 卡 | 执行体节点 |
| 差事卡 | 验收卡、执笔卡 | 职能差事 |
| 评审 | 伴生评审卡；职能席位＝产品经理、技术总监、测试验收总监 | 同名机制 |

### 2.2 装载步骤（人做，一次）

1. **审定**四份方案文件；第十节（G§十）逐条给答复，R§十三 的预裁定清单逐条可否。
2. **备环境**（R§十一）：新建代码目录 `D:\AI_station\AIOS`——从 `Cardlo` 仓库按选定的提交号另行克隆，建集成分支 `aios/main`。专用 WSL 发行版 `aios-build` 不用人建，由探针 P0 建。
3. **放方案**：把四份文件原样放进代码目录的 `docs/aios/plan/`，连同一份空的 `勘误表.md`，作为集成分支上的第一个提交。此后执行卡读方案，读的就是这里。
4. **建项目**：新开一个研发项目。根卡使命填 K§3.1 原文。
5. **装规则**：项目的 `rules.md` 各分区填 R 附录给出的原文。
6. **定正稿**：根卡需求文档正稿填 K§3.2 原文（根卡的正稿由用户当面定）。
7. **职能在岗**：产品经理、技术总监、测试验收总监三席在岗（它们是需求评审的成员）。
8. **开跑**：给根卡建长目标，内容为 K§3.3 原文。

### 2.3 开跑后根卡的头几步（写死，防止一开场就铺开）

1. 建十张域卡，`goal` 填 K§5 里各域的使命原文；连好域卡之间 K§5 列出的通信线。
2. 只向 S0 有活的域下达开工：D1、D2、D3、D5、D6、D7、D9。D4、D8、D10 的域卡此时只写域级需求草稿、开评审，不建单元卡。
3. 等各域的 S0 阶段汇报与 D9 的 G0 关口报告。之后每个阶段照 K§4.4 走。

## §3 根卡

### 3.1 使命（原文，建项目时填）

> 造出 AI OS v1：一个给普通用户日常使用 AI 应用的通用操作系统——Linux 打底，卡网络的运行机制沉在系统里，CardColony 是机上的开发工具——交付可启动的整机镜像，并以十一条整机验收场景在发行镜像上全部通过为完成。方案依据是代码目录 `docs/aios/plan/` 下的四份文件与勘误表。

### 3.2 需求文档正稿（原文，用户当面定）

> **目标**
> 照抄使命。
>
> **需求**
> 1. 范围以总纲第四节为准：「做」的十三项全部做到，「不做」的一项不做，「留缝」的不堵死。
> 2. 架构以《01 系统架构设计》为准；三条根原则（总纲第三节）不得违反。
> 3. 按总纲第七节的六个阶段推进，关口 G0–G5 逐个放行；从 S1 出口起，集成分支上任何时候都造得出一台能开机的机器。
> 4. 十个域按《02 拆卡方案》§5 建立；各域按 §6 的清单拆单元卡。清单之外新建单元卡，须写明承接清单里哪张卡的哪条需求。
> 5. 全树遵守项目规则（即《03 规范与约束》）。
> 6. CardColony 要为本系统做的事，按总纲 6.2 的三类分别处置：甲类不代做，乙类逐件记账，丙类归开发工具产品线。
> 7. 无人值守时的裁定按规则第四节的四类办；「待裁清单」与「待追认清单」常设在本卡现状块。
>
> **交付物**
> 1. 开发镜像与发行镜像；构建它们的一条命令。
> 2. 总纲第二节「做完以后你手里有什么」逐项。
> 3. 六份关口报告（G0–G5）；红样本账本；选型表定稿；基线读数表；融合补件账本；勘误表。
>
> **边界**
> 1. 总纲第四节「不做」清单。
> 2. 规则第十一节的环境红线：不动 Windows 宿主设置、不动现有 WSL 发行版、不重启或停止 5700 服务、不在 `D:\AI_station\Cardlo` 及其现有工作树里动手、不改原型仓库。
> 3. 不改方案原文；改动只经勘误表。
> 4. 本卡不亲自执行：不跑构建、不跑测试、不写代码、不改交付物。本卡亲手产出的东西不计为交付。
>
> **验收**
> 总纲第九节的十一条场景在发行镜像上全部通过，证据由整机验收线独立取得；G5 的其余条件满足。
>
> **判断权**
> 本卡裁：跨域边界与取舍、关口放行、权限内的勘误。本卡不裁：域内事项。须用户裁：规则第四节的第四类事项。

### 3.3 长目标（原文，开跑时建）

> 按方案把项目推进到 G5 放行。每个阶段：向本阶段有活的域下达开工 → 等各域的阶段汇报 → 收整机验收线的关口报告 → 对照关口条件逐条判，放行或列出未过项 → 进入下一阶段。遇到须用户裁的事项，登记进待裁清单并让其余工作继续，不停下整棵树。当前阶段：S0。

### 3.4 根卡现状块只放这些

| 栏 | 内容 | 不放什么 |
|---|---|---|
| 阶段 | 当前阶段；已放行的关口与各自的报告指针 | 各域的进度读数（以各域现状块为准，不复制） |

## §4 探针、曳光弹与关口

### 4.1 十三个探针（S0）

探针的规矩：代码放 `spike/aios/`，不进生产路径；每个探针交一份报告——做法、命令、原始输出、绿与红各至少一例、结论。**「不成立」是合格的结论**：照撤退条件换，并记进选型表。两种修法都试过仍不成立，才算触发撤退。

| 编号 | 要证实什么 | 归口 | 绿 | 红（必须失败的对照） |
|---|---|---|---|---|
| **P0** 建造环境 | 能新建专用 WSL 发行版；里面 systemd 可用；硬件虚拟化可不可用（两种结论都如实记）；Windows 侧提交 → 发行版内按提交号取出并构建，往返成立；执行卡能驱动发行版里的命令并拿回原始输出 | D2-U1 | 一个空提交走完往返；一条命令的原始输出回到执行卡 | 在发行版里对取出的副本做的改动，不会回到 Windows 侧的代码目录（副本只读用） |
| **P1** 镜像与分区 | mkosi 出带分区的镜像；虚拟机 UEFI 启动；系统分区只读；首启建立并扩展数据分区；`/etc`、`/var` 两个候选做法各实测 | D2-U1 | 启动到登录提示；重启后数据分区里的文件还在 | 运行期往系统分区写文件——失败 |
| **P2** 整机测试装置 | 虚拟机的启动、断电、设备热插拔、断开网络链路、截图、远程驱动界面都能由脚本完成；量出跑一轮场景的时间量级 | D9-U1 | 脚本完成一轮「启动—注入—截图—断电—再启动」 | 断电后未落盘的写入不在——证明断电是真的 |
| **P3** 沙箱 | systemd 瞬态单元能接过核心进程递来的标准输入输出；默认无权的各项属性生效；系统容器层里同样成立 | D3-U1 | 单元里的程序经管道与外面对话 | 联网、读指定目录之外的文件、提权、内存超限、任务数超限——逐项失败；并各有「放开那一项时成功」的对照 |
| **P4** 壳呈现 | 单应用全屏合成器加浏览器内核，在没有硬件加速的虚拟机里稳定显示，可远程驱动 | D7-U1 | 全屏显示一页并响应点击 | 页面崩溃后会话被拉起，不掉到命令行 |
| **P5** Linux 取证 | 重构版 CardColony 在 Linux 上构建、全量测试、崩溃与断电后的持久性（给基线 B8 取证） | D1-U2 | 构建成功；测试原始输出在盘；kill -9 与断电后已确认的写都在 | 确认之前断电的那一笔，重启后不得读成「已确认」 |
| **P6** 凭据存放 | systemd 凭据在没有 TPM 与带虚拟 TPM 两种虚拟机里的加密存取 | D5-U1 | 存入、重启、取出一致 | 别的系统用户读不到；数据分区上找不到明文 |
| **P7** 本地模型 | llama.cpp 服务端在镜像里跑一个小型开放权重模型；CardColony 的 OpenAI 兼容适配器接得上；量出内存量级 | D5-U1 | 经适配器完成一次调用 | 没有网络时照样完成（证明没有偷偷外连） |
| **P8** 升级回退 | 写入另一份系统 → 重启 → 确认或不确认 → 自动回退 | D2-U1 | 确认后留在新系统 | 不确认时自动回到旧系统；数据分区不变 |
| **P9** 卷配额 | ext4 项目配额在镜像的内核上生效 | D6-U1 | 额度内写入成功 | 超额写入失败，且不影响另一个配额号下的写入 |
| **P10** 宿主信号 | 各主题的信号在虚拟机里能不能造出来、采得到：设备插拔、链路通断、存储余量、内存压力；电源与发热在虚拟机里行不行如实记 | D3-U1 | 每类至少采到一次 | 没发生变化时不产生信号 |
| **P11** 串口设备 | 虚拟串口接进虚拟机：设备出现事件、读、写 | D3-U1 | 外面写一行，里面读到；反向亦然 | 拔掉后读写失败并有设备移除事件 |
| **P12** 界面隔离 | 应用的前端包跑在独立来源的沙箱内嵌页里，只能经消息桥与外面说话 | D7-U1 | 经桥收发一条消息 | 发网络请求、读外层页面、把外层导航走——逐项失败 |

### 4.2 曳光弹（S1）：最窄的一条贯穿整机的真实链路

分四段，一段叠一段，用同一个最小应用（`hello`，A§6·C1 的例子，D8-U4 交付）。每一段都在虚拟机里、在真实镜像上、经唯一的整机组合根取证。已经绿的段，之后任何一次合入都不许让它熄掉（D2-U5）。

**T-0a 地基**——只用到 CardColony 已经冻结并验收过的部分，不等基线缺口。
1. 开发镜像在虚拟机里启动：系统分区只读，数据分区就绪。
2. systemd 拉起特权手臂与核心进程；核心进程打开事件日志并重建。
3. 核心进程经特权手臂在沙箱里拉起一个测试用的程序节点；节点经现有的参与者协议握手、发一条写请求；闸受理，事件落盘。
4. 系统壳会话起来，占位主屏上显示由这条事件派生的一行。
5. 直接断电 → 再开机：那条事件还在，那一行还在；节点能再写一条。

涉及：D2-U2、D2-U3、D3-U2、D3-U3、D7-U3、D9-U1。
红：沙箱里的节点联网、读聚落存储——失败；不带凭据的拉起请求——被特权手臂拒绝。

**T-0b 应用骨架**——等基线 B6、B7。
1. 用命令行把 `hello` 包装到这台虚拟机上：校验 → 同意 → 实例化成一个项目。
2. 定时触发到点 → 落成事件 → 策略条件成立 → 调用程序节点 → 节点在沙箱里算完交结果 → 写进记录集。
3. 系统壳里 `hello` 的页面上多出一行，不用刷新。
4. 停用 → 不再有新行；启动 → 恢复。重启虚拟机 → 不做任何操作，它接着干。

涉及：D4-U1 至 D4-U6、D6-U2、D6-U4、D7-U5、D8-U1、D8-U4、D1-U4、D2-U4。
红：没申请后台运行的同一个包，重启后自己跑了；停用后仍有新行；改坏的包装上了。

**T-0c 模型**——等基线 B6；用到 B9。
1. `hello` 的程序节点在处理中发起一次模型调用（槽位绑在回放模型上）→ 结果回到节点 → 写进记录。
2. 这次调用的用量落成事件、记进应用的额度；把额度调成零 → 下一次调用被延后，应用出现「受限」读数。

涉及：D5-U2、D5-U3、D5-U4、D6-U5。
红：没声明槽位的节点发起模型调用——被拒；只许本机的槽位绑到机器外的模型——被拒。

**T-0d 智能体**——等基线 B1、B2、B3。
1. 在 `hello` 的页面上对入口智能体说一句话 → 它跑一轮（回放模型）→ 回复出现在页面上。
2. 让它记一件事 → 它用工具写进记录集 → 列表多一行。
3. 停用应用时它正在途中的那一轮按停止链处理，界面如实显示。

涉及：D5-U7、D7-U11。
红：智能体调用清单没给它的工具——被拒。

## §5 十个域

每个域给出：使命（建域卡时 `goal` 的原文）、管什么与不管什么、归口目录、单元卡一览。域卡的需求草稿由这一节加上它名下各单元卡的条目转写而成。

### D1 契约线

> **使命**：让跨域接口只有一份、而且机器可核——把方案里的十二份契约落成仓库里唯一的冻结版本，守住冻结与融合保护区，把重构版 CardColony 的基线读清楚并持续对账。

- **管**：契约的转写、冻结与变更；登记表与启动期自检；融合补件的守门；基线的实读与同步；方案副本、勘误表、选型表。
- **不管**：任何执行器的实现；内容上的裁定（裁的是根卡或用户，本域只管通道与落表）；CardColony 自己没收口的事（甲类）。
- **归口目录**：`contracts/`、`docs/aios/plan/`、`aios/registry/`，以及 `docs/aios/` 下的基线读数表、融合面清单、融合补件账本、选型表。
- **单元卡**：U1 基线实读与融合面清单｜U2 Linux 取证｜U3 契约转写与冻结｜U4 登记表与启动期自检｜U5 融合补件、保护区与基线同步（常设）｜U6 方案副本、勘误与变更通道（常设）

### D2 整机线

> **使命**：让项目在任何时候都有一台能开机的机器——镜像、开机序列、唯一的整机组合根、集成归口、系统升级与回退、安装到磁盘、发行件。

- **管**：镜像怎么造；三个系统进程怎么起；所有能力从哪里接进系统；提交怎么合入；系统怎么升级、回退、安装、恢复出厂、发行。
- **不管**：系统层各项能力本身；替别的域修代码。
- **归口目录**：`image/`、`cmd/colony-core/`、`aios/syswork/`。
- **单元卡**：U1 建造环境与镜像探针｜U2 镜像骨架｜U3 整机组合根与开机序列（常设）｜U4 系统 work｜U5 集成归口（常设）｜U6 系统升级与回退｜U7 关机、断电与恢复｜U8 安装到本机磁盘与恢复出厂｜U9 发行配置与发行件

### D3 宿主融合线

> **使命**：把卡网络的决定变成 Linux 的执行与强制，把机器上发生的事变成卡网络里的事实——只执行、只转述，不做判断。

- **管**：特权手臂；沙箱；宿主事实的采集；宿主动作的执行；设备接入；系统的网络出入口；可移动存储的系统通道。
- **不管**：「该不该」——谁有什么授权、配额是多少，由 D6 决定，本域只负责强制住。
- **归口目录**：`cmd/colony-hostd/`、`aios/sandbox/`、`aios/host/`、`sysnodes/`（取数、入站网关、串口驱动）。
- **单元卡**：U1 宿主探针｜U2 特权手臂｜U3 沙箱运行体驱动｜U4 宿主事实｜U5 宿主动作与网络配置｜U6 设备作为节点·串口类｜U7 系统取数节点｜U8 入站网关｜U9 系统文件通道

- **管**：包与清单；应用的生命周期；程序节点怎么被调用；触发怎么落点；策略怎么装载。

- **单元卡**：U1 包格式、校验器与签名｜U2 实例化器｜U3 应用管理器｜U4 程序节点调度｜U5 触发路由｜U6 策略装载｜U7 应用升级｜U8 卸载、导出与导入

## §6 单元卡清单

读法：每张卡的「使命」是建卡时 `goal` 的原文。「依据」里 A＝《01 系统架构设计》。「判据」只写这张卡特有的；凡写「见 A§6·Cn 判据」的，该契约的判据全部算进来。标了阶段分段的卡，写明了每一段交到哪。

### D1 契约线

#### D1-U1 基线实读与融合面清单 〔S0；之后随上游变化复读〕
- **使命**：把重构版 CardColony 在选定提交上实际是什么样读清楚——十条基线逐条给读数，本系统对它的每条预期需求逐条定归类。
- **依据**：G§6.1、G§6.2；A§13。
- **要做到**
  1. 记下基线提交号（装载时选定的那个）。
  2. B1–B10 逐条实读，结论三选一：到位／部分／未到位。每条给可寻址的证据——文件与行号，或命令与原始输出。读不出来的写「未核」，不写推断。
  3. A§13.2 的预期需求逐条核：对应的扩展面在不在、真实的名字与路径是什么 → 归类为甲、乙、丙或「不需要补件」。
  4. A§13.1 列的每一项可复用面，给出入口路径。
  5. 上游关闭一条基线缺口时，复读那一条并更新读数表。复读由这件事触发，不定期做。
- **交付物**：`docs/aios/基线读数表.md`、`docs/aios/融合面清单.md`。
- **判据**：绿——任取一条读数，第三方照证据能复核出同一结论。红——把代码注释、文档自述或卡面上的说法当成读数依据的，该条不合格（R§六）。
- **前置**：无。
- **边界**：只读不改；不评价 CardColony 的设计好坏。

#### D1-U2 Linux 取证（探针 P5）〔S0〕
- **使命**：给基线 B8 取证——重构版 CardColony 在 Linux 上能不能构建、测试过不过、崩溃和断电之后已确认的写丢不丢。
- **依据**：G§6.1 的 B8；K§4.1 的 P5。

  1. 请求类型是闭集，每种有模式定义：启停沙箱单元；建删应用卷并设配额号；订阅宿主信号；各项宿主动作；挂卸可移动存储。**没有「执行任意命令」这一类。**
  2. 套接字只许核心进程的系统身份连接。
  3. 凡会产生效果的请求必须带「已受理意图」的凭据；同一个交接号再来，只回执、不再动手。凭据的构造与验法随 C4 冻结。
  4. 它不写事件、不持身份、不做判断。它做了什么，由核心进程记成事件。
  5. 它自己崩溃由 systemd 拉起；拉起后与核心进程对账（现有单元清单对租约）。
  - S1 段交到：启停沙箱单元一类请求。其余请求类型随各自的单元卡在 S2 加入，每加一类登记一次。
- **交付物**：`cmd/colony-hostd/`、请求类型表。
- **判据**：绿——合法请求执行并回执。红——不带凭据的请求被拒；同一交接号第二次不再动手；别的系统身份连套接字被拒；表外的请求类型被拒。
- **前置**：D1-U3（C3、C4）；P3。
- **边界**：不解析业务载荷；不缓存授权。

#### D3-U3 沙箱运行体驱动 〔S1 段：最小沙箱；S2 段：全量〕
- **使命**：让每个程序节点的运行体都装在一个默认什么都没有的 Linux 沙箱里，能力只来自授权。
- **依据**：A§6·C3；A§3。
- **要做到**
  1. 作为一种运行体承载方式登记：一个运行体一个瞬态单元，标准输入输出是核心进程递过来的管道。
  2. 默认无权：无网络、无设备、系统只读、只看得见自己的包与卷、独立的动态系统身份、禁止提权、系统调用受限。
  3. 能力映射是一张数据表（A§6·C3 规则 4）。
  4. 生命周期只听租约；单元不带自动重启；退出产生监督事件。
  5. 授权被撤销：停掉受影响的运行体，按新授权重新拉起。
  6. 对账只在两个时机：单元启动时；授权变更事件到来时。
  - S1 段交到：第 1、2、4 条。S2 段：其余，加上每个应用一个切片、孤儿单元的识别。
- **交付物**：`aios/sandbox/`、能力映射表。
- **判据**：见 A§6·C3 判据。每条红样本在整机层判红，并各有「有授权时成功」的对照。
- **前置**：D3-U2；融合补件「运行体的承载方式可在核心之外登记」（若 D1-U1 判定需要）。
- **边界**：授权是什么由 D6 决定，本卡只把它强制住。

#### D3-U4 宿主事实 〔S2〕
- **使命**：机器上发生的事，成为卡网络里的事实——写进事件日志之后才算。
- **依据**：A§6·C4「宿主事实」。
- **要做到**
  1. 主题表（启动与关机、电源、网络、存储、发热与内存压力、设备、时间）；每个主题标「仅本地」或「可出境」，默认仅本地。
  2. 分档规则是数据。
  3. 特权手臂只转述信号；核心一侧的适配器把它写成事实。
  4. 每次开机补一条当前读数作基线。
  5. 沿线投递：应用没有通到相应系统实体的线，就收不到。
- **交付物**：`aios/host/facts/`、主题表与分档表。
- **判据**：见 A§6·C4 判据。另红——同一次状态变化产生多条重复事实。
- **前置**：D3-U2、D2-U4；P10。

#### D3-U5 宿主动作与网络配置 〔S2〕
- **使命**：对机器做的事，都是经闸的动作；应用想动机器，每次都要用户点头。
- **依据**：A§6·C4「宿主动作」；A§6·C2 动作目录「宿主」一行。
- **要做到**
  1. 关机、重启、设置时间、应用系统更新、恢复出厂，各一个执行器，登记进动作目录。
  2. 网络配置：列出可用网络、连接、断开（有线与无线）。无线密码进凭据库，不进事件。
  3. 用户亲手发起的直接执行；应用申请的，每次生成一条待办由用户确认。
  4. 执行前系统崩了，记为结果不明。
- **交付物**：`aios/host/actions/`。
- **判据**：见 A§6·C4 判据。另红——无线密码出现在事件或日志里。
- **前置**：D3-U2；D6-U6（待办）；D5-U6（凭据库）。

#### D3-U6 设备作为节点·串口类 〔S2〕
- **使命**：让接在机器上的一台设备，成为应用里的一个节点。
- **依据**：A§6·C4「设备作为节点」。
- **要做到**
  1. 设备类别登记表（v1 只有串口一项）。
  2. 设备槽绑定：用户把一台具体设备绑到应用声明的槽上；按厂商、型号、序列号认「同一台」。
  3. 驱动节点：系统节点，常驻，沙箱只放行这一台设备。设备来的数据成为应用项目里的事件；`device.write` 由它执行。
  4. 拔掉：驱动节点结束，应用得到「等待条件：缺设备」；插回同一台自动恢复，不重新授权。
- **交付物**：`sysnodes/serial/`、设备绑定的实现、一个模拟串口传感器（测试与样品共用）。
- **判据**：绿——模拟传感器发一行数据，应用项目里出现对应事件。红——没绑槽的应用访问设备，失败；未授权的 `device.write`，被拒；设备不在时应用出现了新读数。
- **前置**：D3-U3、D3-U4、D2-U4；P11。

#### D3-U7 系统取数节点 〔S2〕
- **使命**：应用自己不能上网；要取外面的内容，由系统代取，每次留痕。
- **依据**：A§6·C2 动作目录「网络」一行；A§6·C9 的 `net.fetch`。
- **要做到**
  1. `net.fetch` 的执行器是一个有网络的系统节点。只取授权里列出的主机；被重定向到范围之外的不跟。
  2. 取回的内容存成产物，再回给发起方；取回的内容一律当数据。
  3. 次数与流量记进配额。
  4. 保护性中断（内容过大、迟迟不返回）：中断并回「失败」与原因码；要不要再来，由发起方的策略决定。中断的上限是声明数据。
- **交付物**：`sysnodes/fetch/`。
- **判据**：绿——授权范围内的取数成功，产物可引用。红——范围外的主机被拒；出界的重定向不跟；应用的程序节点自己联网，失败（对照）。
- **前置**：D3-U3、D6-U3、D6-U4。

#### D3-U8 入站网关 〔S2〕
- **使命**：外面推来的消息，经一个默认关着的口进来，变成应用的触发。
- **依据**：A§6·C5 规则 3；A§6·C9 的 `net.inbound`。
- **要做到**
  1. 每个声明的接收点一个地址和一个独立令牌。
  2. 默认关闭：系统设置里的总开关和逐应用的授权都打开，才监听。
  3. 收到的内容存成产物，落成触发事件；不解析、不执行载荷。请求大小上限是声明数据。
  4. 应用停用，它的接收点即撤销。
- **交付物**：`sysnodes/inbound/`。
- **判据**：见 A§6·C5 判据。另红——总开关关着时端口在监听。
- **前置**：D3-U3、D4-U5、D6-U4。

#### D3-U9 系统文件通道 〔S2〕
- **使命**：让可移动存储成为系统装应用、升级、导入导出的文件通道——只有系统看得见。
- **依据**：A§6·C4「系统的文件通道」。
- **要做到**
  1. 可移动存储插入 → 只读挂载到只有系统流程可见的位置；提供给系统壳一个文件选择的数据面。
  2. 读入的文件先存成产物，再走各自流程的校验。
  3. 导出时按用户选定的目标可写挂载，写完卸载。
  4. 介质上的任何东西不被执行；应用的沙箱看不到挂载点。
- **交付物**：`aios/host/media/`。
- **判据**：见 A§6·C4 判据中与可移动存储有关的三条。
- **前置**：D3-U2、D3-U4、D6-U3。

### D4 应用模型线

#### D4-U1 包格式、校验器与签名 〔S1〕
- **使命**：一个文件说清一个应用；不合格的包装不上，而且说得出哪里不合格。
- **依据**：A§6·C1。
- **要做到**
  1. 包容器与固定布局；确定性打包——同样的内容打出同样的字节。
  2. 三层校验（结构、引用、合规）；每条拒绝带稳定的原因码，并指到清单里的位置。
  3. 签名与验签；信任四态：发布者已受信任／签名有效但发布者未知／未签名／本机制作。
  4. 节点模板文件的两层校验。
  5. 校验器是一个库：命令行、安装、封装用的是同一份代码。
  6. 自测用的绿样本与红样本（D9 另有独立的坏包集，两套互不替代）。
- **交付物**：`aios/pkg/`。
- **判据**：见 A§6·C1 判据（「封装往返」一条归 D10-U6）。
- **前置**：D1-U3。

#### D4-U2 实例化器 〔S1〕
- **使命**：把「清单＋用户批下来的东西」变成一份确定的动作计划——安装、升级、工作区，用的都是它。
- **依据**：A§7 链路三第 4 步；A§5.6。
- **要做到**
  1. 纯函数。输入：清单、用户批准的授权与配额、安装参数、槽位与设备的绑定结果。输出：一份有序的意图计划——建项目、建实体、建线、登记策略与工具面、建记录集、建卷、设预算、写种子数据、武装触发。
  2. 同样的输入得到同样的计划。
  3. 能求差：给新旧两份清单，得出增、删、改的计划。
  4. 它不执行，不写事件。
- **交付物**：`aios/instantiate/`。
- **判据**：绿——A§6·C1 例子清单的计划逐条可读，重算一致。红——清单用到了一项没被批准的必需授权：不出计划，并指出是哪一项。
- **前置**：D4-U1。

#### D4-U3 应用管理器 〔S1 段：安装、启动、停用；S2 段：全量〕
- **使命**：管住一个应用从装上到移除的一生；任何时候它的状态都如实、可查。
- **依据**：A§5.4；A§7 链路三、链路六。
- **要做到**
  1. 主状态是事件的投影，没有可以直接写的状态字段。
  2. 按实例化器的计划逐条发起经闸的意图。装到一半崩了：重启后接着装完，或者干净撤回——不留半个应用。同一个包装两次，第二次没有副作用。
  3. 叠加读数（等待条件、受限、出错）带原因码，可以同时有多条。
  4. 停用＝解除全部触发＋项目级软停；读数里有「还有几个在收尾」。
  5. 强制停止＝撤销全部租约；智能体部分走停止链，硬停不可用时读数里如实写「智能体部分只能软停」。
  6. 状态词由本卡给出，界面不拼。
- **交付物**：`aios/appmgr/`。
- **判据**：绿——链路三从头走通。红——在安装的每一步之后各注入一次崩溃，重启后都不得出现半个应用；停用之后有新的触发落点或新的意图被受理。
- **前置**：D4-U2、D6-U4、D1-U4；基线 B6。

#### D4-U4 程序节点调度 〔S1 段：一次性节点；S2 段：全量〕
- **使命**：让程序节点被正确地叫起来、拿到该拿的输入、交回结果——不多给它一样东西。
- **依据**：A§6·C2 ①；A§6·C7 规则 2、4。
- **要做到**
  1. `node.invoke`、`node.start`、`node.stop` 的执行器；一次性与常驻两种工作方式。
  2. 调用信封：调用号、触发来源、输入。输入绑定只有四种来源，过了权限与划界检查才备好递给节点。
  3. 节点放进输出目录的文件：先存成产物，再提交引用它的事件。
  4. 没交结果就退出，算失败；调用号对不上的结果不收。
  5. 节点自己发起的动作，结果回到这个节点。
  6. 监督按清单的声明执行；不再重启的，应用得到「出错」读数。
  - S1 段交到：一次性节点，输入来自触发事件。
- **交付物**：`aios/nodesched/`。
- **判据**：绿——同一个节点在开发模式和沙箱里，同样的输入得到同样的写请求。红——节点拿到了它没声明的输入；甲应用的策略调起了乙应用的节点。
- **前置**：D3-U3、D4-U2、D1-U4；基线 B6。

#### D4-U5 触发路由 〔S1 段：定时；S2 段：全量〕
- **使命**：把「什么让应用动起来」统一成一件事——一条落在应用项目里的事件。
- **依据**：A§6·C5。
- **要做到**
  1. 四类来源统一落成事件；事件里记着来源。
  2. 定时：间隔或日历式时刻；错过了按声明处理（跳过或补一次）；时钟被调整后不重复落点。定时源是系统 work 里的一个实体。
  3. 入站（接 D3-U8）、宿主与设备（接 D3-U4、D3-U6，沿线投递）。
  4. 武装与解除跟着应用的启动与停用走；开机时，重建完成之后才重新武装。
  5. 应用自己声明的事件类型，在安装时登记。
- **交付物**：`aios/trigger/`。
- **判据**：见 A§6·C5 判据。
- **前置**：D4-U3、D2-U4。

#### D4-U6 策略装载 〔S1 段：随安装登记；S2 段：全量〕
- **使命**：让应用的 harness 策略跟着应用装上、换版、卸下；策略只做声明，不变成编程语言。
- **依据**：A§5.2「harness 不是编程语言」；A§6·C5 规则 1。
- **要做到**
  1. 应用的策略集随安装登记、随升级换版、随卸载注销。
  2. 策略能发起的动作，只能是动作目录里、而且这个应用被授权的那些。
  3. 出现循环、赋值、内嵌脚本的策略，拒。
  4. 策略里的取值只来自触发事件的字段与安装参数。
  - S1 段交到：登记一条「事件 → 调用程序节点」的策略。
- **交付物**：策略装载的实现（在 `aios/appmgr/` 内）、策略校验规则。
- **判据**：红——带脚本的策略被拒；策略发起未被授权的动作被拒。
- **前置**：D4-U3；基线 B7、B6。

#### D4-U7 应用升级 〔S2〕
- **使命**：应用能升级；升不上去就回到旧版，数据不丢。
- **依据**：A§7 链路七；A§6·C9 规则 5。
- **要做到**
  1. 暂存并校验新包 → 新旧清单求差 → 新增的授权重新问 → 停用旧版 → 按 `upgrade` 的声明迁数据 → 按计划调整实体、线、策略（被移除的实体归档，不直接抹掉）→ 启动新版。
  2. 任何一步失败，回到旧版可运行的状态。
  3. 只接受清单声明「能从它升上来」的旧版本。
- **交付物**：升级流程的实现、一组新旧版本的样例包。
- **判据**：绿——升级后数据还在，新功能可用。红——新增的授权没经同意就生效；迁移途中崩溃后回不到旧版。
- **前置**：D4-U3、D4-U2、D6-U2。

#### D4-U8 卸载、导出与导入 〔S2 段：卸载；S3 段：导出与导入〕
- **使命**：应用能干净地卸掉；它的数据能整包带走，在另一台机器上接着用。
- **依据**：A§6·C7 规则 6–7；A§7 链路九。
- **要做到**
  1. 卸载时用户三选一：留着数据／导出后删除／直接删除。卸载之后，这个应用的沙箱单元、线、触发、授权都不再存在或不再有效。
  2. 导出包：包文件、全部记录集的当前内容、被引用的产物、清单声明要带的卷、对话的文字稿；用设备密钥签名；不含凭据。
  3. 导入：在目标机器上装同一个包，再用一条导入动作把记录与产物写进新实例（经闸，记明来源）。授权不跟着走，导入时重新同意。
- **交付物**：卸载、导出、导入的实现。
- **判据**：见 A§6·C7 判据中导出导入的两条。另红——卸载后还有残留的单元、线、触发或授权。
- **前置**：D4-U3、D6-U2、D6-U3、D3-U9。

### D5 模型与智能体线

- **判据**：见 K§4.1 相应行。

#### D5-U2 回放模型 〔S1〕
- **使命**：给全树一个「同样的输入给同样的输出」的模型端点，让判据可以复核。
- **依据**：G§十 第 8 条；R§十。
- **要做到**
  1. 一个 OpenAI 兼容的端点：按请求内容匹配录好的应答。匹配规则写明；匹配不上就明确报错，不现编。
  2. 能回放带工具调用的应答，也能回放失败（限流、超时、畸形应答）。
  3. 录制工具：从真实模型录一段，入库前脱敏——不得含凭据与真实用户内容。

- **判据**：绿——同一个请求两次的应答逐字节相同。红——没录过的请求得到明确错误，而不是一段猜出来的回答。

- **边界**：它是测试设施，不进发行镜像。

  4. 绑定结果是事件；用户可改，改了对之后的新工作生效。候选被移走，相关槽位落到「等待条件：缺模型」。

#### D5-U4 模型调用动作 〔S1 段：程序节点发起；S2 段：界面发起与失败分类〕
- **使命**：让不带智能体的应用也能用模型——和智能体走同一个入口、查同一处额度、记同一本账。
- **依据**：A§6·C6 规则 5–6；A§6·C2 动作目录「模型调用」一行。
- **要做到**
  1. `model.call` 的执行器。能发起的只有两种：引用了槽位的程序节点；界面上清单声明过的调用。

  3. 经 CardColony 的模型适配器调用；一次调用回一个完整结果；可以被延后（模型在加载、算力排队）——延后是六种合法结果之一，如实带原因，不是失败、不按失败重试。

#### D7-U6 前端包宿主与桥 〔S2〕

#### D7-U7 安装与同意流程 〔S2〕

### D8 开发者工具链线

#### D8-U6 样品·随手记 〔S3〕
- **使命**：做出一个不带智能体的普通 AI 应用，证明「AI 应用不一定是聊天，也不一定是组织」。
- **依据**：G§十 第 2 条；A§5.2「组织不是门槛」。
- **要做到**

  4. 清单里没有智能体节点。
  5. 没有可用的本机模型时：照样能记；自动整理的部分如实显示「等待模型」。

#### D8-U7 样品·设备管家 〔S3｜等基线 B1–B3〕
- **使命**：做出一个智能体组织型的应用，盯着这台机器自己——证明大小模型一起干活、宿主事件能叫醒智能体、动机器之前先问人。
- **依据**：G§十 第 2 条；A§6·C4、C6。
- **要做到**
  1. 订阅宿主事实：电源、存储、发热与内存压力、网络、设备插拔——各自申请授权。
  2. 两个智能体节点。「分诊」：反射档，只许本机，判断这件事值不值得打扰用户。「解释」：工作档，可出境（所以申请 `models.remote`），在需要时写一段人话的说明与建议；它只经一条放行线拿到分诊交来的摘要。
  3. 一个记录集记下发生过的事与处置（仅本地）。
  4. 需要动机器时（存储将满建议清理、电量很低建议关机）申请宿主动作——每次生成待办，由用户确认。
  5. 界面用声明式组件：状态磁贴、事件列表、待办。
  6. 断网或没配机器外的模型时：分诊照常；解释的部分如实显示受阻。
- **交付物**：`apps/steward/`。
- **判据**：绿——在虚拟机里注入「存储将满」→ 分诊 → 通知；断网时分诊照常。红——没经确认就执行了宿主动作；没经放行，仅本地的内容到了「解释」手里。
- **前置**：D5-U7、D5-U8、D3-U4、D3-U5、D6-U6；基线 B1–B3。

#### D8-U8 样品·传感器看板 〔S3〕
- **使命**：做出一个把硬件当节点的应用。
- **依据**：G§十 第 2 条；A§6·C4「设备作为节点」。
- **要做到**
  1. 一个设备槽（串口类）；绑定后，设备来的每一行数据落成事件。
  2. 策略把事件交给一个程序节点解析成读数，写进记录集。
  3. 界面（声明式）：最新读数的磁贴、历史列表、一个向设备下指令的按钮（需授权）。
  4. 读数越过用户设的阈值时通知。
  5. 设备拔掉：界面如实显示「缺设备」，不出现新读数；插回同一台自动恢复。
- **交付物**：`apps/sensor/`（模拟传感器由 D3-U6 提供）。
- **判据**：绿——模拟传感器发数据，界面出现读数；按下按钮，模拟传感器收到指令。红——设备不在时出现了新读数。
- **前置**：D3-U6、D4-U4、D6-U2、D7-U5。

### D9 整机验收线

#### D9-U1 整机测试装置（P2）〔S0 段：探针；S1 段：供各卡使用〕
- **使命**：造出「在虚拟机里对真实镜像做任何事、并留下证据」的装置。

- **判据**：见 K§4.1 的 P2 行。另绿——别的卡照说明用它跑通一次，并拿到证据包。

#### D9-U2 测试槽 〔S0 起常设〕
- **使命**：让镜像构建和虚拟机排着队用，不把这台机器挤垮。
- **依据**：A§12 第 5 条。
- **要做到**
  1. 一个排队入口：谁要造镜像、起虚拟机，都经它。同时进行的上限是声明数据（缺省：一个构建、两台虚拟机）。
  2. 一个占用什么时候算结束：占着它的进程不在了。不是「过了多久」。
  3. 现在谁占着、谁排着，可查。
  4. 上限按 P2、P7 量出的量级调整；改动留记录。
- **交付物**：`tools/aios/slot/`。
- **判据**：绿——三个同时来的请求，第三个排队，直到前面有一个结束。红——绕过它直接起虚拟机取得的结果，合入闸与关口都不认。
- **前置**：P0。

#### D9-U3 场景套件 〔S1 起，随阶段补齐〕
- **使命**：把十一条整机验收场景做成能在虚拟机里一键重跑的套件。
- **依据**：G§九。
- **要做到**：每条场景给出步骤、绿样本、红样本，并自动出证据包。各条的取证办法定为：

| 场景 | 怎么取证（绿） | 必须失败的对照（红） |
|---|---|---|
| **E1** | 一台新虚拟机从镜像启动 → 走向导（全跳过一遍，全填一遍）→ 主屏；截图序列里没有命令行界面 | 向导中途断电再开机：重新进向导或进主屏，不卡在半截 |
| **E2** | 从可移动存储选一个样品包 → 同意 → 主屏出现 → 打开；同意条目与清单逐条对应 | 坏包集逐个装：全被拒，原因是人话；拒绝一条必需的授权：不安装 |
| **E3** | 装好后不打开界面 → 注入一次触发 → 出现通知；重启虚拟机，不做任何操作，再注入 → 再有通知 | 停用后注入触发：没有落点 |
| **E4** | 三条链各走一遍：网络（外面推一条；定时出去取一次）、硬件（模拟传感器一行数据）、用户输入（界面上的一次操作）；每条链从来源到界面的每一步，在事件导出里指得出来 | 令牌不对的外部推送：被拒 |
| **E5** | 一个同时有智能体、程序节点、策略的应用，做三次替换（换节点的实现、改一条策略、换槽位的档位）：新旧清单的差异只落在被换的那一件上。随手记（没有智能体）装上、用上模型、跑通 | 把程序节点换成一个接口不符的：校验拒绝，另外两件没被动过 |
| **E6** | 设备管家：注入宿主事实 → 分诊（本机模型）与解释（机器外模型）都被用到，两个档位各有用量事件；断开网络 → 分诊照常，解释如实受阻。另用一个真实的本机小模型做一次冒烟 | 把只许本机的槽位改绑到机器外的模型：被拒 |
| **E7** | 四个样品的主流程全程只在应用界面里完成（操作录制）；开发者模式关着时遍历系统壳的全部页面，没有通往工作台的入口；用词扫描无禁用词 | 打开开发者模式后工作台出现（证明前一条的「没有」不是因为功能坏了） |
| **E8** | 随手记写入若干条 → 导出到可移动存储 → 在第二台虚拟机装同一个包并导入 → 逐条哈希一致、接着能用。在仅本地的数据里埋标记串、不给任何放行授权、跑完全套：出机口抓取里搜不到。做一次放行：有授权记录 | 导出包里搜凭据标记：没有；放行之后出机口里出现的，只有被放行的那一份 |
| **E9** | 传感器看板：数据到界面；按钮到设备；拔出后显示缺设备；插回后恢复 | 另一个没绑这台设备的应用去访问它：失败 |
| **E10** | 停用与强制停止后的读数如实；断电后已确认的数据都在；坏的系统升级自动回退 | 反例应用逐个跑：越权的被拒并留痕，失控的被限额拦住；每个之后机器仍然可用——系统壳能操作、核心进程能写事件 |
| **E11** | 在工作台里组装「网页摘要」：定时取网页 → 摘要（智能体，工作档）→ 分诊（智能体，反射档）→ 通知并写记录，界面是一个列表；全程不写代码。试运行见到结果 → 封装 → 装到本机 → 另存到可移动存储 → 第二台虚拟机装上并跑通。回到工作区把「摘要」换成另一个模板再封装：两份清单的差异只在那一个节点 | 封装出的包里搜本机的凭据与授权结果：没有；画布上连一条违反划界的线：被拒 |

- **交付物**：`tests/aios/scenarios/`。
- **判据**：每条场景能一键重跑并出证据包；红样本都判红，且原因是它要验的那个机制。
- **前置**：D9-U1；每条场景另依赖对应的实现卡。E5 的智能体部分、E6、E11 等基线 B1–B3。

#### D9-U4 红样本账本 〔S1 起常设〕
- **使命**：让方案里每一条「必须失败」都有一个真会失败的样本，并证明它咬得住。
- **依据**：A 文首「判据写法」；A§6 各契约判据；K§4。
- **要做到**
  1. 账本：A§6 各契约判据里的每一条红、K§4 里的每一条红，各占一行——出处、样本在哪、怎么造出来、最近一次结果（提交号）。
  2. 每个样本配一个对照：同一个样本在「有授权」或「放开那一项」时成功。只有失败、没有对照的，不算咬住。
  3. 判红的原因必须是它要验的那个机制（看拒绝的原因码或事件），不是别处先坏了。
  4. 账本不发明新判据。发现方案漏了一条该有的红，走勘误。
- **交付物**：`tests/aios/red/`、`tests/aios/red/账本.md`。
- **判据**：绿——账本每一行都能一键重跑。红——一个因为别的原因失败的样本被记成「已判红」，该行不合格。
- **前置**：D9-U1、D1-U3。

#### D9-U5 文档自足性验证 〔S3〕
- **使命**：证明外人只读文档就能做出能装的应用——由一个没看过内部的验证方，做出「网页守望」。
- **依据**：A§6·C2 总判据；A§6·C12 判据；R§十「准备者与验证者分开」。
- **要做到**
  1. 验证方是一张新建的执行卡。任务书只给它三样：开发者文档的目录、命令行与 SDK 的发布件、一套开发模式环境。它的读取范围限于这三样。
  2. 它要做的应用「网页守望」：定时去看几个网页、接收外部推送，筛出值得看的通知用户。怎么设计，由它照文档自己定。
  3. 它边做边记「猜测清单」：文档没写清、只能靠猜的每一处。
  4. 它做出的包在镜像上装得上，并跑通它自己写的验收步骤。
  5. 核对它的读取记录：没有范围之外的路径。读到了范围之外的东西，这个验证方作废，换一张新卡重来。
  6. 猜测清单非空即不通过：缺陷退给 D8-U5 或相应契约的归口，修完之后换一张新卡重验——原来那张已经知道答案了。
- **交付物**：`apps/webwatch/`（验证方的产物）、猜测清单、读取范围核对记录。
- **判据**：绿——应用装得上、跑得动；猜测清单为空；读取范围没有越界。
- **前置**：D8-U5；G2。
- **边界**：本验证通过，证明的是「文档自足」；它不等于「真有第三方接入过」。后者 v1 不取证，任何对外材料不得这样写。

#### D9-U6 反例应用与坏包集 〔S2 起，S4 前备齐〕
- **使命**：造出一批专门干坏事的应用和坏掉的包，给红样本与加固套件当弹药。
- **依据**：A§6·C1、C3、C8、C10 的红样本；A§9。
- **要做到**
  1. 越权类：联网；读别的应用的卷与包；读聚落存储；碰没授权的设备；提权；读可移动存储；发起没声明的动作；前端包发网络请求、够系统壳、仿冒系统对话。
  2. 失控类：疯狂派生进程；吃内存；写满自己的卷；刷记录；刷模型调用；刷通知。
  3. 坏包集：表外字段、悬空引用、用了没申请的能力、带安装脚本、路径逃出包外、签名与内容不符、带脚本的策略。
  4. 每个反例只干一件坏事，名字就说明它干什么。
- **交付物**：`tests/aios/badapps/`、`tests/aios/badpkgs/`。
- **判据**：绿——每个反例在「有授权」或「放开限制」的对照环境里，真能干成那件坏事（证明它不是哑弹）。
- **前置**：D8-U1、D8-U3。
- **边界**：反例只存在于测试目录，不进任何镜像。

#### D9-U7 加固套件 〔S4〕
- **使命**：在最坏的情况下折腾这台机器，看它扛不扛得住。
- **依据**：G§七 S4；A§7 链路十；A§12 第 4 条；R§三。
- **要做到**
  1. 断电：在安装途中、升级途中、写记录途中、封装途中各断一次。
  2. 升级：坏的新系统自动回退；上一版留下的存储，新系统读得了。
  3. 越权与失控：反例全集跑一遍；每个之后核「机器仍然可用」。
  4. 累积：让十个应用常驻、事件累积到声明的规模（规模是声明数据，依据类型＝量级判据），期间内存与响应没有出现不可用级的问题。跑多久只是让累积发生的手段，不是判据。
  5. 每个保护性中断并存一条不靠时间的断言；超时了写明谁做什么，不以「用例无效」了事。
- **交付物**：`tests/aios/hardening/`。
- **判据**：全部通过。偶发的失败不得因为「单独重跑通过了」直接结案——要回答「它要验的机制，这次到底有没有被触达」。
- **前置**：G3；D9-U6。

#### D9-U8 性能基线 〔S2 出口起〕
- **使命**：量出这台机器的基线，之后每个阶段看它有没有变差——只比较，不设门槛。

- **要做到**

- **交付物**：`docs/aios/gates/性能基线.md`。
- **判据**：绿——同一配置连量两次，读数在同一量级。红——把基线读数写成了放行门槛，不合格。

#### D9-U9 泄漏与残留扫描 〔S2 起，S5 前备齐〕

### D10 开发工具产品线

#### D10-U1 开发场景清单与工作台基线 〔S1〕
- **使命**：在动工作台之前，先把「做应用的人在这台机器上干什么」写定。
- **依据**：A§5.6；A§7 链路十三。
- **要做到**
  1. 把场景清单补全。骨架已定：打开开发者模式、进开发工具；新建工作区（空白、从模板、从一个应用包）；往画布上放节点、连线、写使命、选模型档位；让它在某件事发生时动起来（加触发与策略——填表单，不写代码）；定它记什么、给用户看什么；试运行，看它怎么运转、卡在哪；封装，看它会向用户要哪些权限，装到本机或另存带走；把调好的节点存成模板。
  2. 工作台在系统里的页面图：工作区列表、画布、节点目录、节点设置、触发与策略、界面拼装、试运行观察、封装。
  3. CardColony 现有前端要改什么，列成清单，逐项归到丙类（落 `devtool/`）或「必须动 `web/`」（按乙类记账）。
  4. 用词：开发工具的界面可以用卡、线、策略这些词——它的使用者是做应用的人。
- **交付物**：`docs/aios/devtool/场景清单.md`、页面图、前端改动清单。
- **判据**：绿——链路十三的每一步都有对应的页面。红——出现一个必须写代码才能完成的组装步骤（那不属于这条路）。
- **前置**：无；前端改动清单一项需要 D1-U1 的读数。

#### D10-U2 工作区 〔S2〕
- **使命**：让「一个还在开发中的 work」成为系统里的正式对象——能改、能跑，和已安装的应用互不相扰。
- **依据**：A§5.6；A§6·C2 动作目录「开发」一行。
- **要做到**
  1. 工作区是带「开发中」标记的项目。建立（空白、从模板、从应用包）、修改、删除，都是经闸的 `workspace.*` 动作，需要 `develop` 授权。
  2. 修改用实例化器的求差：改一处，只动那一处。
  3. 工作区是活的：触发、节点、智能体在同样的沙箱与授权下运行；用的是开发配额。
  4. 工作区用到的受控能力（取数、设备、宿主事实……）在试运行时同样要使用者同意。
  5. 工作区视图（画布要用的拓扑与运行状态）登记为一种视图类型。
  6. 工作区与已安装应用互相隔离：谁也读不到谁的数据。
- **交付物**：`devtool/workspace/`。
- **判据**：绿——建一个工作区、加一个节点、连一条线，它跑起来。红——没有 `develop` 授权的应用发起 `workspace.*`，被拒；工作区去读一个已安装应用的记录集，被拒。
- **前置**：D4-U2、D4-U3、D6-U4、D2-U4。

#### D10-U3 工作台进系统 〔S2｜等基线 B10、B4〕
- **使命**：把 CardColony 的工作台（画布与会话）装进这台机器，成为开发工具的界面。
- **依据**：A§5.6；A§6·C8 规则 6；A§13.2 最后一行。
- **要做到**
  1. 开发工具是一个系统自带的应用：开发者模式打开后出现在主屏；关上就消失，它的工作区保留。
  2. 工作台的界面在系统壳的应用区域里运行，按工作区定位；数据一律走用户面，不开私有通道。
  3. 画布显示工作区的实体、线与运行状态；会话视图显示某个智能体节点的过程。
  4. 必须动 CardColony 前端（`web/`）的地方，逐项按乙类记账。
- **交付物**：`devtool/workbench/`。
- **判据**：绿——打开开发者模式 → 主屏出现开发工具 → 打开一个工作区看到画布。红——关着开发者模式时，有任何一条路走得到工作台。
- **前置**：D10-U1、D10-U2、D7-U4；基线 B10、B4。

#### D10-U4 组装 〔S2 段：节点与线；S3 段：触发、策略、记录集、界面〕
- **使命**：让做应用的人不写代码，在画布上把一个 work 拼出来。
- **依据**：A§5.6「组装」；A§6·C6 划界。
- **要做到**
  1. 画布上的每个操作落成一条 `workspace.*` 动作：从节点目录放一个节点、连线（三种线）、写使命、选槽位的档位与是否只许本机、给智能体勾选工具。
  2. 触发与策略用表单：选来源、选落到哪个节点、填条件——生成的是合乎校验的声明式策略。
  3. 记录集用表单定字段；界面用声明式组件拼页面。
  4. 每一步之后工作区都是合乎校验的；不合乎的操作当场被拒并说明原因——不让人攒出一个封不了的 work。
  5. 划界在画布上看得见：哪些节点会把内容发到机器外面，哪条线是放行线。
- **交付物**：`devtool/assemble/`。
- **判据**：绿——E11 的组装部分全程不写一行代码。红——画布上连出一条违反划界的线，被拒并说明原因。
- **前置**：D10-U2、D10-U3、D10-U5。

#### D10-U5 节点目录与自带模板 〔S2 段：目录；S3 段：自带模板备齐〕
- **使命**：给组装备好零件——能挑、能存、能导入。
- **依据**：A§5.6「节点目录」；A§6·C1「节点模板」。
- **要做到**
  1. 节点目录视图；三个来源：系统自带的、自己从工作区存的、从文件导入的。
  2. 存为模板、导入模板都是经闸的动作；模板过 D4-U1 的两层校验。
  3. 自带模板。智能体四个：分诊（反射档）、答复（工作档，对话入口）、摘要（工作档）、研判（审议档）。程序节点四个：定时取网页并抽出正文、文本结构化抽取（用模型）、串口读数解析、表格文本转记录。这份清单本卡可以调整，但**每个自带模板都必须被 E11 或某个样品真的用到**；没人用的不带。
  4. 程序节点模板的代码由本卡的执行卡写好；做应用的人只填参数。
- **交付物**：`devtool/catalog/`、自带模板。
- **判据**：绿——从目录放一个模板进工作区，就能运行。红——一个通不过校验的模板文件被导入了。
- **前置**：D4-U1、D10-U2。

#### D10-U6 封装 〔S3〕
- **使命**：把一个调好的工作区冻结成应用包——和手写打出来的包受到一模一样的对待。
- **依据**：A§6·C1「封装规则」。
- **要做到**
  1. 按封装规则冻结；权限与配额的申请由实际用到的能力机械推出。
  2. 封装前给做应用的人看一眼：这个应用装的时候会向用户要哪些权限。他可以补理由、把配额调小，不能删掉用到的权限。
  3. 过同一个校验器；通不过就失败，并指出原因。
  4. 用设备密钥签名；装到本机（照样走同意界面），或另存到可移动存储。

## §8 风险与对策

| 风险 | 会怎么坏 | 方案里的对策 |
|---|---|---|
| CardColony 的基线迟迟不到位 | 项目停在 G1「部分放行」，后面大半张树挂着 | 三分法写死、不造替身；不依赖基线的部分先做完（7.2 末段）；是否把甲类并进来由用户裁（G§十 第 4 条） |
| 两个项目在同一台机器上抢资源 | 构建与虚拟机把内存吃光，两边一起垮（work_027 出过） | 测试槽的上限；建议错开全速期（G§十 第 3 条） |
| 这台机器用不了硬件虚拟化 | 虚拟机只能软件模拟，整机层的测试慢到跑不动 | P0、P2 先量；T13 的撤退条件——关口套件拆小，整机层只留强制类与启动升级类；仍不行，报用户另备 Linux 机器 |
| 探针推翻了某项选型 | 已经写好的东西要换 | 探针先于实现；契约只写语义，不绑定具体选型；每项选型都备了撤退条件 |
| 契约冻结之后发现有洞 | 各域各自打补丁，接口又变成多份 | 变更通道只增不改；勘误表是唯一出口；洞由 D1 统一补 |
| 需求评审出现分歧，无人值守时停住 | 一张卡卡住，带住下游 | 方案定了的以方案为准；没定的按 R§四 四类办；挂起的只是那一张卡 |
| 卡往需求里加方案之外的东西 | 范围悄悄变大，判据对不上 | 需求草稿只许转写；验收里「多做的也是越界」 |
| 系统壳做成了管理台 | 普通用户用不了，E7 不过 | 场景清单先于一切页面；用词表扫描；工作台只在开发工具里 |
| 零件都过了，整机不通 | 重演 work_027 | 镜像先行；曳光弹不许熄；成对与接线两条规矩；关口证据只认整机层 |
| 干净验证方被污染 | 文档自足性验证失去意义 | 读取范围可核；越界即作废换新；修完换新卡重验 |

| 在途的智能体停不下来 | 「强制停止」名不副实 | 界面如实写「智能体部分只能软停」，不谎报；等基线 B5 |
