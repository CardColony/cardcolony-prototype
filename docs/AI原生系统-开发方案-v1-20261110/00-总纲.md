## 一、这份方案是什么

这是交给 CardColony 全自动运行用的**设计方案**：系统长什么样、活怎么分、干活守什么规矩，都在这里定好。卡片的职责是照着执行、验证、如实汇报——**不负责设计**。

| 文件 | 管什么 | 装载后落在哪 |

| 01 系统架构设计 | 分层、边界、十二份契约、主链路、技术选型 | 仓库里的架构依据；各卡只引用、不复述 |
| 02 拆卡方案 | 整棵卡树：每张卡的使命、要什么、怎么算做到、依赖谁；怎么装载、怎么开跑 | 域卡、单元卡的使命与需求草稿的来源 |

**效力顺序**：用户当面裁定 ＞ 本方案（含勘误表）＞ 由本方案转写出的各卡需求正稿与契约冻结件 ＞ 其余一切（原型代码、旧文档、代码里的注释、模型自己的想法）。卡片认为方案有错，走勘误（R§五），不许悄悄偏离。

## 二、要造的东西

**一句话**：一个给普通用户日常使用 AI 应用的通用操作系统——占的是 iOS、Android 那个位置，但它是为 AI 应用而生的。底下是 Linux；让应用「活」起来的引擎，是沉在系统里的那套智能体运行机制；在这台机器上造应用的工具，是 CardColony。

**三样东西，各归各位**：

- **AI OS（给普通用户）**：开机进主屏，主屏上是应用。应用什么形态都行——可以是聊天，可以是一个记事本，也可以是一整个智能体组织。智能体组织是封顶的形态，**不是入门的门槛**；聊天是一种界面，**不是默认界面**。
- **运行时（沉在系统里）**：卡网络那套机制——居民、事件、闸、线、监督、harness——成为系统的一部分。它是「AI 应用能自己活着干活」的引擎，不绑定任何一种应用形态。「原生融合 CardColony」，融进系统的是这层机制。
- **CardColony（给做应用的人）**：这台机器上的开发工具，位置相当于 Xcode 之于 iOS——只不过它自己就是一款多模型、多智能体并发的 AI 原生应用。做应用的人在它的**工作台**（画布与会话）里，把不同的智能体节点**组装**成一个 work，再**封装**成应用包，装到这台或任何一台同样的机器上。普通用户不需要工作台，也看不到它。

**源头是你自己说过的话**（2026-11-05 关于 AI OS 的讨论，以及 2026-11-10 至 11-12 的几条确认与修正）。方案里每一块都要能指回其中一句：

|---|---|

**做完以后你手里有什么**：
- 一个镜像文件：写进 U 盘或硬盘，电脑开机直接进这个系统（虚拟机同理），全程不碰命令行。
- 系统里能装应用：选一个应用包 → 它告诉你它要什么权限 → 同意 → 它出现在主屏，并且从此自己在后台工作。
- 开发工具就在机器上（默认收着，打开开发者模式才出现）：不写代码，把智能体节点组装成应用、封装、装上。
- 四个小应用当验收样品，证明：不带智能体的普通应用成立、智能体组织型应用成立、硬件能当节点、外人只读文档也能做出应用。
- 一套命令行、SDK 和文档：会写代码的人照文档就能做出能装的应用。
- 全部过程文件与验收证据，在仓库和卡面上。

## 三、三条根原则（方案里的一切都从这三条推出来）

**原则一 · 地基租用，语义自有。**
Linux 内核、驱动、基础系统组件只做配置与打包，**一行不改、一个驱动不写**。「这台机器是什么、谁能做什么、发生过什么」全部由卡网络回答。
判据：镜像里没有自编的内核补丁与自写驱动；换一个内核小版本，系统语义不变。

**原则二 · Linux 只负责执行与强制，事实只有一份。**
进程、cgroup、文件权限、systemd 单元，都只是卡网络做出决定之后的**执行结果**，不是第二份真相。任何 Linux 侧的状态都必须能从事件日志重新推出来；推不出来的，就是设计错了。
判据：把全部派生状态（运行中的单元、挂载、投影缓存）清掉再启动，系统从事件日志恢复到同一读数。

**原则三 · 系统即第一个 work。**
系统自己的服务、开发工具、第三方应用走同一套接口。系统服务和开发工具**没有特权通道，只有更大的授权**。
判据：它们用到的每一种能力，都能在公开契约里找到条目；找不到＝契约有洞——补契约，不开后门。

## 四、范围

**做（v1 必须）**
1. 可启动整机镜像（x86_64 电脑与虚拟机）：开机直进系统界面；系统分区只读、数据分区独立；A/B 升级、失败自动回退；可安装到本机磁盘。
2. AI 应用包（`.work`）：格式、清单、校验、签名；安装／启动／停用／升级／卸载；数据导出与导入。
3. 应用积木：智能体节点（卡）、程序节点（沙箱里跑的代码）、harness 策略——全部可选、各自可换；一个不带智能体的应用同样成立。
4. 四类触发：用户输入、定时、网络（外部推送进来、定时出去取）、宿主与硬件事件。
5. 宿主融合：沙箱运行体（权限与限额由 Linux 强制）、宿主事实进事件日志、宿主动作经闸、设备作为节点（v1 实做串口类）、可移动存储作为系统的文件通道（装应用、升级、导入导出用）。
6. 模型是系统资源：反射／工作／审议三档；本地模型运行时；远端模型凭据；按应用槽位绑定；智能体和不带智能体的应用都从同一个入口用模型。
7. 应用界面：自带前端包与声明式界面组件两种做法；系统壳（主屏、待办与通知、设置、首启向导），按普通用户的使用场景设计。
8. 授权与同意：安装时、运行时；可撤销。
9. 配额与核算：运行体数、内存与 CPU、存储、模型用量；超限被拦，机器不被拖垮。
10. 数据主权的最小实现：应用数据默认仅本地；「本地／可出境」划界；放行留授权记录；数据整包导出导入。
11. 开发工具（CardColony 在这台机器上的形态）：工作台、工作区、组装、节点目录、封装成包。
12. 开发者工具链与文档（命令行、开发模式、SDK）；四个样品应用；一组反例应用。
13. 整机验收：十一条场景、红样本账本、加固套件。

**不做（v1 明确不做）**
- 自写内核、驱动、引导器、图形栈；传统桌面环境。
- 手机与 ARM 镜像；触屏虚拟键盘；语音与摄像头输入。
- 多用户与账号体系、锁屏；应用商店、在线分发、更新服务器。
- 重新实现或重新设计 CardColony 的运行机制（含它尚未收口的部分，见第六节）。
- 给应用预设形态与场景：不把聊天当默认界面，不把工作台交给普通用户。
- 「描述需求、由开发组织自动把应用造出来」：v1 的开发工具只做「组装」这条路（原因与留的缝见 A§5.6）。
- 程序节点直连网络；第二种节点运行时（如 WASM）；应用可见的存储设备（例如让相册应用读 U 盘）；跨应用协作线；多机卡网络；租远端机器跑运行体。
- 事件日志签名、安全启动、全盘加密；NVIDIA 专有驱动与 GPU 加速保证。
- 涌现验证；性能数值门槛；对外发布、宣发、官网。

**留缝（现在不做，但设计上不堵死）**
- 档位、授权种类、动作类型、事件类型、界面组件、运行体驱动、设备类别、触发来源、视图类型——全部是登记表里的数据，加一项不改核心（A§6·C2）。
- 分区布局不堵安全启动与加密；身份体系不堵多用户；包签名与导出签名不堵日志签名。
- 带完整历史（工龄）的 work 分发：数据级导出先做；事件历史级的迁移，等 CardColony 的项目迁移能力。
- 让智能体代替人做组装：组装操作全部是已登记的动作，将来把这些动作授权给一个智能体即可，不需要新机制。
- 模型算力的集中调度：把要用同一模型的需求成批组织，小模型多实例并存、处理完一批换下一批——这是目标形态，不是 v1 的事。v1 只做按需加载与压力卸载，但调用的结果语义（可被延后、如实排队）与驻留事件的账目，按「将来由调度器接管」设计（A§6·C6「留缝：算力调度」）。

### 6.2 CardColony 要为 AI OS 做的事，分三类处置（写死）

你说过「cardcolony 也要做一定的迭代，来适应 ai os 的需要」。这些迭代性质不同，不能混着办：

| 类 | 是什么 | 归谁 | 本项目怎么办 |
|---|---|---|---|
| **甲 · 基线缺口** | CardColony 自己本来就要收的口（上表 B1–B10 里没到位的） | CardColony 自己的开发线（work_027） | **不代做、不另做一套**。登记进基线缺口表，受它阻塞的卡挂起，其余照常；不造替身、不拿桩冒充通过 |

## 九、整机验收十一条（根卡的总判据，全部站在使用者角度）

| 编号 | 使用者能做到什么 | 对应原话 |
|---|---|---|
| **E1 开机即系统** | 镜像写进磁盘，开机直接进主屏；第一次开机走完向导（语言、网络、模型）就能用。全程不出现命令行 | 「直接安装于硬件上的 OS」 |
| **E2 装应用像装应用** | 选一个应用包 → 看到它要的权限 → 同意 → 它出现在主屏、点开即用 | 「work 能打包成应用」 |
| **E3 应用自己会动** | 装好以后不打开界面，事件来了它自己处理并通知你；重启机器后不用任何操作，它仍在工作 | 「这个 work 自动运行」 |
| **E4 三种触发都走得通** | 网络、硬件、用户输入各有一条完整的链：触发 → 智能体或程序节点 → 结果 → 界面；每一步在事件里查得到 | 「触发事件来自网络……硬件……用户输入」 |
| **E5 积木可换，组织不是门槛** | 同一个应用同时用到智能体、程序节点、harness，换掉其中一件，另外两件不用动；一个不带智能体的应用照样安装、用模型、跑通 | 「丰富的可组合性」「唯一确定的，是 ai app」 |
| **E6 大小模型一起干活** | 同一个应用里本地小模型和大模型同时在用；断网时本地那部分照常，依赖远端的部分如实显示受阻 | 「N 个不同类型的模型一起运作」 |
| **E7 像应用，不像管理台** | 用完应用的主要功能，不需要看见卡、会话、事件；没打开开发者模式的机器上，哪里都没有工作台的入口 | 「普通用户不需要工作台」 |
| **E8 组织和数据是你的** | 应用数据在本机；能整包导出、在另一台机器导入后接着用；标了「仅本地」的数据不出现在任何发往机器外的请求里；每次放行都有授权记录 | 「算力是租的，组织和数据是你的」 |
| **E9 硬件是节点** | 一个接在机器上的设备是应用的一个节点：它的数据触发应用；应用经授权可以向它下动作；拔掉它，应用如实显示缺了什么 | 「卡网络的节点之一就可以是某个硬件」 |
| **E10 管得住** | 停用、强制停止如实生效；越权的应用被拒且留痕；失控的应用被限额拦住、机器仍可用；断电重启不丢已确认的数据；系统升级失败自动回退 | 「组织和数据是你的」的底线 |
| **E11 组装即应用** | 在工作台里把几个智能体节点连成一个 work → 试运行 → 封装成包 → 装到本机、再装到另一台机器 → 能跑；换掉其中一个节点，其余不动 | 「直接组装不同的智能体节点形成 work，封装成 ai app」 |

每条的取证办法、绿样本与红样本见 K§6·D9-U3。

## 十、需要你确认的事

**1. 名字。** 系统对外叫什么由你定；文中「AI OS」只是工程代号，进程名里的 `colony-` 也只是工程标识。

**2. 四个样品应用。**
系统做出来以后，得真装上几个应用才看得出它能不能用。方案安排顺带做四个小应用当验收样品，每个证明一件事：
- **随手记**（不带智能体的普通应用）：丢进去一句话或一段文字，本地小模型自动起标题、归类、提取待办和日期；可以按标签和日期找，到期的待办每天早上提醒你。没有对话、没有智能体——证明「AI 应用不一定是聊天，也不一定是组织」。（原先想做相册，但照片得从 U 盘进来，而 v1 的设备只实做串口类，相册留到存储设备类别做了以后。）
- **设备管家**（智能体组织型）：盯着这台机器自己——电量、发热、磁盘、网络、插拔设备。有事时本地小模型先判断要不要打扰你，需要时再叫大模型解释；要动机器之前先问你。
- **传感器看板**（硬件）：一个接在机器上的串口设备当应用的一个节点，它的数据触发应用。
- **网页守望**（外部视角）：定时去看几个网页、接收外部推送，筛出值得看的告诉你。它由一张**没看过内部设计、只读开发者文档**的卡来做，证明「外人照文档就能做出能装的应用」。

「组装智能体节点 → 封装成应用」不单设样品，由验收 E11 当场做一遍。你更想看到别的应用，告诉我是什么样的，我换。

**3. 什么时候开跑。** 这是最要紧的一条，我把真实情况说清楚：
- **现在就能做、不依赖 CardColony 进度的**：S0 的全部探针与基线实读；S1 里的契约冻结和曳光弹的第一段「地基」——镜像启动、核心进程起来、沙箱里的程序经现有协议写进一条事件、系统壳显示出来、断电后恢复。这一段只用到 CardColony 已经冻结并验收过的部分。
- **要等 CardColony 的**：曳光弹后三段。「应用骨架」和「模型」两段需要 B6、B7（系统层的动作、事件、策略要能登记进它的闸）；「智能体」一段和之后一切智能体节点需要 B1–B3；界面实时更新需要 B4。这几条现在都还在 work_027 里办。
- **我的建议**：S0 和曳光弹的「地基」段现在就可以跑——它们不改 CardColony 的代码，还能顺手给 work_027 提供「在 Linux 上成立不成立」的证据；其余等 B1–B3、B6、B7 收口再放行。两个项目同时在这台机器上全速跑，构建和虚拟机会互相挤（work_027 出过内存耗尽的事故）。
- 你要定的就是：照这个建议走；还是全部等 work_027 收口后再开；还是现在就全开、让卡自己按「缺什么挂什么」推进。

**4. CardColony 没收口的那几条（6.2 的甲类），要不要并进这次运行。** 默认不并。并进来的好处是这次运行不必等别人；代价是两拨卡同时改同一片代码，而且其中有的事还在等你的裁定。

**5. 开发工具 v1 做到哪。** 方案定的是：v1 做「组装」这条路——不写代码，在工作台里把智能体节点连成 work、试运行、封装、安装。「说一句需求，开发组织自动把应用造出来」不在 v1：那需要在系统里再做一套带编译工具的建造环境，也需要 CardColony 的自主推进先成熟。设计上没堵（组装操作都是登记过的动作，将来授权给智能体即可）。

**6. 目标机器。** v1 只做普通 x86 电脑和虚拟机。手机不在这次范围，设计上不堵。

**7. 我替你先定了的默认值**（全在 R§十三「预裁定清单」，逐条可否）。最要紧的几条：
- 应用数据**默认仅本地**；应用要用机器外面的模型，安装时必须明说并得到你的同意。
- 镜像里**不带模型权重、不带任何密钥**；首次开机的向导引导你配置。
- 开发工具随系统自带但**默认收着**：在设置里打开开发者模式，它才出现在主屏；不打开，哪里都没有工作台。
- 没签名的应用包只有打开开发者模式才能装。
- v1 没有应用商店：应用从 U 盘里的文件或一个网址安装；系统更新同理。
- 系统界面用浏览器内核全屏呈现（使用者看不到浏览器），没有传统桌面。

**8. 模型与下载。** 判据默认用「回放模型」（同样的输入给同样的输出，结果可复核），真实模型只做少量冒烟；凭据走部署侧注入、不进仓库与卡面——沿用你在 work_027 批过的口径，需要你对本项目再点一次头。另外，本地模型的探针和 E6 需要下载一个小型开放权重模型到建造环境里。

**9. 在你机器上新建的东西。** 一个专用的 WSL 发行版、一个独立的代码目录、它们的磁盘上限（R§十一、R§十三）。除此之外不动你机器上的任何东西。

## 十一、术语

- **建造卡／居民卡**：本方案里「卡」有两层意思。**建造卡**＝执行本方案、把系统造出来的那些卡（根卡、域卡、单元卡、执行卡）；**居民卡**＝造出来的系统里、应用内部的智能体节点。未加限定词时：02、03 两份里的「卡」指建造卡，01 里的「卡」指居民卡。
- **AI 应用**：装在这台机器上的应用的统称，形态不限。
- **work／应用包／应用实例**：work 是活的——一组智能体节点、程序节点、harness 和界面；**应用包**（`.work` 文件）是它的便携形态；**应用实例**是包装到某台机器上以后的它，在卡网络里就是一个项目。「封装」＝把活的 work 冻结成包；「安装」＝把包变回活的。
- **实体**：应用里的一个节点。两种：**智能体节点**（卡，持使命、带模型）和**程序节点**（一段代码，跑在沙箱里）。带模型槽位、自己写循环的常驻程序节点，就是自带逻辑的智能体（自由智能体）。
- **harness 策略**：声明式的「什么事发生了 → 做什么」。
- **触发**：让应用里某个实体开始干活的事件。
- **档位**：模型的分档——反射／工作／审议。**槽位**：应用声明「我这里要一个什么样的模型」的位置。
- **宿主事实**：机器自己发生的事（电量变了、设备插上了），写进事件日志之后才算事实。**宿主动作**：对机器做的事（关机、连网、升级），必须经闸。
- **沙箱**：程序节点的运行环境，能碰什么由授权决定、由 Linux 强制。
- **系统壳**：普通用户看到和操作的那层界面。**工作台**：开发工具的界面（画布与会话），给做应用的人。
- **开发工具**：CardColony 在这台机器上的产品形态——工作台＋工作区＋组装＋节点目录＋封装。**工作区**：一个还在开发中的 work。**节点目录**：可拿来组装的节点模板（系统自带的、自己存的、从文件导入的）。
- **系统 work**：系统自己的那个「应用」，系统服务都登记在里面（原则三）。
- **契约**：跨域接口的唯一约定，共十二份（C1–C12）。**冻结**：契约定版，之后改动要走变更通道。
- **探针**：动工前先做的小实验，证实一项技术选择在本机成立。**撤退条件**：出现什么现象就判这项选择不成立、换成什么。
- **曳光弹**：最窄的一条贯穿整机的真实链路，先打通它，再加宽。
- **融合保护区**：仓库里属于 CardColony 的目录。**融合补件**：6.2 的乙类改动。
- **基线缺口**：6.2 的甲类。
- **关口**：一个阶段的出口检查（G0–G5）。
