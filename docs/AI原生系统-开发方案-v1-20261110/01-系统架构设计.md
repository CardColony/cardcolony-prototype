## §1 定位与边界

**是什么。** 一个 Linux 打底的消费级通用操作系统——占 iOS／Android 那个位置，但为 AI 应用而生。「为 AI 而生」的含义：AI 应用要的那些地基是系统的一等公民——智能体可作为居民常驻、模型是可绑定的资源、事件与触发是底层机制、应用数据默认不出机、硬件可当节点。
- 用户看到的：开机进主屏；应用随便什么形态；应用在后台自己工作，有事通知你、要动东西先问你。
- 做应用的人看到的：应用＝一个 `.work` 包；里面可以是一个智能体组织，也可以简单到一个程序节点加界面——组织是封顶形态，不是门槛。
- 造应用用的工具是 CardColony：在工作台把智能体节点组装成 work、封装成包；或描述需求让开发组织代建。
- 系统内部：一切发生过的事是事件，一切效果经闸，一切当前状态是事件的投影。Linux 负责把这些决定执行出来、强制住。

**不是什么。** 不是新内核；不是「Linux 桌面＋AI 助手」；不是跑在别的系统里的一个服务；不是只服务智能体组织的工作站；不是 CardColony 的重写——融进系统的是卡网络的**机制**，CardColony 产品是这层机制之上最复杂的那个应用者：开发工具。

**边界一句话。** 本系统新增：宿主融合层（L1）、系统层（L4）、系统壳（L5）、分发（L7），以及开发工具产品面（D10）。CardColony 的底座与卡侧（L2、L3）作运行时原样复用；Linux（L0）只配置不修改。

## §2 分层与责任

| 层 | 负责 | 不负责 | 建造归口 |
|---|---|---|---|
| **L0 Linux 地基** | 硬件支持、进程与内存、文件系统、网络栈、图形输出；开机时拉起三样东西：核心进程、特权手臂、系统壳会话 | 任何「谁能做什么」的决定；聚落内部进程的启停与重启决定 | D2（只配置） |
| **L1 宿主融合层** | 把租约与授权翻译成沙箱单元并启停；把内核与系统信号转述成宿主事实；执行已受理的宿主动作；设备接入 | 判断。它只执行与转述，不决定「该不该」 | D3 |
| **L2 CardColony 底座** | 状态（事件日志）、闸、消息、调度、监督、Harness、上下文；身份与三种线 | 不认识「应用」「界面」「模型档位」 | 复用 |
| **L3 CardColony 卡侧** | 执行层（跑一轮模型与工具）、投影、内容与规则、用户面推送 | 不认识宿主与硬件 | 复用 |
| **L4 系统层** | 应用管理、触发路由、模型分档与绑定、应用数据面、授权与同意、配额与核算、系统的网络出入口 | 事件怎么存、卡怎么跑（用 L2、L3 的）；界面怎么画 | D4、D5、D6（网络出入口在 D3） |
| **L5 系统壳** | 用户看到和操作的一切：主屏、应用界面宿主、待办与通知、设置、首启向导 | 任何业务事实；不内置工作台（属开发工具） | D7 |
| **L6 应用与开发工具** | AI 应用（任意形态；组织是封顶不是门槛）；CardColony 开发工具（工作台、组装、封装、开发组织） | 越出清单与授权的任何事 | D8、D10 |
| **L7 分发** | 镜像、安装、升级与回退 | 运行期语义 | D2 |

**进核心进程，还是出进程——一条规则：**
- **需要和闸同一事务才能保证一致的，进核心进程**：应用管理、数据面投影、配额核算、触发路由、模型绑定。
- **需要特权的、要联网或监听的、要处理不可信输入的，出进程**：特权手臂、系统取数节点、入站网关、本地模型运行时、一切应用的程序节点、系统壳的浏览器内核。

## §3 原生融合映射表

「原生融合」的含义就是这张表：左栏是卡网络里的概念，中栏是 Linux 这边拿什么承载和强制，右栏是谁说了算。**右栏永远不是 Linux。**

| 卡网络的概念 | Linux 侧的承载与强制 | 权威在哪 |
|---|---|---|
| 居民（卡、程序节点这些实体） | 无——纯语义，不对应任何 Linux 对象 | 事件日志 |
| 项目（一个应用实例就是一个项目） | 一个 cgroup 切片、一组数据卷、一个存储配额号 | 项目事件 |
| 运行体 | 一个进程，装在 systemd 瞬态单元里 | 租约事件；进程只是执行 |
| 租约 | 单元的启动与停止 | 租约事件 |
| 授权 | 单元的沙箱属性（看得见哪些文件、有无网络、能碰哪个设备） | 授权事件；属性是派生物 |
| 预算与配额 | cgroup 的内存、CPU、任务数上限；文件系统项目配额 | 预算事件 |
| 停止令 | 停掉相应单元 | 停止令事件 |
| 事件（宿主事实一类） | udev、netlink、电源、热、内存压力等内核与系统信号 | 写进事件日志之后才算事实 |
| 动作意图（宿主动作一类） | 对 systemd、网络管理、时间、升级组件的调用 | 意图与结果事件 |
| 产物 | 数据分区上按内容寻址的文件 | 产物库与引用它的事件 |
| 投影与视图 | 内存或可删的派生库 | 无（可删、可重建） |
| 监督 | systemd 只管三个系统级进程；聚落内的一切重启决定归 CardColony 的监督 | 监督事件 |
| 用户（主体） | 设备所有者一人；Linux 用户账号只是隔离手段，不是身份 | 身份事件 |

**两个拉起者的分界（写死，防双重监督）**：systemd 拉起并看护的只有核心进程、特权手臂、系统壳会话三样。其余一切进程——系统节点、应用的程序节点、本地模型运行时——都由 CardColony 的调度与监督经租约拉起；它们的瞬态单元一律不带自动重启，重启与否由监督按声明决定。
红：某个程序节点崩溃后被 systemd 自行拉起，而事件流里没有对应的监督决定。

## §4 进程、启动与磁盘

### 4.1 进程清单

| 进程 | Linux 身份 | 谁拉起 | 职责 | 对外的面 |
|---|---|---|---|---|
| **核心进程** `colony-core` | 非特权用户 | systemd | CardColony 全部子系统＋L4 系统层；**唯一写事件日志的进程** | 用户面：本机回环端口（只许系统壳用户连）；到特权手臂的本地套接字 |
| **特权手臂** `colony-hostd` | root | systemd | 启停沙箱单元、采集宿主信号、执行宿主动作。**只听核心进程的，只执行带受理凭据的请求** | 本地套接字（只许核心进程的用户连） |
| **系统壳会话** | 独立的非特权用户 | systemd | 全屏合成器＋浏览器内核，显示系统壳 | 无 |
| **程序节点**（含系统节点：取数、入站网关、本地模型运行时、设备驱动节点） | 每单元一个动态用户 | 核心进程经租约 → 特权手臂 → 瞬态单元 | 各自声明的那件事 | 标准输入输出（参与者协议） |

**特权手臂不是卡网络的公民。** 它没有身份、不持线、不写事件，是核心进程伸进 root 权限里的一只手。卡网络里代表「这台机器」的实体，是系统 work 里的宿主实体，由核心进程内的宿主适配器扮演。这样特权面最小，协议也不用为它改。

### 4.2 开机序列

1. 固件 → 引导器 → 内核 → systemd。系统分区只读挂载。
2. 首次开机：创建并扩展数据分区。之后每次：挂载数据分区。
3. 并行拉起特权手臂与核心进程。
4. 核心进程打开事件日志，按日志重建全部投影；确保系统 work 存在（幂等）；连上特权手臂。
5. 核心进程取一次宿主当前读数，写成基线宿主事实（防止漏掉关机期间的变化）。
6. 重新武装：对每个「运行中」且有自启授权的应用，恢复它的常驻节点租约与触发。
7. 写入「启动完成」事实；用户面就绪。
8. 系统壳会话启动；核心未就绪时显示启动画面，就绪后进主屏（首次开机进向导）。

绿：从上电到主屏不需要任何人工输入。红：第 4 步完成之前，任何应用的触发落了点。

### 4.3 关机与断电

- 正常关机是一条宿主动作意图：核心进程记下意图 → 停止接受新工作 → 在途的收尾或记中断 → 落盘 → 特权手臂调用系统关机。
- 异常断电：下次开机走 4.2，第 4 步的重建就是恢复；在途调用按 CardColony 的规则记为中断或结果不明，不假装成功。主屏给一条「上次没有正常关机，已恢复」的通知。

### 4.4 磁盘布局

| 分区 | 内容 | 读写 |
|---|---|---|
| 引导分区 | 引导器、统一内核镜像（A、B 两份） | 仅升级时写 |
| 系统分区 A／B | 整个系统软件，两份轮换 | 运行期只读 |
| 数据分区 | 一切可变状态 | 读写 |

数据分区内的落点（目录名由 D2 在契约 C11 里定死，此处给语义）：

| 落点 | 放什么 | 性质 |
|---|---|---|
| 聚落存储 | 事件日志、产物库 | **权威**。别的都可以丢，这个不行 |
| 派生区 | 投影缓存、索引 | 可删，开机重建 |
| 应用包库 | 已安装包的解包内容，按内容寻址 | 产物（可由包文件重得） |
| 应用卷 | 程序节点的私有工作目录，带项目配额 | 应用私有，非事实源 |
| 模型库 | 本地模型权重 | 可重新下载 |
| 机器私有区 | 设备密钥、凭据库、机器设置 | **权威**（密钥材料不进事件日志，见 §8） |

**状态落点规则**：系统分区运行期零写入；一切可变状态只在数据分区；核心进程以外的进程不得写聚落存储。
**恢复出厂**的定义：清空数据分区，系统分区不动。

## §5 核心对象

### 5.1 应用包与应用实例

- **应用包**：一个 `.work` 文件，不可变，按内容寻址。
- **应用实例**：包安装后的结果，在卡网络里是**一个项目**。项目本来就是隔离、授权、预算、停止令的边界——应用的沙箱边界就是它，不另造。
- v1 一个应用同一时刻只有一个实例（留缝：实例标识是独立字段，不与应用标识合并）。

### 5.2 两类实体、三件积木

| 积木 | 是什么 | 负责 | 在底座眼里 |
|---|---|---|---|
| **智能体节点（卡）** | 持使命、带模型的智能体 | 想：判断、对话、决定下一步 | 居民 |
| **程序节点** | 不持使命的一段代码，跑在沙箱里 | 算：抓取、解析、计算、读写设备 | 居民（不持使命的那类） |
| **harness 策略** | 声明式的「什么事发生了 → 做什么」 | 条件反射：把事件接到卡或节点上 | 策略（数据） |

程序节点两种工作方式：**一次性**（来一次调用，算完交结果，退出）与**常驻**（一直在，例如盯着一个设备）。

**组织不是门槛**：三件积木全部可选。最小的合法应用可以只有「一个程序节点＋模型槽＋界面」——不带智能体、不带策略，照样是原生 AI 应用。

**可组合性的含义（判据）**：三件各自独立可换——换一个节点的实现不动线与策略；加一个触发来源不动卡；改一条策略不动节点。绿：做这三种替换，清单的差异只落在被换的那一件上。

**harness 不是编程语言。** 它只做「条件 → 动作」的声明，条件用 CardColony Harness 现成的零件；复杂逻辑写进程序节点。红：策略文件里出现循环、变量赋值、内嵌脚本。

### 5.3 线

三种线照 CardColony 的定义，不新增：组织（父子）、通信、依赖影响。无线不交互。
应用与系统之间也靠线：系统 work 里的宿主实体、设备实体、网关实体是线的一端，应用内的实体是另一端。**一个应用收得到某类宿主事件，当且仅当它有一条通到那个系统实体的线，而那条线只在用户授权后才建。**

### 5.4 应用实例的状态

主状态（闭集，事件流的投影，没有可直写的状态字段）：
`已暂存` → `待同意` → `安装中` → `运行中` ⇄ `已停用`；`升级中`；`卸载中` → `已移除`。

叠加读数（不是状态，带原因码，可同时有多条）：
- `等待条件`：缺设备／缺模型绑定／缺授权。
- `受限`：某项配额用尽。
- `出错`：某个常驻节点按监督声明已不再重启，等等。

规则：界面上的状态词由服务端给，前端不拼；叠加读数不并入主状态；「运行中」只表示触发已武装，不表示此刻有东西在跑。

### 5.5 应用数据的三种形态

| 形态 | 用来放什么 | 怎么写 | 是不是事实源 |
|---|---|---|---|
| **记录集** | 小而结构化、要给界面和别的实体读的东西 | 经闸 | 是（事件派生） |
| **产物** | 大而不可变的产出：文档、抓回来的网页、模型长输出 | 先存后引用 | 是 |
| **卷** | 程序节点自己的工作文件 | 节点直接读写 | **不是**。别人要读的东西不许只放在卷里 |

## §6 十二份契约

契约是跨域接口的唯一约定。本节给出每份契约的目的、规则与判据；D1 在 S1 把它们转写成仓库里的契约文档与机器可读件并冻结（K§6·D1-U2）。转写时发现本节有错或有洞，走勘误，不自行补全。

### C1 应用包与清单

**目的**：一个文件说清一个应用的全部——它是谁、里面有什么、要什么、给用户看什么。

**包**
- 单文件、不可变；内部是固定目录：`manifest.json`、`policies/`、`nodes/`、`ui/`、`regions/`、`assets/`、`SIGNATURE`（可无）。
- **包里没有安装脚本，没有任何「安装时执行」的东西。** 安装只由系统按清单执行。
- **来源两种等价**：开发工具把一个活 work 冻结封装导出；或人手写清单＋代码打包。同格式、同校验——「机器造的」不比手写的多一分信任。
- 签名对「清单＋全部文件的哈希清单」做。验证结果三态：发布者已受信任／签名有效但发布者未知（安装时明示）／未签名（仅开发者模式可装）。

**清单（顶层字段为闭集，出现表外字段即拒）**

| 字段 | 含义 |
|---|---|
| `schema`、`id`、`version`、`name`、`summary`、`publisher`、`min_abi` | 身份与兼容性 |
| `params` | 安装时让用户填的配置项 |
| `secrets` | 需要用户提供的密钥的名字。值进系统凭据库，应用内任何实体读不到明文 |
| `entities` | 卡与程序节点 |
| `lines` | 实体之间、实体与系统实体之间的线 |
| `collections` | 记录集的声明（名字、键、字段、是否仅本地） |
| `models` | 模型槽位：哪张卡要哪一档、要不要本地 |
| `devices` | 设备槽：要一个什么类别的设备 |
| `triggers` | 触发来源与落点事件 |
| `policies` | harness 策略文件 |
| `permissions` | 申请的授权，每条带给用户看的理由与是否必需 |
| `budgets` | 申请的配额 |
| `ui` | 主屏入口与页面 |
| `data` | 导出规则 |
| `upgrade` | 能从哪些旧版本升上来，数据怎么迁 |

**组织不是门槛**：`entities` 至少一个、种类随意；`policies`、`lines`、`devices`、`models` 都可为空——一个纯界面应用照样合法。

**一个最小的清单长这样**（就是 S1 曳光弹用的那个应用；字段细节以冻结后的契约件为准）：

```json

  "id": "org.cardcolony.hello",
  "version": "0.1.0",
  "name": "你好",
  "summary": "最小样例：每分钟记一笔，能对话",
  "publisher": { "name": "CardColony", "key": "ed25519:…" },
  "min_abi": "1.0",
  "entities": [
    { "id": "greeter", "kind": "card", "title": "接待",
      "mission": "回答用户的问题；用户让你记事时，写进 notes。",
      "model": "main", "locality": "local",
      "tools": ["record.put", "record.query"], "entry": true },
    { "id": "ticker", "kind": "node", "title": "报时", "mode": "job",
      "runtime": { "kind": "exec", "interpreter": "python3", "script": "nodes/ticker.py" },
      "limits": { "memory": "64M", "pids": 8 } }
  ],
  "collections": [
    { "name": "notes", "key": "id",
      "fields": { "id": "string", "text": "string", "at": "time" }, "class": "local_only" }
  ],
  "models": [ { "slot": "main", "tier": "work", "needs": ["tools"] } ],
  "triggers": [ { "id": "tick", "source": "schedule", "every": "1m", "missed": "skip", "emits": "hello.tick" } ],
  "policies": [ "policies/on_tick.json" ],
  "permissions": [ { "kind": "autostart", "reason": "需要在后台定时记一笔", "required": true } ],

               "model": { "work": { "calls_per_day": 200 } } },

    "entries": [ { "id": "main", "title": "你好", "page": "home" } ],
    "pages": [ { "id": "home", "title": "你好", "layout": [
```

对应的策略文件（格式照 CardColony Harness 的策略契约，这里只示意「事件 → 动作」）：

```json
{ "id": "on_tick", "scope": { "kind": "project" }, "watch": ["hello.tick"],
  "when": { "event": { "types": ["hello.tick"] } },
  "then": { "action": "node.invoke", "node": "ticker", "inputs": { "at": "{event.at}" } } }
```

**校验分三层，全过才算合格的包**
1. 结构：符合清单的模式定义。
2. 引用：清单里每个名字都指得到东西（卡引用的槽位、策略引用的节点、页面引用的记录集……）。
3. 合规：清单里用到的每一种受控能力都在 `permissions` 里申请了；「本地卡／可出境卡」的划界规则不被违反（C6）；界面上每个可操作控件都对应一个已声明的动作（C8）。

**判据**
绿：绿样本集全部通过；同一个包校验两次结果逐字段相同。
红：红样本集逐条被拒，每条拒绝带稳定的原因码，并指到清单里的具体位置。至少包含——表外字段、悬空引用、用了没申请的能力、带安装脚本、路径逃出包外、签名与内容不符。

### C2 系统调用面

**目的**：核心进程之外的一切——程序节点、系统节点、系统壳、应用界面——与系统打交道的唯一接口。它就是这套系统的「系统调用表」。

**四个面**

**① 参与者协议（程序节点用）。** 程序节点就是 CardColony 协议下的一个标准输入输出参与者，**不另造协议**。在它之上只加约定，不加帧类型：
- 启动时拿到的环境：我是哪个应用的哪个实体、哪种工作方式。
- 看得见的目录：自己的包（只读）、自己的卷（读写）、本次调用的输入文件（只读）、本次调用的输出目录（读写）、临时目录。
- 一次性节点：收到一条调用消息（调用号、触发来源、输入）→ 处理 → 经写请求交结果（调用号、状态、输出）→ 退出。没交结果就退出，算失败。
- 常驻节点：握手后一直运行，随时可经写请求产出事件；收到停止消息，收尾后退出。
- **对外效果只有「写请求」一条路**。标准输出只走协议帧；日志走标准错误，系统收作诊断材料，不是事实。
- 程序节点没有读接口：它需要的输入由调度方在调用时备好（经权限检查后放进调用消息或输入文件）。

**② 动作目录。** 一切效果都是某个已登记动作类型的一次意图。每个动作类型登记八栏：名字／谁有资格发起（对应哪种授权）／载荷的模式／由谁执行／六种结果在这里各是什么意思／幂等键怎么定／可不可逆／崩在中途怎么算。v1 的动作：

| 类别 | 动作 | 谁可发起 | 谁执行 |
|---|---|---|---|
| 应用数据 | `record.put`、`record.delete`、`artifact.put` | 本应用的实体；用户经界面 | 数据面 |
| 程序节点 | `node.invoke`、`node.start`、`node.stop` | 本应用的策略与卡；用户经界面；系统 | 节点调度 |
| 智能体 | 派活 | 见 CardColony（基线 B2） | CardColony 执行层 |
| 模型 | `model.call` | 本应用已绑模型槽位的实体（非卡实体走这条） | 模型分档 |
| 用户 | `user.notify`、`user.ask`；`user.answer` | 前两个：本应用实体（需授权）；后一个：用户 | 通知与待办 |
| 网络 | `net.fetch` | 本应用实体（需授权，且目标主机在授权范围内） | 系统取数节点 |
| 设备 | `device.write` | 本应用实体（需授权） | 该设备的驱动节点 |
| 数据放行 | `data.release` | 本地卡申请，用户批准 | 数据面 |
| 宿主 | 关机、重启、配置网络、设置时间、应用系统更新、恢复出厂 | 用户；应用只能「申请」（需授权，且每次都要用户确认） | 特权手臂 |
| 模型 | 设置绑定、安装或移除本地模型 | 用户 | 模型分档；特权手臂 |
| 应用生命周期 | 暂存、安装、启动、停用、升级、卸载、导出、导入 | 用户 | 应用管理 |
| 授权与配额 | 授予、撤销、设置配额 | 用户 | 授权；配额 |

**③ 事件目录。** 系统域（应用生命周期、授权、配额、宿主事实、设备、模型、升级、通知与待办）与应用域（记录变更、节点调用、触发落点，以及应用自己声明的事件类型）的事件类型清单。每个类型照 CardColony 卡侧的规矩声明齐八项（必填字段、可选字段、不适用字段、主体与对象、影响哪些投影、谁可读、事实帧还是过程帧、保留等级）。缺声明的类型不进投影、不参与条件求值。

**④ 用户面。** 系统壳与应用界面读数据的唯一通道：快照可拉、增量只推、用户操作提交。**沿用 CardColony 用户面契约的全部纪律**（版本连续、缺口即重同步、不轮询、同一视图快照与增量同源）。本系统只在其上登记新的视图类型与用户操作：系统视图（应用列表、待办与通知、宿主状态、模型、用量、近况）、应用记录集视图；会话视图与画布视图直接用 CardColony 的。

**版本**：系统调用面有一个版本号。v1 冻结之后只增不改；应用在清单里写它需要的最低版本，系统拒绝装不兼容的包并说明原因。

**扩展点一律是登记表里的数据**：动作类型、事件类型、授权种类、界面组件、宿主事实主题、设备类别、触发来源、运行体驱动、模型档位。
绿：新增任意一项，改动只落在「登记表的一行＋新增的实现文件」。
红：新增一项需要改核心多处、或漏登记时静默失效（必须启动期拒绝并指出缺哪一项）。

**总判据**：一个没读过内部实现的人，只凭本契约的文档，能做出一个可安装、可运行的应用（由 D9 的干净验证方来证，K§6·D9-U5）。

### C3 运行体承载与沙箱

**目的**：让「授权是什么，程序节点就只能做什么」由 Linux 内核强制，而不是靠节点自觉。

**规则**
1. 运行体怎么承载是一个可登记的驱动。v1 三种：进程内（CardColony 既有）、开发模式子进程（无沙箱，只用于开发）、**Linux 沙箱**（整机上唯一允许的方式）。
2. Linux 沙箱：每个运行体一个 systemd 瞬态单元，放在所属应用的切片下。它的标准输入输出是核心进程递过来的管道——所以在协议眼里，它和开发模式下的子进程是同一种参与者。
3. **默认什么都没有**：无网络、无设备、系统只读、只看得见自己的包与卷、独立的动态用户、禁止提权、系统调用受限。
4. 能力只来自授权与声明，映射关系是一张数据表：

| 清单里的声明或得到的授权 | 沙箱上多出什么 |
|---|---|
| 内存、CPU、任务数的限额 | 对应的 cgroup 上限 |
| 卷 | 该卷可读写，受项目配额约束 |
| 设备槽已绑定 | 只放行那一个设备节点 |
| 系统取数节点、入站网关（只有系统 work 能声明） | 放行网络 |
| 本地模型运行时（只有系统 work 能声明） | 模型库只读；可选的图形处理器设备 |

5. 生命周期只听租约。瞬态单元不带自动重启；单元退出产生监督事件，重启与否由监督按声明决定。
6. 授权被撤销时：停掉受影响的运行体，按新的授权重新拉起（规则简单、结果确定，不做运行中热改）。
7. 对账：单元实际属性与授权投影不一致，就是一条事件加一次纠正。对账只在两个时机做——单元启动时、授权变更事件到来时。不轮询。

**判据**（强制类判据只认在自带内核的虚拟机里取的证）
绿：同一个程序节点，开发模式下与沙箱里行为一致（同样的输入，同样的写请求）。
红（每条都必须失败并留事件）：未授权联网；读别的应用的卷或包；读聚落存储；访问未授权的设备；提权；内存超限后仍存活；任务数超限后继续派生；被撤销授权后仍保有那项能力。

### C4 宿主事实与宿主动作

**目的**：机器自己的状态成为卡网络里的事实；对机器的操作成为经闸的动作。这是「应用」永远做不到、而「系统」做得到的那一层。

**宿主事实**

| 主题 | 内容 | 什么时候产生一条事实 |
|---|---|---|
| 启动与关机 | 启动完成、关机请求、上次是否正常关机 | 发生时 |
| 电源 | 接电或电池、电量档位 | 接电状态变化；电量跨档（不逐百分比） |
| 网络 | 链路通断、能否上网 | 变化时 |
| 存储 | 数据分区余量档位 | 跨档 |
| 热与内存压力 | 档位 | 跨档 |
| 设备 | 插入、拔出；类别、厂商、型号、序列号 | 发生时 |
| 时间 | 时钟被调整、日期翻页 | 发生时 |

规则：
1. 事实只在写进事件日志之后成立。特权手臂只转述信号，不判断、不合并、不解释。
2. 分档规则是数据（电量几档、余量几档），不写死在代码里。
3. 每次开机补一条当前读数作为基线，防止漏掉停机期间的变化。
4. 应用要收某个主题，必须有通到相应系统实体的线，而线只在用户授权后建。没有线，就收不到。

**宿主动作**

规则：
1. 目录里每个宿主动作有且只有一个执行器；执行在特权手臂里发生，**特权手臂只接受带「已受理意图」凭据的请求**。
2. 幂等按交接号：同一个交接号再来，只回执、不再动手。
3. 不可逆的（关机、重启、应用系统更新、恢复出厂）：用户亲手发起的直接执行；应用申请的，每次都生成一条待办让用户确认。
4. 执行前系统崩了，按 CardColony 的规则记结果不明，不假装做了或没做。

**设备作为节点**
- 清单声明一个设备槽（要什么类别）；安装或运行时由用户把一台具体设备绑到槽上。
- 绑定后：系统为这台设备起一个驱动节点（常驻、只放行这一个设备）。设备来的数据成为应用项目里的事件；对设备的写是 `device.write` 意图，驱动节点是它的执行器。
- 设备拔掉：驱动节点结束，应用得到一条「等待条件：缺设备」读数；插回同一台，自动恢复。
- v1 实做的类别：串口类。其余类别是登记表上的空位。

**判据**
绿：在虚拟机里注入设备插入、断开网络链路、写满数据分区，各自产生恰好一条对应事实；有线的应用收到。
红：没有线的应用收到了；特权手臂执行了一条不带凭据的请求；同一交接号被执行了两次；应用未经用户确认就让机器重启。

### C5 触发

**目的**：把「什么让应用动起来」统一成一件事——一条落在应用项目里的事件。

| 来源 | 清单里怎么声明 | 怎么变成事件 |
|---|---|---|
| **用户输入** | 界面上的对话与动作，不必单独声明 | 用户操作经闸 |
| **定时** | 间隔或日历式时刻；错过了怎么办（跳过／补一次） | 系统的定时源到点产生事件 |
| **网络** | 入站：声明一个接收点，系统分配地址与令牌。出站：定时触发一个程序节点，用 `net.fetch` 去取 | 入站网关收到后把内容存成产物、产生事件 |
| **宿主与设备** | 声明主题或设备槽，配相应授权 | 沿线投递（C4） |

规则：
1. 清单的 `triggers` 只说「来源是什么、落成哪种事件」。事件来了之后做什么，由 harness 策略决定（唤醒哪张卡、调用哪个节点、通知谁）。
2. 应用停用＝它的所有触发解除武装，四类来源都不再落点；重新启动才恢复。
3. 入站接收点默认关闭。打开等于让机器对外开一个口，必须用户在系统设置里同意；每个接收点有独立令牌。
4. 时钟被调整后，定时触发按声明的错过规则处理，不因时钟回拨而重复落点。

**判据**
绿：四类来源各有一条完整的链，从来源到落点事件，事件里记着来源。
红：停用后仍有触发落点；无令牌或错令牌的入站请求被接受；时钟回拨导致同一时刻触发两次。

### C6 模型分档与绑定

**目的**：应用说「我要一个什么样的模型」，机器回答「我这里给你哪一个」。应用不写死模型名。

**档位**（登记表里的数据，v1 三档）

| 档位 | 用来做什么 | 典型承载 |
|---|---|---|
| 反射档 | 分诊、分类、抽取、要不要打扰人 | 本机上的小模型 |
| 工作档 | 日常推理、带工具干活 | 本机上较大的模型，或远端模型 |
| 审议档 | 研判、合议、规划 | 本机能拿到的最强者，通常在远端 |

**规则**
1. **槽位**：清单为每张卡声明一个槽位——哪一档、是否必须本地、需要哪些能力（工具调用、结构化输出……）。
2. **绑定**：机器上有一张「档位 → 候选模型」的表（首启向导与设置里维护）。安装时系统为每个槽位解出一个具体模型；解不出就不让装，并明说缺什么、怎么补。绑定结果是事件，用户随时可改，改了对之后的新工作生效。
3. **本地模型运行时**是系统 work 里的一个系统节点：提供 OpenAI 兼容端点，按需加载；内存吃紧时由内存压力事实触发卸载（不用空闲计时）。镜像不带权重。
4. **远端模型**：凭据由用户在向导或设置里填，进系统凭据库。**凭据不进事件、日志、产物、界面、卡面、仓库。**
5. **谁调模型**：卡经执行层跑 run 调模型；其他实体经 `model.call` 动作调模型。两条路径走同一套槽位绑定、同一套计量、同一种本地／可出境划界。
6. **用量**：每次模型调用的用量取自执行层已有的调用事件，作为配额核算的输入（C10）。不另记一本账。

**数据不出机的划界**（「组织和数据是你的」的最小实现，全部用线和授权这两样现成的东西）
- 每张卡在清单里标 `local`（本地卡）或 `open`（可出境卡）。本地卡只能绑本机模型；可出境卡可以绑远端模型。
- 每个记录集、每个设备槽、每个宿主主题在清单里标「仅本地」或「可出境」。**默认仅本地。**
- 规则一：「仅本地」的数据，只有本地卡和程序节点读得到。
- 规则二：本地卡到可出境卡之间不许有通信线，除非那是一条声明了的**放行线**。
- 规则三：放行线上每传一次，都是一次 `data.release`——要么用户逐次批准，要么用户事先给过一条范围明确的常设授权。每次放行留授权记录。
- 规则四：应用要用远端模型，必须申请 `models.remote`，安装时系统用人话告诉用户「这个应用的哪些卡会把内容发到机器外面」。

**判据**
绿：断网时，本地卡照常完成工作；可出境卡的工作如实显示失败或受阻。
绿：在「仅本地」的数据里埋标记串，跑完整套场景，在出机口抓到的全部请求里搜不到。
红：槽位解不出仍装上了；本地卡被绑到远端模型；绕开放行线把仅本地的内容送进可出境卡的上下文；凭据出现在任何事件、日志、产物或界面里（扫描）。

### C7 应用数据面

**目的**：应用的数据怎么存、谁能读写、界面怎么拿到。

**规则**
1. **记录集**：清单声明名字、键、字段、仅本地或可出境、保留多少。写＝`record.put`／`record.delete`，经闸，一次一条，同键整条覆盖；不符合字段声明的写被拒。
2. **读**有三条路，各管各的：界面读记录集视图（快照＋增量）；卡用查询工具读（受 C6 划界约束）；程序节点不主动读，它要的输入由调度方在调用时取好递给它。
3. 记录集视图是事件的投影：可删、可重建；同一段事件流重放，读数逐字段一致。
4. **产物**：程序节点把文件放进输出目录、在结果里列出；系统先存进产物库，再提交引用它的事件。记录可以引用产物；界面按引用取。
5. **卷不是事实源**：界面读不到卷；别的实体读不到卷；要给别人看的东西必须落成记录或产物。
6. **卸载**时由用户三选一：保留数据／导出后删除／直接删除。删除的语义照 CardColony 的项目删除（留墓碑）。
7. **导出包**：包文件＋全部记录集的当前内容＋被引用的产物＋（清单声明要带的）卷＋会话文字稿，用设备密钥签名。**导入**：在目标机装同一个包，再经一条导入动作把记录与产物写进新实例（经闸，记明来源）。授权不随导出走——导入时重新同意；凭据不导出。

**判据**
绿：导出 → 在第二台虚拟机导入 → 记录与产物逐条一致（按哈希）；应用接着能用。
红：不符合声明的写被接受；应用甲的实体读写了应用乙的记录集；可出境卡读到仅本地的记录集；界面读到了卷里的内容；导出包里出现凭据。

### C8 应用界面面

**目的**：用起来像应用，不像管理台。

**两种形态**

**① 声明式界面（可选）。** 页面＝若干组件的排列，组件来自系统的组件表（登记表里的数据）。v1 的组件：

| 组件 | 做什么 |
|---|---|
| `conversation` | 与应用的入口卡对话（用的就是 CardColony 的会话视图） |
| `collection_list`、`collection_detail` | 看一个记录集、看其中一条 |
| `status_tiles` | 摆几个关键读数 |
| `action_button` | 一个按钮对应一个已声明的动作 |
| `form` | 填几项内容，提交成一个已声明的动作 |
| `artifact_view` | 看一个产物（文本、Markdown、图片） |
| `inbox` | 本应用等你处理的事 |

**② 自带前端包。** 包里带一套网页，在系统壳的应用区域里隔离运行：不能联网，够不到系统壳的其他部分；只能经一座桥做三件事——读视图、订阅视图、发起已声明的动作。

**规则**
1. **界面诚实**：界面上每个可操作的控件，必须对应清单里声明的一个动作。声明式界面由校验保证；自带前端经桥发起未声明的动作，一律被拒。
2. **系统层永远在应用之上**：授权、安装、宿主动作确认、配额处置，这些对话只由系统壳画——应用画不出、也盖不住。应用区域之外，永远显示「这是哪个应用」。
3. **界面不存业务状态**：清掉界面的本地存储再打开，看到的内容不变（只有主题、面板宽度一类偏好例外）。
4. 状态词由服务端给，前端不拼。
5. 没有界面的应用是合法的（纯后台）；主屏给它一张状态卡。
6. **工作台不在壳里**：CardColony 的会话与画布是开发工具的界面，给造应用的人；普通用户的壳没有它的入口——不装开发工具，它就不存在。
7. **场景不设限**：聊天只是组件表里的一个零件，不是默认形态；自带前端包是一等公民——消费级应用多半要自己画界面。

**判据**
绿：四个样品应用的主流程全部在应用界面内完成，不需要打开系统监视器。
红：自带前端包发出网络请求成功；经桥调用未声明的动作成功；应用遮住或仿冒了系统对话；清掉本地存储后业务内容变了。

### C9 授权与同意

**目的**：应用能做什么，用户说了算，而且看得懂。

**授权种类**（登记表里的数据，v1）

| 种类 | 用人话说 | 什么时候问 |
|---|---|---|
| `autostart` | 开机后在后台自己工作 | 安装时 |
| `notify` | 给你发通知、向你提问 | 安装时 |
| `models.remote` | 把内容发给机器外面的模型（列出是哪些卡） | 安装时 |
| `net.fetch` | 让系统替它去这些网站取内容（列出主机） | 安装时 |
| `net.inbound` | 开一个口，接收外面推来的消息 | 安装时；另有系统设置里的总开关 |
| `host.facts` | 知道这台机器的某类状态（列出哪几类） | 安装时 |
| `device` | 使用某类设备 | 安装时；绑定到具体那一台时再确认 |
| `host.action` | 申请对机器做某件事 | 安装时登记资格；**每次执行都要你确认** |
| `data.release` | 把「仅本地」的内容交给会联网的卡 | 每次；或你事先给的常设授权 |
| 各项配额 | 见 C10 | 安装时 |

**规则**
1. 授权就是 CardColony 的授权事件：谁、对什么范围、能做什么、从何时到何时、依据哪一次同意。
2. 同意界面上的每一条，由清单的申请**机械生成**一句系统的话，再附上应用自己写的理由。两者分开显示——哪句是系统说的，哪句是应用说的，一眼分得清。
3. 必需的授权被拒 ⇒ 不安装。非必需的被拒 ⇒ 照装，相应功能如实显示「未授权」。
4. 随时可撤销；在下一次执行前的检查里生效；受影响的运行体按 C3 第 6 条处理。
5. 升级后的新版本多申请的部分，重新问；不默认继承。
6. 没有「全部允许」这种总开关。

**判据**
绿：同意界面的条目与清单的申请逐条对应；撤销之后，下一次同类动作的结果是「已撤销」。
红：清单没申请的能力被用成了；升级后新增的授权未经同意就生效；应用自己画的同意框被系统当了真。

### C10 配额与核算

**目的**：一个失控或贪心的应用，拖不垮机器，也花不光你的钱。

| 资源 | 谁来强制 | 超了怎么办 |
|---|---|---|
| 同时在跑的运行体数、未了结的意图数 | CardColony 的项目预算 | 新的被延后或拒绝 |
| 程序节点的内存、CPU 份额、任务数 | 内核（cgroup） | 超内存的被杀，记监督事件；CPU 只限份额 |
| 存储：记录与产物 | 闸处按项目记账 | 新的写被拒 |
| 存储：卷 | 文件系统的项目配额 | 写失败 |
| 模型用量（按档位：次数与输入输出量） | 派活前的检查 | 新的派活被延后，原因＝额度用尽 |
| 系统代取的次数与流量、通知与提问的条数 | 闸处按项目记账 | 新的被拒 |

**规则**
1. 配额是声明数据：应用在清单里申请，用户安装时批准（可以批得比申请的少），之后可在设置里改。每次变更是事件，只影响以后。
2. 机器级上限压在所有应用之上；系统给自己留保底——**应用把盘写满，不会让核心进程写事件失败**。
3. 按天算的额度，靠「日期翻页」这条宿主事实重置，不靠轮询。
4. 额度用尽：应用得到「受限」读数；用户得到一条待办（加额／等重置／停用），同一原因只提一次。
5. 用量读数都是事件的投影；程序节点的资源读数只在生命周期边界取（启动、退出、被杀），不定时采样。
6. 本契约只管上限与归属，不设性能门槛（§12）。

**判据**
绿：任何一项用量读数都能逐笔对回事件。
红（反例应用逐条来；每一条都要求**机器仍然可用**——系统壳能操作、核心进程能写事件）：疯狂派生进程；吃内存；写满自己的卷；刷记录；刷模型调用；刷通知。另红：应用把盘写满导致核心进程写事件失败。

### C11 镜像、分区与升级

**目的**：系统作为一个整体被交付、被升级、被恢复。

**规则**
1. 一条命令从仓库构建出镜像；同样的输入得到同样的软件包清单。
2. 镜像两种配置：**开发**（可远程登录、可远程驱动界面、带调试工具）与**发行**（这些全部关闭）。两者的差异是一张明确的清单；发行镜像里不得残留任何开发口。
3. 分区照 §4.4；系统分区运行期只读；首次开机自动建立并扩展数据分区。
4. **升级**：新系统写进不在用的那一份 → 重启进新系统 → 核心进程写出「启动完成」事实才算确认；否则自动回到旧的那一份。数据分区不动。
5. 新系统必须读得了旧系统留下的聚落存储。存储格式有不兼容的变化，必须带迁移，并且拿「上一版留下的、有内容的存储」来测。
6. 升级来源（v1）：本地文件或一个网址；升级包带校验。
7. **安装到本机磁盘**：从启动介质把系统复制到选定的内置磁盘。选哪块盘必须用户确认，并明示这块盘会被清空。
8. **恢复出厂**：清空数据分区。不可逆，用户确认。
9. 镜像里不含：模型权重、任何凭据、任何用户数据、构建机器的痕迹。

**判据**
绿：虚拟机从镜像启动到主屏；升级之后应用和数据都在；故意做坏的新系统自动回退、数据不丢。
红：运行期系统分区被写入；发行镜像里能远程登录；升级中途断电后两份系统都起不来。

### C12 开发者工具链

**目的**：别人能做出应用。

**组成**
1. **命令行工具**：新建应用骨架、校验、打包、签名、装到一台开发中的机器上、看日志、导出。
2. **开发模式**：在普通 Linux（含容器、WSL）里起同一套核心进程与系统层，不需要镜像。沙箱换成开发模式子进程，宿主事实由模拟器给。用于快速迭代。
3. **SDK**：程序节点库（Go）；一个只用标准库的单文件参考实现（Python）；自带前端包用的桥（JavaScript）。
4. **文档四章**：做你的第一个应用；清单参考（由模式定义生成，不手写）；程序节点与界面；权限、配额与数据划界。

**规则**
- 工具里的校验与打包，和系统安装时用的是**同一份代码**。不许有两套校验。
- 开发模式与整机的差别是一张明确的清单：哪些判据在开发模式下不成立（一切强制类判据都不成立），写在文档里。

**判据**：干净验证方只读文档做出的应用，能在发行镜像上安装并运行；它做的过程中记下的「猜测清单」为空（K§6·D9-U5）。

## §7 主链路

每条链路只写骨架步骤与不变量。实现细节由承接的单元卡在自己的需求文档里展开，但不得改变这里的步骤顺序与不变量。

**链路一 · 开机**：见 §4.2。不变量：重建完成之前没有任何触发落点。

**链路二 · 首次开机向导**
1. 选语言 → 2. 连网络（可跳过）→ 3. 配模型：填远端模型的凭据，或下载一个本地模型，或两者，或都跳过 → 4. 生成设备密钥 → 5. 进主屏，自带应用已在。
不变量：每一步都能跳过；跳过的后果如实显示（例如「没有可用模型，需要模型的应用会等待」）；向导里填的凭据只进凭据库。

**链路三 · 安装应用**
1. 用户选一个包（本地文件或网址）→ 暂存：验内容哈希、验签名、做三层校验（C1）。
2. 解依赖：模型槽位能否绑上、设备槽有没有可绑的设备、需要的系统版本。
3. 生成同意界面（C9）；用户逐条同意或拒绝，填参数与密钥。
4. 安装：建项目 → 建实体 → 建线 → 登记策略、工具、区表 → 建卷并设配额 → 写入绑定与授权事件。
5. 启动：武装触发、拉起常驻节点 → 出现在主屏。
不变量：每一步是一条或多条经闸的意图；**装到一半崩了，重启后要么接着装完，要么干净撤回，不留半个应用**；同一个包装两次，第二次是幂等的。

**链路四 · 从触发到结果（后台）**
1. 来源产生事件（定时到点／入站网关收到／宿主事实沿线到达／设备来数据）。
2. 应用的 harness 策略条件成立 → 发起动作意图：调用某个程序节点，或给某张卡派活。
3. 闸：查授权、查配额、查停止令 → 受理。
4. 执行：程序节点在沙箱里算，或卡跑一轮（装配上下文 → 调绑定的模型 → 工具经闸）。
5. 产出：记录变更、产物、通知，全部经闸落成事件。
6. 投影更新 → 界面增量推送；用户不在场也照样完成。
不变量：全程没有不经闸的效果；每一步都能在事件里指认；用户没打开界面，不影响任何一步。

**链路五 · 用户在应用内交互**
用户在应用页面操作（对话只是其中一种形态）→ 用户操作经闸 → 落到应用声明的落点：入口卡跑一轮，或一个已声明的动作 → 结果出现在界面上；中间的工具与动作同链路四的第 3–6 步。
不变量：断线重连后不出现重复或半截的响应（沿用 CardColony 的流式收束）。

**链路六 · 停用与强制停止**
- **停用**：解除全部触发 → 发项目级停止令（软停）→ 在跑的收尾 → 主状态「已停用」。界面如实显示「停止中，还有几个在收尾」。
- **强制停止**：撤销该应用的全部租约（沙箱单元被停）；卡的在途调用按 CardColony 的硬停处理。CardColony 的硬停档尚不可用时，界面必须明示「智能体部分当前只能软停」，不许谎报已立刻停止。
不变量：停用之后没有任何新的触发落点、没有任何新的意图被受理。

**链路七 · 应用升级**
新包暂存与校验 → 比较新旧清单 → 新增的授权重新问 → 停用旧版 → 按 `upgrade` 的声明迁数据 → 按新清单调整实体、线、策略（用 CardColony 的实体生命周期语义；被移除的实体归档，不直接抹掉）→ 启动新版。
不变量：升级失败就回到旧版的可运行状态；数据不丢。

**链路八 · 系统升级**：见 C11 第 4–6 条。

**链路九 · 卸载、导出与导入**：见 C7 第 6–7 条。不变量：卸载后，这个应用的沙箱单元、线、触发、授权全部不再存在或不再有效；它的历史照 CardColony 的规则可查。

**链路十 · 崩溃与断电恢复**
- 程序节点崩溃：监督事件 → 按声明重启或不再重启 → 不再重启的，应用得到「出错」读数。
- 核心进程崩溃：systemd 重新拉起 → 按日志重建 → 清理孤儿沙箱单元（一切单元都要能对回一张有效租约，对不回的停掉）→ 重新武装。
- 整机断电：下次开机走链路一。
不变量：已确认的写不丢；不出现半截状态；在途而结果不明的，如实记为结果不明。

**链路十一 · 配额用尽**：见 C10 第 4 条。不变量：受限的只是用尽的那一项，应用的其他部分照常。

**链路十二 · 设备插拔**：见 C4「设备作为节点」。不变量：设备不在时，应用不报假数据；插回同一台，不需要用户重新授权。

## §8 数据权威矩阵

| 事实 | 唯一权威 | 派生副本（可删可重建） | 丢了怎么办 |
|---|---|---|---|
| 装了哪些应用、各自什么状态 | 系统项目里的生命周期事件 | 应用列表视图 | 重放事件 |
| 应用里有哪些实体、线、策略 | 应用项目里的事件 | 拓扑投影、策略索引 | 重放事件 |
| 谁被授权做什么 | 授权事件 | 授权投影、沙箱单元属性 | 重放事件，重新下发属性 |
| 配额与用量 | 预算事件、用量来源事件 | 用量视图 | 重放事件 |
| 模型绑定 | 绑定事件 | 绑定表 | 重放事件 |
| 应用数据 | 记录事件、产物库 | 记录集视图 | 重放事件 |
| 机器状态 | 宿主事实事件 | 宿主状态视图 | 开机补基线读数 |
| 正在跑的进程 | 租约事件 | systemd 单元 | 按租约重新拉起，清孤儿 |
| 应用包的内容 | 包文件（内容寻址，事件引用其哈希） | 解包目录 | 由包文件重新解包 |
| **凭据与设备私钥** | **机器私有区（唯一不在事件日志里的权威）** | 无 | 丢了就是丢了：凭据由用户重填；设备密钥重新生成，旧导出包的签名不再能由本机复核 |
| 界面偏好 | 界面本地存储 | 无 | 无所谓 |

**两条纪律**
1. 除了「凭据与设备私钥」那一行，任何持久状态都必须能指出它是哪些事件的投影。指不出来的，不许存在。
2. 事件里只记「某凭据已设置、已更换」及其指纹，永不记值。

## §9 安全模型

**信任边界（从最可信到最不可信）**：系统分区上的系统软件 ＞ 用户本人 ＞ 核心进程 ＞ 特权手臂（权限最大，所以接口最窄）＞ 系统节点 ＞ 已安装的应用（其程序节点、卡的输出、自带前端包）＞ 外面来的一切（包文件、网页内容、入站推送、设备数据、模型的回答）。

| 威胁 | 对策 | 落在哪份契约 |
|---|---|---|
| 恶意或写坏的应用越权读写 | 沙箱默认无权；能力只来自授权；内核强制 | C3、C9 |
| 应用拖垮机器或刷爆额度 | 配额在四个强制点上；系统保底 | C10 |
| 应用把私人数据送出机器 | 默认仅本地；本地卡与可出境卡划界；放行留记录；程序节点无网络 | C6、C3 |
| 应用仿冒系统对话骗取同意 | 系统对话只由系统壳画；应用区域隔离 | C8 |
| 坏包、被篡改的包 | 内容寻址；签名；三层校验；包内无安装脚本 | C1 |
| 外面的内容（网页、推送、设备数据、模型回答）夹带指令 | 一律当数据，不当指令；它们触发的任何效果仍要过闸与授权；不可逆动作要用户确认 | C2、C4、C9 |
| 核心进程被攻破后直取 root | 特权手臂只执行带受理凭据的类型化请求，不执行任意命令 | C4、§4.1 |
| 凭据泄露 | 凭据只在凭据库；应用实体读不到明文；全链路扫描 | C6、§8 |
| 升级把机器变砖 | A/B 与自动回退；存储向前兼容测试 | C11 |
| 开发口遗留在发行版 | 两种镜像的差异清单；发行镜像扫描 | C11 |

**不在 v1 的防护**（如实列出，不许对外写成已具备）：物理接触攻击（无安全启动、无磁盘加密）；内核自身的漏洞；事件日志被拥有 root 的人篡改（无日志签名）；远端模型提供方对所收内容的处置。

## §10 技术选型、依据与撤退条件

每一项都要经 S0 的探针证实。**探针不成立，就按撤退条件换，换的事实与原因记进选型表**——不许硬撑，也不许不声不响地换。

| 编号 | 选什么 | 为什么 | 撤退条件 → 换成什么 | 探针 |
|---|---|---|---|---|

### 11.2 测试四层

| 层 | 在哪跑 | 测什么 | 证据效力 |
|---|---|---|---|
| **L1 单元** | 任意系统 | 纯逻辑：校验器、映射、投影、状态机 | 只证逻辑 |
| **L2 系统容器** | 建造环境里的容器（开发模式，或带 systemd 的容器） | 多个进程拼起来的行为：安装、触发、数据面、界面数据 | 可作单元验收的证据；**不作强制类判据的证据** |

## §12 性能与资源纪律

1. **不设数值门槛。** v1 不写任何「必须小于多少毫秒、多少兆」的放行条件——没有依据的数字会变成假判据。
2. **要形态。** 日常操作的成本只与「变化了的东西」成正比，不与应用总数、事件总数成正比；查询走已建好的投影，不现场扫日志；状态靠推，不靠轮询；没有定时器驱动的状态刷新。
3. **要基线。** S2 出口时由 D9 在同一台虚拟机配置下量一次并留档：上电到主屏的时间、空闲时内存、事件到界面的时延、安装一个样品应用的时间、十个应用常驻时的空闲占用。之后每个阶段出口同法复测并与基线比对，结论只有三种：不劣于基线／劣化但在声明的容差内／超出容差须解释。
4. **要累积测试。** S4 的长时运行只为让累积规模发生，判据是「内存与响应不出现不可用级的问题」；跑多久只是载体，不是判据。
5. **建造过程的并发上限。** 同时进行的镜像构建数与虚拟机数由 D9 的测试槽统一排队，上限是声明值（缺省：一个构建、两台虚拟机；依据类型＝量级判据：本机同时还在跑 5700 服务，资源相撞会两边都垮）。

| 需求 | 希望落在它的哪个扩展面 | 如果扩展面不存在 |
|---|---|---|

| 登记本系统的事件类型 | 事件类型的声明 | 同上 |

| 一个应用实例对应一个项目，并带预算 | 项目与项目预算 | 不需要补件 |

### 13.3 融合补件的规矩（全文见 R§七）

- 只许是**通用扩展面**：对 CardColony 自己也成立、不带「应用」「宿主」这类本系统语义的词；能说清「谁能登记、谁受理、受理不了怎么拒绝启动」。
- 不许是特判：出现「如果是系统层就……」的分支，即判不合格。
- 每件登记进融合补件账本；保护区内的每一处改动，都必须能对回账本里的一件。对不回的，就是越界。
- 属于 CardColony 自己没收口的事（基线 B1–B10），不许借融合补件之名在这边另做一套。
