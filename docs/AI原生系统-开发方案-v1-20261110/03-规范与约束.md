## §一 定位、适用与效力

1. **适用范围**：本规范约束参与本项目的全部建造卡（根卡、域卡、单元卡、worker 卡、UI 卡、验收卡、执笔卡）及在场职能（总裁、产品经理、技术总监、测试验收总监、涌现守门）。没有例外卡。
2. **产品基准（全树与评审共用，不必再问）**：
   - **用户是谁**：两类人分开——**普通用户**（每天拿这台机器用各类 AI 应用的消费者，不需要知道什么是卡、事件、画布、策略、工作台）；**做应用的人**（在 CardColony 工作台里不写代码组装智能体节点并封装成应用包的人，或用命令行与 SDK 写代码做应用的人）。
   - **核心定位**：一个给普通用户日常使用 AI 应用的通用操作系统——占 iOS、Android 的位置，但为 AI 应用而生；卡网络的运行机制沉在系统里做运行时；CardColony 是机上的开发工具。应用形态不设限，智能体组织是封顶不是门槛，聊天只是可选组件不是默认界面。
3. **效力顺序**：用户当面裁定 ＞ 本方案四份文件＋`docs/aios/plan/勘误表.md` ＞ 由本方案转写出的各卡需求正稿与 `contracts/` 冻结件 ＞ 项目 `rules.md` ＞ 其余一切（原型代码、旧文档、代码注释、模型自己的想法）。
4. **卡片的本分**：卡片负责照方案执行、取证、如实汇报——**不负责替用户重新设计架构或改写定位**。认为方案有错、有洞或两处打架，一律走勘误通道（§五），严禁私下偏离。

## §二 产品与架构铁律

以下七条是三条根原则（G§三）与多轮定位修正在施工层的硬边界，任何需求草稿、代码提交与验收判据触犯任一条即判不合格：

1. **Linux 只执行、不裁断**：除机器私有区的凭据与设备私钥外（A§8），一切持久业务状态都必须能指认它是哪些事件的投影；删空派生区重启必须逐字段复原。严禁把 systemd 单元状态、进程内存、应用卷文件或前端本地存储做成第二事实源。
2. **系统即第一个 work，零特权暗门**：系统服务与 CardColony 开发工具一律走公开契约里的同一套闸、线、动作目录与用户面，只持有登记在册的授权事件。特权手臂（`colony-hostd`）只收核心进程发来的、带「已受理意图」凭据的闭集类型化请求，**严禁提供「执行任意命令」接口**。
3. **应用形态不设限，工作台绝不进用户壳**：不把聊天当默认界面；无智能体、无组织的普通 AI 应用是一等公民；模型调用是通用系统能力（智能体回合与 `model.call` 走同一套槽位绑定、同一处额度检查、同一本用量账、同一套数据划界，且都必须把「延后／排队」当作合法结果而非失败处理）。未打开开发者模式时，系统壳任何页面不得出现开发工具或通往工作台的入口；普通用户界面的可见文案严禁出现禁用词：`卡`、`事件`、`画布`、`策略`、`闸`、`租约`、`投影`、`harness`、`会话`、`work`（对用户一律称「应用」）。
4. **v1 开发工具只做组装，不做「说需求自动造应用」**：工作台走通「建工作区 → 画布组装 → 试运行 → 封装 → 安装」闭环；封装出的包与命令行手写打出的包同格式、过同一份校验器，不因出自开发工具而多一分信任。
5. **扩展点一律数据化，名字不齐启动即拒**：十类扩展点（A§6·C2）皆为登记表数据；每一对「发出方—受理方」的名字集合在启动期做子集核验，差集非空当场拒绝启动并指明缺项，严禁静默降级或吞错放行。
6. **包与外部输入一律当不可信数据**：应用包与节点模板里严禁存在任何安装或导入时可执行的东西；抓回的网页、入站推送、设备读数、模型输出一律当数据，由它们触发的任何效果仍须过闸与授权，不可逆宿主动作每次都须用户亲手确认。
7. **数据默认仅本地，钥匙只进不出**：记录集、设备槽、宿主主题默认 `local_only`；本地方到可出境方严禁直连普通通信线，只许走放行线并逐次留授权记录；程序节点 v1 无直连网络能力。凭据与私钥只存机器私有区，永不进事件、日志、产物、界面回显、卡面、导出包、封装包或仓库。

## §三 时间、保护性中断与异常恢复纪律

1. **墙钟不是业务判据**：生产逻辑与验收判据严禁拿经过的墙钟时长充当状态成立条件——禁止用 `sleep` 等服务就绪、禁止用定时轮询刷新状态（一律靠事件投影与增量推送）、禁止把「连续跑满 N 小时」本身写成通过标准。S4 长时运行只是让事件与资源累积到声明规模的载体，判据是累积规模下的内存、响应与账目正确性（A§12）。
2. **保护性中断的三项硬条件**：外部网络取数、子进程调用、虚拟机脚本允许设保护性超时上限，但必须同时满足：
   - 上限值是声明数据，不硬编码在逻辑深处，且带依据类型（量级判据／同条件实测基线／产品目标；无依据标「候选值·待验证」）；
   - 每个保护性中断旁必须并存一条**不依赖时间的确定性断言**（核对事件、投影读数或稳定原因码）；
   - 超时触发时必须有明确归宿（中断、记原因码、交发起方策略或待办处置），**严禁把超时算作「测试环境抖动／用例无效」一跳了之**。
3. **崩溃、断电与「结果不明」**：
   - 已向发起方确认受理落盘的写，历经 `kill -9` 或虚拟机直接断电后一笔不许丢；确认前断电的那一笔重启后不得读成「已确认」。
   - 动作已越过进程边界但崩溃前未拿到回执的，恢复后一律记为 `uncertain`（结果不明）——`uncertain` 是合法终态，**严禁猜成成功或伪装成普通失败重试**；特权手臂侧靠交接号幂等防止重复动手。
   - 核心进程恢复后必须拿有效租约核对现存沙箱单元，对不回有效租约的孤儿单元一律停掉；全部重建完成前严禁放行任何触发。
4. **偶发红不许靠单跑洗白**：整机与加固套件里出现过一次失败，不得因为「单独重跑通过了」直接结案——必须定位原因，并回答：**该用例要验的机制在那次失败运行里到底有没有被触达、为什么没咬住**。

## §四 无人值守的四类裁定规则

全自动运行期间，卡片遇到方案未写死之处或需求评审分歧，按以下四类对号入座，不许越级自专，也不许鸡毛蒜皮全推给用户把树停住：

| 类别 | 判别标准 | 谁裁、怎么走 |
|---|---|---|
| **第一类 · 方案已定** | 四份方案文件、`勘误表.md`、`contracts/` 冻结件或 §十三 预裁定清单已有明文规定 | **直接照方案做。** 评审席若提出与方案相悖的意见，不改需求迎合；按方案定稿放行，同时把该意见交 D1-U6 记作勘误提请备查 |
| **第二类 · 原则可唯一下推** | 方案未写细，但只涉及域内内部实现，或由三条根原则与契约判据只能推出唯一合规做法，不牵动跨域接口 | **域卡／单元卡当场自裁。** 在本卡需求或现状块写明依据，不上报根卡、不进待裁清单。牵涉两张卡对接细节的，拉 D1-U3 在对齐场一次敲定；对不齐升根卡裁 |
| **第三类 · 保守且可逆** | 方案未写、存在多种合理做法，但同时满足四条：① 不扩范围、不降判据、不碰安全与数据主权红线；② 不锁死契约对外形态；③ 撤回办法明确且一天内可无损回退；④ 不花钱、不碰外部凭据、不动宿主设置、不做不可逆删除 | **选最窄最保守的一种先行，同时报根卡记入现状块「待追认清单」**（写明：定了什么、备选是什么、怎么撤回）。用户事后点头即销账，否决即按撤回办法改回 |
| **第四类 · 不可逆或触主权** | 命中下方「第四类刚性清单」任一条 | **严禁自行拍板，也严禁借第三类先行。** 只挂起受阻的那一张单元卡（或那一段），写清解除条件；根卡写入现状块「**待裁清单**」（问什么、选项与利弊、卡住谁）并调 `confirm_with_user` 请示，**其余无依赖的域与卡照常推进** |

**第四类刚性清单（命中即挂起该卡等用户裁）**：
1. 增删总纲第四节「做／不做」范围、改动三条根原则、放宽十一条整机验收判据或任何红样本判据。
2. 削弱沙箱默认无权、数据默认仅本地、放行留痕或凭据保护规则。
3. 对已冻结契约做不兼容修改，且无法通过「只增不改」解决。
4. 触碰 §十一 建造环境红线的任何事项（含：为开启硬件虚拟化而改 Windows 宿主配置、动现有 WSL、停启 5700 服务、装宿主级软件、另备物理 Linux 机器）。
5. 把甲类基线缺口（B1–B10）并进本项目代做，或在融合保护区做无法归入通用扩展面（乙类）的修改。
6. 发生未经批准的付费模型调用、超 §十三 上限下载大体量模型、引入闭源或传染性许可证（GPL 应用层库等）依赖、向任何远端仓库推送或对外发布内容。
7. 系统的对外正式命名与发行决策。

## §五 勘误与契约变更纪律

1. **方案原文只读**：`docs/aios/plan/` 下的 `00`、`01`、`02`、`03` 四份文件自首个提交落盘后**一字不改**；一切订正、补洞与选型切换只追加进 `docs/aios/plan/勘误表.md`（全仓仅 D1-U6 有写权限）。
2. **何时必须走勘误**：
   - 发现方案两处表述冲突，或契约存在缺口（如系统 work、SDK 不得不用到 `contracts/` 未登记的能力）；
   - 域卡发现一件无法挂靠到 K§6 既有单元卡职责名下的新活；
   - S0 探针经两种修法仍不成立，需按 A§10 撤退条件切换技术选型；
   - 实核发现方案对重构版 CardColony 基线的某条假定与真实代码不符。
3. **勘误闭环动作**：发现方提交五要素（原文件与节号／问题与实证／建议条文／波及的契约与卡号／所属 §四 类别）→ D1-U6 核实影响面后送根卡（第二、三类及既定探针撤退由根卡裁，第四类转用户裁）→ 裁定落入 `勘误表.md`（编号 `ERR-xxx`）→ D1-U6 **逐张单点通知**受影响卡更新需求或返工。
4. **契约冻结纪律**：D1-U3 发布 `contracts/FREEZE.md`（含各契约件内容哈希）后，跨域接口以 `contracts/` 为唯一准绳。冻结后原则上只增不改；因生效勘误确需改已冻结条文的，必须同步更新机器可读模式、递增版本号、重跑启动期自检与下游复验。**凡未进勘误表与冻结件的「私下约好」，验收一律判红。**

## §六 如实与证据标准

1. **只认一手可复核证据**：基线实读、探针报告、单元验收与关口报告，只认两类证据——① **源码实读**：精确文件路径＋起止行号＋真实调用链核对；② **实跑取证**：精确提交号、镜像哈希、测试层级（L1–L4）、执行命令、未删节原始输出、红样本构造方式。**代码注释、README／设计文档自述、历史卡面或会话里的口头说法、「按理说支持」的推断，一律不算证据**；拿它们当依据的读数直接判不合格。
2. **用词四态分明，禁用含糊词**：状态只准写确定词（到位／部分／未到位／未核；过／不过／未取证），严禁写「基本通过」「大致齐备」「理论上可行」「除小问题外已好」。未上真机测过的项一律写「未取证」；硬停未通时界面与文档如实写「智能体部分当前只能软停」；探针失败如实写「不成立」。
3. **绿红成双，红样本必须配正向对照**：没有红样本的判据不算判据。每条红样本必须满足两条：① 配一个「仅放开该项限制或给足该项授权时能走通」的正向对照，证明它不是因为路径没接通才报错的哑弹；② 拒绝原因码或监督事件必须精准命中被测机制，因崩溃、缺文件或前置报错而失败的不算判红成功。
4. **契约双态与文档诚实**：`contracts/` 中每条条文必须标明「现在可依赖」或「已冻结、待实现」；开发者文档与 SDK 只准把前者写成可用能力，并如实标明守规矩的应用在真实链路上能否收到某个错误码。
5. **数值必注出处**：一切限额缺省、分档阈值、测试槽上限、保底空间、超时值，必须随文标注依据类型（量级判据／同条件实测基线／产品目标）；暂缺依据的显式标「候选值·待验证」，严禁随手编一个常数冒充定论。

## §七 CardColony 融合三分法与保护区纪律

1. **融合保护区边界**：代码仓库中继承自重构版 CardColony 基线提交的全部既有目录（含 `internal/`、`pkg/`、`protocol/`、`cmd/cardlod/`、`adapters/`、`executor/`、`harness/`、`projection/`、`compose/`、`webface/`、`review/`、`web/` 等）统称**融合保护区**。
2. **甲类（基线缺口 B1–B10）——等，不代做**：
   - 严禁在本项目内替 CardColony 实现或重设计 B1–B10 未收口的部分；
   - 严禁另起第二套事件日志、第二套闸、第二套线语义、第二套身份或绕开运行时的私有执行链；
   - 严禁在生产路径放假桩（stub/mock）冒充 B1–B10 已通来骗取关口放行；
   - 受某条 B 阻塞的卡（或其分段）按 K§1.7 挂起并写明解除条件，其余不依赖该条 B 的卡照常完工；D1-U2 在 Linux 上测出的上游缺陷只提缺陷单记入基线读数表，不在保护区擅改上游核心逻辑。
3. **乙类（融合补件）——通用扩展、逐件记账**：
   - 准入四条件缺一不可：① 对 CardColony 自身也成立的**通用扩展面**；② 保护区代码与接口里**零本系统专有词**（不出现 `app`、`aios`、`hostd`、`shell` 等业务词，不写「如果是系统层就……」的特判分支）；③ 说清谁登记、谁受理、名字不匹配时如何启动期拒启；④ 只开最小注册点，不篡改既有语义。
   - 流程与门禁：需求域写补件说明 → 交 D1-U5 守门入账（`docs/aios/融合补件账本.md`）→ 实现合入。合入闸每次核对保护区相对基线提交号的全部 `git diff`：**任何一个被改动文件指不回账本里的有效条目，合入闸直接判红退回。**
4. **丙类（开发工具产品面）——新件落外、动内记账**：
   - 工作区、组装、节点目录、封装等新代码一律落在 `devtool/`，数据交互严走公开用户面与动作目录，严禁开内部直连后门；
   - 确需改动保护区 `web/` 的部分，逐件按乙类规矩经 D1-U5 登记入账。
5. **上游基线同步**：只在「上游关闭某条 B」或「阶段关口前」由 D1-U5 按明确提交号发起、经 D2-U5 合入；发生冲突以上游形态为准；上游已原生提供同类扩展面时，立即撤下本地补件并将账本条目改标为「已被上游取代」。

## §八 需求文档与执行卡任务书规矩

1. **单元卡需求草稿：转写不发明、指针不抄书**：
   - 单元卡首轮把 K§6 对应条目转写成「目标／需求／交付物／边界」四段；引用的契约只写 `contracts/Cx/...` 路径与节号指针，不整段复制契约条文；
   - 严禁借写草稿塞入方案未要求的扩展功能——验收时「需求没写却多做出来的」一律按越界退回；
   - 经评审定为正稿后，只准用补充方式记录细化澄清，实质改动必须重开评审。
2. **执行卡任务书必须自足（六要素齐全）**：
   - 执行卡（`worker` / `ui`）**看不到上级卡面、看不到伴生评审记录、看不到上下游卡的聊天**。派卡时写进 `goal` 的任务书必须自带全部上下文：
     1) **唯一目标与交付路径**：这张卡只做哪一件事，代码／脚本／报告落到哪个精确路径；
     2) **文件级依据指针**：指明去代码目录里读哪份 `docs/aios/plan/` 或 `contracts/` 文件的哪一节；
     3) **绿红判据口径**：写清怎么验算绿、什么反例必须失败及正向对照怎么跑——**严禁在任务书里预填期望的性能数字或统计读数**；
     4) **成对与接线要求**：写清发出方与受理方是谁、如何接进唯一组合根 `cmd/colony-core`；
     5) **禁改与环境边界**：写明本卡不得触碰的共享归口目录及 §十一 环境红线（尤其是只用 `wsl -d aios-build`，禁碰 5700 与宿主）；
     6) **回执格式**：要求交回精确 commit SHA、实际执行的命令、未截断的关键原始输出，以及未完成项的如实说明。
3. **派卡分流与返工留原卡**：
   - 要跑命令、写后端／脚本／构建／测试、起前端预览服务的，一律派 `worker` 卡；
   - 看浏览器渲染、点页面核交互与文案的，派 `ui` 卡（先由 `worker` 卡把预览服务起好并给出可访问地址，`ui` 卡自身无命令行，绝不派它跑构建或起服务）；

## §九 工程、并发与集成纪律

1. **单工作目录单写者**：同一个工作目录同一时刻只允许一张执行卡做写操作。多张执行卡并行施工时，每张卡必须在 `D:\AI_station\AIOS-wt\<卡号>` 下建独立的 `git worktree` 并在各自工作树内提交，合入后移除工作树；严禁两张卡共用同一目录并发改文件。
2. **共享目录单一归口**：
   - `contracts/`、`docs/aios/plan/`、`aios/registry/`：**只许 D1 改**；
   - `cmd/colony-core/`、`image/`、`aios/syswork/`：**只许 D2 改**；
   - `tests/aios/`、`docs/aios/gates/`：**只许 D9 改**。
   其他域需改动上述目录时，向归口卡提交明确变更请求或补丁提交号，由归口卡审验合入；越权直改的提交在合入闸一律退回。
3. **唯一合入口与六道合入闸**：集成分支 `aios/main` 只许集成归口（D2-U5）写入；交接一律报精确提交号（commit SHA），不报分支名；严禁 `git push --force` 或改写集成分支历史。每次合入必过六道硬闸：
   1) 全量构建通过；
   2) 单元测试全过；
   3) 登记表启动期自检（发受子集核验）通过；
   4) 融合保护区 `git diff` 对账（100% 指回补件账本）通过；
   5) 组合根接线检查（无悬空登记、无零生产调用的受理方）通过；
   6) 扩展类提交单行登记＋新增文件边界检查通过。
4. **镜像先行，曳光弹不许熄**：从 S1 出口起，`aios/main` 上任取一个提交都必须能一条命令造出可启动镜像；D2-U5 每合入一批即造开发镜像重跑已绿的曳光弹各段，任一段转红当场用回退提交（`git revert`）撤回该批合入并退回来源卡，严禁带病留主干。
5. **「既有红」的三条铁门槛**：取证或合入时遇到上游遗留失败用例，唯有同时满足三条才准列为「既有红」分列放行：① 在合入前基线提交上同命令复现同一错误，附原始输出；② 根因确属保护区甲类缺口或已立单的上游缺陷，与本次改动的文件和调用链完全无关；③ 失败原文记入合入记录与基线读数表。**严禁以注释、跳过（`skip`）、删断言或改宽条件的方式把红抹绿。**
6. **测试槽统一领用**：在 `aios-build` 内做镜像构建或拉起 QEMU 虚拟机，一律经 D9-U2 测试槽排队领槽（槽位释放只认占用进程退出，不设固定秒数强拆）；绕开测试槽私跑产出的结果不作验收与关口证据。

## §十 验证独立性与防自证纪律

1. **准备者与验证者分离**：任何执行卡不得验收自己写的代码或文档。单元验收必须派独立的 `qa_card`（由测试验收总监进场）对照需求正稿实跑查验；整机场景（E1–E11）、红样本账本、反例应用、加固套件、泄漏扫描与关口报告，全部由独立于实现域的 D9 只依据 G§九 与 `contracts/` 独立构建并取证。D9 不读实现卡的内部设计，不替实现域动手修代码。
2. **文档自足性的无污染验证（D9-U5）**：
   - 干净验证方执行卡的允许读取白名单仅限三处：`docs/aios/dev/`、`colonyctl` 与 `sdk/` 的编译产物、开发模式运行环境；
   - 严禁读取 `aios/`、`cmd/`、`sysnodes/`、`shell/`、`devtool/`、`contracts/` 源码、`docs/aios/plan/` 方案或任何卡面；核出一次越界读取，该卡连同产物立即作废，换新卡重来；
   - 验证过程中凡文档未写清而不得不猜之处，逐条记入「猜测清单」；猜测清单非空即判不通过，D8-U5 修补文档后**必须另建全新执行卡重验**（原卡已知谜底，不得复验）；
   - 本项通过只证明「开发者文档自足」，严禁在任何文档或报告里写成「已有外部第三方开发者完成接入」。
3. **回放模型门禁与真模型冒烟分开**：自动化测试、单元验收与关口回归统一接确定性回放模型（D5-U2：未匹配请求明确报错，严禁胡编应答；录制入库前必须脱敏清零凭据与隐私），确保任意第三方重跑逐字节一致；真实模型只用于用户点过头的少量冒烟（P7 与 E6 的本机小模型），不拿真模型的随机输出做常规门禁。
4. **证据层级严禁以低充高**：凡涉及内核与宿主强制的判据（沙箱断网与文件隔离、cgroup 限额、ext4 项目配额、系统分区只读、A/B 自动回退、直接断电恢复、设备热插拔）**只认 L3 整机层（QEMU 跑真实镜像与自带内核）的证据**；关口放行只认 D9 在 L3 取得的证据包。拿 L1 单元或 L2 容器／开发模式结果顶替的，一律退回。
5. **自设检查留痕，关口报告指路不堆料**：凡声称做过扫描或全例实跑，必须留存扫描范围、命中条数与逐条处置记录；关口报告（G0–G5）逐条给「过／不过／未取证」与证据包路径指针，不粘贴长篇原始日志，不拿部分通过冒充整关通过。

## §十二 协作、汇报与卡面卫生
