# 任务书：卡间消息端点改读收件箱（card-messages → inbox）

> 上游：卡片底座第一步施工回报 §三.4（用户发令处理）。2026-10-15。
> 背景：底座第一步已把新消息落点从"塞对话块"改为"进 inbox 收件箱"。本端点（前端未读角标数据面）仍读会话档案的 card: 块 ⇒ **看不到新消息**。本任务把它改读 inbox。

---

## 〇、目标（一句话）

`GET /api/works/{work_id}/card-messages` 的数据源从"会话档案 card: 块"改为"inbox 表"，新旧消息在端点层合流，前端零改动。

## 一、现状（实证）

- 端点：`src/api/routes.py` L364-418 `list_card_messages`。
  - 数据源：遍历全部卡 → `session_facade.read` → 过滤 `actor` 以 `card:` 开头的块 → 解析头行；
  - `unread_by_card`：每卡用 `card_msg.find_pending(blocks)` 判 pending（二值）；
  - `card_msg_consumed` 打点：端点侧发现"有卡间块且已非 pending"时打。
- 前端消费（零改动依据）：`static/canvas.js` L1654（角标刷新，只读 `unread_by_card`）；`static/esm/api.js` L135（封装调用）；`static/workspace.js`（projMsgRead 已读合成）。**前端只消费 `items` 与 `unread_by_card` 两个键，字段形态不变即零改动。**
- inbox 侧已有原语：`card_db.list_pending(work_id, target)`（读待处理）；但**缺**"列全部（含 consumed）"与"按 work 聚合"的原语——需补。

## 二、任务清单

### T1 card_db 补聚合原语

- `list_inbox(work_id, target_card_id=None) -> list[dict]`：按 work（可选按卡）列全部消息行（含 consumed），按 seq 升序；行转 dict 复用 `_inbox_row_to_dict`。
- 纯新增函数，不动既有三原语。

### T2 端点数据源切换

`list_card_messages` 重写数据获取（返回结构不变）：

1. **items 来源改**：`card_db.list_inbox(work_id)` 全量（含 consumed）→ 映射为既有 items 字段：
   - `id`=msg_id、`ts`=created_at、`seq`=seq、`from_card`=from_card、`to_card`=target_card_id、`type`=type、`type_display`＝注册表 `display_of`（照旧后端取）、正文＝strip 后的 content（首行头行剥掉，保持 items 既有正文语义）；
   - `format_ok` 字段：inbox 行都是结构化写入的 ⇒ **恒 true**（旧档案块才有解析失败）；如前端依赖该字段分组，恒真不影响。
2. **unread_by_card 来源改**：`card_db.list_pending(work_id)` 聚合（每卡 pending 计 1，二值照旧）。
3. **card_msg_consumed 打点移除**：该打点的语义（"端点侧发现信已被处理"）在 inbox 下不再成立——consumed 事实已由 `mark_consumed` 在回合收口落库，端点无需再推断。删除端点侧 `mark_consumed`/ops_log 调用与相关注释；`card_msg.mark_consumed` 函数本体**保留**（进程内去重可能仍有他用，且删函数属化石清理批次的事）。
4. **排序**：items 按 ts 倒序、limit 截断（照旧）。

### T3 历史合流（953 条存量可见性）

- 旧消息（对话块里的 953 条）**不能丢**——用户在通知面板里还要看历史。
- 合流策略：items ＝ inbox 全量 **∪** 旧档案扫描的 card: 块（现有扫描逻辑保留为第二数据源），按 ts 倒序合并、msg_id 去重（同一 msg_id 不会双源出现——旧机制的信不进 inbox，新机制的信不进对话块；去重仅防御）。
- unread_by_card **只看 inbox pending**（旧机制的 pending 推导退役——那个历史 pending 尾巴按 T5 已登记不迁移）。

### T4 测试

- 更新/新增：①新消息（inbox 写入）出现在 items 且字段形态与旧一致；②consumed 消息仍在 items、不计入 unread_by_card；③旧档案消息（造一条 card: 块）仍在 items（合流）；④unread_by_card 只反映 inbox pending；⑤前端两个字段消费契约快照（items 键集＋unread_by_card 形态）。
- 既有相关测试（test_card_msg / 端点测试）如有断言旧数据源，随改。

## 四、约束

1. **返回结构零变**：items 字段集与 unread_by_card 形态保持既有契约（前端零改动的依据）。
2. **纯读端点**：不新增任何写路径（consumed 打点移除是删写，不是加写）。
3. **旧扫描逻辑保留**（作为历史合流源），不删 find_pending 函数本体。
4. **性能口径如实**：inbox 是单表索引查询（idx_inbox_target/idx_inbox_work），比旧的全量会话扫描**更省**——性能净改善，无需声明观察项；但合流后旧扫描仍跑（历史源），两源并存直到化石清理批次退役旧源（不在本任务）。
