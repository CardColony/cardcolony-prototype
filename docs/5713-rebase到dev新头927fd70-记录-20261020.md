## 二、冲突点及解法（2 处冲突，逐处人工解）

### 冲突 1 · `src/api/card_tools.py` → `_h_send_card_message`（发信闸）

| 侧 | 改了什么 |
|---|---|
| dev（`927fd70`，含 5710 角色机制合并） | 树作用域判定旁加 `_role_edge = role_room.linked(...)`：角色卡离树，但「角色↔关注卡」已建立的订阅边允许双向发信 |
| 5713 | 把树作用域判定整体换掉：**通信边界＝通信线**（`require_link` → 无线即拒并指路 `link_cards`） |

**解法（保留双方语义，fail-closed）**：

```python
_role_edge = role_room.linked(work_id, current_id, target_id)   # dev 的订阅边
if require_link and not _role_edge:                             # 5713 的线边界
    try:
        policy.check_linked(current_id, target_id, cards)       # 5713 独立关口
    except PermissionError:
        return err("denied", "...没有通信线——请先用 link_cards 建一条...")
```

理由：`role_room.link()` 会在**两侧卡面各写一条 `links`**，按新口径本就等于「已有通信线」；
仍显式认 `_role_edge` 只是护住「只有档案、未落 links」的 v1 订阅数据。两套口径不冲突而是包含关系，
故取「订阅边 ∪ 通信线」为边界，其余一律无线即拒。dev 在原位置**⑤ 的 `policy.check(SWITCH_READ)` 类型闸**
一个字没动（仍在发信前照跑）。

**实质行为 3/3 都成立**（A 从卡片清单找到 B → 自己建线 → `msg_ask` → B 自己回 `msg_answer`
且 `reply_to` 配对 → 双方各写现状）。r1/r3 判 INCOMPLETE 的那一项，是**判据本身的字面量脆点**，不是行为差异：

- 判据实现：`"B_self_answered_wrote_status": "msg_answer" in (ev.get("status_B") or "")`
  ——在**自由文本**里找 ASCII 关键词 `msg_answer`。
- 而 r1/r3 里 B 的现状块写的是中文「回发应答」，并把**自己的应答 msg_id 与 reply_to 原文抄了进去**
  （r1：`card_002-e67fd707`、`reply_to=card_003-bebaf96d`；r3：`card_002-c30653b3`、`reply_to=card_003-eb5192a3`），
  内容与事件流 `from=<B> reply_to=<A 询问 id>` 一致（`answer_reply_to_matches_ask` 亦为 true）。
- ⇒ 模型一旦不用英文 token 措辞，这条就误报 false。

**建议（未擅自改动验收网，留待裁定）**：把该判据从「碰关键词」改成「碰事实锚点」——
`('msg_answer' in status_B) or (应答 msg_id in status_B) or (reply_to 的询问 id in status_B)`。
