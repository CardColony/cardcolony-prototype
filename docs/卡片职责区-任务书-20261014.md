# 任务书：system 区新增「卡片职责区」

> 日期：2026-10-14
> 性质：实现任务书。只定义规格、边界、验收；不在本文写代码。
> 用户口径（2026-10-14 12:10~12:27，逐字要点）：
> - 「需要在 system 区，增加卡片职责区」
> - 「我说的职责区，是**不同卡片它的职责是什么**，需要明确的讲清楚，**不是原来的【使命】**，那是卡片的目标」
> - 「你不用管具体的了，你只需要给出一个区域，是写卡片职责的；**未来新增一种卡片，这个职责区就需要写上对应的职责信息**」
> - 「**卡片清单放到卡片职责下方**」

---

## 0. 一句话规格

在 system 区新增一个**类型级**的「卡片职责」区：**每类卡片一行，写明这类卡负责什么**；职责文本**跟着类型定义走**（新增一种卡 ⇒ 在类型注册表里写上它的职责 ⇒ 本区**零代码改动**自动带出）。

## 2. 规格

### 2.1 区定义

| 项 | 值 |
|---|---|
| **order** | **`90`**（紧邻 100 之前） |
| **name** | `卡片职责` |
| **channel** | `system` |
| **seats** | `("main",)` —— **仅主模型**；三席维持"100＋150"不变 |
| **source** | `card_store.load_type_registry()` 的 `l1_vocabularies.*.types[].description` |

### 2.2 职责文本来源：复用 `description`（不新增字段）

- 每类卡的职责文本 ＝ 注册表该项的 `description`，**原样取**，不加工、不截断；
- **不新增 `duty` 字段**（用户口径"不用管具体的了"；现成 `description` 已是在讲职责）；
- **不改** `card_type_registry.json` 的任何现有内容（本任务只读它）。

### 2.3 渲染形态

```text
## 卡片职责
- 项目根卡（project）：一个独立推演项目的总架构卡（取代 legacy「剧本」成为唯一根卡类型——底座收口 2026-10-08）。只允许 create_work 流程产生；树词表（rd/research）均不含它 ⇒ 子卡写 project 被闸2 自然拦截。根卡身份由 project_class 承载，project 只是类型名。
- 子项目卡（sub_project）：研发项目下一个相对独立的工作单元。可有子卡、可调用工具卡、是产物与过程的挂载主体。
- 工具卡（tool）：被某个子项目卡调用、执行专项任务（产出文档、调研等）的卡。产物与过程永久挂载在 owner 上；完成后置 completed 不删；不可有子卡。
- 课题卡（topic）：研究项目下的一个课题（研究树子卡统一叫课题卡——用户 2026-10-08 裁定）。可有子卡（研究树存在父子层级）；调研/文献/实验等差异用标签扛，不再细分类型。
```

- 每行格式：`- {label}（{code}）：{description}`；
- 顺序：**按注册表顺序**（`root` → 各 `l1_vocabularies` 的声明序）；
- **全量列出**所有已立项类型（不按当前树过滤）——与"新增一种卡就该出现"的诉求一致。

### 2.4 扩展性（本任务的核心诉求）

**新增一种卡 ＝ 在 `card_type_registry.json` 里加一个类型项（含 `description`）⇒ 本区自动多出一行，零代码改动。**

实现约束：**必须从注册表读**，不得在代码里硬编码类型清单（硬编码 = 扩展性失效）。

### 2.5 顺序

新区在 **100 卡片清单之前**（`90 < 100`）。理由：先讲"这类卡干什么"（规矩），再列"树上现在有哪些卡"（实例）。

### 2.6 fail-open

注册表读不到 / 坏 JSON（`load_type_registry()` 返 `{}`）⇒ **本区不出现**（没有来源就不出现这个区），**不报错、不阻断装配**——与既有各区同纪律。

---

## 3. 连带面与风险（如实报告）

1. **system 变长**：新区按类型数线性增长（现 4 类 ≈ 4 行）。须报告改前/改后 system 字节数。
2. **注册表是校验源**：本区只是它的一个**读方**，不改它、不因它失败而阻断（§2.6）。
3. **三席不受影响**：`seats=("main",)` ⇒ 三席 system 逐字不变；须**断言证明**。
4. **`build_log_regions`**：区进 prompt 日志的 `regions` 键（既有机制，按区自动带出）——须确认新 order 出现在日志里。
5. **与 100 区的分工**：100＝实例（有哪些卡），90＝类型（这类卡干什么）。两者不得互相塞内容。

---

## 4. 验收（严格版）

> **全绿只是最低门槛，不是验收。** 每条须有**可复现证据**；无证据＝未通过。

### 4.1 证据规则

1. 每条判据附证据：测试名＋断言原文／日志摘录／改前改后 diff／实测字节数。
2. 报告须给**改动前后对照**，不许只写"已通过"。
3. **未覆盖项必须显式列出**；用"全绿"掩盖未覆盖＝报告不合格。
4. 任一判据失败 → **停手如实报告**，不得"绕过去让它绿"。

### 4.2 正向判据

| # | 判据 | 证据要求 |
|---|---|---|
| V1 | 新区存在：`order==90`、`name=="卡片职责"`、`channel=="system"` | 打印 `build_context_regions` 的区列表 |
| V2 | 内容**逐条**对应注册表每个已立项类型（label/code/description），无增无删 | 与 `load_type_registry()` 实读逐条比对 |
| V3 | 顺序：90 在 100 **之前** | 断言 order 序列 |
| V4 | 职责文本**原样取**（不加工、不截断） | 与注册表 `description` 逐字相等 |
| V5 | 三席 `vp_system_prompt` **不含**本区 | 断言 |
| V6 | **扩展性**：往注册表加一个类型（测试内 monkeypatch）⇒ 本区**自动多一行** | 该测试 |
| V7 | **fail-open**：注册表读不到 ⇒ 本区不出现、不报错、装配继续 | monkeypatch `TYPE_REGISTRY_PATH` 指向不存在文件 |
| V8 | 区进 prompt 日志 `regions` | `build_log_regions` 输出含 order 90 |
| V9 | 回归 | 全量 pytest 与基线逐条对照；列出基线失败名，证明未动 |

### 4.3 负向判据（**最容易糊弄的地方**）
