# 卡片区域语义与上下文支持 · 卡片模块需求单

> 日期：2026-10-14
> 提交对象：卡片模块
> 状态：需求输入，**请卡片模块先给出支持方案；未授权直接施工**。
> 需求目的：让模型理解卡片每个区域的准确职责，并让每张卡拥有足够的结构化位置，保存其他卡继续工作时需要知道的本卡信息。

---

## 一、背景与问题

当前 system 上下文只提供卡片清单、当前卡标识等信息；卡片正文虽有分区，但模型对区块职责理解不稳定，出现把方案、过程、状态、决定等内容放错区域的情况。

**这并非只需要补一段说明文字。** 用户明确指出：卡片自身目前缺少承载许多必要信息的区域。因此需要卡片模块同时评估：

1. 如何把**正确、明确的区块说明**提供给模型；
2. 卡片本身需要哪些**信息承载区域**，才能保存并供其他卡读取必要信息；
3. 各区域应如何避免互相覆盖职责、如何支持模型在必要时更新正确区域。

本需求单请求卡片模块提出结构与支持方案；**不预设一定新增几个区块、不代定字段、存储列、UI 或迁移方式**。

### 当前工具能力（用户提供的卡片工具区域化改造说明）

用户提供的改造说明描述了以下工具能力，作为本需求设计的上下文：

- 正卡：`read_card(card_id, region?)`，不带 `region` 返回区域清单，带区域参数按需读取 `mission` / `status` / `third`；第三块名称按树类型显示为「需求文档」或「定论」。
- 影子卡：`read_shadow(section?)`，不带 `section` 返回区域清单，带 `section` 按需读取；只能读当前卡自己的影子。
- 影子写入：`edit_shadow(section, content)`，一次覆盖一个指定区域。
- 建卡与删卡：需经用户确认后才执行。

**状态边界**：该说明标注的工具改造位于 `.worktrees/toolzone`，尚未合并主树、未重启生产。本需求将其作为已提供的目标/并行工作区契约参考，不能据此声称主树生产环境已具备这些能力；卡片模块方案需说明如何与该区域化读写接口衔接。

## 二、用户已明确的语义（必须遵守）

### 2.1 正卡已有区域的正确含义

- **使命**：说明这张卡要处理的任务——**要做什么、要做成什么**。它不是“卡片为什么存在”，也不是授权来源。
- **现状**（名称是否合适尚未定）：说明该功能/任务**当前确定的功能状态与结论**，是其他卡读取本卡时的**第一信息源**。重点是低频更新的确定性信息，以及其他卡继续工作所需了解的内容，例如对外接口、涉及/关联模块及当前约定。它不是流水账；“做到哪、卡在哪里”可以是其中的信息，但不足以定义该区域。
- **需求文档**（研发树第三块的对外名称）：保存该功能全部需求的**确定版详细描述**，是该功能需求的**唯一事实确定源**。
- 非研发树现有第三块对外名称为“定论”。卡片模块须在方案中说明它与“需求文档”的适用范围和语义边界；不得将二者仅因共用存储位置就说成同一种内容。

### 2.2 用户认可的跨卡信息类别

用户确认此前归纳的下列信息“都是有必要的”，并指出这些信息要能在卡片自身上下文中被了解、在必要时更新：

1. **职责与边界**：该任务/功能负责什么、不负责什么；哪些事项属于本卡范围。
2. **接口与约定**：对外提供/依赖的接口、输入输出、数据格式、调用约定及约束。
3. **依赖与影响范围**：依赖哪些模块；本卡变更会影响哪些模块、卡片或功能。
4. **当前确定状态**：任务/功能当前已确定的状态与结论，供其他卡据此继续工作。
5. **交接物与权威位置**：结果、文档、代码或数据的所在位置；哪一处是权威来源。
6. **待协作事项**：需要其他卡/模块提供的输入、待办、阻塞或协作关系。

以上是需要被承载和可供跨卡读取的**信息类别**，不等于用户已裁定它们必须各自成为独立区块。请卡片模块提出如何组织，避免重复、冲突和不清晰的归属。

## 三、影子卡区域现状与待解决冲突

按用户提供的最新《卡片与影子卡·区域分块说明》，影子卡当前为四节（顺序固定）：

| 区域 | 当前列/键 | 当前说明 | 状态 |
|---|---|---|---|
| **进度** | `progress` | 用户裁定（2026-10-14 21:21）：**不需要新职责，进度根本不重要** | 不再列为待解决冲突 |
| **待协作事项** | `coordination` | 需要其他卡/模块提供的输入、待办、阻塞、协作关系 | 现有说明 |
| **产物清单** | `artifacts` | 产物（文件/代码/文档）位置及权威来源；含工具卡终态自动回传的产物指针 | 指针唯一归属处 |
| **迭代历史** | `iterations` | 改动指针（改了什么、为什么改） | 现有说明 |

**「进度」悬案已由用户裁定（2026-10-14 21:21）：进度不需要新职责，进度根本不重要。**

因此：

- **不再要求卡片模块为「进度」设计新语义或候选方案**；也不把它的旧“时间线”定义当作需要推翻的对象；
- 但**其余区域的边界仍要划清**：正卡的当前确定状态、影子中的过程/变化记录、系统自动维护的改动历史、产物/代码指针、待协作事项，各归其位、互不重叠；
- 不得擅自给「进度」改名或迁移其既有内容。

影子卡是本卡私有的过程记录，设计上只能由本卡读取；正卡三块是跨卡可读的对外内容。影子信息与正卡信息的可见性边界必须在方案中保留并说明。

## 四、需要卡片模块提出支持方案的事项

请针对以下问题给出可评审方案，不要只回“可以加说明”或“新增区块”：

### 4.1 区块结构与语义

- 根卡与普通卡分别有哪些区域？适用范围是否相同？
- 如何表达第二部分列出的跨卡信息类别？哪些信息归正卡、哪些归影子、哪些仍只在对话流？
- “使命 / 现状 / 需求文档 / 定论”及影子“进度 / 待协作事项 / 产物清单 / 迭代历史”之间如何划清边界？
- 每个区域应明确写出：**存什么、不存什么、更新频率/写入方式、权威性、何时可由模型更新**。
- **必须明确回答是否需要新增区域**：用户指出当前卡片缺少承载多类跨卡信息的区域。若现有区域无法清晰承载职责边界、接口约定、依赖影响、交接物/权威位置、待协作事项等信息，须提出相应新增区域及其读写支持；不得把需求缩减为“只在 system 里补一段说明”。
- 若建议不新增某类区域，须说明现有哪个区域承载、如何避免与其现有职责冲突。
- 是否需调整影子其余既有区域的职责（**「进度」除外**——用户已裁定其不需要新职责）？逐项说明理由与影响；不要先把名字当成语义。

### 4.2 模型上下文中的区块说明

- 给根卡和普通卡的模型上下文提供正确的区域说明，使模型在读取卡片前就知道各块用途、边界和写入规则。
- 说明应与卡片模块最终区块结构同步，不得继续沿用已被用户指出不准确的旧解释。
- 说明如何让模型据此在需要时更新对应区域，而不是把需求、方案、当前状态、决定和过程记录混写。
- 指出上下文注入的位置、适用模型/场景及避免重复注入的方式；这是方案需交代的设计内容，不在本需求单预设实现手段。

### 4.3 写入与更新支持

- 模型如何识别应更新的区域？
- 各区域采用覆盖写、追加写、用户确认或系统自动写的规则是什么？
- 哪些区域是事实/需求/决定的权威来源，修改如何防止相互覆盖或形成多个事实源？
- 系统自动维护的内容（如修改历史、产物指针）与模型可起草/用户确认的内容如何区分？

### 4.4 兼容与迁移

如方案涉及区块结构变化，请说明：

- 旧卡内容如何兼容、是否迁移、迁移前后是否逐字保真；
- 根卡、普通卡、研发树、研究树、工具卡、影子卡分别如何处理；
- 卡片读写 API、起草/确认流程、read_card/read_shadow、上下文装配、快照及测试分别有哪些影响；
- 如何保证“区域各自承载独立语义”，不再依赖 Markdown 整篇文本解析而误分块。

卡片模块请返回一份**可评审方案**，至少包含：

1. 正卡（根卡/普通卡）与影子卡的**区块清单及职责表**；

7. 实施范围、依赖、风险、验收判据；
8. 明确列出需用户裁定的项目，不能把技术实现细节泛泛地抛给用户。

**当前阶段只需给方案，不开始改代码、不改卡片数据、不迁移存量卡。**

## 六、边界与禁区

- 不把“使命”解释为卡片存在理由/授权来源；用户已明确其含义是**任务要做什么、做成什么**。
- 不把“现状”缩减为流水账或泛泛的“已核实情况”；它是其他卡读取本卡的**第一信息源**，描述当前确定性状态及必要的关联/接口信息。
- 不把“需求文档”泛化成临时需求或讨论记录；它是需求的**确定版详细描述和唯一事实源**。
- 不把旧“职责区（charter）”兼容映射当成用户现在所说的“卡片职责”定义。
- 不把用户确认的“信息类别必要”擅自等同于“每类都必须单独新增一个区块”；需要由方案解释组织方式。
- **不得**给「进度」设计新职责（用户已裁定其不重要）；不擅自改名、不迁移其既有数据。
- 不修改 `card_type_registry.json` 的类型 description 来替代卡片区域职责设计；类型说明与每张卡承载的跨卡信息应区分。
- 不改代码、不改卡片内容、不迁移数据。
