# 推演agent 统筹计划板施工任务书

在「对话页 → 项目统筹」增加计划板。统筹查过需求正稿、版本和各域现状后，把后续工作逐条登记到板上。它每次醒来按当前优先级决定推进哪些事项。用户可以看板、调整计划和回查历史。项目内统筹联系域责任卡，责任卡负责域内拆分和派工。

## 一、计划条目与优先级

复用一份计划的现有 `plan.items`、任命、版本及历史。计划板是这些条目的结构化编辑和展示。首次醒来，统筹先查需求原文和已有工作，再按相应域责任卡登记计划。既有事项沿原 `item_id` 继续维护，后续发令、回报、QA 和修正继续按这个标识关联。

| 字段 | 含义 |
| --- | --- |
| `item_id` | 稳定事项标识。新条目由宿主分配，旧条目沿用已有标识。 |
| `title`、`next_result` | 事项及下一个可核查结果。写到能判断进展和完成的程度。 |
| `owner_card` | 承接交办的域责任卡。归属待核实时允许空值，并在面板提示。 |
| `priority` | 正整数，数字越小越优先。同优先级按 `item_id` 稳定排序。 |
| `status` | 待办 `todo`、进行中 `doing`、受阻 `blocked`、完成 `done`。 |
| `depends` | 已存在的依赖事项标识集合，用于判断哪些可以并行。 |
| `requirement_refs` | 需求出处及版本引用，可从现有需求引用体系回读。 |
| `result_note`、`evidence_refs` | 完成或受阻的说明及已有证据坐标。引用沿现有权限和归属核验。 |

- 可插项、改标题、调整目标和责任卡、改优先级和状态。优先级初次可用 100、200、300 留空，后来的工作可以用 50 插到首位，也可以用 150 插在两项之间。排序只是统筹判断的依据。条目能否推进看实际依赖、进展和优先级，互不依赖的事项可以同时交办。
- 统筹核查结果后可将条目标为「完成」，写明完成依据并关联已取得的回执或产物。事项本身约定 QA 时沿该验收口径判断。发出指令、收到回执、取得证据、验收结论和标记完成各自按实际事实显示。发现新问题可重开原事项，保留原完成记录。
- 兼容没有优先级和新增字段的既有计划。缺少优先级时按旧顺序投影为 100、200、300……，首次发生有效编辑时随新版本保存。旧事项 ID、明确完成的状态、依赖与关联证据原样保留。读取和部署本身不批量改库。

## 二、统筹专用工具 `coord_plan_board`

沿现有统筹强模型动作协议注册。读与写共用同一工具，由宿主把计划卡、任命、当前读入版本和权限绑定到调用。

| 操作 | 参数 | 结果 |
| --- | --- | --- |
| `read` | 可选 `item_id`。列表默认读未完成，显式指定可查已完成。 | 当前 `rev`、条目及可回读证据。 |
| `apply` | 一批 `changes`，可包含 `add` 和 `update`。携带本次调整理由。 | 原子保存，回执给出新 `rev`、被改条目及新分配的 ID。 |

`add` 提交标题、下个结果、优先级、可知的责任归属和需求引用。缺资料时可先记一条待核查事项，并写清需查什么。`update` 指定既有 ID，只改明确提交的字段。单纯改优先级保留原状态与证据。`status=done` 同时提交完成依据。

```json
{
  "action": "coord_plan_board",
  "args": {
    "op": "apply",
    "reason": "接入协议是两项联调的共同前置，提前确认",
    "changes": [
      {"op": "update", "item_id": "participant-access", "priority": 50},
      {"op": "add", "title": "核查接入协议对旧调用方的影响", "priority": 150,
       "next_result": "取得旧调用方的兼容性核查记录"}
    ]
  }
}
```

沿现有计划版本校验和事务保存。本批校验包括条目归属、字段类型、依赖引用、需求与证据出处。需求引用复用实际查证结果中的来源卡、原文定位和版本指纹。若其中一条不合法，整批零写入。版本冲突时返回当前版本与变动条目，让统筹或用户重读后再决定。旧版本的同批请求重放，新增条目仍只有首次成功保存的那一份。模型同轮成功改板后，用**宿主保存回执里的新版本**刷新该轮材料和授权核对。后续发令仍走正式发令入口，按既有规则另行核权。

统筹执行轮可写板，旁观模式可维护计划。独立到期回看和用户对话可以读板。用户用现有统筹面板编辑同一份计划，包括任命暂停期间。弱模型只观察。完成、受阻、重开、排序和插入都写入现有计划历史，能回读操作者、时间、变更理由和相关证据。工具调用本身只修改该计划。

统一接管现有写口。强模型旧的整份计划提交继续处理目标、需求引用、观察标准等字段，已登板的条目以计划板操作为准。用户现有计划编辑和新面板走同一个版本保存入口。同轮先改计划再发令按保存回执续接。工作卡派工照旧由域责任卡处理。

## 三、每次唤醒如何带上计划板

在统筹强模型每次正式唤醒的首跳，宿主从 **本任命、当前计划版本、当前观察范围** 读出所有可见未完成项，按优先级投影为一份「统筹计划板」。覆盖首次任命、手动唤醒、弱模型提请、直接节点、到期回看。左侧统筹对话读取同一份板，方便用户追问眼下进度。

材料走现有模型调用的当轮输入口 `turn_tail`。每次出站只带一份当前板，结构包含版本、可见未完成数量、事项 ID、优先级、状态、标题、责任卡、实际依赖和下个结果。需求与证据保留回读坐标。状态为进行中、受阻的事项也算未完成。没有待推进工作时显式写「当前无未完成事项」。完成项保留在板和历史里，按 ID 查阅。

- 普通工具续跳继续带同一份板。改板成功后的下一跳使用保存回执对应的新快照。外部编辑推进版本时沿已有版本守卫处理，原回合从已读版本重新核对。
- 稳定提示词保留职能、规则和工具协议。动态计划条目走当轮材料，预先拼接的整份计划和历史回灌应避免再附一份旧事项列表。由于上下文上限需要缩量时，优先保留所有可见未完成条目的索引，原文和证据按坐标查阅。若连索引也超限，明确标出总数、未展开区间及读取方式。
- 宿主在出站前核对任命、版本和权限。计划板投影及回读遵守现有需求、证据和观察范围校验。存量记录只有整份计划的来源时沿现有过滤口径。有条目来源时按条目过滤。撤权后的回合要用出站证据证明旧材料被排除。
- 弱模型继续读本批变化、匹配的观察标准和需求片段。可附本批涉及事项的状态和下一结果，便于判断是否要叫醒统筹。全板随强模型的推进回合走。

## 四、界面与施工验收

左侧「项目统筹」进入后，在对话和模型设置旁可直接打开「计划板」。默认优先级排序并展开未完成项，「已完成」可单独展开和查看证据。用户可新增、改优先级、改内容、标完成和重开。成功后显示实际保存的版本，刷新后保留。冲突时保留用户正在编辑的内容，并展示当前版本。

| 编号 | 非模拟持久化与正式路径验收 |
| --- | --- |
| PB1 | 任命后，强模型从实际需求正稿和版本查证，写入三条计划。隔离浏览器能读到条目、优先级、责任归属及原文引用。旧计划进入同一面板，原 ID 和关联可打开。 |
| PB2 | 在已有事项之间插项，再把另一项优先级提前，保留原有进行中事项。独立的两项分别允许交给对应域责任卡。回读卡清单与发令记录，计划板修改产生的建卡与发令增量均为零。 |
| PB3 | 标完成后刷新仍为完成，历史与回执仍能打开。下一轮的待推进列表移除该条。重开后以同一 ID 返回列表。未通过的既定 QA 判据继续显示原结论。 |
| PB4 | 捕获模型适配器实际出站消息，覆盖首次、手动、弱模型提请、直接节点、到期回看和用户对话。每次一份当轮板，未完成项按序出现，已完成项缺席。工具续跳及同轮改板后再次核对版本和顺序。 |
| PB5 | 两个客户端从同一版本编辑，只能有一个保存成功。复核非法批次、过期任命、暂停、撤权及弱模型尝试写板。保存增量与指令增量符合各自权限。 |
| PB6 | 统筹按板上优先级向域责任卡发正式指令，用同一事项串起责任卡派工、执行回报、完成标记及下一轮投影。复核普通对话、专属会话、弱观察、QA 与独立回看。 |

回执留在隔离 work 的原事项。附计划版本、条目 ID、真实需求指针、保存结果、实际出站材料、浏览器刷新回读和回归命令。模型输出可固定供验收，存储、上下文装配与权限入口走实际实现。隔离验收完成后再由用户裁定上线时机。
