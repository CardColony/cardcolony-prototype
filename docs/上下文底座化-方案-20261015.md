## 一、底座化＝做什么

把上下文装配从"**写死的接线**"变成"**可组合的模块**"：

| | 现在 | 底座化后 |
|---|---|---|
| 区的**声明** | 分散三处：`REGION_TABLE`（声明）／`build_context_regions`（手工接线）／各 `render_*`（实现） | **一处注册**：每个区＝一个注册项（声明＋渲染器） |
| 区的**装配** | 逐段手写（每个区单独一段取数＋拼 dict） | **遍历注册表**：取数一次 → 逐区渲染 → 非空收下 → 按 order 排 |
| 加/删/调序一个区 | **改装配函数**（还得记得改区表） | **改注册表**（或配置），装配器一字不动 |
| 区的**开关** | 只有各自的隐式条件（如"无来源就不出现"） | **显式可控**：全局开关 ＋ 预留按卡/按类型 |
| IO 与渲染 | **混在装配里**（装配函数自己读库/读注册表/读记忆） | **分开**：装配前一次性取数成 `ctx`，渲染器保持**纯函数**（沿用既有纪律） |

**一句话**：区变成"**可注册、可组合、可控制**"的组件；装配器退化成一台**遍历机**（只按 order 收区拼接、零内容判断——与既有总表 #2/#3 一致）。

- ⇒ **"区表"名存实亡**：它不是装配的依据，只是一份注释式的清单。

## 三、目标态设计

### 3.1 区＝注册项（一处声明）

```python
# src/api/context_registry.py（新）
@dataclass(frozen=True)
class RegionSpec:
    key: str          # 稳定标识（供配置/控制/日志引用），如 "card_duty"
    order: int
    name: str         # 显示名（日志 / prompt 日志 regions）
    channel: str      # system | messages | user
    seats: tuple      # 声明（注：见 §五-2，现装配不消费）
    source: str       # 来源说明（人读）
    render: Callable[[RegionCtx], str]        # 渲染器（纯函数：ctx → 文本；空串＝不出现）
    count: Callable[[RegionCtx, str], int] | int   # entries（供日志）
```

**注册表**＝`list[RegionSpec]`，**唯一声明处**。加一个区＝加一项；删＝删一项；调序＝改 `order`。

### 3.2 装配＝遍历机

```python
def build_context_regions(ctx: RegionCtx) -> list[dict]:
    out = []
    for spec in sorted(enabled_specs(ctx), key=lambda s: s.order):
        text = spec.render(ctx)      # 渲染零加工
        if not text:                 # 「没有来源就不出现这个区」——唯一的内建判据
            continue
        out.append({"order": spec.order, "name": spec.name, "channel": spec.channel,
                    "seats": spec.seats, "text": text,
                    "entries": spec.count(ctx, text) if callable(spec.count) else spec.count})
    return out
```

装配器**不再认识任何具体区**——不认识卡片清单、不认识记忆。它只认注册表。

### 3.3 `RegionCtx`：取数一次（IO 与渲染分家）

```python
@dataclass
class RegionCtx:
    work_id: str
    card_id: str
    cards: list[dict]              # 卡片索引（一次查库）
    work_card_id: str
    cur: dict | None               # 当前卡（从 cards 取）
    cur_meta: dict                 # 当前卡 meta（card_type 等）
    project_class: str             # 本树 project_class
    type_registry: dict            # 类型注册表
    memory_state: dict | None      # 凝练态（routes 传或兜底读）
```

**取数集中在 `build_ctx(...)`**（一处 IO），渲染器**一律纯函数**（沿用 `context_regions` 既有纪律：本模块不做 IO）。

### 3.4 控制面（"可以被控制"）

**控制数据＝配置文件**（沿用本项目"配置即能力"先例：`card_type_registry.json` / `permissions.json`）：

```jsonc
// config/context_regions.json（新）
{
  "_meta": { "version": "context-regions-v1", "note": "区的启停与顺序；未列出＝用注册表默认" },
  "regions": {
    "card_duty":  { "enabled": true,  "order": 90  },
    "card_list":  { "enabled": true,  "order": 100 },
    "identity":   { "enabled": true,  "order": 150 },
    "region_guide": { "enabled": true, "order": 155 },
    "memory":     { "enabled": true,  "order": 200 }
  }
}
```

- **读不到/坏 JSON → 用注册表默认**（fail-open，与类型注册表同纪律：**配置是控制源，不是可用性依赖**）；
- 只实现**全局**这一层；**按卡 / 按卡类型**的覆盖**预留字段不实现**（`scope` 留白）——因为将来的【规则卡】要按卡控制，接口形状先定、实现后补。

### 3.5 与 messages/user 通道的关系（**待用户定**，见 §五-1）

`300 对话历史 / 900 本轮工具轮 / 999 用户消息` 现在由 `message_runner` 装配（不是 system 区）。两种走法：

- **甲（我倾向）**：本步**只管 system 通道**（0/90/100/150/155/200），messages/user 仍由 runner 管；注册表里保留它们的声明（供日志口径统一）。
- **乙**：一步到位，把 messages/user 也纳入同一注册表（runner 改成遍历）——**改动面大得多**，且与消息底座线正在施工的改动面重叠。
