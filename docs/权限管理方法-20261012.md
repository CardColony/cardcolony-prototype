# 权限管理方法（2026-10-12 · 权限底座重做后）

> 本文讲**现在这套权限机制怎么用**：设计是什么、日常怎么配、怎么查、怎么扩展。
> 代码事实均经实读核实；改动记录见 `docs/权限底座重做-方案-20261012.md` / `-任务书-20261012.md` / `-执行回报-20261012.md`。

---

## 一、一句话

**每张卡有一个"类型"，类型决定它开哪些权限开关；权限在建卡那一刻算好、写死在卡上，运行时照读，不重新算。**

## 二、七条设计原则

| # | 原则 | 白话 |
|---|---|---|
| 1 | 按类型分权，两级定位 | 权限看两级：**工牌**（`project_class`，这个项目的性质）+ **类型**（`card_type`，这张卡的角色） |
| 2 | **类型不可变** | 类型建卡时定死，此后一律不许改（API 层 + 存储层双层拒） |
| 3 | **可配置** | 加新类型 = 改配置文件，代码零改动 |
| 4 | **权限固化 + 版本刷新** | 建卡时算一次写进卡；配置改版时跑刷新脚本更新旧卡 |
| 5 | **默认关门** | 没配到的类型 = 一项权限都没有 |
| 6 | **开关可扩展** | 加开关 = 代码加常量 + 配置用起来 |
| 7 | **未来方向** | 卡片只读 + 建卡预置内容（`edit` 最终会收走，本次先保留留余地） |

## 三、12 个权限开关

| 开关 | 白话 | 管哪些工具 |
|---|---|---|
| `read` | 能读 | read_card / read_memory / read_shadow |
| `edit` | 能改（未来会收走） | edit_card |
| `delete` | 能删 | delete_card |
| `create_child` | 能在它下面建子卡 | create_card |
| `link` | 能连线 | link_cards |
| `unlink` | 能解线 | unlink_cards |
| `shadow_write` | 能写自己的影子卡 | update_shadow |
| `manuscript` | 能查阅项目存档原始资料 | list_manuscript / read_manuscript / search_manuscript |
| `invoke_tool` | 能调用工具卡 | run_tool_card |
| `plan` | 能建计划 / 改计划 / 推进步骤 | create_plan / plan_reorder / plan_insert / plan_remove / plan_modify / step_complete |
| `tools_file` | 能读写文件 | list_files / read_file / search_files / write_file |
| `tools_web` | 能联网 | web_search / fetch_web |

12 个开关管住 25 件工具，一一对应（映射表在 `card_tools.TOOL_SWITCH`，测试钉住完备性）。

**每个开关同时决定两件事**：这件工具对这张卡**看不看得见**（工具面），以及这次调用**允不允许**（执行层关口）。两件事同源——卡上没有这个开关，模型压根看不见它，不只是调了被拒。

## 四、当前配置（`config/permissions.json`，version=1）

| 工牌 | 类型 | 权限 |
|---|---|---|
| rd_project | project（根卡） | read, edit, create_child, link, unlink, manuscript, invoke_tool, plan, tools_file, tools_web, shadow_write |
| rd_project | sub_project | 上述全部 + **delete** |
| rd_project | tool | read, edit, delete, plan, shadow_write（**无** create_child / link / unlink / manuscript / invoke_tool / tools_file / tools_web） |
| research_project | project（根卡） | 同 rd_project 根卡 |
| research_project | topic | 同 rd_project sub_project |

四条读法：
- **根卡没有 delete** —— 项目根基删不掉（所以工具面也少一件 `delete_card`，见 24 vs 25）；
- **tool 卡不长树、不连线、不碰文件联网、不查资料、不调工具卡** —— 它是个被调用的执行体，只干活、不探索；它保留 `plan`（要能推进自己的剧本步骤）；
- 两级都查不到 = 空权限 = 全拒；
- 映射表没配的工具 = 不下发（默认关门，防以后加工具漏配开关）。

## 五、运行时怎么判

一次卡片操作，走 `policy.check(actor, target, switch, cards)`，**两道**：

1. **类型分权**：看 `target` 卡上固化的 `perms` 里有没有这个开关 → 没有就拒；
2. **树作用域**（仅写侧开关 `edit/delete/link/unlink/create_child`）：看 `actor` 是不是在 `target` 的子树上游 → 不是就拒。

读侧（`read`）不走树作用域 —— **读侧全盘可读**（存在即放行）。

调工具（manuscript / invoke_tool / plan / 文件 / 联网 / 写影子）看的是**当前卡自己**的 `perms`。

两层的拒绝文案是分开的（"分类不授权" / "越出子树"），模型能分辨自己错在哪。

**事前还有一道工具面**：每轮对话组装工具清单时，`card_tools._filter_by_category` 逐件查这张卡的 `perms` —— 没开关的工具**压根不写进发给模型的清单**。所以模型不是"看得见调了被拒"，而是**看不见**。

三层各司其职：

| 层 | 时机 | 作用 | 表现 |
|---|---|---|---|
| 工具面 | 组装工具清单时 | 这件工具**看不看得见** | 没开关 → 不下发 |
| 类型分权 | 工具被调用时 | 这个动作**允不允许** | 没开关 → `denied` |
| 树作用域 | 写类动作时 | 允不允许**越出自己子树** | 不在子树 → `denied` |

## 六、日常操作手册

### 加一种新卡片类型

1. 在 `config/permissions.json` 的 `permissions` 里，给对应工牌加一行 `"新类型": [...开关...]`；
2. 把 `version` 数字 +1；
3. 跑 `python scripts/refresh_perms.py`；
4. 代码一行不用动。

### 改某类型的权限

同上（改列表 → version+1 → 跑刷新）。**注意：只改已建好的卡要跑刷新；新建的卡自动按新配置算。**

### 加一个新权限开关

两步，缺一不可：
1. 代码 `src/permissions/policy.py` 加一个常量（进 `SWITCHES` 集合）；
2. 配置里用起来。

只改配置不生效是**有意的** —— 防止拼错的名字悄悄变成一个"看起来配了、其实无效"的权限。

### 查一张卡有什么权限

- 直接看卡文件 front matter 的 `perms:` 行；
- 或代码里 `policy.perms_for(project_class, card_type)` 查"这个类型应该有什么"；
- `has_perm(card_meta, switch)` 查"这张卡有没有某个开关"。

### 权限配置改版了怎么办

`config/permissions.json` 的 `version` +1，然后：

```bat
python scripts/refresh_perms.py                  :: 刷新全部 work
python scripts/refresh_perms.py --work work_002  :: 只刷一个
python scripts/refresh_perms.py --dry-run        :: 只报会改哪些，不动盘
```

脚本按 `perms_version` 判落后，只重写版本旧的卡，**幂等**（重复跑无副作用）。只写 `perms` / `perms_version` 两个字段，正文和其他 front matter 一概不动。

## 七、护栏（哪些事机械上做不到）

| 想干的事 | 结果 |
|---|---|
| 改卡的类型 | API 层拒（白名单无 `card_type`）+ 存储层拒（无条件） |
| 删根卡 | 配置里根卡无 `delete` → 拒 |
| 给工具卡建子卡 | 配置里 tool 无 `create_child` → 拒 |
| 工具卡读写文件 / 联网 | 配置里 tool 无 `tools_file` / `tools_web` → 拒（工具不下发 + 执行时拒） |
| 动别人子树里的卡 | 树作用域拒 |
| 用没配的类型建卡 | 默认关门 = 空权限 = 全拒 |
| 工具卡调计划工具 | 有 `plan` 开关，不拒 |

## 八、边界与已知现状

- **`FILE_SCOPE` 还是占位 `[""]`**（全放行哨兵）—— 它是 `perms` 之外额外加的一层"路径前缀"约束，真实前缀待定，当前不影响正确性。
- **`SHADOW_WRITE` 四类型全授** —— 维持现状：影子卡写的是每张卡自己的过程，不涉及越界，按类型区分无意义。
- **`edit` 现在还在** —— 卡片编辑、结论沉淀仍依赖它。未来要收走时，把 `edit` 从配置里删掉即可，代码不用动。
- **`scripts/migrate_card_types.py` 已失效** —— 类型不可变后这个迁移脚本没用了，属历史件，未删未改。
