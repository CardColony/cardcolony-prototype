## 1. 事件类型与 schema（任务 2）

### 1.1 类型登记

- `src/api/event_stream.py:91-98` `EVENT_TYPES` 增加两项：
  `"context_preamble"`、`"context_injection"`（本体论 23 → 25）。
- `src/storage/event_log.py` **无类型白名单**（只有 `RECORD_KEYS` 七键与 `CONTROL_TYPES`），
  故**不新增校验**，七键外壳一字不改，两种事件沿用既有外壳。

### 1.2 `context_preamble`（固定总领）

```json
{
  "type": "context_preamble",
  "data": {
    "source_kind": "thinkchain",
    "source_ref": "board.STEP_BRIEF_TEMPLATE",
    "run_context": {"plan_name": "导出功能"},
    "content": "【步骤执行】你现在执行计划的一步，只做本步的事。\n\n执行纪律：\n1. …\n2. …\n3. …\n4. …"
  }
}
```

- `source_kind` ∈ {`thinkchain`, `toolcard`}。
- **本任务只发 thinkchain**（用户裁定）：toolcard 侧**保留 schema 位**（`source_kind="toolcard"`、
  `source_ref={"script_name": …}`、`run_context`），但**不发事件**——无正文不得发空壳。
- `content` 的 thinkchain 取值＝`board.STEP_BRIEF_TEMPLATE` 的**固定部分**（去掉三行占位变量后的原文）。
  **单一来源**：由 board.py 内一个派生函数从 `STEP_BRIEF_TEMPLATE` 现算（按行剔除含
  `{prompt}`/`{criteria}`/`{deliverable}` 的行），**不新增第二份文本常量**。

### 1.3 `context_injection`（动态步骤）

工具卡 `source_kind="toolcard"`：

```json
{
  "type": "context_injection",
  "data": {
    "source_kind": "toolcard",
    "source_ref": {"script_name": "方案链", "step_id": "p2"},
    "step_id": "p2",
    "content": {"prompt": "……本步提示词原文……", "artifacts": ["01-p1-任务书读取-01.md"]}
  }
}
```
来源：`driver._runtimes[card_id]`（script_name/step_id）＋ `script_loader.load_prompt`（prompt 原文，
一字不改）＋ `artifact_store.manifest_entries`（只列登记文件名，**不读内容、不评价**）。

思维链 `source_kind="thinkchain"`：

```json
{
  "type": "context_injection",
  "data": {
    "source_kind": "thinkchain",
    "source_ref": {"plan_name": "导出功能", "step_id": "S2"},
    "plan_name": "导出功能", "step_id": "S2",
    "index": 2, "total": 4,
    "completed_steps": [{"step_id": "S1", "prompt": "……", "result": "……"}],
    "current_step": {"prompt": "……", "criteria": "……", "deliverable": "……", "type": "execute"}
  }
}
```
来源：`board.snapshot_sync` 快照。`result` 长度口径**沿用现状（800 字符）**，本任务不改。

## 2. 模型消息投影（任务 2 / 5）

### 2.1 投影规则

事件→模型消息的投影**只发生在网关组装处**，事件本体与 data 不变：

| 事件 | 投影 role | 投影 content |
|---|---|---|
| `context_preamble` | `INJECTION_ROLE`（见下） | `〔工作规范〕\n` + 渲染文本 |
| `context_injection` | `INJECTION_ROLE` | `〔当前流程〕\n` + 渲染文本 |

> ⚠️ **[当前轮注入改assistant自述 2026-10-14] 本表已被后续任务书覆盖**：
> 投影 role 由 `user` 改为 **`assistant`**，抬头由 `〔上下文注入·…〕` 改为
> `〔工作规范〕/〔当前流程〕`，正文改为**第一人称自述**。依据
> `docs/当前轮注入改assistant自述-任务书-20261014.md`（v2）。事件层（type/data/
> 七键/幂等键/落盘/timeline）不变。

- `INJECTION_ROLE` 定义为**单一常量**（**现取值 `"assistant"`**，见上覆盖说明），便于一处改、一处测。
- 渲染文本＝把 `data` 结构化字段还原成人类可读文本（toolcard：`【当前剧本】/【当前步】/【本步要求】/【上一步产物】`；
  thinkchain：`当前计划/当前第 N/M 步/已完成步成果/本步要求/完成判据/产出物`）。
  渲染只在**投影层**做，事件日志里**始终是结构化 data**。
- **禁止**：自定义 type（`context_preamble`/`context_injection`）直接当 role 下发；
  `tool_call`/`tool_result` 事件**不得**被当作可发送消息（工具协议配对仍走现有轮槽）。

### 2.2 role 取值：一个待你在评审时确认的点

> ⚠️ **[当前轮注入改assistant自述 2026-10-14] 本节裁定已被覆盖**：原推荐 `user`
> 的结论**作废**；现行为 **`assistant`**（用户 10:44 裁定「用 assistant，包装成
> 自述的工作规范/流程」）。依据 `docs/当前轮注入改assistant自述-任务书-20261014.md`（v2）。
> 下列原文保留以备溯源，不再代表现行裁定。

- 推荐 **`user`**：OpenAI 兼容端点普遍接受，最稳；内容自带 `〔上下文注入·…〕` 标记，
  与真实用户发言可区分；事件/会话/timeline 层仍是 `context_*` 类型，**不构成"伪装成用户发言"**
  （红线针对的是事件与展示身份，不是 wire role）。
- 备选 **`system`**：语义更贴"系统给的上下文"，但**会话中途插 system 消息**在部分
  OpenAI 兼容端点（尤其 Anthropic 经 litellm）接受度不稳。
- **决策依据＝兼容测试**：见 §5.3。若 `user` 被拒 → 回退顺序为 ①合并为一条 user 消息
  ②改 `system`。该回退只改 `INJECTION_ROLE`/投影函数，不动事件层。

## 3. 时序挂点（任务 3 / 4）

### 3.1 现状调用序（实读）

```
round1: call_main(system, user_prompt=用户原文, prior_for_gateway=历史, tools)
        gateway: [system] + 历史 + [user(原文)]
工具分支: slot.append_plain(user 原文) → slot.begin_round(assistant 工具调用) → append_tool_result
round2+: call_main(system, user_prompt="工具结果已返回。", wire_messages=slot, tools)
        gateway: [system] + slot + [user("工具结果已返回。")]
```
（`message_runner.py:338-632`、`gateway.py:543-546`）

### 3.2 挂点：每个模型调用之前统一同步一次

在 `message_runner.step()` 的模型调用**之前**（`check_control` 之后）新增一个同步函数
`_sync_injection(state)`，逻辑：

1. **选源**：沿用现行互斥选择——`driver._runtimes.get(card_id)` 有 → toolcard；
   否则 `board.snapshot_sync` 有当前步 → thinkchain；两者皆无 → **不发任何事件**。
2. **固定总领**：若本 run 尚未发过 preamble 且源为 thinkchain → 发 `context_preamble`
   （thinkchain 固定部分），记 `state.preamble_emitted=True`。toolcard 不发（§1.2）。
3. **动态步骤**：算当前步身份键（§4）。键未发过 → 发 `context_injection`，记入已发集合。
4. **投影落地**（关键——决定注入在序列中的位置）：
   - `state.rounds == 1`（尚未有任何工具轮）：把 `[user 原文, preamble 消息?, injection 消息?]`
     作为 `turn_tail` 传给网关（见 §5）；同时存进 `state.turn_tail`。
   - `state.rounds >= 2`：把新产生的注入消息 `slot.append_plain(...)` 追加到轮槽当前末尾。
     该位置恰在**上一步推进事件（step_advanced）之后、下一步首个动作之前**——符合任务书 §四.3。

### 3.3 工具分支的配套改动

`message_runner.py:468-469` 现只把 `user 原文` 追加进 slot。改为把 `state.turn_tail`
**整段**追加进 slot（含 preamble/injection），使 round2+ 的 `wire_messages` 已含这些消息——
**续调不再重贴**，位置固定在它们首次出现处。

### 3.4 各场景的注入位置（对照任务书 §四）

| 场景 | preamble | 第一条 injection | 说明 |
|---|---|---|---|
| 无注入（直答、无板无运行时） | 不发 | 不发 | 与"没有来源就不出现"等价 |
| 续轮（turn 开始时板/运行时已在） | round1，紧随 user 原文 | round1，紧随 preamble | 满足 V1 |
| 新拆解轮（round1 才 create_plan） | round2 起，随第一条 injection | round2 起（板刚上架） | 板在 round1 工具结果后才存在，无法更早 |
| 工具卡轮 | 不发 | 运行时出现处 | toolcard 本任务不发 preamble |
| 步骤推进 | 不重发 | 推进事件之后、下一步首动作之前 | 满足 V4 |

> ⚠️ 上表「新拆解轮」与「步骤推进」两行的位置，是把"步骤开始处"取为**该步首次进入的点**；
> 这是本方案对任务书 §四.3「在其步骤开始时插入」的落地口径，请评审确认。

## 4. 幂等键（任务 2 / 4）

- **键** ＝ `f"{run_id}|{source_kind}|{step_identity}|{content_ver}"`
  - toolcard：`step_identity = f"{script_name}:{step_id}"`；`content_ver = sha1(prompt 原文 + 排序后的 artifacts)`
  - thinkchain：`step_identity = f"{plan_name}:{index}:{step_id}"`；`content_ver = sha1(current_step 三字段 + completed_steps 的 (step_id,result))`
- 已发集合存 `RunState.injection_keys: set[str]`；**同 run 内键相同即不发**。
- 为什么带 `content_ver`：任务书 §八.3 要求"同一内容是否因板修订而变化"可辨——改板后同一
  步身份但内容变 → 键变 → 发新注入（这是**有意**的，不是重复）。
- **不靠"当前轮最后一条"判断**（任务书明令）。

## 5. gateway 变更范围（须先批准——本次只呈报）

### 5.1 现状

`gateway.stream_call`/`call` 与 `MockGateway` 同款构造：
```
messages = [{"role":"system","content":system_prompt}]
if prior_messages: messages.extend(prior_messages)
messages.append({"role":"user","content":user_prompt})     # ← user 恒为最后一条
```
`user_prompt` 是单条字符串，**无法在它之后插入多条注入消息**。

### 5.2 拟改（最小、向后兼容）

给 `call` / `stream_call`（真实＋Mock 各两份）增加**可选**形参
`turn_tail: list[dict[str, Any]] | None = None`：

```python
if turn_tail is not None:
    messages.extend(turn_tail)                              # 新增路径
else:
    messages.append({"role": "user", "content": user_prompt})  # 既有路径，逐字不变
```
- `model_service.call_main` 同步加 `turn_tail=None` 并透传；fallback 递归也透传。
- **默认 `None` ⇒ 既有所有调用方（三席/凝练/起草/卡间调起等）消息构造逐字不变**（零回归面）。
- 只有主循环 round1 走新路径。

### 5.3 兼容证据（须在实现时给出）

1. `grep` 全部 `call(`/`stream_call(` 调用点，确认仅 `call_main` 一处透传、其余不传新参。
2. 单测：`turn_tail=None` 时 messages 与改前逐字节一致。
3. **端点兼容测试**：对 config 里配置的真实 provider 发一次含 `turn_tail`（user-role 注入，
   含连续 user 消息）的请求，断言 200。**须实现环境有授权与可运行条件**；否则如实标注
   "未实弹，仅 mock"，不得把 mock 描述成实弹验收。
4. 若 `user` 连续消息被拒 → 按 §2.2 回退，并记录被拒端点与原文案。

### 5.4 禁改边界说明

任务书 §八.2 要求：若方案认为必须改 gateway，先单独呈报范围与理由。
**本方案 §5.2 即该呈报**：范围＝`gateway.py` 两函数各加一可选参 ＋ `model_service.call_main`
透传一参；理由＝不改则无法表达"user 之后插注入"；风险＝默认路径零变化。
