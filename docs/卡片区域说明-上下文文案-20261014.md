## 二、文案（按树 × 卡种）

**第三块的名字由本树决定，文案里只出那一个名字**（研发树→需求文档；研究树→定论），**不并列、不互相提及**。

### 2.1 研发树 · 普通卡（`sub_project` / `topic` / `tool`）

```text
〔卡片区域说明〕这张卡的正文分三块，各管各的，不要混写：

使命——这张卡要做什么、要做成什么（目标与交付物）。
      写法：≤5 行，一句话说清；立项定稿，只有用户能改，你没有写它的通道。

现状——这张卡当前确定的状态与结论。
      别的卡读这张卡，先读的就是它——所以这里写**别的卡继续工作要知道的三类东西**：
      · 当前确定状态：现在已经确定了什么、哪些能作为其他卡工作的依据；
      · 接口与约定：它对外提供什么，输入输出、调用方式、约束是什么；
      · 依赖与影响范围：它依赖哪些模块；它变更时哪些卡或功能会受影响。
      写法：整块覆盖、只保留最新一份；只写已经确定的结论；
            不写过程、不写"做到哪"的流水账。

需求文档——本功能全部需求的确定版详细描述，是本功能需求的唯一确定源。
      写法：按需求逐条写清"要什么、验收标准是什么"；只写确定版；
            讨论、备选、过程不写这里。
```

### 2.2 研发树 · 根卡（`project`）

```text
〔卡片区域说明〕这张是项目根卡，正文分三块，各管各的，不要混写：

使命——整个项目要做成什么（总目标与范围）。
      写法：≤5 行；立项定稿，只有用户能改，你没有写它的通道。

现状——项目当前确定的状态与结论。
      别的卡读根卡，先读的就是它——所以这里写别的卡继续工作要知道的三类东西：
      · 当前确定状态：项目现在已经确定了什么、哪些能作为其他卡工作的依据；
      · 接口与约定：项目对外提供什么，输入输出、调用方式、约束是什么；
      · 依赖与影响范围：依赖哪些模块；变更时哪些卡或功能会受影响。
      写法：整块覆盖、只保留最新一份；只写已确定的结论，不写过程。

需求文档——本项目全部需求的确定版详细描述，是项目需求的唯一确定源。
      写法：按需求逐条写清"要什么、验收标准是什么"；只写确定版，不写讨论与过程。
```

### 2.3 研究树（第三块＝定论）

同上两套，把「需求文档」整段替换为：

```text
定论——本课题已经作出的决定与收敛。
      写法：只追加、不删不改；一条一行，写清"决定了什么、依据是什么"；
            某条失效就在原处标一行"→ 被Dxx取代"，不保留原文。
```

### 2.4 影子卡（本卡私有——只有本卡读得到）

正卡文案之后接一段：

```text
〔影子卡区域说明〕影子是本卡自己的过程记录，别的卡读不到，只有你能读写：

产物清单——**交接物与权威位置**：完成的结果在哪里，哪份文档/代码/数据是准的。
      写法：一行一条指针（路径＋用途），只写指针，不搬正文。

待协作事项——**需要谁提供什么、卡在什么外部条件上**。
      写法：一条一项，写清"等谁确认什么、确认后本卡才能继续"。

迭代历史——系统自动记的改动留痕，你不用写。

进度——不重要，不必特意维护。
```

**不含「修改历史」**（用户 22:04：模型不需要知道）。

## 四、注入点设计（上下文侧，我定）

| 项 | 值 | 理由 |
|---|---|---|
| 形态 | **system 区**（不是注入消息） | 它是"读卡/写卡前必须知道"的**常驻规则**，不是一次性的轨迹引导；随当前卡变化 |
| order | **155**（紧随 150 当前卡之后） | 讲的就是当前卡的块；与"当前卡"相邻成组 |
| name | `卡片区域说明` | |
| channel | `system` | |
| seats | `("main",)` | 写卡的是主模型；三席只审议 |
| 择套 | 按当前卡 `card_type`（根卡/普通卡）× 本树 `project_class`（研发/研究） | 方案 §6.3.3 ＋ 用户 22:04 ② |
| 重发 | 随区装配每轮生成；**换卡即变**（无跨轮状态，天然不重复） | 方案 §6.3.5 |

**与 `read_card` 工具说明的分工**：工具说明讲"怎么调"，本区讲"每块是什么、怎么写"。
