# 串行执行策略（2026-10-22）

> 适用范围：`config/exec_mode.json` = `serial` 的 work（当前 5703 实验）。
> 本文是**策略**：定规则，不定实现。文中标「现状」的是已经长在代码里的，
> 标「待做」的是还没实现的。

## 零、一句话

同一时刻一个 work 只有一张卡在跑；**跑什么、按什么顺序、信息怎么流、失败怎么办**，四件事分开定。

---

## 一、调度顺序（下一个跑谁）

一轮 = 一次模型调用 + 若干工具调用 + 一次收口。**每轮结束重新选**，不是一张卡跑到死。

优先级（高 → 低）：

| 级 | 谁 | 为什么 |
|---|---|---|
| 1 | **人类回合**（有人在等回复） | 人的等待是唯一有外部时钟的 |
| 2 | **职能同步**（有未处理的 watch 同步） | 它只在"被关注卡收口"这个瞬间有意义，错过就过时 |
| 3 | **任务卡**：只在「没有活跃子卡」的卡里选，叶子优先，同级按创建时间 | 深叶子先跑＝先把活干出来 |

「没有活跃子卡」的判据已有：`auto_driver.has_active_child()`（`goal_state=="active"` 的直接子卡）。
**这一条保证了 U6/U8（一张子卡跑完再下一张），不需要靠"锁持有整个目标周期"**。

> 现状：锁是「整目标生命周期」（`serial_gate.py:10`），队列纯 FIFO 无优先级。
> 待做：轮级锁 + 上面的优先级。

---

## 二、信息顺序（谁先看到谁的结果）

串行的正确性不只在"谁先跑"，更在**信息到达的先后**。一条协作信息的生命周期：

```
① 父卡派活          → 子卡建 goal
② 子卡被调度、跑一轮 → 更新自己的「现状」
③ 子卡目标终止       → 发完工回执给父卡（msg）
④ 父卡被唤醒         → 读子卡的「现状」→ 继续
⑤ 任何卡收口         → 把新增内容同步给 watch 它的职能
⑥ 职能判完           → 写判词 / 发指令（指令要求对方执行并回来验收）
```

**四条硬规则**：

1. **现状先于回执**：子卡必须先把「现状」写进去，再发完工回执。
   父卡读的是**现状**，不是回执——回执只说"我完了"，现状才说"我做成什么样"。
2. **同步后于收口**：职能的同步必须发生在被关注卡**收口之后**，不能看半成品。
   现在的落点是对的（`role_room.after_turn` 在回合收口后调）。
3. **指令后于结果**：职能必须先看到结果，才能下指令。不许凭"应该做完了"下指令。
4. **回执不替代验收**：父卡收到"完工"不等于验收通过——要按需求文档核三环
   （交付物↔需求↔目标），核不过就打回。

## 三、重试（两级，都不进对话）

### 3.1 调用级（现状，已实现）

`model_gateway/gateway.py` 内部按错误类别重试：

```
auth 1 次 / timeout 2 次 / 503 5 次 / rate_limit 5 次 / connection 3 次 / error 3 次
总预算 300 秒，退避上限 30 秒
```

失败重试耗尽 ⇒ 如实上抛，不做降级切换（2026-10-19 产品裁定）。

### 3.2 回合级（待做）

一轮异常结束（`outcome in ("error", "max-tokens")`）时，**现在会 `disarm`（撤销续轮）**，
卡就停了。策略要求改成：

```
异常 → 记一次 retry_count
      retry_count < N（建议 5）
        → 退避（2s / 4s / 8s / 16s / 30s）
        → 用**同一份输入**重跑这一轮
      retry_count >= N
        → disarm + 标 blocked(reason="连续 N 次回合异常")
```

### 3.3 为什么重试不能发消息

「上次失败了，再试一次」如果作为一条 `user_message` 进对话：

- 模型会看到自己失败过 → 后面每一轮都背着这个包袱 → 判断被污染；
- 事件流里留下一条"失败"，刷新后还在，人会以为真的出过事；
- 同一件事在上下文里出现两遍，卡片"现状"与对话不一致。

**所以重试只发生在调用层和回合层，对话面零痕迹**。
现在的 `goal_prompt` 走 `append_user=False`（不落档案）——这个口径要保住。

## 四、职能（role / function）在串行里的位置

职能是**离树观察者**：不建树、不占任务执行锁。

| 项 | 规则 |
|---|---|
| 占不占串行锁 | **不占**（`card_type in ("role","function")` 跳过 `acquire`） |
| 什么时候被调度 | 第 2 优先级：有未处理同步时 |
| 能不能打断任务卡 | **不能**。它插在轮与轮之间，不抢正在跑的那一轮 |
| 看到什么 | 被关注卡的「现状」+「需求文档」，不是半成品 |
| 产出 | 判词（记台账）/ 指令（对方必须执行并回来验收）/ 警报（直达人） |

> 现状：职能走 `_run_message` → `serial_gate.acquire` ⇒ 排在任务卡后面，
> 而任务卡持有锁直到**目标终止** ⇒ 职能等于不工作。
> 待做：跳过 `acquire`。

## 五、饿死与死锁（怎么兜底）

| 场景 | 现状 | 策略要求 |
|---|---|---|
| 父卡等子卡 | ✅ 让位放锁（`has_active_child`） | 保持 |
| 卡目标永不终止 | ❌ 锁永不释放，全队列饿死 | 回合级重试上限 → 标 blocked，让人看到 |
| 职能抢不到锁 | ❌ 饿死 | 职能不占锁 |
| 人插话 | ❌ 排到队尾 | 第 1 优先级，立即插 |

**不设锁超时**（超时本身就是一种闸）。兜底靠「回合级重试上限 → blocked」，它是**可观测的**，
而不是无声挂起。

## 六、改动清单（若要实施）

| # | 改哪 | 改什么 | 影响面 |
|---|---|---|---|
| 1 | `serial_gate.py` | 轮级锁 + 优先级队列（或换成调度器） | 小，只这一个文件 |
| 2 | `routes.py` `keep` 判定 | 轮末必放锁（不再"整目标周期"） | 一处 |
| 3 | `serial_gate.acquire` | 离树卡跳过 | 一处 |
| 4 | `goal/driver.notify_idle` | `error` 时按 retry_count 重跑而非 disarm | 一处，要加计数 |
| 5 | 新增调度函数 | 按 §一 的优先级选下一张卡 | 新增 |

前 3 项是串行的核心；第 4 项是重试；第 5 项把"谁先跑"从"谁先抢到锁"变成"谁更该跑"。
