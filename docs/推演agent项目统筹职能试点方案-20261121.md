# 推演agent 项目统筹职能试点方案

**待确认设计 · 2026-11-21**

外部开发从[项目统筹职能施工任务书](./推演agent项目统筹职能施工任务书-20261121.md)进入。本文说明角色与试点目的，任务书规定第一版入口、权限、执行顺序和验收用例。

建议在推演agent里把「项目统筹」做成一项可以任命给职能卡的差事。一个计划由一位强模型负责人持续判断方向、安排开发、协调子卡和纠偏。弱模型替它观察变化，按强模型写的标准提请唤醒。第一期用 CardColony 重构计划检验这项职能。开发与试点授权均以用户后续确认为准。

## 谁对计划负责

| 角色 | 负责的决定 | 一次具体工作 |
|---|---|---|
| 用户 | 定目标、授权范围、改变产品取舍、任免统筹 | 指定底座本期承诺，授权统筹观察和指挥本 work 的开发卡 |
| 项目统筹，强模型 | 维护唯一施工计划，依据现行需求直接判偏、改顺序、拆工作，向责任卡发指令并跟踪结果 | 发现合法多线场景被拒，查原文和实现，协调关系域与装配域修复 |
| 观察，弱模型 | 按当前计划判断某个变化是否值得提前叫醒统筹 | 指出某个新必填字段可能把无卡参与者挡在门外，附条款与变更位置 |
| 产品经理、技术总监、测试验收 | 按需回答具体问题；前两者通过本次拟增的计划内只读专业回合给依据，验收方沿已有验收差事独立复验 | 产品经理找出原始用户场景，技术总监核身份来源，测试验收用无卡 agent 独立复验 |

第一期把统筹任命给一张独立于根卡的职能卡。允许现有产品经理兼任，通过计划专属的差事上下文执勤。日常产品经理、评审席位和这项差事各自使用对应职责与工具。弱模型是这项差事内部的一次只读调用，无须再建一张需要别人汇报的卡。

**同一事项由一位负责人收口。** 例如，把卡号改成公共入口的必填项，会同时影响自由 agent 接入、三个模块的开发顺序和验收用例。如果产品经理和项目经理各自指挥，处理一个变化就要交接两次。第一期由统筹把需求判断和工程调整放在同一个决定里。已有需求能判定的偏离，统筹可以直接下令。需求含混时可以请产品经理或技术总监核实；真正要改变用户承诺，由用户决定。统筹可以核实自己发出的指令是否生效，独立验收仍由验收方负责。如果以后确需多位统筹，按可以独立验收的计划分别授权，交叉事项明确一个负责人。

## 计划与专属上下文

在 work 中选择一张卡作为计划载体，在其卡面保存一份可修改、可回看版本的计划。首版计划写清目标、依据的需求及版本、本期承诺、各项负责人和依赖、下一个可观察结果、唤醒标准和最迟独立回看时间。项目事实继续来自各卡、正式事件和产物。计划引用它们，避免复制一棵很快过期的卡树。用户可随时查看、改目标、暂停或收回授权。

**强模型醒来**先看到用户目标、当前计划、上次决定及其待验证结果、本次为何被叫醒、此后有实质变化的卡及证据入口。它随时可以打开全 work 的授权进展视图，主动检查一张长期无人提起的卡，按需读需求、原始运行输出、代码和工具回执。普通汇报即使已送达，也不自动进入统筹对话或单独起一轮。向用户发言主要留给需要用户取舍和用户主动询问的情形。

**弱模型**只看当前观察标准、关联条款、该事项自上次观察后的变化和证据指针。它可以指出标准以外的实质矛盾。它的输出包含是否提请唤醒、哪项承诺可能受影响、依据在哪里、需要强模型决定什么。它只能读取已授权材料和提交观察结果。

## 怎样唤醒

1. **发生有意义的变化。** 宿主从已有事件流汇总正式需求或契约变更、任务归属变化、验收结果、可核实的运行结果等。同一事项的多条通知合成一批。普通工具逐跳、重复汇报、统筹自身记账不单独触发模型。源码层的判断以可读取的变更或证据为准；没有对应事件的变更，由独立回看主动抽查。
2. **弱模型提请提前唤醒。** 标准由强模型在建立或调整计划时写下，包含要保护的行为、可以放过的变化、应当升级的变化。高影响而证据不足也可以升级。强模型看过证据再决定是否干预。同一风险的重复回报只补充证据；新证据改变影响范围可再次提请。
3. **指定节点和最迟回看直接唤醒强模型。** 用户点名、计划明确指定的关键决策节点，以及独立回看到期，都走直接路径。最迟时间由强模型按返工代价约定，保存在宿主。即使所有卡都静默，或弱模型每次都判断正常，活跃计划仍会到期回看。强模型须实际抽查一项原始承诺，并留下结论或尚缺的证据，才可设下一次期限。临时处理别的事、重复事件和预算合并均不能偷偷顺延。
4. **介入和休眠。** 强模型核对原文与产物，选择继续观察、补证据、调整计划、向责任卡发指令或提请用户取舍。它记下依据、收件卡、动作回执、何时再核结果，随后休眠。到期时若已有强模型回合，回看并入该回合或紧随其后。暂停、到期欠办、撤销、计划结束在卡面可区分。模型不可用或额度耗尽时，宿主保留待办并显示原因，恢复后处理。

**唤醒标准示例。** 本阶段保护「外部 agent 无卡也能接入」。卡片模块内部增加可选关联时继续观察。公共协议把卡号改为必填，或正式启动开始查询卡片注册表时，叫醒统筹。影响已经到达公共入口但无法从变更判断兼容性时也叫醒，带上根卡条款、改动位置和仍未知的那一点。

## 怎样接进现有推演agent

| 已有能力 | 第一期要补的部分 |
|---|---|
| 职能目录、按场取职责书与授面，已有评审、派驻与执笔差事 | 增加可选的计划统筹差事，绑定 work、计划卡、任职职能、授权范围和两条模型路由。用户按计划启用；只在任职期间获得这项上下文和工具。 |
| 卡面、需求、任务及原始证据 | 计划正文只在计划卡写一份。观察进度、处理到哪个事件、到期时间与回执属于运行状态。回合提交前核对计划版本，已撤销的授权或过期计划不得继续发令。 |
| 已落盘事件、条件分发、模型调用及卡回合调度 | 增加按计划合并变化的入口、一次只读的弱模型判断和持久的到期唤醒。每个计划同一时刻至多一个强模型回合。重启后恢复未处理事项及欠办回看；多 runner 同见一次变化只认领一次。 |
| 现有按权限读卡、通信线检查、`direct` 和收件回执 | 明确“观察全 work”和“对授权开发卡发令”的范围与执行身份。发令沿现有通信路径，按授权建立所需连接，保留接收方权限和消息号。处理结果按事项归集，普通回报走观察路径。实测一张无父子关系的目标卡确实收令，以及撤权后同样动作确实被拒。 |

现行目录已退役早期的宽授权治理场。试点复用职能身份和派驻机制，新增部分限定在一份计划的生命周期内。实现时优先核对职能授面、差事存储、事件分发与真实发令入口。[职能目录](../config/function_catalog.json) · [职能身份与授面](../src/api/function_room.py) · [差事存储](../src/storage/function_store.py) · [已落盘事件分发](../src/infra/policy_runner.py) · [卡间指令](../src/api/card_tools.py)

用户在计划卡上操作任命、暂停、恢复、撤回，能看到上次独立回看、下次最迟回看、当前待判断事项及已发指令。首次启用须有有效的最迟回看时间。每次实际介入绑定计划版本、目标卡和原指令回执，收件与执行结果分别显示。观察调用按事项合并，强弱模型均计入计划用量。

## 用重构验证

| 阶段 | 做什么 | 可以据此验收什么 |
|---|---|---|
| 一，历史回放 | 固定 `work_073` 的只读副本，按当时发生顺序回放。选无卡身份、多线拒绝、Harness 定时读源以及一段正常开发；隐藏后来的纠偏结论，另留一段未参与编写标准的历史作对照。 | 能指出哪项承诺受损和当时可见的依据；正常进展不反复叫醒强模型；严重漏报能在独立回看暴露。 |
| 二，旁观当前重构 | 在试点 work 启用观察，记录“会不会叫醒、准备给谁下什么指令”。与实际外部监督判断对照，校准观察窗口和标准。 | 分别量出强弱模型调用次数、实际 token 用量、有价值的提前介入、误报、漏报及发现延迟。与同段历史的强模型逐批判断及仅到期回看比较。 |
| 三，有限范围实际发令 | 用户选定一个可回退的开发事项及责任卡，统筹亲自查证、发令、读回执行结果。其余事项继续旁观。 | 指令在目标卡有真实收件记录；失败或重启重试可继续核对，已落信不重复发。强模型能说明是否纠正了原问题。暂停或撤权后不再产生新的介入。 |

另设四个直接决定可用性的场景：全程零事件，到期仍唤醒；弱模型连续放过偏离，到期时间保持；同一事件被两个 runner 投递，只有一次有效提请和一次实际指令；运行中用户修改计划或撤回授权，旧回合的发令被拦住。成本与判断质量用回放实测共同决定是否扩大试用。
