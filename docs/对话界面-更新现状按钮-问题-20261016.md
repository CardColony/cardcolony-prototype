## 〇、现状流程（先把事实摆清）

**路 A · 输入条「更新现状」**（用户指的就是这条）
1. 点「更新现状」→ 弹窗「现状更新起草」，显示「起草中…」；
2. `POST …/draft {kind:"status"}` → **无工具纯文本调主模型起草**，返回 `{draft, base_hash}`（**不落盘**）；
3. 弹窗里草稿**只读**；底部三键：关闭 / 反馈 / 确认；
4. 「确认」→ `POST …/commit {kind,draft,base_hash,feedback_rounds}` → 后端 `base_hash` 乐观锁比对（不符→409 零改动）→ `update_card` **整块替换** `status_block` → 影子记一行迭代历史；
5. 「反馈」→ 展开反馈框 → 带意见**重新起草**；「关闭」/遮罩/× → 关弹窗、**不发请求**、草稿丢弃。

**路 B · 右栏「编辑现状 / 保存现状」**（并行一条）
「编辑现状」→ 内联文本框 → 「保存现状」→ `PATCH …/cards/{c} {status_block}`（**无 `base_hash` 裸写**）。

**依据**：`static/workspace.js`（`openDraft` / `_requestDraft` / `submitCommit` / `saveConclusion`）、
`static/stream.js`（`optimisticUser` 等无关，此路不涉及）、`src/api/card_draft.py`（`draft` / `commit`，`ALLOWED_KINDS=("requirements","status")`）、
`src/api/routes.py`（`/draft` / `/commit`）。

## 一、梳理方列的问题

### 1.1 流程问题（6 条）

1. **★ 起草期间切卡 → 确认写到别的卡上。**
   弹窗与草稿**不绑卡**、`currentCard` 是活的、`open()` 不关弹窗 ⇒ 在 A 起草、切到 B 点确认 →
   `POST …/cards/{**B**}/commit`；若 A、B 现状**都为空**（hash 相同），后端那道锁**拦不住**，
   真把 A 的草稿写进 B。（与用户已报的「串卡」同类病。）
2. **确认只能「整块接受 / 整块否决」。**
   草稿**只读**，改不了草稿一个字；模型起草差一点，只能「反馈」**再烧一次模型调用**。
3. **整块替换语义。**
   提示词明写「输出即为该块完整正文（整块替换语义）」，commit 也是整块覆盖。现状是**快照**，
   用户常只想补/改一点 —— 现在等于每次都用模型新写一份盖掉旧的，**易冲掉旧内容**。
4. **两条路改同一字段、保护不一致。**
   路 A 有 `base_hash` 乐观锁；路 B **裸写**无锁。同一字段两个写入口、两套保护，谁覆盖谁没约定。
5. **关闭 / 遮罩直接丢草稿、无二次确认。** 起草花了一次模型调用，误点即丢、不提示。
6. **按钮名「更新现状」但行为是「起草」。** 点一下＝一次模型调用，名实不符。

### 1.2 上下文相关（2 条）

7. **起草喂全量历史 + 又喂凝练记忆 ⇒ 内容重叠。**（**★ 用户已质疑，见第二部分 #7**）
8. **起草无工具、纯文本**，只能凭上下文写，不能去查。
