## 二、做了什么（逐条含根因）

### P1 · 选中态从 hash 迁到路径（根因修法）

2026-10-17「阶段2 A2.2」已把页面身份搬进路径（`/work/{wid}/card/{cid}`），
但**选中态仍留在 hash**。于是 `open()` 里：

```
select.set()            → 写 hash
history.replaceState()  → 写路径（把 hash 抹掉）
```

`select.get()` 读的就是 hash ⇒ 恒 null ⇒ 三处读点同时失准：
`row_model`（侧栏高亮）、`nav_system`（收起全部保留当前链／定位到当前卡）、
`nav_breadcrumb`（画布面包屑）。

**修法**：`state_layers.js` 的 `select` 层改为**路径优先、hash 兜底**；
`select.set()` 写路径；hash 仅保留作旧链接兼容（`select.parse()` 只认 hash，
`bootRestore` 用它判旧链接，**不能用 `select.get()`**——那会返回「当前页自己」
⇒ `location.replace` 把自己换掉 ⇒ 无限重定向）。
另把 `hashchange` 监听改为 `popstate`（选中态不再走 hash）。

**验证**：`navCurrent` 由 0 → 2（项目行＋卡片行均高亮）；URL 不再带 hash 噪音。

### P2 · 顶栏动作归位

- `canvasEntryBtn` 由**顶栏最左**移入**右侧动作区**（原位置紧贴侧栏右缘，
  视觉上像侧栏自己的控件；且与面包屑首段功能重复）。
- 两个「回画布」入口**行为统一**：都带 `?sel=<当前卡>`，回去后画布直接选中它。
- 草稿态（`WORK_ID==="draft"`）**隐藏该入口**——草稿项目没有画布可回，
  原来点了只跳回本页。落库后由 `ensurePersisted()` 放出来。

### P3 · 过程行溢出归零

`.step-detail` 的 `flex:1 0 100%`（basis＝行内容盒 766）＋ `margin-left:10px`
⇒ 外尺寸超行宽 ⇒ 整行横向溢出 10px、右边框被裁。
**margin 不计进 flex-basis，padding 计入**（全局 `box-sizing:border-box`），
故把缩进由 margin 改 padding：视觉缩进不变、溢出归零。
（`style.css` 与 `ui.css` 两条定义都要改——`ui.css` 的 `body.page-chat .step-detail`
优先级更高，是实际生效的那条。）

### P4 · 骨架兜底 ＋ 草稿项目落地引导

- `stream.js` 暴露 `EventFlow.markLoaded(wid, cid)`；`replayTrace` 改 `try/finally`
  （原来 `fetchTimeline` 抛错 ⇒ 骨架永久停留）。
- 两个草稿入口（`/work/draft`、新建卡）显式调 `markLoaded` ⇒ 骨架收起。
- 新建项目页补**项目落地引导**（图标＋标题＋说明＋3 个可点起始问法）；
  `applyEmptyState` 支持显式传视图键（草稿卡的画板键是 `new-N`，与
  `meta.card_id` 不同，否则空态会写到别人的画板上）。

### P5 · 工具结果不再空白

`renderResultContent` 原把**对象型字段整条丢弃**（`typeof d[k]==="object"` ⇒ continue）
⇒ `create_card` 这类「结果里只有 card 对象」的工具，点开**一片空白**，
用户以为点坏了。

**修法**：对象型字段改为给一段截断 JSON 摘要（2000 字上限；正文 `content`
字段仍**不截断**，保持 5702 的原口径）；实在没有可展示字段时明说
「（该结果没有可展示的字段）」。

### P6 · 通知面板 Esc 后可再打开

`theme.js` 的 Esc 处理器除了摘 class 还写了**内联** `style.display="none"`；
内联样式压过类规则，而打开处理器只加 class、不清内联样式
⇒ **按一次 Esc 之后通知面板再也打不开**。
**修法**：只摘 class（`.notify-panel` 默认态本就是 `display:none`）。

### P7 · 注释纠偏（模型名的数据源）

`renderAssistantNode` 旁的注释写「模型名从**节点顶层**取：落盘记录的 model 在顶层
（data 里没有）」——**说反了**。实测落盘记录的模型名在 **`data.model`**
（timeline 里 `assistant_text` 事件 `data.model = "deepseek-v4-pro"`），顶层没有 model 键；
是装配器的 `modelOf(rec, data)`（rec.model 优先、再 data.model）把它**算**到节点顶层的
`node.model` 上。照着原注释去改「顶层落盘形状」会改错地方。
**修法**：注释改准确，并点明老记录（2026-10-04/05 当时的调用方未传 model）与新记录的区别。

### P8 · 浅色主题下老令牌控件不自适应

对话页里仍有一批控件用的是 `style.css` 的**老令牌**（`--panel/--text/--dim/
--border/--bg…`）。老令牌在 `:root` 只有**一套深色值、没有浅色覆盖**——
浅色主题（`html[data-theme="light"] body.page-chat`）只重定义了 `--ui-*`。

后果：模型选择器 `.model-pill`（`--panel` 底 ＋ `--text` 字）在浅色界面里是
**近黑底白字的实心药丸**，一屏浅色里视觉权重最高，读起来像告警条而不是辅助控件
（实测截图）。

**修法**：在对话页作用域内把老令牌**映射**到新设计系统的对应值——

```css
html[data-theme="light"] body.page-chat {
  --bg: var(--ui-bg);  --bg-deep: var(--ui-surface-3);
  --panel: var(--ui-surface-1);  --panel-hover: var(--ui-surface-2);
  --border: var(--ui-line-2);
  --text: var(--ui-text);  --text-soft: var(--ui-text-2);  --dim: var(--ui-text-3);
}
```

一次修好**所有**还在用老令牌的对话页控件，而不是逐个打补丁。
**只作用于浅色主题**：深色下老令牌的观感已由既有样式调过，不动它（零回归）。

**验证**：pill 背景由深色改为 `rgb(255,255,255)`、字色 `rgb(20,23,28)`、
边框 `rgba(16,19,24,0.13)`，与输入卡／按钮同族。

## 二之二、第二轮的转向：**先写网，让网抓问题**（而不是按报的两类做网）

用户批评成立：「我列两条你就修两条」——说明排查不完整。**正确的解法不是再修两条，
是让网去抓。** 这一轮把网补成了三张：

| 网 | 位置 | 规模 | 覆盖 |
|---|---|---|---|
| 装配器既有网 | `tests/assembler.test.mjs` | 32 条 | 工具合体、思考归属、乐观上屏、revoke、幂等、畸形输入… |
| **run 作用域网（新）** | `tests/assembler_run_scope.test.mjs` | 11 条 | **归属的 run / round 作用域**（既有网全在同一个 run 里 ⇒ 这条分支**从来没被测过**） |

| **插话通道网（新）** | `tests/test_steer.py` | 7 条 | 置位／消费／清扫／轮槽插入／事件可见／事件内容覆盖 |

### 网抓出三个**同类**缺陷（一条根因，三处表现）

根因：**归属判据「不限 run、不限轮」**。装配器三处都犯：

| # | 缺陷 | 症状 | 修法 |
|---|---|---|---|
| ① | 思考**跨 run** 挂错消息 | 长链 run 的 **247 条 reasoning 全部挂到前一个 run（21:26）那条老消息下** ⇒ 刷新后那整段出现在更早的消息下面 | 思考**建自己的节点**，键＝`stream:{run}:{round}`（与 live 路径同一把键） |

### 终局修法：让 disk 与 live **同源**，而不是逐处打补丁

之前只改了「限 run」——**只堵了一半**（同 run 跨轮仍串，且工具配对也漏）。
真正的根子是：**disk 路径没有「每轮一个 assistant 节点」的概念，而 live 路径有**
（`stream:{run}:{round}`）⇒ 两条路径归组规则不同源 ⇒ 刷新前后必然不同。

于是把 disk 路径改成与 live 同构：

- **后端**：每轮落一条 `assistant_text` 事件（`round`＝**轮号**，正文可空）
  ⇒ disk 也有了「每轮一个 assistant 节点」；轮末那条**定稿**轮首那条（同节点）。
- **后端**：收口那条（`clean_text` 合并全文）**不再落事件**（会话块照落
  ⇒ **模型上下文零变化**；各轮正文早已在轮槽里，clean_text 的作用只是把它们
  补进会话文件供下一回合读——那部分完全保留）。
- **装配器**：思考建自己的节点、键与 live 相同；`tool_result` 配对限同 run。
- **插话落点修正**（网抓到的）：收口时的插话**直接进轮槽**——原来进 `steer_tail`，
  而 `steer_tail` 只在**工具轮**固化 ⇒ **无工具轮的插话永远丢失**。

### 契约变更（既有网同步更新，写明原因）

既有网两条用例锁的是**旧行为**：`reasoning 不带 model → pending，assistant 到达时吸收`、
`reasoning 永不丢 → 落兜底节点`。新契约下思考**直接建本轮节点**（思考-only 的一步），
不再走 pending。**两条已更新，并在用例注释里写明为什么变**（不是为了让测试变绿，
而是新行为确实更对：思考归本轮自己的节点，位置＝思考到达处＝工具之前）。

## 二之七、第七轮：把性能这条线**做完**（正文流节流 / 缓冲键带轮号 / 收口必落盘 / 下标索引）

## 二之九、第九轮：**快照机制**改造（不是加体积闸，是把机制改对）

用户批得对：「不是靠体积闸，这个快照机制就很愚蠢」⇒ 这轮治**机制**。

### 病根（用真实数据说）

**先看主实例快照库的真实账**（`D:\AI_station\推演agent_data_snapshots`，26 个 work，共 **49.8GB**）：

| work | 过程批次数 | 单份**可变状态** | 单份**只追加留痕** | 占盘 |
|---|---|---|---|---|
| work_025 | 198 | **59.2MB**（cards.db） | 114.2MB（events） | **29.58GB** |
| work_018 | 196 | 12.3MB | 92.3MB | **17.95GB** |
| 其余 24 个 | 3~186 | 0.3~4.6MB | 0~7.7MB | 合计 2.3GB |

⇒ **机制愚蠢在哪**：每次写操作都把**整个会话状态全量拷一份**，而其中绝大部分是
**只追加**的 events/sessions——它们**不会变旧**，快照拷它们等于**把同一份历史反复抄 200 遍**。

### 改后（`src/storage/data_snapshot.py`）

| # | 改法 | 效果 |
|---|---|---|
| 1 | **过程批次只拷「可变状态」**（cards.db 等）；只追加留痕交给**日备**（每天一份全量） | 单份 173.4MB → **59.2MB**（work_025）／104.6MB → **12.3MB**（work_018） |
| 2 | **指纹只按可变状态算** ⇒ 只追加留痕增长**不再触发新批次** | 写操作再多也不会刷副本 |
| 3 | 每批次写 `<stamp>.manifest.json`（**批次旁边**）：这批是什么、省略了哪些留痕、完整留痕在哪个日备 | 恢复路径可查（可恢复性的凭据） |
| 4 | 日备留存 30 → **7 天**（日备是全量，一份＝整个会话） | 7 份全量 ≈ 2.5GB（最重的 work） |

### 新的账（**全库 26 个 work**，不是挑一个）

| | 旧机制 | 新机制（同样份数） | 新机制＋体积闸兜底 |
|---|---|---|---|
| work_025 | 198 份 × 173.4MB = **33.5GB**（实占 29.58） | 198 份 × 59.2MB = **11.7GB** | 闸 2GB → **2GB** |

| 其余 24 个 | 2.3GB | **≈ 0.5GB** | ≈ 0.5GB |
| 日备（7 天） | — | ≈ 2GB | ≈ 2GB |
| **合计** | **49.8GB** | **≈ 16GB**（**3.1 倍**） | **≈ 7GB**（**7 倍**） |

> D 盘余量 **949GB**（总 1651.6GB / 已用 702.6GB）⇒ 新机制下**根本用不着靠限量求生**。
> 体积闸（`KEEP_BATCH_BYTES` 2GB/work + 全局清扫脚本）**保留但降级为兜底**——防呆，不是治本。

### 本轮**自己推翻自己**的四处（全部有实测/契约依据，不是嘴硬）

这一轮我在机制改造里塞了「**30 分钟最小间隔**」，跑全量后**打出 7 条新红**。查下来是我错了，连带挖出 3 个真缺陷：

| # | 我加的东西 | 为什么撤/改 | 证据 |
|---|---|---|---|
| 1 | **最小间隔 30 分钟**（删卡/恢复/收口强制拍） | **整条撤掉**。①它砍掉了产品里写明的既有契约：「清指纹 ⇒ 本次必须真拍」「上批失败 ⇒ 下次必须重试」——全量直接多 7 条红（`test_data_snapshot_lockresilience` 6 条 ＋ `test_snapshot_roundtrip` 1 条）；②它是**限量**不是治本（用户批的正是这个）；③它给全库挖了 **30 分钟盲窗**（改卡时段的改动没有任何恢复点）。 | 7 条新红 → 修回 0 |
| 2 | 指纹时间戳用**整秒**（`int(st_mtime)`） | 改**纳秒**（`st_mtime_ns`）。整秒精度下，**同一秒内的两次改动**（改卡→立刻再改）会被判成「没变」⇒ 快照被跳过 ⇒ **那一次改动没有任何恢复点**。实测踩中：同一秒写两遍 cards.db，第二份批次根本没产生。 | 新网 `test_no_min_interval_blind_window` |
| 3 | manifest 写进**批次目录里** | 挪到批次**旁边**（`<stamp>.manifest.json`）。批次目录的既有契约是「**只装运行数据**（顶层只有 `works/`）」，manifest 塞进去会破坏它，也会让 `list_snapshots` 把元数据算成数据。 | `test_snapshot_roundtrip` 的 `tops == {"works"}` |
| 4 | 恢复 = 「复制文件 + 删 `-wal`/`-shm`」 | 改成**走 SQLite backup API 回写内容**。删旁挂文件在 Windows 上**常常删不掉**（长活连接握着它 ⇒ WinError 32）；**删不掉的旧 WAL 会把旧数据复活**——文件已是快照内容，读出来却是旧值，而 `restore_from_snapshot` **返回 ok=True** ⇒ **静默失败**。这不是我引入的：机制改造前的版本单跑同样红在同一行（dev 的旧 junit 里也能看到同一条断言失败 ⇒ 这个洞在生产里是活的）。 | 新网 `test_restore_really_rolls_back_content`（单跑也红→现在绿） |
| 5 | 撤掉间隔后变成「**每次写都真拍**」 | **把「合并」挪回正确的层**：调度层（`schedule`）做合并窗口（默认 30 秒，trailing edge ⇒ 拍的是最后那次的态、**不丢恢复点**），API 层（`snapshot_sync`）保持「调用即执行」。实测：每次写都拍 ⇒ 全量从 157s 涨到 253s，并让有时限的用例（`test_coder_card::test_create_coder_card_builds_and_starts`「建卡即首跑 4 秒内产出」）**稳定打红**（两次全量失败集合完全一致 ⇒ 不是随机抖动，是我的改动造成的）。合并窗口在**调度层**⇒ 删卡/恢复/收口**当场拍**、不等窗口。 | 全量回到 **157s 量级**；那条 coder 卡恢复通过；新网两条钉死调度层语义 |

### 网 `tests/test_snapshot_mechanism.py`（6 → **12 条**）

分层（只拷可变状态）｜日备仍全量｜manifest 说清省略了什么（且在批次外）｜
只追加留痕变化**不**产生新批次｜状态变化产生新批次｜
**内容没变就不拍**（指纹去重）｜**清指纹必须真拍**（被间隔砍掉的契约）｜
**上批失败下次必重试**（被间隔砍掉的契约）｜**没有间隔盲窗**｜
**后台合并窗口：窗口内连续写不立刻拍**｜**删卡/恢复/收口当场拍不等窗口**｜
**恢复必须真回滚**（旧 WAL 不得复活旧数据）。

另外照旧跑了既有快照网（`test_data_snapshot_lockresilience` 6 条 ＋ `test_snapshot_roundtrip` 3 条 ＋ `test_disk_governance` 6 条）＝ **28 条全绿**。

   委派失败（实测：该执行体「桌面端登录态失效」）⇒ **回落系统路径** ⇒
   系统路径再发一条 `round_start`（`phase: main/tools`）⇒ **同一轮两条**。
2. **前端**：装配器的节点键是 `ns:seq:kind` ⇒ 每条 `round_start` 各自成一个节点；
   渲染层对**每条**都画一行「第 N 轮」⇒ 界面上就是**两行**。

### 改法（前端幂等 · `static/esm/assembler.js`）

给 `round_start` 一个 **`(run_id, round)` 稳定键**：同键**合流**（后到的更新数据、
**不新增节点**）⇒ 无论上游发几条、无论新旧历史数据，**界面一轮一行**。

- 没有 `run_id` 的老数据**不按轮合流**（否则不同 run 的同轮号会被吞成一条）。
- live 与 disk 两条同轮也合流（两套数据源同键）⇒ 与上一轮「disk/live 同构」同一处纪律。

`src/api/wb_exec/` 是**另一施工线今天新加的模块**（dev 上已前进 **230 笔**，
