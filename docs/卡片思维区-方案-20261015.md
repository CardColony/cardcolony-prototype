## 一、判据：什么才算「公共底座」

**一条判据**：**加一种卡类型，机制侧只需要动一处（类型注册表），其余自动跟上。**

拆成两句：

- **机制自动**：新类型**不需要**注册、**不需要**声明、**不需要**改代码；它在所有「按类型挂文本」的维度里天然存在（没写＝空）。
- **内容可选**：想给新类型写一段就写；不写就不注入、**不报错、不算"漏配"**。

**反面（v1 我犯的错）**：把 `project / sub_project / tool / coder / topic` 五个类型名写进配置文件。
那**就是硬编码类型清单**——本项目在 90 区注释里明令禁止：

> 「**必须从注册表读**：新增一种卡＝注册表加一项 ⇒ 本区自动多一行、零代码改动；
> 不得在代码里硬编码类型清单（否则扩展性失效）。」

⇒ v2 的全部改动，都是为了让这条判据成立。

## 二、设计

### 2.1 一个通用概念：**按卡类型挂的文本**（多维度）

- **键**＝卡类型 code（与 `card_type_registry.json` 的 `l1_vocabularies.*.types[].code` 同源）；
- **值**＝一段文本；
- 一份配置承载**多个"维度"**——一个维度＝「每类卡都要挂的一种文本」；
- **「卡片思维」只是第一个维度**（维度名 `thinking`）。

**配置文件 `config/type_texts.json`：**

```jsonc
{
  "_meta": {
    "version": "type-texts-v1",
    "purpose": "按卡类型挂的文本（多维度）；每个维度在区注册表里对应一个上下文区",
    "semantics": {
      "key": "卡类型 code——**以 card_type_registry.json 为唯一来源**；本文件不列全表、不校验、不预设",
      "value": "该类型该维度的正文；空串或条目缺失 ⇒ 该类型该维度不注入",
      "fail_open": "文件缺失 / 坏 JSON / 结构不对 ⇒ 视为全空，绝不阻断装配"
    },
    "write_path": "模型起草→用户确认（另立方案，本方案不含）"
  },
  "thinking": {
    "sub_project": "先想清边界与交付物再动手；别一边想一边改。"
  }
}
```

**关键**：`thinking` 下**只写"有字的类型"**——没有空键、没有全表。
⇒ **加一种卡，不用动这个文件。**

### 2.2 区：每个维度对应一个区

区注册表（`src/api/context_regions.py:REGION_TABLE`）加一项：

| 字段 | 值 |
|---|---|
| key | `type_thinking` |
| order | **95** —— 紧随 90「卡片职责」：90 讲"这类卡**干什么**"，95 讲"这类卡**怎么想**" |
| name | 卡片思维 |
| channel / delivery | `system` / `system` |
| profiles | `main` / `viewpoint` / `draft`（与 90 区同待遇） |
| source_owner | `assembler` |
| render | 取 `type_texts["thinking"][本卡 card_type]`；取不到 ⇒ 空串 |
| count | 有字＝1；无字则该区不出现 |

**渲染三条硬规矩：**

1. **只出当前卡那一类**的文本，**不并列别类**（子项目卡只读子项目卡那段）；
2. **没写字的类型 ⇒ 整个区不出现**（沿「没有来源就不出现这个区」）；
3. 正文**原样进**，不加工、不摘要、不截断（渲染零加工）。

**模型实际看到的**（当前卡＝子项目卡）：

```text
## 卡片职责
- 子项目卡（sub_project）：研发项目下一个相对独立的工作单元…
- 工具卡（tool）：被某个子项目卡调用、执行专项任务…

## 卡片思维
先想清边界与交付物再动手；别一边想一边改。
```

### 2.3 取数（一处 IO，落在 `build_ctx`）

`context_assembler.load_type_texts()` → `{维度: {类型: 文本}}`（**只保留非空字符串**），
放进 `RegionCtx.type_texts`；**渲染器保持纯函数**（既有纪律：本模块不做 IO）。

### 2.4 控制面

`config/context_regions.json` 加一行：

```json
"type_thinking": { "enabled": true, "order": 95 }
```

⇒ 可全局停用 / 调序（既有机制，零新代码）。

## 三、于是"加东西"全是加一行

| 你要加什么 | 动哪里 | 结果 |
|---|---|---|
| **加一种卡类型** | **只动类型注册表** | 90 区自动多一行；思维区没字 ⇒ 不出现。**不用碰 `type_texts.json`** |
| **给某类卡写/改思维** | `type_texts.json` 的 `thinking` 加/改一个键 | 下次请求自动生效（这是**内容**，不是机制） |
| **加一个维度**（以后每类卡要挂别的文本） | `type_texts.json` 加一个键 ＋ 区注册表加一行 | 新区自动生效，**代码零改** |
| **加一个区** | 区注册表加一行 | 既有机制 |

⇒ **"新增类型漏配"这个风险不存在**——它本来就不需要配。

## 五、写通道（模型起草＋用户确认）—— **另一件，本方案不含**

你已定维护方式＝**模型起草＋用户确认**。它与现有"起草卡片正文"**不是一回事**：

| | 现有起草/确认 | 本需求需要 |
|---|---|---|
| 粒度 | **按卡**（某张卡的某一块） | **按类型**（某类卡的某维度） |
| 落点 | 卡片正文列 | `config/type_texts.json` |
| 确认对象 | 那块正文 | 该类该维度那段文本 |

⇒ 需要**另开一条"按类型起草 → 你确认 → 写入该维度"的通道**（起草＝模型调用；**确认后才写文件**）。
**本方案只做「读＋注入」**；写通道单独出方案、单独做。
