# 卡间通信 · 现状完整梳理（2026-10-13）

> 目的：为「一起构建卡间通信机制」提供一份**代码级事实底册**。
> 口径：只写现状，不写建议；每条结论都给出文件:行号或可复现的现场证据。
> 阅读对象：用户（决策方）＋ 后续施工者。

---

## 〇、一句话结论

卡间通信**已有一条完整的「发信 → 投递 → 调起收件方 → 自动回发」闭环**，四段全部落地并有单测；
但这条闭环**从未在真实模型下端到端跑通过**——真实档案里只有「只发不收」的遗留（952 封无应答），
且存在一处**几乎必然在真实 API 上失败的角色字段隐患**（见 §十三·R1）。
机制当前**只能由流程代码触发**（模型工具面已摘除），**没有任何 UI/HTTP 入口能主动发一封信**。

## 三、消息格式（线格式）

**头行**（正文第一行，`card_msg.build_header`）：
```
[[card-msg id=<msg_id> type=<type_code> from=<from_card> reply_to=<msg_id|空>]]
```
- `msg_id` ＝ `{from_card}-{uuid4().hex[:8]}`（`make_msg_id`，总长 17）
- 语法约束：只匹配**首行**；键＝小写 ASCII 下划线；值＝`[A-Za-z0-9_\-:.]+`；必需键 `id/type/from`；重复键/裸 token/中文值 → 解析失败返 `None`（**不抛异常**）
- **落盘形态**：整封信作为一块存入收件方档案，`actor=f"card:{from_card}"`、`from=<from_card>`、`behavior=""`（→ 进对话投影＋进模型视野）、`end=""`（不闭合轮）
- 正文＝头行 ＋ `\n` ＋ 内容（`card_tools.py:1167`）

真实落盘样本（`works/work_001/sessions/session_003.md:9-20`）：
```
---MSG---
seq: 0
actor: card:card_002
from: card_002
turn: 0
pair: unknown
pair_id: unknown
ts: 2026-10-11T00:52:16.832737+08:00
---
[[card-msg id=card_002-7ad82adf type=msg_ask from=card_002 reply_to=]]
数字是多少？
---END---
```

## 四、类型注册表（`config/message_type_registry.json`）

**当前恰三个类型**，把互动方向穷尽：

| code | display | reply_expected | reply_type | 语义 |
|---|---|---|---|---|
| `msg_ask` | 询问 | **true** | `msg_answer` | 需要对方信息/判断才能继续，等回话；**不许沉默** |
| `msg_answer` | 应答 | false | `""` | 回应询问（`reply_to` 必填），是「下文」不是新话题 |
| `msg_notify` | 通知 | false | `""` | 告知，不需回话，不构成待办 |

**「加类型＝加条目零代码」如何成立**：
- 读取全部**现读**（`load_registry` 每次读文件，热加载）→ 消费方零类型字面量
- 发信校验用 `card_msg.type_codes()`（现读）；激励文用 `display_of`/`when_to_use_of`/`note`（现读）
- 缺 `when_to_use/reply_expected/reply_type` 时 fail-open 到缺省值（不抛）

## 五、发送链路（六道门槛，`_h_send_card_message`）

按顺序，**一条不减**：

| # | 门槛 | 失败返回 |
|---|---|---|
| ① | 收件卡存在（`target_id in cards`） | `not_found` |
| ② | 不得给自己发 | `invalid` |
| ③ | 类型在册（`type_codes()` 现读） | `invalid`（文案列合法值） |
| ④ | `reply_to` 与类型一致：`msg_answer` 必填；其余不得带 | `invalid` |
| ⑤ | 正文非空 | `invalid` |
| ⑥ | 权限：`policy.check(..., SWITCH_READ)` ＋ **显式** `_is_in_subtree` 双向判定 | `denied` |

**权限口径（关键，含一处与设计册的偏差修正）**：
- `policy.check` 的树作用域**只对 TREE_SWITCHES（edit/delete/link/unlink/create_child）生效，`read` 不在其中**——照册字面只传 `read` 会退化成纯类型判权、子树限定失效。
- 故实现**显式补** `_is_in_subtree`：判据从「收件方必须在发件方子树内」**放宽为「两卡同一棵任务树内」（双向各查一次）**——父子/祖先链可互发；**兄弟、跨树挡死**。
- **推论：跨 work（跨树）发信在现有通道下被彻底挡死**——`cards` 表本就是单 work 的（`card_store.iter_card_metas(work_id)`），`target_id` 根本不在表内。

**落信后的三个副作用**（成功才发生，错误全走 err 信封不落档）：
1. `session_facade.append` 落块到**收件方**档案
2. `session_ops.ops_log("card_msg_send", …)` 留痕
3. `card_msg.TRIGGERS.setdefault((work_id, target_id), []).append(msg_id)` 记**调起意图**（进程内）
4. `event_stream.emit(work_id, target_id, "card_message", …)` 在**收件方键**上发通知帧（前端角标）

## 六、投递与调起链路（K3，`schedule_card_message_triggers`）

**触发点**：`routes.py:912`——**A 的回合收口时**（`_run_message_inner` 段⑥之后）。

流程：
1. 取走 `card_msg.TRIGGERS` 全部登记项（**读完即清**，不累积）
2. 逐 target 用 `card_msg.find_pending(blocks)` 判 pending（**零新增存储，从档案推导**）
   - `find_pending`：从尾向前扫，最后一条 `actor` 以 `card:` 开头的块之后**没有 assistant 块** → 该块即 pending
3. 有 pending → 记尾批 `snapshot_ids`（回发边界）→ 动态构造激励文 → `asyncio.create_task(_routes._run_message(..., append_user=False))` **非阻塞**起收件方回合
4. `_watch_pending` 协程 await 该任务：返回 dict（成功）→ 触发 `_auto_reply_pending_letters`；409 → `card_msg_pending`；502/404/423 → `card_msg_answer_failed`

**两层分工（写死）**：
- **快速通道**：`create_task`（可能因进程退出丢失）
- **持久保证**：档案里的信是持久的——丢任务不丢信；`schedule` 被**每个回合收口调用**，天然承担补齐

**激励文**（`_CARD_MSG_PROMPT` ＋ 动态构造）：
> 「上一轮之后，卡 card_002（《标题》）给你发来一条消息（类型：询问）。{注册表 note} 见上文以 card: 开头的条目，请阅读这些消息并处理。」

**关键约束**：激励文**只走当轮 user_prompt，绝不落收件方档案**（`append_user=False`；`routes.py:861-868`）。

## 七、自动回发链路（S4，`_auto_reply_pending_letters`）

**触发**：收件方回合**成功结束**后（判据＝`_run_message` 返回 dict，即 finish 响应体）。

流程：
1. 读档案取**最后一块**，双条件：`actor==assistant` 且 `end==model_done`（防竞态：**绝不遍历找更早的 model_done 块**，否则人停回合会转发旧话）
2. 从尾向前扫到上一条 assistant 为止，收集全部 `card:` 块（含越 human 块）→ 过滤 `id ∈ snapshot_ids`（回合期间新到信不回发）＋ `reply_expected_of(type)`
3. 逐封：`reply_type` 空串 → `reply_type_missing` 不发；正文空 → `no_content` 不发；否则经 `send_card_message` 落信（**六道门槛一条不减**）
4. 打点 `card_msg_answer_sent` / `card_msg_answer_failed`；**全程不抛出**

**被停（human_stop/policy_stop）/出错/被顶（竞态）回合一律不回发。**

## 八、收件方如何「看见」消息（上下文投影）

- `routes.py:837` 读 `prior`（全部块）→ `message_runner.build_context` 投影为 `[{"role": m["role"], "content": m["content"]}]`
- **只过滤 `behavior` 非空的块**（留痕块不进投影）；card: 块 `behavior=""` → **保留**
- card: 块的 `role` ＝ `actor` ＝ **`card:card_002`**（`session_facade.py:511` 映射：`{"human":"user","assistant":"assistant"}.get(actor, actor)`）
- **⚠ 这就是隐患**：`prior_messages` 被原样 extend 进 `messages` 送 API（`gateway.py:112-115`），role 值 `card:card_002` **不是 OpenAI 合法角色**（见 §十三·R1）
- BASE_PROMPT 有专节「卡间消息处理」（`prompts.py:102-104`）：告知模型「系统会负责把应答发回，你不需要也不能使用发信工具」

## 十一、消息生命周期（状态机）

```
[A 回合收口]
    │  send_card_message（六道门槛）
    ▼
落信到 B 档案（actor=card:A，behavior=""，end=""）
    │  TRIGGERS 登记 + SSE card_message 帧
    ▼
[A 回合收口 段⑥ → schedule]
    │  find_pending(B) == 该信？
    ▼
create_task 起 B 回合（激励文，append_user=False）
    │  ├─ B 忙 409 → ops card_msg_pending（信仍在，下轮收口补齐）
    │  └─ 成功 → B 产出 assistant 块（end=model_done）
    ▼
[watch] → _auto_reply_pending_letters
    │  reply_expected 且 reply_type 非空
    ▼
回信落到 A 档案（msg_answer，reply_to=原 id）
    ▼
find_pending(B) == None（B 已有 assistant 块）→ 该信「已消费」
```

**唯一「已处理」判据＝`find_pending`**（档案推导，无独立状态存储）。

## 十二、约束与边界（硬边界清单）

1. **模型不可发信**——工具面已摘除，模型只能「产内容」，发送由流程代码完成
2. **同一棵树内才能发**——父子/祖先链可互发；**兄弟、跨树、跨 work 全挡死**
3. **发信无 UI/HTTP 入口**——`send_card_message` 目前只被 S4 自动回发调用（全仓仅一处消费点 `message_runner.py:1062`）
4. **调起只在「回合收口」发生**——无独立调度器；无回合收口则信滞留（靠下次任一回合收口补齐）
5. **TRIGGERS 是进程内内存**——重启丢失；但档案是持久保证，靠 pending 推导补齐
6. **无重发去重**——同一内容可无限次发（952 条即实例）
7. **不做持久化「已读/未读」**——pending 推导 ＋ 前端 localStorage 两处口径合成
8. **`card_msg.py` 禁 IO 副作用**（除 `load_registry` 读表）

## 十三、已知缺口与风险（**构建机制前必读**）

### R1【高危·未验证】收件方角色字段 `card:card_XXX` 送真实 API 几乎必然失败
- **事实**：card: 块的 `role` ＝ `card:card_002`；`build_context` 只过滤 behavior，**不归一 role**；`gateway.py:113-114` 把 `prior_messages` **原样** `messages.extend(...)` 送 litellm。
- **旁证**：`grep -l "card:card_" logs/prompt_*.json` **零命中**——即真实环境**从未**有一个回合把 card: 块带进 prior 送过模型（收件方从未被真实调起）。
- **后果**：一旦真实调起收件方，role 非法 → 端点 400 → 收件方回合失败 → 自动回发链断。
- **待办**：真实 key 下实测一次；若无归一逻辑，需在投影处把 `card:` 块 role 归一为 `user`（内容已自带 `card:` 标识与头行，语义不丢）。

### R2【机制级】接收端闭环从未端到端跑通
- 所有 K3/S4 测试均 `monkeypatch.setattr(model_service, "call_main", fake)`（mock）。
- 真实档案 `work_001/session_003.md`：**952 个 card: 块、0 个 assistant 块**——只发不收。
- **待办**：真实模型下端到端实弹一次（A 发 → B 被调起 → B 应答 → A 收到回信）。

### R3【能力级】无「状态到达即自动推送」的触发源
- 现唯一触发＝**回合收口**。用户构想中的「卡到状态时自动推送」（如卡完成需求/方案/任务书时推送）**没有现成挂钩**。
- 相关事实：`方案链/任务书链` 工具卡（`works/toolcard_scripts/`）是产出方案/任务书的现成流程，其收口点是可用的挂载候选。

### R4【一致性】`card_message` 事件不在本体论 `EVENT_TYPES` 内
- `event_stream.py:91-98` 的 EVENT_TYPES 列表**不含** `card_message`，但 `card_tools.py:1181` 直接 emit 它。
- 且 `tests/test_token_stream_isolation.py::test_event_ontology_is_19_types` 当前为**红**（本体论计数漂移）。

### R5【性能】通知端点每卡读整档
- `session_facade.read` 的 `from_seq` 是**后置过滤**（io 层总读整档），`card-messages` 端点遍历**全部卡**读整档。卡多档大时是热点。

### R6【产品级】发信无任何入口
- 模型不可发、UI 不可发、HTTP 不可发——**目前只有系统自动回发在发信**。
- 「用户/流程主动发起一次卡间通信」这一最基本动作**缺失**。
