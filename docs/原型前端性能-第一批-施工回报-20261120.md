### 3. 消除首屏回底带来的同步布局

**病根：宿主读写的是错的元素。**

真正的滚动容器是视图里的 `.flow-view-scroll`（`overflow-y:auto`）；
宿主（`workspace.scrollChatBottom` / `stream.activate`）读写的是 `#chatArea`
（`.chat`，`overflow:hidden`）⇒ 它**根本不能滚**：
- 「写 scrollTop」是 no-op；
- 「读 scrollHeight」却**照样强制一次整棵画板的排版**。

⇒ 后果两个：① 首屏路径上多一次强制布局；② **「切回恢复滚动位置」一直是 no-op**
（存进去的是 `#chatArea` 的 0，取出来还是 0）—— 热切回对话跳回顶部。

| 改动 | 位置 |
|---|---|
| 滚动位置**只由对话视图持有** | `static/esm/flow/chat-view.js` 新增 `getScrollTop()` / `restoreScrollTop()`；`static/stream.js` `activate()` 改为存取视图；`static/workspace.js` `scrollChatBottom()` 改为向视图发令 |
| 同批 DOM 更新合成一次 | `chat-view.js` `render()`：全部先进 `DocumentFragment`（不在文档流 ⇒ 追加不碰活树），再**一次**插回；序没变时一次搬动都不做 |
| 每批只做一次滚动校正 | 读布局（scrollHeight）与写位置各一次，收在视图内 |

### 3.1 K3 为什么会坏、怎么修的

真正的滚动容器是视图里的 `.flow-view-scroll`；宿主（`workspace.scrollChatBottom` /
`stream.activate`）读写的是 `#chatArea`（`.chat`，`overflow:hidden`）⇒
**它根本不能滚**：写 scrollTop 是 no-op，读 scrollHeight 却**照样强制一次整棵画板的排版**。
⇒ 「切回恢复滚动位置」**一直是 no-op**（存的是 `#chatArea` 的 0，取的还是 0）。

⇒ 现在**滚动位置只由对话视图持有**（`chat-view.getScrollTop()` / `restoreScrollTop()`），
宿主只发号令。顺带把首屏那次「对着画框读高度」的强制布局也去掉了。

### 3.2 K4 是本批**修掉的真缺陷**（不是本批引入）

打开一条失效的旧链接（`/work/work_073/card/card___nope__`）：
原来**地址栏纹丝不动**⇒ 停在这个错地址，刷新还是它。

两个原因叠在一起：
1. `open()` 自己把取卡失败**吃掉了**（有 catch）⇒ `bootRestore` 里那段回滚**永远等不到**；
2. `open()` 的 catch 只回滚了**左栏选中态**，没碰地址栏。

⇒ 现在 `open()` 的 catch 也回滚路径。★ **回滚目标不能直接取路径**：冷开时路径里
**就是**这张打不开的卡 ⇒ 「上一张卡」＝ 它自己 ⇒ 拿它回滚等于把同一个坏地址写回去
（我第一版就踩了这个坑，实测地址栏纹丝不动）。判据改成「上一张**确实不同**才用它，
否则退到项目根」。

## 8.1 返工 ①：右栏会串到另一个 work

**复现**（用户口径）：work A 的 card_007 详情延迟返回 → 切到 work B 的 card_007 →
A 的正文覆盖了 B 的当前卡。

**根因**：卡号**只在项目内唯一** ⇒ 「A 的 card_007」与「B 的 card_007」同号。
而 `ensureCardFull` 的归属守卫只比 `card_id`：

```js
if (currentCard && (currentCard.meta || {}).card_id === cid) currentCard = full;
```

⇒ A 的详情晚到时，「当前卡的 card_id 也是 card_007」⇒ **A 的正文被写进 B 的当前卡**，
右栏接着渲染它。

**修法**：
1. 请求发起时**冻结** `(work_id, card_id)`（不取后来的 `WORK_ID`）；
2. 落地前校验「**当前工作仍是 wid** 且 **当前卡仍是 cid**」；
3. 在途条目按 `wid|cid` 分键 ⇒ 不同项目的同号卡不共用一条请求；
4. `renderInspector` 渲染前再核一次当前选择（补读正文是异步的，期间可能已切走）。

**证据**（`tests/chat_work_isolation.test.mjs`，Chrome 实测）：

| | 修前 | 修后 |
|---|---|---|
| 通过数 | **4/9** | **9/9** |
| W1b 右栏含 A 的正文 | **true**（A 的正文盖住了 B） | false |
| W1c 右栏显示的是 B 的正文 | **false**（右栏长 139227 字符，全是 A 的） | true（B 的指纹在） |

修前那次的右栏正文长度 **139227**（A 的大正文），修后 **5382**（B 的）⇒ 串卡确凿。

## 8.2 返工 ②：共享 GET 的三个时序缺口

## 8.3 返工 ③：开卡失败只回滚了地址

**复现**（用户口径）：跨 work 取卡失败 ⇒ 地址回到原卡，但 `WORK_ID`、对话画板、
输入框仍绑在失败目标。

**根因**：失败分支只做了「路径 ＋ 左栏选中态」的回滚；
而 `open()` 在发请求**之前**就已经把 `WORK_ID` 换成失败目标、`bindBoard()` 切了画板、
`switchComposer()` 换了输入框 ⇒ 界面停在失败目标，地址却在原卡 ⇒ 不一致，
且在原卡上**没法继续输入**。

**修法**：
1. 记「**上一次成功打开**的卡」（`_lastGood`）——失败的那次绝不能成为回滚目标；
2. 失败时**整套**退回去：项目上下文 ＋ 画板 ＋ 输入框 ＋ 选中态 ＋ 地址栏 ＋ 徽标；
3. 回滚目标**不能用路径里的上一张**：冷开时路径里就是这张失败卡自己 ⇒
   拿它回滚＝把同一个坏地址写回去（第一版就踩了这个，实测地址栏纹丝不动）。

**证据**（同 `chat_work_isolation.test.mjs`）：
