阅读本任务书和本仓 AGENTS.md。按一至五顺序推进，先让单个临时 work 走通任务一的界面与持久化。每段回执写明“已实现的用户动作、改变的文件、可复跑命令、实际输出、未验证项”；完成一段即可继续下一段。用模拟模型验证机械行为，用真实模型验证判断质量。只能做一段时请报告完成到哪一段，勿用“已完成统筹功能”概括局部结果。

## 第一版要交到用户手里的功能

用户打开一张已有的普通计划卡，点击「任命统筹」，选择一张非根职能卡、强弱模型、可观察的范围与可发令的目标，填入目标和首次最迟回看时间。统筹首次醒来拟定计划。此后用户在同一张卡上看到计划、版本、上次实际核查、下次最迟回看、为什么唤醒、向谁发过什么指令、对方是否收件及结果。用户可编辑、点名唤醒、暂停、恢复和撤回。没有任命的 work 沿用原行为。

一个计划同时只有一位强模型统筹。它负责计划、依据现有需求判偏、跨卡协调和发令。产品经理与技术总监提供专项判断。弱模型只观察。需求未改而实现有偏差，统筹当轮即可指挥修正；已有方案确实需要改变用户承诺时，把影响和待选项显示给用户。用户正在聊天、父卡愿不愿转发以及子卡是否主动汇报，都不是统筹工作的前提。

### 用户从哪里打开

- **从 work 进入。** 在[画布顶栏](../templates/work.html)现有「项目动态」旁增加可见的「项目统筹」按钮。点击打开本 work 的计划列表。首次使用时列表显示「任命统筹」，点击后选择承载计划的普通卡、职能与授权；项目已有计划时，点击计划名直接进入那张卡的「统筹计划」区域。列表只用于导航。为它提供只读的 `GET /works/{work_id}/coordination`（沿用现有 API 前缀），返回本 work 已任命的计划卡、名称、负责人和状态。打开列表、刷新和浏览历史均不唤醒模型。
- **从卡进入。** 在[卡详情](../templates/card.html)的右侧「卡详情」面板提供「统筹计划」入口，由[工作区详情渲染](../static/workspace.js)接入。未任命的普通卡可直接点「任命统筹」，预选当前卡；已任命的卡打开同一份计划，可编辑计划、立即唤醒、暂停、恢复或撤回。两条路径共用同一任命表单与计划数据。
- **UI 验收。** 用浏览器从一个没有计划的临时 work 开始，全程点击完成任命；刷新后从画布找回原计划，再从计划卡详情暂停并返回画布，列表应显示「已暂停」。另开一个 work，应只看到它自己的计划。提交浏览器操作记录或截图和对应回读结果；仅调用 API 成功不能判 UI 通过。

## 任务一　让用户能任命并管理一份计划

1. 在计划卡面增加独立的「统筹计划」区域。归属键用 `work_id + plan_card_id`；一张计划卡一份当前计划。当前内容与历史版本可回读。计划正文不占用卡的需求文档、现状或原目标。用户和在任统筹是计划编辑者。保存时提交读入版本，版本冲突时返回最新版本并要求重读，不能以旧全文覆盖。
2. 计划包含用户目标、需求引用、责任卡、依赖、下一项可验证结果、强模型写给弱模型的唤醒标准、要直接叫醒强模型的节点。每项工作保留稳定标识，改标题不换标识。计划卡面是计划的唯一编辑入口；差事记录引用计划卡与版本。调度器持有下一次回看时间，卡面直接读取该值。
3. 任命绑定在任职能、专属场会话、可观察卡范围、可发令目标、两条模型路由、运行模式、首次回看时间。观察范围可选整个 work，包括后来加入的卡；发令范围分别支持显式目标集合、或用户明确授予的本 work 全部开发卡。模型工具拿不到任命、调权和切换实发模式的权限。缺少模型配置、到期时间或合法负责人时，界面直接指出缺项。
4. 用户状态操作为任命、暂停、恢复、撤回、结束。任命后活跃；暂停保留计划和证据但停模型与新指令；恢复重新核算欠办回看；撤回终止本任命，重新任命产生新任命标识。结束保留历史。上述操作和用户改目标须使旧执行令牌失效。运行模式分「旁观」和「实发」，默认旁观，切为实发由用户在计划卡操作。
5. 在已有 API 路由前缀下增加 `/works/{work_id}/cards/{plan_card_id}/coordination`。GET 返回当前计划、版本、授权摘要、状态、到期、待办及行动回执，尚无任命时返回空面板；POST 的 `op` 为 `appoint/pause/resume/revoke/finish/wake/set_mode/set_grant`；PATCH 提交 `expected_rev` 与完整的新计划。任命以外的变更带当前任命标识和读入版本。版本过期返回 409，越权返回 403，参数错误使用仓内已有校验响应。UI 通过这些正式入口操作。运行中的强模型只通过受限工具提交计划和行动，不能代调用户控制接口。

## 任务二　让两种模型拿到不同的材料

**强模型首次起轮**由用户任命触发，即使还没有观察标准也能开工。执行锚为计划卡，身份为所任职能，使用计划专属会话。输入包括用户目标、需求原句与版本、已有任务和授权，全程使用所选强模型路由。输出一份可执行计划和唤醒标准。以后的回合先给当前版本、上次决定及待验结果、本次原因、按事项合并的变化和证据指针。它可以列举有权观察的全部卡，包括从未发过消息的卡，再按卡回读进展、原文和授权证据。普通卡对话、PM 日常回合、其他评审席位各自沿原上下文。

**弱模型**只接收计划版本、当前观察标准、关联需求原句、这批变化和宿主给出的可读证据片段。由宿主使用显式弱模型路由发起一次无工具调用。记录实际路由与用量。子卡文本始终按引用材料装入，正文里的“修改标准”“给某卡下令”没有控制效力。

下例为弱模型输出协议，字段名按此实现。宿主提供事件引用，核对返回引用属于输入及授权范围。弱模型可以提请标准之外的风险。非法 JSON、引用不存在、模型不可用都记为「未判断」，保留该批待处理；同一故障不即时循环重试，也不推进最迟回看。到期或用户点名仍能直接唤醒强模型。

```json
{
  "decision": "wake",
  "item_id": "participant-access",
  "reason": "公共协议将卡号设为必填，无卡参与者可能无法接入",
  "evidence_refs": ["event:work_demo:card_017:42"],
  "question": "这个必填字段会不会挡住已承诺的无卡接入？"
}
```

`decision` 只接受 `wake` 或 `pass`。通过观察时仍保留理由供抽查。缺少已有事项可用 `item_id: null` 报新风险。弱模型的输出不直接产生发令、改计划、改期限或改状态的效果。

## 任务三　接事件、合并变化、保证到期回看

| 输入 | 应产生的行为 |
|---|---|
| 用户点名、首次任命、计划已登记的关键节点达成 | 直接排强模型；点名和节点不能被弱模型否决。节点用明确事项、来源卡、实际事件类型及可核对的值表达。 |
| 计划所涉卡的需求变更、归属或依赖变化、阶段结果、证据变化 | 正式事件源先接 `card_block_edited`、`goal/change`、`msg_directive`、`worker_done`、`review_batch_closed`；读取实际载荷后归到事项。`msg_report` 仅在含关联事项的新证据时进入这一批。新发现的授权范围内风险可用来源卡作临时分组。新代码事实必须有产物引用或在回看中查到。 |
| 重复进度、模型逐字流、普通工具逐跳、统筹自己的记账事件 | 同一事实不重复送模型；回执若证明了新的工作结果，按对应事项进入观察。记录过滤原因，避免统筹自己唤醒自己。 |
| 活跃计划的最迟回看时间到达 | 宿主无须等事件就排强模型。强模型忙时保留独立回看原因，当前回合实际完成回看或紧接着再起一轮。额度不足、模型故障、服务停机导致逾期时保留原到期值，界面标欠办；恢复后认领一次。 |

各 runner 可采集本地已落盘的事件，以来源坐标去重并持久化待办。初次启用从记录下的启用水位开始，回放另走历史副本。进程故障后从已提交水位补读。一个事项从第一条变化起开始合并，合并窗口用试点显式配置；后续变化不能无限延后首批判断。同一计划同时最多一个有效强模型回合。计时与派发由单进程或 runner-0 调度，实际回合转计划卡属主；截止时间用有时区的绝对时间持久化。测试注入可推进的时钟，无需真实等待。

只有独立回看收口才更新上次回看。收口必须记录实际核查的需求引用、证据读取或读取失败的回执、结论或尚缺事项、下一次绝对时间。普通处理回执、弱模型 `pass`、子卡全部变绿都不能冲销欠办。用户改目标可以要求更早回看。

**验收**　同一事件经过两个 runner 并重复投递，只进一批。连续变化持续超过合并窗口，仍有首批观察。无事件、连续放过、旧回合忙、跨进程重启、模型失败恢复五种场景均能用假时钟证明到期任务未丢失。

## 任务四　让统筹能判断、问专家和真正介入

**先按这个顺序做决定。** 强模型先读需求与原件。已能判定就直接处理；若缺产品解释，问 PM；若缺实现判断，问 CTO。两问独立可并行。任职者恰是 PM 时在本回合完成产品判断，不给自己再开一个 PM 差事。专业答复回到原事项，只有统筹修改施工计划并发令。QA 独立执行验收，结果可为失败。

| 谁 | 接收的输入 | 必须给出的结果 |
|---|---|---|
| PM | 一个待回答问题、需求版本及来源、受影响的真实用户场景 | 原有承诺、可观察的验收例、仍需用户取舍的分歧。 |
| CTO | 一个技术问题、对应承诺、现有代码或契约位置 | 当前生产路径、实现建议、涉及的责任域、能证伪建议的验证方法。 |
| QA | 明确被验对象、验收条款和产物 | 实际运行或读取了什么，哪些通过、失败、未验证，附原始证据。 |

在计划差事内新增受限的“问专业问题”动作，只启动指定职能的一次只读回合，绑定问题、计划版本和证据引用，答复落回事项。普通 PM 执笔语义和 CTO 现有评审语义保持。独立验收沿用正式 QA 差事；由有权针对对象派 QA 的责任卡派驻，统筹保存差事引用。没有答复、差事被拒、职责书缺失都显示原状态，不能生成模拟专家答复。

**发令契约。** 发令绑定任命标识、计划版本、事项、目标、指令正文、验收判据和宿主分配的行动标识。旁观模式只记“拟向谁发什么”。实发模式在真正写入目标之前重验任命有效、版本、目标范围、角色授面及通信线。普通开发卡为目标；用户属于人工操作入口；职能卡走专业差事。可按该次授权通过现有建线入口建立所需通信线；原生建线不被允许时回报拒因。委托的跨支线能力只在这个已授权的差事中生效，普通卡的 `direct` 权限保持。源消息记录计划卡执行身份及所任职能，接收方可追溯，不能借根卡或用户身份发送。

**先解决落信幂等，再启用实发。** 复用 `direct` 的权限、落信及属主唤醒路径，在底层正式落信口补可选的宿主行动键，已有调用方照旧。目标属主以同一行动键原子记录唯一收件和稳定消息号，重复请求返回原号；随机生成新号再搜相似正文不足以判重。撤权和落信须有确定先后，落信前的有效性复核与唯一收件须在同一 work 的原子写入边界内完成。若当前落信助手不能参加该事务，先抽取其共用事务写入步骤，保留会话块、事件及消息头的原语义，再接协调入口。落信已成功而唤醒失败，只补唤醒。界面区分「拟发、待投、已落信、已唤醒、已取得执行证据、被拒」。普通汇报不单独唤醒统筹，不取消其他卡本来的回执义务。

行动键由宿主在第一次对外提交前持久化，由任命标识、决策标识、该决策的行动序号确定。转发、超时查询和补唤醒使用原键。用户撤权后可以读回已落信回执，不再投递新的效果。弱模型的 `pass` 只能消费它读入的那批变化，旧版本的弱模型答复不能清掉新版待办。强模型若同轮既改计划又发令，先成功保存计划，用保存所得的新版本再提交该行动。每次提交宿主从本 work 的任命记录重读权限，模型输出或 HTTP 正文自报的身份和工具清单不能提升权限。

## 任务五　验证并交付

先在临时 work 用固定模型结果验证权限、调度和落信，再在只读固定副本验证模型判断质量。复制 SQLite 时用一致快照，同时固定事件和将供回放的证据文件及版本；按当时可见顺序喂入。时间点之后的纠偏话术、当前卡面、后来改过的源码不能倒灌。无法还原当时证据的案例标资料不足。调用会取走待注入内容的 `build_ctx` 只能作用于副本。代码测试、模型回放、旁观试点、真实介入四类证据分别标注。
