## ② 热生效实弹（保存即热生效，不重启）

**做法**：在**运行中的服务端进程**里，把 `draft` 绑定由 `haiku` 改为 `glm-flash` →
`PUT /api/settings/models` → 不重启 → 经该进程 gateway 真发一次调用。

**证据**：
```
PUT reloaded=True  backup=models_20261012_185900.yaml
PID 不变        9204 == 9204          ← 进程没重启
gateway 单例已换  1747507927440 != 1747508384848
resolve('draft') haiku → glm-flash     ← 进程内同源读已切换
真调用 seat=glm-flash  model_used=glm-5.3-flash  reply='收到'
```

**通过标准**：改绑定 → 保存 → 不重启 → 真发调用走新配置。四项全部逐条命中：
进程 PID 未变、单例已换、`resolve()` 读到新绑定、真调用确实由新模型应答。

> 这条是「先建后换」语义的关键取证：`id(gw)` 变了说明 `reload_gateway()` 换掉了单例引用，
> 而 PID 不变说明确实没重启；在跑调用持旧对象跑完、新调用拿新对象。

```
  [models_20261012_185911.yaml] 一致: True

```

**通过标准**：头部 1-13 行（拆闸铁律）逐字未变。达成 —— 经历 **9 次保存**后 sha256 仍全等。

> **首轮判 FAIL 是一处判据错误，不是缺陷**：原判据用
> `git diff config/models.yaml` 找头部增删行，但 git HEAD 里**还没有**这个头部
> （头部是第一步收拢时才建的），于是把**第一步的正常新增**误报成第二步的损坏。
> 改判据为「逐份保存产物之间比对头部 sha256」，结论：10 份文件全等，逐字未变。
>
> 头部全文（前 13 行拆闸铁律本体）已逐行留存，见 `_backups/models_20261012_184843.yaml`。
