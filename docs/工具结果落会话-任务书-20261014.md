## 0. 一句话规格

**工具调用（assistant）与工具结果（tool）作为一对消息块，落进会话，成为对话的一部分。**

由此：
- 它们同时进入 ① 模型上下文（本轮＋跨轮）② 未凝练内容 ③ 未凝练计量（算进 80 万 token 触发线）；
- **凝练时剔除工具块**，只送 user/assistant 给凝练模型（与原来一致）；
- 触发线的**窗口按含工具块的完整窗口**计算；
- **销账（mark 推进）带工具块一起销**。

一句话：**窗口边界与计量按含工具算；喂给凝练的内容不含工具。**

## 0.1 补充裁定（v1.1 · 2026-10-14 11:33，执行方 5 问的答复）· **原样保留**

> 前三条是 v1 漏写（我的责任），现定死；后两条须用户拍。

### 疑问 1 · 块 A（带 tool_calls 的 assistant 块）会误闭合轮 → **采 (a) 机械规则**

事实：`session_facade.append` 对 `actor=assistant` 且未显式给 `end` 的块，自动补 `end="model_done"`。块 A 正是 `actor=assistant`、`content=""` ⇒ 一落盘就把本轮闭合 ⇒ 块 B 被算进下一 turn，工具块与用户不在同一 turn。

**裁定**：`append` 的 `end` 自动补逻辑改为——

- `actor==assistant` **且块带 `tool_calls`** ⇒ **不补 `end`**（该块未闭合轮）；
- 其余照旧补 `model_done`。

**理由**：`end` 的语义是「轮末块」，而带 `tool_calls` 的块后面还跟着工具结果与后续轮次，**结构上就不是轮末**；`tool_calls` 是块上的结构化字段，据此判定是**机械判据、不是猜**。

**不采 (b)（显式传参）**：那要调用方记得传，正落「靠下游记得做对」的坑（项目明令反对）。

连带核对（须实测）：`_auto_reply_pending_letters` 取「最后一块且 actor=assistant 且 end=model_done」——块 A 无 end 后，仍应由最终回复块命中，回发行为不变。

### 疑问 2 · 块 A 会多发一条空 assistant_text 事件 → 堵住

**裁定**：`session_facade._block_event_type` 增加一条——

- `actor==assistant` 且带 `tool_calls` ⇒ 返回空串（不发事件）；
- `actor==tool` ⇒ 空串（§2.8 已定）。

**理由**：`content=""` 的事件是噪音；过程通道已有 `tool_call`/`tool_result`，不需要再来一条。

### 疑问 3 · 块 A 与块 B 的落盘原子性 → 收齐后一次性落

**裁定**：一个工具轮内，先把该轮的 A（带全部 tool_calls）与全部 B（工具结果）在内存收齐，然后一次性写进会话（A 在前、B 紧随）。

**理由**：N1（不得出现孤立 tool 块）是红线，孤立会致端点 400。原子落盘把该风险从"低概率"降到零。

与 §2.2「A 在前、B 紧随」的关系：那条讲的是文件里的顺序，不是写盘时机；一次性落仍满足顺序要求。

### 疑问 4 · 端点实测授权 → 用户 11:35 明确允许（实弹）

- 允许对真实端点发请求，跑一个含工具回合验证 `role=tool` 配对是否被接受。
- 要求：记录端点名 / 请求消息序原文 / 响应码 / 响应体；若被拒，如实记录并停手呈报，不得自行回退或绕过。
- 报告须明确区分「实弹证据」与「离线/mock 证据」，不得混写。

> ⚠️ **v2 注**：该授权发于 10-14，**是否仍然有效请用户确认**（v2 施工前重问）。

### 疑问 5 · 计量口径里 tool_calls 的参数算不算 → **计入**（按建议落，可推翻）

v1 原任务书写「不计入」；v1.1 改为「计入」。理由：`write_file` 这类工具的参数可能很大，不计入会漏算——80 万线算小、凝练触发偏晚，线就不准了。

实现要求：`memory_store._msg_meter_tokens` 改为——

- 基础＝`content` 的长度（照旧）；
- 若该块带 `tool_calls`，再把每个调用的 `arguments` 长度计入。

`_truncate_window` 与 `_meter_sum` 共用该函数 ⇒ 自动跟随，无需另改。

> ⚠️ **本条为口径变更：v2 施工前须用户重确认**。若认为「只算工具结果、不算调用参数」，一句话即可改回。

### 疑问 6 · 自发现：凝练输入会把「空 content 的 assistant 块」也塞进去（v1 漏写）

事实：§2.5 写的是「凝练输入只收 `actor ∈ {human, assistant}`」。但块 A 正是 `actor=assistant`、`content=""` ⇒ 它会被收进凝练 prompt，产出空的 `[块n]` 条目。

**裁定**：凝练输入在 §2.5 的筛选上再加一条——**排除 `content` 为空的块**（含带 `tool_calls` 的 assistant 块）。

**理由**：凝练是「把内容压成结论」；空内容块无内容可压，且空 `[块n]` 会干扰模型。这与用户口径「只塞 user 和 assistant 消息去凝练」一致——指的是**有内容**的 user/assistant 消息。

## 2. 规格

### 2.1 块格式（新增两个字段）

在 `BLOCK_FIELDS` 白名单内新增：

| 字段 | 用在 | 内容 |
|---|---|---|
| `tool_calls` | `actor=assistant` 的工具调用块 | 该轮工具调用的数组（`[{id, type, function:{name, arguments}}]`），与轮槽里构造的同源 |
| `tool_call_id` | `actor=tool` 的工具结果块 | 与上面对应调用的 id，一一配对 |

- **渲染**：`_render_v2_block` 增加这两字段的输出（JSON 串，单行，转义规则同 content）。
- **解析**：`_materialize_v2_block` 读回并保留；缺字段＝空（**存量会话零迁移**——旧块没有这两个字段，照旧解析）。
- 白名单外字段仍走既有 `unknown_field` 前向兼容通道（本任务把这两个字段**正式入白名单**，不走兼容通道）。

### 2.2 落点（工具交换成对落会话）

在 `message_runner` 工具执行处（现 `slot.append_tool_result` 同一位置，`:806`），除入轮槽外，**另落两个会话块**：

- **块 A**（`actor=assistant`）：`content=""`，`tool_calls=[该轮全部调用]`
- **块 B**（`actor=tool`）：`tool_call_id=<对应 id>`，`content=<工具结果全文>`

- 一个工具轮有 N 个调用 → **1 个块 A**（含 N 个 tool_calls）＋ **N 个块 B**。
- **顺序：块 A 在前、块 B 紧随**（配对不破）。
- `content` 取值走同一投影函数 `card_tools.render_tool_result`（**禁止另拼**）。
- `turn`/`pair` 与所在回合一致；`behavior=""`。
- 块 A 的 `content` 取空串——中间正文维持现状（由 `analysis_parts` 进最终回复），不重复搬运。理由：`message_runner` 的 T14 拼接（分析在前、回复在后）属消息层拼装，**不在本任务范围**。

### 2.3 工具块与"环节留痕块"的区分

两者都用 `actor=tool`：

| | `behavior` | 进投影？ |
|---|---|---|
| 工具结果块（本任务新增） | 空串 | **进**（模型要看） |
| 环节留痕块（triage/plan/step/final/revision） | 非空 | 不进（既有过滤） |

现过滤条件 `if not m.get("behavior")` 恰好满足此区分——但须在代码注释中**写死这条区分**，防后人误改。

### 2.4 历史投影放行（**v2 落点已改**）

投影**已不在 `message_runner`**，而在 `context_regions.project_history_messages()`（`:354`）。改为：

- `actor=assistant` 且带 `tool_calls` → 投影出 `{"role":"assistant","content":…,"tool_calls":[…]}`
- `actor=tool` → 投影出 `{"role":"tool","tool_call_id":…,"content":…}`
- 其余不变（含 `reasoning_content` 保留、卡间块换头）

**硬约束**：`role=tool` 必须**紧跟其配对的 assistant(tool_calls)**、且 `tool_call_id` 与之一致——否则端点 400。故 §2.2 的成对落盘与顺序是**前提，不是可选项**。

**v2 新增连带（v1 漏写）——日志 `regions` 会跟着变**：
`context_regions.build_log_regions` 的 `history` 条目（`json.dumps(history_messages)` 的字节与指纹）会因放行 tool 块而变。⇒ 验收须**把改前/改后的 regions 字节与指纹记下来**（审计凭据不得静默分叉）。

**v2 新增连带——`prior_key` 边界**：
10-15 起，prior 槽由两个区共用一份 payload：`history`(300) 与 `tool_turn`(900)，**谁匹配 `prior_key` 谁出、另一个让位**（防历史发两遍）。工具块进会话后：

- round1：`prior_key="history"` ⇒ 出的是**含工具块的历史投影**；
- round≥2：`prior_key="tool_turn"` ⇒ 出的是**整条轮槽 wire**（也含工具块）。

⇒ 两处都要**实测"工具块只出现一次"**，不得因两个区并存而重复。

### 2.5 凝练（两处，方向相反）

- **计量含工具**：`pending = prior[mark:]` 天然含工具块；`_meter_sum(pending)` 天然把工具块算进 80 万触发线——不改（口径＝按块 content 计；**tool_calls 参数是否计入见 §0.1 疑问 5 ⚠️ 待重确认**）。
- **窗口切片**：`_truncate_window` 仍按含工具块的完整 pending 切——不改（用户口径：窗口按带工具的窗口算）。
- **凝练输入剔除工具**：`_build_condense_user_prompt(window)` 改为只收 `actor ∈ {human, assistant}` 的块，且**排除 `content` 为空的块**（§0.1 疑问 6）。
  - 边界：若某窗口筛完为空（整窗都是工具块）→ **不发凝练调用**，按既有失败哲学处理（留痕、mark 不动、不阻断），不得送空 prompt 给模型。

### 2.6 销账

`target_mark = window[-1].seq + 1` 不改——窗口含工具块，故销账天然"带工具结果一起销"。本任务只需在代码注释写明该语义。

### 2.7 前端（**v2 整节重写**）

**v1 写的落点已作废**：`static/workspace.js` 的 `renderChat`（读 `GET /session`）**已退役**——`static/stream.js:6` 原话：「消息渲染通道（workspace.renderChat）已退役」。现在显示走 **`GET /timeline` → `static/esm/assembler.js` 装配器 → 节点快照 → 渲染**。

⇒ **本任务前端侧从"要改"降为"确认不重复"**：

- 工具调用/结果的**显示**由**事件通道**（`tool_call` / `tool_result` 事件）承载，装配器已认；
- 本任务新增的是**会话块**（喂模型的），**不是**显示源；
- 须核对：**同一次工具调用不会在界面上出现两遍**（事件行 ＋ 会话块行）。
- 若实测发现装配器**也**读会话块（`/session`）→ **停手回报**，届时再定渲染方案。

### 2.8 事件流

工具块**不额外发新事件类型**——过程通道已有 `tool_call`/`tool_result` 事件，再发一遍是双份噪音。`session_facade._block_event_type` 对 `actor=tool` 保持返回空串（不落事件）；对**带 `tool_calls` 的 assistant 块**新增返回空串（§0.1 疑问 2）。

4. **存量会话**：旧块无新字段，解析为零迁移；但新旧混排的卡（旧块无工具记录 ＋ 新块有）须抽样验证。
5. **mark 语义**：块数因工具块增多，mark 的数值含义随之变化；**语义不变**（＝块序号），但**数值不可跨版本比较**，写明。
6. **（v2 新增）日志 regions**：见 §2.4——字节/指纹会变，须留改前改后对照。
7. **（v2 新增）`prior_key` 双区**：见 §2.4——须实测工具块不重复。
8. **（v2 新增）显示双份风险**：见 §2.7——事件通道与会话块不得在界面上重复。

## 4. 验收（严格版）

**全绿只是最低门槛，不是验收。** 每条须有可复现证据；无证据＝未通过。

### 4.1 证据规则

1. 每条判据附证据：测试名＋断言原文／日志摘录／改前改后 diff／实测数字。
2. 报告须给**改动前后对照**，不许只写"已通过"。
3. **未覆盖项必须显式列出**；用"全绿"掩盖未覆盖＝报告不合格。
4. 任一判据失败 → **停手如实报告**，不得"绕过去让它绿"。

### 4.2 正向判据

| # | 判据 | 证据要求 |
|---|---|---|
| V1 | 一次含工具的回合结束后，会话文件里出现成对的 `assistant(tool_calls)` ＋ `tool(tool_call_id)` 块 | 打印该卡会话的块序列 |
| V2 | 工具块进了模型上下文（下一轮 prior_messages 含它们） | prompt 日志摘录：跨轮后仍见上一轮工具块 |
| V3 | 工具块算进触发线计量 | `_meter_sum(pending)` 含工具块的实测数字（改前 vs 改后） |
