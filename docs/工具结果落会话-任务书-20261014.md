## 0. 一句话规格

**工具调用（assistant）与工具结果（tool）作为一对消息块，落进会话，成为对话的一部分。**

由此：
- 它们同时进入 ① 模型上下文（本轮＋跨轮）② 未凝练内容 ③ 未凝练计量（算进 80 万 token 触发线）；
- **凝练时剔除工具块**，只送 user/assistant 给凝练模型（与原来一致）；
- 触发线的**窗口按含工具块的完整窗口**计算；
- **销账（mark 推进）带工具块一起销**。

一句话：**窗口边界与计量按含工具算；喂给凝练的内容不含工具。**

## 0.1 补充裁定（v1.1 · 2026-10-14 11:33，执行方 5 问的答复）

> 前三条是**本任务书漏写**（我的责任），现定死；后两条须用户拍。

### 疑问 1 · 块 A（带 tool_calls 的 assistant 块）会误闭合轮 → **采 (a) 机械规则**

事实：`session_facade.append` 对 `actor=assistant` 且未显式给 `end` 的块，自动补 `end="model_done"`（`session_facade.py:515-516`）。块 A 正是 `actor=assistant`、`content=""` ⇒ 一落盘就把本轮闭合 ⇒ 块 B 被算进下一 turn，工具块与用户不在同一 turn，违反 §2.2。

**裁定**：`append` 的 `end` 自动补逻辑改为——

- `actor==assistant` **且块带 `tool_calls`** ⇒ **不补 `end`**（该块未闭合轮）；
- 其余照旧补 `model_done`。

**理由**：`end` 的语义是「轮末块」，而带 `tool_calls` 的块后面还跟着工具结果与后续轮次，**结构上就不是轮末**；`tool_calls` 是块上的结构化字段，据此判定是**机械判据、不是猜**。

**不采 (b)（显式传参）**：那要调用方记得传，正落「靠下游记得做对」的坑（项目明令反对）。

**连带核对（须实测）**：`_auto_reply_pending_letters` 取「最后一块且 `actor=assistant` 且 `end=model_done`」——块 A 无 `end` 后，仍应由最终回复块命中，回发行为不变。

### 疑问 2 · 块 A 会多发一条空 `assistant_text` 事件 → **堵住**

**裁定**：`session_facade._block_event_type` 增加一条——

- `actor==assistant` **且带 `tool_calls`** ⇒ 返回空串（**不发事件**）；
- `actor==tool` ⇒ 空串（§2.8 已定）。

**理由**：`content=""` 的事件是噪音；过程通道已有 `tool_call`/`tool_result`，不需要再来一条。

### 疑问 3 · 块 A 与块 B 的落盘原子性 → **收齐后一次性落**

**裁定**：一个工具轮内，**先把该轮的 A（带全部 `tool_calls`）与全部 B（工具结果）在内存收齐**，然后**一次性写进会话**（A 在前、B 紧随）。

**理由**：N1（不得出现孤立 `tool` 块）是红线，孤立会致端点 400（R1 同类）。原子落盘把该风险**从"低概率"降到零**。

**与 §2.2「A 在前、B 紧随」的关系**：那条讲的是**文件里的顺序**，不是**写盘时机**；一次性落仍满足顺序要求。

### 疑问 4 · 端点实测授权 → **用户 11:35 明确允许（实弹）**

- 允许对真实端点发请求，跑一个**含工具回合**验证 `role=tool` 配对是否被接受。
- 要求：记录**端点名 / 请求消息序原文 / 响应码 / 响应体**；若被拒，**如实记录并停手呈报**，不得自行回退或绕过。
- 报告须明确区分「实弹证据」与「离线/mock 证据」，不得混写。

### 疑问 5 · 计量口径里 `tool_calls` 的参数算不算 → **计入**（按建议落，**可推翻**）

原任务书写「不计入」；**现改为「计入」**。理由：`write_file` 这类工具的**参数可能很大**，不计入会**漏算**——80 万线算小、凝练触发偏晚，线就不准了。

**实现要求**：`memory_store._msg_meter_tokens` 改为——

- 基础＝`content` 的长度（照旧）；
- **若该块带 `tool_calls`，再把每个调用的 `arguments` 长度计入**。

`_truncate_window` 与 `_meter_sum` 共用该函数 ⇒ 自动跟随，无需另改。

> ⚠️ 本条为口径变更：若用户认为「只算工具结果、不算调用参数」，一句话即可改回。

### 疑问 6 · 自发现：凝练输入会把「空 content 的 assistant 块」也塞进去（**本任务书漏写**）

事实：§2.5 写的是「凝练输入只收 `actor ∈ {human, assistant}`」。但块 A 正是 `actor=assistant`、`content=""` ⇒ 它会被收进凝练 prompt，产出**空的 `[块n]` 条目**（`_build_condense_user_prompt` 只拼 content）。

**裁定**：凝练输入在 §2.5 的筛选上**再加一条**——**排除 `content` 为空的块**（含带 `tool_calls` 的 assistant 块）。

**理由**：凝练是「把内容压成结论」；空内容块无内容可压，且空 `[块n]` 会干扰模型。这与用户口径「只塞 user 和 assistant 消息去凝练」一致——指的是**有内容的** user/assistant 消息。

## 2. 规格

### 2.1 块格式（新增两个字段）

在 `BLOCK_FIELDS` 白名单内**新增**：

| 字段 | 用在 | 内容 |
|---|---|---|
| `tool_calls` | `actor=assistant` 的工具调用块 | 该轮工具调用的数组（`[{id, type, function:{name, arguments}}]`），与轮槽里构造的同源 |
| `tool_call_id` | `actor=tool` 的工具结果块 | 与上面对应调用的 id，一一配对 |

- **渲染**：`_render_v2_block` 增加这两字段的输出（JSON 串，单行，转义规则同 `content`）。
- **解析**：`_materialize_v2_block` 读回并保留；缺字段＝空（**存量会话零迁移**——旧块没有这两个字段，照旧解析）。
- 白名单外字段仍走既有 `unknown_field` 前向兼容通道（本任务把这两个字段**正式入白名单**，不走兼容通道）。

### 2.2 落点（工具交换成对落会话）

在 `message_runner` 工具执行处（现 `slot.append_tool_result` 同一位置），**除入轮槽外，另落两个会话块**：

```
块 A（actor=assistant）：content=""，tool_calls=[该轮全部调用]
块 B（actor=tool）    ：tool_call_id=<对应 id>，content=<工具结果全文>
```

- 一个工具轮有 N 个调用 → 1 个块 A（含 N 个 tool_calls）＋ N 个块 B。
- 顺序：块 A 在前、块 B 紧随（配对不破）。
- `content` 取值走**同一投影函数** `card_tools.render_tool_result`（禁止另拼）。
- `turn`/`pair` 与所在回合一致；`behavior=""`。

**块 A 的 `content` 取空串**——中间正文维持现状（由 `analysis_parts` 进最终回复），**不重复搬运**。理由：`message_runner` 的 T14 拼接（分析在前、回复在后）属**消息层拼装**，不在本任务范围（用户 10-14 已明确）；本任务只做"工具交换落会话"。

### 2.3 工具块与"环节留痕块"的区分

两者都用 `actor=tool`：

| | behavior | 进投影？ |
|---|---|---|
| 工具结果块（本任务新增） | **空串** | **进**（模型要看） |
| 环节留痕块（triage/plan/step/final/revision） | **非空** | 不进（既有过滤） |

现过滤条件 `if not m.get("behavior")` **恰好**满足此区分——但须在代码注释中**写死**这条区分，防后人误改。

### 2.4 历史投影放行

`build_context` 的投影（现只取 role/content 两键）改为：

- `actor=assistant` 且带 `tool_calls` → 投影出 `{"role":"assistant","content":…,"tool_calls":[…]}`；
- `actor=tool` → 投影出 `{"role":"tool","tool_call_id":…,"content":…}`；
- 其余不变。

**硬约束**：`role=tool` 必须**紧跟**其配对的 `assistant(tool_calls)`、且 `tool_call_id` 与之一致——否则端点 400（R1 同类故障）。故 2.2 的成对落盘与顺序是**前提**，不是可选项。

### 2.5 凝练（两处，方向相反）

- **计量含工具**：`pending = prior[mark:]` 天然含工具块；`_meter_sum(pending)` 天然把工具块算进 80 万触发线——**不改**（口径＝按块 `content` 计；工具调用块的 `tool_calls` 参数**不计入**，写明为已知口径）。
- **窗口切片**：`_truncate_window` 仍按**含工具块的完整 pending** 切——**不改**（用户口径：窗口按带工具的窗口算）。
- **凝练输入剔除工具**：`_build_condense_user_prompt(window)` 改为**只收 `actor ∈ {human, assistant}` 的块**——与原来一致（原来窗口里本就没有工具块）。
  - 边界：若某窗口**筛完为空**（整窗都是工具块）→ **不发凝练调用**，按既有失败哲学处理（留痕、mark 不动、不阻断），不得送空 prompt 给模型。

### 2.6 销账

`target_mark = window[-1].seq + 1` **不改**——窗口含工具块，故销账天然"带工具结果一起销"。本任务只需在代码注释写明该语义。

### 2.7 前端

`workspace.js` 的会话渲染（`renderChat`，源＝`GET /session`）要认识新块：

- `actor=assistant` 带 `tool_calls`：渲染为工具调用（显示工具名与参数摘要）；
- `actor=tool`：渲染为工具结果（**全量**，与"对齐其他 agent"一致；长内容可折叠，但**内容必须可得**）。

**注意**：前端另有一处过程行渲染（`stream.js` 的 `tool_call`/`tool_result` 事件）——那是**事件通道**，与本任务的**会话块**是两路。本任务只加会话块的渲染，不改事件行。

### 2.8 事件流

工具块**不额外发新事件类型**——过程通道已有 `tool_call`/`tool_result` 事件，再发一遍是双份噪音。`session_facade._block_event_type` 对 `actor=tool` 保持返回空串（不落事件）。

## 3. 连带面与风险（必须如实报告）

1. **上下文体积**：工具结果全文进历史后，每轮重送 → 上下文显著变大（实测单条工具结果可达 10,904 字）。这正是 80 万触发线存在的理由；但**首次触发前的这段会变大**，须实测报告量级。
2. **`tool_fold`（轮折叠）**：`TOOL_FOLD_ENABLED` 缺省关。工具结果进会话后，该机制的作用面变了——**本任务不动它**，但要报告"它现在会折什么"。
3. **三席**：三席 prior 取 `prior_for_gateway[:history_len]`，历史含工具块后会变；三席另有 `tool_full_texts` 注入 → **须核对是否重复**，如实报告。
4. **存量会话**：旧块无新字段，解析为零迁移；但**新旧混排**的卡（旧块无工具记录 + 新块有）须抽样验证。
5. **`mark` 语义**：块数因工具块增多，mark 的数值含义随之变化；语义不变（＝块序号），但**数值不可跨版本比较**，写明。
