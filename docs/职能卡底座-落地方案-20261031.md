# 职能卡底座 · 落地方案（2026-10-31）

> 定位：本线是「职能卡」的系统化重做。依据＝用户裁定串（职能卡是自由卡型，
> 以职能视角参与工作；可管理、可评审、可直接干活；**哪里需要去哪里**；
> 流程岗＝工作流节点自动派岗）＋与评审线的《开工前回执》《职能卡线回执》。
>
> **边界（写死，防越界）**：什么时候叫它＝他线（harness 策略、deploy 动作、
> 事件投递、回合调度）。叫来的是什么、它进场拿什么身份/权限/职责书、
> 它的账记在哪＝**本线**。
>
> `RunState` 四锚已就绪（他线）：执行锚 `card_id`、身份锚 `act_as`、
> 上下文锚 `ctx_card`、授面 `tool_allow`＋`prior_extra`。本线不碰
> message_runner，只供这四个锚的取值来源。

## 〇、一句话

**差事（deployment）是一等对象**：职能每次被派出去都落一行——谁派的、
什么场、什么活、发了什么钥匙、干完没有。人格装配与授面解析是它的
`act_as` 供给侧；台账是它唯一的持久记忆（会话只是草稿）。

## 一、数据模型：`function_deployments`

### 1.1 DDL（照 `function_ledgers` 同法：写路径惰性建表，读路径不跑 DDL）

```sql
CREATE TABLE IF NOT EXISTS function_deployments (
    id           TEXT PRIMARY KEY,
    work_id      TEXT NOT NULL,
    function_id  TEXT NOT NULL,
    venue_kind   TEXT NOT NULL,            -- review|consult|deploy|govern
    venue_ref    TEXT NOT NULL,            -- 场锚点：评审卡id / 发起卡id / 目标卡id / work
    batch_id     TEXT DEFAULT '',          -- 评审差事绑批次
    mandate      TEXT NOT NULL,            -- 渲染后的差事正文（不是模板引用）
    delegator    TEXT NOT NULL,            -- user | card_id | policy:<rule_id>
    tools        TEXT DEFAULT '[]',        -- 本差事实发工具名单（∩天花板∩能力）
    exit_kind    TEXT DEFAULT '',          -- verdict|answer|acceptance|revoked|manual
    status       TEXT NOT NULL DEFAULT 'active',  -- active|done|withdrawn|escalated
    result_ref   TEXT DEFAULT '',          -- 产物落点指针（票/答案/交付物）
    meta         TEXT DEFAULT '{}',
    created_at   TEXT NOT NULL,
    activated_at TEXT DEFAULT '',
    closed_at    TEXT DEFAULT ''
)
CREATE INDEX idx_fn_deploy_fn    ON function_deployments(work_id, function_id, status);
CREATE INDEX idx_fn_deploy_venue ON function_deployments(work_id, venue_ref, status);
```

### 1.2 幂等

`(work_id, function_id, venue_kind, venue_ref, batch_id)` **active 唯一**：
create 时已有 active 记录 ⇒ 返回现有行，不建第二条。
（harness 补种/规则重放不会双开差事——这是 deploy 动作幂等的兜底。）

### 1.3 状态机与关账

```
active ─→ done        退出判据满足（exit_kind 判）
      ─→ withdrawn    派遣方/系统撤回
      ─→ escalated    差事上交（伴随 divergence 落账，指针回总裁）
```

关账三通道（多通道冗余，任一命中即关）：

| 通道 | 机制 | 覆盖 |
|---|---|---|
| 惰性核对 | read 时按 `venue_kind` 的 exit checker 校验，满足即视作 done | 评审（verdict 行存在⇒done）、会诊（答案送达⇒done）——**面渲染永远显示真相，不依赖任何写** |
| 事件关账 | `msg_sync`/`done` 等事件驱动的规则（harness 配 action，或本线订阅点） | 会诊等事件可判的场 |
| 显式 close | delegator / 系统调 `close()` | 治理授权收回、人工干预 |

### 1.4 venue_kind 语义表

| kind | venue（执行锚 card_id） | 上下文锚 ctx_card | exit_kind | 授面 |
|---|---|---|---|---|
| review | 伴生评审卡 | 被评目标卡（＋现场 prior） | verdict（表态即完） | 读件+approve+reject+write_ledger |
| consult | **发起卡**（答案原地落发起方会话） | 发起卡 | answer（答案送回） | 读件+write_ledger |
| deploy | 目标卡 | 目标卡 | acceptance（判据满足） | 按 mandate 给编辑件 |
| govern | work 域 | 管辖域 | revoked（授权收回） | 管理件（direct/curate_face 等） |

> 「会话不回流」是锚点天然的：回合落在 venue 的执行锚上 ⇒ 工作内容
> 进 venue 会话，不进职能自己桌面。桌面只装用户对话与它自己的回合。

### 1.5 CRUD（function_store 新增）

```python
create_deployment(work_id, fn, venue_kind, venue_ref, *,
                  batch_id="", mandate, delegator, tools=None,
                  exit_kind="manual", meta=None) -> dict   # 幂等(1.2)
activate(work_id, dep_id) -> None                        # activated_at
close(work_id, dep_id, *, status="done", result_ref="") -> bool
get(work_id, dep_id) -> dict | None
active_for_function(work_id, fn) -> list[dict]           # 惰性核对后仍 active
active_for_venue(work_id, venue_ref) -> list[dict]
history(work_id, fn, *, limit=8) -> list[dict]           # closed 倒序
has_prior(work_id, fn, venue_ref, venue_kinds) -> bool   # 「作者不评自己」判据
```

惰性核对＝`exit_checkers` 注册表：`{venue_kind: fn(work_id, dep)->bool}`。
`active_for_*` / `history` 出口先跑一遍 checker，满足的懒关账后再返回。

## 二、人格装配 `identity_for`（act_as/act_meta 供给侧）

```python
identity_for(work_id, fn_id, venue_kind) -> dict
# 返回 RunState.act_meta 形状（与评审线现合成件同构）：
# {"function_id","function_name","catalog_code","charter":{"text":...}}
```

**职责书取值链**：目录 `charters[venue_kind]` → 目录 `charter`（默认日常职责）→
`review_charters.json` 兼容层（按卡实例→按目录 code，评审线现有链）→ ""。

- 目录条目新增 `charters` map（按场型存职责书）；`charter` 字段保留＝default
  （向后兼容：没配 charters 的条目行为逐字不变）。
- **同一职能在不同场穿不同职责书**：评审场穿评审职责，派驻场穿作业职责，
  会诊场穿顾问职责——这是「职能视角」能换场合活的根。

## 三、授面解析 `grant_for`（tool_allow 供给侧）

```python
grant_for(work_id, fn_id, venue_kind) -> list[str]
# = venue_grants[venue_kind]（条目级→_meta 默认表）
#   ∩ toolface.allow（目录天花板）∩ abilities 展开（能力闸，下游还会再窄一次）
# 产出即 RunState.tool_allow 的取值。
```

`_meta.venue_grants` 默认表：

```json
{"review":  ["read_card","read_archive","read_linked","read_file","list_files",
             "search_files","read_shadow","approve","reject","write_ledger"],
 "consult": ["read_card","read_linked","read_file","list_files","search_files",
             "write_ledger"],
 "deploy":  [],      // 不预置——delegator 按 mandate 明给
 "govern":  []}      // 不预置——按授权书
```

条目级 `venue_grants` 可覆盖默认（如 observer kind 的涌现守门，评审场授面里
就没有 approve/reject——它不是评委）。

## 四、台账硬规矩（卡面权威化第一落地）

1. **目录 ledgers 条目加 `required_meta`**：`{"key":"要求说明"}`。
   `_h_write_ledger` 校验——缺 key ⇒ `err("validation")` 拒收，文案指明补什么。
   前提台账：`{"source":"用户明示|物理约束|推定待确认"}`——没来源的前提
   不许落账（work_025 事故的机械闸）。
2. **`function_ledger` 事件 data 加 `superseded`**（`_h_write_ledger` 已发事件，
   补一个字段）——本线只负责把「哪条被取代了」发出去，传导给谁是他线的 inject。
3. **引用约定**：`台账code#条目id`（如 `premises#a1b2c3d4e5f6`）——先做文本
   约定（台账正文与面渲染可解析），结构化引用后做。
4. **作者不评自己**：`open_review` 挑 members 时，`has_prior(fn, target,
   ["deploy","author"])` 为真的职能**降为答辩人**——不进投票席，记进
   批次 meta `author` 供展示（它到场解释，不投 approve/reject）。

## 五、职能卡面两块新账

`summary()` 认两个新 face_blocks 名（目录 face_blocks 补进去）：

- **在派任务**：惰性核对后仍 active 的差事 → `场 / 差事(120字) / 谁派的 / 何时`
- **参与记录**：最近 8 条 closed → `status / 场 / 关账时间`

面从「身份+台账」升级为「身份+权威+在役+轨迹」——它此刻被派在哪、
去过哪，脸上一眼看完。

## 六、目录 v12（`config/function_catalog.json`，纯配置）

## 七、接入点（本线负责的建差事点，共三个）

1. **`open_review`**（card_tools，回执已指配）：`open_batch` 后对每个 member
   `deployments.create(venue_kind="review", venue=rid, batch_id, mandate=模板渲染,
   delegator=caller, tools=grant_for(fn,"review"), exit_kind="verdict")`；
   members 过滤按 §四-4 排除作者。
2. **会诊**：`_h_scene_direct` 目标是职能卡 ⇒ `create(venue_kind="consult",
   venue=caller, mandate=问题正文, delegator=caller, exit_kind="answer")`；
   回合以 `card_id=caller + act_as=fn + ctx_card=caller` 跑——
   **答案原地落发起方会话**，fn 桌面零污染。
3. **harness `deploy` 动作（他线）**：调 `deployments.create`——
   本线只保证这个入口存在且幂等，动作本体是他们的事。

## 十二、明确不做

- 不做 harness 侧一切（deploy 动作、策略规则、事件投递、回合调度）
- 不接工作流规则（QA 自动验收/PM 初稿的策略配置是组织上线时的事，
  本线只保证 `create` 入口在）
- 不做差事排队/并发闸——**单例瓶颈**留开放问题（见下）
- 不建派驻/治理场型的实际消费（venue_kind 位与授面表位留好，第二个
  用户是会诊；派驻等会诊验证后再接）
- 不做结构化引用（`premises#id` 先文本约定）

## 十三、风险与开放问题

1. **单例瓶颈**：全项目一个 PM，三张卡同时要初稿 ⇒ 差事排队。
   机器上各场上下文本就隔离（venue 会话互不污染），并行差事没有
   技术障碍——「场场并行、台账串行」。但要不要限流留给上线观察，
   本轮不造闸。
2. **会诊关账的判定**：`exit_kind=answer` 靠「fn→caller 的 msg_sync/答复」
   判——边缘情形（它答了但没 sync 回去）靠惰性核对之外的显式 close 兜底；
   mandate 文本里写死「答完必须 sync 回发问方」。
3. **死字段**：watch/speak_contract/scope 仍在目录与 profile 里（无消费者），
   清的时候只停播种不删列，动之前先知会评审线（他们列的防撞车件）。
4. **model 绑定**：席位用哪个模型是既有 profile/binding 通道的事，
   本方案不动——`identity_for` 只给身份与职责书，模型归模型层。
