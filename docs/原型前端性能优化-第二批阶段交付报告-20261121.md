## 一、思考详情按贡献段回取

装配器保留同一思考节点的贡献段 `{seq, text, brief}`，包含已完整的段和预览段。展开时按发起会话的 `st.wid`、`st.cid` 读取相应事件，然后按原段序拼接。两个段有相同预览时仍能放回各自位置。详情响应列出的撤销段显示占位提示。未命中且没有撤销标记的段保留原预览。[装配器](../static/esm/assembler.js#L252) · [详情回取](../static/stream.js#L999) · [重拼函数](../static/esm/flow/think-stream.js#L29)

请求失败后重置已加载标志，下次展开可以重试。返回前检查对应元素仍连接在页面上，避免刷新或切换后继续写入已移除的元素。主会话的详情 URL 已实测符合 `session=card_007`。附加会话和详情在途换会话仍应纳入门禁。[思考详情界面](../static/esm/flow/think-stream.js#L128) · [浏览器场景](../tests/chat_brief_check.mjs)

客户端回取边界仍需覆盖长思考。详情路由每次最多取 64 个 seq，当前思考回取会提交全部预览段。超过上限时，余下段会保留预览，而回包处理又会清掉贡献段索引。正式验收补一条超过 64 段的用例，验证单次展开可完整取回或明确指出仍有未加载内容。详情接口沿用巨块响应裁剪，截断预览与归档原文的展示语义也需一并确认。[详情路由](../src/api/routes.py#L2263) · [回取与索引清除](../static/stream.js#L1000)

## 三、服务端四段与前端布局

时序响应通过 `Server-Timing` 暴露 `queue`、`read`、`project`、`encode`。依次覆盖首次线程任务排队、尾窗读取与解析、响应裁剪及窄投影、编码调用。route 前置校验、响应写出等阶段仍在四段之外。探针通过浏览器 Resource Timing 读取服务端头。[时序实现](../src/api/routes.py#L2201) · [采样实现](../tests/chat_perf_segments.mjs#L189)

大卡 brief 的两条有效分段按同一次请求对账。四段加总与浏览器请求至首字节耗时分别是 **36.4 / 742 ms** 和 **60.2 / 596 ms**，占 **4.9%** 和 **10.1%**。尾窗读取两次约 19 ms。这批样本支持先查四段之外的等待，再判断是否需要专门的 brief 读盘实现。当前余量包含多个环节，连接池、浏览器调度、web 接入和服务循环之间的份额待取证。瀑布存在负下载时间，下载分段需要用同一请求的 Resource Timing 时钟复核后再归因。[同请求原始记录](../logs/chat-seg-VKOt50/segments.json)

大卡 brief 的前端样本中，Markdown、挂载、滚动中位分别约 **4 ms、291 ms、288 ms**。滚动测量与挂载存在嵌套，按包含关系读数。下一次轨迹将 `render()`、`toBottom()` 的 JS 调用和 Chrome 布局事件对齐，确认可以省掉哪些首屏工作。[视图计时点](../static/esm/flow/chat-view.js) · [前端分段结果](../logs/chat-seg-VKOt50/segments.json)
