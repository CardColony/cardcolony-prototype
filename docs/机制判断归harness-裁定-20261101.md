# 机制判断归 harness · 架构裁定

日期：2026-11-01。状态：**用户裁定，方向确立**。

本裁定回答一个问题：**"系统对机制状态的判断"（这张卡什么状态、该不该干预、谁该被叫醒）以后写在哪里。**

答案：全部归 harness 的事件→派生事实→策略→动作链路；不再以手写字段、散落 if、进程内标记的形式新增机制判断。

## 一、裁定的直接证据：card_140 / card_141 复盘

- card_140 被父卡叫停后无人能接：`state=active` + `goal=paused` + 内存停止标记 + 手动卡——四字段拼出的半状态，`continue_task`、`resume_child`、发消息、UI 恢复五条路全不认。
- card_141 同形：执行体哑火 5 分半被人按停后，落进同一个死法。
- 病根：**"这张卡什么状态"在系统里有四个互不相干的答案**（生命周期列、目标相位、进程内 halt 标记、回合占用），每扇门各验一个。排查不是在改代码，是在考古——四个存储层、五处写入点拼真相。
- 先例：goal 相位早就走过这条路——`report_done` 曾手写 `goal_state=complete` 导致"DB 说 complete、事件流说 active"驱动跑到 43 轮。修法是"目标相位只能由 GoalService 写"。`state` 是没吃上那次教训的最后一个手写投影。

## 二、裁定正文

### 2.1 归 harness 的（解释与判断层）

- 对系统状态的**解释**：交付走到哪一格、卡是不是被停了、执行体是不是哑了、部署该不该关账——一律是事件流上的**派生事实**，带溯源（哪几条事件推出来的）。
- 对系统的**干预判断**：该不该递话、递给谁、什么变化算解决——一律是**策略**，经用户批准后生效（沿用方案 §4.5 权属四层）。
- 后果：**不再新增手写的机制状态字段**。`state` 这类"五只手轮流记的账"是最后一代；新机制判断出生即 harness 原生（事件＋派生事实＋策略）。

### 2.2 留代码的（地面不变量）

- 写入闸、子树权限、回合互斥、halt/点火机制本身、事件落盘顺序、fact store 本体、内核四段链路——**永驻代码**。
- 理由：这是策略层站立的地面。权限闸每次工具调用要同步回答；监督者不能用被监督的电梯修自己的地面。内核必须保持又小又哑又硬。

### 2.3 集中的代价与三条防呆

集中不减少故障，是把故障搬到能装仪表的地址——"坏一扇门工程照样停"已被实证，分散只换来故障藏得深。集中后唯一要防的坏法是**派生事实悄悄失真**（crash 会喊，错的投影会骗人），防法三条：

1. **溯源**：每条派生事实记住由哪几条事件推出，"为什么这么判"可重放；
2. **对账**：派生视图与事件流持续机械核对（红账本手法），不一致立刻亮；
3. **fail-closed**：查不到答案按最保守判——宁可拒一次派活，不可放一次越权。

## 三、迁移秩序（方向，不是本轮施工令）

1. **halt 事件化**——被停这个事实现在只活在内存、重启即丢，先落事件。独立于 harness，是 140/141 之后最廉价的一刀。
2. **派生"交付位置/运行状态"视图**，与 `state` 列全库对账——推到的一样才算数。
3. **闸门逐个迁到视图**：收信拒 completed → continue_task 资格 → UI 状态显示。
4. 视图被实战证明忠实后，`state` 列退化成写穿缓存或退役。
5. 其他手写机制投影（同类病）按同一顺序逐个收编。

## 四、与其他裁定的关系

- 沿用不推翻：方案 v1 的 S0–S4 分期、"harness 递话不派活"口径、"不用墙钟/轮次/字数替代业务判断"、策略须用户批准、卡面权威。
- 执行体哑火这类**机械健康**判定不是业务判断，不违反"不用墙钟"裁定——红线禁的是拿墙钟猜"任务偏没偏"，不是禁拿事实查"管线通不通"。
- work_027 盘点归属：**机制判断/派生事实/策略执行内核标给 Cardlo 底座监督层**；**业务策略内容标给 CardColony 应用层**。
