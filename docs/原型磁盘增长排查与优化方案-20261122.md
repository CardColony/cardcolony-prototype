### 1. 数据库抽检在反复制造多 GiB 副本

`_integrity_probe` 依次复制正在更新的 `.db`、`-wal` 和 `-shm` 到临时目录，再跑 `quick_check`。三个文件并非同一个提交时点的快照。副本检查失败后，`_preserve` 再直接从活文件拷一套并永久留下。完整性检查分支没有沿用尺寸告警的去重，也没有总量预算。现有隔离记录里，27 次返回结构检查错误，1 次是打开或检查副本的 I/O 错误。11 月 21 日的最近几份分别报过行号顺序异常和页面重复引用。这些记录证明**抽检副本报错并触发复制**。活库是否有相同损坏，需要对一致副本复核。另外，检查异常分支缺少连接关闭的兜底，临时目录清理失败也会被吞掉，需核对是否与残留副本有关。 [抽检和保全](../src/storage/db_watchdog.py#L83) · [抽检临时文件](../src/storage/db_watchdog.py#L161) · [最近一份隔离记录](../db_quarantine/20261122_013937_work_073_cards/_NOTE.txt)

### 2. 日备实际承担了快照的大部分体积

当前 40 GiB 的全库预算只计算过程批次。日备另按每 work 的日期和份数保留，三个大日备日期各约 25.4 至 27.3 GiB。`work_027` 最近三份日备每份约 15.08 GiB。它们大小接近，是否能共用空间仍须按内容和恢复依赖核实。过程批次也包含持久化的上下文投影等表，`work_073` 最近的一份约 0.54 GiB。 [快照范围](../src/storage/data_snapshot.py#L383) · [过程批次和日备保留](../src/storage/data_snapshot.py#L654) · [全局预算](../src/storage/data_snapshot.py#L730)

### 3. 共享日志曾因轮转失败放大，裸 stdout 仍在追加

对 runner2 大文件取六处偏移样本。中间多段反复出现 `server.log → server.log.1` 的 Windows `WinError 32`，以及 Python logging 将整段错误堆栈打到 stderr 的输出。正常工具事件和 HTTP 轮询也写进同一 stdout 文件。当前源码已改成按角色和 runner 编号分别轮转。11 月 22 日 11:19 至 11:25 启动的进程早于该文件 11:35 的修改，盘点时共享 `server.log` 仍在写，角色日志尚未出现。站点启动脚本和看门狗的 stdout 追加仍需独立治理。 [角色日志修正](../src/infra/server_log.py#L32) · [启动重定向](../start.bat#L65) · [看门狗重定向](../watchdog.py#L274)

## 二、实施顺序

### 第一批 · 停止重复保全和日志放大

1. **修库看门狗。** 保留对主文件归零、突降和消失的即时告警。周期完整性抽检改为核验已发布的一致备份。确需取新副本时，对可正常打开的源使用 SQLite 一致备份接口，将复制与检查放在有预算的后台任务。疑似归零或损坏的源继续走应急取证，记录副本完整性和捕获结果。打开失败、I/O 失败和结构检查失败分别记账。一次抽检错误只生成一条合并记录，同一事故后续更新次数和最近观测，跨进程、跨重启共用事故记录。新错误签名或有恢复后再出故障时可以立新案。
2. **限制复制的空间峰值。** 先预算最终副本和临时副本的峰值，再决定就地建、转指定归档盘，或告警待处理。每次仅允许一份同库的抽检副本在途。隔离文件带事故 ID、来源路径、创建时间、完整标志和校验值。已保全的必要证据支持固定保留。系统同时报告跳过原因，便于人工区分空间不足与校验成功。
3. **接续现有的按角色轮转修正。** 隔离四个 runner 并发打日志，检验改名成功、日志检索和轮转后的连续性。用一个能安全切段的写入方处理每进程 stdout 和 stderr，或把正常的 HTTP、工具事件统一写到有轮转的应用日志。保留故障和异常的短尾诊断。Windows 上验证写入句柄持续打开时的实际路径，避免只给仍由 `>>` 持有的文件添加目录清理。访问日志和派发台账已有读者，轮转同时更新读侧。

**通过条件**　模拟同一次故障连续 10 次、再重启后复查，仅保留策略允许的整库副本，所有次数可对账。真实归零仍会报警并留下取证结果。一致备份、临时抽检失败及目标盘空间不足都能解释。多 runner 并发打日志跨两个轮转周期，零改名冲突，在线目录总量受配置约束。 [SQLite 一致备份接口](https://sqlite.org/backup.html)

### 第二批 · 收回 WAL 高水位并控制数据库增长

1. **三类生产库统一观测。** 按库和 work 记录主文件字节、WAL 物理字节、有效帧、已回写帧、检查耗时和忙状态。先识别「已回写后的体积残留」「持续有回写积压」「主库本身在长」。维护任务铺到一个协调入口，避免各 runner 遇到大 WAL 同时发起检查。在多进程隔离实例验证后，为写连接配置合理的 `journal_size_limit`，用成功重置后能回落的体积作验收。对积压分别核查长读事务、批量写入、失败后的事务状态和 checkpoint 进展。
2. **释放已确认的存量高水位。** 先拿到可恢复备份和正在运行的任务清单。由批准的维护窗口做 checkpoint 和必要的 WAL 截短。在读写繁忙时使用可让行的检查，忙则记录并延后。文件体积下降须与读回业务事实和恢复测试同时成立。 [SQLite WAL 维护](https://sqlite.org/wal.html#avoiding_excessively_large_wal_files)
3. **事实索引先减复制，再减存量。** `facts.db` 来自事件派生，生产接入按事件写入。已有 `evict` 提供过期淘汰，当前已核实的实际调用点是重建后。按现有策略窗口、在办事项和等待恢复的引用，确定在线留存。从最小窗口分批清理过期派生行。先重放验证策略命中、汇报去重、等待唤醒和恢复，再精简重复的大正文。SQLite 的空闲页可被新写入复用，物理缩库单独做容量评估。 [事实写入与淘汰](../src/infra/fact_store.py#L208) · [重建调用](../src/infra/fact_store.py#L565) · [SQLite 缩库行为](https://sqlite.org/lang_vacuum.html)
4. **从一致备份量化活库各表。** 核对 `session_blocks`、`context_board`、`memory_nodes` 和消息台账各自的体积与日增量。先减少可重建副本和重复字段。会话原文、真实工具回执、事件审计、凝练水位和来源坐标继续按权威数据保管。任何冷归档方案都要验证时间线、精确找回和按块分页。

**通过条件**　用隔离库复现大 WAL 重用及长读阻挡两种形态。前者确认缩回预算，后者能记录积压而不持续阻塞服务。四 runner 加凝练进程联合压测，恢复后工具回执、日常读取、事实重放和原文找回保持一致。

### 第三批 · 给日备和诊断产物补上总预算

- **日备继续提供完整恢复点。** 先按一次恢复的完整依赖量预算空间，将 D 盘热份数和归档盘保留份数分别配置。可以先验证「本地一份近期完整点，另外两份完整点放归档盘」的恢复耗时，再决定是否对冷档做压缩或增量备份。全局预算显示日备、过程批次、在建、失败、固定保留各自的占用，也展示单 work 的贡献。临时文件完成、清单校验通过并发布后，再让旧恢复点退出。稳定数据可按文件哈希复用或在同盘安全去重，跨日增量须保留全部依赖链。优先验证能否从完整点和权威事件重建可再生索引，降低过程批次重复备份的体积。
- **日志按用途设期限和体积。** 执行诊断默认留结构字段、长度、错误码及关联 ID。完整请求、凝练回包和性能材料限量留样。有争议的回合可按 ID 固定保留。预算按目录和全实例两级执行，空闲时也会清扫过期段。执行体日志、测试目录和输出完整 JSON 的几个入口都登记到同一账里。历史工具派发和恢复对账仍要能跨已滚动分段查询。 [模型请求已有预算](../src/api/prompt_log.py#L24) · [凝练回包落盘](../src/storage/memory_store.py#L1523) · [逐日观测日志](../src/infra/observe.py#L46)
- **工作区和证据独立管理。** 先登记活跃工作区、验收原始证据、固定测试材料、过期测试副本和目录属主，生成包含路径、最近写入和字节数的报告。证据归档保留原始路径映射、散列和可回读入口。临时副本按租期或测试结束回收，构建产物按可再生契约回收。仅在确定目录用途和确认使用者之后处理存量。

**通过条件**　用生产数据规模的隔离副本跑多个日备周期，能从最新和上一份完整恢复点各恢复一张仍在活动的卡和一张跨日卡。恢复后抽验会话 seq、凝练水位、工具回执和到达目标。模拟备份失败、归档盘断开、空间不足及程序中断，旧可用恢复点仍可读取。
