# 卡片内容组件化 · 需求描述（提前准备版，2026-10-14）

> 性质：提前需求描述（**不是施工任务书**）。目标读者＝各功能对应的 agent 方。
> 背景：生态第二层「官方支持层」＝把我们已经具备的能力，做成**可被组合的组件**，由用户按诉求定义与组合，形成更丰富的卡片形态（承 `docs/卡片生态-架构定义-20261014.md`）。
> 本批目的：**提前准备**——各功能方研读现状、理清自己组件的边界、输出组件自述。**不动工**；动工要等底座第一层"接口"定型后再发施工任务书。

---

## 0. 为什么"提前准备、不动工"

组件最终要经统一接口被组合。接口未定型就动手抽象，每个组件会各自定义自己的接口，最后接不上、整体返工。所以本批只做三件事：**研读、盘点、自述**。自述将来是组件化施工的直接输入。

本批与底座第一层（沿关系读与通信）**无关**——那是一个独立的施工任务（另有文档）。请勿混淆两批。

## 1. 统一准备动作（每个组件都做这三件）

1. **研读**：把自己组件的现有代码从头读到尾（位置见下表），不许只读函数签名。
2. **盘点**：回答四个问题——
   - 我的组件**输入**是什么（谁调我、给我什么）？
   - 我的组件**输出**是什么（我产出什么、交给谁）？
   - 我**依赖**什么（我调了哪些别的能力/存储）？
   - 我现在的代码里，哪些是**机制**（放之四海皆准），哪些是**业务写死**（个别功能的口径、文案、顺序写在死处）？
3. **自述**：把上面四问写成一份组件自述（格式见 §2），交回。

## 2. 组件自述格式（统一）

```
组件名：
一句话是什么：
输入：
输出：
依赖（调用了别的什么）：
现状藏身（文件：行号范围）：
机制 vs 业务写死（各列）：
作为组件后，最可能的对外接口（草案，仅猜测，供将来讨论）：
```

## 4. 各组件准备时的注意点

- **组件 1（三席共识）**：现状已高度独立（编排器 offers 交互模式），自述时重点分清"多模型编排"与"提交轮集成"的边界——哪些属于组件本身、哪些是 message_runner 的调用约定。
- **组件 2（剧本链）**：现状就是"数据驱动"（剧本 JSON＋提示词＝零代码加卡），已经接近组件形态，自述重点是理清它与"工具卡底座"中哪些部分是绑定死、哪些已可独立。
- **组件 3（思维链计划板）**：与"入口自判（triage）"的关系要摸清——board 是板，triage 是入口判断，二者组合还是分离，自述里给出你的判断。
- **组件 4（凝练记忆）**：分布最散（触发、归拢、下探三处），自述先把完整链路拼出来。
- **组件 5（产物归档）**：现状是工具卡的产物专用通道，自述时问一句"它将来该不该只服务工具卡"。
- **组件 6（进度上报）**：最薄，自述简洁即可。
- **组件 7（全量留痕）**：它是横切件（照常积压），自述重点是"作为组件它对外提供什么、谁在调它"。
