# 规则卡 · 工程任务书（2026-10-15 · v1）

> 派工性质：**施工任务书**。自给自足规格，外部 agent 照此执行，不得自由发挥。
> 依据方案：`docs/规则卡-方案-20261015.md`（同目录，先读它，以它为准）。

## 一、背景（为什么做）

把散落的行为约束收拢成一张全局规则卡（＝agent 的 AGENTS.md）：一 work 一张、按卡类型分区、右侧常驻可编辑、按当前卡类型自动注入上下文。模型永远不能直接写规则；唯一模型侧通道＝根卡提议 + 用户弹窗审批。这同时落地上下文底座化方案预留的「规则卡提供按卡类型配置」蓝图（`config/context_regions.json` `_meta.scope` 原文）。

## 二、用户裁定条目（不可改，违反即作废）

1. 每 work 一张规则卡，parent=根卡；规则全局唯一。
2. 规则卡按卡类型分区（区名＝card_type code），各区可分别编辑。
3. **画布右侧常驻显示**规则面板（独立右栏，不跟当前卡走）。
4. 用户可在面板直接编辑、**保存即生效**（无确认框——用户自己的操作不审批）。
5. **根卡可提议规则修改**：根卡对话的模型起草 → **弹窗提示用户 → 同意才落盘**；其它卡无此通道。
6. 注入位置 order **85**（instruction 之后、卡片职责之前）。
7. 规则卡本体模型侧只读（rule perms 只 read）；一切模型侧写入必须过用户审批。

## 三、基线（施工前核对，对不上即停手回报）

- `TOOL_TABLE_VERSION="tools-tc-5"`、TOOL_REGISTRY **18 件**；`BASE_PROMPT_VERSION="t20-1"`。
- pytest collected 基线以施工方开工首跑为准（回报写明；预期 660 上下，含编程卡 9 件）。

## 六、分块（3 笔，逻辑内聚）

### 块 1 · 类型 + 注入区

**任务**：
- `card_type_registry.json`：rd_project 与 research_project 两词表各加 rule 项（code=rule、label=规则卡、description=「全局行为准则卡，按卡类型分区，注入对应卡上下文；模型只读」、can_have_children=false、requires_owner=false、default_template=rule；allowed_transitions **不设**——规则卡不进 active/completed 状态机）。
- `permissions.json` v5：`rd_project.rule=["read"]`、`research_project.rule=["read"]`（**只 read，含 shadow_write 也不给**）。
- `config/context_regions.json` v4：regions 加 `"rule": {"enabled": true, "order": 85}`。
- `context_regions.py`：REGION_TABLE 加 rule 区（order 85、name=规则注入、channel=system、seats=("main",)、owner=context、profiles=("main","viewpoint","draft")、render=lambda ctx: render_rule_region(ctx.rule_sections, 当前卡 card_type)）；RegionCtx 加 `rule_sections: dict[str,str]` 字段；render_rule_region 纯函数：按当前卡 card_type 取区，空/缺→空串。
- `context_assembler.py`：build_ctx 里扫本 work card_type=rule 的卡（首张）→ 按 `## ` 行切区 → 填 rule_sections（一次 IO；多张 rule 卡取首张 + ops 留痕）。
- 跑 refresh_perms.py（v4→v5 全量刷 perms_version）。

**硬判据**：
1. 两词表含 rule；`policy.perms_for("rd_project","rule")==["read"]`、research 同。
2. `context_regions.REGION_TABLE` 13 区、orders 含 85、rule 区 seats=("main",)、render 可调用。
3. render_rule_region({"sub_project":"准则A"}, "sub_project")=="准则A"（带区头）；({"sub_project":"X"}, "coder")==""（无对应区→空串）；rule_sections={} → ""。
4. 控制面 v4 生效：把 rule 的 enabled 改 false（monkeypatch 或临时改配置）→ 区不出现；fail-open：坏 JSON → 全按注册表默认。
5. refresh_perms 后存量卡 perms_version=5、值不变（零误伤）。

**交付**：三配置 + context_regions.py + context_assembler.py。

### 块 2 · 规则面板（用户直改通道）

**任务**：
- `routes.py`：`GET /works/{w}/rule`（读规则卡全部分区：{exists, sections:{区名:内容}, hashes:{区名:hash}}；无规则卡→exists=false）；`PATCH /works/{w}/rule/sections/{section}`（入参 content+base_hash：比对→按区替换→重算 content_hash→写回；过 card_store 写闸）。
- 分区替换实现：读规则卡全文 → 定位 `## {section}` 区头到下一区头（或文尾）→ 只替换该段 → apply_hash → 走 card_store 写路径（键形态按写闸最小侵入定，**禁为规则卡新造第二套写路径**，回报取舍）。
- `templates/work.html`：加 `#rulePanel` 右栏（常驻开合按钮，照 inspector/nav-rail 模式；分区列表：每区标题+编辑框+保存按钮+「正被 N 类卡注入」提示=该区名对应的卡类型数）。
- `static/workspace.js`：面板开合、分区加载（GET /rule）、分区保存（PATCH，hash 冲突→toast「已被改，请重新加载」）、导航树 rule 卡点击→开面板（不开对话）、**画布态隐藏 rule 卡节点**（canvas.js 渲染跳过一处：card_type==="rule" 不渲染）。
- 保存即生效验证靠装配 fresh（无需缓存失效代码）。

**硬判据**：
1. GET /rule：无规则卡 → {exists:false}；有 → sections 六区齐全、hashes 与盘上一致。
2. PATCH 分区：content 替换成功、content_hash 变、**其它区字节不变**；base_hash 不符 → 拒绝、零改动。
3. 下一回合对话（同卡）注入内容＝保存后内容（fresh 验证，可沙箱推）。
4. 前端：面板可见/开合；rule 卡在导航树可点但不开对话；画布无 rule 节点。
5. 保存路由不需要任何模型调用（纯 IO）。

**交付**：routes.py + work.html + workspace.js + style.css + canvas.js 一跳。
