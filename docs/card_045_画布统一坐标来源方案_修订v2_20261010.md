## 0. 本版相对原方案改了什么

原方案方向正确、骨架可用。本版改了四处、新增三处、删除两处。

### 改动

**改 1（核心）· 病灶定性从「双写」改为「基准不同源」。**

原方案把病灶定在"两份坐标互相覆盖"。实测：`reflowLayout` 根本不读显示快照（它读的是基准快照，然后覆盖显示快照），所以"双写"这条线是死的。真正活的那条线是——快路径从一份旧快照开始算，而慢路径从当前数据重新算，**两条路径的基准不是同一个东西**。这个区别决定修法：要统一的是"基准"，不是"路径"。

**改 2 · 原方案第 3 步的派生入口，会在首绘时量不到尺寸。**

原方案要求新的派生入口"从当前 DOM 量取的尺寸"生成坐标，并要求 `reflowLayout` 与 `renderCanvas` 都走它。但这两处的 DOM 状态相反：前者就绪（能量），后者刚被清空（量不到）。**照原方案实现，首绘必然退回用估算值**——两把尺子会从"基准/显示"改名成"首绘/重算"，而原方案验收第 6 条（"允许因实测尺寸产生的细微变化"）会把这个残余正式收编进基线，此后难以察觉。

本版的做法是把 `renderCanvas` 拆成两阶段（先全建节点、再一次性测量），见施工段 3。

**改 3 · 原方案第 7 步拆成独立一段。**

原方案把"有用户可见行为变化"的取舍（拖到钉住的卡上不再被推开）和纯结构收口混在同一步。改坏了会分不清是哪一半的问题。本版拆成施工段 5，独立提交、独立回滚。

## 1. 根因

### 1.1 症状

拖动卡片后，卡片位置在后续某次重绘时弹回拖动前的位置。

**复现状态：原方案自述此现象为读码推断，未在浏览器复现。本版实测确认本机具备复现能力（附录 A），但完整复现尚未执行**（原因见 §9 边界声明）。

### 1.2 病灶定性：基准不同源

**两条渲染路径，基准不是同一个东西。**

**慢路径（全量重绘，`renderCanvas`）**：清空节点 → 算布局 → 建节点 → 量尺寸 → 避让 → 应用。这条路径每次从当前数据重新算，**结果是对的**——因为布局计算内部会读 `positions`，把钉住卡的坐标写进结果。

**快路径（防抖重算，`reflowLayout`，定义在 `canvas.js:512`）**：直接取 `state._baseLayout` 当基准（`canvas.js:513`）。而这份基准**只在慢路径里更新**（`canvas.js:578`，全文仅此一处赋值）。

**关键事实：拖动结束时只调了存盘与画线，没有走慢路径。** 于是拖动之后真值变了、基准快照没变。**下一次快路径重算（100ms 防抖，由换档、摘要回填等触发），必然用旧快照覆盖刚放下的位置。**

**快路径的触发点（实测）**：`canvas.js:101`（档位变化）、`:1119`、`:1141`、`:1161`（摘要回填）。

**为什么这个定性比"双写"准：**

实测 `_layout` 的全部引用点是 `:517`、`:631`（写）、`:757`（读）、`:1267–1268`（写）。其中 `:757` 只在拖动结束那一瞬间读它画连线。**快路径不读 `_layout`，它重算后覆盖它。** 所以"两份坐标互相覆盖"这条描述指向的是一条不产生症状的线；真正产生症状的是"基准是旧的"。

**由此推出一条反直觉现象（实测推导，见 §7 A3）**：`pinned` 在这段代码里保护的**不是"用户放下的位置"，而是"基准快照里的那个位置"**——因为避让执行时的钉住集合取自 `positions`，而基准取自快照，两者不同源。于是用户把一张卡拖到新位置并被打上钉住之后，系统会忠实保护一个过期坐标，同时丢弃用户刚放下的真坐标。

### 1.3 顺带发现：写路径的浅合并

**这是原方案没有、核实中撞到的一条当前就通的毁数据路径。**

- 后端：`src/storage/canvas_store.py:176` → `cur.update(positions or {})`，**键级整对象替换**
- 前端：`static/canvas.js:1289` → `patch[cid] = { pinned: false };`，**只带钉住标记、不带横纵坐标**

两者一碰：**用户点一次"整理画布"，被整理那些卡的横纵坐标就被整条替换掉、永久丢失。**

**为什么至今未发作（实测）**：当前 `work_002` 的 5 条坐标全部是 `{x, y, pinned:true}` 的完整形态，**没有一条残条**——说明这个按钮从未被点过。**路径是通的，触发器还没有被按。**

**发作后的表现**：那张卡退回自动布局位置。用户关掉页面再打开，看到的就是"正常"的自动排布——**没有任何提示，他无法知道自己丢过一次排布**（`merge_positions` 失败也只记 warning，前端 catch 为空处理）。

## 2. 目标形态

### 2.1 数据：坐标只有一个来源、两个语义

**坐标记录是用户意图的唯一载体。** 结构保持现状不动（三个字段：横、纵、是否钉住）。它职责单一，不引入第二个职责——**这是它现在最干净的地方**。

**两个语义必须区分：**

- **用户明确给的位置** → 写进坐标记录
- **系统推算出来的位置**（避让位移） → 只用于显示，用完即弃，不写进坐标记录

### 2.2 渲染周期目标形态

```
建全部节点（占位坐标，整层隐藏但占位）
  → 一次性全量测量尺寸
  → 用实测尺寸算基准（纯函数）
  → 避让（纯函数）
  → 一次性全部应用
  → 取消隐藏
```

此后所有重算走同一条路径，**基准只有一个来源**。

### 2.3 明确不做的

- **不引入自动布局写回坐标记录。** 将来若做自动排布、按依赖重排、AI 建议排布，一律落在显示层，不写坐标记录。
- **不做坐标的记录迁移。** 存量保持原样（理由见 §6）。
- **不改坐标记录的字段结构。** 包括不新增字段（除段 5 明确语义所需）。

### 段 3 · 渲染周期改两阶段（风险最高）

**改什么**：

```
建全部节点（占位坐标，整层隐藏但占位）
  → 一次性全量测量尺寸
  → 用实测尺寸算基准（纯函数）
  → 避让（纯函数）
  → 一次性全部应用
  → 取消隐藏
```

**为什么**：这是病灶的正面手术。原方案的派生入口在首绘时量不到尺寸（节点刚被清空），只能退回估算值——两把尺子会改名留下来（见 §0 改 2）。

**✱ 纪律性约束（必须写死进代码注释）**

> **必须用「隐藏但占位」的方式（元素仍在布局流中、尺寸可读），不许用「不占位」的方式（元素不参与布局、量不到尺寸）。**

**【新增·更正：这不是本版引入的新约束，是既有约定】**

本版初稿曾把这条写成"我引入的约束"，**方向说反了**。实测 `static/style.css:420` 已有同款书面记录（**自述，不作依据；但此处作"既有约定存在"的凭证**，原文逐字）：

> `显隐用 visibility 而非 display:none——隐藏的画布保持可测量（renderCanvas 的 measureSizes/fitView 依赖 clientWidth），对话区 scrollHeight 也恒有效。`

**所以本段是沿用既有纪律，不是新立规矩。** 这个区别对后来人有实际影响：写成"我引入的"会让他以为这条可以商量；写成"既有约定"才是它本来的性质。

**这条不写死的具体后果：改错不会报错、不会异常。** 它只会让测量拿到 0 或拿不到，然后整个两阶段静默退化成"全用估算值"，而表面上一切正常。

**为什么本段风险最高**：渲染周期是唯一一个所有其他东西想变成可见都必须经过的环节。它的输入（坐标、树、尺寸）全对，而它错了，结果就是位置全乱或一片空白——**是显性的、全局的，不是局部的**。

**它的安全网是三件事，缺一件都不该动本段**：
1. 段 0 的基线——出事时能对着改前数据比，立刻分清"是改坏了"还是"本来就那样"
2. 段 1 的等价性断言——能分清"是渲染周期错了"还是"是算法错了"
3. 段 2 的单测——能在浏览器之外先跑纯函数，把算法层错误提前排掉

**怎么验证**：
- 首绘无可见跳动（两张截图比对）
- 卡片两两不相交
- **尺寸测量在一轮渲染里只发生一次**

**附带收益（实测现状）**：`measureSizes`（定义在 `canvas.js:486`）有 5 个调用点：`:320`（树布局内）、`:515`（快路径内）、`:629`（全量渲染内）、`:887`（连线渲染内）、`:1214`（落点仲裁内）。其中一次完整的全量渲染会经过 `:320`、`:629`、`:887` 三处。**每测量一次都会强制浏览器重算布局。** 两阶段合并后降为一次。

**怎么退**：单文件回滚，不留残渣。

**【新增·快路径函数的最终去处（初稿未交代）】**

初稿只说"改 `renderCanvas`"，**没有交代快路径函数（`canvas.js:512` 定义的那个）最后怎么了**——删掉？保留？改名？这是原方案 §四 第 5 步的落点，必须写明：

> **函数保留，改名不变，但内部实现改为调用统一入口的"不重建节点"分支。**
>
> 具体：它不再取基准快照当基准，而是走与全量重绘相同的计算链（实测尺寸 → 纯函数算基准 → 避让 → 应用），**唯一区别是不重建 DOM 节点**（节点已在，只更新位置）。
>
> **为什么保留而不删**：两个触发时机（首绘要建节点、换档/回填不要重建）是真实存在的两种需求，合并成一个函数的两个分支，比强行合并成一条路径更清楚。**"统一"统一的是基准与计算链，不是调用时机的数量**——见 §1.2。

**怎么验证**：除本节已列三项外，追加——**换档与摘要回填后，位置与"重新加载页面后的位置"一致**（证明快慢两条路径给出同一结果）。

### 段 4 · 删两份快照、改单写

**改什么**：
- 删基准快照（`canvas.js:513` 读、`:578` 写，全文仅此两处）
- 删显示快照（`:517`、`:631`、`:1267–1268` 写，`:757` 读）
- 显示坐标改为临时变量传递、用完即弃
- 存盘函数只写坐标记录

**为什么**：这两份快照就是"基准不同源"的载体。**具体后果（不删）**：快路径会继续从旧快照开始算，于是"用户刚放下的位置被下次重算覆盖"会换个触发条件再次出现。

**怎么验证**：检索断言（基准快照零引用、显示快照只剩派生赋值、存盘函数内无第二份写入）+ 浏览器里跑"拖动后不回弹"。

**【新增·删掉显示快照后，连线怎么画（初稿的实质缺口）】**

**这是初稿最危险的一处遗漏。** 实测：拖动结束时（`canvas.js:757`）**正是靠显示快照画连线的**——而本段要删掉它。初稿只说"删显示快照"，**没说删完之后连线吃什么**，照字面实施会直接导致**拖动后连线不动或错位**。

定死如下：

> **拖动结束后的完整动作序列**（替代原先的"存盘 + 用显示快照画线"）：
>
> 1. 存盘只写用户松手的坐标（段 5）
> 2. **立刻调用一次统一重算的"不重建节点"分支**（即快路径的新实现）
> 3. 该分支产出的显示坐标表**直接用 于更新连线**——连线与卡片节点吃同一份结果，不再有第二份来源
>
> **关键点**：连线不再是"谁顺手更新一下"的旁路，而是**统一重算产物的一部分**。这样删掉显示快照才是安全的。

**怎么验证**：
- 检索断言：**"读取显示快照"的代码位置数 = 0**（本段的核心断言，见 §4.1 第 6 条）
- 行为断言：**拖动后连线端点立即正确**（§4.2 第 14 条）
- 行为断言：拖动后**无需任何其他操作**，连线即到位

**怎么退**：纯减法，单文件回滚，不留残渣。

**【新增·清理失效引用（原方案 §四 第 10 步）】**

删掉两份快照后，**所有引用它们的位置都要清理**——包括但不限于：连线渲染（`:757`）、存盘函数（`:1264–1273`）、落点仲裁（`:1212` 附近）。**实测命中 6 行**（5 处代码 + 1 处注释，注释见 §4.1 第 3 条口径说明）。

**清理的验收**：`§4.1 第 6 条`的"读取位置数 = 0"同时覆盖这一条。

### 段 5 · 存/显分离 + 钉住语义定死

**改什么**：
- 存盘只写用户松手的原始坐标
- 避让算出来的位置只用于显示
- 钉住语义定死为：**这张卡的坐标由用户明确给定，因此它不参与避让位移**

**为什么**：现状是"系统推算出的避让位置"被当成"用户意图"存下去。**具体后果（不改）**：用户把卡拖到另一张卡上，系统推开它、并把推开后的位置记成"用户要的位置"——用户的真实意图从未被保存，而其后所有重算都建立在这个假意图上。

**必须提前说清的行为变化**：用户把卡拖到另一张钉住的卡上时，会真的重叠（现状会被推开）。取舍是"用户放哪就是哪，系统不自作主张"。

**怎么验证**：浏览器里拖到钉住的卡上，断言存的是松手坐标、显示可重叠。

**怎么退**：独立成段的原因就是它有用户可见的行为取舍——退它不影响前四段。

### 段 6 · 写路径改深合并

**改什么**：后端合并从整条替换改为逐字段合并（`src/storage/canvas_store.py:176`）。

**【新增·二选已定，不留活口】**（初稿此处写"前端该按钮的载荷补全坐标，**或**依赖深合并"，是留给下游自由发挥的口子，现定死）

> **后端改深合并；前端不改。** 深合并落地后，前端继续发 `{pinned:false}` 即为安全——缺失字段保留原值。
>
> **理由**：深合并保护的是所有将来要加的字段，不只是这一次；若改前端，下一个加字段的人会重犯同一个错。**把安全性放在收口处，不放在每个调用方。**

**为什么**：见 §1.3——**这是当前就通的毁数据路径。**

**为什么必须在本次做**：段 5 会改到同一个按钮的载荷。**如果不修这里，段 5 改完反而会踩上它。**

**为什么选后端改**：它保护所有将来要加的字段，不只这一次。**每加一个字段就多一条被静默抹掉的风险**——这是格式演进最贵的陷阱。

**怎么验证**：单测（发 `{pinned:false}` 之后横纵坐标仍在）+ 手工点一次该按钮确认坐标不丢。

**怎么退**：后端单文件回滚，不留残渣。

**本段可独立于其它段先做**——它修的是现存缺陷，与坐标体系重构无依赖。若要降低一次性改动量，这是唯一可以拆出去单独上线的段。

### 段 7 · 长期不变量落成约束

**改什么**：写注释与上验收项，几乎零代码：

- **兜底方式改正**：非法坐标**兜底到自动布局位置，不许跳过、不许消失**。（原方案与本方案初稿写的是"跳过并告警"，**那是错的**：跳过等于那张卡从画布上消失，而丢卡是最坏的失败形态——人不会知道少了一张。）
- **写死"位置不表达状态"**：将来有人想用"把做完的挪到一边"表达进度时，这条会拦他一次。
- **写死"钉住的坐标是绝对锚点，布局算法换代只影响派生位置"**：用户手放的卡在算法换代后原地不动。
- **写死"位置跨视图共享"**，并配一条验收："下钻再返回，位置不变"。

**为什么**：**具体后果（不做）**：下一个改这块代码的人会重犯同一个错——他会写一个自动布局把结果写进坐标记录，会为了"少打搅用户"把非法坐标静默跳过，会为了让画布更清楚用位置表达状态。**这些都不是恶意，是不知道。**

**怎么验证**：注释审查 + 验收项上表。

**怎么退**：无代码风险。

### 6.2 历史偏差：影响上限 5 条（即全部），一条都不清

**从数据快照还原的演化**：键数 `3 → 4 → 5`；值上 `card_010`（342,289 → 341.091,294.455）与 `card_016`（343,-27 → 352,-14）被改过，`card_019` 一动未动。

**几何特征（推断，非实证）**：这 5 张全部是根卡的直接子卡；横坐标全部落在 321~352（跨度 31），而自动布局给第一层子卡的位置就在 340 附近；纵坐标从 -211.5 拉到 619（跨度 830）。**这个形状看起来像自动布局的结果被钉住，而不是用户的空间意图。**

**但不断言。** 用户操作记录不存在于任何持久化载体（会话不记录、日志不埋点、代码不打点）——**来源无法判定。**

**为什么一条都不清**：

1. **真值已丢**。若来源确为系统推算，用户原始松手位置在存盘那一刻就被覆盖，快照里存的也是覆盖后的值——**没有真值可恢复，清它不是修正，是拿猜测替换现状。**
2. **它们现在是用户浏览器里看到的权威**。改它们等于替用户做决定——**而这正是本次改动要消灭的那件事。**
3. **5 条合法数据，改它收益为零，风险是动到用户可能真做过的一次微调。**

### 6.3 将来加新字段怎么办

**读时兜底 + 后端改深合并 + 不刷库。**

缺字段策略：
- 钉住标记缺失 → 视为未钉住
- 横纵坐标缺失 → 该卡不参与按记录摆放，退回自动布局
- 未来新字段 → 一律"缺失即采用默认值"，**不做一次性刷库**

**不刷库的理由**：7 个 work、76 张卡、5 条坐标——这个规模小到"刷"这个动作本身没有意义；而读时兜底是永远正确的做法，不管存量多少。**真正要一次性处理的不是数据，是那条浅合并的写路径（段 6）。**

### 6.4 不清的代价落在哪

- **那 5 条可能带"系统冒充意图"的历史污点**（若来源确为系统推算）。不会再产生新的——段 5 改完后避让坐标不再写进记录。旧的这 5 条会被新语义重新解释为"用户明确给定的坐标"；不管当初怎么来的，用户看到的就是这个位置。
- **`card_040` 的纵坐标 -211.5 可疑**（推断）：自动布局从 0 向下排，没有理由产生负值；两种可能是用户往上拖了，或避让把它向上推出去了。**判不出来，标注为未解。**
- **真正的风险不在存量数据，在写路径**——只要合并仍是浅合并，那颗雷就一直埋着。**不清数据不会让它发作，点那个按钮才会。**

## 7. 风险分级

> 分级规则：**A 级 = 已实测的现存缺陷**（必须附"怎么测出来的"）；**B 级 = 结构上必然**（必须指出它现在以什么形式存在）；**C 级 = 设想场景**（另起一节，写清前提）。**C 级不出现在本节。**

### A 级 · 已实测的现存缺陷

**A1 · 写路径浅合并会抹掉坐标**

- **怎么测出来的**：读 `src/storage/canvas_store.py:176`（`cur.update(positions or {})`，键级替换）+ 读 `static/canvas.js:1289`（`patch[cid] = { pinned: false };`，只带一半字段）+ 实测 5 条现存数据全为完整形态（说明按钮从未被点过）。两头对齐即得该路径。

**A2 · 尺寸在一轮渲染里被测量三次**

### B 级 · 结构上必然

**B1 · 基准不同源必然产生"真值被旧快照覆盖"**

- **它现在以什么形式存在**：`canvas.js:513` 读快照、`:578` 写快照，而快路径的全部触发点（`:101`、`:1119`、`:1141`、`:1161`）都不经过 `:578`。
- **为什么是必然**：快照的更新时机与真值的更新时机是两个独立事件，而重算只认快照——**只要这两个时机不重合，就会读到过期的那个。**
- **处置**：段 3 + 段 4。

**B2 · 布局不纯必然要求一份快照兜底**

- **它现在以什么形式存在**：树布局内部直接调尺寸测量（`canvas.js:320`），而该时点 DOM 可能尚未就绪，所以必须有估算值兜底（`:323–324` 的 86/36）。
- **为什么是必然**：不纯的函数无法在"数据未就绪"时自我保护，只能外挂一份状态。
- **处置**：段 1 消除不纯，段 3 消除兜底需求。

## 8. 长期不变量

**为什么单列一节**：以上是"这次怎么改"，本节是"无论怎么演化都必须为真"。**前者会被下一次改动覆盖，后者不会。** 违反其中任何一条，画布会从"能用的画布"变成"不能用的画布"——而不是"差一点的画布"。

**L1 · 人的位置只由人给。**

系统推算出的任何位置，都不许写进用户的坐标记录。这不只是"避让不回写"——将来若引入自动布局、按依赖重排、AI 建议排布，**一律必须落在另一层。**

*为什么是长期约束*：一旦系统能写，用户记录里就再也分不清哪些位置是他自己给的。**这个污染无法事后清理**——因为分不清哪些是被系统改过的。

**L2 · 位置独立于卡片语义。**

卡片改名、换类型、变状态、换归属，位置不受影响。位置只回答"在哪"，不回答"是什么"。

*为什么是长期约束*：位置记录是这套系统里唯一一件"给人看"的东西。它一旦和语义耦合，改语义就会动到人的空间记忆。

**L3 · 重放必须确定。**

同一份坐标记录 + 同一棵树 → 必须给出同一张图。

*为什么是长期约束*：**这是画布存在的意义本身，不是可测试性收益。** 人的空间记忆建立在"我上次看到的样子"上。重放一旦不稳定——他记得"在右上角"、打开发现不在——**他建了几个月的位置记忆当场作废，而且他不知道为什么。** 一条会漂移的画布不是难用的画布，是**不能用的画布**。

**L4 · 动作只有一个权威解释。**

拖动是人的意图，避让是系统的行为。两者混在一起那一刻，坐标记录就不再是人的账了。

**L5 · 任何一张卡，任何时刻，都必须能被找到。**

非法坐标要**兜底到可见位置**，不许跳过、不许消失。

*为什么是长期约束*：**丢卡是最坏的失败形态**——人不会知道少了一张。一个"少了一张卡但看起来一切正常"的画布，比一个明显报错的画布危险得多。

**L6 · 位置不承担状态表达。**

哪些做完了、哪些卡住了，必须在卡上，不能靠"摆在哪里"来读。

*为什么是长期约束*：位置一改，状态就跟着变，而状态是账、位置是记忆。**两者一旦耦合，改一个就动另一个**——而它们本该各归各的。

**L7 · 布局算法换代时，人的相对空间关系必须能保住。**

*为什么是长期约束*：这是这套东西**能不能承受自己变好**的关键。人花三个月摆出的布局，如果因为换了算法全部重算到新位置，**那三个月的记忆一次性作废。** 所以换代必须是保关系映射，不是全量重排。

**L8 · 坐标的归属层级必须明确。**

*为什么是长期约束*：现在它是 work 级的（一份坐标）。将来一旦出现多视图（同一棵树按时间、按状态、按依赖三种投影），"一份坐标"就不够了。**现在就要把语义写明**——本版定为「钉住坐标跨视图共享」，因为人的空间记忆是"这东西在哪儿"，不是"在哪个视图的哪儿"。
