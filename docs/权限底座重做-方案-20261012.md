# 权限底座重做方案（2026-10-12 · v2）

## 一、目标与已定原则

把"按卡片类型分配权限"从现状（散在代码、每次现查、类型可变、口径不一）重做成干净底座。

已定原则（用户裁定）：
1. 按类型分权，两级 = `project_class`（工牌）+ `card_type`（类型）。
2. **类型不可变**：建卡定死，`update_card` 改 card_type / project_class 一律拒绝。
3. **可配置**：加类型 = 改权限配置，代码零改动。
4. **权限固化 + 版本刷新**：建卡时算一次写死进卡，运行时照读；配置改版时跑刷新脚本更新旧卡（权限会随迭代变）。
5. **默认关门**：没配到的类型 = 全拒。
6. **开关可扩展**：后续可加可减，改配置即可。
7. **未来方向**：卡片只读 + 建卡预置内容（`edit` 会收走），底座为此留余地。

## 二、设计

### 1. 权限开关（可扩展词汇表，初始 10 个）

| 开关 | 什么意思 |
|---|---|
| read | 能读 |
| edit | 能改（未来会收走） |
| delete | 能删 |
| create_child | 能在它下面建子卡 |
| link | 能连线 |
| unlink | 能解线 |
| search | 能用搜索 |
| tools_file | 能读写文件 |
| tools_web | 能联网 |
| shadow_write | 能写自己的影子卡 |

开关词汇表在代码里定义成一个常量集合（防配置拼错）；加新开关 = 代码里加一个常量 + 配置里用起来。配置里没配到的开关 = 没这权限。

### 2. 权限配置（独立文件 `config/permissions.json`，带版本号）

```json
{
  "version": 1,
  "permissions": {
    "rd_project": {
      "project":      ["read","edit","create_child","link","unlink","search","tools_file","tools_web","shadow_write"],
      "sub_project":  ["read","edit","delete","create_child","link","unlink","search","tools_file","tools_web","shadow_write"],
      "tool":         ["read","edit","delete","search","shadow_write"]
    },
    "research_project": {
      "project": ["read","edit","create_child","link","unlink","search","tools_file","tools_web","shadow_write"],
      "topic":   ["read","edit","delete","create_child","link","unlink","search","tools_file","tools_web","shadow_write"]
    }
  }
}
```

- 两级：`project_class`（rd/research）→ `card_type`（project/sub_project/tool/topic）→ 开关列表。
- 根卡查 `permissions[project_class]["project"]`；子卡查 `permissions[project_class][card_type]`。
- 根卡没有 delete（删不掉）；tool 卡没有 create_child / tools_file / tools_web（不长树、不碰文件、不联网）。

### 3. 权限固化 + 版本刷新

- 建卡时：按两级定位查到开关列表，写进卡的 `perms` 字段，同时记 `perms_version`（当时配置的 version）。
- 运行时：读卡上 `perms` 直接判断，不查配置。
- 改配置：`version` +1，跑 `scripts/refresh_perms.py`，把 `perms_version` 落后的卡按新配置重算、更新。

**为什么要有版本号**：类型不变，但"这个类型配哪些权限"会随迭代变。固化的 perms 会过时，靠"版本号 + 刷新脚本"在改配置时批量刷新，而不是运行时每次查。

### 4. 树作用域（防越界）

"能不能碰自己子树外的卡"是独立一层，不属于类型分权：

- 卡片操作（edit/delete/link/unlink/create_child）在类型分权通过后，再判断"操作者是否在目标上游"。
- 独立函数，逻辑沿用原 `_is_in_subtree`。
- **未来 edit 收走后，越界操作自然消失，这一层可删**。这次重做先保留，只是从权限开关里拆出来。

### 5. 默认关门

配置里没配到的类型 → 空权限（全拒）。修掉 card_tools.py:1260 那个"卡号空就全放行"的兼容分支。

## 四、落地步骤

1. **配置**：新建 permissions.json（两级 + version=1）。
2. **权限核心**：policy.py 重写（读配置 + has_perm + 树作用域）。
3. **固化**：card_store 建卡算 perms+perms_version + update_card 堵改类型 + 落盘加字段。
4. **消费端**：card_tools / card_proposal / file_tools 改成读 perms。
5. **刷新**：scripts/refresh_perms.py 对 88 张存量卡补 perms（= 第一次刷新）。
6. **验证**：全量 pytest + 真链路口径。

## 五、存量迁移

88 张存量卡没有 perms，跑一次 refresh_perms.py：读每张卡的 card_type / project_class → 查配置 → 算出 perms + perms_version=1 → 写回。

## 六、验收判据

1. 建卡后卡面带 `perms` + `perms_version`，值 = 配置。
2. `update_card` 传 card_type / project_class → 拒绝。
3. tool 卡调文件/联网工具 → 不下发 + 执行拒。
4. 根卡 delete → 拒。
5. 未配置类型 → 全拒。
6. 改配置 version+1 后跑 refresh_perms.py，旧卡 perms 刷新到新配置。
7. `pytest -q MOCK_LLM=1` 全绿，绿数写回。
