# 卡片编辑机制改造方案（2026-10-12）

## 一、目标

让「需求文档」在**卡内**产生，成为该功能「应该长什么样」的**唯一权威源**。两条主线：

1. **块集改造**：研发卡正文块从「使命/现状/定论」改成「使命/现状/需求文档」。
2. **写权限收回**：模型不再能直接 `edit_card` / `update_shadow` 改卡，改成「模型起草 + 用户按钮确认写入」。

## 二、已定原则（来自需求文档，用户裁定）

- 需求文档 = 该功能应长什么样的唯一权威源，卡内产生、不需要子卡。
- 模型只负责起草，**写入必须经用户按钮确认**。
- 使命块永远不经起草/确认通道，只能用户界面改（立项定稿）。

## 三、设计

### 1. 块集（数据结构）

- **判据**：`card_store._root_project_class(work_id)`（`card_store.py:522`，读根卡 `project_class`，现成函数，不新造）。
  - `rd_project` → 研发卡块集 = 使命 / 现状 / **需求文档**。
  - `research_project` → 其他卡块集 = 使命 / 现状 / **定论**。
- **落点**：`src/storage/hash_utils.py:104` `NEW_SECTION_MAPPING` 加一行 `"## 需求文档": "requirements"`。`OLD_SECTION_MAPPING` / `OLD_KEY_TO_NEW` 不动——「需求文档」是新区头，不参与旧键归一。
- 研发卡的 `rulings`（定论）不再作为写入目标；存量研发卡的定论保留**只读**。
- 读侧按判据取块，缺失返回空，不报错。

### 2. 写权限收回（依赖权限线交付）

- 权限线正在修「工具面按 `edit` / `shadow_write` 下发」这一处（即 `_filter_by_category` 目前只按 `tools_file`/`tools_web` 过滤、`edit_card`/`update_shadow` 不在过滤范围的缺陷）。
- 权限线交付后：模型主卡工具面不再出现 `edit_card` / `update_shadow`，且执行层 `card_tools.py:272`（`SWITCH_EDIT`）、`:361`（`SWITCH_SHADOW_WRITE`）的 `policy.check` 已就位。
- **本方案不重复写收回逻辑**，只在验收判据里记一条「依赖权限线交付」的核对项。

### 3. 起草接口 draft（新增，无写工具）

- 路由：`POST /works/{work_id}/cards/{card_id}/draft`
- 入参：`kind`（`requirements`｜`status`）、`feedback`（可空）、`prev_draft`（可空）。
- 调模型：`model_service.call_main(system_prompt, user_prompt, tools 缺省 None)`——走主模型、不传工具、纯文本输出；**独立路由、独立调用，不进 `message_runner` 工具循环**（不改 `gateway`/`model_service` 签名）。
- 上下文：当前块现有内容（必带）+ 本卡对话相关段 + 上一版草稿 + 用户反馈。
- 草稿只存内存/会话态，**不落盘**，关闭即丢；返回时附带当前块的 hash 指纹。

### 4. 确认写入 commit（唯一写入口）

- 路由：`POST /works/{work_id}/cards/{card_id}/commit`
- 入参：`kind`、`draft`、`base_hash`。
- 流程：
  1. 比对 `base_hash` 与卡内该块当前 hash，不一致 → 拒绝，提示重新起草。
  2. 草稿整块替换：`card_store.update_card` 只写对应键（`requirements` 或 `status_block`）。
  3. 过 `_write_gate`（`card_store.py:524`）与块规则闸。
  4. 系统自动在影子「## 迭代历史」记一行（时间、按钮类型、旧块 hash、新块 hash、反馈轮数），用现有 `shadow_store.append_to_section`（`shadow_store.py:185`，落 `## 迭代历史`），**不让模型写**。
- 使命块永远不经此口。

### 5. 前端交互

#### 5.1 按钮

- 位置：`templates/work.html:74`（`inputmeta` 行，`sendBtn` 左侧）加两按钮，ghost 级（弱于 sendBtn）。
- 按当前卡块集判据显示文案：
  - 研发卡（`rd_project`）：**「需求确定」** + **「更新现状」**。
  - 其他卡（`research_project`）：**「定论确认」**（写定论块，只追加）+ **「更新现状」**。

#### 5.2 弹窗（modal，新建）

- 前端现无 modal 组件（只有 `window.prompt` + `notifyPanel` 浮层）。新建一个浮层，参照 `notifyPanel` 的 `class="open"` 开合模式（`workspace.js:1309`）。
- 结构（自上而下）：
  1. 标题栏：按 `kind` 显示「需求文档起草」/「现状更新起草」。
  2. 草稿区：模型草稿**只读**展示（用户不直接改，要改走「反馈」）。
  3. 反馈框：默认收起；点「反馈」后展开，输入「哪里要改」。
  4. 底栏三键：**确认** / **反馈** / **关闭**。

#### 5.3 流程（状态机）

```
点按钮
  → 调 draft(kind)，弹窗进「加载中」
  → 返回 草稿 + base_hash，弹窗进「草稿态」（只读展示，暂存 base_hash）
  → 用户三选一：

  〔确认〕→ commit(draft, base_hash)
             ├ 成功 → toast「已写入」、关弹窗、刷新 inspector
             └ hash 不一致 → 弹窗提示「内容已被改，请重新起草」，回到草稿态

  〔反馈〕→ 展开反馈框 → 提交 feedback
             → 重新 draft(kind, feedback, prev_draft) → 更新草稿 + 刷新 base_hash

  〔关闭〕→ 直接关，不发任何请求（草稿丢弃，卡 hash 不变）
```

- 关键约束：**「关闭」与「反馈」都不落卡**，只有「确认」走 commit；draft 请求工具列表为空（验收 P4）。
- 弹窗打开期间不锁卡；若期间卡被别的操作改过，由 commit 的 `base_hash` 比对兜底（见 §三.4）。

## 六、存量迁移

- 存量研发卡：定论块保留**只读**，不显示为可编辑块；需求文档块缺失返回空。
- **零数据删除、零数据迁移**——只是读侧判据变化 + 新增两接口，不动任何卡内容。

## 七、验收判据

| 期 | 判据 |
|---|---|
| P1 块集 | 研发卡无定论块、其他卡无需求文档块；存量卡读取不报错 |
| P2 写权限收回 | 主卡工具面无 `edit_card`/`update_shadow`；执行层直调 denied（依赖权限线交付） |
| P3 关闭无副作用 | 弹窗关闭/取消后，卡 hash 不变 |
| P4 确认写入 | 整块替换成功；期间卡被改则确认被拒；反馈轮次上下文连续；draft 请求工具列表为空 |
| P5 全链路 | 两按钮各走一遍：起草 → 反馈两轮 → 确认；再走一遍取消，确认无落卡 |

## 八、红线

- 只动 §四 白名单文件，不碰会话底座、卡间信、凝练、思维链、toolcard。
- 使命块不可经 draft/commit 改，只能用户界面。
- 草稿请求绝不进 `message_runner` 工具循环。
- 不删数据、不新增依赖。
- 5700 在跑时编辑走 worktree，重启只走 `restart_safe.py`。

## 九、待用户拍（默认值已给，未拍前按默认施工）

1. **非研发卡「需求确定」→「定论确认」写定论块**：默认同意。
