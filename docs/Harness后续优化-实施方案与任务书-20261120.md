Harness 要帮模型在三个时点做出更好的决定。阶段负责人派工前，能看到产品目标有没有落到负责人和验证路径。执行卡开工前，能拿到生效需求、可做步骤和验收判据。准备进入下一步时，能查到前置是否真的满足。此次把两份前案的八条策略排成可独立交付的施工批次。[任务遵循与接力前案](Harness需求遵循与任务接力-实施方案-20261120.md) · [产品方向前案](Harness执行中守住产品方向-补充方案-20261120.md)

## 2. 执行与判断的分工

| 入口 | 做什么 | 如何记录 |
| --- | --- | --- |
| 用户及授权负责人 | 确认任务、需求和阶段方向，决定取舍、批准变更和验收 | 绑定当前需求正本、裁定记录、计划或验收记录 |
| Harness | 核对引用是否存在、生效且相符，识别显式前置，选定需要提示或核证的时点 | 同一业务事项复用既有事项，记录触发事实、动作、目标、解除依据 |
| 模型 | 理解条款、选择实现、提出遗漏的验证及反例、解释证据覆盖 | 给出能回到原文和原始结果的建议，由责任方裁定 |
| 任务、执行及验收入口 | 兑现当前任务授权、前置和暂停，投递、提交、写回执 | 按原任务和动作身份受理，记录实际写入或拒绝，结果未明先回查 |

**手动卡**在原任务进入模型前得到依据，在当前任务内查证和交付。方向提示只送进当前或下一次自然回合，另有明确授权的卡间消息按既有入口处理。**自动卡**也用这份依据。只有属于当前授权目标、确有可做步骤且属主允许起轮时，才经现有目标驱动接续。人工停止、取消和换版优先，恢复时重新核对。Python 原型的手动与自动差异由各卡的执行入口兑现。Go 按 S5 已批准的动作契约验证，`message` 和 `inject` 不唤醒，`continue` 含一次唤醒。[原型模式边界](原型自动模式-目标推进与事件续跑方案-20261120.md) · [S5 动作契约](../works/work_073/_card049_zhenggao.md#L90)

策略按 work、具体任务和动作启用。优先沿用 `inject`、`message` 及原执行入口。原型现有 Harness `continue` 走评审专用路径，普通自动卡续动由目标驱动消费已核实的事由。建议、证据和执行状态各沿原入口读写。触发可用既有事实，缺少权威信号时在相应入口补最小引用。无法定位权威来源的旧记录先供回放和人工核查。[原型动作实现](../src/infra/harness.py#L146) · [目标驱动](../src/goal/driver.py#L400)

## 3. 派工批次

### A · 双 work 回放与去重基线

**施工。** 提取 `027/230` 和 `073/050` 的同一评审状态反复产出新事件片段，再取席位恢复和正常派定稿样本。固化输入、原始位置、当时可见的事实和预期结果。另为下文其余策略准备窄夹具。现有 `runnable` 作为基线，离线重放使用记录型投递器。盲回放以当时的时间截点为准，把后来用户的解释留在验收真值中。

**通过条件。** 同一事件重放、同一等待状态的新事件、重启后恢复，均不得让等待期间增加请求或出现第二个开放事项。可运行步骤确实出现时能恢复一次。旧事件缺 `runnable` 记为信息不足。复用干预台账的事项与动作两级记录，分别按业务状态和实际动作去重。原有动作唯一索引绑定触发事实，新事实仍可能描述同一业务状态，须验证动作入口也沿用原动作身份。[现有去重与台账](../src/infra/intervention_store.py#L36) · [现有评审回归](../tests/test_policy_set.py#L516)

### B · 执行卡开工依据与证据收口

| 施工项 | 接入点和最小交付 | 关键验收 |
| --- | --- | --- |
| 开工时送入有效依据 | 从已有派工绑定原消息 ID、责任卡、实际需求版本及条目、当前步骤、暂缓事项和验收点。优先从现有需求权威入口读正本。第一次相关请求前，注入短条文、依据指针和允许的下一步。作用域按任务和版本核对。 | `007` 首次派工允许起草、查证、汇报，写需求和开评审分别保留为暂缓。`017` 的 R7/R19 在评期间仍使用已生效条款。正式变更只使受影响的任务重新对齐。同卡另一任务取不到本任务注入。 |
| 凭证据收口 | 接一个真实交付或验收入口，用 `worker_done` 或阶段交付触发核对。逐条记录判据、目标、代码或装配快照、原始记录和有权接受方。输出通过、未通过、待核实、未覆盖及具体缺项。 | 测试装配、单段走通、正式启动分别按对应证据落账。假工具结果壳、正文声称已发、目标不符、缺记录锚均不能使判据通过。投递未确认按已有记录追查。补证只送具备职责的人，已派发或结果不明时零自动重写。 |

| --- | --- | --- |
| C1 · 从阶段目标反查责任 | 阶段计划或批量派工准备提交时，对照获准的产品目标和已生效的变更，列承诺、负责卡、验证路径或批准延期。根稿修订也核对产品能力的保留、变更和延期。将无明确承接的项交阶段负责人。 | 旧线 M1-C 的多模型并发结果照常保留，同时指出共享存储上的并行承诺还缺责任或验证。已有责任和判据，或权威记录已批准延期时静默。 |

### D · 明确前置的一个正式步骤接力

**施工。** 只接一个动作「提交 ACC-1 正式阶段验收」。在真实提交入口核对原任务、需求版本、实际正式启动尝试及必需证据。一次真实失败可以交回诊断和安排复跑，成功判据仍待满足。证据缺失时展示缺项、责任卡和解除条件。其它步骤可照常进行。前置满足后向原下一责任方传送证据引用。手动卡记录待办，有明确续轮授权的自动卡经既有驱动接续。由业务入口保有写入和验收权。

**通过条件。** 只有最后一项有效证据补齐才让正式提交可进入，接力至多一次。接收回执、准备动作与实际写入之间如有暂停、换版、撤销或任务已结束，按新的权威状态复查。重复通知、两 runner 竞争、重启回读及发送结果不明均不可重复提交或重发副作用。提交入口的约束只作用于本任务的当前步骤。已在途动作走原回执对账。主动接力启用需要隔离验收通过及试点授权。[原型等待与恢复证据](../notes/声明式等待-隔离验证-20261120.md#python-原型收口)

## 4. 共用记录与放量判据

每批回报附复跑方式、快照、输入时间截点、权威记录与执行结果。按业务维度关联 `work → 原任务或计划 → 有效需求或目标版本 → 步骤或判据 → 证据`。干预另记策略、事项、动作、实际目标和受理或消费凭据。复用已有字段，缺的字段由实际生产者补。相同的业务状态须持久复用同一事项和动作，去重以有意义的状态变化为准。人工接管、策略撤回和换版时停止未受理的旧动作，已受理的动作按原编号核对。

| 要回答的问题 | 采样与通过条件 |
| --- | --- |
| 有没有更早发现偏离 | 比较首次具备证据的时间、策略首次提出问题、下一次相关派工及随后负责人的裁定。盲回放要在后续纠正公开前，指出缺负责人、缺验证或当前断点。完整、已获授权的计划要能走下去。 |
| 模型有没有更忠实执行 | 按相同任务形态、需求版本和模型路由记有效引用、必做步骤的遗漏、暂缓动作的越序、结论可回读的比例和人工纠正次数。报告样本数与反例。回放验证策略行为，真实试点验证模型表现。 |
| 有没有新空转或误拦 | 必测反例中人工停止后零自动续跑，普通研判与获准并行项零误拦，同一业务状态零重复动作，结果未明零自动重写。正常允许的步骤可继续，正确的前置到齐后接续一次。分别记录模型请求和已实记 token。 |

交付次序为回放、影子评估、隔离动作验证、单 work 单任务主动试点。主动试点先开 B 的定向注入与核证提示，再开已经验证的 C 提示，最后启用 D 的单节点等待。该任务书交付方案和验收要求。改动原型后端涉及 5700 时，按项目规则单独报批。[项目规则](../AGENTS.md)
