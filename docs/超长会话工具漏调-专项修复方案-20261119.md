# 超长会话工具漏调专项修复方案

先解决 `card_007` 在子卡汇报唤醒后「零调用却说已发」的复发。复用现有工具循环和执行回执，在当前轮提示模型先调工具，在交付面把模型研判和实际执行结果分开。读、搜、改、发沿用同一套结果规则。长期记忆和工具结果投影保持既有语义。

## 复发证据

- 11 月 19 日 22:31，`card_007` 收到 `card_013` 的汇报，回复「两条指令已发」。网关记录是 `stop` 和零工具调用，同一回合没有派发。 [22:31 回合](../logs/prompt_card_007_20261119223155.json)
- 22:34–22:35，它先承认上一条只写正文，又声称「三条都已真发」。两跳均为零调用，派发台账为空。 [22:35 回合](../logs/prompt_card_007_20261119223508.json)
- 22:16，用户提醒「没调工具」后，同一 Flash 模型在相近的长上下文条件下产生原生调用和成功回执。现有自然案例可定位故障，无法推出固定的上下文长度阈值。 [22:16 纠正轮](../logs/prompt_card_007_20261119222221.json)

收到汇报触发的是普通内部回合。当前回执检查只覆盖部分专用操作和指令唤醒，所以模型可以零调用直接收口。已有实验曾用正文关键词提取完成声明并自动唤回，后因误触发撤除。这里沿用可信入口与执行事实。 [汇报入口](../src/api/card_tools.py) · [回执检查](../src/api/tool_receipt.py) · [机制沿革](../src/api/prompts.py)

## 一 当前轮提示给出明确的两条路径

由宿主传递真实的汇报来源、汇报引用和本次可用工具。在靠近当前请求的位置加一句短提示，随实际端点协议生成。管理卡可以只回复判断，也可以采取行动。需要查证、修改或下达指令时，先通过本端点支持的工具通道发出实际调用，看到结果再汇报。示例使用自然语言，调用参数以工具 schema 为准。

这项提示先在底座管理卡的汇报唤醒回合验证。用户的正常聊天、显式操作以及其他卡原有行为分别核对。若汇报进入正在运行的回合，随现有插话传递来源信息。判断原回合是否欠某个操作仍由该回合已有的执行要求决定。

## 二 交付状态由执行器生成

管理回合的模型正文作为研判或草稿展示。单独显示一个由工具执行事实生成的本轮结果，流式交付、最终回复和刷新后的历史使用同一结果。无调用时显示「本轮未执行工具」，允许正常交付研判。正文即使写「三条已发」，界面的操作状态仍以系统生成的结果为准。模型继续使用按回执生成的短状态核对接续事项。

| 本轮证据 | 系统呈现 |
| --- | --- |
| 无实际工具派发 | 本轮未执行工具 |
| 实际读取或搜索 | 显示读取或搜索的资源及结果，空匹配如实呈现 |
| 动作遭拒或工具失败 | 显示失败原因及目标 |
| 写入或发送落账 | 显示已写入的目标和真实记录标识 |
| 已落信但运行态未受理，或执行结果暂不可查 | 分别显示「已写入，投递未确认」或「结果待核实」 |

复用现有工具事件和接收方原始记录。以工作、会话、回合、调用、动作及目标对齐，每项单独记结果。工具 `ok` 仅按该工具的实际语义解释。`direct` 的 `delivered=true` 表示运行态下发受理，目标处理完成仍需后续事实。多项动作中一项成功时只展示该项成功。旧回执、其他目标、其他动作都无法满足当前执行要求。

流式上屏需要验证现有 `assistant_text` 和交付路径。模型正文与系统回执使用不同来源标识，确认态在收到事实之前保持未确认。持久化后用实际读取接口验证回执结构，再以相同方式展示。模型输出的同名标记只是正文。

## 三 给明确欠动作的回合一次针对性补救

可信的专用操作、任务步骤或用户明确提交的结构化补执行请求，可以绑定动作、资源与依据。收口时若确认本轮尚未派发它，沿现有循环做一次定向续跳。提示只说明「已知要做什么、目标是什么、当前尚未执行、可用调用通道」。续跳使用同一权限和已有资料引用。有明确失败原因时带上实际原因。结果未知或可能已有副作用时，查询原记录再决定后续操作。

普通汇报中的研判结束可以零调用收口。模型仅在正文说已完成、系统又没有可信的待办对象时，交付执行事实即可。目标和内容要从已确认的任务或用户选择获得。现有 Harness 和回合循环如都能收到失败事实，按同一动作去重，由一处负责续跳。补救只针对这个动作，日常工具循环维持原规则。

若超长输入中的定向续跳仍反复漏调，再单独验证一次面向该动作的精简请求。请求只带授权、对应任务原文或引用、真实回执与当前工具面。一条自然案例只能证明这次行为变化，不能证明长会话的整体漏调率下降。

## 验收

用历史模型输出做离线回放，走真实来源入口和工具执行链，使用隔离数据。实际弱模型在真实超长会话中的表现继续按自然使用观察。

1. 重放 22:31 和 22:35 的原始回复。保持「收到汇报」入口，系统结果为未执行。流式、完整回复和刷新后的界面一致。接收方零新增。
2. 重放 22:16 的真实调用形态。隔离接收方实际写入并取得回执。再测正常研判、查证、搜索、写入和发信，检查每项状态是否准确。
3. 有明确动作要求时，重放首跳零调用、一次纠正后真调、纠正后仍无调用三种情况。核对后两种的真实写入数分别为一和零。另测多项动作部分成功、无关工具成功、写入后回执丢失、用户停止和插话。
4. 正常汇报仅需评审时，原有对话可以结束。引用旧回执、代码示例与写作中的「已发」，均不触发发信或额外唤醒。

回交每项的输入来源、请求标识、模型输出分类、实际调用、接收方事实和最终展示。优先验收「没有执行却显示完成」是否被消除，再跟踪实际超长对话里漏调是否减少。相关通用边界见 [通用修复方案](工具调用与真实回执-修复方案-20261119.md)。
