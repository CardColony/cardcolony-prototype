# 角色机制 5710 · v2 实现说明（2026-10-20）

## 一句话

角色卡不是“普通卡 + 一段 prompt”，而是一种**独立的卡结构**：有管辖域、关注信号、发言契约、升级线、值班态、版本化职责书，以及判断簿/警报簿/同步队列三本台账。它离树、由根卡组阁、按信号同步、每次巡检必须落判词（沉默也落账）。

## 为什么 v1 不算实现

v1 把角色机制做成了“普通卡三块（使命/现状/定论）＋旁路 JSONL ＋专用 prompt”。机制能跑，但：

- 管辖域是自由文本，不可校验、不可去重；
- 关注没有信号，所有新增全量推；
- 判词/警报在 JSONL 旁路，不在卡上、`read_card` 看不到；
- 没有值班态，不能停职/复职/撤岗；
- 职责书没有版本，改了就覆盖；
- UI 只能拼 sidecar，卡结构仍是作业卡那块。

v2 把以上全部改成正式结构。

## 数据模型（`card_db._ROLE_DDL`，幂等建表）

| 表 | 作用 | 关键列 |
|---|---|---|
| `role_profiles` | 角色档案，一角色一行 | jurisdiction / watch / speak_contract / escalation / duty / charter |
| `role_verdicts` | 判断簿 | decision / reason / sources / targets / evidence / auto / superseded_by |
| `role_alarms` | 警报簿 | severity / status / acked_at / corrected_by / supersedes |
| `role_sync` | 待巡检同步队列 | source / from_seq / to_seq / signals / status(pending/consumed) |
| `role_charter_history` | 职责书版本史 | version / text / ratified_by / ratified_at |

`role_profiles` 的 JSON：

```json
{
  "jurisdiction": {"domain": "timeline_contract", "statement": "接口层时间口径", "exclusive_key": "timeline_contract"},
  "watch": {"cards": ["card_002"], "signals": ["turn_completed", "status_changed"]},
  "speak_contract": {"advice_when": ["gap_or_risk"], "alarm_when": ["mutually_exclusive_fact"], "silence_default": true, "max_messages_per_wake": 2},
  "escalation": {"advice_to": "source_card", "alarm_to": "human", "critical_to": "root_and_human"},
  "duty": {"state": "active", "since": "...", "last_wake_at": "...", "pending_sync": 0},
  "charter": {"version": 1, "text": "...", "ratified_by": "root:card_001", "ratified_at": "..."}
}
```

## 卡面六节（不是作业卡三块）

角色卡的 `read_card` 与 UI 渲染：

1. **管辖**：责任域 + 排他键 + 一句话职责
2. **关注**：工作卡 + 关注信号
3. **发言契约**：建议条件 / 警报条件 / 默认沉默 / 单次最多几条
4. **升级线**：建议→谁、警报→谁、严重→谁
5. **值班**：active / suspended / archived；最后巡检；待同步
6. **职责书**：版本 + 批准者 + 版本史

账：**判断簿**（speak/silent、依据、来源、证据、被取代）＋**警报簿**（severity/status/ack/更正链）。

## 生命周期

`create`（根卡组阁，profile 必填）→ `link`（订阅，建线从当前末尾起算）→ `sync`（按信号剪枝，seq 区间进 `role_sync`）→ `wake`（单飞、冷却、忙时延后、失败留队）→ `judge`（必须 `record_verdict`；漏记机械补记 silent）→ `advise`（给关注卡）/ `alarm`（按升级线）→ `correct`（`supersedes` 或 `correct_alarm`）→ `suspend`/`resume`/`archive`（撤岗保留台账，只解关注）。

同步信号：

- `turn_completed`：回合收口（默认）
- `status_changed`：现状块哈希变化（材料自动补当前现状）
- `decision_appended`：第三块哈希变化
- `turn_error`：回合失败

## 工具与 API

根卡专用：`create_role`、`role_watch_cards`、`update_role_profile`、`role_set_duty`。
角色专用：`record_verdict`、`raise_alarm`、`correct_alarm`。
角色仍不能：建子卡、改他人卡、调文件/命令、角色之间通信。

HTTP：

- `GET/POST /api/works/{wid}/roles`
- `GET/PATCH /api/works/{wid}/roles/{rid}`
- `POST /api/works/{wid}/roles/{rid}/check|watch|duty`
- `DELETE /api/works/{wid}/roles/{rid}/watch/{cid}`
- `GET /api/works/{wid}/alarms`
- `POST /api/works/{wid}/alarms/{aid}/ack|correct`

## UI

角色页右栏：值班条 / 立即巡检 / 编辑档案 / 停职 / 复职 / 撤岗；六节结构；判断簿（含证据、被取代）；警报簿（已知/更正/更正链）；职责书版本。
根卡右栏「角色（参谋线）」：角色名 + 责任域排他键 + 一句话职责 + 职责书 → 组阁。
左栏角色行、项目警报红点、导航铃铛。

## 角色权限（不是全权限）

配置里的角色 perms 只有 5 项：`read / edit / read_linked / send_card_message / shadow_write`。
实际下发的工具面 12 件：`read_card / read_memory / read_shadow / read_linked / update_shadow / send_card_message / read_inbox / record_verdict / raise_alarm / correct_alarm / update_status / append_ruling`。

- `edit` 是 **TREE_SWITCH**：离树角色（`parent=""`、不可有子卡）只能写自己；`update_status` / `append_ruling` 即使传别人的 `card_id`，也会被 `policy.check` 的 tree_scope 拒；`edit_card` 不在角色工具面，直接调也被 tree_scope 拒。
- `read` 是同一项目内全局读（正文/影子/记忆），这是唯一宽的地方——跨卡观察者要能取证；不是写权。
- `send_card_message` 只能发给已关注卡；`shadow_write` 只能写自己的影子。
- 没有 `delete / create_child / link / unlink / tools_file / tools_web / plan / manuscript / bash / write_file`。

## 边界

- 角色无否决/拦截权；只建议与警报。
- 角色之间不通信；不做跨项目共享角色。
- 撤岗保留档案与台账，不物理删卡。
- 同步按工作卡回合收口，不按事件逐条推；单批上限 24k 字符。
