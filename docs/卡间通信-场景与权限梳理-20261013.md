> 性质：设计输入（方案前置）。结论标注【事实】【判断】【待裁】三类。

## 〇、一句话结论

现状基础设施只覆盖了**四类场景中的一类半**（同树内、流程触发、一对一、三类消息），
而权限判据**借错了开关**——发信是「向对方档案写 + 起对方回合」的**调用类**动作，
却用 **READ**（读侧）把关，且**判的是收件方、发送方权限从不被查**。
要支撑用户构想（枢纽卡汇聚/分发、状态到达推送、跨树），需要**补齐场景坐标 + 重建消息权限面**。

## 一、场景全景

### 1.1 四维坐标系

任何一次卡间通信都可由四个维度定位：

| 维度 | 取值 | 说明 |
|---|---|---|
| **① 拓扑（发给谁）** | 向上（子→父/祖先）／向下（父→子/后代）／横向（兄弟）／跨树／一对多 | 决定「范围判据」 |
| **② 触发（谁在何时发起）** | 模型回合收口（流程代发）／卡状态到达／人工点击／定时超时／系统自动（回发·补齐） | 决定「触发源」 |
| **③ 意图（消息类型）** | 询问／应答／通知／派单／回执／升级 | 决定「注册表条目」 |
| **④ 处置（收件方怎么办）** | 自动起回合应答／仅入库待人工／转达 | 决定「是否烧算力」 |

### 1.2 具体场景清单（12 条）

| # | 场景 | 拓扑 | 触发 | 意图 | 现状 |
|---|---|---|---|---|---|
| S1 | **向上请示**：子卡遇不确定 → 问父卡 → 父卡答 → 子卡继续 | 向上 | 回合收口 | ask→answer | ✅ 支持 |
| S2 | **向下追问**：父卡问子卡进展/判断 → 子卡答 | 向下 | 回合收口 | ask→answer | ✅ 支持 |
| S3 | **向上汇报**：子卡完成产出 → 通知父卡 | 向上 | 回合收口 | notify | ✅ 支持 |
| S4 | **向下告知**：父卡告知子卡一件事 | 向下 | 回合收口 | notify | ✅ 支持 |
| S5 | **状态到达推送**：卡到某状态（如方案/任务书定稿）→ 自动推给枢纽卡 | 跨树/向上 | 状态到达 | notify | ❌ 缺口（无触发源） |
| S6 | **枢纽汇聚**：项目管理卡收集各卡的产出 | 跨树/一对多 | 状态到达 | notify | ❌ 缺口 |
| S7 | **枢纽分发**：项目管理卡按模块派活给执行卡/验收卡 | 跨树/向下 | 流程 | 派单 | ❌ 缺口（无类型+跨树） |
| S8 | **执行回推**：执行/验收完成 → 回推需求卡 | 跨树 | 状态到达 | 回执 | ❌ 缺口 |
| S9 | **横向协作**：兄弟卡互问（无管辖关系） | 横向 | 回合收口 | ask→answer | ❌ 挡死 |
| S10 | **超时升级**：ask 发出无人答 → 升级到上级 | 向上 | 定时 | 升级 | ❌ 缺口（无超时） |
| S11 | **人工发信**：用户以某卡身份发一封信 | 任意 | 人工 | 任意 | ❌ 缺口（无入口） |
| S12 | **广播**：一条消息给多个卡 | 一对多 | 任意 | 任意 | ❌ 挡死（一对一硬编码） |

**覆盖度**：12 条中 **4 条已支持**（全在「同树 + 回合收口 + 一对一」这一格内）。

### 1.3 现状的能力边界（机械事实）

【事实】四条硬边界把场景锁死在很小的一格：
1. **只能一对一**——`target_id` 单值（`card_tools.py:1126`）
2. **只能同树**——双向 `_is_in_subtree` 判定（`card_tools.py:1162-1164`）
3. **只能回合收口触发**——`schedule` 只在 `_run_message_inner` 段⑥被调（`routes.py:912`）
4. **只能流程发起**——模型工具面已摘除，且无 UI/HTTP 入口

## 二、权限模型

### 2.1 现状诊断（五条问题）

**P1【核心】判据借错开关，且判错了对象。**
【事实】发信权限判据＝`policy.check(current_id, target_id, SWITCH_READ, cards)`。
而 `check(actor, target, switch)` 读的是 **target 的 perms**（`policy.py:221-222`）——
即**检查「收件方能不能被读」，发送方自己的权限从不被查**。
又因所有卡类型都含 `read`，这一关**近乎恒真**——实际只剩「同树」一条在起作用。

**P2【语义错位】发信是「写侧 + 调用」动作，却用「读侧」把关。**
【判断】一次发信实际做了两件事：
- 往**收件方档案**写一块（数据写入——对应 `edit`/`create_child` 那类写权限）
- 起收件方**一个模型回合**（消耗算力——对应 `invoke_tool` 那类调用权限）
按项目口径，它更像 `invoke_tool`（调用工具卡），**不像 `read`**。

**P3【粒度缺失】无方向分权。** 向上/向下/横向用同一条判据（同树即放行）。
但三者的「管辖关系」强度完全不同：
- 向下＝父对子有天然管辖（同 `create_child`/`edit`/`delete` 的树作用域）
- 向上＝子对父的汇报/请示（协作必需，用户 10-09 20:24 已裁定）
- **横向＝无管辖关系**——兄弟之间互发**没有任何机械依据**，理应默认关门

**P4【粒度缺失】无消息类型分权。** `msg_notify`（只需收下）与 `msg_ask`（强制对方作答、烧算力）
在权限上不作区分。

**P5【结构缺失】无「发起方身份」维度、无跨树通道。**
模型/流程/用户/系统四种发起方目前不分；跨 work 因 `cards` 表是单 work 的而彻底不可达。

### 2.2 应有模型（提案）

**核心原则**：发信是**调用类**动作，应按「调用类」分权——**给消息一个自己的开关，不借 READ**。
沿用项目既有机制（开关词汇表 + 配置化 + 建卡固化 + 树作用域独立），做三件事：

#### ① 能力开关（发送方 / 收件方各一个）

在 `src/permissions/policy.py` 的 `SWITCHES` 加两个常量（**加开关＝代码加常量 ＋ 配置用起来**）：

| 开关 | 含义 | 落点 |
|---|---|---|
| `msg_send` | 这张卡**能发出**卡间消息 | 发送方能力面（决定工具/接口可不可用） |
| `msg_receive` | 这张卡**能被发消息**（能被写入档案） | 收件方能力面 |

> 可选再加 `msg_wake`：**能被调起回合**（`msg_receive` 只入库、不烧算力）。
> 这解决「通知类消息不该无条件起对方回合」的资源问题——把「收信」与「被调起」拆开。

#### ② 范围判据（独立函数，照 `_is_in_subtree` 先例）

方向由**树结构机械判定**，与类型分权正交：

| 方向 | 机械判据 | 默认 |
|---|---|---|
| 向下（父→后代） | `_is_in_subtree(sender, target)` | **放行**（同管辖域） |
| 向上（子→祖先） | `_is_in_subtree(target, sender)` | **放行**（协作必需） |
| **横向（兄弟/同树非同链）** | 双向皆不命中 | **默认关门**，需显式开关 |
| 跨树 | `cards` 表不含 → 结构上不可达 | **关门**（除非另开通道） |

横向放行用一个配置开关表达：`msg_peer`（默认不配＝关）。

#### ③ 判据顺序（对齐既有 `check` 的两级结构）

```
发信判据 = 发送方有 msg_send
        ∧ 收件方有 msg_receive
        ∧ 方向在允许集内（向下/向上放行；横向需 msg_peer）
        （跨树：结构不可达）
```

两态同记打点（照 `check` 的 `granted true/false` 口径），不做二次判定。

### 2.3 配置形态（示例，`config/permissions.json`）

```jsonc
"rd_project": {
  "project":     [..., "msg_send", "msg_receive"],           // 根卡：可发可收（上下）
  "sub_project": [..., "msg_send", "msg_receive"],           // 子项目卡：可发可收
  "tool":        ["read", "edit", "delete", "plan", "shadow_write",
                  "msg_receive"]                              // 工具卡：只收不发
},
"research_project": {
  "project": [..., "msg_send", "msg_receive"],
  "topic":   [..., "msg_send", "msg_receive"]
}
```
（横向放行＝在某类型上加 `msg_peer`；默认全不加＝横向全关。）

### 2.4 与现状的兼容

- 现有 4 类场景（S1~S4）在「上下方向 + 流程触发」下**照旧放行**（只要配置补上两个开关）。
- 存量卡需 `version+1` ＋ 跑 `scripts/refresh_perms.py` 刷新 `perms`（既有机制，幂等）。
- 发送方权限此前从未被查——补上后**可能出现新的拒绝**（原先靠「同树」混过），需评估存量行为。

| 要补的 | 可复用的 | 需新增 |

## 四、决策点（需用户裁定）

> 以下每条都会实质改变设计走向。**先定这几条，方案才写得下去。**

**D1｜权限粒度到哪一层？**
- (a) 只加 `msg_send` / `msg_receive` 两个开关（最小）
- (b) 再加 `msg_wake`（收信与烧算力分开）
- (c) 再加方向开关 `msg_peer`（横向显式授权）
- **我的建议：(c)**——三者恰好覆盖 P1~P4 四条问题，且都是既有机制的自然延伸。

**D2｜横向（兄弟）通信，开还是不开？**
默认关门是安全的；但「两个子项目卡有依赖」是真实需求。开＝加 `msg_peer`；不开＝靠父卡中转。

**D3｜「状态到达」的「状态」是什么？**
现状卡状态机只有 `active → completed`（`card_type_registry.json:112`）。
用户构想里的「需求/方案/任务书定稿」**不是卡状态**，而是内容块或工具卡产出。
→ 需要先定义：**用什么作为「推送触发信号」？**（卡状态迁移？工具卡收口？内容块写入？）

**D4｜跨树通信要不要做？**
「真·全局枢纽卡」需要跨 work 通道，这是**架构级**改动（`cards` 表按 work 隔离）。
若暂不做，枢纽卡方案退化为「每棵树内一张」（即之前 18:5x 的裁定方向）。

**D5｜发起方身份要不要进判据？**
现状流程发起、以 `from_id` 的身份判权。若要开放「用户手动发信」，
用户以哪张卡身份发、是否受该卡权限约束，需要一条明规则。

**D6｜消息类型要不要扩？**
派单/回执/升级 三类是枢纽卡场景的刚需（S7/S8/S10）。
扩＝注册表加条目（零代码）；但每类的**处置语义**（回不回、超时怎么办）要逐类定。

---

## 五、我的初步判断（供参考）

1. **优先修 P1/P2**（借 READ + 判错对象）——这是**权限漏洞**，不修则后面所有场景都建在沙子上。
2. **权限按「调用类」重建**（`msg_send`/`msg_receive`/`msg_peer`），而不是继续借 READ。
3. **横向默认关门、跨树暂不做**——先把「同树上下」这条线做扎实。
4. **D3（状态定义）是枢纽卡场景的真正卡点**——比权限更靠前，建议先想清楚。
