## 2. 第一批连接池隔离（procs.py）

### 修了什么
- **relay 与 sse 分池**：原来 `_forward`（浏览器转发+卡级 SSE 直通）与工作级扇入泵共用 stream 池——订阅者常驻连接占满池会把进度等普通转发饿死。现四池：`short`（扇入 30s 语义）/`relay`（普通转发+卡级流，64/16）/`sse`（常驻泵 32/32，`keepalive_expiry=None`——连接由泵退出关闭，不被空闲过期拆掉）/`ctl`（模型回合长任务）。
- **fanin 客户端预热**：客户端族建好即对每台 runner 发轻量 GET 把 keepalive 连接预建进池。
- **SSE 泵错峰启动**：泵按序号错开 50ms，拆掉一次性 SYN 连接风暴。
- **服务循环 B 迟滞仪表**：`start_lag_monitor(loop_b, serving=True)`；`/api/health` 新增 `serving_loop_lag_ms`。

### 占满场景复验（`scripts/perf_batch1_flood_test.py`）
- 复跑：`PYTHONPATH=. python scripts/perf_batch1_flood_test.py --base http://127.0.0.1:5900 --n-sse 10`（10 订阅 × 4 runner = **40 条常驻泵连接 > sse 池上限 32**，真占满）
- 预期：SSE 占满 sse 池时，nav/running（short 池）、progress（relay 池）、timeline（本地）全部毫秒级返回；SSE 流健康收帧。
- 实际（终版两轮 + 返工前一轮，共 3 次）：**PASS**——SSE 期 nav P50 15.6-17.6ms、timeline P50 9.2-12.5ms、progress P50 12.6-14.7ms；每轮收到 60-128 行 SSE 帧、err=无。
- **遗留（如实登记）**：Windows loopback **SYN 丢弃窗口**未根除——SSE 连接风暴后的第一次现场新建 TCP 偶发秒级等待（复验记录：20.4s → 17.0s → 预热+错峰后 1.8s/3.9s，量级与频率双降）。runner 侧 access log 实证：`22:42:59.142 nav ×3 ms=0`、`22:43:16.165 ms=17024`——三片秒达、第四片 17s 后才**到达 runner**（处理仅 0ms）＝卡在连接建立（SYN 重传），非服务端慢。预热（连接预先建好）+ 错峰（拆风暴）是应用层全部可用手段；彻底根除需系统级 TCP 配置，超出本批范围。
- B 迟滞仪表读数：占满期间 `serving_loop_lag_ms` 恒 ≤16ms ⇒ web 循环本身不被 SSE 挤死（定责依据）。
- 证据：`agent_perf_iso/logs/server.log` 的 `[procs] fanin` 行（逐片毫秒）、`logs/access_log.jsonl` 时序对照、flood 探针输出、`kinds=short/relay/sse/ctl verify_bypass=True` 族建行。
