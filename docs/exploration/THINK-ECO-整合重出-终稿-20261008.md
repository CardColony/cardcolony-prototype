## 1. 功能背景

用户 2026-10-08 09:49 令：把信息流本次改造的落地方案做完整——此前方案不完整（用户点名要的「逐字流」被标 Phase 2 默认不做；长请求下反馈可见性无兜底；主模型慢未治理），必须重出覆盖这三项的落地方案。

**需求级铁令**：需求范围与取舍只由用户定。「逐字流」（模型输出逐字显示，像 ChatGPT/DeepSeek）是用户点名要的，必须包含进本方案，不得标成可缓办、不得默认不做、不得再让用户拍板要不要。技术实现（怎么做、参数、性能取舍、gateway 流式分支怎么解）由 agent 自己扛、自己定，不推回用户。

**为什么做（三个缺口，全挂实测证据）**：

**缺口1 · 逐字流被砍（需求级）**：用户点名要的「逐字流」标成 Phase 2 默认不做、未征求用户。实证：kimi-k3 默认请求 content=null、全部输出在 reasoning 字段（Nous 实测）——即使事件级，用户也看不到模型在打字。需求级铁令已立：逐字流必做。

**缺口2 · 长请求反馈可见性无兜底（体验级）**：kimi-k3 单次主模型调用 latency_ms=279500（4.6 分钟，model=main）；用户 09:21 一条消息到 09:46（25 分钟）仍在工具循环未结束、无最终回复；刷新补不出状态（超长请求「进行中」标志在服务端不可靠）。「发消息即时可见＋刷新补态不再丢」必须纳入验收。

**缺口3 · 主模型可用性未治理（技术级，我拍）**：kimi-k3 在 Nous 端点默认 reasoning effort=max 全开致极端慢（与直连轻请求 12.2s 差 23 倍）；旧验收无端到端时长判据。实测 Nous 支持 reasoning 降档（reasoning_tokens 2→0、正文恢复）——降档即可拉回秒级。

## 4. 方案正文（实现设计；内含「全日志打点」小节）

### 设计点 A · 逐字流：gateway 双增量解包（缺口1 核心）

**改动锚**：src\model_gateway\gateway.py stream_call（L502）；只解 delta.content 处（L563）。

**设计**（R-01 修正后）：
- `stream_call`（L561-568）chunk 解包改为 **delta.reasoning 与 delta.content 都解、分别 yield**，不混流。yield 结构升级：`{"chunk_type": "reasoning"|"content", "text": ...}`，兼容旧 `{"chunk": ...}` 调用方。
- 调用参数补 `on_reasoning` 回调（与既有 on_status 并行），供上游把思考增量推入事件流。
- **不改**：`call`（非流式）路径、finish 检测、续写 Completable 判定（L518 注释）——只加增量出口，不破坏现有完成语义。
- **兜底**：供应商只回一种增量时（content=null 只回 reasoning），空流不报错、前端不把思考误当正文。

**逐字流的定性（修正 R-01，技术项我拍）**：核心是「像 ChatGPT 一样看到打字」＝**正文字流（content chunk 逐字蹦）**。思考流是**有则显示、无则空**——降 reasoning 后思考字会很少或没有，但这不损害逐字流的核心效果（正文仍在逐字打）。**不再要求"思考流必须丰富"**，与设计点 B（降 reasoning）自洽。

### 设计点 B · 可用性治理：kimi-k3 reasoning 降档（缺口3，技术项我拍）

**改动锚**：config\models.yaml main 段；gateway extra_body 透传（L552）。

**设计**：
- models.yaml main 段 extra_body 加降思考参数，使 kimi-k3 单次调用从 279.5s 降至秒级。Nous 实测两套写法均返回正文（顶层 reasoning_effort=low 时 reasoning_tokens=2、reasoning.enabled=false 时=0）。
- **【施工前提·R-02 消化】落地前必须先探针实测 extra_body 的两套写法（嵌套 reasoning.effort vs 顶层 reasoning_effort）在 models.yaml 的 extra_body 透传路径里哪一种真生效**，以实测命中者为准写入配置；不确定前不写死。
- 降档档位（low/disabled）属性能质量取舍，我拍：优先 `low`（保部分推理能力）；若仍慢则 `disabled`。
- 效果：reasoning_tokens 2→0 实测，正文恢复，消息端到端可及。

### 设计点 C · 反馈可见性：正文字流持续推流 + 刷新补态加固（缺口2）

**改动锚**：static\stream.js（双路渲染）；static\workspace.js EventFlow.start（L779/L903）、attachRunningState（L739）；src\api\event_stream.py。

**设计**：
- **前端双路流**：stream.js 升级渲染器——📄 正文字逐字蹦（主题）+ 🟡 思考字有则显示；工具轮保持事件级🔧；结束折叠。
- **发消息即时可见**：send/resend 发 POST 即 EventFlow.start（代码已在 L779），接 content chunk → 正文流 1 秒内出现。
- **刷新补态加固**：/progress 活跃判定对「超长且仍在推进」的请求不 stale；restoreFromHash 刷新 from=0 重放正文流＋过程卡＋最终回复。
- **事件并入**：逐字流 chunk 作为新事件类型进 event_stream.py（17 类加 reasoning_chunk/content_chunk，或独立流）——以 17 类本体论不被破坏为准。

### 设计点 D · 事件级机制保留（不破坏既有）

**改动锚**：src\api\event_stream.py（17 类）、红线。

**设计**：既有 17 类事件原样保留，逐字流转入独立流不与事件混；红线不动（事件不进模型输入、POST/T10/T14 零改动、works 零触碰）。
