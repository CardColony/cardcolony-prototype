## 1. 功能背景

〔挂 C-001/C-002/C-003/C-004/C-005/C-006/C-007/C-008/C-009/C-010〕

用户 2026-10-08 09:49 令：把信息流本次改造的落地方案做完整（C-001）。此前方案不完整——用户点名要的「逐字流」被标 Phase 2 默认不做；长请求下反馈可见性无兜底；主模型慢未治理（C-002），必须重出覆盖这三项的落地方案。

**需求级铁令（C-003/C-004）**：需求范围与取舍只由用户定。「逐字流」（模型输出逐字显示，像 ChatGPT/DeepSeek）是用户点名要的，必须包含进本方案，不得标成可缓办、不得默认不做、不得再让用户拍板要不要（C-004）。技术实现（怎么做、参数、性能取舍、gateway 流式分支怎么解）由 agent 自己扛、自己定，不推回用户（C-005）。

**为什么做（三个缺口，全挂实测证据）**：

**缺口1 · 逐字流被砍（C-004/C-005）**：用户点名要的「逐字流」标成 Phase 2 默认不做、未征求用户。实证：kimi-k3 默认请求 `content=null`、全部输出在 `reasoning` 字段（Nous 实测，reasoning_tokens 占满额度）——即使走事件级，用户也看不到模型正在打的字。需求级铁令已立：逐字流必做。

**缺口2 · 长请求反馈可见性无兜底（C-006/C-007/C-008/C-018）**：kimi-k3 单次主模型调用 `latency_ms=279500`（4.6 分钟，model=main，_boot_5700_out.log）；用户 09:21 一条消息到 09:46（25 分钟）仍在工具循环未结束、无最终回复；刷新补不出状态（超长请求「进行中」标志在服务端不可靠，workspace.js restoreFromHash→attachRunningState 活跃判定失效）。「发消息即时可见＋刷新补态不再丢」必须纳入验收（C-007）。

**缺口3 · 主模型可用性未治理（C-009/C-010）**：kimi-k3 在 Nous 端点默认 reasoning effort=max 全开致极端慢，与直连轻请求 12.2s 差 23 倍；旧验收无端到端时长判据。技术项由我拍（C-010）——实测 Nous 支持 reasoning_effort=low 与 reasoning.enabled=false（reasoning_tokens 2→0，正文恢复），降档即可把单次调用拉回秒级。

## 2. 项目位置与接口规范（内含「输入接口」「输出接口」两小节）

〔挂 C-011~C-017/C-019〕

### 输入接口

- **逐字流输入（C-012/C-013/C-014）**：模型调用启 `stream=True`（gateway L543 已开）+ 传 `on_chunk` 回调；chunk 解包须同时取 `delta.reasoning`（思考字）与 `delta.content`（正文字）。实证：kimi-k3 content=null、reasoning 有值——只解 content 则逐字流空转。
- **降 reasoning 输入（C-012）**：models.yaml main 段 `extra_body` 加 `reasoning_effort: low`（或 `reasoning.enabled: false`）；Nous 实测 low/disabled 均生效，reasoning_tokens 从占满降到 2/0。
- **刷新补态输入（C-015/C-016）**：`/progress` 活跃判定 + `EventFlow.start(from=0)`；长请求下须保证活跃判定不因超时 stale。

### 输出接口

- **逐字流输出（C-004/C-013）**：前端双路逐字显示——🟡思考字实时蹦 + 📄正文字实时蹦；工具轮仍事件级🔧；结束折叠。
- **可用性输出（C-009/C-010）**：kimi-k3 单次调用从 279.5s 降至秒级（降 reasoning 实测生效）；端到端消息可及。
- **反馈输出（C-007/C-018）**：发消息即刻见思考流在动（≤1s 首 chunk）；刷新 from=0 补回过程与最终回复。
- **不动对象（C-019）**：POST/T10/T14 契约零改动；事件不进 session/prior/模型输入；17 类事件本体论不破坏；works 数据零触碰；凡称落盘必回读核验附实测 SHA；不走子代理。

## 4. 方案正文（实现设计；内含「### 全日志打点」小节）

〔挂 C-011~C-017/C-019/C-021/C-022〕

### 设计点 A · 逐字流：gateway 双增量解包（缺口1 核心）

**改动锚**：`src\model_gateway\gateway.py` `stream_call`（L502）；只解 `delta.content` 处（L563）。

**设计**（C-004/C-005/C-012/C-013）：
- `stream_call`（L561-568）chunk 解包改为：`delta.reasoning`（思考增量）+ `delta.content`（正文增量）**都解、分别 yield**——思考增量与正文增量不混流。
- yield 结构升级：`{"chunk_type": "reasoning" | "content", "text": ...}`；兼容旧 `{"chunk": ...}` 调用方。
- 调用参数补 `on_reasoning` 回调（与现有 `on_status` 并行），供上游 routes/simple_service 把思考增量推入事件流。
- **不改**：`call`（非流式）路径、finish 检测、续写 Completable 判定（L518 注释「由 orchestrator 在收到最终结果后处理」）——逐字流只加增量出口，不破坏现有完成语义。
- 兜底：供应商若只回一种增量（如 content=null 只回 reasoning），空流不报错、前端不把思考误当正文。

### 设计点 B · 可用性治理：kimi-k3 reasoning 降档（缺口3，技术项我拍）

**改动锚**：`config\models.yaml` main 段。gateway `stream_call`/`call` 已支持 `extra_body` 透传（L552）。

**设计**（C-009/C-010/C-012）：
- models.yaml main 段 `extra_body` 加：
  ```yaml
  extra_body:
    reasoning:
      effort: low
  ```
  （Nous 实测支持 nested `reasoning.effort`；备选顶层 `reasoning_effort`——以部署时实测为准，两者都先探针验一次）
- 效果：kimi-k3 单次调用从 279.5s/次降到秒级（reasoning_tokens 2→0 实测），消息端到端可及。
- **保留质量取舍权在我**：若 low 质量不可接受再调 medium/默认，属性能质量取舍、我拍，不推回用户。

### 设计点 C · 反馈可见性：逐字流持续推流 + 刷新补态加固（缺口2）

**改动锚**：`static\stream.js`（双路渲染）；`static\workspace.js` EventFlow.start（L779/L903）、attachRunningState（L739）；`src\api\event_stream.py`（事件并入）。

**设计**（C-006/C-007/C-008/C-015/C-016/C-018）：
- **前端双路流**：`stream.js` 升级渲染器——🟡 思考流（reasoning chunk 逐字蹦）+ 📄 正文流（content chunk 逐字蹦）；工具轮保持事件级🔧；结束折叠。
- **发消息即时可见**：send/resend 发 POST 即 EventFlow.start（代码已在 L779），接双路 chunk → 思考流 1 秒内出现。
- **刷新补态加固**：`/progress` 活跃判定对「超长且仍在推进」的请求不 stale（长请求下活跃态须延续）；restoreFromHash 刷新 from=0 重放思考流+正文流+过程卡。
- **事件并入**：逐字流 chunk 作为新事件类型进入 event_stream.py（17 类加 `reasoning_chunk`/`content_chunk`，或独立流）——以 17 类本体论不被破坏为准。

### 设计点 D · 事件级机制保留（不破坏既有）

**改动锚**：`src\api\event_stream.py`（17 类）、红线（事件不进模型输入）。

**设计**（C-019）：
- 既有 17 类事件（run_start/context/tool_call/.../fastlane_route/card_op）原样保留，逐字流转入独立流，不与事件混。
- 红线不动：事件不进 session/prior/模型输入；POST/T10/T14 零改动；works 数据零触碰。
- report-only 边界维持（C-020）：本方案产出落地方案，施工在后续 taskbook+执行。

### 全日志打点

〔挂 C-021/C-022〕

**设计**：为逐字流与可用性治理加结构化打点（只写日志、不参与判定、不设闸）：
- **逐字流**：双增量解包命中（reasoning/content 各自 chunk 数、总 token）、推流延迟（首 chunk 距 request 秒数）。
- **可用性**：每次 model=main 调用 latency_ms（已有）、reasoning_tokens（补）、extra_body 生效与否。
- **刷新补态**：/progress 活跃判定结果、from=0 重放是否成功补齐。
