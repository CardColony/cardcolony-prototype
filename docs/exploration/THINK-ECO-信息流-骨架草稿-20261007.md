## 一、目标与背景

**用户原话（逐字，最高依据）**：
> 「我希望整个系统，卡片对话的信息流，能像deepseek harness那样，每一步调用每一个中间环节，都对我可见，像这些成熟的agent一样，流式展示在对话里」
> 「这应该涉及到整个对话流的完全改造」

**要解决什么**：卡片对话现在是黑盒。一轮对话内部依次发生配对、六区装配、工具循环、三席后置、统合、T14 拼接、建卡、落盘（`routes.py:388-759`），用户能看见的只有一条 2 秒轮询的进度条（8 个阶段标签，`progress.py` 全文 24 行）。

**六处断点（每条有代码依据）**：模型每轮调用无上报（`routes.py:486-509`）；工具结果只记三键无参数无正文无耗时（`631`）；三席正文 `meta["text"]` 已到调用方却被剔（`simple_service.py:198`／`routes.py:756-757`）；上下文装配不可见；抢救／T14／建卡仅服务端日志；刷新零重放（`workspace.js:740-752`）。

**一句自证**：`routes.py:644` `user_prompt = "工具结果已返回。"` —— 这就是"六个字"的代码真身。

**不做会怎样**：用户无法判断 agent 干了什么、值不值得信；只能等结束后从摘要灰条猜。

```
run_start(pair_id) · context(regions, condense) · round_start(round, purpose) ·
round_end(latency, chars, tool_calls, finish_reason) · rescue ·
tool_call(name, target, args) · tool_result(ok, bytes, text) ·

deliver(T14 branch) · proposal(created) · done(pair_id, model) · error(msg) · ping
```

Schema：`{"seq": n, "ts": …, "type": "…", "data": {…}}`；seq 单调；`run_start` 清零重放。

### 4.1 事件流载体：新建 `src/api/event_stream.py`

**（a）事件日志**：按 `(work_id, card_id)` 分桶的内存环形日志，容量上限 **300 条**；单条正文 **8KB** 截断并置标记位。截断阈值依据是 `routes.py:639-642` 的 `tool_full_texts` 单条可能含 `edit_card` 全文，不设上限则单条可达数十 KB。

**（b）订阅者扇出**：每订阅者一个 `asyncio.Queue`；`emit()` 同步写日志并向所有队列投递；`subscribe(from_seq)` 为异步生成器，先重放日志中 `seq >= from_seq` 的部分，再转入实时投递。断连时从订阅者表移除。

**（c）生命周期**：新请求 `run_start` 时清本桶日志（与 `progress.py` last-write-wins 同语义，见 `progress.py:16`）；`ping` 事件按固定间隔产生以保活。

**（d）单进程前提的继承**：`progress.py:12` 是模块级字典、docstring（`progress.py:5`）明示「单进程 uvicorn 内存态」；本模块照同一前提实现，不新增多 worker 破绽。

**（e）测试可重置入口**：模块级内存字典不在 `conftest.py` 重置之列（`conftest.py:36-80` 只重置模块级常量与 `model_service._gateway` 于 `78`）。故本模块的日志表与订阅者表须以**可 patch 的模块级名称**暴露，供测试重置——依据是既有先例 `test_uiopt_e2e.py:27-29`。

**（f）与既有归档器的关系**：`src/infra/trace_recorder.py`（172 行）具备「一轮一文档、append-only」能力（`40`／`56`／`83`／`149`），但落 `traces/{trace_id}.md`（`17`）、事后读、且全仓 grep 该模块名 7 处命中全在自身内部（零生产调用方）。本线另起 `event_stream.py` 的理由：前者是**落盘事后归档**，本线要的是**内存实时流**；两者目标形态不同。
