# 惰性新建 · 重写方案 v2 —— 先出画面 = 真界面

- 日期：2026-10-17
- 取代：《惰性新建-先出画面后落库-任务书-20261017.md》中的 A 场景（新建项目）设计
- 保留：B 场景（建卡，2026-10-17 10:11 用户定稿）实现不动
- 缘起：用户实测骂出的两个缺陷——①点「＋新建项目」给了空白画布（"你他妈直接进根啊"）；②进了根卡对话界面是假的，发对话零反应，必须刷新
- 本方案纪律（2026-10-17 11:31 立规的第一次实践）：每个环节写死「用户看到什么 / 系统做什么 / 怎么证明做对了」。证明方法写不出的环节不许动工。

## 一、总原则（三句话，压住一切细节）

1. **草稿 = 身份未定，不是功能残缺。** 草稿页上每一个用户看得见、点得到的控件，行为必须与真项目页完全一致。禁止任何「草稿期置灰/跳过/静默无反应」——那是假界面的制造方式。
2. **先出画面 = 出真画面。** 新项目的真画面就是根卡对话页（本产品 13/13 个项目的主体工作方式都是根卡对话）。空白画布对新项目 = 零内容零入口的中间态，用户从不需要，废弃。
3. **动作先落库，再走原路径。** 用户任何产生数据的动作（发消息/改名/规则保存/关系变更/现状更新），第一步 ensurePersisted 换真身，第二步走**原有代码路径，一字不动**。原有路径经过生产长期验证，重写它们 = 重造 bug。

## 二、用户旅程逐环节（方案的根）

### A1 · 点「＋新建项目」 → 直接进根卡对话页

| 件 | 定义 |
|---|---|
| 用户看到 | **零等待**进入根卡对话页：与真项目根卡页**逐控件一致**的界面。标题「新项目」占位、可编辑；消息区空；**光标已落在输入框**（点＋的人就是来说事的）；左栏照常在（草稿期左栏不含此项目）。URL = `/work/draft/card/draft` |
| 系统做什么 | 跳转 `/work/draft/card/draft`。页面装配**全量跑**（绑定输入框/发送/EventFlow 容器/SSE 容器），**只守卫网络请求**（不 getCard、不拉 timeline、不建 SSE——因为后端还没有这张卡）。零 POST |
| 怎么证明做对了 | ①点＋到界面可打字 ≤200ms；②此过程 Network 零 POST；③逐控件对照：草稿页与真项目根卡页的可见控件集合、可点行为集合**相等**（脚本断言，非肉眼） |
| 消失的步骤 | 旧旅程的「草稿画布→找入口→弹窗填标题→进对话」整链删除。点＋时用户还没表达任何内容，先要标题 = 先给用户出一个问题；直接进对话 = 直接听他说。想改标题随时改，改名本身触发落库 |

### A2 · 发第一条消息（上轮死掉的那条，本次核心）

| 件 | 定义 |
|---|---|
| 用户看到 | 点发送 → **消息立刻上屏**（乐观 UI 本来就有）→ 模型回答流出来。全程界面不重载、输入框内容不丢；URL 在过程中**静默**变成 `/work/{wid}/card/{cid}`；落库完成后左栏出现这个新项目（名字=当前标题） |
| 系统做什么 | send() 第一步 `await ensurePersisted()`（带锁、复用同一 Promise，防连点双 POST）：POST /api/works（title=当前标题，空则「新项目」）→ 写 WORK_ID 与 window.__WORK_ID__ → replaceState 真地址 → SSE/轮询通道此刻用真键建立。第二步：**原有 send 流程一字不动**（乐观上屏/EventFlow/pullUserBubble/自愈轮询四通道此时已全是真键） |
| 怎么证明做对了 | **对照测试**：同一沙箱、同一动作（打字→点发送→消息上屏），草稿页跑一遍、真项目页跑一遍——上屏时序、请求序列、错误数**零差异**。这是「真界面」的终极证明：不是像，是不可区分 |
| 边界 | 沙箱禁模型调用，验到「消息上屏 + POST 发出 + 通道建立 + URL 已切真」为止；模型回答那段留给用户生产亲验（V10） |

### A3 · 草稿期改名（含一切数据动作）

- 用户看到：改标题 → blur → 左栏出现该项目（所改的名），「未保存」标消失。
- 系统：blur 触发 ensurePersisted → PATCH 真身。
- 证明：只改名不发消息 → works +1、目录名/卡名 = 所改值（沙箱实测）。
- **同类动作全清单核对**（阶段 2 完成标准）：对话页每一个会写数据的控件——发送、标题、使命、现状、关系增删、规则卡保存、更新现状、需求确定——逐个核对已接 ensurePersisted，一个不漏（产出核对表，验收要看）。

### A4 · 什么都不做就离开 = 蒸发

- 打了字没发、关页/切走 → works 计数不变、works/ 零新目录。不弹确认（维持 D5）。
- 已打未发的文字随刷新蒸发——用户已接受（D5），**不拦 beforeunload**，方案明示。

### A5 · 失败不吞

- ensurePersisted 失败（服务挂/500）→ toast「创建失败，输入已保留」→ 输入不清空 → 再点发送重试整链。
- **上轮验收放行未测的就是这类，本次 V6 硬测**（mock 500 + 恢复重试）。

### B 场景（建卡）——不动

维持 2026-10-17 10:11 定稿：先出画面（零等待进该卡对话页）+ 后台立刻落库 + 静默换真 URL。已验收（烟测 G + 我方复跑 20/20），零改动。

## 三、旧实现为什么错（根因，不是 bug 罗列）

1. **空白画布**：我把「先出画面」实现成「先出一个中间态页面」——给用户造了一个他不需要的中间态。错在把「画面」理解成页面跳转的产物，而不是「用户接下来要做的事的那张界面」。
2. **假界面（发对话零反应）**：我把草稿实现成「每个模块认识 draft，然后**跳过自己的功能**」——open() 早退、SSE 不建、通道不立。守卫式跳过的必然漏洞：被跳过的正是用户要用的功能。send 的四条并行通道全部以真实 (WORK_ID, cardId) 为生，draft 身份下它们无从工作——「发了没反应、刷新才活」是这个结构的**必然产物**，不是哪一行代码写错。
3. **结构结论**：守卫的对象搞反了。该守卫的是**网络请求**（后端还没有这张卡），不该守卫**界面装配与用户动作**。v2 全部设计从这一句推导。

## 四、实现设计

### 结构原则

- 草稿态进入页面的初始化 = 真初始化路径 + 网络请求层守卫。即：DOM 装配、事件绑定、容器创建**全量执行**；getCard/timeline/SSE/轮询等以真身为前提的请求**跳过**，ensurePersisted 完成后补建。
- 落库切换三动作原子化：写 WORK_ID（本地变量 + window.__WORK_ID__）、replaceState 真地址、通道换真键——三件在同一 Promise 完成点执行，执行完才放行用户动作的后续步骤。
