## 一、这件事是什么（白话）

**症状**：你在对话里发了新消息，等半天没有回复；等回复出来之后，**它接的却是你前面那句话**——像是没看见你最新说的。

**已核实的现场**（`works/work_001/sessions/session_005.md` 逐字）：

```
L112  role: user       15:54:20.041947   ← 你问
L117  role: user       16:11:38.340497   ← 你又问了一遍（等了 17 分钟没动静）
L122  role: assistant  16:15:53.464844   ← 回复 A 落盘（答的是 15:54 那句）
L163  role: assistant  16:16:24.757309   ← 回复 B 落盘（答的才是 16:11 那句）
```

**文件里的顺序，就是这四条的落盘顺序。** 所以你和下一轮模型读到的样子是：

```
user: 16:11:38        ← 你最新那句
assistant: 16:15:53   ← 而这条答的是早 17 分钟那句
assistant: 16:16:24
```

**「回复不接最新消息」——症状从这里来。**

## 三、因果链（根因与加重项分层）

### 根因① · 没有配对标识 —— 全库零命中

```
搜 request_id | message_id | pair_id | reply_to  （src/ 全部 .py）
→ 命中 0
```

**一条回复不携带「我答的是哪一句」这个信息。** 回复与提问之间只有「谁先写进文件」这层隐式关系——**一旦有两条在途，这层关系就不成立。**

### 根因② · 写文件无锁 —— 真锁 0 处

`src/storage/session_store.py:66-67` 逐字：

```python
async with aiofiles.open(path, mode="a", encoding="utf-8") as f:
    await f.write(block)
```

**「追加模式打开 → 写 → 关」，中间无任何互斥。** 全文搜 lock，命中的两处都是 `block` 这个单词里的字母，**真锁 0 处**。

**两条请求同时在跑时，谁先跑完谁先落盘——落盘顺序 ≠ 因果顺序。**

### 根因①＋② 合起来，就是现场那四条

请求 A（15:54 发起，跑 21 分钟）、请求 B（16:11 发起，跑 5 分钟）。**落盘顺序与发起顺序不一致，而回复又不带标识——读者无法分辨。**

### 加重项③ · 重发会重复落盘

前端重发时**不重复显示你那句话**（你以为只发了一次），但**后端 `:346` 会再落一条**。**记录里「你的提问」比实际次数多。**

### 加重项④ · 历史只留两字段，工具痕迹全被剥掉

`routes.py:355` 逐字：

```python
prior_for_gateway = [{"role": m["role"], "content": m["content"]} for m in prior]
```

**只取 role 和 content。** 工具调用、工具结果、观点——**一样都不进历史**。

**后果**：模型下一轮不知道上轮调过什么工具、拿到了什么——会重复劳动，或答得像失忆。**这也是「答非所问」的来源之一。**

### 加重项⑤ · 慢（不是 bug，是触发条件）

单次调用跑几分钟是常态（三席并发＋统合＋工具循环，无闸）。**慢本身不是缺陷，但它是错位的触发条件**——等急了才重发，重发才产生两条在途。

### 已修项 · gateway 的历史拼装顺序（不在本方案范围）

`src/model_gateway/gateway.py:111-116` 逐字：

```python

# 原版将prior_messages追加在后（服务于工具续写场景），对话场景会答非所问

    messages.extend(prior_messages)
```

**历史在前、当前提问在后——顺序已经是修复态。** 上游文档把它当隐患列出，**实际它已经改过一版。此条不进本方案。**

## 五、修法六条（每条写死改哪、怎么改、什么效果、怎么验）

### 4.1 加配对标识（对应根因①）

**改哪**：`src/storage/session_store.py` 的消息格式 ＋ `src/api/routes.py` 的主链路

**怎么改**：

1. **生成点**：`src/api/routes.py` 主链路读取历史之前（`:343` 之前），生成一个本次请求的标识，**形态＝UUID4 十六进制串**（`uuid4().hex`），避免可猜测与冲突。
2. **落盘点**：`src/storage/session_store.py:53-55` 的消息块头部组装处，在 `timestamp` 行之后追加一行 `pair_id: {标识}`。`:346`（用户消息）与 `:514`（回复）两处调用点把**同一个标识**传入。`append_message` 签名相应扩一个可选参数，**缺省不写该行**——旧调用方不受影响。
3. **读取侧**：`read_session` 的解析处（同文件 `:80-120` 段）按行前缀识别，**缺该行时该条 `pair_id` 置空**——C-8 的向后兼容由此保障。
4. **是否进模型输入**：**不进。** `routes.py:355` 的 `prior_for_gateway` 组装保持只取 `role`/`content` 两键，配对标识是对账字段，不是上下文。
5. **先后关系**：重发路径的 `pair_id` 由前端给出（取自被重发那条提问）；**后端仅在请求未携带 `pair_id` 时才自行生成**。
6. **字段命名**：全文只用一个名字——**`pair_id`**。不出现第二个指代同一事物的字段名。

**消息块格式**（`pair_id` 存在时）：

```
---MSG---
role: user
timestamp: ISO8601
pair_id: <uuid4hex>
---
```

**改完什么效果**：**每条回复都能指回它答的那条提问**；排查时可精确对账；旧文件照常解析。

**怎么验**：见 C-1／C-2／C-3／C-8。

### 4.2 落盘互斥（对应根因②）

**改哪**：`src/storage/session_store.py:66-67`

**怎么改**：`aiofiles.open(path, mode="a")` 外层加一把**按文件路径分键**的锁，**键＝`(work_id, card_id)`**，不同卡不互堵（与项目既有 `card_store._get_lock` 同族做法——那处已按路径分键，本次沿用同一模式）。锁的生命周期覆盖「打开—写—关」整段，不给外部留半开窗口。

**打点**：加锁等待超过 **1 秒**时记一行 warning（含 `work_id`／`card_id`／等待毫秒数）。**该阈值为日志触发条件，不构成任何终止判据**——超时仍照常写入、不放弃、不重试。

**改完什么效果**：**同一张卡的两次并发写入不再交错**，落盘顺序与写入发起顺序一致。

**怎么验**：见 C-5。

**风险（如实登记）**：这是**动对话数据的写路径**。按边界（长期目标 2026-10-04 17:55 条）属技术修法归诸葛；**改完后必须做并发实测**，不能只靠代码审阅。

### 4.3 重发去重（对应加重项③）

**改哪**：前端 `static/workspace.js` 的 `resend` 路径 ＋ 后端 `src/api/routes.py:346`

**两侧处理，判据逐字同一句。**

**前端**：`resend` 路径在发起请求前，先取当前卡的会话列表，判定：**若最后一条是用户消息、且其后没有任何回复条**，则本次重发**复用该条的 `pair_id`**，不再落新提问条。前端若未持有 `pair_id`，则本次按新消息落盘、由后端生成新 `pair_id`。

**后端**：`src/api/routes.py:346` 落盘前按同一判据二次判定——**请求携带的 `pair_id` 已存在于本会话且其后无回复条时，复用而不追加**。

**最终仲裁**：前端漏判时后端拦住，**后端即为最终仲裁**。

**判定口径只有这一条**，不含「时间接近」这类模糊条件。

**为什么必须两侧**：后端 `:346` 对**任何进入的请求**都无条件落一条用户消息——**前端只拦得住「页面上点重发」，拦不住「同一句被当成全新请求发进来」。**

**改完什么效果**：记录里「你的提问」与实际次数一致。

**怎么验**：见 C-4a／C-4b／C-4c（**三条同时过才判通过**）。

> **【此条由诸葛代拍，用户可事后推翻】**
> 依据：①用户 2026-10-04 18:58 原话「它没有回复我的最新消息的问题要解决」——这是解决问题的授权；②用户 2026-10-04 17:54 边界原话（问的边界）——**修诸葛自己造成的、仍在生产上跑的技术缺陷，属例行技术动作，直接做完报账**；③本改动改的是 `src/api/routes.py:346` 的落盘判定逻辑，**只加一条「复用」判据，不删不改任何既有写入路径**，且 C-4b／C-4c 有机械判据可复核。
> 若用户不认这条：改成「只保前端、删 C-4b／C-4c 判据、如实标注『重发仍会重复记一条，属已知残留』」即可——**其余五条不受影响。**

### 4.4 工具痕迹摘要（对应加重项④）

**改哪**：`src/api/routes.py:355` 的历史组装处

**怎么改**：在把 `prior` 映射为两字段列表时，对**上一条**回复查找它在本次会话中触发的工具记录，若有则拼一行纯文本摘要追加到该条的 `content` 末尾。

**摘要行格式写死**：`[上轮工具：<工具名>、<工具名>]`——**顿号分隔，无参数、无结果。**

**工具记录来源写死**：`tool_events` 中 `card_id` 与本会话当前卡一致、**且时间戳落在上一条回复落盘之前**的那一批；**取不到则拼空**。

**范围写死**：只处理最后一条回复、只带工具名列表、不带参数与结果；**摘要不进会话文件**——它只在送网关的那一份历史里临时拼上，`session_store` 落盘内容**一个字节不改**。

**改完什么效果**：模型下一轮知道自己上轮干了什么，不再重复劳动或答得像失忆。
