## 一、四次用户裁定与最终形态（本次交付的核心）

### 1.1 裁定①【12:52】**取消一切容器**

- 任务书 T1／方案设计点 A 原文要求「新建一条 `.msg.assistant.live` **气泡**」承载全部环节。
  用户否决：「**气泡算哪门子的在对话流里，这他妈还不是独立区域？**」
- **判定**：一个容器装全部过程 = 独立区域（换壳）——与「把『流式展示在对话里』读成旁挂过程卡」同源病。
- **终态**：**不存在任何容器**。`/stream` 每个事件各自一条 `.step-row`（`chatArea` 直接子元素）；
  `/tokens` 逐字正文是单条助手消息本体。**判据：除 `chatArea` 外装下 ≥2 条环节行的元素数 = 0。**

### 1.2 裁定②【13:0x】**刷新后痕迹仍在**

- 用户令核实「每一条信息是不是会确定的自动推送进对话框里，即便刷新了也会存在在那」。
- 实测：**自动推送＝是**；**改前刷新后＝否（0 条）**；**内存 journal 仍在**（手动挂流可完整重放 17 条）
  ⇒ **根因不是红线，只是没人去取**（`attachRunningState` 只见活调用才挂流）。
- **终态**：`EventFlow.replayTrace` 在卡页打开时补回上一条调用的痕迹（**只重放环节行、不重放正文**，避免与会话已渲染的回复撞出重复气泡）。
- **边界**：事件从不落盘 ⇒ **同进程 ＋ 该卡此后未再发请求** 才成立。真持久须另开单加落盘痕迹存储。

### 1.3 裁定③【13:3x】**次序铁律：流式信息不得停在正式回复下面**

- 用户裁定：「dsh 这样的成熟 agent 是你做成的那样吗？**流式信息会他妈停留在正式回复下面？**」
- 复查又挖出**四个我自己的缺陷**：①`dropText` 把已就地接管的正式回复 `remove()` ⇒ 同页连发第二条时**上一轮回复消失**；
  ② 新 `run_start` 的 `clearRows` 波及同一数组 ⇒ **上一轮过程行被清**；③ 刷新重放 append 在 `renderChat` 之后 ⇒ **行落在回复下面**；
  ④ 我新加的 `replayTrace` 3s 兜底计时器**误关新一轮刚连上的两路流**。
- **终态（三处端序保证）**：生成期「新环节行落下即把**非空**正文推队尾」／结算「就地接管、行原地不动」／刷新重放「收流时 `anchorRows()` 把行整块移到该轮回复之前」；
  且**每轮自成一组**（`beginGroup` 封存上一轮）。
- **判据：末条 `.step-row` 的 DOM 下标 < 末条 `.msg.assistant` 的下标。**

### 1.4 裁定④【13:4x】**正式回复过后，过程信息可一键收起**

- 用户裁定：「正式回复过后，过程信息是可以隐藏掉的」——补上 **T2／CB-028 本就要求、执行方此前漏做**的一條（只做了每行 JSON 详情展开，没做整组收起）。
- **终态**：`done`/`error`（＝正式回复过后）到达时给本组加 `▴ 收起过程（N 步）` 开关；点击隐/显**本组**行。
  **行仍是各自独立条目，开关不包裹、不归拢、不改次序**；**默认展开**（非默认隐藏）。
