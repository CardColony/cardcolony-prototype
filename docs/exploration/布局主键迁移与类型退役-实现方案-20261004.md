## 1. 功能背景

**两个问题，同一批改造解决。**

**问题一 · 卡片的门牌号会自己变。** 现在编号是**按位置推算**的——`_next_seq` 扫正卡目录取最大号 +1（`card_store.py:114-122`）。它的输入是「目录里现在有哪些号」，不是「这张卡是谁」，所以卡片一挪位置、一换父卡，它可能拿到的号就跟原来的不是一回事。

**问题二 · 六个类型名，四个是空壳。** 白名单定义六个值 `ALLOWED_CARD_TYPE = ("剧本","世界观","行为体","节点","假设","线索")`（`card_store.py:39`），而全库 36 张卡的实测分布是「剧本」×6 ＋「线索」×30，四个小说词零命中。

**不做会留下什么（三条，全部有实读支撑）：**

**① 按名字判的判据已经烂了一条。** `canvas.js:134` 的 `isEnding = (c) => c.title === "目标" || anchoredIds.has(c.card_id)`——它拿标题严格相等比「目标」，而全库没有一张卡叫这个名字。这条规则从来没生效过。

**② 前端按类型滤卡的那段代码在空转。** `canvas.js:123-127` 五行按 `card_type` 滤出五组（节点／世界观／行为体／假设／线索），滤出来的那四组在全库零命中——它们永远是空数组。

**③ 删类型名是静默的、有连带的。** `_resolve_card_type` 对白名单外的值一律降级为「线索」（`card_store.py:89-90`，原文注释：「非法值一律降级为"线索"（不报错不丢弃）」）。这意味着：谁把四个名字从白名单删掉，而某张存量卡还写着那个名字，下次读它时就会被悄悄改写、不报错、不提示。这条是「不删名字、只关入口」的机理依据（裁定 D-06）。

**继承一条硬约束（逐字）**：底稿 §五 护栏⑤ 原文——「影子卡 `card_type: "shadow"` 在元组之外——类型退役不得把它卷进白名单。」（底稿 `:135-142`）。**本改造继承此条：影子卡的类型值保持在元组之外，任何环节不得把它并进白名单。**

## 3. 预期效果

**① 新卡的编号不再随位置变。**
- 可观察：建一张卡 → 记下它的号 → 把它挪到别的父卡下 → 再读它的号，与挪之前逐字相同。
- 验证方式：对同一个 `card_id`，在「建卡后」与「换父卡后」两个时点各读一次编号，比对逐字相等。
- 前置未决：见 §2 前置二（编号落点的确认）——未确认前本判据不可跑。

**② 四个类型名的存量卡不被静默改写。**
- 可观察：改造前对全库 36 张卡逐张记 `card_type`；改造后再逐张读一次；两轮结果逐张相等。
- 验证方式：全量 diff 两轮的类型字段快照，差异数必须为 0。
- 机理对应：`_resolve_card_type` 对白名单外值降级为「线索」（`card_store.py:89-90`）——若改造中误删名字，此判据立刻变红。

**③ 权限判据与布局判据的行为不变。**
- 可观察：改造前后各跑一轮权限判定（`can_read` 四判据）与布局判据（`isTopLevel`／`childMap`／`renderBreadcrumb`），同一组输入得到同一组输出。
- 验证方式：固定输入集按四类判据各取实样本构造——**子树样本**取「work_* 中的父卡与其直接子卡一对」；**血统链样本**取「同一血统链上相隔两层的两张卡」；**relations 样本**取「relations 字段中已有关系记录的一对卡」；**锚卡全局样本**取「任一剧本根卡与任一非本子树卡」。四组样本从现盘 `works/` 实取（不新建卡、不改数据），每组判定「改造前结果＝改造后结果」。

**④ 按名字判的死条件得到处理。**
- 可观察：`canvas.js:134` 的 `isEnding` 不再依赖 `title === "目标"`——**唯一处置为：废止 `title === "目标"` 那一支、保留 `anchoredIds` 那一支。**
- 验证方式：全库检索该判据的新形态；`title === "目标"` 在代码中无残留引用（grep 零命中）。
- 现状依据：全库零张卡叫「目标」，该条件恒为假。

**⑤ 类型退役后，新建入口不再提供四个废弃类型名。**
- 可观察：建卡入口的类型选项列表里不再出现那四个名字；而白名单元组里仍有它们（裁定 D-06：留名字、只关入口）。
- 验证方式：①读建卡入口的类型枚举——四个名字零命中；②读 `ALLOWED_CARD_TYPE`（`card_store.py:39`）——六值仍在。

**⑥ 改造不动存量卡数据。**
- 可观察：改造部署前对 `works/` 全量取一次指纹，部署后（不动任何卡的前提下）再取一次，两次逐文件逐字节必须全等。
- 验证方式：全量前后 diff，**差异数必须为 0**。
- 允许改动的字段白名单＝**空集**——即：改造不得改动任何存量卡文件的任何一个字节。依据：裁定 D-02（老卡不补号）＋D-06（类型名留白名单不删）＋铁律二——本次改造全部落在代码层（`card_store.py`／`card_tools.py`／`canvas.js` 的判据逻辑），不产生任何存量卡数据写入。
- **这条同时是本次改造的最大红线**：任何非零差异即等于「改造动了存量数据」，立即回退。

## 4. 方案正文（实现设计）

**总纲：三条改造线，落在三处文件；每条线只改判据来源，不改数据形态；全部改动落在代码层，不产生任何存量卡写入。**

### 4.0 裁定对照表（逐条对唯一依据）

| 裁定 | 内容 | 本稿落点 |
|---|---|---|
| **D-01** | 号码沿用 `card_%06d` 现有形态 | 设计点 Ⅰ |
| **D-02** | 老卡不补新号 | 设计点 Ⅰ 设计边界 |
| **D-03** | 分两步：先主键改造，类型退役后做 | 全稿阶段划分：§4.1＋§4.2 为第一步，§4.3 为第二步 |
| **D-04** | 父子关系按 `parent` 排 | 设计点 Ⅱ |
| **D-05** | 不做双写期 | 设计点 Ⅰ（新号只发不回溯） |
| **D-06** | 类型名留白名单、只关新建入口，不删名字 | 设计点 Ⅳ |
| **D-07** | 不停服改完一次部署 | §4.4 部署方式段 |

**七条逐条有落点，无一条悬空。**

### 4.1 编号固定化（对应裁定 D-01／D-02／D-05）

**设计点 Ⅰ · 编号来源改为「发放式」而非「推算式」。**

- **改动锚**：`card_store.py:114-122`（`_next_seq` 函数体）。
- **改什么**：把「扫目录取最大号 +1」改为「从已发放号序列的尾部取下一个号」。**输出形态必须保持现有 `card_%06d`**（裁定 D-01）——8 处扫描点的 glob 模式是 `card_*.md`，形态一变则全部寻址失配。
- **为什么这么切**：编号一旦由「目录现状」推导，任何目录变动都会改变推导结果；改为「只增不改的发放序列」后，编号与目录内容解耦；且因为所有扫描点是**路径匹配**（不是号段匹配），新旧号可天然共存，不必做双写（裁定 D-05）。
- **设计边界**：不补发存量卡的号（裁定 D-02）。存量 34 张卡继续用现有号，一个字节不动。

**设计点 Ⅰ-附 · 编号序列的持久化载体（定死，不留"另行决定"）。**

- **落点**：`works/{work_id}/.card_id_seq.json`
- **为什么落这里**：在**工作目录内**、但**不在 `cards/` 扫描通道内**、也不在 `shadows/` 内——依据「8 处 glob 全部只扫 `cards/` 目录」，该文件不进入任何现有扫描通道，因此不干扰寻址。
- **格式**：`{"seq": <int>, "issued": [<card_id>, ...]}`
- **写入时机**：每次发号成功后立即写盘。（载体名与格式由本环节定死，不再留后议。）
- **连带**：该文件落在 `works/` 下 → 会进快照（`data_snapshot.py` 全树遍历）→ 这是**预期行为**（它也属该剧本的状态）。改前须核快照行为是否受影响。

### 4.2 父子关系判据归一到 `parent`（对应裁定 D-04）

**设计点 Ⅱ · 五处「按类型判」的位置，逐处改为「按 parent／根卡标识判」。**

| 序 | 改动锚 | 现状 | 改为什么 |
|---|---|---|---|
| **Ⅱ-1** | `canvas.js:98` | `isTopLevel = root && root.card_type === "剧本"` | 改为判「该卡 `parent` 为空」——根卡的机制定义就是无父（依据 `card_store.py:130-131`：剧本卡 parent 强制 `""`） |
| **Ⅱ-2** | `canvas.js:123-127` | 五行按 `card_type` 滤出五组 | 改为按 `parent` 分组（与 `:90-94` 的 `childMap` 同源，避免两套分组并存） |
| **Ⅱ-3** | `canvas.js:134` | `isEnding = (c) => c.title === "目标" \|\| anchoredIds.has(c.card_id)` | 废止 `title === "目标"` 那一支（全库零命中，恒假）；保留 `anchoredIds` 那一支（它在生效） |
| **Ⅱ-4** | `card_store.py:409` | `is_work_card = cur_meta.get("card_type") == "剧本"` | 改判 `card_id == work_card_id`（依据 `:486` 已有的同源写法——删卡侧本就不依赖类型名） |
| **Ⅱ-5** | `card_tools.py:262` | `if anchor_tgt is not None and anchor_tgt.get("card_type") == "剧本"` | 同上，改判 `card_id == work_card_id`（`work_store.work_card_id_of` 已在同文件被调用） |

**为什么这么切**：`parent` 与 `card_type` 对「父子关系」是两套并存的判据源。系统里已有三处（`card_store.py:210`／`:226`／`:248`）以 `parent` 为第一关键字——本设计是**在既有方向上收口到单一判据源**，不是另起新机制。判据源唯一化之后，类型名不再参与任何父子／权限判定，这也为 §4.3 的退役腾出空间。

**设计点 Ⅲ · 四处兜底保留不动。**

- **锚**：`card_store.py:132`／`:220`／`:348`／`:365`（「parent 缺失 → 回退 `work_card_id`」四处）。
- **改什么**：**不改**。这四处是判据源唯一化之后的机械兜底。
- **一处纠正**：底稿称此处「三处」，实读为**四处**（多出 `:365`）。以实读为准。

**设计点 Ⅱ-4／Ⅱ-5 的执行约束（分步、可回退、不得并行）**

根卡判据双处同源化，**分两步**：

- **第一步**：只改 `card_store.py:409`。改完立刻跑「根卡保护判据」回归——对剧本根卡调 `update_card` 应返回拒绝、对非根卡应放行。
- **第二步**：改 `card_tools.py:262`。改完立刻跑「锚卡全局可读」回归——对剧本根卡应全局可读、对非根卡应仅按四判据。
- **两步之间不得并行**；任一步回归不通过即回退该步，不带病进下一步。

**前后端时序约束**：`canvas.js` 三处（`:98`／`:123-127`／`:134`）属前端展示层，改动不影响生产读写路径，可与存储层改动并行开发，但**必须在同一部署窗口内一起上线**——否则前后端判据源不一致，界面与存储层判断会打架。

**设计点 Ⅱ-6 · 前端旧语义清除检查。**

`isTopLevel` 改判 parent 为空后，**全库 `grep isTopLevel` 与「按 `card_type === "剧本"` 判根卡」的引用必须零残留**——残留即视为改造未完成。

### 4.3 四个类型名退役（对应裁定 D-03／D-06）

**⚠️ 本节属第二步（裁定 D-03 分两步），须在 §4.1＋§4.2 完成并验证之后才开工。**

**设计点 Ⅳ · 建卡入口关闭四个类型名，白名单元组不动。**

- **改动锚**：**待定位**——「建卡入口向调用方提供类型枚举的那一处 file:line」（含后端路由与前端表单两处）。
- **前置硬条件**：见 §2 前置一。**定位之前本设计点不成立、不得施工。**
- **改什么**：建卡入口提供的可选类型列表去掉四个小说词；`ALLOWED_CARD_TYPE`（`card_store.py:39`）六值元组原样保留。
- **为什么这么切**：`_resolve_card_type`（`card_store.py:88-90`）对白名单外值静默降级为「线索」——不报错、不提示。若把四个名字从元组删掉，任何仍写着这四名的存量卡在下次被读时会被悄悄改写。**保留元组＝保留「读得懂旧名」；关闭入口＝新卡不再产生旧名。** 这是裁定 D-06 的全部内容。
- **继承条款（逐字）**：本改造继承底稿 §五 护栏⑤——「影子卡 `card_type: "shadow"` 在元组之外——类型退役不得把它卷进白名单。」
- **设计边界**：本条不涉及任何存量卡的字段改写——存量卡的 `card_type` 一个字节不动。

**设计点 Ⅴ · 前端空转的五行同步处理。**

- **锚**：`canvas.js:123-127`。
- **改什么**：与设计点 Ⅱ-2 同一处——按 `parent` 分组后，这五行按类型滤卡的逻辑自然退场（四组恒为空是现状，不是需要保留的行为）。

### 4.4 部署方式（对应裁定 D-07）

- **不停服做，改完一次部署。** 依据：代码改动不影响运行中进程（影子卡机制即如此：改完一次重启生效）。
- **部署那次重启＝必须另行取得用户明确许可**——不属于本方案的施工范围，不得自行执行。
- **部署窗口内一起上线**：§4.1＋§4.2（第一步）的存储层与前端改动必须同一窗口上线；§4.3（第二步）在第一步验证通过后另行窗口。

### 全日志打点
