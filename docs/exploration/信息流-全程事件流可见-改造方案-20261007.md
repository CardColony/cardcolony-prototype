# 信息流 · 全程事件流可见（DeepSeek-harness 式）改造方案

状态：report-only · 待用户授权施工 · 2026-10-07
挂靠：card_022「信息流」（父 card_016「卡片功能优化总卡」）

---

## 〇 复核结语

- **需求成立**。用户要的是「每一步调用、每一个中间环节，可见、流式展示在对话里」。现状系统对这些环节的处理是「做完才知道发生过」（终态 JSON 灰条）或「永远不知道」（三席正文、上下文装配、中间机制）。
- **改造定性：执行链不动，传输与呈现层重做。** 工具循环、E-探针三席、T14 交付拼接已经是天然的「分步执行结构」，每个步骤在 `routes.py` 里都有明确代码位置——缺的不是步骤化，是一条把这些步骤**实时**送到用户眼前的通道。
- 本方案新增**过程通道**（SSE 事件流＋事件日志）；既有**结果通道**（POST /messages）与**审计通道**（prompt_log／会话）契约零改动。
- 佐证就在当下：用户与代理的每一轮对话本身也跑在这套系统里——代理每调一次工具，用户看到的只是「工具结果已返回」六个字。这正是本方案要消除的不可见性。

## 一 用户原话与需求拆解

原话两条（2026-10-07，逐字）：

> 「我希望整个系统，卡片对话的信息流，能像deepseek harness那样，每一步调用每一个中间环节，都对我可见，像这些成熟的agent一样，流式展示在对话里」
> 「这应该涉及到整个对话流的完全改造」

拆解：
- **每一步调用** → 事件粒度＝每次模型调用（轮）、每次工具执行、每席观点、统合、建卡、交付、异常。
- **每一个中间环节** → 除调用外还包括：配对标识、上下文装配（六区）、文本抢救、T14 拼接分支——凡 routes 里发生的事。
- **流式展示在对话里** → 载体是对话区：过程以可折叠时间线（过程卡）嵌入，不打断最终回复气泡。
- **完全改造** → 用户预期是重构级；方案判定为**传输层重构＋埋点补全**，模型执行链保持（理由见〇、§三）。

## 二 现状机制：三条通道与六处断点

现状已有三通道雏形，但没有一条能承载「过程」：

| 通道 | 载体 | 形态 | 局限 |
|---|---|---|---|
| 结果通道 | POST `/messages` | request-response，终态单 JSON | 全程黑盒，结束后只给摘要灰条 |
| 进度通道 | GET `/progress` | 2 秒轮询；progress.py 24 行内存 dict | 只有 `{stage, detail}`——8 个阶段标签，无内容、无身份、无轮次、刷新零重放 |
| 审计通道 | prompt_log／会话文件 | 事后全量 | 实时不可见 |

**六处断点**（用户「看不见」的机制清单）：

| # | 环节 | 现状 | 用户所见 |
|---|---|---|---|
| 1 | 模型每一轮调用 | 循环内无上报（仅轮次数进 stage detail「第 N 轮工具续跳」） | 等待气泡里的一个标签 |
| 2 | 工具调用与结果 | 终态 JSON 的 tool_events：仅 `{tool, card_id, ok}`——无参数、无结果、无耗时 | 响应后一条灰条 |
| 3 | 三席观点 | text 在返回前被剔（上下文回流铁则），全文只落 prompt_log | 「观点：模型✓耗时」灰条，正文永不可达（P7） |
| 4 | 上下文装配（六区/凝练水位） | 无上报 | 不可见 |
| 5 | 文本抢救／T14 拼接／建卡解析 | 无上报（仅服务端日志行） | 不可见 |
| 6 | 中途刷新 | progress 只剩 stage 标签可重挂（attachRunningState），过程零重放 | 转圈标签 |

## 三 既有资产（为什么这是加法不是重写）

1. **执行链已分步**：`_run_message` 结构＝配对 → 装配 → 工具循环（轮）→ E-探针三席（后置一次）→ 统合 → T14 拼接 → 建卡 → 落盘返回。每步都有可埋点的代码位置。
2. **回调已埋一半**：`run_viewpoints(on_progress=...)`、`_call_viewpoint(on_done=...)` 已把每席完成元信息送到调用方；routes 内 `progress.set_stage` 已在约 10 个位置打点——`emit()` 可以包住它们。
3. **网关有流式骨架但有两处盲区（关键约束）**：`gateway.call(stream=True, on_chunk)`（FE4 段）已存在，但流式分支只累积 `delta.content`：不解析 tool_calls 增量、无 reasoning_content 兜底、finish_reason 取自流对象必然失败。⇒ 现状流式分支**对工具轮与推理模型不安全**（开启即可能把工具轮误判为终轮）。且 `model_service.py` 模块 docstring 标注 gateway「禁止修改，按其实际签名接入」。
4. **MOCK_LLM 离线测试链在**——SSE 可离线验收。

## 四 目标架构：三通道

- **结果通道（不动）**：POST /messages 契约、T10 配对（1 问 1 答）、T14 拼接、终态 JSON 全部保持。旧前端零改动可用。
- **过程通道（新增）**：`GET /api/works/{wid}/cards/{cid}/stream?from={seq}`（SSE）。服务端为每 (work, card) 维护一份**事件日志**（内存、环形、seq 单调）；POST 执行期间每个步骤 emit 一条事件，实时推给所有订阅者；刷新后 `from=0` 重放。纯展示层：不进模型输入、不落盘、不进 session——对齐 progress.py 哲学与上下文回流铁则（SSE ≠ session；三席正文经此可见不违反 2026-10-02「去模型名」裁定，那条禁的是进统合官输入，同 card_016 §10.4-2b 的既有判断）。
- **审计通道（不动）**：prompt_log／会话／pair_id。

**事件本体论（15 类）**：

```
run_start(pair_id) · context(regions, condense) · round_start(round, purpose=main|synth) ·
round_end(latency, chars, tool_calls, finish_reason) · rescue(文本抢救) ·
tool_call(name, target, args) · tool_result(ok, bytes, text) ·
seats_enter(工具结果条数) · seat_start(seat, model) · seat_end(ok, latency, chars, text) ·
deliver(T14 branch) · proposal(created) · done(pair_id, model) · error(msg) · ping(保活)
```

Schema：`{"seq": n, "ts": ..., "type": "...", "data": {...}}`，seq 单调递增，run_start 清零重放。

## 五 后端改动清单

1. **新模块 `src/api/event_stream.py`**（约 150 行）：事件日志环形存储（默认上限 300 条、单条正文 8KB 截断并标记）、订阅者 fanout（asyncio.Queue）、`emit()` / `subscribe(from_seq)` 异步生成器、新请求 run_start 清日志、断连自动清理。
2. **routes.py 埋点约 18 处**（每处一行 emit；emit 内部兼调 `progress.set_stage`——旧 /progress 端点与旧前端零感知兼容）。锚点：配对段、装配段、循环每轮 call_main 前后、抢救分支、每个 tool_call 执行前后、三席进场、每席起止（经回调）、统合轮前后、T14 拼接后、建卡后、落盘后、异常段。
3. **simple_service.run_viewpoints 增可选参 `on_seat(kind, meta)`**（默认 None，零行为变化）；routes 传入转发 emit。
4. **POST /messages 一字不动**；progress.py 保留为降级路径（Phase 1 验收后评估退役，附录 B·采纳 3）。

## 六 前端改动清单

1. **新模块 `static/stream.js`**（约 250 行）：EventSource 管理＋**过程卡**渲染器——嵌在对话区的可折叠时间线：
   - 🧠 轮次（模型／耗时／字数／发起的工具名）
   - 🔧 工具（参数与结果默认折叠，可展开全文）
   - 💬 三席（每席状态与正文折叠展开）
   - ✚ 建卡、✓ 交付摘要、✗ 错误；结束后自动折叠为一行摘要。
2. **workspace.js**：send()/resend() 发 POST 的同时开 EventSource（from=0）；POST settle 后关流，按既有路径渲染最终气泡与灰条；`attachRunningState` 升级——活跃态时 from=0 重放重建过程卡（刷新不再丢过程）；EventSource 失败 → 回退 createWaitingBubble 轮询（既有代码路径即降级保底）。
3. **style.css** 过程卡样式（约 60 行）；**work.html** 加 1 行 script 引用；**api.js 不动**（POST 契约不变，SSE 用原生 EventSource）。

## 七 分期

- **Phase 1（本方案主体）**：事件级全程可见——§五§六全部。一次后端重启生效，前端刷新生效。
- **Phase 2（token 级打字机，需单独裁定）**：统合轮与三席逐字流式。前置：网关流式分支补齐 tool_calls 增量拼装与 reasoning_content 处理，或另立旁路流式通道——两者都触碰「gateway 禁改」标注，须用户先裁。主循环工具轮即便 Phase 2 也保持事件级（工具调用本身无「正文可流」的必要；deepseek harness 呈现的同样是步骤粒度）。
- **Phase 3（可选，另立）**：事件日志落盘为「运行台账」，跨重启回放；与「纯展示层不落盘」哲学有张力，默认不做。

## 八 不变量与红线

1. POST /messages 契约、T10 配对、T14 拼接与「上屏＝会话」、prompt_log.response 末轮语义：**零改动**。
2. 上下文回流铁则：事件不进 session／prior_messages／模型输入。
3. 三席匿名裁定：事件里 seat 带 model 名（meta 本就含名，仅不进统合官输入）——展示层带名不违反 2026-10-02 裁定。
4. 单进程限制继承 progress.py（多 worker 下日志不同步；现状单 uvicorn，不新增破绽）。
5. 同卡并发第二请求：journal 清零重放（与 progress last-write-wins 同语义，加 run_start 界标）。

## 九 验收判据 V1–V8（草案）

- V1 发送后 1 秒内过程卡出现 run_start／context 事件行。
- V2 工具调用即时逐条可见：名称＋目标＋参数可展开；结果完成即出（✓/✗＋字节＋全文可展开），不等终态。
- V3 三席逐席可见：开始／完成即时；成功席正文可展开；失败席显示错误。
- V4 deliver 后最终气泡与 POST reply 逐字一致（T14 不破）。
- V5 跑动中刷新：过程卡 from=0 重建至当前，无丢失。
- V6 SSE 失败降级：回退旧等待气泡，POST 正常。
- V7 回归：/progress、灰条、绿条、T10/T14/prompt_log 语义不变；旧 api.js 路径可用。
- V8 MOCK_LLM 离线 e2e：事件序列断言（run_start→context→round_start→…→done 有序）。

## 十 风险与代价

- **事件洪水**：工具循环不设轮次上限 → 日志环形＋前端只保留摘要态；live 推送无上限但单卡串行。
- **大参数**（edit_card content 全文）进事件：live 全量（本机传输）、journal 截断、前端默认折叠。
- EventSource 每域 6 连接上限：本应用每页 1 条，不触；代理缓冲本地直连无碍，15s ping 保活。
- 前端两套等待逻辑并存期（过程卡＋旧气泡）：降级设计使然，Phase 1 验收后旧气泡退为纯降级路径。

## 十一 待裁定（默认即执行，不阻塞）

1. 三席正文经过程通道实时可见 → 默认**可见**（折叠态；不进上下文铁则不变）。
2. 工具结果全文进事件 → 默认**全文**（前端折叠；journal 单条 8KB 截断）。
3. Phase 2 是否解冻 gateway → 默认**先做 Phase 1**，Phase 2 另立任务书再裁。
4. 事件日志落盘台账 → 默认**不落盘**。
5. 旧等待气泡去留 → 默认**保留为降级路径**。
6. 传输形态（附录 B 新增）：默认**「GET-SSE＋事件日志重放」**（三通道）；备选**「POST-SSE 流式主端点」**（三席输出 1 案）→ 登记备选，不改默认。

- 统合输入标注三份、实到两份（输出 1／输出 2；第三份缺席，留痕不追）。
- **采纳三条**：
  1. **POST-SSE 备选登记**（输出 1 案：POST /messages 本体改 StreamingResponse）：单连接天然有序、token 流零额外管道；代价＝旧 POST 契约须并行保留、刷新重放仍需事件日志（POST 连接刷新即断，重放横竖要 journal）、EventSource 不可用（须 fetch＋ReadableStream 手写客户端约 30 行）、query 传 content 有 URL 长度上限。判定：不取默认，入 §十一·6。

  3. **progress.py 去向**：由「保留（兼容 shim）」改为「保留为降级路径、Phase 1 验收后评估退役」（两席方向一致）。
- **更正一处（两席同犯，关键）**：「gateway 已支持流式、只差 model_service 透传一行」**不成立**。FE4 流式分支〔gateway.py:163-183，实读段〕只累积 delta.content：① tool_calls 增量不拼装——流式下 message 取自流末块、`raw_tool_calls` 恒空 ⇒ tool_calls=[]；② 无 reasoning_content 兜底（该兜底只在非流式分支）；③ finish_reason 经 `response.choices` 取值在流式对象上必失败。而本系统统合官**允许带工具续查**（routes「统合官仍需查证」分支）——今天对带 tools 的调用开 stream=True，工具轮会被静默误判为终轮、工具调用整体丢失。⇒ Phase 2 前置＝修 FE4 或建旁路，均触碰 model_service.py「gateway 禁止修改」标注，须用户单独裁定；Phase 1 零网关改动（§七维持）。
- **前端细节**：EventSource 仅支持 GET——输出 1 正文示例以 EventSource 传 content 属笔误（其风险节已自纠）；本方案前端为「GET 订阅＋POST 并行」，无此问题。
