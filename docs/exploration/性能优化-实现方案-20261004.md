## 一、功能背景

### 1.1 要解决什么

**让这套画布界面摸起来是「活的」，而不是「钝的」。**

内核目标逐字引自上游需求文档 §1.2：

> 内核目标：让这套界面摸起来是**活的**，而不是**钝的**。三件先做的活都是纯前端、热生效、零重启。

两条用户可感知的体验路径（需求文档 §1.2 逐字）：

- **「越用越钝」**——刚打开顺滑，逛一圈回来鼠标发滞（对应 R1／R5 互为放大器）
- **「卡卡的」**——每次单击开卡都有硬延迟（对应 R2）

### 1.2 实证支撑（每条挂已核实出处）

**支撑一 · R1 的监听器泄漏是真的，且比文档描述更重**

- **机制**（实读 `canvas.js`，函数级定位）：`bindNodeEvents` 函数体内**直接执行**两行 `document.addEventListener("mousemove", onDragMove)` / `("mouseup", onDragUp)`——**不在 `node.mousedown` 回调内**，即「建一个节点＝注册两个 document 监听器」
- **闭包**：`onDragMove`／`onDragUp` 是 `bindNodeEvents` 内定义的嵌套函数，捕获 `node`（DOM 元素）＋ `dragState`（局部变量）＋ `zoom`（模块级）
- **零移除**：全文 `addEventListener` **12 处**命中，`removeEventListener` **零命中**
- **诸葛补充的半句**（文档未写）：捕获 `node` 意味着**整棵卡片 DOM 子树**（`tname`／`ttype`／`summary`／`meta2` 四个 div）被一并钉住——泄漏体量比文档描述的「2 个 handler」大
- **每次渲染的增量**：`renderCanvas` → 全清 `nodeMap` → 逐卡 `createNode` → 逐卡 `bindNodeEvents` → **+2×节点数**

**支撑二 · R2 的 250ms 是「等第二次点击」的必然代价**

- **机制**（实读 `bindNodeEvents`）：单击走 `setTimeout(..., 250)`；**双击不是独立判断间隔，而是「同一计时器复用」**——首次点击起计时器，250ms 内第二次点击走双击分支，超时走单击
- **下游**：单击 → `Workspace.open`（开工作区）；双击 → 有子卡则 `setViewRoot`（换视图根）；徽章点击 → `clearTimeout(clickTimer)` ＋ `stopPropagation` 后 `setViewRoot`

**支撑三 · R3 的表述须修正（诸葛实读发现，与上游文档不同）**

- 上游文档原文：`chatArea.innerHTML = ""（在 renderChat 内），发一条消息就重建全部历史`
- **实读 `send()` 全函数后判定：后一句不准。** `send()` 正常路径全程只调 `appendMessage`（增量追加）——`appendMessage("user", ...)` → `postMessage` → `appendMessage("assistant", ...)` ＋ 各类系统条；**不调 `renderChat`**
- **`renderChat` 的真实调用点只有两处**：① `open()`（打开／切换卡时）② `tryRecover()`（响应连接中断后的恢复）
- **准确表述**：**「每次打开／切换卡、以及响应中断恢复时全量重建」**——不是「每发一条消息」
- **（性质说明）**：与文档自己给 R4 做的那次修正同性质（它把「每次渲染 N+1」修正为「每张卡首次进入视图发一次」）——**R3 也该照此修正，但文档没修**

**支撑四 · R4 的缓存分支确在（文档的自我修正准确）**

- `lazyLoadVisibleSummaries`：未缓存 → `getSummary` 请求；命中 → 回填 DOM 不请求
- `getSummary`：缓存命中直接返回；否则 `API.getCard()` → 取 `card.body.conclusion` 第一行 → 超 120 字截断加省略号
- **诸葛补充的落点事实**（实读 `canvas_store.py` 全文 147 行）：`canvas.json` 是**可重建缓存**（文件头注释逐字：`canvas.json 是可重建缓存，卡片文件才是真身`）；其 `cards` 数组由 `rebuild()` 内 `cards.append({...})` 打五种字段生成（`card_id`／`title`／`card_type`／`parent`／`created_at`）——**不含结论摘要**；而 `parse_front_matter()` 已返回 `(meta, body)`，`hash_utils.split_body_sections(body)` 的映射表逐字含 `"## 结论区": "conclusion"`——**取摘要不需要新增解析能力**
- **连带发现**：`setViewRoot` 内有一次 `summaryCache.clear()` ——换视图根会清空缓存，下钻后重新发一轮请求

**支撑五 · R5 是 R1 的放大器**

- `workspace.js:176` 返回画布按钮 → `window.ReloadCanvas()` → 画布侧 `reloadCanvas` → 替换三字段 → `rebuildCardMap` → `renderCanvas`（**全清重建 → 触发 R1**）
- **`reloadCanvas` 的调用点共三处**：`workspace.js:176`（返回画布）、`workspace.js:317`（删卡成功后）、画布侧新建卡成功后
- **咬合坑**：`hideWorkspace()` **两处调用点**（`setViewRoot` 内 ＋ `reloadCanvas` 末段）——返回画布会关掉正在编辑的工作区

**支撑六 · R6 的两处证据均属实**

- `progress.py` 全文 24 行，模块级 `_store` 字典；文件头逐字「单进程 uvicorn 内存态……只上报状态，不拦截、不限制、不进任何模型输入——不是闸」
- `api.js:25-28`：`if (!url.includes("/messages"))` → `AbortController` ＋ `setTimeout(15000)`；`API.getProgress` 与 `API.getCard`（摘要用）**都走这个闸**

### 1.4 不做会留下什么

## 四、方案正文

### 4.0 改动总纲

**六条诊断分三类处置**（同 2.1 表）；**一条不可动摇的边界**：本方案**不新增任何写用户数据的路径**——`canvas.json` 是由后端从卡片文件重建的**缓存**，R4 加字段是**改缓存的组装逻辑**，不碰 `works/` 里的卡片、会话、画布真身。

### 4.1 R1 · document 监听器泄漏（纯前端）

**改哪里**（函数级定位）：`bindNodeEvents` 函数体内、`node.addEventListener("mousedown", ...)` 之后的那两行 `document.addEventListener("mousemove", onDragMove)` / `("mouseup", onDragUp)`。

**怎么改 —— 两条路径，本方案推荐 (乙)**：

**(甲) 提到模块级注册一次**
- 把两个 `document.addEventListener` 移出 `bindNodeEvents`，放到模块级（IIFE 顶层，与平移监听器同区）执行一次
- **代价**：`dragState` 现在是 `bindNodeEvents` 内的局部变量，模块级 handler 看不到它——**必须把 `dragState` 一并提到模块级**，且要处理「当前在拖哪个节点」（handler 需知道 `node`）
- **改动面**：比 (乙) 大

**(乙) 拖拽开始挂、结束卸 —— 本方案推荐**
- 把两行 `document.addEventListener` **从函数体挪进 `node.mousedown` 回调内**（即按下时才挂）
- `onDragUp` 末尾（`dragState = null` 之前）加两行 `document.removeEventListener("mousemove", onDragMove)` / `("mouseup", onDragUp)`
- **好处**：`dragState` 与 `node` 的作用域**完全不用动**（handler 仍是该节点的闭包，只在拖拽期间存活）
- **依据**：需求文档 §二 R1 修法原文给了这条（`或拖拽开始时 addEventListener、结束时 removeEventListener`）

**⚠️ 一处改正（对诸葛 14:43 评审的更正）**：评审时称「R1 修法**须**连带改 `dragState` 作用域」——**那只对路径 (甲) 成立**；路径 (乙) 不需要动作用域。**此处以 (乙) 为准。**

**必须处理的边界（路径 (乙) 的硬要求）**：
- **窗口外松手兜底**：`mouseup` 若发生在窗口外，`onDragUp` 可能不触发 → 监听器残留。**处置写死**：新增一个**模块级** `window.blur` 监听器（**注册一次、不随节点增长**），触发时取消当前拖拽并卸掉两个监听器
- **卸监听器必须用同一函数引用**（`onDragMove`／`onDragUp` 是命名函数，引用稳定）——**不得改成匿名箭头函数**（那样卸不掉）

**依据（实读）**：见 1.2 支撑一。

**连带影响**：
- 修后「监听器 ＋ 整棵旧节点 DOM 子树」都不再被钉住
- **平移监听器三处（IIFE 顶层）不得被误伤**（C-9 守门）
- T08 若同时改 `bindNodeEvents`，本处须与其合并施工（见 4.7）

### 4.2 R2 · 单击 250ms（纯前端 · **随裁定择一**）

**改哪里**：`bindNodeEvents` 内 `node.addEventListener("click", ...)` 段（含 `clickTimer` 判定）。

**路径 (a) · 拆掉双击**（随裁定）
- **怎么改**：`click` handler 内去掉计时器判定，直接调 `onSingleClick(card)`；`onDoubleClick` 不再由 click 触发
- **收益**：单击开卡**立即**（不再等 250ms）
- **代价＋🔴 与 T08 的交互后果（写死）**：T08 任务书 3-1 已将 `▸N` 徽章改为「展开/折叠开关」（原调 `setViewRoot`，改调 `toggleExpand`）。**徽章被 T08 改掉之后，下钻入口只剩双击**——**若本路径再拆掉双击，下钻入口全部消失。** 因此**「下钻改走哪」须由同一轮裁定一并给出**；**裁定未给出则本路径不得实施**——执行者无权自行择一
- **判据**：3.2 表中两条（单击 50ms 内开卡 ＋ 下钻入口守门）

**路径 (b) · 保留双击、阈值降到 ~120ms**（随裁定）
- **怎么改**：`setTimeout(..., 250)` 的 250 改为 120
- **收益**：单击延迟减半；**与 T08 无冲突**（双击保留，下钻入口不受影响）
- **代价**：仍有约 120ms 等待
- **判据**：3.2 表中 (b) 行

**共同约束**：徽章点击段的 `clearTimeout(clickTimer)` ＋ `stopPropagation` **必须保留**（否则点徽章会误触发单击开卡）。

### 4.3 R3 · 会话区重建（纯前端 · **含表述修正**）

**改哪里**：`static/workspace.js` 的 `renderChat`（函数体内 `chatArea.innerHTML = ""` 那句）。

**表述修正**（见 1.2 支撑三）：上游文档写 `发一条消息就重建全部历史`——**不准确**，真实触发点是 `open()`（打开／切换卡）与 `tryRecover()`（响应中断恢复）。

**怎么改**：
- `renderChat` 改为「首次构建 ＋ 后续增量」：维护一个内存游标（已渲染消息条数），重建时只 append 新增部分
- **增量规则写死**：以服务端返回的消息数组长度为基准——服务端长度 **>** 本地已渲染数 → **只 append 尾部差额**；服务端长度 **<** 本地（消息被删）→ **回退全量重建**（不能只 append）
- `open()` 首屏仍全量构建；`send()` 的既有增量路径**不动**

**难点（如实列出）**：本条的收益限于「切卡／恢复」路径，**不是高频路径**；但它是打开大 session 卡顿的直接原因，仍值一修。

**判据**：C-4 ＋ C-6。

### 4.4 R4 · 摘要逐卡请求（前端＋后端各一处）

**改哪里（两处）**：

**后端** —— `src/storage/canvas_store.py` 的 `rebuild()` 内 `cards.append({...})` 处（L82-88）：**加一个字段** `conclusion_summary`

**怎么改（算法写死）**：
- 取 `parse_front_matter()` 已返回的 `body`
- 用现成的 `split_body_sections(body)` 得 `sections["conclusion"]`
- 取该结论的**第一行非空文字**，**超 120 字截断加 `…`**——**与前端 `getSummary` 现有算法逐字一致**（前端原文：`firstLine.length > 120 ? firstLine.slice(0, 120) + "…" : firstLine`）
- **结论为空或全空白 → `conclusion_summary` 写空字符串**；前端 `.summary` 保持空白（**不写占位文字**，与现有行为逐字一致）
- 写入 `cards.append({... "conclusion_summary": <该字符串>})`

**前端** —— `canvas.js` 的 `getSummary`：**优先读卡片数据里的 `conclusion_summary`**；若该字段缺失（老数据／未重建），**回退到现有的 `API.getCard` 路径**（向后兼容，不硬依赖）

**依据**：见 1.2 支撑四。

**连带影响**：
- `canvas.json` 体积增大（每卡 ≤120 字）——**它是缓存、可重建，不碰卡片真身**
- **需后端重启才生效**（与纯前端条目不同类）
- 缓存重建触发点：`card_store` 的六处 `update_cache` 调用（建卡／改卡／删卡／关系变更等）——加字段后这些路径自动带上摘要
- `setViewRoot` 的 `summaryCache.clear()` **无需改动**（清空后重读的是卡片数据里的字段，不发请求）
- **摘要内容须保留**（上游文档 §二 R4 前提：见 card_007 §五）——本方案不改结论语义

**判据**：C-3。

### 4.5 R5 · 返回画布全量重拉（纯前端 · **只记录不改**）

- **判据**：C-5

### 4.7 施工顺序（技术取舍，用户可推翻）

**核心事实：三处改动落在 `bindNodeEvents` 同一个函数体内。**

| 动的地方 | 谁动 | 函数级定位 |
|---|---|---|
| 徽章 `click` handler | **T08 3-1** | `bindNodeEvents` 内 `badge.addEventListener("click", ...)` 段 |
| 单击／双击判定 | **性能 R2**（若选拆双击） | `bindNodeEvents` 内 `node.addEventListener("click", ...)` 段 |
| document 两行注册 | **性能 R1** | `bindNodeEvents` 内函数体末两行 |

**推荐序**：

1. **先 T08、后性能**——T08 任务书已派工、施工进行中，先让它落地稳定
2. **R1 与 T08 3-1 合到一次改造里做**——同函数双改分两遍，第二遍须先读第一遍改完的样子
3. **R2／R3／R4 各自独立**——R2 与 T08 的交互须先裁定（4.2 已写明后果）；R3 在 `workspace.js`；R4 涉后端

**中间态风险（写死）**：若分两遍改同一函数，第一遍改完到第二遍之间若发生部署，**画布会处于「徽章已改展开、R1 未修」的半改状态**——可用，但泄漏仍在。**合一次做可消除这个中间态。**
