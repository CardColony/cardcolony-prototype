## 二、需求清单（按优先级）

### R1 【P0】document 监听器泄漏 —— 唯一硬 bug

**证据**（`canvas.js`，实测）：
```js
// bindNodeEvents 内，:513-514
document.addEventListener("mousemove", onDragMove);
document.addEventListener("mouseup", onDragUp);
```
- **每个节点无条件注册**（不等 mousedown，绑定即注册），且 `onDragMove`/`onDragUp` 是为该节点生成的**闭包**。
- 全文件**无 `removeEventListener`**（已全文件检索）。
- `renderCanvas`(:400) 每次 `node.remove()` + `createNode` **全量重建节点**。

**量级**：每次渲染新增 **2×N** 个 document 监听器；旧节点闭包被 document 引用而无法回收。切十几次视图后，每次鼠标移动要跑数百个空转 handler。

**现象**：越用越钝——不崩，但拖垮手感。

**修法**：mousemove／mouseup 提到模块级注册一次，用当前 `dragState` 变量判断；或拖拽开始时 `addEventListener`、结束时 `removeEventListener`。

**验收判据**：切 15 次视图后，Performance 面板中 document 上 mousemove 监听器数**不随渲染次数增长**（恒为常数）；空闲鼠标移动不触发多余 handler。

**别误伤**：画布平移的 document 监听器（`:801 / :807`）注册于 IIFE 顶层、**只一次**，不是泄漏源。

### R2 【P0】单击开卡被动等 250ms

**证据**（`canvas.js`，实测 `:494`）：
```js
clickTimer = setTimeout(() => {
  clickTimer = null;
  onSingleClick(card);
}, 250);
```
双击靠同一计时器判定（`:486-491`）。为兼容双击下钻，「单击开卡」这一最频繁操作每次都硬等 250ms——「卡卡的」手感即源于此。

**修法**：下钻只走 `▸N` 徽章（`:476` 注释自称「比双击更可发现」）与双击替代入口，单击立即开卡；或保留双击但降到 ~120ms。

**验收判据**：单击卡 → 工作区打开延迟 < 50ms（感知即时）；徽章/双击下钻仍可用。

**【待裁定】** 彻底拆掉双击，还是保留双击仅降阈值——二选一。

---

### R3 【P1】会话区全量重建

**证据**（`workspace.js`，实测 `:325`）：`chatArea.innerHTML = ""`（在 `renderChat` 内），**发一条消息就重建全部历史**。单张卡 session 实测 15 万字节量级（见 CHANGELOG）。

**修法**：仅增量追加新消息。

**验收判据**：发消息后既有消息的 DOM 节点对象**不被替换**（增量 append）；10 万字节级 session 发送后无明显卡顿。

---

### R4 【P1】摘要 N+1 请求（表述需修正）

**证据**：`canvas.js` `:755` `lazyLoadVisibleSummaries` 对每个**未缓存**的可见卡调 `getSummary`(`:730`) → `GET /cards/{id}`，每请求吃 15s 超时上限。

**修正表述**：原记「每次渲染 N+1」**不准确**——`:757` 有 `summaryCache`，命中则回填不请求。真实量级是**每张卡首次进入视图发一次**；但每次首屏/下钻仍是一串并发小请求。

**修法**：`canvas.json` 带上 `conclusion_summary` 字段，一次拿完。

**前提**：摘要内容须保留（见 **card_007 §五** 结论区＝唯一接口的可视化表达）。

**验收判据**：首屏渲染对 `GET /cards/{id}` 的请求数由「N 张可见卡」降为 **0**（摘要随 `canvas.json` 一次到手）。

---

### R5 【P1】返回画布全量重拉 —— 且是放大器

**证据**（`workspace.js`，实测 `:176`）：
```js
document.getElementById("wsBackBtn").onclick = () => window.ReloadCanvas();
```
→ `canvas.js:888` `reloadCanvas` → `renderCanvas` 全量重建 → **触发 R1**。

**验收判据**：返回画布后 R1 的监听器计数**不增长**。

**咬合警告**：`reloadCanvas` 末段有 `hideWorkspace()`——建卡后若写成 `window.ReloadCanvas()` 会**关掉正在编辑的工作区并静默丢未保存内容**（见 card_007 咬合链）。

---

### R6 【P2 · 归属待定】进度内存态 + 15s 超时边界

**证据**：
- `src/api/progress.py`（24 行）`_store: Dict[Tuple[str, str], ...]` **进程内存、不落盘、不进模型**（文件头注释自述「纯展示层……不是闸」）→ **刷新即失、多 worker 即失效**。这正是影子树（card_005）要替掉的那一层。
- `api.js`（实测 `:25-28`，原记「:26 起」实质一致）：非 `/messages` 端点统一 **15 秒超时**（AbortController）。若 `getProgress`／`getSummary` 将来变重（子树扫描）会**误报超时**。

**【待裁定】** 本条是「性能」还是「架构」归属未定——暂挂本卡，与 card_005 落点决策联动。

## 三、跨卡咬合链

> **R5「返回画布全量重拉」→ `renderCanvas` 全量重建 → R1 监听器泄漏**

三条互为放大器：重拉越频繁 → 泄漏越快；泄漏越多 → 重拉后的交互越钝。**修 R1 的收益会同时放大于「返回画布」与「建卡后刷新」两条路径。**

## 四、建议排序（三件先做）

**① R1 修监听器泄漏 → ② R2 去掉单击 250ms → ③ 修 pinned 语义与视觉标识（见 card_007）**

三者皆纯前端、热生效、不碰后端、零重启，改动量小，直接决定「这套东西摸起来是活的还是钝的」。
