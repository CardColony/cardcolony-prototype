### 六条诊断（原文 §二，逐条要点）

**R1 【P0】document 监听器泄漏 —— 唯一硬 bug**

- 证据：`bindNodeEvents` 内 `document.addEventListener("mousemove", onDragMove)` / `mouseup, onDragUp`
- 特征（原文逐字）：**每个节点无条件注册**（不等 mousedown，绑定即注册），且 `onDragMove`/`onDragUp` 是为该节点生成的**闭包**；全文件**无 `removeEventListener`**（已全文件检索）
- 量级（原文逐字）：`每次渲染新增 2×N 个 document 监听器；旧节点闭包被 document 引用而无法回收。切十几次视图后，每次鼠标移动要跑数百个空转 handler。`
- 现象（原文逐字）：`越用越钝——不崩，但拖垮手感。`
- 修法（原文逐字）：`mousemove／mouseup 提到模块级注册一次，用当前 dragState 变量判断；或拖拽开始时 addEventListener、结束时 removeEventListener。`
- 验收判据（原文逐字）：`切 15 次视图后，Performance 面板中 document 上 mousemove 监听器数不随渲染次数增长（恒为常数）；空闲鼠标移动不触发多余 handler。`
- 别误伤（原文逐字）：`画布平移的 document 监听器（:801 / :807）注册于 IIFE 顶层、只一次，不是泄漏源。`

**R2 【P0】单击开卡被动等 250ms**

- 证据：单击走 `setTimeout(..., 250)`；双击靠同一计时器判定
- 现象（原文逐字）：`为兼容双击下钻，「单击开卡」这一最频繁操作每次都硬等 250ms——「卡卡的」手感即源于此。`
- 修法（原文逐字）：`下钻只走 ▸N 徽章（:476 注释自称「比双击更可发现」）与双击替代入口，单击立即开卡；或保留双击但降到 ~120ms。`
- 验收判据（原文逐字）：`单击卡 → 工作区打开延迟 < 50ms（感知即时）；徽章/双击下钻仍可用。`
- **【待裁定】**（原文逐字）：`彻底拆掉双击，还是保留双击仅降阈值——二选一。`

**R3 【P1】会话区全量重建**

- 证据：`workspace.js` 的 `renderChat` 内 `chatArea.innerHTML = ""`，**发一条消息就重建全部历史**
- 量级（原文逐字）：`单张卡 session 实测 15 万字节量级（见 CHANGELOG）。`
- 修法（原文逐字）：`仅增量追加新消息。`
- 验收判据（原文逐字）：`发消息后既有消息的 DOM 节点对象不被替换（增量 append）；10 万字节级 session 发送后无明显卡顿。`

**R4 【P1】摘要 N+1 请求（表述需修正）**

- 证据：`lazyLoadVisibleSummaries` 对每个**未缓存**的可见卡调 `getSummary` → `GET /cards/{id}`，每请求吃 15s 超时上限
- **修正表述**（原文逐字）：`原记「每次渲染 N+1」不准确——:757 有 summaryCache，命中则回填不请求。真实量级是每张卡首次进入视图发一次；但每次首屏/下钻仍是一串并发小请求。`
- 修法（原文逐字）：`canvas.json 带上 conclusion_summary 字段，一次拿完。`
- 前提（原文逐字）：`摘要内容须保留（见 card_007 §五 结论区＝唯一接口的可视化表达）。`
- 验收判据（原文逐字）：`首屏渲染对 GET /cards/{id} 的请求数由「N 张可见卡」降为 0（摘要随 canvas.json 一次到手）。`

**R5 【P1】返回画布全量重拉 —— 且是放大器**
