### 已核实的实测事实（设计依据，非推断）

1. **kimi-k3 输出全在思考字段**：默认档 `content=null`、输出全在 `reasoning`（`reasoning_tokens` 计数非零）、`finish_reason=length`——旧代码只接 `content`，所以用户一个字都看不到。
2. **reasoning 实测可关可降**：默认（effort=max）→ 正文空；`reasoning_effort=low` → 正文正常出；`reasoning.enabled=false` → 正文秒出。
3. **慢的实锤**：服务内单次主模型调用 `model_call_success latency_ms=279500`（4.6 分钟）、`tokens=18289`；用户 09:21 那条消息到 09:46（25 分钟）仍在工具循环内未结束。
4. **gateway 已有 `stream_call`**：逐字流不是「解禁被禁改的旧分支」，而是改这一个方法的解包逻辑。

## 三、任务分解（可派工，含依赖）

### Task 1 · gateway 双增量解包（零依赖）

- 改 `src\model_gateway\gateway.py` 的 `stream_call`（L502 起）：chunk 解包处（L563 一带）由「只取 `delta.content`」改为 **`delta.reasoning` 与 `delta.content` 均解、分别 yield**。
- yield 载荷形态：`{"chunk_type": "reasoning" | "content", "text": <str>}`；**兼容旧形态 `{"chunk": <str>}`**（既有消费方零感知）。
- 签名补 `on_reasoning` 回调（与 L510 的 `on_status` 并行、可选参、缺省 None 零行为变化）。
- **不改**：`call` 路径（L134-159）、finish 检测、续写 Completable（L518）、fallback（L590-591）。
- **兜底**：单增量（只有 reasoning 或只有 content）不报错；前端不得把思考误当正文。
- **完成标准**：单测 mock 双增量 chunk 通过；yield 含 `chunk_type`。

### Task 2 · reasoning 降档（零依赖，与 T1 并行）

- 改 `config\models.yaml` 的 `main` 段（L24-30 之间）新增 `extra_body`，降 kimi-k3 的思考档（参照同文件 MiniMax L65／qwen L78 的先例写法）。
- **【施工前提 · 必须先验】** 落码前先做探针实测：`extra_body` 里两种候选写法（`reasoning: {effort: low}` 形式 vs `reasoning_effort: low` 形式）经 L552 透传路径**哪一种真生效**，以实测结果为准写入；**不确定不写死**。
- 档位取用顺序：**先 low；若仍显著慢，则 disabled**。
- **完成标准**：写入的写法经实测确认生效；kimi-k3 单次调用 `latency_ms` 相对 279500ms 显著下降。

### Task 3 · 前端双路渲染（依赖 T1/T2）

- 改 `static\stream.js`：**📄 正文字逐字显示（主题）＋ 🟡 思考字（有则显示、无则不留空痕）**。

- **完成标准**：真请求下正文字逐字连续出现、首 chunk ≤1s；思考字存在时可见、不存在时正文流正常。
