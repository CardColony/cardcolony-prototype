# 建项目 · 全流程重写方案（2026-10-17）

> 本方案取代《惰性新建重写-方案-20261017.md》。
> 范围由用户 2026-10-17 12:10 钉死：**只有建项目的流程**——从人类点下「新建项目」，到他能在这个新项目里正常干活，这一条线的每一个环节。建卡、规则卡编辑、画布整理等其他流程，本方案不碰、不掺。

---

## 0. 使用者是谁

他不懂技术。他不能调代码、不能看日志、不能刷新来"救"界面。他的全部手段是：看屏幕、点鼠标、打字。
他对这个系统的用法只有一种主形态：**跟模型对话**。
所以他点「新建项目」的唯一意图是：**开始一段新的推演对话**。
方案里每一条设计只服从这个意图。凡是让他在意图之外多看一个东西、多点一下、多等一秒的，都是错的。

---

## 1. 流程逐环节

每个环节四件：**他看到什么 / 他此刻想要什么 / 系统做什么 / 拿什么证明做对了。**

### 环节 1 · 入口——三个＋，一个结果

- **他看到什么**：三处能开始新项目——首页「新建项目」大按钮、画布页左栏＋、对话页左栏＋。
- **他想要什么**：开始新项目。他不关心自己此刻在哪个页面。
- **系统做什么**：三个入口，**同一个动作**——跳转 `/work/draft`（整页跳转，本机服务零点几秒）。废除现状的三种不同行为（首页跳草稿画布 / 画布页就地变空白画布 / 对话页跳转）。
- **证明**：E1——三个入口点完，最终 URL、页面形态、输入框聚焦状态**逐项相等**。

### 环节 2 · 落地——直接进根卡对话页

- **他看到什么**：一个完整的对话界面（和任何真项目的根卡对话页长得一模一样）：顶部标题「新项目」，中间空的对话区，底部输入框，**光标已在输入框里闪**。
- **他想要什么**：立刻打字。
- **系统做什么**：`/work/draft` 返回**对话页模板**（card.html），不是画布模板。WORK_ID 为 draft 时跳过取数（没有数据可取），但界面**按真页面同一套代码完整装配**。到可打字 ≤ 1 秒（一次页面加载）。
- **不出现的东西（负面清单，逐条禁）**：空白画布（他没有卡可看）；「未保存」小标（内部机制漏给用户，他看到只会困惑"要不要按保存"——发消息自动落库，他不需要知道任何中间态）；任何需要刷新才激活的假界面。
- **证明**：E2a——草稿落地页与真项目根卡页的**可见控件集合、可点行为集合相等**（脚本断言，非肉眼）。

### 环节 3 · 打字、发第一条消息（核心环节，现版本死在这里）

- **他看到什么**：打完字点发送（或回车）——他的消息气泡**立刻上屏**，紧接着模型回答开始逐字流出。和他平时在任何卡里发消息**没有任何区别**。
- **他想要什么**：就是发消息，看到回答。他不知道也不需要知道背后有"先建库"这回事。
- **系统做什么**（一条链，全自动）：
  1. 消息气泡乐观上屏（走真页面同一条渲染路径）；
  2. `await ensurePersisted()`：POST 建项目＋根卡＋快照（本地 ~100ms，用户感知只是首 token 晚零点一秒）；
  3. 用真 (WORK_ID, card_id) 走**原有 send 全流程**——SSE、模型调用、回答流出，原代码路径一字不动；
  4. 落库成功的同时：URL 静默换成真地址、左栏出现新项目（排最前）。
- **他全程做的事**：只有打字和点发送。
- **证明**：E2b——**对照测试**：同一句话，在草稿页和真项目页各发一遍，对比消息上屏时机、回答流出、请求序列、报错数——**行为不可区分**（落库那次 POST 除外）。这是"真界面"的终极证明：不是"像"，是分不出来。

### 环节 4 · 回答之后——他已经在真页面上了

- **他看到什么**：对话继续。第二条消息、第三条……一切如常。
- **系统做什么**：无任何草稿逻辑。URL 已真、WORK_ID 已真，走的就是普通对话页。改名、状态、关系、规则卡，全部是真页面行为。
- **证明**：E5——发完首条消息后抓 Network：此后**没有任何请求带 draft 字样**；左栏出现新项目；刷新页面回到该真地址。

### 环节 5 · 先起名再说话（改名即落库）

- **他看到什么**：他可能落地后先点标题改成「XX 推演」再打字。
- **系统做什么**：改名是数据动作——改名那一刻 `ensurePersisted()` 落库（项目以他起的名字真建），然后走原改名路径。之后他发消息时项目已在，直接发。
- **证明**：E6——草稿页只改名不发消息：works/ 出现新目录、标题＝所改名、左栏出现、零多余请求。

### 环节 6 · 中途离开——什么都没干就走，就当没来过

- **他看到什么**：落地后一个字没打，点了左栏别的项目（或关了页面）。
- **系统做什么**：草稿蒸发，**零确认弹窗**（他什么都没干，没有可确认的东西），盘上零残留。
- **证明**：E3——进入草稿、离开：works/ 计数不变、全程零 POST。

### 环节 7 · 出错——不吞、不丢、能重试

- **他看到什么**：极端情况（后端挂了）他发消息，会看到一条报错提示；他打的字**还在输入框里**；再点一次发送，成功。
- **系统做什么**：落库失败 → toast、输入保留、草稿态保持、可重试。消息**绝不丢**。落库成功后 send 失败 → 走真页面既有失败处理，不变。
- **证明**：E4——mock 落库 500：toast 出现、输入内容保留、恢复后重试整链成功。

### 环节 8 · 边界（想清楚、定死，不做糊涂账）

| 情形 | 定案 |
|---|---|
| 草稿页刷新（F5） | 回到一个**新的空草稿**（URL 仍是 /work/draft；他没发过消息，无内容可恢复；不发任何"离开确认"） |
| 连点两次＋ | 等于放弃第一个草稿进入第二个；第一个自动蒸发（没数据，无损） |
| 草稿页点左栏其他项目 | 草稿蒸发，正常跳转 |
| 草稿页里建子卡 | **本轮不做**（属建卡流程），但接口留好：建卡是数据动作，触发即先落库——与本方案机制天然一致 |
| 首页点进旧项目 | 不受本方案影响 |

## 2. 病根：为什么现版本是死的（已查实，非猜测）

两个被用户骂碎的缺陷（空白画布、发消息没反应）同一个根：

**上一版把 draft 当成了一种"卡形态"，守卫的对象搞反了。**
- open("draft") 早退 → 界面装配被跳过 → SSE、消息通道、上屏通道**全都没建立** → 发消息点下去什么都不会发生，直到刷新。
- 入口把人送进**画布模板** → 一个没有任何卡可看的空白画布。
该守卫的是**网络出口**（后端还没有这个项目，请求发出前先落库），不该守卫的是**界面装配和用户动作**。

**本次核心设计判断：draft 不是一种卡，draft 只是"WORK_ID 还没定"。**
- 页面按真页面完整装配（唯一跳过的是取数——没有数可取）；
- 一切数据动作的出口处先 `await ensurePersisted()`（该机制上一版已建，保留）；
- ensurePersisted 成功 → WORK_ID 变真 → 后续代码全部走在真路径上。

## 3. 技术骨架（给执行线）

1. **`/work/draft` 路由改返回对话页模板**（card.html，CARD_ID="draft"）——后端唯一改动点（改一个模板选择）。
2. **三入口统一** `location.href = "/work/draft"`：home.js、canvas.js 的 #navNewProject、workspace.js 的 #navNewProject。废除 enterDraftProject / enterDraftCanvas / 就地变草稿画布那套。
3. **main_chat 启动**：WORK_ID=="draft" → 跳过 getCard/timeline/规则卡 GET（无数可取），界面完整装配，标题「新项目」，输入框聚焦。
4. **数据动作出口统一前置 ensurePersisted**：send、改名、规则卡保存、状态、关系（send 已接，其余沿用上一版接线）。ensurePersisted 成功后 replaceState 真地址 + renderNav + 继续原动作。
5. **删除**：「未保存」小标及其样式（.draft-badge）、草稿画布整套（enterDraftCanvas/enterDraftProject/discardDraftCard 及相关守卫——凡因"空白画布"而存在的代码全撤）。
6. **不重写**：send 全流程、乐观上屏、SSE、EventFlow、ensurePersisted 本体——全部沿用生产验证过的原路径。

## 5. 红线（沿用项目纪律）

- 开工前盘面检查：目标文件无他线在途，有则停。
- 显式文件名单提交，禁 add -A；改动面与名单逐一对账。
- 版本戳：内容变即升，全量同升（含外层引用）。
- 语法校验用**模块口径**（.mjs），不重演宽松口径放走语法错的教训。
- 探针当日清；沙箱验证零触生产数据。
- 每完成一个环节跑该环节的 E 项验证，**证明不闭合不进下一环节**。

## 6. 明确不做（本轮）

- 建卡流程的任何改动（草稿项目内建子卡仅留接口）。
- 性能优化（切卡跳转提速等）——另案。
- 任何未被本方案覆盖的"顺手改"。
