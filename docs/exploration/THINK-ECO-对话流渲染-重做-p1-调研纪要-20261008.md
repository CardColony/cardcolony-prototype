## 风险点

1. **渲染目标迁移的最大风险**：逐字流从「旁挂卡 append」改到「对话 `.msg` 列表长成生成中消息」，与现有多条依赖 `.msg` 计数的逻辑打架——send 基线（workspace.js L781 `.msg:not(.thinking)`）、renderChat 重建（L638）、刷新补态（restoreFromHash→EventFlow.start L757）——计数口径错会反复。**需统一「生成中逐字消息」是否计入 baseline 的判定。**
2. **最终回复与生成中消息的衔接**：逐字消息（POST 进行中长成）与 POST 完成后的最终回复 `.msg`（renderChat 渲染）必须合并/衔接到同一条，不能出现「一条打字中的 + 一条最终」两条割裂气泡——方案必须写死衔接规则。
3. **reasoning_chunk（思考字）在消息内的呈现**：降 `reasoning_effort:low` 后模型几乎不思考（实测 reasoning_tokens 40→4），思考字可能长期为空。方案须定义「思考字有则显示、缺省折叠/省略」——正文逐字是主，思考字是附（用户要的是「看到过程」不是「看到思考全程」）。
4. **废弃 flow-card 的耦合**：stream.js start（L201-231）两路 EventSource 共用 st（ensureCard 建的卡对象）当 state 容器；改造须保留 state 容器、去掉卡 DOM——若复用 st 做消息 DOM 的 state，需一并迁。
5. **V-T3-1 历史未达标项**（首正文字 6.7-10s，prefill 延迟）——本次是纯前端渲染迁移，**不解决 prefill 慢**；方案须如实声明「首字时间的瓶颈在模型 prefill，不在渲染层」，不把未达标当本次验收目标。
