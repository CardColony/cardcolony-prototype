# 卡片接口 · 调用协议与句柄集（call-protocol v1，2026-10-14）

> 性质：接口定义（未施工）。承架构 v3（底座只做装载/调用/权限，不定形态）。
> 姿态声明：本文全部内容是**"底座给你的"**（offer），没有一处是"你只能"（constraint）。句柄是门，方案是家具——全看你需不需要。
> 版本化：call-protocol v1。向后兼容承诺：v1 内句柄只增不废、签名不破坏性变更；破坏性变更升 v2 并保 v1 卡合理期限内可跑。

---

## 一. 接口是什么：一句话

**接口 ＝ 一次调用（invoke）＋ 三个交互面的能力句柄（handle）＋ 一摞现成方案（ready-made）。**

底座调起一张卡时，递给它三样东西：调用请求（谁在叫你、为什么、参数）、只读上下文视图、一组能力句柄。卡拿这些做什么、怎么做，完全由卡决定。

```
底座 → 卡：  invoke(request, context, handles)
              │            │         └─ handle_card / handle_model / handle_artifact ...
              │            └─ 只读快照：当前卡/树/对话
              └─ 调用意图
卡 → 底座：  完成(产物指针＋结论) / 进行中(多轮) / 失败(结构化原因)
```

## 二. 交互面一：上下文（card 怎么看世界）

**原则：结论是卡片间唯一接口（产品第一律，接口层照办）。** 卡读世界靠句柄，写世界靠结论与产物——不直接污染别人的上下文。

| 句柄 | 给什么 | 底座现成机制（实证） | 需要权限 |
|---|---|---|---|
| `context.read_card(id)` | 目标卡正文块全集 | card_store.read_card（cards.db） | read_context |
| `context.read_tree()` | 树结构（id/标题/父子/卡种） | activity.iter_card_metas | read_context |
| `context.read_conversation(id)` | 目标卡对话时序线（事件流） | events/{card}.jsonl ＋ timeline 合并读 | read_context |
| `context.read_shadow(id)` | 目标卡过程记录 | shadow_store | read_context |

**反向（卡→上下文）两条正路**：①产出结论落卡（结论随树上行注入，现有机制）；②包入口声明里的描述自愿进「可用卡」区（模型发现你的依据）。除此之外底座不给任何"直接往别人上下文塞东西"的口子——这是产品律，不是接口小气。

## 三. 交互面二：卡-卡（card 怎么找同事）

| 句柄 | 给什么 | 底座现成机制（实证） | 需要权限 |
|---|---|---|---|
| `cards.message(to, type, content)` | 给别的卡发消息；三型（询问/应答/通知）、须答型自动回发、收件方应对由系统驱动 | card_msg ＋ message_type_registry（加类型零代码） | send_card_message |
| `cards.invoke(name, params)` | 调起另一张卡（新实例） | run_tool_card（建实例→入口→产物挂卡） | invoke_tool |

消息协议细节（when_to_use／reply_expected／reply_type）全部继承现有注册表——第三方甚至能注册自己的消息类型。

## 四. 交互面三：模型调用（card 怎么用脑子）

| 句柄 | 给什么 | 底座现成机制（实证） | 需要权限 |
|---|---|---|---|
| `model.call(role, messages)` | 按角色调模型（think/execute/synthesize/condense…或包自指定绑定） | model_gateway（litellm 封装：多端点/重试/降级/**每次调用全文落 logs**） | 无（随卡） |
| `model.stream(...)` | 同上，流式 | stream_call 双路解包（正文/思考） | 无 |

**白送的全家桶**：多供应商路由、重试降级、全量 prompt 留痕、三方可对账——卡作者一行不写全部继承。

## 五. 现成方案目录（你需要就拿；看不上就自己写，接口照常伺候）

| 方案 | 是什么 | 你怎么用 | 底座对应机制 |
|---|---|---|---|
| **剧本链（flow）** | 步骤循环运行时：你只写剧本（JSON）＋各步提示词，底座替你跑循环、逐步喂上下文、收产物、断点续跑 | 包里放 script.json＋prompts/，入口声明指 flow | toolcard：script_loader/driver/state_store（零改动包装） |
| **三席共识（panel）** | 把一个问题并发三路模型出观点、统合官收敛成唯一结论 | 入口声明指 panel，配一问一收两个提示词 | simple_service（三席＋统合，现有） |
| **多步计划板（board）** | 复杂任务上板：拆步/排序/插删改/逐步收口 | 句柄 `board.*`（create/reorder/insert/remove/modify/complete） | thinkchain（现有七工具） |
| **产物归档（artifact）** | 产物自动挂卡、命名、版本化、下探取回 | 句柄 `artifact.write/read` | toolcard/artifact_store |
| **进度上报（progress）** | 阶段性进度实时可见 | 句柄 `report(stage, detail)` | progress 体系 |
| **审计留痕（audit）** | 你的每次模型调用/工具动作自动入账，三方对账 | 什么都不做，自动有 | prompt_log＋tool_events＋git |

**目录本身就是开放集**：上面每件都是"底座用自己的机制实现的一个包"，第三方可以提供更好的同类件，也可以长出全新品类——底座照单装载，不管长什么样。

## 六. 权限映射（能力码 × 句柄）

`read_context`→context 面；`send_card_message`→cards.message；`invoke_tool`→cards.invoke；`model.call/artifact.write/report`→随卡默认授予（留痕覆盖）；`tools_file/tools_web/manuscript`→经 `use_tool` 走统一权限关口。安装时按包申请明示、用户批准、运行时按批交付句柄（没批的句柄不递给卡）。

## 七. 一页总览

```
invoke(request, context, handles)
 ├─ context.   read_card / read_tree / read_conversation / read_shadow
 ├─ cards.     message / invoke
 ├─ model.     call / stream
 ├─ artifact.  write / read
 ├─ board.     create / reorder / insert / remove / modify / complete
 ├─ report.    stage / detail
 └─ use_tool.  （统一权限关口下的平台工具）
现成方案：flow 剧本链 / panel 三席共识 / board 计划板 / artifact 归档 / progress 进度 / audit 留痕
```

接口的完整定义就这些。句柄会随版本**只增不废**；方案目录随时欢迎第三方件进驻。
