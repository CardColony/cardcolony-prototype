## 〇、一屏结论

**16 个可独立验收的阶段 + 1 个后续迭代（键盘，不占本轮）**，顺序主轴＝地基→骨架→肌肉→自动：**契约 → 状态 → 渲染 → 交互 → 呈现 → 自动**。

先做 **P1 契约改造**——唯一理由：`/api/nav` 返回的每张卡必须自带 `work_id`，它是后面全部阶段的数据输入；契约不先落，前端全建在旧数据上，改契约那天整批返工。

每个阶段都能单独停下验收（命令/字段/DOM/请求四类机械判据之一），没有一个阶段要等别的阶段完才看得出变化。

**环检查：无环。** 唯一需当心的一对：R-15(diff 新时间戳)→R-11(状态重算)→R-36(排序重算)→位置变化——由 R-C2「状态分变化≠立即重排」破环（分数随时变、位置只在安全时机机动）。

**顺序不可颠倒的三条链（违反会怎样）**：

| 链 | 违反会怎样 |
|---|---|
| R-01 → R-05/R-06 → 全部前端 | 先做前端：改契约日整批返工（一次全重写） |
| R-32 → R-17 → R-16 | 行高不定：虚拟滚动按 38px 算可视区 → 错位/重叠渲染 |
| R-11 → R-36/R-38 | 无状态先做排序/收起：凭空造输入，等于做假功能 |

**两条顺序修正（议题 2→3 当场钉死）**：
1. 异步加载与虚拟滚动无硬依赖（虚拟滚动只消费行序列，不关心数据来源）；先 P5 虚拟滚动（mock 全量序列验收更纯）后 P6 异步加载（换真实 children 端点），顺序为验收纯度而设。
2. R-04 单列独立阶段，不阻塞前端主链：前端对缺 status 字段容错，主链照走；R-04 在自动层(P15)开工前就绪即可。存量卡不迁移（守住不碰用户数据铁律），只新建卡写字段、接口暴露。

## 四、反向验证结论

### 查漏（42 条逐条对阶段表）

- 当场抓到 **R-06 版本号端点漏归属** → 补归 P4（P4 范围加「版本号端点＋diff 消费」，验收补一条）。理由：diff 刷新是 P4 核心，版本号是触发源，拆两阶段=切重。
- 其余 41 条全部有落点；R-32/R-34 属"同需求两半各落两阶段"（P5 前提/P11 样式；P8 语义/P11 视觉），验收各自独立，标注清楚，不算切重。

### 查包装（逐阶段问"只做一半用户看得出变化吗？能否独立停验？"）

- 16 阶段无一被包装（每阶段单一需求主题、验收独立）。
- 三个基础设施阶段如实标注"用户不可见、命令可验收"，不装成可见：**P1 契约改造**（纯后端，界面零变化，验收=curl 字段）、**P3 行对象四态**（界面无独立变化，验收=mock 读字段）、**P12 状态维度**（界面无排序无收起，验收=字段/接口/单测）。地基阶段天然不可见是真阶段的特征（单需求性+命令可验收），不是包装。

### 查不可验收（逐条判据："怎么判真假、谁来判"）

- 无一条"体验良好"类主观词；判据全部确定形态（curl 字段、localStorage 值、行对象字段、DOM 节点数/类名/子树存在性、network 请求计数、URL 变化、快照比对、单测输出、序列顺序）。
- 三类判据承担者如实标注：**命令/脚本判据**（P1/P2/P3/P12 多数）＝我执行；**浏览器操作判据**（P4-P16 多数）＝我实现时可做脚本，但真实渲染需用户看一眼确认；**视觉体验判据**（P16 平滑过渡"不闪跳"）＝机械只覆盖 transition 触发监控，"是否真不闪"需用户看一眼。无一条可假装全机械验。

### 最可能出问题的一步（判断＋处置）

**P4 渲染骨架**——唯一"动地基"的阶段：渲染模型换底（整树 innerHTML→按需+折叠即卸载+diff+版本号）；diff 边界面最宽（增/删/字段变/层级变/两次取数间删卡/加载中节点）；且是 P5/P6/P15/P16 的地基，错会在后续放大。
