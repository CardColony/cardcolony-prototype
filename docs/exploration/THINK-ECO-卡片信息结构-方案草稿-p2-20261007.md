# 卡片信息结构改造 · 实现方案草稿（proposal 链 p2 骨架草稿）

## 1. 功能背景

卡片正文现用「四区」结构（职责区／结论区／否决记录区／修改历史），系写作 agent 遗产——方案对照表旧列逐字标注「旧（写作agent遗产）」（`卡片信息结构改造方案.md:84`）。该结构在代码里是硬编码而非可配置项：渲染器写死四个区头（`card_store.py:227`／`:230`／`:233`／`:236`），区名→键映射写死（`hash_utils.py:106-111`），读卡固定返回四键（`card_store.py:461-471`）。

结构缺陷落在两处。**其一，六类信息只有一个正文落点**：方案规定六类信息各有唯一的家（`C-12`~`C-17`），而模型经 `edit_card` 传入的整篇正文被硬编码塞进 `conclusion` 一个键（`card_tools.py:348-351`）——决定、事实、指针无各自落点。**其二，权威语义无机械兜底**：方案要求「模型在对话里说"定了""做完了"不算数——收口仪式＝用户确认或验证通过」（`C-18`），而现状 `update_card` 只消费 `charter/conclusion/rejections` 三键（`card_store.py:540-546`），既无区分字段，也无拦截。

不做会留下两项后果：决定可被静默改写且不可追——`edit_card` 是覆盖写，一次调用即可抹掉既有定论条目，而方案要求「条目被删/被改写→拒绝」（`C-08`）；事件流水与状态快照混住——方案为此单列「防流水账侵蚀」一节（`C-10`），现状无任何分区约束阻止时间线堆进主卡。

同批线路的实测坐标（本次调研实证）：权限线**已施工完毕**（`card_tools.py:238-257` 已是全盘放开新态），其方案文档仍写「五判据」——文档自述落后于代码；信息结构线**零落地**——`status_block|rulings|## 使命|## 现状|## 定论|mission` 在 `src/` 全库零命中；快车道线**并发进行中**（`routes.py:472` 前新增 `route(content)`），上线后模型带工具直答，若走 `edit_card` 将高频触发上述落点缺陷。

## 4. 方案正文（实现设计）

### 4.1 设计枢纽：把改卡从「键级覆盖」改为「正文级分区写」

现状 `edit_card` 把模型传来的整篇正文写进单一键（`card_tools.py:348-351` 逐字 `{"conclusion": content}`）。**这是全部矛盾的根**：模型交的是含区头的整篇正文，落点却是一个键——因此「三块各自归位」在物理上不可能发生，S3 要做的「分区 diff」也无从取新旧两份解析结果。

设计：`edit_card` 的落点语义改为**整篇正文覆盖写**——取旧卡正文、取新 content，两份都过拆分器，按分区做 diff 判闸，放行则整篇写回。改动锚 `card_tools.py:333-354`（分发段改造）、`:348-351`（落点改造）。条目 `C-22`、`C-47`、`C-62`。

此设计同时消解方案未言明的接口疑点：`update_card` 的键级 `updates` 通道保留（供 HTTP 与内部调用），正文级通道另立（供 `edit_card`）——两者共用同一套拆分/渲染内核，不产生第二套真值。条目 `C-44`。

### 4.2 拆分器：双表识别 + 形态带出 + 规范键归一

改动锚 `hash_utils.py:100-123`（`split_body_sections`）、`:106-111`（mapping）。条目 `C-32`、`C-33`、`C-43`。

**双表并存**：现有 mapping 为旧四区（`charter/conclusion/rejections/history_text`）。新增新区名→新键映射，与旧表并列；识别时按正文实际出现的区头自适应，两套区名混用不报错。条目 `C-43`。

**规范键归一**：旧区头命中时，其内容归入对应的新键——`## 职责区`→`mission`、`## 结论区`→`status_block`、`## 否决记录区`→`rulings`、`## 修改历史`→`history_text`（后者键名不动）。依据即方案对照表（`C-34`~`C-37`）。归一化的目的：**下游消费点只需认一套键**，存量卡与新卡在读侧不分叉。

**形态带出**：拆分器在返回结果中同时带出本次识别到的区头形态（旧／新），供渲染器保形使用。形态**不写入卡片文件、不新增 front matter 字段**——它是解析的副产物，随解析结果传递。条目 `C-60`（新卡 front matter 干净）、`C-70`（不造机器字段）。

**键名差异须辨明**：拆分器返回 `history_text`，而 `read_card` 组装 body 时转为 `history`（`card_store.py:461-471`）——该转换点须随归一化同步复核，防新旧键名在同一函数内并存。

### 4.3 渲染器：按卡原形态保形输出

改动锚 `card_store.py:205-238`（`_render_card`；区头写入点 `:227`／`:230`／`:233`／`:236`）。条目 `C-30`、`C-31`、`C-45`。

设计：`_render_card` 增加形态入参，按形态输出对应区头——新卡输出 `## 使命`／`## 现状`／`## 定论`，存量卡输出原旧区头。**不做隐式迁移**：存量卡在编辑后结构不变。依据 `C-58`（存量卡不批量迁移，收工时按完成仪式蒸馏）。

此设计的必要性由调研实证支撑：`_render_card` 有**三个**调用点——`card_store.py:369`（`create_card`）、`:553`（`update_card`）、**`:691`（`_append_relation`）**。方案文档只提"改拆分器与 update_card"，未提第三处；漏改即产生新旧混挂。card_027 现存状态即为该症状的现场证据：新三块手写标题与旧三区空标题并存。

### 4.4 create_card：骨架默认值

改动锚 `card_store.py:320-421`（`create_card`）、`:326`（`charter: str = ""`）、`:355-367`（meta 初始化）、`:369`（调渲染器）。条目 `C-26`、`C-39`、`C-42`。

设计：`charter` 参数默认值改为三块骨架模板；新建卡经渲染器输出新形态。**骨架套用须在区头检测之后**：`card-proposal` 接口传入的 content 若已含区头则原样使用，不含区头才套骨架——依据 `C-39` 逐字「content 不含区头时自动套骨架」。该检测落在 `create_card` 内部，`card_proposal.py:191` 的调用点无需改动语义。条目 `C-39`。

连带面：`routes.py:69-75`（`CreateCardRequest` 含 `charter/conclusion`）、`:181-197`／`:322-336`（两个建卡路由）、`work_store.py:143-145`（内部建 work）——均以旧键传参，经归一化后落新形态。

### 4.5 update_card：键扩展与归一

改动锚 `card_store.py:476-566`（`update_card`）、`:540-546`（消费键段）、`:553`（调渲染器）。条目 `C-28`、`C-44`、`C-45`。

设计：`updates` 键扩展新增 `mission/status_block/rulings`，旧键 `charter/conclusion/rejections` 保留。两套键在函数内归一后落到同一处存储，**不产生双写路径**。渲染时按卡原形态输出（承接 4.3）。条目 `C-44`。

### 4.6 S3 写入闸

挂点锚 `card_tools.py:333`（`edit_card` 分发前拦截），参照实现锚 `:340-342`（影子写守卫）。条目 `C-47`、`C-22`、`C-23`。

**判据源**：新旧两份正文的拆分结果（承接 4.1、4.2），逐块 diff。六条规则与方案逐字对应：使命区不等→拒绝 `使命块为立项定稿，修改需用户确认`（`C-48`）；定论区非超集→拒绝 `定论块只追加；失效用就地标记（→被N取代）`（`C-49`）；行首 `→` 的失效标记放行（`C-50`）；现状区 diff 不校验（`C-51`）；修改历史区 diff 忽略（`C-52`）；旧结构卡不校验（`C-53`）。

**两处边界必须写明**。其一，**锚点不做机械强制**：方案明确否决"含锚点才放行"的机械校验，理由逐字「机械强制会激励伪造锚点，伪证比缺证更伤权威机制」（`C-54`、`C-80`）——本设计不实现锚点闸。其二，**闸的作用域**：S3 闸执行的是块写入规则，不是访问控制（`C-55`、`C-66`、`C-78`）；且闸只拦模型工具通道（`card_tools.py:333`），**用户经 HTTP PATCH 的通道是"用户确认"的合法来源，不设同一闸**——使命块对用户开放修改，对模型拒绝。此点方案未言明，为本设计的判断，须在复核中受检。

### 4.7 HTTP 通道与白名单

设计：新三键入白名单。**校验点两处须同改**——`:239` 与 `:354` 是同一白名单的两个消费点，只改一处即出现"新版能用、兼容层被拒"的不一致。旧键保留在白名单内，供存量卡路径。

### 4.13 边界：本设计不覆盖的部分

权限体系（跨卡读影子、管辖判定、访问控制）→ 独立任务，S3 闸不属此列（`C-66`、`C-78`）；读侧注入（清单摘要、权威标注入上下文）→ 独立任务（`C-67`）；类型退役（`card_type` 词表）→ card_009 域，本设计仅保证 `create_card` 默认骨架不依赖类型字段（`C-59`、`C-68`）；`content_hash` 语义 → 不动，理由逐字「只算正文会导致存量哈希一次性全失配」（`C-69`）；`role/status` 字段复活 → 不做，生命周期用「现状块文字＋定论收口」表达（`C-70`）。

**一处方案未言明、本设计据代码补实的因果**：`content_hash` 算全文（`hash_utils.py:26-39`），`read_card` 有哈希校验（`card_store.py:443-451`）；若对存量卡重渲染，校验会逐卡追加 `[外部修改]` 行并触发快照。4.3 的保形设计使存量卡编辑后正文区头不变，恰好避开该连锁——与 `C-58`「存量卡不批量迁移」同向。
