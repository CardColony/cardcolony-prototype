# 卡片生态规范 · 开发—权限—市场（cardspec-v1 草案，2026-10-14）

> 性质：生态总规范草案（未施工）。承 2026-10-14 用户五轮裁定：①卡独立于类型 ②卡市场对标 dsh 插件市场 ③AI 是第一开发者（接口第一读者是 AI）④完整规则＋尽可能给出接口 ⑤下载时必须向用户明示卡的权限。
> 规范自身版本化：**cardspec-v1**。承诺：v1 内向后兼容；破坏性变更升 v2 并保证 v1 卡在合理期限内继续可跑。
> 三条设计总纲：**接口机器优先**（自描述＋金样本，喂给 AI 即能生成合法卡包）；**权限即知情**（卡申请什么，用户批什么，运行时只能用什么）；**校验一码三用**（同一份校验逻辑，开发者自检／市场上架／用户安装三处跑同一套）。

## 第一部分 · 开发规范（一张卡长什么样）

### 1.1 卡包物理格式

```
<card_name>/
  manifest.json      # 身份＋权限＋市场元数据（唯一必填的"表"）
  script.json        # 流程剧本（步骤序列；单步卡可极简）
  prompts/           # 每步的提示词文件（.txt）
  artifacts/         # 可选：卡自带的静态资源（模板、参考样例）
```

### 1.2 manifest.json 字段定义（cardspec-v1 全量表）

| 字段 | 必填 | 类型 | 说明 |
|---|---|---|---|
| `spec` | ✓ | string | 恒 `"cardspec-v1"`（校验闸第一道判据） |
| `name` | ✓ | string | 卡的唯一标识（目录名必须与之一致；小写字母数字连字符） |
| `display` | ✓ | string | 显示名（用户在界面/市场看到的名字） |
| `version` | ✓ | string | 语义化版本 `MAJOR.MINOR.PATCH` |
| `author` | ✓ | string | 作者标识 |
| `description` | ✓ | string | 这张卡干什么（一句话；注入模型「可用卡」区＋市场货架卡片） |
| `when_to_use` | ✓ | string | 什么时候该用这张卡（注入模型，供其自主决策调用） |
| `permissions` | ✓ | array | **运行时权限申请清单**（词汇表见第二部分；空数组＝无权限卡） |
| `steps` | ✓ | array | 步骤概要：`[{id, purpose}]`（与 script.json 一致性由校验闸核对） |
| `outputs` | ✓ | string | 产物说明（告诉用户和模型这张卡产出什么） |
| `min_base_version` | 　| string | 底座版本下限（缺省＝不限制） |
| `homepage` / `license` | 　| string | 市场展示用 |
| `changelog` | 　| object | 版本→变更说明（市场展示） |

### 1.3 script.json（流程剧本）

沿用现有 `toolcard/script_loader` 格式，正式化：

```json
{
  "name": "方案链",
  "scenario": "从任务书到可施工方案",
  "steps": [
    {"id": "p1", "prompt_ref": "prompts/方案链-p1.txt"},
    {"id": "p2", "prompt_ref": "prompts/方案链-p2.txt"}
  ],
  "artifact_naming": "{seq}-{step}-{name}-{ver}{ext}"
}
```

- `steps[].prompt_ref` 指向包内相对路径；**卡包自包含**（不引用包外任何文件）。
- 每步可选 `provides_context: true`（该步产出并入下一步上下文——现有机制，显式声明）。
- **cardspec-v1 为纯声明式**（无代码）；带逻辑/代码的卡属 v2 议题。

### 1.4 金样本

官方卡「方案链」「任务书链」按本规范重包装后公开发布＝活教材。AI 开发闭环：**规范文档＋两份金样本 → AI 生成卡包 → 校验接口 → 按结构化报错自修复 → 交付**。

## 第二部分 · 权限规则（卡申请什么、用户批什么、运行时查什么）

### 2.1 卡运行时权限词汇表（封闭集合，底座版本化）

| 权限码 | 白话含义（**用户明示文案直接用这列**） |
|---|---|
| `read_context` | 读取雇佣它的那张卡的内容 |
| `write_artifact` | 在项目里写下自己的产物 |
| `tools_file` | 读写本地文件 |
| `tools_web` | 联网搜索/访问网页 |
| `manuscript` | 查询项目资料库 |
| `send_card_message` | 给其他卡发消息 |
| `invoke_tool` | 调用其他卡 |

- 词汇表封闭：manifest 里出现表外权限码 → 校验拒（报错指明合法词汇表）。
- 词汇表随 cardspec 版本走；新权限＝升版本，不偷偷扩。
- **与雇主侧闸门的关系**：雇主卡能不能"雇"卡，仍走雇主自己固化权限里的 `invoke_tool`（现有机制不变）；本表管的是**卡被雇之后**自己能行使的能力。两道闸独立。

### 2.2 授权状态机（下载到可用的完整路径）

```
已下载(downloaded)
   │  系统弹出权限明示：这张卡申请──读你的文件、联网搜索……
   ├── 用户全部同意 → installed（授权=manifest.permissions 全集，固化到 installed.json）
   ├── 用户逐项勾选 → installed（授权=勾选子集；卡用到未授权能力时被拦并明示）
   └── 用户拒绝 → 未安装，包不落地（下载即取消）
```

**权限提升规则**：卡升级（v1→v2）新增权限项时，**已装用户必须重新确认新增项**；未确认前，卡按旧授权集继续可用（新功能涉权处被拦），不静默扩权。

### 2.3 运行时执行

- 每次卡执行涉权动作（文件/网络/消息/跨卡调用），关口查**该卡的固化授权**（installed.json），不是查 manifest——manifest 是"要价"，授权记录是"成交价"。
- 越权拒绝文案三段式：这张卡想做什么 × 你没批过什么 × 去 installed.json 或设置里可调整。（同时是给 AI 的修复指引：换用已授权路径或提示用户授权。）
- **全量留痕照旧**：卡的每次涉权调用记入现有 tool_events／prompt 日志体系，三方对账口径不变。

## 第三部分 · 市场规则（远期，但格式现在定死）

### 3.1 上架物与上架门槛

- 上架物＝符合 cardspec-v1 的卡包（zip）。
- 上架门槛＝过**校验闸**（与用户安装时跑的是同一份校验代码——一码三用：开发者自检、市场上架、本地安装）。
- manifest 即货架数据源：名称/版本/作者/描述/权限清单/变更日志全部从 manifest 读，市场不维护第二套元数据。
- **市场页必须原样展示权限清单**（2.1 的白话文案列）——用户在下载前就看到，下载确认时再看一次，双重知情。

### 3.2 版本与生命周期

- 版本语义：MAJOR＝权限变化或流程重构；MINOR＝新增步骤/能力；PATCH＝修文案修提示词。
- 市场保留历史版本；用户可锁版本（installed.json `pinned_version`）。
- 下架：不影响已装用户（包在本地）；更新通道断。删除本地包＝卸载，正在跑的实例按快照跑完（版本锁机制，已在底座方案 v2 定义）。
- 官方卡与第三方卡在市场同规格展示，官方加标识不加特权。

## 第四部分 · 接口清单（底座须提供）

### 4.1 卡包管理（HTTP，挂现有 /api 前缀）

| 接口 | 方法 | 作用 |
|---|---|---|
| `/api/cardpacks` | GET | 列已装卡：名称/版本/来源(官方\|用户)/授权状态/生效范围 |
| `/api/cardpacks/install` | POST | 安装：入参=包路径或上传体；**返回=校验结果＋权限申请清单（待确认态）**；此接口不落最终态 |
| `/api/cardpacks/{name}/confirm` | POST | 权限确认：入参=用户逐项勾选结果；写 installed.json、卡转可用 |
| `/api/cardpacks/{name}` | GET / DELETE | 看详情／卸载 |
| `/api/cardpacks/{name}/scopes` | POST | 设置生效范围（哪些项目类型里启用；缺省全部） |

### 4.2 校验（AI 开发闭环的关键接口）

| 接口 | 方法 | 作用 |
|---|---|---|
| `/api/cardpacks/validate` | POST | 独立校验：入参=卡包；**返回=结构化错误清单（字段级：哪个文件哪个字段错＋合法值是什么＋怎么改）**。AI 拿报错自修复重交。与安装闸同一份代码 |

### 4.3 调用与可见性（改造现有件）

| 项 | 改造 |
|---|---|
| `run_tool_card` 工具 | schema 描述去硬编码示例，改指「可用卡清单见上下文」；执行前加两道复核：生效范围＋卡运行授权 |
| 上下文装配线 | 新增「可用卡」区：按当前树生效范围过滤，渲染 display＋when_to_use（模型自主发现与调用的依据） |
| 权限关口 | 卡运行时涉权动作查 installed.json 授权（2.3） |

### 4.4 市场远期预留（本批只定义不改）

`/api/marketplace/*`（search/detail/download）——全部读卡包 manifest 即可支撑，底座无需为此预写代码。

## 第五部分 · 与现状的距离（诚实账）

| 项 | 现状 | 本规范要求 | 性质 |
|---|---|---|---|
| 卡物理格式 | works/ 数据区两卡，事实格式 | 卡包目录＋manifest 全字段 | 格式升格＋官方两卡重包装（内容字节不动） |
| 权限模型 | 仅雇主侧闸（类型白名单，与权限表打架） | 雇主侧改权限判据（解绑）＋**新增卡运行时授权层**（词汇表/状态机/关口/留痕） | 一处底座修改＋一层新增 |
| 装载 | 开机读单目录 | 双源目录＋每轮轻扫＋版本锁 | 装载层重写（fail-open 沿用） |
| 可见性 | 工具描述硬编码示例 | 上下文第七区＋run_tool_card 复核 | 上下文装配线修改 |
| 校验 | 无 | cardspec 校验器（一码三用）＋结构化报错 | 新增 |
| 接口 | 无 | 4.1–4.3 共 8 个端点/改造件 | 新增＋改造 |
| 市场 | 无 | 不做；仅 manifest 字段定死 | 远期 |

## 第六部分 · 红线（承前，不变）

官方两卡内容字节不动（md5 对账）；权限固化机制/schema 锁 1/全量留痕/restart_safe 零改动；前端交互层零碰（confirm 流程的后端语义先就位，界面后续接）；五铁律逐条不动；fail-open 沿用。
