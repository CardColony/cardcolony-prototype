## A. 功能背景（为什么做，全挂实测证据）

原信息流落地方案在本批降至「事件级过程可见」，三个缺口导致用户实际不可用，必须重出：

**缺口1 · 逐字流被砍（需求级）**：用户点名要「像其他 agent 一样看到全部过程」，但「token 级逐字流」（模型输出逐字显示）被标为 Phase 2 默认不做、未征求用户。结果：用户只能看到「🚀/🔧/✓」这类事件级大节点，看不到模型正在打的字。用户 09:49 怒斥「我他妈要你按照方案做」，需求级铁令已立：逐字流必须做，需求范围只由用户定。

**缺口2 · 长请求下反馈可见性无兜底（体验级）**：kimi-k3 单次主模型调用 `latency_ms=279500`（4.6 分钟，`_boot_5700_out.log` model=main）；用户 09:21 一条消息到 09:46（25 分钟）仍在工具循环未结束、无最终回复。系统回复模式＝整条跑完才回，前端长请求下无即时反馈；刷新补不出状态（超长请求「进行中」标志在服务端不可靠，`workspace.js` restoreFromHash→attachRunningState 活跃判定失效）。用户原话：「网页任意消息也没收到，刷新了也没用，之前刷新还能补出状态，现在连补出状态也没有」。

**缺口3 · 主模型可用性未治理（技术级）**：kimi-k3 在 Nous 端点默认 `reasoning effort=max` 全开，实测默认请求 `content=null`、全部输出在 `reasoning` 字段、`reasoning_tokens` 占满额度（Nous 实测）。旧验收无端到端时长判据，主模型极端慢不可用。

**不做留下什么**：继续「像 ChatGPT/DeepSeek 逐字流」不可得（缺口1）；发消息不可用级慢且无过程无反馈、刷新补不出态（缺口2）；主模型一动就 25 分钟（缺口3）。

### 2) 接口规范（前置输入／后置输出逐条定死）

**前置输入**：
- **逐字流输入**：模型调用时启 `stream=True`（gateway L543 已开）+ 传入 `on_chunk` 回调（接 routes/simple_service）；chunk 须同时解 `delta.reasoning` 与 `delta.content`（实证：kimi-k3 content=null、reasoning 有值）。
- **降 reasoning 输入**：models.yaml main 段 `extra_body` 加 `reasoning_effort`（或 reasoning.enabled）；Nous 实测 low/disabled 均生效。
- **刷新补态输入**：`/progress` 活跃判定 + `EventFlow.start(from=0)`；长请求下须保证活跃判定不因超时 stale。

**后置输出**：
- **逐字流输出**：前端双路逐字显示——🟡思考字实时蹦 + 📄正文字实时蹦，工具轮仍事件级（🔧）；结束折叠。
- **可用性输出**：kimi-k3 单次调用从 279.5s 降至秒级（降 reasoning 实测）；端到端消息可及。
- **反馈输出**：发消息即刻见思考流在动；刷新 from=0 补回过程与最终回复。
- **不动对象**：POST/T10/T14 契约零改动；事件不进 session/prior/模型输入；17 类事件本体论不破坏；works 数据零触碰。

## C. 预期效果（逐条可复核判据）

1. **逐字流可见**：模型调用时前端可见 🟡 思考字逐字蹦、📄 正文字逐字蹦（对照现状 content=null 无任何字）——判据：真请求期间 SSE 帧含 reasoning chunk 与 content chunk。
2. **发消息即时反馈**：发消息后 1 秒内前端出现思考流在动（对照现状 4.6 分钟无任何反馈）——判据：request 后 ≤1s 有首 chunk 显示。
3. **刷新补态不再丢**：长请求中刷新，过程与最终回复从 from=0 重放补齐（对照现状补不出）——判据：刷新后过程卡重建 + 最终回复在场。
4. **主模型可用**：kimi-k3 单次调用端到端可控（降 reasoning 后，对照现状 279.5s）——判据：单次 model=main 调用 latency_ms 显著下降（目标 ≤30s），消息端到端可及。
5. **事件级机制不破坏**：17 类事件本体论保留、事件不进模型输入、POST/T10/T14 契约零改动——判据：回归。
6. **需求级兑现**：逐字流被纳入本方案必做范围（不再标 Phase 2 默认不做）——判据：方案正文覆盖逐字流全部链条。
