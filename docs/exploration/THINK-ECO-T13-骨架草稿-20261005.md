（本稿为 p2 环节经 p3 红灯回归修订后的 v2 版：消红灯 1 行号误标、红灯 2 B2 扫描规则、关联窗口补 E7；正向覆盖 R-069~R-079 全落点。）

## 1. 功能背景

对话回复的上屏链路存在结构性问题——**回复只取「不带工具调用的那一轮」的正文**〔R-003〕：`routes.py:446-447` `if not tool_calls: final_reply = assistant_content`，只有 `tool_calls` 为空的轮次正文才进 `final_reply`〔R-005〕。落盘型工作流的分析正文全部写在**带工具调用的轮**里，而那几轮的 content 只进 `prior_for_gateway` 与 prompt 日志、**不进会话、不进 reply**〔R-006〕；最终回复、解析、落盘全绑定末轮 `clean_text`（`routes.py:541` parse、`:546` append、`:552` reply）〔R-009/010/011〕。收官轮手里只剩收据，**分析结构性不上屏**〔R-004〕。

**需求成立有盘上实证**（`session_025.md` 对照）——同一段分析两个版本：16:18 那条因同时带 `edit_card`／`write_file`／`update_shadow` 按末轮判定被丢弃、不上屏，会话只落一条回执；16:41:57 重发那条不调工具、进 `resp.reply` 上屏且进会话〔R-027/028〕。该轮实际产出 **5 段** assistant 正文、会话只落 **1 条**〔R-026〕。**同一段文字，挂在哪一轮，决定它到不到用户眼前**〔R-029〕。

用户诉求（原话在册）：「我认为它应该是做了分析的，只是我没收到」〔R-019〕「我要看到的是那轮综合观点」〔R-020〕。内核一句：**分析的交付目的地，从「卡片／文件」扩展到「对话」；且不得取代回执**〔R-022〕。需求判定五条必须（R1 分析正文进对话／R2 回执不丢排后／R3 对话会话一致／R4 配对不变／R5 send-resend 同源）〔R-034~038〕。

不做会留下什么：用户继续只见结果清单、不见分析正文；「分析与回执争同一条独木桥、最后一个说话的人赢」〔R-033〕；建卡提案被夹在工具轮里、因 `parse_proposals` 只扫末轮而无法兑现〔R-009〕。结构后果三处丢弃点叠在同一链路上〔R-030/031/032〕。

## 2. 项目位置与接口规范

### 输入接口

- **一轮调用的全部 assistant 轮次正文**——源头为 `_run_message` 工具循环各轮 `assistant_content`（含带 `tool_calls` 的轮，`routes.py:463-475` 当前只进 `prior_for_gateway`）〔R-006〕；含被 `text_tool_rescue` 抢救处理后的正文（`routes.py:434`）。
- **parse_proposals 扫描输入**——当前为 `final_reply`（末轮 clean_text，`routes.py:541`）〔R-009〕；本方案使扫描输入覆盖「分析＋回执」拼接后全文（B2 行为变化登记，〔R-059〕）。
- **三席观点全文**——**不是本功能输入**。回流铁则：观点全文不进 `prior_messages`、不进 `session`（`simple_service.py:13`，既有设计，R6 本轮不做）〔R-043/R-039〕。

### 输出接口

- **回复 reply**——`routes.py:552` `"reply": clean_text`，消费方前端 `workspace.js:492`（send）／`:587`（resend）〔R-013/014〕；判据要求分析＋回执进 reply（R1/R2）〔R-034/035〕。
- **会话落盘**——`routes.py:546` `append_message(..., "assistant", clean_text, model=model_used, pair_id=pair_id)`〔R-010〕，消费方 `session_store`（签名 `model=None, pair_id=None` 不动，会话格式零改动）〔R-016/R-042〕；判据：会话 assistant 条与 reply 逐字相等（R3）、配对 1:1 不变（R4）〔R-036/037〕。
- **日志**——`routes.py:511` `response=final_reply if error is None else None`〔R-008〕；红线：`prompt_log.response` 语义不动（仍记末轮）〔R-047/R-055〕。
- **建卡扫描（行为变化 B2）**——`routes.py:541` 扫描输入扩到拼接后全文：工具轮若含 `card-proposal` 块、此后会真建卡〔R-059〕，须在验收中见证〔R-068〕。

## 3. 预期效果（逐条编号）

- **E1（R1＋R2，必须）分析正文进对话、回执不丢且排在后**——对含工具调用的请求，`resp.reply` 同时含先前轮次的实际分析正文与末轮回执，分析在前、回执在后；用 `session_025` 同型真实请求实测，改造后 reply 中能读到此前被丢弃的分析正文〔R-061〕。
- **E2（R3，必须）对话与会话一致**——前端上屏的 reply 与会话对应 assistant 条逐字相等；刷新/切换卡（`workspace.js:472` 走 `renderChat` 从会话重建）后显示与首次一致〔R-063〕。
- **E3（R4＋R5，必须）配对语义与重发行为不变**——一次请求仍 1 提问 1 回复、pair_id 对应关系与改造前一致（T10 不变量）〔R-037〕；send 与 resend 共用同一后台逻辑、重发回复同样含分析正文〔R-065〕。
- **E4（回归，必须）纯对话轮与旧会话兼容**——不含工具调用的纯对话轮，改造前后 reply 逐字相同〔R-064〕；旧会话文件零新增字段、原样可读、无迁移〔R-050/R-057〕。
- **E5（B2 风险受控，必须见证）建卡扫描面扩大可见**——正文夹 `card-proposal` 协议块的请求，`parse_proposals` 扫到并产出真实建卡；无协议块的普通分析正文不误扫出伪提案；两条均实测见证〔R-068〕。
- **E6（边界与失败，必须）空正文与失败路径不破坏**——末轮空→只交付中间轮分析正文；两空→空回复、不报错不产生多余会话条〔R-067〕；调用失败时 `prompt_log.response` 语义与改造前一致〔R-047〕。
- **E7（关联窗口，必须）simple_service 首轮路径不受影响**——`simple_service.py:50` 也调用 `parse_proposals`（首轮统合输出过解析，既有行为）；本改动只改 `routes.py:541` 调用点的输入，`simple_service.py:50` 的输入仍是首轮统合输出、不随拼接变化〔R-076〕；完成判据须含该路径回归确认。

## 4. 方案正文（实现设计）

**设计总纲**：病灶是三处丢弃点（带工具轮正文不 append 会话／reply 只取末轮／前端只渲染 reply 一条）叠在同一条链路上〔R-030/031/032〕。方案只动第一处与第二处的接口——**把「带工具轮的分析正文」采集起来，与「末轮回执」按分析在前、回执在后拼接成同一份交付全文**，然后让回复、落盘、解析三处全部走这份拼接全文；日志 `response` 例外、独立保持末轮（红线 8）。改动限制**只改 routes.py 一个文件**〔R-048/R-056〕。

**改动点 1 · 采集分析正文（带工具轮）**

- 在声明位 `routes.py:390` `final_reply: Optional[str] = None`〔R-007〕旁新增局部变量 `analysis_parts: list[str] = []`。
- 在带 `tool_calls` 轮的 append 处（`routes.py:463-475`，**该轮 `assistant_content` 当前仅 `prior_for_gateway.append(...)`**——注意 L458-461 是 `rounds==1` 的用户原文固化、非 assistant 正文，勿混淆）（实读 routes.py:440-484，call_bb6d1ab2 定案）〔R-006〕：同步将该轮 `assistant_content`（抢救处理后的正文，`routes.py:434`）追加进 `analysis_parts`。
- **只收带工具轮的正文**——纯对话轮（无 `tool_calls`）走 `final_reply` 分支（`routes.py:446-447`）〔R-005〕，不进 `analysis_parts`；对齐「不设闸、不截断、不封顶轮次」〔R-045/R-053〕，`analysis_parts` 全量收集、不限长。

**改动点 2 · 拼接「分析在前、回执在后」**

- 落位：`routes.py` 工具循环结束、**日志写入之后**（`routes.py:511` 之后）、`parse_proposals` 之前（`routes.py:541` 之前）插入拼接段。
- 拼接式：`delivered = "\n\n".join(analysis_parts + [final_reply])`——分析在前、回执在后、`\n\n` 分隔（待裁定 1 默认）〔R-069〕。
- **V7 边界**〔R-067〕：`analysis_parts` 非空且 `final_reply` 空 → `delivered = "\n\n".join(analysis_parts)`（只交付中间轮）；两者皆空 → `delivered = ""`（空回复）；`final_reply` 非空且 `analysis_parts` 空 → `delivered = final_reply`（纯对话轮原样、回归不变）。
- 拼接后 `final_reply = delivered`。
- **落位顺序是命门**：拼接段必须插在日志写（`routes.py:511`）**之后**、解析（`routes.py:541`）**之前**——插在日志前会污染日志语义（红线 8，〔R-047/R-055〕）。

**改动点 3 · 日志 response 保持末轮（红线 8 独立保留）**

- `routes.py:511` **本行不动**，`response=final_reply if error is None else None` 保持原样〔R-008/R-047〕。因改动点 2 的拼接插在 L511 **之后**，此时 `final_reply` 仍是末轮 clean_text——日志 `response` 自然保持末轮、语义不变，供审计对照。此顺序不可挪。

**改动点 4 · 解析／落盘／返回全部走拼接全文**

- `routes.py:541` `clean_text, proposals = card_proposal.parse_proposals(final_reply or "")`〔R-009〕——扫描输入＝拼接后全文（含分析正文），B2 兑现。**扫描规则定格（p3 第 6 问修正，署「诸葛定，用户可推翻」）**：扫描输入＝`delivered`；`parse_proposals` 照既有机制运行（`card_proposal.py:151-159` 双形态提取＋`L141-145` 按 `card-proposal:` 协议头识别，**不新增筛选逻辑、守不设闸**）；误扫防护靠既有协议头识别（普通分析正文不含协议头即不命中）；验收 V8 用含／不含协议块的真实分析正文双侧实测见证〔R-068〕。
- `routes.py:546` `append_message(..., "assistant", clean_text, model=model_used, pair_id=pair_id)`〔R-010〕——落盘＝拼接后 clean_text（R3 一致：reply 与落盘同一 `clean_text` 变量）〔R-036〕。
- `routes.py:552` `"reply": clean_text`〔R-011〕——返回＝拼接后 clean_text（R1/R2 达成）〔R-034/035〕。
- **配对不变**：仍是单次落一条 assistant（`routes.py:546` 一次 append_message），pair_id 原样传入〔R-037/R-051〕；B3「assistant 条变长但仍一条、配对 1:1」由这条保证〔R-060〕。

**改动点 5 · 回归与兼容防线**

- 不新增字段（`session_store.py` 签名 `append_message(..., model=None, pair_id=None)` 不动）〔R-016/R-042/R-050〕；纯对话轮经改动点 2 分支 `delivered = final_reply` 原样、reply 与现状逐字相同〔R-064〕；旧会话文件读取路径不受影响〔R-057〕。
- `simple_service.py:50` 关联面：**本改动不动该行**（其输入仍是首轮统合输出、不经过拼接段），仅确认回归不受影响〔R-076〕。
- 只改 `routes.py` 一个文件的红线〔R-048〕由改动点 1/2/4 全部落在 routes.py 内保证。

### 全日志打点

- **prompt_log.response**（`routes.py:511`）——**语义保持不动**（红线 8〔R-047/R-055〕）：仍记末轮 `final_reply`（拼接前值）。因拼接点在 L511 之后，此行为天然满足；不改本行，只加一行注释说明「response 保持末轮供审计；交付全文（分析+回执）可经会话 / prompt 日志 regions 复核」。
- **拼接动作打点**——新增一行日志（走既有 logger，不新增日志类型）：`analysis_parts` 段数、拼接后字节数 vs 末轮字节数、命中 V7 哪一分支（正常拼接／只交付中间轮／空回复／纯对话原样）。这是 B1「单条回复变长」〔R-058〕与拼接行为的审计可见性。
- **建卡扫描面观察点**——`routes.py:541` 处新增日志：`parse_proposals` 实际扫描输入的段数与首末段字节——对应 B2「须在验收中见证」〔R-059/R-068〕，使「扫描输入是否含工具轮正文」可事后审计。
- **失败路径**——`error is not None` 时日志 `response=None`（`routes.py:511` 既有分支）保持不变〔R-047〕；拼接动作在失败路径不执行、`analysis_parts` 不写任何长期存储。
