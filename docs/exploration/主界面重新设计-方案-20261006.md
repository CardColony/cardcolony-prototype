## 〇、结语（三句话）

## 三、设计定案

### 3.1 总形态：三联外壳（App Shell），取代「画布页 ＋ 全屏覆盖面板」

```
┌──────────┬────────────────────────────────────────────┐
│          │  topbar（面包屑 · zoom · 整理 · ＋新建卡）      │
│  app-nav ├────────────────────────────────────────────┤
│  （左）   │                                            │
│  44 / 260│   stage（主视图，二选一）                    │
│   px     │   ├ #viewport  画布（默认）                  │
│          │   └ #workspace 对话区 ＋ inspector（右，320）│
└──────────┴────────────────────────────────────────────┘
```

**结构重排（不是加浮层）**：`.work-page` 由 `column` 改 `row`；新增 `.app-nav`（恒在）与 `.app-main`（`flex:1; column`）；`.app-main` 内新增 `.stage`（`flex:1; position:relative`），`#viewport` 与 `.workspace` 改为 `absolute; inset:0` 互斥显隐。

**三态（由 `.app-main[data-view]` 驱动）**

| 态 | 左 nav | 中 stage | 右 inspector |
|---|---|---|---|
| **画布态**（默认，用户第 1 条） | 44px 窄条 | 画布占满 | 收起 |
| **卡片对话态** | 260px 导航树 | 对话区 | 320px，**默认收起** |
| （无第三态） | 项目切换由 nav 的分组头承担；剧本架页保留为「新建项目」入口 | | |

**不设「项目列表态」**（§9.3 曾有）——nav 的分组头已覆盖项目切换，另立一个态是多余层级。【模型自定】

### 3.2 对话导航栏（本令核心交付）

**数据结构**：`项目分组头 → 卡片树`。

- **一级＝项目根卡（`work.json.work_card_id`）的直接子卡**；根卡自身作为分组头显示，**不**在树里重复列一项。
- **层级口径写死：以项目根卡为第 0 层**。⚠ 与画布 `state.viewRoot` 派生的「相对深度」**是两个口径，不得混用**（画布随下钻变，导航恒定）。这是本设计最易出错的一致性陷阱。
- **层数不封顶**【模型自定】：用户说「一级／二级」是最浅形态；封在两层的后果是**深卡从导航里进不去**，等于把用户第 3 条的「导航」降级成「目录预览」。默认展开＝**一级 ＋ 当前卡所在路径**，其余折叠。
- **排序由服务端给**（§4），前端**按收到顺序原样渲染**，不二次排序——保证与服务端口径一致。

**行规格**

| 元素 | 内容 | 交互 |
|---|---|---|
| 分组头 | `▾ 项目名 · N 卡 · 2 小时前` | 点击折叠／展开；当前项目高亮；悬停出「＋ 新建卡」 |
| 卡片行 | `▸ 标题` ＋ 右侧相对活跃时间 | 点击＝切到该卡对话；当前卡高亮（左 2px 强调条＋底色）；悬停出 `⋯`（建子卡／卡详情） |
| 展开钮 `▸/▾` | 仅 `child_count > 0` 显示 | 只翻展开态，**不切卡**（与画布 `toggleExpand` 同语义） |
| 空态 | 「还没有项目」＋「＋ 新建项目」 | 跳剧本架新建 |

**窄条态（44px）**：只显示 `☰` ＋ 当前项目色点；悬停浮层显示完整树【模型自定：保留而非整栏隐藏，理由＝随时换项目，不必退回剧本架】。

**不做**：搜索框、过滤器、拖拽排序、「运行中」转圈（后者依赖 `/progress`，而进度是**进程内存态、刷新即失**——card_006 §七.4）。

### 3.3 Inspector（右栏）：卡片编辑能力的**搬迁**，不是删除

- **内容原样搬入**（顺序不变）：标题＋类型徽章＋来源 → 职责区（charter）→ 结论区（conclusion）→ 否决记录 → 关系（含添加行）→ 修改历史 → ＋建子卡 → 危险操作（删卡，剧本站不显）。
- **依据**：这三块是「卡的真身」，系统其他部分依赖（**结论区＝卡片间唯一接口**，card_007 §八），**不得因左栏改导航而消失**。
- **默认收起**，32px 竖条带 `ⓘ` 触发；展开 320px。对话区头部亦有「ⓘ 卡详情」与「← 画布」两个按钮。
- **分工一句话**：**左区走、中区谈、右区改。**

### 3.4 顶部与返回

- 顶栏保留（面包屑／zoom／整理／＋新建卡 全不动），位于 `.app-main` 顶部、**右侧于 nav**。
- 「← 返回画布」＝切 `.app-main[data-view]` 回 `canvas`；**必须是纯显隐切换，不得再走 `reloadCanvas()`**（见 §6 风险 R-1）。

### 3.5 视觉规格（设计权范围内，直接定）

**对齐现状色板**（`style.css:7-38` 的 `:root`），不引入新色：

| 项 | 值 |
|---|---|
| 字号／行高 | 卡行 13px／30px；分组头 11px（`var(--dim)`，letter-spacing 1px，同 `.blocktitle` 口径） |
| 缩进 | 每层 +14px |
| 悬停 | `background: var(--panel-hover)`（`#1c2128`） |
| 当前项 | `background: rgba(56,139,253,0.10)` ＋ 左 2px `#58a6ff` 强调条 |
| 时间 | 右对齐，11px，`var(--dimmer)`；每 60s 重算，格式「刚刚／N 分钟前／N 小时前／N 天前／YYYY-MM-DD」 |

**证据等级如实说明**：本机**无「通用 agent」界面实物参照**（`trading-workspace` 下是另一项目的深蓝／青绿 dashboard，风格无关）。上表系按**会话侧栏通行范式**（ChatGPT／Claude／Cursor 一类）描述，非抄本机实物。

## 四、数据层：「最后活跃」从哪来

### 4.1 权威来源

**卡级活跃 ＝ `max(该卡会话文件末条消息的 timestamp, 卡前置字段 updated_at)`**

- 会话末条 ＝ 聊天活跃（**这条是关键**：光聊天不改卡时，`updated_at` 不动，只用它会把天天聊的卡排到下面，正好排反）。
- `updated_at` ＝ 兜底（从未聊过、但被编辑过的卡）。
- 项目级 ＝ `max(该项目所有卡的卡级活跃, work.created_at)`。

**被否备选**：①文件 mtime（备份／恢复会改写 mtime——本项目刚从 git 回退事故里恢复过，`VERSIONING.md` 有案）②拿 `canvas.json` 缓存当来源（见 §4.4）。

### 4.2 现算，不缓存

**每次请求从真身现算**（卡前置字段 ＋ 会话末文件尾）。理由：任何缓存都要处理失效——而**聊天不触发卡写入、也不触发画布重建**，缓存必然滞后（§4.4）。

- 成本：本库 3 项目 × 约 20 卡 ＝ 数十次小文件读；最大会话 86KB。
- **实现纪律**：取「末条时间戳」**不得复用 `read_session()`**（它全量解析全部消息，`session_store.py:107`）——须从**文件尾部反向扫描**若干 KB 找最后一个 `timestamp:`（或等价 O(tail) 读法）。
- 后续优化（**不在本方案**）：按 `mtime` 记忆化，命中即跳过。

### 4.3 端点设计（新增 `GET /api/nav`）

**一次请求拿全导航树**（避免「先 `/api/works` 再逐项目 `getCanvas`」的 N+1）：

```json
{"projects": [
  {"work_id": "work_002", "title": "推演agent", "work_card_id": "card_001",
   "last_active_at": "2026-10-06T18:38:01+08:00", "card_count": 19,
   "cards": [
     {"card_id": "card_018", "title": "主界面设计", "parent": "card_007",
      "child_count": 0, "last_active_at": "2026-10-06T18:38:01+08:00"}
   ]}
]}
```

**排序契约（服务端负责，前端不重排）**：
1. `projects` 按 `last_active_at` **降序**；
2. 每个项目的 `cards` 按 `last_active_at` **降序** → 前端按 `parent` 归组后，**同级兄弟天然降序**（因为父卡的活跃度不影响子卡相对顺序，只需保证同一父下的相对次序＝全局降序的相对次序）；
3. 无时间者排末位；并列时以 `card_id`／`work_id` 升序**稳定**收尾（保证刷新不跳序）。

**孤儿卡**（`parent` 指向已删卡）挂到该项目**根层末尾**，不丢弃。

**另需**：`/api/works`（`work_store.py:49`）改为附 `last_active_at` 并按其降序——它同时供剧本架页使用，两条路径口径必须一致。

### 4.4 为什么**不能**把活跃度写进 `canvas.json`

`canvas.json` 自称「可重建缓存」（`canvas_store.py:1-3`），且 `rebuild` 只在**卡片变更**时被调用——**聊天不触发重建**。若把 `last_active_at` 附进 canvas.json：

- 用户聊完天，缓存里的活跃度**不变** → 排序不动 → 用户第 4、6 条**静默失效**；
- 且 `canvas_store.load()`（`:159`）命中已有缓存就**直接返回、不重建**，新字段在存量项目上**永远不出现**。

⇒ **结论：活跃度必须是请求时现算的真身派生值，不得入缓存。**

| # | 风险 | 处置 |
