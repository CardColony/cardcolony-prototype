### ③ `72ch` 实测 —— 与用户诉求冲突（关键判断）

规格 §13.3 与规格件 §3.1 都把助手侧宽度写成 `max-width: 72ch`。我**用无头浏览器实测了这个值**：

| 量 | 实测值 |
|---|---|
| `72ch` 实际宽度（14px，`--font` 字体栈） | **543.4px** |
| 单个汉字宽度（14px） | **14.00px** |
| 折合每行汉字数 | **38.8 字** |

⇒ **`72ch` = 543px，比现状 720px 更窄**（少 177px）。

**结论**：规格里的 `72ch` 与用户今天「自适应窗口」的诉求**方向相反**。若照规格落地，正文会比现在更窄、右边空得更多。

**本次处置：以用户诉求为准，`72ch` 不作为宽度目标**。理由：用户是最终裁定者，且本次指令晚于 10-07 规格；规格的立法意图是「给行宽定一个可读上界」，本次仍保留上界（见 §四·M2），只是上界值与实现机制不同。

### M2 · 宽度自适应

**现状**：`max-width: min(82%, 720px)`（`style.css:1060`）——宽屏下**永远 720**（不跟随窗口），窄屏下 82%（跟随）。**"不跟随"正是病根**。

**设计**：

```css
:root {
  --read-max: 60em;          /* 可读上限：14px 下 = 840px ≈ 60 汉字/行 */
}
.msg {
  max-width: min(100%, var(--read-max));   /* 原 min(82%, 720px) */
}
```

- **跟随窗口**：`100%` 相对 `.chat` 内容盒 ⇒ 窄窗口占满、宽窗口封顶
- **可读上限**：`60em`，14px 下 840px（60 汉字/行）
- **短消息不被拉伸**：`.msg` 是 `align-self: flex-start/flex-end` 的 flex item，无 `width` 声明 ⇒ 自然 fit-content 宽度，`max-width` 只封顶

**三档实算**（`.chat` 内容宽 → `.msg` 实际宽）：

| `.chat` 内容宽 | 现状 `min(82%, 720px)` | 本次 `min(100%, 840px)` |
|---|---|---|
| 1344px（1680 宽屏） | 720px（空 624） | **840px**（空 504） |
| 800px | 656px | **800px**（占满） |
| 500px | 410px | **500px**（占满） |

**这个 `60em` 是本次唯一一个由我定的数，也是最可能需要调的**：

| 方向 | 后果 |
|---|---|
| 调大（如 `72em` = 1008px ≈ 72 汉字） | 宽屏下更满，但行长接近上限、阅读时视线回扫距离变长 |
| 调小（如 `48em` = 672px ≈ 48 汉字） | 更省眼，但宽屏下空得更多 |

依据：中文屏幕阅读的舒适行长经验区间约 35–50 汉字，宽松上限约 60 汉字。840px ÷ 14px ＝ 60 汉字，取宽松上限。**改一个变量即可调整，不需要动其他任何地方。**

### M3 · `white-space` 接缝（必做，否则渲染出来是双倍行距）

`.msg` 现为 `white-space: pre-wrap`（`style.css:1066`）。Markdown 渲染出的 HTML **带标签间换行**，在 `pre-wrap` 下这些换行会变成**可见空行**（每块之间多一行）。

**处置**：只对助手侧解除，用户侧保持原样——

```css
.msg.assistant { white-space: normal; }   /* 加在 style.css:1069 */
```

- 用户消息保持 `pre-wrap`（其换行由 `formatMsgContent` 的 `\n`→`<br>` 承担，改不改都行，但**不动更稳**）
- 代码块不受影响：`.msg pre` 自带 `white-space: pre`（`style.css:1079`）
- 流式期间不受影响：`.live-content` 自带 `pre-wrap`（`style.css:1382`），且接管时 `innerHTML` 被整体替换（`workspace.js:784`），`.live-content` 随之移除
