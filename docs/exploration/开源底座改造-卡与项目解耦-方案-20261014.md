# 开源底座改造 · 卡与项目解耦 · 方案 v2（2026-10-14）

> 性质：设计方案（未施工）。用户令：先讲清怎么改、与现状差多大；不接受临时改法，一切以最终图景为准；不接受「能走通」级方案，按全生命周期最优做。
> 范围裁定（2026-10-14 18:35–18:51 用户三轮）：底座层；交互层不做（另行排期）；市场本体不做（远期运营层）。
> 最终图景一句话：**卡＝完全独立的单元——独立分发（卡包）、独立于项目类型（生效范围自选）、装上即通（四条链路自动接）；项目类型只管树怎么搭。**
> v2 变更：①装载时机改每轮轻扫（消灭重启依赖）；②新增实例版本锁（卡包更新/删除与在跑实例隔离）；③同名优先级反转（用户目录盖官方目录）；④如实标注四处「真·底座修改」（非纯加法）；⑤补工具表动态化的契约治理影响。

## 0. 现行系统的一处自相矛盾（改造正当性 · 实证）

- `config/permissions.json`：`research_project.topic` 的开关清单**含 `invoke_tool`**（权限层说：课题卡能调工具卡）。
- `src/storage/card_store.py` L55-61：`TOOL_CARD_OWNER_TYPES = ("sub_project", "project")`，闸3 按**类型白名单**判 owner 资格（闸口说：topic 不能）。
- 后果：topic 卡调 `run_tool_card` → 工具面可见（有 invoke_tool）→ 建卡被闸3 拒 → 报错。**权限说能调、闸口说不能**，两套判据打架（即 card_tools.py ~L750-757 挂着的「topic owner 被闸3 拒·待用户裁」旧问题）。
- 根因：资格判定放错了层——按类型（封闭集合）判，而不是按授权（开放集合）判。机制二落地后此矛盾自动消解，无需逐类型裁定。

## 二. 卡生态全生命周期设计（v2 核心）

一张卡从下载到退役，七个环节逐一定义行为——不留「不知道该怎样」的灰色地带：

| # | 环节 | 会怎么坏（朴素改法的 bug） | 全盘设计 |
|---|---|---|---|
| ① | 装载时机 | 开机扫一次：下载后须重启才生效，用户以为坏了 | **每轮对话前毫秒级轻扫**（目录 mtime 快照比对，无变化零成本）；装了立刻生效，永不重启 |
| ② | 卡包更新 | v2 覆盖 v1，在跑实例立刻错乱（跑到第3步内容已被换） | **实例版本锁**：卡实例出生时快照剧本版本＋提示词内容哈希，跑着的用快照跑完，新实例用新版 |
| ③ | 卡包删除 | 删包→实例孤儿→下一步找不到提示词，死锁 | 版本锁自带的干粮跑完；快照不完整（历史实例）→ 明确报「来源卡已移除」，不死锁不装死 |
| ④ | 同名冲突 | 官方同名卡优先级高，用户下载的社区版永不生效 | **用户目录盖官方目录**（用户显式动作 > 出厂默认）；合并结果留痕 |
| ⑤ | 坏包进入 | 文件残缺/引用断裂/权限声明不合法 | 结构校验闸（manifest 可解析／script 可解析／prompts 引用全存在／required_perms ⊆ SWITCHES）；坏包跳过＋留痕，不传染。**诚实边界**：提示词内容好坏不可机械判——那是市场上架审核的地盘 |
| ⑥ | 中断恢复 | 断电/崩溃停在半路 | 现有断点续跑机制（状态在卡上）＋版本锁保证提示词稳定，续跑不歪 |
| ⑦ | 卡数量增长 | 50 张卡撑爆模型视野 | 「可用卡」区紧凑渲染（一行一卡：名＋一句话）；量大时的相关性排序**预留口子不实现**（满负荷实测后再裁） |

**用户视角只有三步**：下载（文件落目录）→ 说一句话（AI 从「可用卡」区自己发现、自己决定用）→ 得到产出。装载/验证/版本锁/生效范围/权限/断点全部机械接管。

## 三. 三大机制终态

### 机制一：卡包体系（E＋C 部分）

**格式**：一个文件夹＝一张可分发卡。

```
<卡包根>/<card_name>/
  manifest.json     # name/version/author/display/description/when_to_use/required_perms/min_base_version
  script.json       # 流程剧本（toolcard/script_loader 现有格式逐字不动）
  prompts/*.txt     # 步骤提示词（prompt_ref 引用方式不变）
```

**双源目录**：官方 `cardpacks_official/`（随代码仓）＋用户 `works/cardpacks/`（市场下载落点）。同名时**用户源优先**（环节④）。

**模型可见性**（动骨项 B）：上下文装配线新增第七区「可用卡」，从 manifest 渲染（display＋description＋when_to_use 一行），**按当前树生效范围过滤**（机制三）。`run_tool_card` 工具描述删除硬编码示例「如方案链」，改为「可用卡清单见上下文可用卡区」。

**契约治理**（动骨项 C 关联）：run_tool_card 的 schema 文本变化 → TOOL_TABLE_VERSION 递增（既有纪律）；edit_card 按树动态拼装 → 版本化从「全表文本指纹」调整为「结构版本＋按树渲染」——每树的实际 schema 随 prompt 日志照常全量留痕，对账口径不变（日志里看到的即是模型收到的）。

### 机制二：解绑（A）

- 闸3 判据：`owner 的固化 perms 含 invoke_tool`（`policy.has_perm(owner_meta, SWITCH_INVOKE_TOOL)`）。
- `TOOL_CARD_OWNER_TYPES` 常量退役（留过渡注释，随化石清理批次删）。
- permissions.json / 固化机制 / has_perm：**零改动**（topic 已含 invoke_tool，自然放行）。
- registry `gate_3_owner_required.desc` 同步改写（两处口径一致纪律）。

### 机制三：生效范围（F）

- `works/cardpacks/installed.json`：`{ "<card_name>": {"enabled_scopes": ["*"]|["rd_project",...], "pinned_version": "..."(可选)} }`。缺省＝`["*"]`。
- 双语义过滤（权限口径同源）：未对当前树生效的卡＝「可用卡」区不渲染（看不见）＋ `run_tool_card` handler 复核拒绝（调不动）。
- 与 required_perms 是两道独立闸：范围管「这棵树用不用」，权限管「雇主卡够不够格」。

### 类型插口六件（D＋C＋G）

| # | 现状（实证行号） | 终态 |
|---|---|---|
| 1 | 类型词表住 config/ 单文件 | `typepacks/` 目录包＋装卸扫描合并；rd/research 转出厂官方包 |
| 2 | CreateWorkRequest 只有 title；work_store 默认 rd_project | 后端入口收 project_class，校验＝已装类型包；缺省保持官方研发包（前端零感知） |
| 3 | routes.py `_apply_block_set` L57-89 / card_tools.py L226/L244-246 硬编码分支 | 第三块名查类型包 `block_names` 声明；代码零类型码字面量 |
| 4 | NEW_CARD_SKELETON 全局一份；default_template 零消费者 | 骨架按类型包模板渲染，取不到回落全局默认；激活预留字段 |
| 5 | edit_card 描述写死三块名＋条目语法 | 描述按当前树类型包动态拼装（结构版本治理见机制一） |
| 6 | permissions.json 独立表 v2 | 格式不动；条目随类型包携带进装卸口；policy.py 零改动 |

## 五. 红线（全期）

1. 现有两张卡内容**字节不动**（md5 前后对账）。
2. 权限固化机制、schema 锁 1、全量留痕、restart_safe——零改动。
3. 前端/交互层零碰；旧调用路径行为不变（create_work 缺省、旧 run_tool_card 调用）。
4. 五铁律逐条不动；fail-open 口径沿用（装载失败留痕降级，不阻断启动）。
5. TOOL_TABLE_VERSION 递增纪律遵守；prompt 日志照常全量（日志即模型所见）。
6. 每期独立交付：pytest 全绿（零新增失败）＋施工回报（证据优先）。
