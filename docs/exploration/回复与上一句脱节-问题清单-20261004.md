## 三、定位到的机制问题

### P1（主因 · 对应 S1）提问与回复之间没有配对标识，靠「追加顺序」隐式绑定

证据链：

1. **写路径无锁**：`session_store.append_message`（`session_store.py:55-70`）以 `aiofiles.open(mode="a")` 追加，**无任何并发保护**。对比 `card_store.py:43-72` 项目已有「每文件路径一把 asyncio.Lock」的现成模式——会话层未采用。
2. **消息无配对 id**：消息字段只有 `role / timestamp / model`（`session_store.py:55-70` 头部三/四行）；全库搜 `request_id` **零命中**（`src/` 35 文件 0 命中）。
3. **回复在「完成时」按顺序追加，不绑定所答之问**：`routes.py:514` 处理完才 `append_message(..., "assistant", ...)`。
4. **前端按「到达顺序」渲染，不校验对应哪条提问**：`workspace.js:419-500 send()` 拿到 `resp.reply` 即 `appendMessage` 到界面末尾。
5. **加重项**：前端 `resend()`（`workspace.js:528-543`）注释自陈「不重复追加用户消息，直接重调接口」，但后端 `postMessage → _run_message` **仍会再 append 一次用户消息**（`routes.py:346`）——即每次重发都在 session 里多落一条提问、多落一条回复。

**实盘实证**（`works/work_002/sessions/session_005.md`）：

- 用户「那三张卡删了」出现两次：`15:54:20`、`16:11:38`；
- 随后两条 assistant：`16:15:53`、`16:16:24`（间隔 31 秒）；
- 文件顺序 = 追加顺序：`user(15:54) → user(16:11) → assistant(16:15) → assistant(16:16)`；
- **于是读者看到的顺序是：用户 `16:11` 那句之后，紧跟着的是 `16:15:53` 那条——而它实际答的是 `15:54` 那句。** 前一条请求耗时约 21 分钟，用户在等待中重发了同一句。
- 即：S1「回复接的是前一句」在这里有完整的时间戳复现。

**结论**：错位不是「历史丢了」，而是「**提问 ↔ 回复的配对不可靠**」——长等待 → 用户重发 → 多条请求在途 → 回复按完成时间追加，落在错误的位置。

### P2（主因 · 对应 S2）三思考席观点匿名拼在「用户原话」之后注入统合官

**证据**：`simple_service.py:46-56 build_viewpoint_prompt`

```
sections = "\n\n".join(f"### 输出 {i + 1}\n{m['text']}" for i, m in enumerate(ok_metas))
return f"{user_prompt}\n\n{VIEWPOINT_HEADER}\n{sections}"     # VIEWPOINT_HEADER = "## 其他模型的输出"
```

观点**按序号标注、不带模型名、不带来源**。

- 后果 A（稀释）：统合官看到的「当前提问」后面拖三段他人分析 → 倾向「综合观点」而非直接回答那句短话。
- 后果 B（带偏）：某席幻觉与正确席并排、等权、无来源标记，统合官无从判断可信度。
- **实盘实证**：`logs/prompt_card_012_20261003215154.json` —— 用户问「什么意思？你执行了什么？」，三席其一（qwen）产出**反向幻觉**（自称「什么都没落盘、上条是幻觉」），与另两席相反，且注入时不带来源。
- **背景（重要）**：去模型名是 2026-10-02「职责分离裁定」的**有意**决定（`simple_service.py:36-38`，为防统合官滑向「裁决者姿态」）。代价即上面两条 → **是否恢复来源标记，需裁定。**

### P3（次因 · 对应 S2）历史里的 assistant 不含工具痕迹

**证据**：`routes.py:472` `prior_for_gateway = [{"role": ..., "content": ...}]` 只取两字段；assistant 历史存的是 `clean_text`（`routes.py:514`，已剥协议块）。

- 后果：模型下一轮看不到「我上轮调过什么工具、建了什么卡」，易重复劳动或失忆式作答。

### P4（审计缺口 · 加重以上三条）

`prompt_{card_id}_{timestamp}.json` 与 session 消息之间**无 id 关联**（`prompt_log.py:36`）。事后想对账「这条回复对应哪条提问、用的哪份上下文」，只能靠时间戳凑——而 P1 已证明「多条在途」时时间戳不足以定序。项目卖点之一是可审计，此处是洞。

## 五、待裁定

1. **P1 修法取向**：给消息加配对 id（提问 id ↔ 回复 id）／会话写加锁／前端禁止重发重复落盘——三者取哪些、先后如何。
2. **P2**：三席观点注入时是否恢复来源标记（或改为「来源可查但不显名」）。
3. **P3**：历史 assistant 是否附带工具调用摘要。
4. **P4**：prompt 日志是否写入所答提问的 id。
5. **归属**：本清单与 card_015「卡片各自上下文机制」／card_002「上下文记忆系统」的边界（card_016 自定「只谈卡实体」）。
