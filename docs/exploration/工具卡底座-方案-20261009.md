## 三、底座形态定义：底座与工具卡的分工边界

### 3.1 底座是哪一层

**底座 = 「让一张工具卡按剧本、一步一步、自动跑完，且每步产出与状态都留痕、且能保证跑完」的通用机制。**

它**不是**某条链的内容（方案怎么写＝剧本的事），**也不是**卡片分类体系（已有）。

### 3.2 分工表

| | 底座负责（管"怎么跑"） | 剧本负责（管"跑什么"） |
|---|---|---|
| 内容 | D1 剧本装载 / D2 步骤推进 / D3 状态持久化 / D4 产物落库 / D5 完成判据 / D6 终态收口 | S1 步骤定义 / S2 每步提示词 / S3 判据内容 / S4 产物命名 |
| 形态 | 代码（机制） | **纯数据**（步骤 id 序列 ＋ 提示词文本 ＋ 判据声明） |
| 变更 | 加新能力才改 | **加一张工具卡＝加一份剧本，零代码** |

### 3.3 「拼装和稍微定制」的技术含义

- **拼装** ＝ 写一份剧本文件（步骤 id 序列 ＋ 每步提示词指向）→ 底座自动能跑
- **稍微定制** ＝ 改剧本文件里的提示词/步骤，**不改底座代码**

**对照**：ZhuGe 的形态是「代码常量＋注册表加一行」（`chains/index.ts` L1-13 逐字「加链必须改本文件一行——这是刻意的登记动作」）——**每加一张工具卡要动代码，不叫拼装**。所以本方案的剧本形态**不照抄 ZhuGe 的甲形态**。

### 3.4 剧本形态（【待用户裁】）

| 形态 | 先例 | 优点 | 代价 |
|---|---|---|---|
| **甲 代码常量** | ZhuGe 全部 19 条链 | 类型安全、加载确定 | 每加一张卡要写代码＋改注册表——**不叫拼装** |
| **乙 数据文件（JSON/YAML）** | 推演系统 `config/card_type_registry.json`（144 行纯数据） | **加卡＝加文件，零代码**——贴合「拼装＋定制」 | 需自建 schema 校验；长提示词放 JSON 可读性差 |
| **丙 卡身区块** | 影子卡三节、card_041/043 卡身 | 卡片自解释、界面可见 | 与「卡身不装」的表述冲突（须澄清） |

**本方案倾向乙（数据文件＋提示词另立文本文件）**，理由＝用户要的「拼装和稍微定制」在甲形态下做不到。**但用户没说死，标【待用户裁】。**

## 四、机制设计

### 4.1 前提：判「事实」，不判「质量」

ZhuGe 拆掉的是**判内容**的校验（`chain-schema.ts` L104-107 列出的 17 个函数，含 `checkMinLength` 长度闸）；**保留**的是「提交入口的产出非空底线」（`chain-schema.ts` L8-9 逐字）。

**本方案的全部机械判据只落在「事实层」，一条都不碰「内容层」。**

### 4.2 D3 步骤状态：存哪里、什么结构

**双载体**：

| 载体 | 存什么 | 谁读 |
|---|---|---|
| **卡面 front matter 机械字段** | `step_id` / `step_status` / `step_round` / `chain_name` | **代码**（判据的唯一读取源） |
| **影子卡进度节** | 每步时间线（第几步、何时、产物在哪、判据结果） | **人**（复盘用） |

**为什么两处**：字段给机器读（结构稳定，不因措辞变化而解析失败）；文本给人读（复盘可看）。**被否备选**：只存文本（解析脆弱）／只存内存（`progress.py` 教训：L4 逐字「单进程 uvicorn 内存态」）。

**落点选择**：状态**随卡走**（用户 L47「产物和过程永久挂载在该子项目卡上」、L1921「过程内容始终保留，供随时查阅复盘」）。**被否备选**：ZhuGe 的 `<DSH_HOME>/chain-output/*.json`（工程更稳，但状态落仓库外、与卡分离）。

**缺什么（实测）**：`shadow_store.py` 六个函数全是整块读/整块写——**没有分节读、没有增量写**。要新写 `read_progress_section()` 与 `append_progress(entry)`（后者复用 L136 的 `_get_lock` 锁）。

### 4.3 D5 完成判据：三层，代码只碰第一层

| 层 | 判什么 | 谁判 | 依据 |
|---|---|---|---|
| **L1 事实层** | 产物**存在吗**／**非空吗**／（声明 json 时）**可解析吗** | **代码判** | 用户「不能只靠模型自觉」；ZhuGe 保留「产出非空底线」先例 |
| **L2 结构层** | 产物形态对不对（段标题在不在、顺序对不对） | 剧本声明 + 代码执行 | **ZhuGe 已拆 `requireSectionsOrdered`——【待用户裁】，不默认做** |
| **L3 内容层** | 写得对不对、全不全、好不好 | 模型 / 用户 | ZhuGe 裁定：机械闸门是不信任模型的产物——**此层绝不机械化** |

**L1 三类断言（仅此三类）**：①存在性 ②非空性（字节 > 0）③可解析性（仅当剧本声明 json）。
**明确排除**：不设时间阈值、不设长度下限、不设轮次上限。

**不通过怎么办——回喂事实，不拦推进**：

> 【上一步判据 · 机械事实】p2 声明产物 `04-p2-骨架草稿-01.md` —— 存在：是；非空：是（8,432 字节）；可解析：不适用（md）。
>
> 未通过时：【上一步判据 · 机械事实】p2 声明产物 `04-p2-骨架草稿-01.md` —— **存在：否**。本步未产生声明产物。

**为什么不"拒绝推进"**：拒绝＝闸（ZhuGe 已拆）。**回喂事实**＝把真相摆在模型面前，它不能再"以为自己做了"（正是用户 10-08 遭遇的「假落库」病：模型说落了、系统从不核对）。

**分寸**：【回喂事实】＝本方案定案（低风险）；【准入条件】（判据不过不许进下一步）＝更强，**标【待用户裁】**。

### 4.4 D2/D3 跨请求连续性

**问题（实测）**：`RunState` 是请求局部对象（`message_runner.py` L92 逐字「请求局部对象」），请求结束即销毁。

**设计**：状态落卡 → 下一轮读卡恢复。
1. 开跑：读卡面 `step_id` → 无则取剧本第一步
2. 每步提交后：**代码写**卡面 `step_id` ＋ 追加影子卡进度节
3. 下一轮：读卡面 `step_id` → 从这一步继续

**为什么可靠**：写状态的是**代码**（提交必经口），不是模型自己写——ZhuGe 同一纪律（`chain-artifact-store.ts` 逐字「由代码原子落盘（**不是模型自觉写盘**）」）。

### 4.5 D4 产物落库与版本化

- **落点**：`works/{work_id}/toolcards/{工具卡id}/`（**在 work 内**）——依据用户 L47「永久挂载」、L1921「供随时查阅复盘」
- **文件名**：`{两位序号}-{stepId}-{名称}-{版本号}.{ext}`（移植 ZhuGe L160-174）
- **版本化**：重做不覆盖，同一步重做落 `-02`（ZhuGe L146-157）
- **原子写**：tmp→rename（ZhuGe L127-136；推演系统 `chain-output-store` L13 逐字「项目既有范式」）
- **manifest**：终态写索引，列每步 `{序号, stepId, 文件, 提交时刻, 字节数, 写入成功}`（ZhuGe L206-209）

### 4.6 异常处理

| 情形 | 处理 | 依据 |
|---|---|---|
| 请求中断 | 状态在卡上，下一轮续跑 | 不引入超时判定 |
| 产物落库失败 | 记失败账、终态重试一次 | ZhuGe L192-205 逐字「不重试第三次、不阻断链收口」 |
| 步骤卡住 | **不做超时、不自动推进**——模型判断或用户介入 | 不得引入时间闸 |
| 状态字段损坏 | fail-open：报错给模型/用户，不静默猜 | ZhuGe `chain-output-store` L12 逐字 |

### 4.7 D6 终态收口

跑完 → 写 manifest ＋ 卡 `state: completed`（注册表 tool 定义：`allowed_transitions: ["active","completed"]`）＋ 产物挂 owner（用户 L47）。

## 七、【待用户裁】（不自行拍板）

1. **剧本的存放形态**：甲（代码常量，ZhuGe 现成）／乙（数据文件，贴合"拼装"）／丙（卡身区块）。倾向乙。
2. **判据要不要做成"准入条件"**：回喂事实（本方案定案）／判据不过不许推进（更强，触碰 ZhuGe 裁定）。
3. **L2 结构层判据要不要恢复**：ZhuGe 已拆 `requireSectionsOrdered`。
4. **状态是否要"仓库外镜像"**：卡上存（接用户诉求）＋仓库外镜像（工程稳妥）。
5. **「调用侧」与「回传侧」的设计**（§五 缺口 12/13/14）——这是本方案的最大空白，须用户确认这三条的准确含义（尤其「主卡影子卡的文档栏目」指哪一节、「接替主卡」的切换条件是什么）后，才能补全。
