## 1. 功能背景

（条目挂载：R-001~R-013、R-044~R-045、R-145~R-151、R-173~R-192、R-230~R-238）

**用户原话（逐字，最高依据）**（R-007~R-013）：

「我希望整个系统，卡片对话的信息流，能像deepseek harness那样，每一步调用每一个中间环节，都对我可见，像这些成熟的agent一样，流式展示在对话里」

「这应该涉及到整个对话流的完全改造」

**要解决的问题**（R-230~R-238）：卡片对话的整条执行链对用户是黑盒。一次对话从 `POST /api/works/{wid}/cards/{cid}/messages`（`routes.py:266-271`）进入 `_run_message`（`routes.py:388-389`），内部依次发生配对、六区装配、工具循环、三席后置、统合、T14 拼接、建卡、落盘，而用户可见面只有一条 2 秒轮询的进度通道。

**现状可见面**（R-145~R-151）：`src/api/progress.py` 全文 24 行——模块级内存字典 `_store`（`progress.py:12`）；`set_stage` 只存三键 `{stage, detail, ts}`（`progress.py:15-20`）；`get_stage` 只读（`progress.py:23-24`）；模块 docstring 自述「只上报状态，不拦截、不限制、不进任何模型输入——不是闸」（`progress.py:5`）。全链 `set_stage` 实测 8 处调用点：`routes.py:485`／`491`／`500`／`561`／`570`／`647`／`726`／`747`；`get_stage` 消费点 1 处（`routes.py:280`）。

**前端消费现状**（R-173~R-192）：`workspace.js:689-698` 的 `STAGE_TEXT` 把这 8 个 stage 映射成 8 个中文标签；`createWaitingBubble`（`workspace.js:699-729`）挂 `.msg.thinking` 气泡（`701`）＋1 秒计时（`710`）＋2 秒轮询（`711`／`721`）；刷新恢复走 `attachRunningState`（`740-752`），活跃态白名单 `ACTIVE_STAGES`（`739`），命中则挂回「思考中…（刷新前已启动）」（`747`）。

**六处断点**（R-230~R-238）：①模型每一轮调用无上报——循环体内无上报语句（`routes.py:486-509`）；②工具调用与结果不可见——终态只记三键 `{"tool","card_id","ok"}`（`routes.py:631`）；③三席观点正文不可达——`meta["text"]` 已送到调用方（`simple_service.py:198`），返回响应前被剔（`routes.py:756-757`）；④上下文装配不可见——`build_log_regions` 已算好（`routes.py:654-659`；`context_regions.py:137-172`）但只进日志；⑤文本抢救／T14 拼接／建卡解析不可见——仅服务端日志行（`routes.py:518-534`／`704-723`／`735-736`）；⑥中途刷新零重放（`workspace.js:740-752`）。

**代码级自证**：`routes.py:644` 的 `user_prompt = "工具结果已返回。"` —— 模型每调一次工具，用户看到的全部内容就是这六个字。

**本功能的定性**（R-044~R-045）：新增一条过程通道，执行链不动。结果通道（`POST /messages`）与审计通道（`prompt_log`／会话）保持不动；事件为纯展示层——不进模型输入、不落盘、不进 session。

### §4.1 事件流载体：新建 src/api/event_stream.py

（条目挂载：R-231、R-239~R-265、R-211~R-215、R-275~R-289）

新建模块，两环境均不存在，故无既有锚。设计取六块。

**（a）接口契约**（R-231 逐字要求「`emit()`／`subscribe(from_seq)` 接口…落成可施工的接口契约」）——三个函数，签名逐行给出：

`def emit(work_id: str, card_id: str, type: str, data: dict) -> int` —— 写日志并向所有订阅者扇出，返回本条 seq。同步函数（内部 `put_nowait`，不 await）。

`async def subscribe(work_id: str, card_id: str, from_seq: int = 0)` —— 异步生成器。先重放日志中 `seq >= from_seq` 的条目，再转实时投递；生成器退出（客户端断连）时自动移出订阅者表。

`def reset(work_id: str, card_id: str) -> None` —— 清本桶日志与订阅者表。`run_start` 时调用；**测试亦用此重置**（见 §4.9）。

**（b）事件日志**：按 `(work_id, card_id)` 分桶的内存环形日志，容量上限 **300 条**；单条正文 **8KB** 截断并置标记位（依据：`routes.py:639-642` 的 `tool_full_texts` 单条可能含 `edit_card` 全文）。

**（c）淘汰界标**：满 300 条时淘汰最旧条并置 `dropped_before` 界标（记录被淘汰到的最大 seq）。`subscribe` 若 `from_seq < dropped_before`，先发一条 `type: "gap"`（`data: {dropped_before}`）再重放现存条目——前端据此显示「（早前 N 条已略）」，**不静默缺失**。

**（d）断线续传**：每条事件带 `id: {seq}`。`subscribe` 支持 `Last-Event-ID` 请求头；该头在场时以其为 `from_seq` 起算，并覆盖 `from` 查询参数——浏览器 EventSource 自动重连时携带该头，**续传不重放**。
