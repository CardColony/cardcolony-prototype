## 一、它是什么

### 1.1 一个项目一张

【用户】你 22:05 说「当然跟项目啊」。

所以：每个项目（系统里的一个工作区，比如"股权财政"）配一张规则卡。这个项目里所有卡片，都受它管。

不是全系统共一张——不同项目守的规矩本就不一样（研究项目和研发项目的活法完全不同，见第二节）。

### 1.2 它是一张特殊的卡

【用户】你 21:49 说「规则卡是一张特殊卡，和现有卡片不同，是一张全局卡」。

"特殊"体现在三处：
- **不挂在卡片树上**——它不是谁的子卡
- **不进卡片清单**——模型看到的卡列表里不会出现它
- **管所有卡**——别的卡各管自己的事，它管全项目的规矩

【起草】它的打开和编辑，和你现在编辑任何一张卡一样——能看、能改、能更新。改完就是新规矩。

### 1.2.1 它物理上放在哪

【起草】这是必须说清的一格，否则"不进卡片树"就只是句空话。

【现状】现在一个项目的目录是这样：`项目名\` → 下面有 `cards\`（所有卡片都在这儿）、`sessions\`、`shadows\`，加几个配置文件。系统的"卡片清单"是按 `card_*.md` 这个文件名规律扫 `cards\` 目录的——**所以只要不叫这个名字、不放在这个目录，就天然不会出现在清单里。**

【我自定的技术选择，可推翻】规则卡存在**项目目录下、独立的一个文件**（放在 `cards\` 之外），文件名区别于卡片。这样做的好处：不需要额外写"过滤掉规则卡"的代码，它天然不会被扫到。

### 1.3 卡里分七层

【用户】你 22:27 说「分几层，你出一个初稿，一个开发项目的方方面面」。

你点过的四层是：**文档规范、文件规范、代码规范、测试规范**。
【起草】我按"一个开发项目的方方面面"补了三层，凑成完整闭环：

| 层 | 管什么 | 来源 |
|---|---|---|
| 一、方案 | 一件事怎么开头：目标写清、验收标准定死、方案书和任务书怎么写 | 【起草】 |
| 二、任务书 | 写出来的东西长什么样：卡片三块怎么写、条目怎么编、结论要不要挂证据 | 【用户】文档规范 |
| 三、文件与版本 | 东西放哪、怎么改、怎么留痕：哪些能进版本、哪些绝不能、改前要不要先取证 | 【用户】文件规范 |
| 四、代码 | 代码写成什么样：目录怎么分、命名怎么起、注释写不写 | 【用户】代码规范 |
| 五、测试 | 什么时候必须测、测到什么程度算过 | 【用户】测试规范 |
| 六、交付与验收 | 做完怎么交：谁能动正式环境、重启要不要先问、验收判据怎么写 | 【起草】 |
| 七、协作与留痕 | 跟你怎么打交道：什么时候必须问、什么时候自己定、临时品怎么登记 | 【起草】 |

【现状】这七层不是凭空编的——系统里已经散落着一批**真在用的规矩**，正好能归位进去：

| 层 | 系统里已有的现成内容 | 在哪 |
|---|---|---|
| 二、任务书 | 卡片三块语法（使命／现状／定论）＋条目语法 | 使用说明里 |
| 二、任务书 | 影子卡三节结构＋三条禁止 | SHADOW_CARD_RULINGS.md |
| 三、文件与版本 | 版本管理三条永久禁令＋快照机制 | VERSIONING.md |
| 一、方案 | 方案链、任务书链两套流程，每步带专属提示词 | works\toolcard_scripts\ |
| 六、交付与验收 | 部署与重启须先行许可＋发布阻塞清单 | 既有红线／RELEASE_BLOCKERS.md |
| 七、协作与留痕 | 临时品登记规矩＋清理规程四条判据 | TEMP_LEDGER.md／SOP_清理废弃剧本.md |

**要新写的只有两层半**：代码规范、测试规范，以及交付验收里"判据怎么写"那部分——这三样系统里从来没有过成文规矩，历次都是现写现用。

## 二、谁拿哪几层

### 2.1 靠什么分——卡片类型

【用户】你 22:27 说「卡片类型=职能，哪那么复杂」。

【现状】系统里现有四种卡片类型，注册表里每种都写着它是干什么的：

| 类型 | 注册表原文对它的描述 | 白话 |
|---|---|---|
| 项目根卡 | 「一个独立推演项目的总架构卡」 | 定这个项目是什么、往哪走 |
| 子项目卡 | 「研发项目下一个相对独立的工作单元」 | 把一件事从方案做到落地 |
| 工具卡 | 「被调用、执行专项任务的卡」 | 按剧本跑一套固定流程 |
| 课题卡 | 「研究项目下的一个课题」 | 调研、推演、出结论 |

**类型本身就是职能，不需要新建任何东西。**

### 2.2 谁拿哪几层

【起草】按每种卡实际干的活，映射如下：

| 卡片类型 | 拿哪几层 | 为什么 |
|---|---|---|
| 项目根卡 | 全部七层 | 它是总纲，得知道整个项目守什么 |
| 子项目卡 | 全部七层 | 它要把事从方案做到交付，四类活都干 |
| 工具卡 | 一、二、六、七 | 它按剧本跑专项任务——要守方案任务书怎么写、文档怎么写、怎么交、怎么跟你打交道；**代码和测试它不碰** |
| 课题卡 | 一、二、七 | 研究项目只调研推演——**永远拿不到代码、测试、版本那几层** |

【现状】这套映射和实际项目对得上——实测（2026-10-10 22:42 逐个项目点数）：

| 项目 | 类别 | 实际卡型分布 |
|---|---|---|
| 股权财政 | 研究项目 | 1 张根卡 ＋ 22 张课题卡（共 23 张） |
| 项目管理agent | 研发项目 | 1 张根卡 ＋ 36 张子项目卡（共 37 张） |
| 记忆机制论文 | 研究项目 | 1 张根卡 ＋ 13 张课题卡（共 14 张） |

另有四个测试／诊断用项目（卡很少或为空），不影响这个结论。

### 2.3 「不污染」是自动的

【用户】你 21:49 说「不同的内容也不会污染不相干的卡片」。

【起草】这句话靠上面的映射表自动成立——课题卡拿不到代码规范，是因为它这个类型根本不取那一层。不用额外做什么。

## 三、怎么进上下文

这一节讲"规矩怎么送到 AI 眼前"。四件事。

### 3.1 机制直接送，不靠 AI 自己去取

【用户】你 21:49 说「不需要靠卡片拉，直接注入卡片的上下文特定区域」。

【现状】这和系统现有做法正好相反——普通卡片的正文是"拉取制"（AI 要自己调工具去读，系统不主动推）；规则反过来：系统主动送。

【起草】这样做的理由：规矩不能等 AI 想起来才去取——它想不起来就等于没有规矩。

### 3.2 送到哪——上下文的"分区"里

**【先说两个词】** 下面会反复出现「主模型」和「三席」：
- **主模型**＝真正干活的那个——它读你的话、调工具、写卡片、出结果
- **三席**＝三个"出主意的"——它们只在关键时候被叫来，各说各的看法，由主模型汇总。**它们不动手，只出观点**
- 这不是两个独立的系统，是同一套流程里的两种角色

【现状】系统给 AI 的材料是按"区"分块拼起来的，现在有这些区（按顺序）：

| 序号 | 区名 | 给谁 |
|---|---|---|
| 0 | 使用说明 | 主模型 |
| 100 | 卡片清单 | 主模型＋三席 |
| 150 | 当前卡 | 主模型＋三席 |
| 160 | 工具卡步骤指令 | 主模型（运行时才出现） |
| 165 | 思维链活板 | 主模型（运行时才出现） |
| 200 | 记忆（凝练） | 主模型 |
| 300 | 对话历史 | 主模型＋三席 |
| 900 | 本轮工具轮 | 主模型 |
| 999 | 用户消息 | 主模型＋三席 |

【现状】一张表里其实有两种区：**160 和 165 不在静态清单里**，是装配时按当时情况临时加的（这张卡有工具卡在跑才出现 160，没有才轮到 165——两者只出一个）；其余各区都写在静态清单里。

【起草】规则区加进去，**插在 50 号位**（在使用说明之后、卡片清单之前）。

【我自定的技术选择，可推翻】选这个位置的理由：规矩要排在前头，AI 才先看到；又不能像使用说明那样占 0 号（那是最基础的，不动它）。

【现状】"插一个新区"这条路系统里走过——记忆区（200 号）就是后插进去的，当时的记录写着「只 append 200，其余条目一字不动」。

### 3.3 给谁——只给主模型

【起草·我自定，可推翻】规则区默认只给主模型，不给三席。

依据：三席是纯观点席、零指令——这是系统早就定下的规矩（三席只出观点，不给它们行为指令）。

### 3.4 怎么知道该给哪几层

【现状】系统里已经有一个同形的现成做法：**工具卡步骤指令区**（160 区）就是这样——它自己去看"当前这张卡在跑哪套剧本、走到第几步"，然后把对应内容拼出来，不需要别人告诉它。

【起草】规则区照同一个路子做：**自己去看当前卡是什么类型 → 从映射表查出该给哪几层 → 只把那几层拼进区里**。

【我自定的技术选择，可推翻】这样做的理由：不去改动现有"卡片清单"区的数据源（那个区只取三个字段是有意为之的），规则区自己负责自己需要的输入。

### 3.5 它是一层，不和别的混

【用户】你 21:49 说「可以就作用于这个规则层」。

【起草】这句话的意思是：规则到了 AI 眼前，是**自成一块、界限清楚的一层**——不和对话历史混在一起、不和卡片清单混在一起、也不和那段系统使用说明混在一起。AI 一眼就能分清"哪些是规矩、哪些是别的"。

【我自定的技术选择，可推翻】做法上靠两件事保证：①它单独占一个区（区与区之间由系统给的分隔与标题隔开）；②它的内容就是规则卡里对应那几层，不掺别的东西。

### 3.6 工具卡跑不同剧本，拿的是同一套

【用户】你 22:05 举的例是「写方案的卡片拿到什么规则，写代码的卡片拿到什么规则」。

【起草】这里有一格要说清：工具卡（比如"方案链""任务书链"）**类型相同**，按 22:27"类型即职能"的口径，**它们拿同一套**——都是一、二、六、七层。

（因为流程链是"按规矩办事"的机器，它自己不写代码也不做测试；它拿到的规矩，管的是"任务怎么起、文档怎么写、做完怎么交"。）

## 四、怎么落到文件

这一节讲"为什么还有一份 AGENTS.md 文件、它和卡是什么关系"。

### 4.1 同一份数据，两个面孔

【用户】你 22:15 说「卡的数据和文件的数据不应该是同步的吗？哪来的矛盾？」

所以：**卡是操作面，文件是它的落点。** 一份内容，两种存在方式：
- 在系统里，它是**卡片**——能看、能改、能分层、能被系统按类型分发
- 在项目目录里，它是 **AGENTS.md 文件**——别的 AI 工具一进项目就能读到

### 4.2 什么时候读、什么时候写

【用户】你 21:26 说「一个项目只需要读一次，读完之后，作为一张卡片存起来」。

**读的方向——一次**：建项目的时候，如果项目目录里已经有 AGENTS.md（你自己写的，或从别处拷来的），读一次，生成规则卡。此后这个文件就不再是源头了。

**写的方向——每次改都落**：
【起草】规则卡一被改动，就把整份内容写成项目目录下的 `AGENTS.md` 文件（整份覆盖，不做比对合并）。

【我自定的技术选择，可推翻】这样做的理由：让"同步"没有中间状态——不存在"待同步""已过期"，也就不存在"两边不一致"这种情况。改了就写，没改就不写。

### 4.3 落在哪

【现状】每个项目在系统里就是一个目录，里面有 cards（卡片）、sessions（对话）、shadows（影子卡）三个子目录，加上几个配置文件。

【起草】AGENTS.md 落在**项目目录的最外层**。

【现状】实测：现在七个项目目录里**全都没有**这个文件——这是从零开始建，不是改造。

### 4.4 为什么值得这么做

【起草】你的原话是「这样用其他 agent 的时候，可以同步过去」。

翻译成好处：**你的规矩不用锁死在这一套系统里**。用这套系统时，规矩是能编辑、能分层的卡；换别的 AI 工具时，它们读同一份文件，守同一套规矩。

## 五、这份方案不包含什么

【起草】明确说一下，免得以为漏了：

- **不包含各层规范的具体正文**——那要等机制建好，你自己往里写。这份方案只设计"盒子"，不装"内容"。
- **不包含实现步骤**——这份是方案，不是任务书。
- **不包含任何代码改动**——全程只读，一行没动。
