# 左侧边栏底座·最优解

> 一句话定性：**左边栏是这套系统里唯一一个「项目维显式在场」的视图——它是用户在多项目、多卡片、持续变化的平面上定位自己、准确到达任何地方的导航面；它的最优解是：数据自带归属、状态分层自治、渲染按需生长，让"导航"这件事在任何规模下都不惩罚用户。**

---

## 一、本质

系统里其他一切视图（画布、卡片详情、上下文、会话、记忆）都是单项目锁定的——项目维由页面隐含携带。唯独左侧边栏，一屏同时呈现所有项目的卡片树。

**所以它的本质：它是系统里唯一一个跨项目显式视图。** 它回答三个问题：我在哪（哪张卡、哪个项目）、我要去哪、这里现在是什么状态。别的视图回答"这张卡里有什么"，只有它回答"卡在哪儿、怎么去"。

**从本质推出的必然**：项目会变多、卡片会变多、树会长深、数据永远在动——导航负担与系统规模同步增长，它上面的每个错都以"用户天天看见"的方式显形。

---

## 二、真实约束（硬约束，本质决定；当前实现的毛病不是约束）

1. **寻址是二元的**——跨项目语境下，一张卡只能由 `work_id + card_id` 复合指认。这是存储层的自然事实（每个项目目录各自从 card_001 编号）。违反了会发生什么：单凭卡号的寻址在跨项目语境下以高概率指向另一项目的同号卡；不仅是显示错，若动作（进入/注入/写入）落错卡，就是**不报错的数据级错误**。
2. **数据是文件，不是数据库**——树是现场组装出来的，没有索引、没有事务、没有推送。外部变化只能由查询方自己发现。违反了会发生什么：任何"实时同步"的期待都会落空；这不是缺陷，是文件即数据的本性。
3. **判断归模型，代码只判机械**——代码不替模型判断"这个节点是什么、该挂什么徽章"。违反了会发生什么：代码去生成语义违反系统最高原则，而且必然猜错（把卡号当全局唯一就是"代码猜语义"的同族）。
4. **卡片是接口**——一切交互最终落向一个明确的 `(work_id, card_id)`。违反了会发生什么：指向模糊 → 动作落错卡 → 不报错。
5. **页面是单项目工作台，左边栏是总览入口**——工作台一次显示一个项目，左栏是这道门。违反了会发生什么：左栏若承担超出导航的职责，与页面职责重叠、状态双份、谁知道谁。

**非约束（当前实现的病，思考最优解时一律不得作为理由出现）**：60 秒轮询整树、innerHTML 全量重写、状态裸变量堆、展开态不持久化、卡片对象不带项目号。

---

## 三、职责边界

> **左边栏管「卡的地址」，不管「卡的内容」。**

**判据**：一个功能回答的是"卡在哪、怎么去"，还是"卡里有什么、怎么改"——前者归它，后者归画布/详情/编辑器。

**不该塞给它的（每条答"越界会发生什么"）**：
- 卡片内容预览 → 左栏同步内容更新状态，数据源多一份、同步点成倍增长
- 卡片编辑 → 绕过卡片自己的校验链（权限/快照/校验），改了不落、显示与真相脱节
- 跨项目迁移/移动 → 只动 UI 不动底层，假操作，刷新原样回来
- 规则层注入/展示 → 又一个读取注入状态的调用点，显示过期状态却像最新
- 会话内容展示 → 重复渲染一份残缺历史，误导
- 统计/仪表盘 → 导航工具变成看板，两件都做不好

**接口面**：读系统数据（项目清单＋卡片树）；写自己的状态（展开/折叠/视野——回看偏好，非系统数据）；输出寻址（切项目/开卡）。它永不改写卡片本身。

**独立性**：必须独立于页面存在（导航面跟页面走，用户就失去"我在哪还能去哪"的空间感）；它的状态归它自己（回看偏好不属于任何项目/页面/卡片）。

## 四、结构决策

### 决策一 · 数据契约：一份树形快照，节点自证归属，全量取、按需重取

- 形态：`projects[]`，每项 `{work_id, title, cards[]}`；每张卡 `{work_id, card_id, title, parent, child_count, last_active_at, branch_active_at}`。
- **归属由给数据的一方提供**（每张卡自带 work_id），不由用数据的一方推断——给方知道、用方不知道；十个调用点十种猜法，各错各的（这就是现在的病）。数据自带归属，是唯一一处声明。
- **层级**：`parent` 指同一 project 内的裸 card_id（项目内裸 id 合法，此时上下文已被 work_id 锁定）；跨项目一律复合键。
- **为什么全量不是增量**：本系统无变更推送（文件即数据）；增量需要服务端记录 diff 状态，是自找的分布式一致性问题；树全量是 KB 级，全量比维护增量协议简单可靠得多。
- **被否决**：卡片不带 work_id、用方从父级遍历 ← 否决：把"归属"变成每个调用点的再推断，错一次就是一个不报错的数据级错误（已实证发作）；全局唯一编号迁移 ← 否决：全量迁移（画布/连线/会话/台账全重排）为没病的东西付全款，编号"项目内唯一"本身没问题，问题在没声明。

### 决策二 · 状态模型：三层自治，各管各的存活期

- **第一层·临时态**（不持久化）：滚动位置、悬停、输入中的搜索词。刷新即丢合理（瞬时状态没有恢复意义）。
- **第二层·回看偏好**（持久化到浏览器本地 localStorage）：展开的节点集、项目级开关、视野。只对这个用户、这个浏览器有意义，属于个人回看偏好，不属于系统数据。
  - **被否决**：存服务端写入项目数据文件 ← 个人偏好污染系统数据文件；本系统无用户概念，跨设备同步是伪需求。
  - **违反会发生什么**：节点一多，用户每次回来都要重新整理视野——整理成本随规模线性上涨（10-04"展开态刷新即丢"的老病，再犯就是第二次）。
- **第三层·选中态**（存 URL）：当前选中的 `(work_id, card_id)`。URL 天然可回退、可分享、刷新不丢。
- **状态与数据的边界**：数据＝服务端给的，前端不能改；状态＝前端自己的，不能写回服务端。判别句：**"系统里本来就有的"是数据；"只有这个用户这次看才有的"是状态。**
- **切项目/刷新/定时刷新的处置**：切项目→偏好保留、瞬时清、选中保持复合键；刷新→偏好从本地恢复、瞬时清、选中从 URL 恢复；**定时刷新→三种状态一律不动**（用户的视野不能被数据变化打翻）。

### 决策三 · 渲染模型：DOM 按需更新，折叠即卸载，数据快照与 DOM 分离

- **视图变化（展开/折叠/切项目/搜索）只增删改对应节点，不重建整树。**
- **折叠即卸载**：折叠的子节点 DOM 移除；展开时从内存数据即时重建。渲染成本与"用户展开的视野"成正比，与总节点数无关。
  - **被否决**：保留全部 DOM 只隐藏 ← 总节点上千时全部 DOM 常在，滚动/查询/内存都背着上千节点的成本，视野只有三五十个也要全扛。
  - **被否决**：虚拟滚动 ← 树有折叠结构，折叠一节点改变整棵布局，与虚拟滚动天然冲突；几百节点量级按需更新足够轻。
- **外部数据变化**：数据快照与 DOM 分离。刷新→diff 变化（新增/删除/标题变/徽章变）→只动变化的部分。全树不动，用户的展开/滚动/焦点安然。
- **违反会发生什么**：用户正在展开/滚动，定时刷新整树重建——交互被打断、滚动丢、展开丢（现有病根的准确形态）。

### 决策四 · 扩展点：四样增长各占各的层，互不交叉

| 未来功能 | 加在哪 | 不用改什么 |
|---|---|---|
| 新徽章（类型/规则状态/未读数） | 字段加一个＋模板加一种 | 契约结构、状态模型、渲染模型 |
| 新过滤/搜索维度 | 过滤条件＝第一层临时态；渲染接一件过滤逻辑 | 三层结构 |
| 拖拽（项目内移动） | 节点 DOM 交互层新事件；跨项目移动是存储层的活、不进左栏 | 数据契约 |
| 更深树（5-10 层） | 递归渲染天然支持 | 结构无变化 |
| 更多交互状态 | 归入三层之一 | 结构无变化 |

**违反会发生什么（若没有分层）**：新功能来了要么改契约（影响所有数据消费者）、要么改渲染（全量重写一次）、要么状态乱放（冲突丢失）——每加一个功能都成牵动全身的手术。

## 五、已知三病根如何天然消除（每一条都指到"哪一处结构使其不可能"，不是"我们会注意"）

| 病根 | 被哪一处结构消灭 |
|---|---|
| 契约缺归属（卡片对象不带项目号） | 服务端输出形态本身改为每卡自带 `work_id`（决策一）；"只给 card_id 就能路由"在数据契约里不存在了 |
| 状态裸变量堆（无单一来源、键不带项目、只增不减、刷新即丢） | 状态只有三层容器一个入口（决策二）；键怎么写是契约的一部分（跨项目一律复合）；每层有明确的存活与清空规则；偏好持久化、选中入 URL |
| 渲染全量重写（整树 innerHTML 重画＋定时重跑） | 渲染模型里**不存在"重建整棵树"这个动作**（决策三）：视图变化只动对应节点、数据刷新只 diff 变化字段、折叠即卸载——整树重写这个函数形态被消灭了 |

## 六、这块会输在哪（如实标边界，不说"这样就没问题了"）

1. **万级节点＋全展开**会退化：折叠即卸载的前提是"用户同时展开的节点有限"；全展开时 DOM 照样爆。虚拟滚动当时被否（与折叠冲突），冲突依然存在，所以这是真实边界不是疏漏。
2. **diff 与用户交互的竞态**：定时刷新差量更新时，若用户正拖拽/正展开同一节点，字段更新可能打断交互或闪烁。"只更新变化字段"做到了，但"不触碰正在被交互的节点"这个细粒度保证没有完全闭合——**设计里最实的一个洞，如实标**。
3. **搜索与折叠的交叉语义**：过滤条件下"展开/折叠"指什么、匹配节点被过滤掉是隐藏还是可展开、跨折叠子树搜索要不要临时展开匹配节点——**这个语义边界没定死，如实标**。
4. **偏好只在单浏览器内持久**：localStorage 换浏览器/清缓存/换机器即丢。本系统无用户概念，跨设备同步是伪需求，可接受；但"刷新不丢"只在同一浏览器内成立。
5. **快照与现实的缝隙**：两次取数之间卡片可能被删；展开刚被删的卡→寻址落空→需要兜底（标记消失不报错）。兜底设计只在"选中/展开目标不存在"一条路径上，其他路径未完全覆盖。
6. **明确不解决的**：多用户/多设备（系统无此概念）；内容层（预览/编辑——职责已划走）；实时推送（文件即数据，40-60 秒粒度的发现是本性不是缺陷）。

## 七、结尾

**这个最优解明确不解决什么**：不解决判断能力（它只保证"导航"这件事不惩罚用户，不保证内容正确）；不解决多用户（系统无此概念）；不解决实时性（文件即数据的本性）。

**什么条件下它需要重新评估**：
1. 万级节点成为常态（那时虚拟滚动要带着折叠冲突重新评估）；
2. 出现真正的跨项目共享/同步需求（那时状态归属要从"浏览器本地"向上挪）；
3. 左边栏的职责被重新定义（不再是导航，而是看板/工作台——决策二三四随之失效）。

**一句话盖章**：这不是"最优"的字面完美，是**在"文件即数据、判断归模型、项目是容器、卡片是接口"这四个硬约束下，能让导航这件事长期不惩罚用户、且每条结构决策都答得出"为什么不是别的"**的方案。推倒就是推倒——它就是这块的推倒重做蓝图。
