## 一、要解决什么（基线 §一，原样保留）

同一张卡、同一时点，一次调用 prompt 负载 **447,988 字节**（最大 534,657）；该卡会话文件仅 4,873 字节——**负载是会话文件的 92 倍**（现值重算 17 倍）。

机制（三处实读）：工具结果从不进入会话文件（`append_message` 仅两个调用点）；历史侧零工具痕迹（投影成 role/content 两键）；**44 万字节全部来自本轮工具循环内**（assistant＋tool_calls ／ 首轮用户原文固化 ／ tool 结果逐轮加长、每轮整段重送）。

被否证旧表述：①「工具结果跨轮累积膨胀」→ 否（跨轮无堆积无痕迹）；②「装配线放最后做」→ 否（出口自持、零平台耦合，应排第一步）。

## 六、轮槽与折叠器（基线 §五，原样保留＋两件套定义指向 p1 实读）

### 6.1 作用域
轮槽为**请求局部对象**、**不做全局内存态**——单进程可并发处理不同卡请求，全局态会跨卡串味。

### 6.2 折叠单元＝工具轮
第 r 轮产物＝一条含工具调用的 assistant＋其对应若干条工具返回。**不折红线**：首轮用户原文固化、抢救回注、当前轮全文。

### 6.3 折叠动作（机械，纯函数）
保留窗口 K（最近 K 轮全文，K=2 自拍），更早的轮次：
- `assistant.content` → 首版不动（自拍）
- 工具**入参** → 压成【结论】＋【依据】两件套
- 工具**返回** → 压成【结论】＋【依据】两件套

**两件套定义（照「已核实结论」常驻机制的做法，p1 实读 evidence-index.ts 全文 558 行）**：
- **【结论】**：这次调用得到了什么，一句话——折叠发生时由模型压出，**不设长度限制**（用户 00:13，200B 上限作废）
- **【依据】**：证据在哪、怎么找回原文（工具名＋参数＋原文位置）——代码机械写，不动脑子、不会编

**产出机制**：装配时对窗口外旧轮次执行一次折叠（请求局部）；【结论】对「该轮工具做了什么、返回了什么」做一次模型压出（独立压缩动作，不改变消息条数与配对结构）；压出结果作为该轮返回正文替身写进轮槽；【依据】代码机械登记；原文在轮槽内释放、需要细节时模型按【依据】重取；失败→该轮不折、全文保留、留痕记错误条目（不留白）；边界——【结论】仅是轮槽内压缩替身，不进会话文件、不进证据索引、不推送。

**为什么两边都折**：写文件／改卡／写影子三类工具的全文内容在入参里、不在返回里——只折返回会漏掉最重的一块。

**只读工具白名单落点**：落工具定义处（自拍）——白名单是「工具的属性」，属性跟工具住一起。

### 6.4 协议约束（硬）
保留配对结构：只压内容、不删消息（删了触发上游配对校验失败）。按轮次分组、不按调用 id（id 每轮从 0 重起、跨轮重复；切段按追加顺序；重复 id 为观察项首版不改——真报 400 时第一嫌疑在此）。

### 6.5 失败处理（划界）
任一异常→记 warning＋该轮不折、全文保留＋留痕记错误条目（不留白）。折不动≠机制失败（后果是「没省下」不是「数据错了」）。禁止因折叠异常改变消息条数或结构；禁止静默跳过不打点。
