## 二、现状（实读）

### 2.1 数据在哪 —— 一条 SQL 就够

`cards` 表（每 work 一库 `works/{work_id}/cards.db`）已有：

- `parent` 列 ＋ **`idx_cards_parent` 索引**（`card_db.py:_SCHEMA`）；
- `status_block` 列（正文三块之一）。

⇒ 直接子卡现状＝
`SELECT card_id, title, status_block FROM cards WHERE work_id=? AND parent=? ORDER BY card_id`
**SQL 不递归**，"只看直接子级"是天然成立的结构性事实，不靠过滤逻辑保证。

### 2.2 取数通道

`card_db.read_sync(work_id, fn, default)`（同步只读，供必须保持同步签名的读）或 `run_read`（异步）。
既有先例：`context_assembler._load_cards_index` 就是 `read_sync` 取 id/title/parent 三列。

### 2.3 落点

区注册表（`src/api/context_regions.py:REGION_TABLE`）＋取数（`context_assembler.build_ctx`）。
底座已就位：加一个区＝加一个注册项，装配器一字不动（§八 已验证）。

### 2.4 现在父卡怎么"看"子卡

`100 卡片清单` 只给 `id · 标题 ·（父：parent）`——**没有任何子卡进展信息**；
模型要看进展只能自己调 `read_card`/`read_shadow`。本方案补的正是这个缺口。

## 三、设计

### 3.1 新增一个区（key=`child_status`）

| 字段 | 值 |
|---|---|
| key | `child_status` |
| order | **170**（紧随 155 卡片区域说明之后、200 记忆之前——"我是谁"→"我的子卡怎么样"→"我的记忆"） |
| name | 直接子卡现状 |
| channel | system |
| delivery | system |
| profiles | **待裁，见 §五-1**（我倾向 `("main", "viewpoint", "draft")`，与其余 system 区一致） |
| owner / source_owner | `context` / `assembler`（沿 §八 口径） |
| render | 纯函数：`direct_child_status` → 文本 |
| count | 有非空现状的子卡数 |

### 3.2 取数（一处 IO，落在 `build_ctx`）

```python
def _load_direct_child_status(work_id, parent_id) -> list[dict]:
    """只取直接子卡的 id/title/status_block；SQL 不递归 ⇒ 不含孙级。"""
    # SELECT card_id, title, status_block FROM cards
    #  WHERE work_id=? AND parent=? ORDER BY card_id
```

- **只取三列**——不读子卡的 mission/rulings/history，更不碰影子；
- `RegionCtx` 增一个字段 `direct_child_status`；
- 取不到库/无子卡 → 空表（不报错，沿既有 fail-open 纪律）。

### 3.3 呈现（我裁的实现细节，可推翻）

```text
## 直接子卡现状

### card_007 · 上下文装配线
（该子卡的现状正文，原样）

### card_011 · 工具卡底座
（…）
```

- **空现状的子卡跳过**（现状是空白＝没有信息，不占位、不写"（未写）"）；
- **全部子卡现状都空 → 整个区不出现**（沿「没有来源就不出现这个区」）；
- 子卡顺序＝`card_id` 升序（稳定、可复现）；
- 正文**原样呈现**，不摘要、不截断（沿渲染零加工）。

## 五、待你裁（只有两条是**你的**，其余我裁）

### 5-1 `profiles`：谁看得到子卡现状？

- **甲（我倾向）**：`main + viewpoint + draft` 一致——三席与起草助手也拿到同一份"我是谁＋我的子卡"；
- **乙**：只 `main`——三席只看执行材料，不掺子卡现状。

**这是产品语义**（"三席要不要知道子卡进展"），故交你裁。

### 5-2 体量：现状要不要限长 / 限条数？

渲染零加工原则说"不截断"，但**子卡现状可能很长**（它按设计要写"接口与约定、依赖与影响范围"三类东西）。极端情况：一个卡有 20 个子卡、每个现状 2KB ⇒ 每轮多 40KB。

- **甲（我倾向先做）**：**不限**，先跑起来看真实体量；不够再谈限长；
- **乙**：现在就定上限（如每子卡 N 字节 / 最多 M 条）；
- **丙**：现状只取首段（第一段/前若干行）。

**这是"注入多少"的产品判断**，交你裁。

### 5-3 我裁的实现细节（可推翻，无需你答）

- 区 key 名 `child_status`、order `170`；
- 呈现形态（`## 直接子卡现状` ＋ `### id · title` ＋ 正文）；
- 空现状跳过、全空不出现；
- 子卡排序＝`card_id` 升序；
- 只取三列、不碰影子。
