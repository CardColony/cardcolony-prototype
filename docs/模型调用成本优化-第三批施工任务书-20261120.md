# 模型调用成本优化 · 第三批施工任务书

**施工对象**　推演agent 原型的需求评审席回合。  
**交付目标**　让增量确认和同版补票只收到完成本次表态所需的材料。以真实出站字节和投票事实验收。  
**开工顺序**　先做版本与发言绑定，再做选材，最后走真实回合复验。评审缩量独立开关建议用 `REVIEW_CONTEXT_PHASES=1`，缺省沿用现行完整装配，便于单独放行。 [成本总方案第四节](模型调用成本优化-方案与施工任务书-20261120.md#四-第三批-评审按阶段装配)

## 一、从现有入口接着做

1. 从 `review_runner.run_once` 进入。现有 `_classify` 决定叫哪一席及步骤。`_seat_turn` 已向 `routes._run_message` 传评审批次、席位和 `step`，执行锚是评审卡，身份锚是席位，`ctx_card` 是被评卡。沿这条调用链传选材依据。阶段由宿主结构化字段决定。 [步骤入口](../src/api/review_runner.py#L173) · [席位回合](../src/api/review_runner.py#L628)
2. 试点只处理普通需求评审 `requirements` 的 `confirm` 和 `vote_nudge`。首评 `speak`、重评 `re_eval`、对齐批 `requirements_align`、场务、被评卡修订与定稿、普通主对话、普通三席和起草全部走各自现行入口。测试验证它们的出站材料和流程与基线等价。
3. 当前 `confirm` 已用上次批准快照计算 diff，但仍接入完整被评卡上下文。`vote_nudge` 目前使用完整草稿和场内历史，最近一次席位发言只有作者和回合等信息，不能直接证明稿次。先补下节的证据绑定，再动装配。 [差事文本](../src/api/review_runner.py#L757) · [场内历史](../src/api/review_runner.py#L918) · [回复落块](../src/api/message_runner.py#L2666)

## 二、先把材料绑定到实际审阅的稿

1. **读取本轮材料快照。** 在属主 runner 取得评审卡、被评卡、批次、席位、步骤、水位、草稿版本及草稿原文指纹，从现有 `review_state`、`review_approvals` 和被评卡的 `requirements_draft` 取得。审批表中的 `draft_snapshot` 是该席批准时的草稿。计算现稿指纹时直接使用本次取到的原文。`sync_draft` 在被评回合收口才推进版本，原文指纹与已登记稿次不符时暂缓这一步，等现有稿次推进链处理。分开记录「确认缺证」和「原文确实相同」。 [草稿版本](../src/storage/review_store.py#L324) · [投票快照](../src/storage/review_store.py#L468) · [状态读回](../src/storage/review_store.py#L777)
2. **给新发言留下回读锚。** 复用已有的受理回合标识、发言块与宿主来源，最少能把有效发言追溯到评审卡、批次、席位、稿次和原文指纹。现有锚无法证明时，只补必要的宿主元数据并验证持久化往返。发言绑定取实际送给席位的版本，不能在落块时用当时最新版本补签。老块缺证直接走完整装配，保留历史和界面原文。给模型复用的发言走现有可见性和隔离投影。 [席位回合身份测试](../tests/test_review_turn_identity.py)
3. **发请求和落票都核对这份身份。** 复用 `run_once(expect=…)`、现有批次守卫和 `approve`／`reject` 工具。轻量材料计算后到首跳之间发生换批或改稿，按现有过期路径交回，最新步骤由现有调度决定。工具续跳核对稿件身份，同轮有效投票改了票态后正常收口。投票在现有写事务内复核本轮的批次、席位、稿次和正文指纹，拒绝把旧材料上的票落到新稿或新批次。并发测试要在校验与写入之间制造一次真实变更。合法成员在有效批次内依旧可以直接投票、改投。发言依据只用于选材。 [步骤过期回执](../src/api/review_runner.py#L148) · [现有投票入口](../src/api/card_tools.py#L6454)

## 三、再做两类轻量装配

| 步骤 | 首跳必须给到 | 回到完整装配的条件 |
| --- | --- | --- |
| `confirm` 增量确认 | 席位职责、原评审条件和必要的用户裁定、评审卡／被评卡／批次、原批准票及其稿次、现稿版本、批准快照到现稿的真实 diff。保留每个修改区块和判断改动所需的上下文。原批准理由有可核实的发言锚时一并带上。 | 旧票快照缺失、旧票与本轮无法对账、改动无法完整定位、关键背景无法保全。两份可信原文逐字相同才可显示「正文一致」，并列两份版本、保留现有投票流程。 |
| `vote_nudge` 同版补票 | 上述共用身份与评审依据、当前稿次、该席在同一批次和同一正文版本的可核实意见、当前投票状态、意见涉及的草稿原文片段及坐标。意见保留原文和发言锚。 | 只有「发过言」标志、意见跨批次或跨版本、必要条款无法定位、基准不可查、新的否决依据或用户裁定需要重新理解草稿。沿原流程提供当前完整材料。 |

- 在选材入口传给现有分区装配一个受限的当轮决定。只对判定成功的两个步骤跳过与本次动作无关的整棵卡片清单、子卡状态、被评卡长历史、大段记忆和无关依赖全文。一份需要保留的材料只经一个入口发送。保留职责、评审规则、投票说明、有效用户发言、必要的上游约束和真实工具对。继续沿用原来的席位能力与场授交集。 [分区装配](../src/api/context_regions.py#L1250) · [评审场授面](../src/api/review_runner.py#L743)
- 草稿坐标从本次快照的逐字原文计算，片段带块名、稿次及位置。现有 `read_card` 跨卡不能读草稿，需要的原文由有权的评审入口随本轮给出。无法完整提供必需片段时回退完整草稿。普通读卡权限由现有工具处理。 [草稿读权限](../src/api/card_tools.py#L1031)
- 第一跳、工具续跳和同跳重试看同一份有效材料，保持调用和回执配对。重试期间材料身份失效时走过期处理。正常插话、停止和换批使用原控制链。选材及回退都在当前合法回合内完成。

## 四、给施工方的复验清单

用 `tests/conftest.py` 的隔离库，先做一份带长草稿、长历史、子卡现状、场内用户纠正的基线。在必须保留和准备省去的材料上分别设唯一标记，逐次请求核对。各组从同一份状态独立起跑。沿 `review_runner.run_once` 进入 `_seat_turn → routes._run_message → gateway → 适配器`。可在传输层回放模型帧，保留实际席位装配、工具执行、投票落账和回读。沿用批二的出站抓取方式。 [传输抓取样例](../tests/test_batch2_outbound.py#L178)

| 必测 | 验收证据 |
| --- | --- |
| 增量确认 | 用正式投票工具建立旧版通过票，修稿并沿正式步骤进入确认。两处独立改动都在出站 diff 内，完整保留席位原票、必要评审依据和当前稿次。分别回放通过与否决，读回票所属评审、批次、版本、席位与理由发言锚。 |
| 同版补票 | 同一席位在当前版本真实发言且未投票，下一步由 runner 选为 `vote_nudge`。首跳收到该席原意见、对应草稿原文和待投票态。在调用计划加入一次真实读取与一次同跳重试，核对投票前后的真实回执、工具配对及重试材料一致。 |
| 回退与过期 | 分别构造旧快照缺失、原文相同的空 diff、内容改变但稿次尚未推进、发言缺锚、同席旧稿意见、条款定位失败及新否决依据。逐例核对选材或过期原因。有完整材料时保留已有的原文和用户裁定。 |
| 并发和用户控制 | 分别在装配后首跳前、在途工具投票前换批和改稿，含同稿次正文变更。旧材料产生的新版本票为零，既有合法票和新批次记录可回读。用真实插话和停止入口验收，下一有效请求带上用户纠正或正确停止，记录实际新增请求数。 |
| 边界及权限 | 首评、重评、对齐批、被评卡修订和定稿保留各自出站材料与行为。在补票试点核对实际发出的工具表，越权跨卡读草稿和非成员投票沿真实工具入口被拒。 |

## 五、交付与放行

1. 交一个可复跑的隔离测试或回放入口，以及本批施工回报。按评审卡、步骤、批次、稿次／原文指纹、席位、回合、跳次、尝试和实际出站座记录。逐请求给完整载荷字节、草稿或 diff／意见、历史及其他主要分区字节，汇总同一步的总请求数和总出站字节。无可查的供应方缓存读写、未命中输入记为未知。
2. 对 `confirm` 和 `vote_nudge` 分别提交开关关／开两组实际适配器出站及对应投票回执。通过条件是**相同判据、相同业务结果下，两类轻量步骤各自总出站字节降低，请求数无增加**。回退及非试点场景以正确性验收。只测模板、手工拼接字符串或只报告首跳字节，均缺出站验收证据。
3. 回报逐项列代码位置、测试命令、实测结果、旧有失败及对照依据。性能回放使用隔离库，组间按冻结状态重新复制。5700 整组发布按项目规则单独请示。
