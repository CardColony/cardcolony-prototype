# 原型自动模式的目标推进与事件续跑

2026-11-20 · 原型优化建议，排在新增 Harness 方向策略的主动试点之前

## 架构决定建议

自动模式的目标是让卡及其子树自主完成用户交付的目标，并允许用户随时接管。建议由**模型或负责人确定下一步及其前置，Harness 核对这些已声明的条件，现有目标驱动器启动自动回合**。事件和条件的匹配在本地完成。[原型自动模式的初衷](自动模式-方案-20261016.md#L7) · [机制判断与执行不变量的原裁定](机制判断归harness-裁定-20261101.md#L16)

| 责任方 | 要负责的事 |
| --- | --- |
| 用户、目标与任务的权威入口 | 确定当前目标和优先级、授予执行范围、变更方向、停止和恢复。计划中可以保留多个可并行步骤。 |
| Harness | 对已登记的任务关系和获准规则核对目标版本、前置结果与回执归属。有匹配事实时交给驱动器相应的续轮事由。策略可以把需要研判的问题交给指定责任方。 |
| 原型目标驱动器与执行入口 | 持有唯一自动续轮预约。执行前核对目标版本、开关、人工停止、属主、在途预约及权限。负责排队、互斥、取消、去重和恢复时的回读。实际写入继续走对应业务入口。 |
| 执行模型 | 在已有工作回合中解释目标、选择优先事项、判断步骤能否独立进行，必要时提出等待哪项结果。遇到产品方向冲突由有权者裁定。 |

### 现有能力与试点缺口

原型条件引擎支持事件、字段比较、计数、先后关系及逻辑组合。已有定稿事项会根据评审批次和真实定稿状态判断是否解除。通用自动任务还需要能查询「正在等哪笔派工」「这条回执属于哪一步」「这份结果是否已经消费」。例如现有 `worker_done` 的 `reply_to` 是可选字段，同一张卡先后接过两件事时，仅凭发件卡相同不能关闭指定等待。施工时优先复用已有派工或消息 ID，缺少可靠关联就显示待核实。[条件求值实现](../src/infra/harness_cond.py#L76) · [已有定稿核对](../src/infra/intervention_runner.py#L53) · [完工事件契约](../config/event_catalog.json#L1672)

「这次技术分析有没有价值」「有没有一项值得做的独立工作」属于语义判断。优先让正在工作的模型在形成计划、派工或交付时说明。只在目标未完成且确实缺下一步时安排定向研判。没有登记等待、也没有收到回执，本身不能证明卡该停工。

现行原型的正常回合收口会通知 goal 驱动；目标满足 active、armed 等条件时可排下一轮。驱动已有目标版本和回合预约。原型 Harness 的 `inject` 等下轮消费，`message` 能选择是否唤醒，`continue` 当前只接评审卡。旧 `auto_driver.after_turn` 中仍有零工具轮计数，当前通用回合收口已把续轮职责交给 goal 驱动。只改旧计数，或直接给普通卡发 `continue`，都覆盖不到本题的正式路径。[收口入口](../src/api/routes.py#L3672) · [旧路径说明](../src/api/routes.py#L3761) · [目标驱动与预约](../src/goal/driver.py#L204) · [原型 Harness 投递](../src/infra/harness.py#L210)

## 一件任务如何持续推进

现行 goal 驱动的 `_yield_to_children` 按是否存在未终止子卡整体让位。建议先用一例对照验证这个边界：当父卡同时有确实独立的待办时，是否应当继续。执行串行配置、真实资源占用和原权限仍由执行入口裁定。[当前让位逻辑](../src/goal/driver.py#L171)

以「正式跑通 ACC-1」为例。007 把启动复跑交给 057 时引用本次派工，并声明下一步等它的运行结果。如果 007 的计划里另外列出可以独立做的 S1 核对，系统能按记录继续该步。只剩已声明的等待时，让出回合。057 的启动失败报告准确关联到派工后，也可以满足「结果已返回」，让 007 解释失败并选择下一步。若前置写的是「启动成功」，失败报告只触发故障研判，成功条件仍未满足。相同回执再次到达时复用处理记录。

| 现场情况 | 推荐处置与省下的调用 |
| --- | --- |
| 用户给了新目标，或者已有授权步骤可执行 | 新目标允许模型起步、理解与拆解。续轮带当前目标、优先事项、已知结果及可做步骤。可由本轮直接完成的动作走正常工具循环。 |
| 已派工、在等执行或外部结果 | 只让对应步骤等待。相同状态的 idle、重复通知和相同回执不再开模型回合。真实成功、拒绝、失败、撤销均可触发重新判断。 |
| 上一轮在做分析、比较方案或整理结论 | 一份能供下一步使用的结论，或一个新的、与目标有关且可核实的假设，都可以支持继续。零工具的有效研判应能正常向前。反复读同一材料、原样复述计划，则要核对还有什么具体问题待解。 |
| 目标未完，也找不到已登记的下一步或有效等待对象 | 对这一份目标和现场事实，给执行卡一次定向梳理的机会，列出可以立刻做的工作或指出缺谁的什么决定。得出可做事项马上推进。仍无可做事项时给负责人一条可处理的具体障碍，保留可见待办和恢复条件。新的依据到达后重新求值。 |
| 用户接管、改目标、暂停，或副作用结果未明 | 用户输入优先。取消过时预约，保留已受理动作的锚。结果未明先读原回执，重新执行要有明确未受理的事实和仍有效的授权。人工停止由显式恢复解除。 |

目标驱动保留已有的显式预算与运行边界。工具次数、文字长度、沉默时长只能辅助诊断空转。自动续跑的依据应能具体说成「哪一个动作现在有条件执行」「哪一个依赖刚结束」或「哪个疑点值得做一次新的查证」。模型自行换措辞或添一个编号不能无限制造新的事由。

## 手动和自动的边界

两种模式统一使用当前需求、用户优先级和真实回执。手动卡在用户已发起的当前任务内可以查证、调用获准工具并完成交付。单纯发现另一项可做工作时，默认留给用户或下一次自然回合。已有明确授权的指令、评审和消息按各自入口处理。自动卡在已授权目标内可以自主接下一步、等依赖和恢复。分别读取每张目标卡当时的模式与权限，父卡的自动开关不构成叫醒手动卡的依据。切回手动后撤销待执行的目标续轮，已经在执行中的工作服从已有停止与接管语义。

这是 Python 原型的优化。CardColony 的底座正稿 A14-6 在 1.0 只配默认运行模式，模式维保留在能力模型中。Go S5 已批准的动作中 `message`、`inject` 均不唤醒，`continue` 含一次唤醒。未来适配同类业务策略时，按这份产品契约落地。[模式裁定记录](../works/work_073/sessions/session_018-rv_e3e151f57d.md#L877) · [S5 动作契约](../works/work_073/_card049_zhenggao.md#L90)

## 施工次序与验收

1. **先做旁路对照。** 在真实 `notify_idle → drive → _run_message` 链记录现行决定，同场记录候选策略为何继续或等待。关联工作域、卡、目标版本、原任务或步骤和来源事实。比较的是同一份现场状态。历史暂停只表明当时的记录状态，要另核是人工停止、正常等待还是故障。
2. **再试一条自动卡链。** Harness 对事实求值，试点 goal 驱动只消费一次有效的推进事由，并沿既有预约起轮。保留用户首次交付、插话和显式恢复入口。等依赖复用已有派工、执行回执和任务存储。登记等待时先订阅再回读，或用等价的原子交接。属主进程恢复时按照持久记录补核遗漏的完成事实。正常等待期间无需用模型轮询。
3. **双向验收。** 同时交付以下正反例的源事件、真实模型请求数与最后可见状态，隔离实例通过后才评估实际启用。

| 用例 | 可核验结果 |
| --- | --- |
| 同一等待收到多次 idle，随后唯一子任务回执到达并重复投递 | 等待期新增模型请求为零。解除后有独立待办时恰好续一次。 |
| 一个子任务一直在跑，父卡还有一项已授权、无依赖的当前优先任务 | 父卡能推进独立事项，已派子任务零重复派发。 |
| 回执先于等待登记到达，或登记后属主重启 | 从原记录恢复，已完成条件能触发接续，已处理的回执不重放副作用。 |
| 纯分析产生有效交付，与反复调用只读工具复查相同结果 | 分析可以完成或推进。重复轮能指出具体缺项或转成可见等待。 |
| 目标还没完、无子卡、下一步不明确 | 有一次面向缺项的梳理机会。随后给出可执行下一步或可见阻塞及其负责人。同一事实不会反复消耗梳理回合。 |
| 自动卡切回手动、人工停止、旧目标结果晚到 | 旧预约不会启动。人工明确恢复后按当前目标行动。手动卡的正常工具执行和授权消息仍能工作。 |

对照统计按任务记录偏离当前优先级的轮次、相同等待状态下的模型调用与实记 token、条件已满足却未恢复的任务，以及完成率与人工催办次数。节省了多少额度、有没有使工作更易停滞，都要用相同任务条件下的运行读数回答。

## 施工方派工单

**对象与范围。** 在 Python 原型隔离实例建设一条自动父卡与子卡的最小验证链。使用隔离数据复现 007→057 的派工形态。按卡型取实际返回入口，普通子卡使用真实汇报，worker 使用其完工回执。沿原派工编号关联任务，覆盖同卡连续承接两件事的情况。工作目录为本仓，本单交付到隔离验收，5700 后端发布另行请示。

**施工顺序。** 先从真实回合收口走到目标驱动器、预约校验及模型请求，对同一输入记录现行行为和候选判断，旁路判断只记结果。再在隔离实例由候选策略提供有效续轮事由，经现有驱动器执行。模型在已有工作回合声明下一步和等待条件，Harness 机械核对。本次隔离验收包含上表全部场景，尤其要在无有效关联、只有其它任务回执时保留原等待并展示原因。

**交回材料。** 提交改动文件、可复跑命令、专项与相关回归结果，以及逐用例的原始证据。证据须能对上任务和目标版本、来源事件、策略判断、自动回合预约、实际模型请求和最终任务状态。同一步可以有多个正常工具调用，分别统计逻辑回合与实际模型请求。旁路预测、隔离实跑和实记 token 分列。等待期间增调模型、应恢复却停工、重复派发副作用或人工停止后自行重启，任一复现即该项未通过。[现有自动模式测试](../tests/test_auto_mode.py) · [目标恢复测试](../tests/test_goal_reactivate.py) · [策略派发测试](../tests/test_policy_runner.py)
