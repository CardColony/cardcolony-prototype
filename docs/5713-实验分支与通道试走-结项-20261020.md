## 二、现有基建探明结论（照着做，不改）

1. **worktree 约定**：实验分支一律 `git worktree add .worktrees/<名字> -b <分支> dev`，
   现有 20+ 个同类 worktree（5711/5712/5715/lab5703/role5710…）。
2. **快照数据根自动隔离**：`src/storage/data_snapshot.py` 里
   `SNAPSHOT_ROOT = BASE_DIR.parent / f"{BASE_DIR.name}_data_snapshots"`，`BASE_DIR` ＝代码根。
   ⇒ 在 `.worktrees/5713` 跑，快照自动落 `.worktrees/5713_data_snapshots`，**与生产快照库物理分离**。
   （实测：`BASE_DIR=…\.worktrees\5713`、`SNAPSHOT_ROOT=…\.worktrees\5713_data_snapshots`。）
   隔壁那批 `*_data_snapshots` 目录正是这么派生出来的。
3. **测试实例不 import main**：`scripts/run_test_instance_5701.py` 照抄 main.py 的 app 装配但
   **跳过 `startup_init()`**——因为 main.py 在导入期会 `git add -A`+commit 并覆盖 `.server.pid`
   （2026-10-03 事故禁令）。测试实例因此**不写 pid、不碰 git**。
4. **沙箱机制**：`ECO_TEST_SANDBOX=1` 时 `redirect_roots()` 把
   `card_store/work_store/canvas_store/session_store/manuscript_store` 的 `WORKS_DIR`、
   `data_snapshot.BASE_DIR/SNAPSHOT_ROOT/_FINGERPRINT_FILE`、`prompt_log.LOGS_DIR`、
   `file_tools.BASE_DIR/ALLOWED_ROOTS/BACKUP_DIR` 全部改指沙箱根；
   配合 `ECO_SANDBOX_ROOT=<固定路径>` 可复用同一沙箱（否则每次 `mkdtemp`，实验数据全丢）。
5. **进程身份探针**：`GET /__instance__` 返回 `instance/base_dir/sandbox_root/pid`——
   每次实验先打一发，核对代码根是不是自己的 worktree、沙箱是否开着（本实验即以此验身）。
6. **凭证**：`.env` 被 gitignore，worktree 里没有；实验时从主仓复制一份到 `.worktrees/5713/.env`
   （与 5711 / lab5703 / permexp 的既有做法一致）。

## 三、改了什么（3 个提交）

### 25c08c3 · 卡间通信的边界改为通信线（主线改动）

| 文件 | 改动 | 为什么 |
|---|---|---|
| `src/permissions/policy.py` | `check()` 新增 `scope` 档位：`subtree`（缺省＝历史行为，逐字不变）/ `linked`（已有通信线即通）/ `any`（不判树作用域）；新增 `_linked_between()`；新增**独立关口** `check_linked()` | 树作用域只对 `TREE_SWITCHES`（edit/delete/link/unlink/create_child）生效，而发信开关是 `read`/`send_card_message`——硬塞 `scope` 会被整体跳过、等于没拦（首版实测踩到，故做成独立关口） |
| `src/api/card_tools.py` | `link_cards`/`unlink_cards`/`link_rel`/`unlink_rel` 取 `SCOPE_ANY`：**建/解线不再受 parent 树约束** | 平级卡若建不出线，就永远通不了话（先有鸡先有蛋） |
| 同上 | `_h_send_card_message` 新增 `require_link` 形参：模型侧走 `policy.check_linked`（**无线即拒，并指路"先 link_cards"**）；流程薄壳 `send_card_message` 传 `require_link=False` | 完工回执、blocked 通知、S4 自动回发是**系统通道**，不是模型自主通信，不该被自己新加的闸挡死 |
| 同上 | 工具面 `send_card_message` 描述改口径（原「只能发给同一棵任务树内的卡」） | 工具面文案与执行层必须同源，否则模型按旧话术发信、撞新闸 |
| `src/api/prompts.py` | 注入上下文的工具说明同步改口径 | 同上 |

判定语义（`_linked_between`）：**任一侧 `links` 有指向对方的条目即成立**（A 建的线，B 能沿它回话）；
`relations`（依赖关联线）**不算**；自指不成立；缺卡即假。

### 2c5ddf7 · 验收网随新口径对齐
- `tests/test_card_msg.py`：夹具按用例需要铺通信线（002→003 主线、001→002/004），**002→004 故意不铺**（越权例）；
  test_t4 第 8 例改为「无线即拒」，新增 8b「子树内但无线也拒」——线取代树的边界。
- `tests/test_dep_relations.py`：`link_rel` 兄弟建线由 denied 改放行（有意推翻旧口径）；
  隔离用例结论不变（relations 不构成通行证），机械断言改判 `policy.check_linked` 单点。

### 2555bc1 · 同轮「先建线再发信」要能走通 + 另两处验收网
- `card_tools`：四个建/解线 handler 落库成功后**同步 `cards[current_id]`**（与 `_h_create_card` 同手法）。
  不补这一步，模型在同一轮里先 `link_cards` 再 `send_card_message` 时，发信读到的还是**本回合开始时的旧卡面**
  （没有新线）→ 被「无线即拒」错杀。`test_auto_mode::test_g2` 实测踩到，属真问题、不是测试问题。
- `test_perm_gateway_acceptance`：`test_link_unlink_subtree_tightening` →
  `test_link_unlink_no_tree_scope_with_type_gate`（旁支可连/可解；**类型分权、自身、悬空线**三条硬约束保留）。
- `test_auto_mode::test_g2`：甲第 1 轮**先建线再发信**（agent 自主建线的真实形态），并断言线确实是甲自己建的。

## 四、通道试走（真机实测，证据 `verify/5713/evidence_channel_walk.json`）

**怎么跑**：见 `verify/5713/README.md`。一句话：起 5713 隔离实例 → `python verify/5713/channel_walk.py`。

**设计**：测卡A＝发起方（auto＋goal，建成即自动开跑）；测卡B＝应答方（auto 但**不给 goal**）——
B 不空转跑轮次，只在 A 的信到达时被 K3 调起，由**它自己的模型回合**作答（不是 S4 兜底代答）。

**实跑结果（`work_002`，跑在 `2555bc1` 这版代码上）**：判定 **PASS**，8 项机械判据全 true。

| 环节 | 证据 |
|---|---|
| 发现另一张卡 | A 现状块：「对方卡：card_002 ·《测卡B-通道试走应答方》（来源：上下文「卡片清单」，未猜测）」 |
| 建通信线 | `card_003.links = [{target: card_002, type: 关联, note: 通道试走：A→B}]`；A 记「建立返回 ok=true」 |
| 发消息 | `msg_ask`，`msg_id=card_003-b2b6d071`，card_003 → card_002 |
| 收到应答 | `msg_answer`，`msg_id=card_002-a684472e`，`reply_to=card_003-b2b6d071`（配对已在事件流原文核对） |
| B 是自主应答 | B 自己的现状块逐条写了收到询问、建线回话、`send_card_message(...reply_to=card_003-b2b6d071)` |
| A 被唤醒并留证 | A 现状块写明四段全通、无一步被拒，`goal_state=complete` |
| 暗号校验 | 应答正文含「暗号 5713」＋B 的真实标题，与卡片清单一致 |

**机械判定 8 项**：`A_found_B / A_built_link_to_B / A_sent_ask / B_answered /
B_self_answered_wrote_status / answer_reply_to_matches_ask / A_wrote_evidence_in_status` 全 true。

> 首跑（同一驱动器、修 `same-turn` 缓存前的代码）也跑通了，但 A 是「建线一轮、发信下一轮」才成的；
> 修完缓存同步后，终版代码重跑一次，才是上表这份证据。

   同一源卡多条线必须一次写完，分两次写会互相冲掉。
