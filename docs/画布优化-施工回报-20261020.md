## 二、做了什么

### 2.1 信息更新：工作级事件广播（新增能力）

**病根**（逐条核实，不是推测）：

- 卡片结论／待裁定数／work_state／最新对话**只写在 `createNode` 里** ⇒ 只有全量
  `renderAll` 才生效；而 `renderAll` **只由用户自己的操作触发**（建卡、删卡、
  重命名、拖动落定…）。后台真实发生的变化——模型写卡、裁定被记下、自动模式推进
  ——**没有任何通道能通知画布**。
- 既有 SSE 是**单卡**的（订阅表 `key=(work, card)`），**没有工作级广播**。
- `canvas.js` 订阅的是 `card_id=WORK_ID`（根卡）那一条 ⇒ 别的卡的 `card_message`
  收不到。
- `/works/{w}/pulse` 的 running/recent **不驱动卡面重绘**（`applyLiveStates` 只写
  `dataset.live` 与一行消息条，conclusion/pending_count/work_state 一个都不碰）。

**修法**（三层）：

| 层 | 文件 | 内容 |
|---|---|---|
| 事件 | `src/api/event_stream.py` | 新增工作级广播：`emit_work` / `subscribe_work` / `work_subscriber_count`。与主通道**完全隔离**（不进 `_journals`、不占主 seq、不写 works 文件、不进模型输入），零阻塞零抛出 |
| 写路径 | `src/storage/card_store.py` | 新增 `_notify_card_changed(work_id, card_id, kind)`，挂在 create／update／delete／restore 四处。**延迟 import**（storage 不在导入期依赖 api，与既有 `from ..api import scheduler` 同手法），失败零阻断 |
| 载荷 | `src/storage/canvas_store.py` | 新增 `card_projection(work_id, card_id)`：从**刚重建过的**画布投影里取那一张卡 ⇒ 事件里的 card 对象与首屏 `/canvas` 返回的**字段完全同源**，不会出现"事件里少个字段导致卡面缺零件" |
| 端点 | `src/api/routes.py` | `GET /api/works/{work_id}/events`（SSE，帧形态与既有 `/stream` 同构，15s 心跳） |
| 前端 | `static/canvas.js` | 订阅 + **就地更新那一张卡**（不重建整棵树） |

**前端为什么是"换卡面"而不是"换节点"**：

初版实现是 `old.replaceWith(fresh)`——后台一次更新就把用户**正要点的**那张卡换掉了，
那个 click 落在一个已脱离文档的节点上 ⇒ **点了没反应**。现改为**保留节点身份**：
只把卡面内容（innerHTML + dataset + aria）搬到老节点上 ⇒ 监听器、焦点、拖拽态、
展开的对话单元全都在。配套把**卡面子元素**的监听（子卡徽章／↗／待裁定条目）从
**节点级**监听里拆成 `bindCardFace`——换卡面后要重绑子元素，而节点级监听**不能**
重绑（重绑＝重复绑定：单击跳两次页、展开翻两次）。

**实时更新必须同时改两张表（这条是踩出来的）**：

`state.data.cards`（原始列表）与 `state.index`（派生索引）**必须同步**。
初版只改了 `state.index`，而**布局算法读的是 `state.data.cards`**
（`collectProjectionInput` → `computeLayout(input.cards…)`）——两张表一分裂，
布局算出来的位置里就没有这张卡 ⇒ 增量渲染写不回坐标 ⇒ 节点永远停在占位坐标 (0,0)
且带 `.entering` ⇒ **整片画布的卡片全部不可见**（只剩连线）。
这是"索引是派生数据、原始列表才是真相"的典型：只改派生数据 = 制造不一致。

配套加了一道**半渲染自检**（`_assertNoGhostNodes`）：增量渲染之后若还有节点
"既是 (0,0)、又带 .entering" ⇒ 说明坐标没落到位 ⇒ **退回全量重绘**。
全量重绘慢一点，但一定对；半渲染错一点点，就是整片看不见。

**新卡的插入位置也必须与服务端同口径**：

服务端投影是 `ORDER BY card_id`；若把新卡 `push` 到列表末尾 ⇒ `childMap` 顺序变了
⇒ 同层卡排布变了 ⇒ **实时更新过的画布与刷新过的画布长得不一样**（肉眼不一定
看得出，但按坐标点击会落到不同的卡上——e2e 的差异就是这么暴露的）。
现在新卡按 `card_id` 升序**插入到正确位置**，两条路径产出同一布局。

**可执行不变量**（加进 `tests/canvas_live_update.mjs`）：

> 建一张卡再删掉它（触发两轮实时更新）之后，DOM 顺序必须与**重新加载页面**之后的
> DOM 顺序**逐字相同**。实测 `invariant_liveEqualsReload = true`。

**SSE 健康度要单独记**：`EventSource` 对象存在 ≠ 连接可用（企业代理会"接受连接
但不投递"）。兜底轮询按**健康度**（`onopen`/`onerror`）接管，而不是按对象在不在；
兜底命中时走**静默重拉**（`reloadCanvas({silent:true})`）——画布上已经有内容了，
再弹一次骨架屏就是一次"白一下"。

### P0-4 的两条失败模式（都实测过，改法不是拍脑袋）

| 机制 | 症状 | 为什么"改成 transition 就行"是错的 |
|---|---|---|
| `@keyframes` 起始帧 `opacity:0` | 动画不跑 ⇒ 停在起始帧 ⇒ 卡片永远透明 | — |
| `@starting-style` + `transition` | transition 不跑 ⇒ **starting-style 一直挂着** ⇒ 卡片同样永远透明 | 探针实测：`animation` 关掉后 p3 仍是 `opacity=0` |

⇒ 唯一可靠的口径：**入场的起始态里不能有 opacity**。改成只动 transform 后，
起始态即便钉住，卡片也**照样看得见**（只是没有淡入）。退化方向必须是
"少个动画"，不能是"看不见"。

> 这条缺陷**基线也有**（dev 原样跑，在内置浏览器里打开画布同样只剩连线）。
> 它之所以长期没被发现：绝大多数时候窗口在绘制、动画能跑 ⇒ 卡片正常；
> 一旦窗口未绘制/标签页在后台，就出现"画布空白"，且**没有任何错误信息**。

## 四、偏差自裁

1. **一版实现被我推翻**：实时更新初版是"替换节点"，实测会**吃掉用户正在进行的点击**
   （后台写卡撞上用户点击 ⇒ 点了没反应）。改成"保留节点身份、只换卡面"。
   ——教训：增量更新不能假设"用户此刻没在交互"。
2. **我一度把"自己的 bug"判成了"测试不稳定"——这是本轮最大的误判，如实记下**：
   中途 e2e 的 `A10a 单击＝进入对话页` 在 5711 上 FAIL、在基线上 PASS，我先归因为
   "共享沙箱被前序测试改动"，又做了"基线自身确定性检查"（同数据连跑 3 次），
   然后下了"该 e2e 在本机 inherent 非确定"的结论。
   **这个结论是错的。** 真因是**我写的实时更新路径只改了 `state.index`、没同步
   `state.data.cards`**，把画布状态搞成不一致（见 §2.1）⇒ 画布卡片不可见 ⇒
   e2e 看到的第一张卡、初始 pan 全部漂移。基线之所以"稳定"，是因为它根本没有
   实时更新这条路径。
   ——教训：**"两边不同"先怀疑自己**。我做基线确定性检查时，用的是"同数据连跑三次
   看基线自己会不会飘"，而不是"两边用**完全相同**的沙箱跑同一条命令"——
   前者只能证明基线稳，后者才能定位差异来源。控制变量要控制到**状态**一级，
   不是到"数据看起来一样"一级。
3. **"改成 transition 就安全"也是错的**（我自己写了一遍才发现）：
   `@starting-style` + transition 在 transition 没跑时，starting-style 会**一直挂着**
   ⇒ 卡片同样永远透明。探针实测：`animation` 关掉后卡片仍是 `opacity=0`。
   ⇒ 最终口径是"起始态里不许有 opacity"。**失败模式必须逐个实测，不能靠推理。**
4. **修了两个"范围外"的连带项**：
   - 测试实例缺 `settings_router` ⇒ 探针里那 2 个 404 是**装配缺件**不是产品缺陷。
     但 dev 在 `03f0b86` 已经做了同一件事 ⇒ 合并时取 dev 侧（代码等价）。
   - 视图存档的 `openCells` 不持久：注释写着"必须持久"但没实现 ⇒ 属画布行为，
     在本轮修掉。
5. **没有动的（明确登记，不擅自改）**：
   - `style.css` 的 `.card-node.entering{animation:card-in}` 是**共用**规则，
     对话页也在用。本轮只在**画布页**（canvas.css）显式 `animation:none` 覆盖它，
     **没有去改共用规则**——改它会波及对话页的入场效果，不在"优化画布界面"范围内。
     （画布页的覆盖是完备的：共用规则对画布页不再生效。）
   - `style.css` 在首页/设置页仍是 `?v=40`、画布/对话页是 `?v=45` ⇒ 同模块双版本
     （浏览器可能吃旧缓存）。这是**首页与设置页**的事，不在画布范围；改它要连带
     验证那两个页面的外观，故登记不动。
   - `test_dsh_flow_render.py` 里 `workspace.js` 等对话页链路的版本基线与实际值
     的偏差——由 dev 那条线负责（合并时按两侧各自的改动合并了期望值）。
   - 既有 100 余条 pytest 失败：绝大多数是**测试里真调模型且鉴权失败**
     （worktree 无有效 key），与画布无关。
6. **A10a/A8f/A8g/A8h 等既有 e2e 失败**：两边一致，属既有缺陷，本轮**未修**

   需要单独立项，不在"优化画布界面"的可控范围内）。

## 五、是不是补丁

**不是补丁**。判据三条：

1. **不是绕过，是补上缺失的机制**：工作级事件广播是**新增的一层**（事件层＋写路径
   挂钩＋端点＋前端消费），不是给既有路径打补丁绕过。
2. **不是特例处理，是一次性把口径对齐**：浮层显隐收回 `.active`（对齐
   `style.css` 的语义）、可见集改读投影（对齐 V3 不变量）、存档读写两侧对齐、
   版本戳与测试基线同步——都是**把两套口径并成一套**。
3. **新增的验收工具会长期在网**：`canvas_live_update.mjs` 是"信息更新"这条诉求的
   **可执行定义**；`canvas_audit.mjs` 是画布的体检清单。两者都进版本库。

**遗留的债（如实登记）**：

- 工作级事件**只覆盖写卡路径**。影子（`shadow_store`）的变更、记忆凝练、工具卡的
  内部推进**不走** `card_store` 的四个写入口 ⇒ 那些变化暂时还不会推到画布。
  补齐它们需要各自的写路径挂钩（下一轮）。
- 事件流是**单进程内存态**（继承 `event_stream` 的既有约束 A44）：进程重启后
  订阅断开，前端靠 `EventSource` 自带重连 + 4s 指纹探测兜底。
- 前端仍是**扁平 DOM + 逐卡内联样式**，没有虚拟滚动；300 卡已经是 2475 个 DOM
  节点，再上一个量级需要另立一轮。
