# 模型调用成本优化方案与施工任务书

施工对象为推演 Agent 原型，首批用 `work_073` 的真实卡片回放验收。本线用三个可复验的节省量衡量结果：完成同一任务需要的模型请求数、实际发送的输入体积、提供方报告的输入和输出 token。优化前后使用同一模型路由、相同任务和输入版本。先验证关键材料、工具权限和真实执行结果，再看成本变化。方案以现存代码、请求回放和执行回执取证。 [项目规则](../AGENTS.md) · [原型性能方案](原型性能系统优化-方案-20261119.md)

## 一 基线和施工顺序

按以下顺序分别提交改动和验收。第一批可单独交付。第二、三批先用隔离回放确认语义，第四到第六批按各自入口逐项验证。第七批收益观测随各批采集，前面的确定性优化可以独立验收。每批写出所用样本、命令和实际读数。

| 顺序 | 工作 | 优先验收 |
| --- | --- | --- |
| 1 | 同一次请求里的依赖正稿去重 | 两条线、一份完整正稿、重复正文减少约 287 KB |
| 2 | 清单和子卡现状走当轮输入口，控制依赖正文体积 | 实际出站的稳定前缀和动态事实位置，续跳与状态更新 |
| 3 | 评审补票与增量确认用短材料 | 相同草稿版本、权限、票与理由，实际输入缩小 |
| 4 | 工具结果按证据区间和引用复用 | 保证原文可取，减少重复读取和重复回灌 |
| 5 | 合并重复唤醒与同一次请求的重试 | 降低实际出站次数，保住用户停止、授权及接收方记录 |
| 6 | 复用可证明未变化的凝练和归拢结果 | 水位及原文锚点等价，减少模型跳数或输出 |
| 7 | 建立同口径的请求、缓存和完成情况对照 | 每批能够独立重放并计数 |

## 二 第一批 依赖正稿无损去重

**入口。** `context_assembler._dep_relations_for` 装配正向与反向关系，`context_regions.render_dep_relations_region` 当前在每条正向边下面拼一次目标正稿。先修渲染口，保留关系的数据模型。 [关系取数](../src/api/context_assembler.py) · [依赖区渲染](../src/api/context_regions.py)

**施工。**

1. 按现有顺序保留所有边。对每一条正向边，先输出目标卡、关系类型和关系说明。
2. 在单次渲染里建立已经展示的正稿集合。身份为「目标卡＋当前版本」。如果当前投影没有实际版本字段，用原正文的稳定指纹对账。以同一快照读到的正文为准，版本不同或文本不同的记录保留可区分的来源。
3. 第一次看到同一目标同一正文，原样展示完整正稿。再看到时，沿关系线保留一行指向同卡本区的正稿。两个不同卡号即使文字一样，仍各有自己的文档身份。
4. 原来的边权限、正文可见性、反向关系和上游需求注入从各自现有入口继续读取。第一批范围只覆盖依赖区的确切重复。跨区的重复另列观察结果，确认引用契约齐备后再处理。

**通过条件。** 用两个不同语义的正向关系指向同一卡，断言两条关系、两份关系说明及一份逐字一致的正稿。另测空正文、两个同名目标、版本变化、反向关系和原本无重复的卡。用 `card_009` 快照复跑，在模型实际解析的请求中数正稿正文的出现次数。对比字段报告删除的字节，避免只以某个分区消失当作通过。主要回归 `test_context_registry.py`。 [回放样本](../logs/prompt_card_009_20261120094647.json)

## 三 第二批 动态材料走当轮输入口

**入口。** `context_regions` 的清单区和子卡区当前属于 system，`message_runner._sync_injection` 和 `_engage_slot` 已能通过 `turn_tail` 随当轮发出材料并让工具续跳继续看到。沿用这一生命周期。 [分区定义](../src/api/context_regions.py) · [当前轮注入](../src/api/current_turn.py) · [轮槽接续](../src/api/message_runner.py)

### 清单和子卡现状

1. **先移动，后缩小。** 第一小步用同一份清单与现状做对照，把材料从主 system 移到宿主生成的当轮事实消息。沿用现有投影机制和来源标记，保留卡号、取数快照、状态来源和必要权限。人类原话保持单独可识别。逐个验证实际端点序列化后的落点。
2. **第二小步按任务选材料。** 明确指定对象、指令来源、活板当前步骤、评审目标和当前目标等已有结构化数据优先。对子卡专项验收，首跳带对象的使命与必要现状，再带相关依赖的短列表。对全局统筹，首跳给管辖范围内全部子卡的简表和异常项，详情可按现有工具取回。没有可靠任务范围时保留现有完整材料。自然语言出现的卡号可用来检查遗漏，权限与触发仍由宿主确定。
3. **每个逻辑回合只插入一次同版本材料。** 首跳经 `turn_tail`，进入工具轮后随轮槽复用。重复装配和同一位置重试不再追加同一份。若任务依赖的卡片状态确已更新，下一个需要该事实的跳次应收到新版本，并标明替代了哪个旧快照。其他卡片变化无需触发模型调用。区分轮槽里只有一份与网络续跳仍会重送整份请求这两件事。
4. **依赖正文采用同一套价值分级。** 默认带关系说明、目标卡、相关条款或原文定位。跨域接口验收、明确审阅全文及依赖条款无法可靠定位时，给所需目标的完整正稿。复用现有 `read_card` 的块与行段读取。记录文档版本或指纹，定位失败时展示原文读取入口。禁止让模型根据标题编造条款。
5. **后续才处理其他大区。** 拆开当前卡里的必要身份、活跃任务与大段历史记录，检查现状、历史和凝练是否在讲同一个事实。优先消除确定的重复或用有锚点的证据片段投影。用户依赖的长期记忆、尚未关闭的指令、人工纠正和任务所需原文必须在对应场景可取得。沿用上下文板及原文账的可见性契约。

**通过条件。** 验收对象分别选 `card_057` 的单卡委派和 `card_007` 的全局管控。首跳、至少一次工具续跳、一次重试及一次相关子卡状态变化都抓取最终请求。检查同版本只出现一次，更新后新事实可见，完整依赖正文仍可按需要读取。邻近两次相同任务同时报告出站字节和稳定前缀。以普通主对话为首批覆盖范围，评审、草稿和席位原有分区另行复验。主要回归 `test_context_registry.py`、`test_context_board.py` 和 `test_t11_tool_fold.py`。 [单卡委派实录](../logs/prompt_card_057_20261120101337.json) · [管理卡实录](../logs/prompt_card_007_20261120094329.json)

## 四 第三批 评审按阶段装配

**入口。** `review_runner` 调 `_run_message` 时已提供 `source.kind=review_step`、阶段 `step`、批次和席位。 `_seat_mandate` 已区分整审、增量确认和补票。由这些实体字段选择材料。 [评审链路](../src/api/review_runner.py) · [回合入口](../src/api/routes.py)

| 阶段 | 首跳必须携带的材料 |
| --- | --- |
| `confirm` 增量确认 | 席位职责、当前批次、已批准版本、现版本、真实 diff 和原批准结论。 |
| `vote_nudge` 同版补票 | 当前草稿版本、该席在该版发过的意见和已有投票状态；意见所指条款可定位到原文。 |
| 首评、重评或变更范围无法判清 | 继续提供本阶段需要的全文、既有决议、历史争议和必要背景。 |

优先对前两类小任务减材料。保留现行工具许可、评审席身份、批次守卫和投票流程。只在能证明批次与版本相同的情况下复用此前意见。版本已变、有新的拒绝理由或缺少基准快照时，发对应阶段的完整材料。避免把目标卡的无关子卡、旧评审全文和大段记忆顺手带入轻量步骤。

**通过条件。** 同一份草稿，用现有链路分别重放一次确认与补票。核对投票所属批次、版本、席位、理由及边界结果。重放旧批次切换、diff 为空、旧意见不可查和用户介入。确认模型只收到所需材料且权限保持一致。主要回归 `test_review_turn_identity.py`、`test_review_batch_guard.py`、`test_two_round_review.py` 和 `test_review_user_intervention.py`。 [评审回归](../tests/test_review_turn_identity.py)

## 五 第四批 工具轮只回传足够的证据

**入口。** `ToolTurnSlot.wire_messages` 已有内容去重、60,000 字符单条上限和 300,000 字符默认总预算。工具结果在回合内仍可能累积很大。优化从高频的 `search_files`、`read_file` 开始。 [工具轮投影](../src/api/tool_fold.py) · [文件工具契约](../src/api/file_tools.py)

1. 搜索结果先给命中位置、数量、是否截断和必要的原文行。显式请求定位区间时，以区间原文为主，保留文件身份和行号。真实结果的落盘和回执仍使用原有来源。
2. 同一轮已经取得的同版本同区间结果，用调用 ID 或确定的原文引用复用。再次发起访问前同时核对工作、权限、工具参数和资源版本。版本不明时允许重新读取。复用的提示在对应原文仍可读取时才成立，旧结果不得冒充新的执行回执。
3. 工具预算按本轮任务和端点量化，先验证短结果与紧邻证据。达到预算后用可复查的定位说明缩减旧结果。保留完整的 assistant 调用和 tool 结果配对、错误码与派发来源。敏感权限和副作用工具的结果不能因投影裁剪改变含义。

**通过条件。** 回放一条搜索后精读的任务、一组重复读取和一次写后回读。验证一次真实读取或可追证的复用，变更后读到新版本。比较工具调用次数、工具区字节及最终模型输入；断言配对与错误状态一致。主要回归 `test_t11_tool_fold.py`、`test_tool_result_in_session.py` 与 `test_quarantine.py`。 [原始工具回执链方案](工具调用与真实回执-修复方案-20261119.md)

## 六 第五批 合并可避免的起轮与重发

### 自动唤醒

先改两个已观察到的来源。其一是 `status_block_oversize_reminder`。同一卡在一次连续超限期间，只保留一条待处理提醒，后续超限修改更新该提醒的事实。恢复到阈值内清理待处理态，再次超限开始新一轮。必要的用户安排和任务触发照常可见。其二是 `pseudo_call_reinvoke`。识别到同一个原回合、同一个协议异常时，用已有受控续接路径接回原任务与有效工具结果，避免同一异常既重发完整首跳又走循环补救。关键指令和真实验收回执沿对应入口即时投递。 [策略定义](../config/harness_policies.json) · [投递实现](../src/infra/policy_runner.py) · [协议异常续接方案](超长会话工具异常隔离与续接-修复方案-20261120.md)

### 重试

网关内层重试、同层回退和循环器外层重发，按「原回合＋模型跳次」共享一次实际出站预算。每次真实请求都扣同一本账。先用已配置的路由重试限制制定联合预算，再以故障回放确定启用参数。断线等可恢复故障可重试；参数、鉴权和明确协议格式错误先修正错误再发。已经产生的真实副作用、用户停止及待确认状态从已有执行记录恢复。恢复流程冒出新请求时沿用原逻辑跳次的标识。 [流式回退](../src/model_gateway/gateway.py) · [循环器重发](../src/api/message_runner.py)

**通过条件。** 对同一问题重复触发、资料更新和新任务分别计数。确认重复提醒合并，新的有效指令照常启动。对断线、确定性拒绝、已落信但投递未确认、用户停止和层内切换，使用模拟传输计数实际出站及落信，避免只断言配置里的次数。主要回归 `test_policy_runner.py`、`test_llm_retry.py`、`test_steer.py` 和 `test_long_session_missed_call.py`。

## 七 第六批 降低凝练和归拢的重复成本

**入口。** `memory_store` 维护各卡凝练水位与归拢，`condense_two_layer.run_two_layer` 负责事件边界、摘要与细节。已有失败恢复与阶段缓存优先复用。 [记忆存储](../src/storage/memory_store.py) · [分层凝练](../src/storage/condense_two_layer.py)

1. 按工作、卡、原文可见区间、原文指纹、阶段与模型提示版本列账。先确认同一批的重复调用是否来自内容确实变化、断线恢复、输出校验失败或归拢重跑。
2. 只在原文范围、可见性与阶段契约都相同的情况下复用已校验的产物。新原文、旧块撤销、编辑、隔离标记改动都要进入失效判断。在原文锚点的职责不变时，让字段、范围和引用由现有机械逻辑生成。
3. 独立试验减少重复的摘要措辞以及按需展开细节。输出上限靠先测同一批内容的实际读数再调，设得过低导致截断和整批重凝会增加成本。保留足以支撑任务回溯的锚点、变更原因、人工裁定和未完事项。

**通过条件。** 同一段原文连跑两次，再补一段原文、撤销一条、改变一个可见性标记。第一种复用有证据，后三种正确失效。按原文锚点抽查相同事实、先后顺序、证词和关键约束，验证可重建。报告调用次数、输出 token、截断重试和实际前进水位。主要回归 `test_condense_two_layer.py`、`test_condense_scope.py` 和 `test_memory_release_policy.py`。生产凝练仍由属主进程调度。

## 八 第七批 统一验收读数与交付方式

统计以任务为单位，关联工作、卡、回合、模型跳次、尝试号和路由。一次启动、评审调起、后台凝练、协议补救和自动重发分别可辨。首跳从远端回执取得缓存读、缓存写与未命中输入时分别记录；字段缺席保留未知。SIWC 总输入、DeepSeek 适配器扣缓存后的输入以及本机估算字节都要带原口径。调度成功、工具成功和任务完成分别核对。 [模型观测](../src/infra/observe.py) · [SIWC 用量](../src/model_gateway/llm_siwc/adapter.py) · [OpenAI 兼容用量](../src/model_gateway/llm_openai_compat/translate.py)

**施工方操作顺序**

1. 锁定一份改前快照及同一任务的预期：用户原话、来源、文档版本、所需权限、关键证据、应有的实际执行结果。
2. 走正常入口，使用隔离工作和受控模型或传输替身抓取适配器实际提交的请求。可重放原始模型输出验证工具及回执。统计模型跳次、真实出站次数、总字节及主要分区字节。提供方缓存命中由自然会话的端点回执补证。
3. 在同一份输入上应用本批改动。对比两个最终请求及接收方事实。先跑本批指定测试，再按改动面跑相邻回归。测试入口采用 `PYTHONPATH=tests python -m pytest tests/对应文件.py -q`。
4. 回报中提交改动文件、用例、改前改后读数、可复查的日志或请求位置、用户可见差异、已知局限。若试点效果不确定，留好回退到既有装配或路由的条件。5700 未生效的改动单独请示，整组启停遵循项目规则。

| 每批回报字段 | 验收方要核对的内容 |
| --- | --- |
| 样本和范围 | 卡号、原回合、任务类型、模型路由、材料版本、是否使用替身。 |
| 成本证据 | 请求次数、首跳和总输入字节、本轮工具区字节、可取得的模型输入和输出及缓存口径。 |
| 正确性证据 | 用户要求、权限、任务需要的事实、工具调用配对、原文锚点和接收方状态。 |
| 域外影响 | 当前回合和下一轮、空数据、插话、停止、失败、授权拒绝与状态更新。 |

和其他 Agent 做可比试验时，选择同一模型路由、同一任务材料和同一验收判据，按一次成功交付的全部请求对照。现有数据可以证明重复输入和重复启动的结构问题，也能独立验证第一批节省量。
