---

## 一、背景（为什么做）

系统现有两种连线：**父子线**（卡上 `parent` 派生，画布分组 `parent-child`）与**通信线**
（卡上 `relations` 字段，`read_linked` / `send_card_message` 沿它寻址，画布分组 `relations`）。

「通信线」这个名字叫 `relations` 是**沿用老字段名**、名不副实——`relations` 表达的是「关系」，
而它实际承担的是「通信」。本次把名字理顺，并新增真正表达「关系」的第三种线。

---

## 二、已定口径（用户裁定 + 已认可建议，施工不得偏离）

**用户裁定（违反即作废）**

1. **命名腾挪**：`relations` 这个名字从通信线收回，**归第三种线（依赖关联线）**；通信线让名。
2. 新线不单是关系表达，还要**记录内容**——"依赖什么、关联什么、关联哪些"。
3. 新线**不参与通信**：不能沿它 `read_linked` / `send_card_message`。
4. 新线**双向**：A 发起，B 也要知道。
5. 新线由**模型侧工具**建。
6. 新线**注入上下文**，位置**不能太靠上**。
7. **画布展示本次不做**。

**已认可建议（2026-10-16「就这么定」）**

8. 通信线新名＝ **`links`**。
9. 新线注入区 order＝ **250**（200 记忆之后、300 对话历史之前）。
10. 工具形态＝**新开一对** `link_rel` / `unlink_rel`（不扩展 `link_cards`）。
11. 方向＝**保留方向**（source 发起、target 被指）**+ 双向可见**（不做纯无向）。
12. 通信线现有 type（`先后`/`关联`/`锚定`/`兑现`）**原样保留**在 `links` 里；与新线
    `kind=关联` 的重名**不影响**——两者在不同字段，程序上不冲突。

## 六、分块（3 笔，逻辑内聚）

### 块 1 · 存储层：改名 + 新列 + 迁移

**任务**

- `card_db.py`：
  - 新造幂等改名机制 **`_COLUMN_RENAMES: tuple[tuple[str,str,str], ...]`**（表名, 旧列, 新列），
    在 `_ensure_schema` 里**排在 `_ensure_columns` 之前**执行：
    `PRAGMA table_info(cards)` → 若**有旧列 `relations` 且无新列 `links`** → `ALTER TABLE cards RENAME COLUMN relations TO links`；否则跳过（幂等）。
  - `_COLUMN_RENAMES = (("cards", "relations", "links"),)`。
  - `_COLUMN_UPGRADES` **追加** `("cards", "relations", "relations TEXT")`（给老库补新列；新库走 `_SCHEMA` 已有则跳过）。
  - `_CARD_COLUMNS`：`"relations"` → `"links", "relations"`（两列并存）。
  - `_JSON_COLUMNS` / `_JSON_LIST_COLUMNS`：**加入 `links`**（保留 `relations`）。
  - `_SCHEMA`：`relations TEXT,` → `links TEXT,` ＋ `relations TEXT,`。
- `card_store.py`：
  - FM 渲染（:340）`relations: {...}` → `links: {...}`。
  - `_UPDATABLE_META_KEYS`：`"relations"` → `"links", "relations"`。
  - 建卡默认（:846）`"relations": []` → `"links": [], "relations": []`。
  - `_append_relation`（:1188，系统派生「锚定」用）：写 `links`（**跟旧数据走**，语义不变）。
  - 新增新线写入辅助（或直接由 `card_tools` 走 `update_card({"relations": ...})`，二者取一，回报取舍）。
- `canvas_store.py`：SELECT 与投影里 `relations` → `links`（画布本期只用通信线）。

**硬判据**

1. 老库跑一次连接后：`PRAGMA table_info(cards)` 同时含 `links` 与 `relations`；`links` 里**保有原 relations 的旧数据**（抽查一个已知有连线的 work，条目数一致）。
2. 新库：建库即含 `links`＋`relations` 两列；表结构与老库升级后**一致**（逐列比对）。
3. 幂等：对同一库重复跑 `_ensure_schema` 多次，结构与数据零变化。
4. 全库扫描：改前备份存在；改后任一 work 的 `relations`（新列）全为空、`links` 内容与改前 `relations` 逐字节一致。
5. `card_store.read_card` 返回的 meta 含 `links` 与 `relations` 两键。

**交付**：`card_db.py` + `card_store.py` + `canvas_store.py` + 迁移备份记录。

### 块 2 · 工具层：旧线改名 + 新线工具

**任务**

- `card_tools.py`：
  - 旧线改名：`_h_link_cards` / `_h_unlink_cards` / `_h_read_linked`（沿边寻址，:806）/
    `read_card` 返回 / `_collect_card_meta` —— 一律 `relations` → `links`。
  - `read_card` 返回结构**新增** `relations` 键（新线），与 `links`（通信线）并列。
  - 新增工具 **`link_rel(target_id, kind, detail)`**：
    - `kind ∈ ("依赖", "关联")`（新常量 `MODEL_DEP_KINDS`）；`detail` 为自由文本（必填，写清"依赖/关联什么"）。
    - 校验：target 存在、≠自身、`kind` 合法；权限走 `policy.SWITCH_LINK`（树类收紧同款：只能连自己子树内的卡）。
    - 幂等：同 `(target, kind)` 已存在则不重复追加（detail 变化则更新）。
    - 写入卡上 **`relations`**（新字段），条目 `{target, kind, detail}`。
  - 新增工具 **`unlink_rel(target_id, kind?)`**：从 `relations` 移除；`kind` 缺省＝移除全部指向该 target 的条目；权限走 `policy.SWITCH_UNLINK`。
  - `TOOL_SWITCH` 加两行；`TOOL_TABLE_VERSION` → **`tools-tc-7`**；工具面过滤按现有四级机制自动生效。
- `routes.py`：`ALLOWED_UPDATE_KEYS` 加 `"links"`。
- `prompts.py`：BASE_PROMPT 加两个新工具说明；把「卡与卡通过 parent（父子）与 relations（连线）」
  改为「parent（父子）、links（通信线）与 relations（依赖关联线）」；工具清单里 `link_cards`/`unlink_cards`
  的字段口径同步；版本 → **`t22-1`**。

**硬判据**

1. `grep -c '": ToolDef(' card_tools.py` == **21**；`TOOL_TABLE_VERSION=="tools-tc-7"`；`BASE_PROMPT_VERSION=="t22-1"`。
2. `link_rel` 建线后：卡上 `relations` 增一条 `{target,kind,detail}`；`links` **零变化**。
3. **隔离判据（核心）**：建了依赖线（`relations`）但没建通信线（`links`）的两张卡之间，
   `read_linked` 返回 **「无通信线」**；`send_card_message` 同样不可达。
4. `unlink_rel` 缺省解除全部指向该 target 的条目；指定 `kind` 只解对应条目。
5. 越权：`link_rel` 连子树外的卡 → denied；未授 `link` 的卡工具面**看不到** `link_rel`。
6. `read_card` 返回同时含 `links` 与 `relations` 两键。

**交付**：`card_tools.py` + `routes.py` + `prompts.py` + 测试。
