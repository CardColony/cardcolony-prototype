# 评审驱动 · harness 化重做（方案）

> 日期：2026-10-31
> 依据：用户口径（原话逐字引在 §二）＋ 现状取证（HEAD `35c86c5` ＋ 当前工作区）
> 范围：**只出方案，不动代码**。施工由用户或另一条线执行。

---

## 〇、一句话

把评审从「**代码里写判断 + 两套循环并存**」改成「**一次唤醒＝一个席位的普通卡回合，其余全部交给 harness 按事件驱动**」。

---

## 一、现状：为什么现在这套「不能用」

### 1.1 驱动逻辑不在 harness 里，在评审代码里

`harness` 的 `continue` 手段（`src/infra/harness.py:271-326`）本该是「原状态再调起一次」，
但它的实现是**转手调用评审代码**：

```python
# src/infra/harness.py:305-306
from ..api import review_runner
r = await review_runner.run_once(work_id, target)
```

⇒ harness 只当了转发器。**决定「下一步做什么」的仍然是 `review_runner` 里的 Python 分支。**

### 1.2 两套循环并存

| 循环 | 位置 | 形态 |
|---|---|---|
| `run_round` → `_round_loop` | `review_runner.py:236-264` / `442-521` | `while True` 跑完整轮：无墙钟、无次数上限、自己决定下一步 |
| `run_once` → `_run_step` | `review_runner.py:279-323` / `326-391` | 跑一步就返回，流程存续交给 harness 的 continue |

两套都在用（旧的那套还挂在 `main.py` 启动续跑与日志里的 `run_round()` task 上）。
**一个机制两套实现，本身就是「越改越错」的来源。**

### 1.3 判断逻辑堆在 `_run_step`

```python
# src/api/review_runner.py:341-391
st = await review_store.state_of(...)      # ① 还有批次吗
if st_now.get("all_passed"):               # ② 全员通过？→ 去定稿
    return await _step_promote(...)
todo = [m for m in members if m not in spoken]   # ③ 还有谁没发言？
if todo: ... speak(todo[0]) ...
rev = await revise(...)                    # ④ 全员发完 → 叫子卡改一次稿
```

这四条分支就是「做一堆判断逻辑」的落点。它们的每一条都**应该由 harness 的事件判据表达**。

### 1.4 `reject` 是空操作（机制失效，不是风格问题）

```python
# src/api/card_tools.py:4567-4580  _h_reject
batch = ...
if not batch: return err("validation", "当前没有进行中的批次")
await _render_review_status(work_id, rid)
return ok_({"review_card_id": rid, "role": current_id, "verdict": "reject"})
```

**不写库、不撤票、不校验成员。** 数据实证（`works/work_027/cards.db` 只读）：

```
batch_id=rv_d06189ef22  role_id=fn_004  draft_ver=5   ts=16:29:57  revoked=0
```

`fn_004` 在 16:29:57 表态通过，16:58 又调 `reject` —— **那一票仍然是 `revoked=0`、仍然计入 `passed`**。
⇒ 「说过不通过的人仍算通过」，且 `all_passed` 可能被误判为真。

### 1.5 八条原始约束的现状

原始口径见 `notes/需求-伴生评审卡-20261026.md:48-58`。

| # | 约束 | 现状 | 落点 |

## 二、目标规格（用户口径逐字 → 落点）

> 「1，按照评审席位，一次调一个评审席位起来评审，算作一轮」
> 「2，模型 done，才判断它是否做了通过不通过操作，如果没做，就再调起它，提示它没完成评审，如果做了，就调起下一个评审席位」
> 「3，通过后的评审席位，再也不调起」
> 「4，所有评审跑完，就调起本卡角色来回应」
> 「5，而且它应该是回应，而不是必须改，它的回应要留在上下文里，因为回应是用来回应不通过模型的 / 你也要告诉它，它可以不改，它可以拒绝，但它要说明理由 / 它拒绝的话，可以调工具完成它的工作 / 系统就再调起没评审的评审出来」
> 「6，所以这会形成互相回应，最终达成一致（评审通过或正卡修改）」
> 「所有的驱动整个流程走到底的，应该都用 harness 这套机制去实现」

| # | 规格 | 机制落点 | 谁驱动 |
|---|---|---|---|
| 1 | 一次调一个席位＝一轮 | 评审卡跑一次**普通卡回合**（`_run_card_turn` → `message_runner.step`），**复用卡片已有的循环内核** | 评审卡（**不自写循环**） |
| 2 | done 后才判断有没有通过操作 | 回合结束读 `RunState.tool_events`（`message_runner.py:75-199`），得 `voted` 事实 | 评审域**读事实** |
| 2 | 判据本身 | `review_turn_done` 事件自带 `voted` 字段；harness 用 `{"field":"trigger_data.voted","cmp":"eq","value":false}` 判 | **harness** |
| 2b | 没做 → 再调起它、提示没完成 | 规则 R1：`target=self`, `mode=continue`, 消息＝「你没完成评审」 | **harness** |
| 2c | 做了 → 调起下一个席位 | 规则 R2：`target=self`, `mode=continue`；下一轮从状态读「下一个还没表态的」 | **harness 唤醒** ＋ 状态读取 |
| 3 | 通过后的席位不再调起 | 候选席位 ＝ `members − 已通过`（集合运算，非 if 分支） | 状态 |
| 4 | 全部评审跑完 → 调起正卡回应 | 落 `review_all_voted` → 规则 R3：`target=event:target`（正卡）, `mode=message` ＋ 唤醒 | **harness** |
| 5 | 回应不是必须改、可拒绝但要说明理由 | 正卡走**普通卡回合**；提示词明确「可以不改、可以拒绝，但必须说明理由」，可调工具改稿 | 正卡普通回合 |
| 5b | 回应留在上下文 | 正卡发言落在**正卡自己的会话** ⇒ 评审席下一轮的 prior（子卡 history 区）自动看得到 | 现有机制，零改动 |
| 5c | 再调起没评审的 | 规则 R4：正卡有实质回应 → 回评审卡继续；**R5：零信息则停，等人** | **harness** |
| 6 | 互相回应直到一致 | 全员 approve ⇒ 正卡调 `promote_draft` 写正稿 ⇒ 收口 | 现有机制 |
| 6b | **不会有空转** | 出口 ＝ **这一轮有没有信息增量**，不是轮次上限（详见 §3.7） | **harness 判据** |

**关键设计取舍：唤醒目标只有两个。**

- **评审卡**（`target=self`）：它这一轮扮演「当前该发言的席位」。
- **正卡**（`target=event:target`）：它这一轮扮演「被评方回应」。

「席位」是**身份**不是卡（职能卡 `fn_004` 不在 `cards` 表，`harness.resolve_targets` 读不到），
所以席位不能当唤醒目标 —— 唤醒评审卡、让它扮演席位，是唯一不侵入回合内核的做法。

**「下一位是谁」是状态读取，不是流程控制**：
候选席位 ＝ `members − 已通过 − 本轮已表态`，纯集合运算，代码里一行 `if` 都不用写。

## 三、机制设计

### 3.1 复用卡片已有的回合内核（不新写循环）

```python
# src/api/review_runner.py:846-870（现状，已经是对的）
async def _run_card_turn(work_id, card_id, *, system_prompt, user_prompt, prior, tools) -> str:
    state = _mr.RunState(work_id=work_id, card_id=card_id, content=user_prompt)
    ...
    while True:
        outcome = await _mr.step(state)          # ← 卡片已有的回合内核
        if getattr(outcome, "kind", "") in ("deliver", "error"):
            break
    return str(state.final_reply or "")
```

改法：**让它把 `state.tool_events` 一并返回**（或由调用方直接读），
这样「这一轮有没有调 approve/reject」＝**读事实**，不需要任何自造循环。

```python
# 目标形态
async def _run_card_turn(...) -> tuple[str, list[dict]]:
    ...
    return str(state.final_reply or ""), list(state.tool_events or [])
```

### 3.2 新增事件（`config/event_catalog.json`）

| 事件 | 触发时机 | `data` 的 part | triggerable |
|---|---|---|---|
| `review_turn_done` | 一个席位的回合结束（模型 done） | `batch`, `seat`, `voted`, `verdict`, `target` | ✅ |
| `review_all_voted` | 全部席位都表态过 | `batch`, `target`, `members`, `pending` | ✅ |
| `review_target_replied` | 正卡的回应回合结束 | `batch`, `target`, `review_card_id`, `reply_len`, `changed` | ✅ |

> `reply_len` ＝ 本轮正卡实质发言字数；`changed` ＝ 有没有调工具改稿。
> 这两个字段是 §3.7 出口判据的**唯一输入**。
> `review_all_voted` **不带** opinions —— 意见走上下文（§3.6），不走事件数据。

登记格式照抄现有 `review_round_done`（`config/event_catalog.json`，`fields.part` 必带零件是条件面唯一取数面）。

> ⚠️ `tool_result` 事件本身 `triggerable=false`（`event_catalog.json`），
> 所以**不能把它写进 `watch`**。本方案不在 `watch` 里用它 ——
> 「有没有表态」由 `review_turn_done.voted` 承担，判据落在事件自带字段上。

> **R4 的事件发在正卡上**（`card_id` ＝ 正卡），`scope.kind=card` ⇒ 本子挂在正卡上；
> 目标从事件数据取评审卡 id。这样「正卡说完话 ⇒ 评审继续」不需要评审域再插一脚。

### 3.4 为什么判据写 `field: trigger_data.*` 而不是 `event:` 节点

`harness_cond.eval_cond` 的 `field` 节点走 `get_path(ctx, field)`（`src/infra/harness_cond.py:326-329`），
而 `ctx` 里带 `trigger_data`（`src/infra/harness.py:75`）⇒ **判据直接落在触发事件自己的数据上**。

这一点很关键，因为评审卡**没有轮边界**：

- `turn_end` 事件只在 `src/api/routes.py:2817` 发，而评审回合走 `_run_card_turn`、**不经过 `_run_message`** ⇒ 评审卡上没有 `turn_end`；
- 轮窗口 `_turn_window` 的锚是 `run_start`（`src/infra/harness_cond.py:188-190`），且会**跳过触发事件自身**；
- ⇒ 用 `event:{types:[review_turn_done], where:{voted:false}}` 这种「在窗口里找同类事件」的写法，
  会因为触发事件被跳过而**永远判不成立**。

用 `field: trigger_data.voted` 就绕开了整个序列问题：**判据只看这一条事件自己说了什么。**

### 3.5 状态模型

`cards.review_state`（JSON 列）新增三个字段：

| 字段 | 含义 |
|---|---|
| `cursor` | 当前该发言的席位 id（空 ＝ 该找下一个了） |
| `round` | 轮次号（每「全员表态完 → 正卡回应完」进位一次） |
| `seats` | `{seat_id: {"verdict": "approve"\|"reject", "round": n, "at": ts}}` —— 席位表态留痕 |

`review_approvals` 表新增一列：

| 列 | 含义 |
|---|---|
| `verdict` | `'approve'` / `'reject'`（**取代**用「有没有行」表示通过的旧口径） |

> 同一 `(work_id, batch_id, role_id)` 主键 ＝ 同一席位同一批次只有一票，
> **后写的覆盖先写的** ⇒ 「先 approve 后 reject」自然变成「reject」，修掉 §1.4 那个 bug。

**候选席位算法**（集合运算，无分支）：

```python
members  = st["members"]
passed   = {seat for seat, v in st["seats"].items() if v["verdict"] == "approve"}
spoken   = set(st.get("spoken_this_round") or [])
candidates = [m for m in members if m not in passed and m not in spoken]
```

### 3.6 正卡的回应

- **走普通卡回合**（`message_runner.step`），不是专门的「改稿回合」——
  现有的 `revise()` / `_revise_inner()` / `_revise_tools()` / `_revise_system_prompt()` / `_revise_user_prompt()`
  那一整套（`review_runner.py:525-800` 一带）**整段删掉**，它的职责由普通回合承担。
- 提示词里明确写：
  - 评审意见原文（各席位的发言）；
  - **「你可以改，也可以不改——但必须说明理由」**；
  - 「要改就调工具完成它的工作」（正卡自己的工具面里就有 `edit_requirements` / `edit_status` 等）。

**正卡怎么拿到评审意见 —— 读评审卡的会话原文，不做摘要。**

复用 `_prior_messages`（`review_runner.py:1341-1383`）：它读评审卡自己的会话
（`_sid(review_id, batch)`），**本批次发言一句不截断地返回**（注释原文：「本批次有几句就带几句」），
连用户的发言（`actor=="human"`）都带。评审卡的会话**就是那个共享现场**。

⇒ 正卡回应轮的 prior ＝
- 正卡自己的 history 区（装配层给），**＋**
- **评审卡本批次发言原文**（`_prior_messages` 给）。

⇒ **零摘要、零信息丢失。** 席位那 3000–4500 字的意见原文直接进正卡的上下文。

**双向可见因此自然成立（零同步代码）**：

| 谁读谁 | 读的是 | 效果 |
|---|---|---|
| 评审席 → 正卡 | 子卡 history 区（＝正卡自己的会话，正卡的回应落在那里） | 评审席自动看得到正卡的回应 |
| 正卡 → 评审席 | 评审卡会话（本批次发言原文） | 正卡看得到每个席位的理由原文 |

### 3.7 出口判据：不是轮次上限，是「这一轮有没有信息」

**用户口径（2026-10-31）**：「只要你信息给对，上下文给对，我认为不可能会出现一直空转没有出口的情况。」

翻译成机械判据 —— **不设轮次上限、不设墙钟、不杀任务**，但**每轮必须有信息增量**：

| 情形 | 有无增量 | 处置 |
|---|---|---|
| 正卡改了草稿 | 有 | 继续评审还没通过的席位 |
| 正卡不改，但**说明了理由** | 有（席位看到新理由，可能被说服＝出口；或给出新的反对理由＝又是增量） | 继续 |
| 席位表态了（通过或不通过），理由在发言里 | 有 | 继续下一个还没表态的席位 |
| **正卡这一轮什么都没说**（没发言、没调工具） | **无** | **停，等人介入** |

⇒ `review_target_replied` 事件带 `reply_len`（本轮实质发言字数）与 `changed`（是否调了工具改稿）。
harness 判据：`{"field":"trigger_data.reply_len","cmp":"gt","value":0}` ⇒ 继续；
不成立 ⇒ **不投递任何东西**（这一轮白跑了，停在那里等人）。

**为什么这不是「人为上限」**：上限是「第 N 轮强制收口」，本判据是「**这一轮零信息 ⇒ 它不会再有信息**」。
两者性质不同：前者会把还在推进的评审砍断；后者只拦「原地重复」。

> 同理，席位若重复上一轮**一模一样**的理由，也是零增量 ——
> 但那属于「信息给不对」（模型在复读），不在本方案的机械判据里；
> 抓手在提示词（「理由要具体到哪一条不满足、要改成什么」）与 `review_charters.json` 的职责书。

### 3.8 收口

- 全员 approve ⇒ 落 `review_all_passed{need_promote:true}` → 现有规则
  `review_all_passed_need_promote`（`config/harness_policies.json`）继续负责叫正卡调 `promote_draft`。
- `promote_draft` 写完正稿 ⇒ `review_store.finalize` 收口（批次清空、正稿入 `verdict`）。
  **收口＝正稿写完**，不是全员通过那一刻（`review_store.py:461-468` 的既有铁则，保留）。

## 四、harness 只需要一处通用扩展

在 `src/infra/harness.py`，是**通用能力**（不是评审特判），
且 `ctx` 里已经带 `trigger_data`（`harness.py:75`），所以改动很小。

### 4.1 target 支持引用事件数据

```python
# src/infra/harness.py:187  resolve_targets(target, ctx)
elif target.startswith("event:"):
    path = target.split(":", 1)[1].strip()
    out = [str(get_path(ctx.get("trigger_data") or {}, path) or "")]
```

用途：目标卡 id 运行时才知道（正卡 id、评审卡 id 都在批次创建时确定）。
现存五种 target（`self`/`parent`/`ancestors`/`links`/`card:<id>`）都是静态的，这是唯一的缺口。

### 4.2 为什么**不需要**「消息里插事件内容」

原设计里 R3 的消息要带 `opinions`（评审意见），因此想加 `{event.<path>}` 占位符。
**但意见不该走消息、该走上下文** —— 走消息就意味着要**摘要**，摘要会丢信息
（席位那 3000–4500 字里真正有用的是「哪一条不满足、要改成什么」）。

改成：R3 的消息是**静态指令**（"评审已完成一轮，下面是各评审席位的意见"），
意见原文由 §3.6 的 prior 层带进去 ⇒ **零摘要、零信息丢失**，
**harness 少开一个口子**。

> 两代 harness 共用 `resolve_targets` / `render_message`
> （第二代 `policy_runner.py:102/108` 调的就是这两个）——**改一处两代都受益**。

## 九、风险与遗留

1. **在途两批的续跑**：`rv_d06189ef22` 的 fn_004「先 approve 后 reject」在旧口径下被记成 approve，
   迁移后按 `revoked=0` 反推仍是 approve ⇒ **与它后来的 reject 矛盾**。处置建议：
   这两批**作废重开**（`decide(action="close")` 或开新批次），别让历史票带进新机制。
2. **「正卡拒绝修改 ＋ 席位坚持 reject」的收敛性**：
   用户口径（2026-10-31）：「只要你信息给对，上下文给对，我认为不可能会出现一直空转没有出口的情况。」
   ⇒ 本方案的处置：**不设轮次上限、不设墙钟、不杀任务**；
   出口判据是「**这一轮有没有信息增量**」（§3.7）：正卡零发言 ⇒ 停，等人。
   **实现时必须保证两件「信息给对」的事**：
   ① 席位 reject 的理由必须落在**共享现场**（评审卡会话）里，不是只在工具参数里；
   ② 正卡的回应必须落在**正卡自己的会话**里（否则评审席看不到，闭环断）。
   这两件都是**落点问题**，不是新机制 —— 现有 `speak()`（评审卡会话）与普通回合（正卡会话）已经满足。
3. **每批次独立 session**：`review_runner._sid` 已改成 `card_124-rv_xxx`（工作区未生效，盘上仍是 `session_124.md`）。
   本方案沿用它 ——「旧批次的东西物理上进不来」比「批次守卫」判断可靠。
4. **`review_state` 变成多写者**：现在批次状态由 `review_store` 写、`card_tools` 渲染投影。
   加 `cursor`/`round`/`seats` 后仍是**同一份 JSON、同一批写点**，不引入第二个可写源。
5. **`site-packages` 里的流氓 `tests` 包**：`from tests.test_s4_seams import …` 在本机永远收集失败
   （`test_s5_verdicts` / `test_model_process_events` / `test_iter3_type_contract` 三个文件）。
   与本方案无关，但**每次全量回归都会撞上**，建议随本方案一并修（加 `tests/__init__.py` 或卸掉那个包）。
